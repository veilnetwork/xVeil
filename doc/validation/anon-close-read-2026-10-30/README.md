# Anonymous C stream close при незавершённом чтении — 2026-10-30

Базовая SDK `df6edab1`, исправление `34299cb6`. При разборе [последней физической серии](../family-send-stages-2026-10-30/README.md)
подтверждён отдельный дефект владения C-handle. Он воспроизведён независимо от
Android, реле и потерь. Связь с физическими файловыми ожиданиями пока не доказана.

## Дефект и исправление

`veil_anon_stream_read` получает собственный `Arc<VeilAnonStreamFfi>` перед
блокирующим чтением. Прежний `veil_anon_stream_close` только удалял token из
таблицы. Пока read удерживает этот Arc, объект и его writer остаются живы;
отсутствующий FIN может быть единственным событием, после которого peer закончит
ответ и разблокирует read. Получается замкнутое ожидание без неисправной сети.

Close теперь удаляет token, затем освобождает writer внутри ещё живого объекта.
Свободный mutex берётся через `try_lock`, без ожидания C-потока. Если writer
занят, один runtime task ждёт окончания его критической секции и освобождает
половину после неё. Удаление generational token допускает только одну такую
задачу на live close; повторный или NULL close остаётся бездействующим.

Закрытие command channel использует прежний graceful driver path: уже принятые
байты проходят перед FIN, RST не подменяет нормальное завершение. Reader не
удаляется под работающим C-вызовом и получает EOF от peer обычным образом.
`abort`, retry policy, wire/C ABI, криптография, mailbox и relay QoS не менялись.
Исправление не обещает немедленного EOF от молчащего peer и не обрывает текущий
write ради освобождения mutex.

## Регрессионное доказательство

Тест запускает реальный локальный IPC server/client для runtime FFI и настоящий
`OnionStream` driver поверх in-memory cell peer. Используются настоящие C write,
read и close. Peer подтверждает данные, но не даёт читающему C-вызову ни payload,
ни EOF до получения нашего FIN. Перед close проверено, что C read действительно
вошёл в reader mutex. Закрытие вызывается с другого OS-потока дважды.

| Сценарий | Прежний close | Исправленный close |
| --- | --- | --- |
| Реальный C read удерживает объект, writer свободен | FIN не приходит; read ждёт до явного test cleanup abort | FIN, чистый EOF, все 73 байта дошли, Arc освобождён |
| Тот же read и занятый writer | FIN также не приходит после освобождения writer | C close возвращается до освобождения mutex; 73 байта и добавленный writer-tail дошли перед FIN, EOF, Arc освобождён |

Во втором сценарии занятая writer critical section моделируется удержанием
того же native mutex и продолжением записи через его `OnionWriter`. Это не
квалификация всех backpressure-путей C write. Во всех случаях C read/close и
первоначальный C write настоящие. До assertions тест освобождает и join-ит
потоки, закрывает IPC и runtime; baseline не оставляет висящий worker.

Оба финальных теста упали на прежнем production-коде, затем прошли на исправлении.
Двухсекундные bounds — guards от deadlock/неподнявшегося fixture; скорость сети
ими не оценивается. Проверяется порядок событий: FIN должен прийти до внешнего
прерывания read, close должен вернуться до отпускания занятого writer. Числа:
[summary.json](summary.json).

Полный FFI suite: **328 unit passed, 2 ignored**; внутренний subprocess не
прибавлен, 5 ignored doctests отдельно. FFI flags: `--no-default-features
--features node-embedded,production-seeds,packet-tunnel`. Отдельно прошли **13**
проверок driver: `close_handoff` (5), `close_linger` (2), `queued_writes` (2),
`reset_backpressure` (4). Это выбранные integration suites, не повтор полного
stream-suite. FFI Clippy `--lib --tests -- -D warnings`, rustfmt и diff-check
прошли. Внешний target проверялся по mount/device до и во время сборок.

## Что это означает для xVeil и файловых пауз

Обычный `_VeilAnonReliableStream.close` в xVeil **уже вызывает `finish()` перед
`close()`**. Этот путь мог обходить найденное C-close ожидание. Поэтому исправление
контракта SDK нельзя объявлять причиной устранения 37-секундной физической
загрузки, восьмибайтовых хвостов, Windows one-way или прежнего «33%».

Дополнительный разбор предыдущих raw logs без нового запуска стенда разделил
RTO-наблюдения: три разных логических stream имели срезы `pending=8` при
запрошенном FIN и доходили до retry limit; один из этих же stream ранее имел
RTO на bulk-данных. Совпадение stream IDs использовано только приватно, в сводку
вынесены counts. Эти две стадии нельзя считать одним и тем же сетевым ожиданием.
Срез `pending=8, inflight=0` может быть снят после RTO rewind и сам по себе не
доказывает, что восемь байт не отправлялись.

Вопрос, дошли ли финальные DATA/FIN до peer и где потерялся ACK, остаётся открытым.
Нужна атрибуция фактических handoff/приёма этих cells; aggregate unknown counters
и совпадающие длительности этого не доказывают. Новых GUI, телефонных приложений
или реле в этом цикле не запускали/не меняли; исправление на устройства не
устанавливалось. Тестовые процессы завершены. Push/релиз не выполнялись.
