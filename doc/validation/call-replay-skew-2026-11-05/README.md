# Повтор завершённого звонка при рассинхронизации часов — 2026-11-05

База `adb01210`. Локальная правка, без push/релиза, изменения wire/ABI,
consent или mailbox собственным устройствам.

## Подтверждено

Приём offer допускает timestamp отправителя на 30 секунд впереди местных
часов. Finished-call cache жил только 90 секунд. Поэтому offer, принятый при
максимальном допустимом skew, после завершения вызова снова проходил приём
через 91–120 секунд: cache уже истёк, а возраст offer ещё не превышал 90 секунд.
Это самостоятельный дефект подавления повторов, а не доказанная причина
пользовательской недоставки вызовов ПК ↔ Android.

Четыре assertion-red на исходном CallService: горячее завершение/восстановленный
journal × прямой/аутентифицированный sibling-канал. Горячий сценарий сначала
доказывает, что исходный offer с будущим timestamp действительно звонит, затем
отклоняет вызов. Часы инъецируются в FSM; сетевых и wall-clock порогов нет.
Начальная ошибка имени метода в fixture была compile failure и в red не зачтена.

## Исправление и проверки

Finished-call evidence хранится на сумму offer max-age и skew allowance,
то есть 120 секунд. Размер cache, peer/call-ID ключ, восстановление истории,
проверка свежести и допустимая разница часов не меняются.

Все четыре сценария проходят. Повтор проверен на +91 с и ровно +120 с;
changes stream не содержит краткого ringing. Сразу после +120 с оригинальный
offer уже отсекается по возрасту, а новый call ID с актуальным timestamp звонит.
Все четыре положительных контроля свежего вызова проходят.

Серия CallService + cold/native history + realtime signaling: **306 passed**.
Контроль **806 passed / 39 файлов / без skip** с diagnostics и явно выбранной
проверенной HVS; прежний идентичный набор имел 802 теста. После локального
форматирования добавленного блока четыре теста повторены; analyzer двух файлов
чистый, diff check чистый. Первая попытка scoped-команды содержала несуществующий
путь теста: она не считается успешной серией, затем запущен корректный набор.

Это проверка FSM и существующей storage/inbox интеграции; отдельный физический
clock-skew или новый native process-прогон этой границы не выполнялись.
Произвольные скачки часов, отсутствие timestamp у старого offer и вытеснение
более чем 256 записей не объявлены решёнными этой правкой.

## Физическая подготовка

Актуальные Veil/HVS Android FFIs собраны на закреплённом Rust в отдельном
Cargo target с контролем внешнего mount. Изолированный debug APK с текущим
Dart запускается на телефоне, основное приложение и прежние QA-контейнеры
сохранены. Windows source ZIP проверен по SHA, закреплённый toolchain и
изолированная сборка нативных библиотек использованы для
[физической сигнализации Windows ↔ Android](../windows-android-signaling-2026-11-05/README.md).
Это не отдельная физическая проверка clock-skew.

Медиадвижок для этого signaling-only стенда намеренно заморожен на release pin.
Он **не совпадает с текущим C++ source digest**; symbol gate также указывает
два отсутствующих noise-suppression setter. Проверки не подавлялись. Ни этот
APK, ни будущий такой Windows stand не квалифицируют новые аудиоправки,
шумоподавление или слышимость. Перед их проверкой нужен актуальный движок.
