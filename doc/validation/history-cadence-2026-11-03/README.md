# Время durable-записи входит в интервал history replay

2026-11-03. Локальный цикл без push/релиза, установки на устройства,
обновления native pins или публичных реле.

## Подтверждённый механизм ожидания

После каждой полной порции `replayHistoryForAsk` ждал окончание `postBatch`,
затем всегда ждал ещё 150 мс, затем проверял свободное место у sibling.
`postDeviceEvents` уже завершает работу только после local commit и durable
replication admission (исправление `c09d3c6d`). Поэтому медленная запись и
постановка в Outbox сами замедляли производителя, а отдельная полная пауза
добавляла ещё время. Это не объяснение всех 46 секунд миграции и не её
единственный источник задержки.

На виртуальных часах baseline даёт 40+150=190 мс и 500+150=650 мс до room gate.
Проверки нового контракта падают на baseline при 150/500 мс: порция уже
запущена и committed, но room callback ещё не вызван. Предусловия запуска и
commit проверены явно. Начальная версия оснастки не могла продвигать gate
fake-HV, созданный вне fake-clock zone; она не засчитана как доказательство.
Исправленный тест заранее читает fixture-значения и создаёт futures внутри
виртуальной зоны. Остальные storage/group тесты используют прежние хранилища.

## Изменение и ограничения

Только для `postBatch` вместе с `awaitRoom` таймер минимального интервала
начинается перед durable append. После append ожидается остаток интервала,
потом тот же room gate. В модели 40-мс запись достигает room gate в 150 мс,
500-мс — в 500 мс. Gate по-прежнему может удерживать следующую порцию сколько
нужно. При отказе/исключении append таймер отменяется, следующие порции не
публикуются. Частичный последний batch имеет прежнюю семантику.

Host без backlog admission сохраняет trailing pause; одиночный `post` путь
не меняется. Не менялись размер порции 25, предел bulk API 64, backlog room
128, replication cap, ACK/ratchet/durable barriers, подписи, порядок событий
или правила слияния. Это не увеличение лимита Outbox и не accepted-view cache.
Оптимизация опирается на уже исправленную границу durable admission batch API;
её нельзя переносить на отправитель, завершающийся до постановки в очередь.

Проверены быстрый/медленный append, удержанный room, отсутствие admission,
отказ и исключение без оставшихся таймеров, порядок history/live, partial
refusal, отмена, attachments и bounded input. **502 passed, 3 skipped**,
analyzer чист.

## Native A/B/A

Серия выполняется со старым кодом, кандидатом и обратным старым контролем.
Каждая фаза создаёт 2000 исходных сообщений и начинает migration timer только
после linking; seed time не включается. Три процесса A/B/C, настоящие
Riverpod-провайдеры, worker/HV, native-подписи, изолированное loopback-реле.
CPU-профайлер выключен; storage census одинаков. SDK/CLI/FFI заморожены на
ранее проверенном `eb644a83`, HV одинаков. Это проверка Dart-изменения, не
последней SDK. Публичные seeds/discovery выключены.

Во всех фазах окончательные ID, порядок, source positions и terminal statuses
совпали. В B после первого полного количества один опрос ещё видел временно
иной порядок/позиции; следующий сошёлся. Количество поэтому не выдаётся за
готовность всей истории. Это известная промежуточная сходимость, не обещание
неизменного порядка на каждом шаге догрузки.

В этой серии B примерно на 4,7–4,8 с быстрее обоих контролей. Опрос раз в пять
секунд и один цикл A/B/A ограничивают точность; это наблюдение на одном
Mac/JIT/loopback, не универсальный процент ускорения и не Android/AOT
квалификация. Задержка всё ещё около 41,5 с и не объявляется устранённой.
Потенциальные 80 пауз по 150 мс нельзя целиком вычесть из общего времени:
порции, receiver apply, фоновые чтения и ожидания очередей перекрываются.

До/после каждой фазы сверены 1394 frozen-файла, native artifacts и чистота SDK.
A₁/A₂ совпадают по всему source manifest; в B отличается только
`lib/state/device_history_backfill.dart`. Итоговый кандидат восстановлен после
обратного контроля и отдельно сверён с источником проверенной B-фазы.
После каждой фазы проверены выход 18 собственных PIDs и освобождение 22/20/24
портов соответственно. Живых собственных процессов/слушателей нет,
временные runtime-контейнеры удалены. Raw-журналы, синтетические секреты,
адреса и correlation hashes не публиковались.

Следующая проверка: history-room в bridge перечисляет `otherDeviceIds`, а
sender использует `addressableOwnDevices`; на linked-источнике объявленный
transport-адрес master может отличаться от registry identity. `pendingFramesFor`
ищет точный peer-ключ Outbox. Это пока кандидат по коду, не воспроизведённый
новый дефект и не объяснение всех оставшихся задержек. Нужен поведенческий
тест самой проводки. Расширенная multi-device матрица, длительный offline,
физический mobile handover и остальные случаи сохраняют статус.
