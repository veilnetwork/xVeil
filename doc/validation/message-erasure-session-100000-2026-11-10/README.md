# Удаление истории не переживает смену backing space

## Подтверждённый дефект

Удаление сообщения, очистка чата и удаление старой истории читали исходные
строки, затем переписывали их внутренние log slots. Подготовка могла
приостановиться до commit. Вся операция не входила в набор принятых записей,
которые `close`, `open` и `eraseSpace` присоединяют перед заменой хранилища.
Продолжение старой операции могло получить новый `_as` и затереть строку
другой личности с тем же внутренним slot, хотя conversation и message ID
различались. Это воспроизведение storage API, не установленная причина
пользовательской жалобы или свидетельство потери реальных данных.

Три deterministic parent-red для delete/clear/prune проверяют точное тело
строки второй личности: вместо него получен `null`. Gate удерживает
подготовку вне scan gate; виртуальные часы не подменяют production storage.
Первый вариант prune-fixture не достигал нужного gate и не засчитан;
после исправления fixture все три падения относятся к потере строки.

## Исправление

`_withMessageErasure` регистрирует всю принятую операцию через `_trackLogWrite`,
включая подготовительные чтения. Обслуживание хранилища ждёт её завершения,
прежде чем заменить backing space или переиспользовать slots. Вложенные
записи уже принятой операции используют существующий accepted-write zone;
новые внешние запросы после fence отклоняются. Счётчик/epoch стирания
сохраняются, отказ операции освобождает барьер и возвращается вызывающему.

Форматы данных/пакетов, авторизация, revoke, cursor и durable ACK не менялись.
Sibling mailbox не добавлен. Изменение не оптимизирует длительную доставку.

## Проверки

Десять новых unit checks: три смены личности; delete/clear/prune при close
и erase с отказом позднего запроса; ошибка принятой операции с последующим
открытием другой личности. Related suite: **559 passed / 1 skipped**.
Пропущен явно включаемый native roster lifecycle probe, не объявлен пройденным.
Analyzer production-файла и двух новых тестов чист.

Native smoke на 512 строк использует настоящий worker-backed контейнер:
все три варианта сохраняют каждую строку второй личности и выполняют удаление
в первой. Первоначальный FakeAsync/native fixture завис до первого открытия,
был остановлен и не засчитан. Один код выхода 0 после SIGINT не считается
успехом: квалификация требует terminal test result и точные data assertions.

## Native на 100000

Контроль старого production-кода явно удерживает удаление первой личности,
дожидается открытия второй и только затем отпускает удаление. Получено
**99999/100000** точных уникальных строк: одна чужая строка затёрта.
Закрытие старого backing и открытие нового наблюдались до release gate.
Это negative control на опасный порядок, не performance A/B: исправленный
код принципиально не может завершить такое открытие до release.

Исправленный production-код прошёл все три сценария: **100000/100000**
точных уникальных строк для delete, clear и prune. Проверены ID, тела,
статусы, авторы, sequence/canonical positions и timestamps, затем повторно
открыта первая личность: её строка удалена и tombstone сохранён. Принятая
операция завершилась успешно; закрытие старого backing и открытие нового
до release не наблюдались. Все данные второй личности считаны после нового
открытия native-контейнера, без опоры на прежний in-memory fold.

Зафиксированы 1512 неизменных входных файлов и отдельный production variant.
SHA native-библиотеки сверена до запуска, её фактическое отображение в
`flutter_tester` проверено в каждом варианте. После negative control
восстановлен candidate с проверкой байтов. В обоих прогонах по три собственных
процесса завершились; один контрольный и три candidate runtime удалены.
Времена 25,47 и 67,74 с включают разные наборы сценариев/seed: это не
измерение ускорения. Кеш сохранил 92 файла / около 9,5 ГиБ, рост не обнаружен.
Сырые журналы, пути и process/mapping evidence остаются вне Git.

## Границы

Это Mac/JIT storage API с настоящим native worker, не end-to-end UI-переключение
и не Android/AOT-квалификация. Полная матрица revoke/split-brain/crash и
задержки догрузки не закрыты. Обход давних удалений при offline sibling
требует отдельной квалификации. Релиз и push в этом цикле не выполнялись.
