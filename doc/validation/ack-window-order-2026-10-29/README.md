# Запоздавший ACK и окно отправки — 2026-10-29

## Подтверждённый дефект и исправление

Veil `33eff379` исправляет применение устаревшего receive-window в
`veil-onion-stream::StreamEngine::on_ack`. Прежде `tx.rwnd = win` выполнялось
до проверки ACK: запоздавшее подтверждение могло заменить окно более свежего
кумулятивного ACK. Например, получатель уже освободил буфер и подтвердил новые
байты, но задержанная копия прежнего ACK с `win=0` снова останавливала новые
DATA. Когда неподтверждённых сегментов уже нет, продолжение ждёт persist-probe.
Обратный случай тоже неверен: старый ACK с открытым окном мог отменить более
новое нулевое окно и послать DATA в заполненный буфер.

Такое переупорядочивание допустимо на независимых обратных circuit и при
локальном backpressure. Это отдельный дефект протокольного движка, не вывод
о том, на каком реле задержался пакет в предыдущей физической серии.

Теперь сначала действует прежняя проверка верхней границы реально отправленных
байтов. Окно обновляется только при `ack >= snd_una` с прежним сравнением
циклических номеров. Старые SACK-подсказки всё ещё обрабатываются; ACK с той же
кумулятивной позицией сохраняет возможность обновить окно. Не менялись ARQ,
таймеры, congestion control, подписи, ratchet, C ABI, wire и политики mailbox.
Реле не узнаёт тип приложения и не получает новых правил приоритета.

Изначальный кандидат — прореживать скопившиеся локальные ACK — не реализован:
нельзя без отдельной проверки терять dup-ACK/SACK evidence для восстановления
потерь. Исправление ограничено применением окна на принимающей ACK стороне.
Wire v1 не позволяет этим сравнением различить возраст двух ACK с одинаковой
кумулятивной позицией; этот случай не объявляется исправленным. Piggyback-window
в DATA данной правкой также не изменён.

## Воспроизведение и проверки

В `tests/ack_window_order.rs` используются настоящие sans-I/O sender/receiver,
реальные handshake, DATA, чтение буфера и сформированные получателем ACK.
Никакая сеть, Android или экономия батареи для воспроизведения не нужны.

| Сценарий | Проверяемое поведение |
| --- | --- |
| Старый нулевой ACK после нового продвижения | Следующая DATA выходит сразу при очередном poll, без ожидания probe |
| Старый открытый ACK после нового нулевого | DATA остаётся заблокированной; настоящий equal-ACK с освобождённым окном возобновляет её |
| ACK ещё не отправленного байта с `win=0` | Отвергнутый ACK не закрывает рабочее окно |
| ACK ещё не отправленного байта с открытым окном | Отвергнутый ACK не открывает заполненное окно |
| Допустимые equal-ACK window updates | Без продвижения ACK окно может закрыться и снова открыться |

Первые три теста запущены на прежнем движке: **0 passed / 3 failed**.
Все fixture-проверки до ошибочного поведения прошли; ошибки — именно отсутствие
следующей DATA или её ошибочный выход. После правки эти тесты зелёные.
Пять итоговых сценариев включают переход через `u32::MAX`; два варианта
переупорядочивания проверены с RACK и без него. Числовых порогов времени нет.

Итог: **174 stream-теста прошли, ignored нет**; **326 FFI-тестов прошли,
2 ignored**, с `--no-default-features` и
`node-embedded,production-seeds,packet-tunnel`. Дочерний subprocess не прибавлен
к основному счёту. Clippy stream `--lib --tests -D warnings` прошёл.

## Границы атрибуции прошлой серии

В сохранённых driver-срезах предыдущего раунда (516 Mac / 520 Android)
нулевое окно не наблюдалось. Среди `Established`-срезов (516/519) минимальные
зарегистрированные окна — 8 287 383 / 8 303 382 байта. Ещё один Android-срез
с окном 1982 байта относится к handshake, а не к передаче установленного потока.
Срезы относятся к разным stream и не являются полным журналом каждого ACK.
Поэтому дефект выше **не объявляется
причиной** прежней паузы 15,6 с и остановки на 33%.

Дополнительно из прежних endpoint-трасс извлечено ожидание локального
recoverable-source: до 90/6 мс Mac/Android; максимальное зарегистрированное
`outbox_to_transport_max_us` — 203 085/204 924 мкс. Это локальные наблюдения
данного окна, не per-hop RTT и не доказательство отсутствия иных задержек.

У гипотезы «identity resolve → miss → device resolve» есть альтернативное
объяснение: `warmPeer` запускает `warmStreamPeer` через `unawaited`, нативный
прогрев создаёт отдельную задачу, а opening-map индексируется адресом назначения.
В то же время content pull вызывает `openStream(streamTargetFor(holder, cid))`,
где при наличии device-hint уже выбран адрес устройства. Пять файлов этой
проводки совпадают с замороженным frontend `f389116a` физического стенда.
Это не доказывает, что все десять identity misses принадлежат прогреву; но
само наличие miss ещё не доказывает последовательный fallback скачивания.
Общая нагрузка DHT и иные общие ресурсы тоже могут влиять на параллельные задачи.

## Физическая квалификация

Release FFI Mac arm64 / Android arm64-v8a собраны из чистого `33eff379` с
обычными production-features, без native test hooks/test-low-difficulty.
Внешняя ФС target проверялась до сборок и каждые 0,5 с в процессе; не пропадала.
Frontend — прежний `f389116a`: Mac debug/JIT и Android AOT profile. Заменён
только FFI; прочие APK entries, debug signing certificate, Mac kernel/media/HV
сохранены. Это проверка native-правки, не всей текущей Dart/AOT сборки.

Две разные личности на Mac/Android; третий связанный Mac остаётся offline.
Контактный P2P временно запрещён, файлы передаются через circuit stream.
Штатный Bulk active-limit Mac — 2. Пять файлов по 3 145 979 байт в каждом
направлении, с новыми случайными байтами и без локальной копии у получателя.
Все десять загрузок завершились с совпавшим SHA-256. Камера, звук и звонки
не запускались. Debug-summary 500 мс и существующий `rt_trace` включены на
время серии; контролируемого A/B с одинаковыми путями и условиями нет.

В установленных stream драйвер зарегистрировал минимальное окно
8 265 648 / 8 263 742 байта Mac/Android, нулевого окна снова не наблюдалось.

Новые журналы реле за это окно не снимались; прежние 49 нулевых relay-shed
срезов на него не распространяются.

Для stage-анализа использован один основной журнал на процесс: 89 записей
Mac и 129 Android. Дополнительные 89 Mac-записей — точная копия, повторно
не суммируются; дополнительный Android-файл пуст.

независимо. Исходный QA APK восстановлен со сверкой полного хеша; основное
приложение не изменялось. Настройки контакта, `rt_trace` и debug-property
