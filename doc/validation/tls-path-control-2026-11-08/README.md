# NETCALL-01: TLS и одновременный TCP/TLS-контроль

**Уточнение после TCP_INFO-контроля:** независимый измеритель и серверы
использовали другие MSS/send-buffer/not-sent settings, чем Veil. Его
результаты не квалифицируют TLS или TCP с профилем сокетов приложения;
[различия проверены по коду](../tcpinfo-path-control-2026-11-08/README.md).

**Подтверждено:** TLS не устраняет секундные паузы во всех проверенных
условиях. Отдельная TLS-серия была бы обнадёживающей, но одновременный
TCP/TLS-контроль воспроизвёл паузы в обоих транспортах. Product-код,
транспортные настройки xVeil и SDK не менялись; **NETCALL-01 открыт**.

Предыдущий [TCP/UDP-контроль без Veil](../native-path-control-2026-11-08/README.md)
уже воспроизвёл секундные задержки на этом Poco и двух серверных адресах.
Здесь проверялся конкретный кандидат обхода: TLS поверх TCP.

## Измеритель и предварительные проверки

Отдельный native C executable под UID shell, без SDK, контейнеров и аудио.
Полезная нагрузка каждого кадра — 512 Б синтетических данных, включая
случайный тестовый token, sequence и timestamp; содержимое echo проверяется
целиком. Новые кадры создаются каждые 50 мс. RTT измеряется одним клиентом.
Сохраняются producer cadence, local write wait и время приёма каждого echo.

TLS подключается через системный libcurl CONNECT_ONLY, затем используются
его native send/recv. Android — BoringSSL, Mac smoke — SecureTransport.
Проверка сертификата и имени включена; временный сертификат явно доверен
только измерителем, proxy отключён. Это не замена или изменение существующей
аутентификации узлов Veil.

Оба варианта измерителя — два TLS-канала и четыре одновременных TCP/TLS-канала —
прошли loopback: все кадры возвращаются, испорченный CA-файл и недоверенный
сертификат отвергаются. Искусственная задержка 1100 мс обнаруживается при
регулярной генерации кадров; held receive gaps 1152–1163 мс. Локальные
серверы завершены, тестовые порты освобождены. Перед каждой физической серией
Mac smoke проверил сертификат и 40/40 echoes каждого удалённого канала.

## Сначала только TLS

Заранее заданный порядок: Wi-Fi 45 с → Cellular 60 с → Cellular 60 с →
Wi-Fi 45 с. По одному TLS-каналу к каждому серверу. Новые соединения
открываются после подтверждения target network / VALIDATED.

| Фаза | Sent / echoes на каждом канале | Median RTT R1 / R2 | Max RTT R1 / R2 | Max receive gap R1 / R2 |
|---|---|---:|---:|---:|
| Wi-Fi-1 | 900 / 900 | 114 / 51 мс | 279 / 56 мс | 214 / 55 мс |
| Cellular-1 | 1200 / 1200 | 157 / 102 мс | 486 / 431 мс | 358 / 361 мс |
| Cellular-2 | 1200 / 1200 | 160 / 105 мс | 476 / 417 мс | 356 / 368 мс |
| Wi-Fi-2 | 900 / 900 | 115 / 53 мс | 335 / 109 мс | 270 / 103 мс |

Все 8400 кадров вернулись, включая 4800 мобильных; мобильных RTT >1 с нет.
Max producer gap <57 мс, local write wait <3 мс. Сравнение с прежними
TCP-результатами до 3,93 с **не является причинным A/B**: измерения сделаны
в другое время, с другими соединениями и меняющимся состоянием сети.

## Затем TCP и TLS одновременно

Один измеритель создаёт кадры одним общим tick для четырёх соединений:
TCP и TLS к R1, TCP и TLS к R2. На каждом адресе один и тот же тестовый
порт; временный сервер различает TLS handshake и открытый TCP, затем
обслуживает одинаковые 512-байтовые кадры. Для raw token исключён конфликт
с первым байтом TLS handshake. Контейнеры и xVeil по-прежнему не запускаются.

Порядок: Wi-Fi 30 с → Cellular 60 с → Cellular 60 с. Каждый мобильный
канал получил 1200/1200 echoes в обеих фазах. Ниже максимумы RTT / receive gap:

| Фаза | TCP R1 | TCP R2 | TLS R1 | TLS R2 |
|---|---:|---:|---:|---:|
| Wi-Fi | 122 / 57 мс | 58 / 54 мс | 115 / 53 мс | 59 / 53 мс |
| Cellular-1 | 1487 / 1173 мс | 1253 / 1209 мс | 1506 / 1172 мс | 4309 / 2754 мс |
| Cellular-2 | 1430 / 1210 мс | 1283 / 1222 мс | 1446 / 1202 мс | 1274 / 1211 мс |

Все 12000 кадров вернулись; среди 9600 мобильных echoes 690 имеют RTT >1 с.
Пропусков, повреждённых кадров, дублей, skipped work, missed ticks или
I/O errors нет. Max producer gap ≤60,5 мс, local write wait ≤6,2 мс.
Следовательно, секундные gaps не объясняются секундной остановкой генератора
в используемом clock domain или таким же ожиданием локальной записи.

Этот тест **удваивает поданную полезную нагрузку** относительно двухканальной
серии: 40 вместо 20 КиБ/с в каждом направлении, без учёта TCP/IP/TLS overhead.
По нему нельзя заключать, что TLS сам замедляет сеть, что шифрование является
причиной или что разница обусловлена только классификацией протокола.
Количество соединений тоже различается. Результат отвергает утверждение
«TLS автоматически убирает наблюдаемый класс пауз», но не все варианты
TLS-настроек и нагрузок.

## Что добавляют серверные записи

Порядок и sets sequence каждого валидного server session сверены с client
send records: Mac smoke и все phone phases, отдельно для каждого протокола.
Connection IDs не предполагаются последовательными; постороннее соединение
не считается частью теста без правильного token.

В мобильных фазах максимальные **server application arrival gaps**:

- TCP R1/R2: 1176 / 1176 мс и 1179 / 1179 мс;
- TLS R1/R2: 1169 / 2745 мс и 1171 / 1171 мс.

Между генерацией соответствующих соседних кадров на телефоне было всего
49–50 мс. Это разности времени внутри каждого хоста, без вычитания
несинхронизированных clocks. Wi-Fi arrival gaps на всех каналах ≤53 мс.
Записи сделаны перед echo; это наблюдение приложения сервера, **не NIC capture**
и не доказательство конкретного сетевого хопа или one-way latency.

Дополнительное описательное сопоставление: для 33 raw TCP receive gaps
длиной ≥750 мс проверены средние 80% каждого интервала на соответствующем
TLS-канале того же адреса. В 32 интервалах TLS echoes также отсутствуют;
в одном есть единственный echo с RTT 998 мс. Порог выбран для анализа,
а не как заранее заданный pass/fail gate. Это не независимая выборка 33
сбоев, но оно не подтверждает постоянно здоровый TLS-spare во время TCP-пауз.

## Границы и следующий шаг

22 + 15 environment snapshots: Awake, питание подключено, Doze/Light Doze
ACTIVE, target network VALIDATED. CLOCK_MONOTONIC и эти срезы не заменяют
непрерывного наблюдения suspend. Это не screen-off/OEM test, не проверка
приложения под его UID и не сохранение одного соединения во время handover:
перед каждой фазой открываются новые sockets.

**Исправление продукта по результатам не внесено.** Увеличение аудиоокна или
переключение default transport на TLS пока не обоснованы. Следующий контроль —
зависимость пауз от предложенной нагрузки при неизменном числе соединений;
отдельно сохраняется задача квалификации настоящего звонка и handover.
Конкретный виновник между ядром/модемом/промежуточной сетью не установлен;
виновность оператора и причина всех исторических NETCALL-01 не заявляются.

Все native processes завершены; собственные directory/binary/token/CA
с телефона удалены по owner marker. Исходные Wi-Fi/data/stay-on и validated
сеть восстановлены. APK обоих приложений и QA root container повторно
сверены по SHA; контейнеры не открывались. Обе пары временных server units
и root credentials удалены, порты свободны. Production PID/restarts/binary/
config сверены независимо. Frozen source/binary/runtime hashes не изменились.
Raw records, сертификаты, токены и operational metadata остаются private.
Коммит без подписи; push/релиза нет.
