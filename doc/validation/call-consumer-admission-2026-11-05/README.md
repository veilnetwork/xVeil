# Сигнал звонка подтверждается при подключённом consumer — 2026-11-05

База `b2b9697c`. Локальная работа без push/релиза, APK, engine pins,
изменений сидов, Rust/native ABI и mailbox для своих устройств.

## Подтверждённый дефект

На обоих входящих каналах call signal получал ACK и frame-seen запись до
проверки наличия onCallSignal. При отсутствии обработчика callback не
выполнялся; после подключения CallService повтор того же frame ID попадал
в duplicate и тоже не выполнялся. Sender мог уже удалить durable копию.
Это реальный consumer-readiness механизм потери сигнализации, не доказанная
причина исходного репорта Windows ↔ Android.

Два assertion-red: ordinary/realtime, неизменный ID и handler, подключённый
между первой копией и повтором. Ожидаемый callback 1, фактический 0. Финальная
версия тех же fixture дополнительно проверяет отсутствие раннего ACK, carrier
onDeclined, duplicate по другому каналу и duplicate после detach. Она повторно
проверена на трёх прежних production files из HEAD: 2 assertion-red, затем
исходники кандидата восстановлены побайтово и 2 green. Порогов времени нет.

## Изменение

Ordinary lane откладывает ACK/dedup call signals до общей точки передачи
consumer. Realtime использует ту же точку. Она сначала снимает snapshot
обработчика; для новой копии при его отсутствии не создаёт seen ID, не
подтверждает доставку и сообщает carrier о локальном отказе. Уже переданная
копия всё ещё подтверждается как duplicate, даже если consumer позднее
отключился. При доступном обработчике dedup/ACK и синхронный handoff не разделены
await; ACK не блокирует callback. Нового буфера, таймера или mailbox пути нет.

Существующие provenance/consent/active-call-device/ending gates сохранены.
P2P endpoint и остальные durable кадры продолжают прежний путь. Бросающий
исключение consumer и завершение асинхронных операций самого CallService этой
правкой не переопределялись.

## Process A/B/C

Три OS-процесса на одном Mac, A/B одной личности и C другой, anonymous/onion
режим, три изолированных loopback relay. Дополнительного C ↔ B join нет.
Каждый положительный сценарий проверяет точный новый call ID:

1. C звонит обоим A/B; отмена C завершает вызов у всех.
2. B перезапущен; C снова звонит A/B; отклонение B доходит до A/C.
3. A остановлен; C звонит B; отклонение B доходит до C.
4. B звонит C при выключенном A; отклонение C доходит до B.
5. A/B выключены; C начинает набор; B запускается и принимает тот же вызов.

Все пять сценариев прошли. Terminal oracle использует свежий callEnded
счётчик и точный reason в обычной анонимной диагностике, отсутствие live slot
и одну durable journal row нужного call ID/outcome. Null slot не выдаётся за
доказательство завершения нужного вызова. Первый прогон ошибочно требовал
сохранённый ended slot, хотя CallService намеренно очищает его сразу; этот
fixture failure не является product-дефектом и не зачтён как квалификация.

Fixture-only XVEIL_E2E_DIAGNOSTICS включает штатный compile flag у workers;
приватный file control читает normal allowlisted snapshot, teardown сохраняет
его после остановки сервиса. Не добавлено production HTTP API. Шесть реальных
report snapshots прошли независимую структурную проверку: только фиксированные
schema/event/metric имена и числовые значения; dropped events 0. Это проверка
этих артефактов, не обещание отсутствия любых побочных каналов.

Финальная серия 127,292 с целиком, не latency benchmark. Все шесть markers
(пять сценариев и общий) присутствуют. Заморожены 1478 source/test/dependency
inputs; native source/lock/features и Veil/HVS SHA проверены. Teardown: **24 PID /
33 порта**, собственных процессов/listeners нет, runtime удалён. Первый
неуспешный стенд также закрыт: 18 PID/22 порта, runtime удалён.

## Дополнительный открытый случай

После cold restart B на 21-й мс диагностической шкалы получил offer старого,
уже отменённого первого вызова; на 31-й мс получил его cancel. Это те же ID в private call-signal
журнале, не отождествление по совпадению счётчиков. Диагностика фиксирует ещё
один переход ringing → remote-cancel (около 10 мс программного состояния).
Поэтому суммарно B имеет 6 terminal events, а C — 5 и A — 2. Все пять новых
вызовов прошли; отсутствие любых дополнительных кратких звонковых состояний
не объявляется доказанным. Визуальное уведомление или слышимый гудок этого
короткого состояния не измерялись. Следующая работа — отдельный durable
finished-call replay тест при перезапуске и проверка источника старого offer.

Исходный [репорт ПК ↔ Android](../user-pc-android-calls-2026-11-05/README.md)
остаётся активным: Windows SSH снова timeout, нового физического повтора нет.
Медиа, человеческая слышимость, смена Wi-Fi/mobile во время разговора и вся
multi-device матрица этим signaling-only стендом не квалифицированы.
