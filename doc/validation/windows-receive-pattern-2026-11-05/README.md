# Известный сигнал в приёмном тракте Windows — 2026-11-05

Проверен реальный Windows ADM с опубликованным и текущим медиадвижком.
Это квалификация части тракта, **не закрытие жалобы на тишину в звонке**.
На телефоне захват речи не выполнялся; владелец подтвердил продолжение без
телефона. Production-код приложения и SDK в этом раунде не менялся.

## Зачем другой стенд

Предыдущая акустическая [попытка с речью](../controlled-speech-2026-11-05/README.md)
не установила прохождения заданного сигнала через микрофон телефона.
Теперь [отдельный native probe](../../../test/native/windows_audio_receive_probe/README.md)
подаёт синтетический Opus/RTP непосредственно в datagram callback неизменённой
Windows media DLL. Внутри неё работают настоящие WebRTC decode/NetEq/mixer
и Windows ADM. Маленькая stand-only DLL заменяет Veil transport, не движок.
Никаких тестовых hooks в media DLL для этого не включалось.

Фикстура — три тихих тона и интервалы тишины за 12 секунд. Начальный пик
0,03 полной шкалы, без чтения микрофонов. Пакеты по 20/40/60 мс проверены
отдельно: результат для 20 мс не переносится молча на адаптивные размеры.
Целочисленные RTP sequence/timestamps, число пакетов, длительности и конец
каждой фактически сгенерированной Opus-фикстуры проверены дополнительно.

Probe запущен в desktop session на Windows 11 `10.0.26300.0`, с
`send=0, recv=1`. Громкость и системный маршрут скриптами не менялись.
Каждый запуск перечисляет audio sessions, выбирает единственную активную
сессию **своего PID** и читает её peak meter. Это не endpoint-wide измерение
чужих приложений. Неполная/неоднозначная выборка или неподдерживаемый meter
не превращаются в нулевую громкость/успех. Реальная реализация Windows дала
полноценный meter во всех срезах.

| Текущий C++, source digest `72e053fe…` | SHA `ac1e720a…`, совпадает с квалифицированной Windows-сборкой; все исходные engine inputs совпали с текущим деревом до и после серии |

Оба используют закреплённый WebRTC `4ef980bc…`. Helper/stub собраны MSVC x64

Сравниваются две DLL в одном независимом стенде; это не mixed-client проверка
и не изменение принятого владельцем решения о совместимости.

## Финальный результат

Все **7 запусков прошли строгий oracle**. Каждый имеет отдельный реальный
exit code 0, 66 срезов, playout result=1, capture result=−1, worker_stalled=0,
576 000 emitted samples и снятый receive callback после destroy.
Во всех семи стартовых снимках app/endpoint mute=false, громкость приложения 100%, endpoint
56%; default и communications output совпали. Эти условия не задавались
стендом — они прочитаны из ОС.

| Движок / данные | Пакет | RTP принято | Три тона в native и Windows session |
|---|---:|---:|---|
| Текущий / тона | 20 мс | 600 | да |
| Релизный / тона | 20 мс | 600 | да |
| Текущий / тона | 40 мс | 300 | да |
| Релизный / тона | 40 мс | 300 | да |
| Текущий / тона | 60 мс | 200 | да |
| Релизный / тона | 60 мс | 200 | да |
| Текущий / тишина | 40 мс | 300 | сигнала нет, ожидаемый negative control |

В tone windows медианы session peak ≈0,0303–0,0305, в quiet — 0–0,000031.
В silence control все окна ≈0,000031. Полные безопасные агрегаты —
[summary.json](summary.json). Это нормализованный цифровой пик, не dB/SPL,
выход из физического динамика или оценка слышимости человеком.
[Контракт GetPeakValue](https://learn.microsoft.com/en-us/windows/win32/api/endpointvolume/nf-endpointvolume-iaudiometerinformation-getpeakvalue).

Oracle требует все три сигнала, тихие интервалы, собственную audio session,
свежие продвигающиеся RTP counts, emitted PCM, соответствие packet duration,
binary SHA, завершение процесса и cleanup. **10 Python tests passed**:
положительный pattern/silence, duration/count mismatch, null exit, чужой SHA,
постоянный шум, пропущенный третий тон, замороженные RTP/отсутствующий PCM,
неизвестный meter, незакрытый callback, сигнал в silence control и приватная
ошибка парсера. Несколько условий проверяются внутри одного unittest.

## Границы и незачтённые попытки

Установлено: обе DLL могут принять и декодировать заданные Opus packets всех
трёх размеров и вывести соответствующий рисунок в собственной Windows audio
session на этом компьютере. Размер пакета сам по себе здесь тишину не вызвал.
Не проверены реальный звонок, сохранённый UI-выбор устройства, signaling,
Veil/sealing/relay, вход телефона, мобильный провайдер, loss/jitter, физические
динамики, AEC/NS и человеческая слышимость. Исходная Windows 10 жалоба этим
стендом не квалифицирована. Оснований менять receive gain по серии не найдено.

Ранний launcher не зарегистрировал задачу из-за account-name mapping;
исправлен выбором SID текущего пользователя. Первая выполненная проба не
зачтена из-за null ExitCode оболочки: wrapper теперь удерживает Process.Handle
до WaitForExit, не делает Refresh перед чтением ExitCode. Ещё один batch
не стартовал из-за длины SSH command line — скрипт передан файлом. Это ошибки
стенда, не дефекты xVeil. Предварительные 20-ms прогоны с прежним collector
не складываются с финальной семёркой.

## Уборка

Все семь receiver и batch shell завершились. Собственная scheduled task и
весь отдельный Windows stand directory, включая fake `veilclient_ffi.dll`,
удалены; ≈15,4 МБ в финальном каталоге и ≈14,4 МБ в предварительном.
Собственных QA-app процессов нет; прежняя source media DLL сохранила SHA.
Лишняя локальная копия release DLL удалена, исходный проверенный архив сохранён.
Обычные приложения/контейнеры, настройки звука и сиды не менялись. Портов и
forward не создавалось. Raw rows, PID/job metadata и журналы остаются приватными;
сохранены только публичные агрегаты и воспроизводимый stand. Push/релиза нет.
