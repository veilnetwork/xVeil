# Отбой во время подготовки медиа — 2026-11-05

Подтверждены два связанных дефекта `VeilCallMediaController.start` до создания
engine. Они найдены при разборе NETCALL-01, но причиной всей пользовательской
паузы или отсутствия звука не объявляются.

## Что воспроизведено

1. Start ожидает чтение SharedPreferences, пользователь завершает звонок.
   После завершения чтения прежний start приобретает platform network activity,
   запрашивает микрофон и открывает media channel. Поздняя проверка epoch
   закрывает channel, но **network activity остаётся удержанной после stop**.
   Это подтверждено состоянием настоящего `CallNetworkActivity.shared` и
   историей вызовов его MethodChannel. Чтение с отказом даёт ту же утечку.
2. Отбой во время acquisition network activity, permission preflight или
   чтения peer-facing identity также допускает ненужное открытие channel
   отменённым запуском. В этих вариантах поздний network grant снимается;
   утечка из первого случая не переносится на них без доказательства.
3. Если следующий start приходит во время первого чтения предпочтений,
   `_devicePreferencesLoaded=true` уже выставлен, хотя чтение ещё не завершено.
   Следующий start пропускает ожидание и запускает текущий engine без
   сохранённого выбора микрофона. Воспроизводитель требует восстановления
   конкретного сохранённого входа, а не только результата true.

## Исправление

После чтения предпочтений, acquisition, foreground-service await, permission
preflight и peer-facing lookup проверяются epoch, call ID и microphone owner.
Отменённый start возвращает false до следующих platform/native действий.
Уже начатый системный запрос этим не отменяется; его прежние callbacks
сохраняют собственные проверки актуальности.

Чтение предпочтений теперь представлено общей Future вместо преждевременно
установленного bool. Следующий start ожидает то же чтение. Отказ необязательных
предпочтений по-прежнему позволяет запустить звонок с устройствами по умолчанию.
Cleanup следующего звонка не выполняется из старого continuation.

## Квалификация

Production controller, настоящий shared network-activity manager и fake
platform channels/transport/engine. Границы ожидания фиксируются completers;
пятисекундный timeout — только deadlock guard. В next-call случаях один
нулевой event-loop turn позволяет уже готовым операциям продвинуться при
закрытом gate; это не порог производительности.

Финальный набор — 15 случаев: пять стадий (включая отказ prefs), каждая без
отмены, с отбоем и с последующим звонком. На исходном production-файле из
`3b6d2404` этот же oracle дал **7 assertion-red / 8 passed**. Исходник и
candidate зафиксированы SHA; после baseline candidate восстановлен побайтно.
Ранние 12-case прогоны не складываются с итоговой выборкой.

Финальный контроль десяти файлов — **373 passed / без skip**, включая call
service, direct/group media, route operations, audio routing, intent, network
activity и foreground-service проверки. Analyzer двух изменённых файлов
чистый. Проверены запрет лишних channel opens, отсутствие удержанного grant
после отбоя, успешный следующий engine и восстановление сохранённого входа.
Отказ prefs отдельно проверен как допустимый запуск с default input.

Это macOS controller/MethodChannel квалификация, не настоящая Android FGS,
радиосеть или физический звук. Новая platform-channel группа тестов на других
ОС явно skipped; на этом Mac выполнены все 15. Телефон по ADB отсутствует,
исходные NETCALL-01 и слышимость речи остаются открытыми. Rust/C++ и native
pins не менялись; внешние сборки и установки не выполнялись. Flutter запущен
с `TMPDIR=/private/tmp/`, процессы завершены. Raw logs и credentials не
добавлены в репозиторий; push, релиза и изменений сидов нет.
