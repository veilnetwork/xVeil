# Обновление открытого чата после потерянного ответа commit

**Подтверждено и исправлено локально:** запись `delivered` могла выполниться,
а приложение получало отказ вместо ответа об успехе. Локальный повтор уже
умел прочитать записанный статус, но не уведомлял открытый чат: UI оставался
на `sent` до другого события или повторного открытия. Это потеря обновления
представления, а не потеря сохранённого статуса или сообщения.

## Воспроизведение

Widget-тест использует настоящий `messagesProvider`, его production throttle
и `MessagingService`/`HiddenVolumeStorage`. Подменены только KV backing с
управляемым отказом, транспорт без получателя и фиксированный размер окна
чата. Сам provider и его stream не подменяются. Widget отображает прочитанный
из него статус, как экран чата.

1. В открытом представлении виден `sent`.
2. Fake KV применяет настоящие операции status commit, затем бросает ошибку
   вместо возврата результата. Прямое чтение storage уже даёт `delivered`,
   а представление ещё показывает `sent`.
3. Отказ снимается, выполняется обычный maintenance без нового ACK. До фикса
   представление не менялось. Контрольный запуск на `456b1e96` падает именно
   на assertion отображаемого `delivered`; остальные 17 сценариев проходят.
4. После фикса то же открытое представление показывает `delivered`, без
   переоткрытия, повторной отправки и нового события `msgStatus`.

Виртуальное время продвинуто за известное 200-мс окно throttle; проверка не
задаёт порога скорости сети. Это воспроизведение отказа ответа на уровне
storage API, не аппаратная ошибка диска и не потеря питания.

## Изменение

Внутренний результат ACK writer теперь различает **новую запись** (`moved`)
и **подтверждённое сохранённое состояние** (`delivered`). Maintenance может
уведомить подписчиков после успешного read-back, сохраняя прежний контракт:
событие для собственных устройств создаётся только при новой записи.
Обычный inbound caller по-прежнему получает только `moved`; joined writers
не получают повторный переход. Дополнительного чтения или status commit
для обновления интерфейса нет — используется уже проверенный target.

Отсутствующий target не считается доставленным сообщением. Проверка удаления
теперь дополнительно подтверждает отсутствие как orphan journal event, так
и лишнего UI tick. Ограничения очереди, отказ закрытого сервиса, монотонность
доставки, ratchet, wire и формат контейнера не менялись. В production нет
тестовых flags или импортов fixture-кода.

## Проверки

**100 тестов прошли, без skips**, включая 18 ACK persistence сценариев,
настоящий provider/widget, read-window экрана чата, cache/status/mirror,
route-up retry, own-history lifecycle и inbound backpressure/dispose.
Targeted analyze и `git diff --check` проходят.

Последовательно пройдены **3 native E2E без skips**: sender-crash после
status commit с восстановлением sibling через новый пустой остров при
выключенном получателе; receiver-crash до и после append с повтором, ACK и
дальнейшим двусторонним обменом. macOS arm64, JIT-хосты, CLI/SDK 0.11.50
(`e963fbdb`), локальная hidden-volume `293792d`. SHA native inputs проверены
до запуска; inputs и снимок исходников lib/test неизменны до завершения.
После стенда проверены выход 30 учтённых процессов/групп, освобождение
30 зарегистрированных портов и отсутствие test VM. Сгенерированный тестовый
кэш удалён после завершения процессов. Native-серия квалифицирует crash/
обычные пути новой логики; аппаратный отказ ответа commit в ней не вводился.

Установленная пользователю macOS 0.13.98 не заменялась: проверка использует
отдельные тестовые процессы и синтетические данные. Изменение локальное,
без push и нового релиза; вся multi-device матрица этим сценарием не закрыта.
