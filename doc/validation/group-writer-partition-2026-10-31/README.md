# Обход цепочек ключей устройств — 2026-10-31

**Подтверждено и исправлено:** при построении принятой истории GroupService
повторно обходил все canonical-строки для каждой пары scope/author. Несколько
ключей устройств одной личности создают отдельные scope; работа росла вместе
с числом ключей, даже при неизменном количестве сообщений.

Теперь свежепроверенные canonical-строки один раз распределяются по прежнему
ключу scope/author. Проверка последовательности, predecessor, fork и retention
cut выполняется внутри каждой полученной цепочки прежним алгоритмом. Результат
не кэшируется между чтениями; before/after ingest по-прежнему проверяются
независимо. Изменение verifier немедленно влияет на следующую выдачу.

Кодирование ключа устройства использует ту же таблицу hex-цифр, что NodeId,
вместо временной строки для каждого байта. Формат, произвольная длина ключа и
пересчёт после изменения mutable-байтов сохранены. Wire, подписи, ratchet,
сохранение и ACK не менялись.

## Контроль алгоритма

128 или 256 строк одной личности распределены между 1/2/8/16 ключами. Счётчик
обращений к ключу включает обязательную работу тестового verifier. Сам verifier
вызывается для каждой строки на каждом чтении во всех вариантах.

| Строк в чтении | Ключей | Старый A₁ | Partition B / итоговый C | Старый A₂ |
|---:|---:|---:|---:|---:|
| 128 | 1 | 640 | 512 | 640 |
| 128 | 2 | 768 | 512 | 768 |
| 128 | 8 | 1536 | 512 | 1536 |
| 128 | 16 | 2560 | 512 | 2560 |
| 256 | 1 | 1280 | 1024 | 1280 |
| 256 | 2 | 1536 | 1024 | 1536 |
| 256 | 8 | 3072 | 1024 | 3072 |
| 256 | 16 | 5120 | 1024 | 5120 |

Выполнен контроль A₁/B/C/A₂, где B — только partition, C — partition и общий
hex-кодек. Во всех фазах 20 чтений на профиль, одинаковые строки и порядок.
Тест независимости работы от числа ключей красный на исходном коде.

Для 256 строк / 16 ключей время 20 чтений: 92,255 / 23,452 / 12,602 / 93,949 мс.
Это JIT-микропрогон с синтетическими подписями и in-memory load. Он не измеряет
настоящую криптографию, fsync, полную доставку или ускорение Android. Основное
доказательство — счётчики работы и сохранённые результаты, а не время.

## Физическая проверка A/B/C

A — Mac, B — Android той же личности, C — второй Mac другой личности. Все
три используют текущий Dart-код; Android — profile/AOT, Mac — JIT с прежними
Runner/plugins. Native SDK и остальные библиотеки зафиксированы, маршруты
публичной сети не закреплены. Использованы существующие QA-личности и история;
перед началом проверено присутствие всех 20 сообщений предыдущего прогона.

Пока B остановлен, A отправил 98 сообщений, C — ещё два. A/C имели все 100.
После минимум 300 секунд offline C остановлен, B запущен; A остаётся online.
Фактический интервал остановка B → готовность B составил 355,5 с, включая запуск.
Принудительных flush/sync и очистки очередей нет.

| После готовности B | Видно из 100, C offline |
|---:|---:|
| 82,167 с | 0 |
| 92,431 с | 2 |
| 123,217 с | 52 |
| 144,752 с | 78 |

**Независимое восстановление от A в 300-секундном окне не прошло.** После
возвращения C итоговая проверка дала 100/100 на всех трёх, одинаковые ID и
порядок, без дублей. Это не доказывает, что возврат C причинил доставку остатка:
одновременно продолжали работать ранее поставленные очереди A/B. В контрольном
чтении после возврата C журнал A содержал события всех 100 сообщений; промежуточное
чтение журнала B — 79. Последующее полное схождение подтверждено отдельно.
