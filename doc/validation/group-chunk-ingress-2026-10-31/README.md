# Догрузка: фрагменты за медленными обновлениями — 2026-10-31

**Подтверждено:** части нового snapshot ждали в общей последовательной полосе
приёма, пока старые небольшие group-delta читали, проверяли и сохраняли журнал.
В физическом захвате ожидание до начала обработки достигло **66,7 с** при уже
полученных транспортным callback кадрах. Сохранение ratchet не объясняло это
ожидание: median 1,0 мс, max 315 мс в том же захвате.

## Как локализован остаток

Все три роли используют текущий Dart-код: A/Mac и B/Android одной личности,
C/Mac другой. B выключен на время создания 20 сообщений; C выключается перед
возвратом B, A остаётся online. Синхронизация выполняется настоящими сервисами,
контейнерами и native SDK. Android profile/AOT; Mac — JIT с прежними Runner и
плагинами. Это не измерение обычной release-сборки.

Первый прогон на `ee57d863` дал 20/20 на B до возвращения C: первые два сообщения
в наблюдении через 31,6 с, все — через 41,7 с. Очередь source на Mac ждала
median 0,083 мс, max 41,6 мс; локальные попытки занимали max 60,4 мс. Отмена
подтверждённых ожидающих source jobs в этом захвате не сработала ни разу.
Это исправленный механизм, но не объяснение данного ожидания.

Во втором прогоне добавлены отдельные QA-отметки у транспортного callback,
начала сериализованной обработки и завершения ratchet flush. Результат —
20/20 до возвращения C, первое полное наблюдение **83,164 с**. Для 64 начатых
обработок median ожидания 54,6 с, max 66,7 с; для 55 сопоставленных логических
group-кадров callback → dispatch median 59,2 с. Максимум общей очереди —
109 кадров. Потерь строк диагностического кольца не было.

До завершения второй догрузки выполнено 28 ingest, 27 без новых device-строк.
Чтение журнала достигало 2,09 с, ожидание его group gate — 3,10 с, save median
593 мс/max 1,09 с. `fresh=0` не доказывает равенство snapshot: контрольные записи,
ключи и локальные receipts требуют отдельных проверок. Такие кадры не удалены
и не подтверждаются без применения.

83/42 с не являются сравнением скорости A/B: история и оставшийся Outbox росли,
маршруты не фиксировались, во втором прогоне больше QA-отметок. Тем не менее
ожидание **после callback** измерено прямо в часах одного устройства. Срез Android
на этом участке: foreground Activity, Awake, питание, оба Doze ACTIVE.

## Правка

У `groupEntryChunk` теперь отдельная **одна** последовательная полоса обработки.
Обычные кадры сохраняют свою последовательность, включая pre-consent проверки
и message dedup. Обе полосы используют прежний общий `InboundAdmission`: новый
лимит памяти/кадров не добавлен. Shutdown учитывает обе полосы.

Фрагмент проходит прежний ratchet checkpoint, проверки отправителя, digest,
reassembly и актуальной авторизации. Полный snapshot по-прежнему применяется
через сериализацию мутаций GroupService по group ID. ACK разрешён только после
успешного применения; прерванная привязка его не создаёт. Никакие старые кадры,
подписи или операции сохранения не пропускаются этой правкой.

Это снимает блокировку сбора истории за обычным обработчиком. Медленные чтения,
повторное применение старых delta и ожидание group gate остаются отдельными
участками; полного устранения задержек не заявляется.

## Проверки и границы

- Красный тест на прежнем коде: удержанный обычный apply не даёт собрать новый
  составной snapshot. На кандидате сборка завершается при закрытом gate.
  Контрольный возврат старого core с итоговыми тестами дал три падения;
  кандидат затем восстановлен побайтово.
- Дополнительно проверены ACK после apply, обычный chat во время удержанного
  chunk apply, сохранение однократности и ожидание новой полосы при shutdown.
- Существующая проверка backpressure теперь требует сохранения нового chat
  **до** снятия блокировки snapshot. Проверки coalescing 100 одинаковых частей,
  общего бюджета и отсутствия дублей сохранены.
- **755 passed, 3 skipped**, analyzer чист. Включены group/epoch/revoke,
  фрагментация/ACK, Outbox, ratchet, consent, provenance и admission.
- Native-стенд: четыре сообщения всем 12 узлам ровно один раз; локальный TCP,
  один процесс/Mac, настоящие подписи, контейнеры и ratchet. Это функциональная
  квалификация, а не сравнение скорости.

## Физическая серия кандидата

Тот же сценарий завершился **20/20 до возвращения C**, первое полное наблюдение
через **31,510 с** после готовности B. У всех трёх устройств одинаковые ID и
порядок, без дублей. Строки журнала на участке — 361–399; 5/6 ingest не давали
новых device-строк, один применил 20 mirrors и 18 статусов.

| Участок на B | Предыдущий захват | Кандидат |

| Ожидание `groupEntryChunk`, median / max | 60,1 / 64,2 с | 4,95 / 9,38 с |
| Ожидание обычного `groupEntry`, max | 66,7 с | 18,8 с |

Это **не** контролируемый A/B скорости: состав backlog, маршруты и момент
прихода пакетов различались. Окно заканчивается после видимости двадцати
сообщений, поэтому статистика оставшегося хвоста цензурирована. Gate-тест
доказывает устранение механизма, серия подтверждает работоспособность новой
полосы; всему разрыву 83 → 31,5 с причинная атрибуция не присваивается.
Ожидание частей до 9,38 с и обычных кадров до 18,8 с остаётся открытым.

Приложения и native-стенд остановлены, процессы/порты проверены; исходный QA APK
восстановлен по SHA, собственный ADB forward убран. Основное Android-приложение
не менялось. Удалены 3,01 ГиБ логического объёма собственных промежуточных сборок;
