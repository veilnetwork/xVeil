# Повторное использование страниц индекса при чтении истории — 2026-11-04

## Подтверждённая лишняя работа

Предыдущий замер storage-worker показал 5,30 с суммарной обработки 1202
`kv.readLogGroups` в закрытом 43-секундном окне. Это adapter + FFI + native,
не исключительно диск или CPU. Разбор native показал: данные DataBatch уже
разделялись между exact-ID группами, но поиск каждого ID заново читал и
дешифровывал те же страницы индекса.

Counting-I/O regression на 32 записях из одного leaf и одного DataBatch:
прежний код сделал **33 chunk reads вместо двух**. Тест красный до правки;
после неё проходит. Замер не зависит от сетевых или временных порогов.

## Изменение

HVS `eceb9158`: один синхронный `read_log_groups` использует ограниченный
LRU-кэш декодированных страниц: 64 узла / 1 МиБ учтённой памяти узлов,
плюс ограниченный числом entries overhead HashMap. Во время чтения возможна
ещё одна декодируемая страница; oversized-страница не сохраняется. Кэш
уничтожается по завершении вызова. Индексные буферы используют существующий
Redacted/zeroization; между space, commit и вызовами кэш не переносится.

Каждый exact ID начинает собственный TreeWalk, включая cache hit: цикл,
глубина, предел слотов и namespace проверяются до использования страницы.
Digest проверяется для каждой log-reference по-прежнему. Порядок, дубли ID,
ранний отказ при missing/byte ceiling и свежесть следующего вызова сохранены.
Scalar get использует общий guarded descent без Rc-аллокации и без кэша.
Публичный API, формат контейнера, авторизация и durable ACK не меняются.

## Контроль компонента

Один неизменный синтетический контейнер, три отдельных процесса, прежняя /
новая / прежняя библиотеки; checksum контейнера совпал до/после каждой фазы.
Везде по 100 чтений 32 payload по 2 КиБ в восьми группах. Каждое чтение
проверяет точные bytes; warmup одинаков. Ни один timing не является assert.

| Данные | A1, прежняя | B, новая | A2, прежняя |
|---|---:|---:|---:|
| Сжимаемые | 146,771 мс | 105,305 мс | 140,232 мс |
| Псевдослучайные | 187,219 мс | 136,896 мс | 171,616 мс |

Это измерение конкретного native чтения; оно не доказывает такой же выигрыш
полной догрузки, других платформ или мобильной сети. В отдельном worker /
FileStore контроле все bytes, missing, byte ceilings и freshness прошли.
Его scalar/groups/scalar времена не являются A/B новой и старой библиотеки.

## Сквозная проверка

Один native A/B/C island с настоящими контейнерами, SDK и transport:

- B принудительно завершён на 1580 наблюдавшихся строках; после локального
  восстановления без A/C сохранены 1583. Есть sparse-копия с поздним хвостом
  и provisional positions; prefix fallback реально выполнен.
- Вернулся только A; все 2000 ID, порядок, source positions и delivered
  сошлись. Completed-history retries — 0, invalid snapshots — 0.
- Результат сохранился после повторного запуска B без обоих источников.
- После готовности A — 41,827 с. Это **не парный замер ускорения**: в
  предыдущем прогоне B восстановил 1798 строк, теперь 1583; объём недостающей
  истории и обработки отличается. Ни ускорение всей догрузки, ни регрессия
  по сравнению с прежними 31,299 с не устанавливаются.
- Oracle и driver завершились с 0; независимый teardown проверил 29 PID,
  42 порта, отсутствие listeners и удаление runtime. Все 1413 frozen inputs,
  native SHA и dependency checkouts во время прогона неизменны.

Закрытый storage timeline после перезапуска B квалифицирован: 15161 RPC
сопоставлен с 15161 worker handlers, внутреннего пропуска нет. Окно 53,039 с
из capture 53,232 с; исключены 83/84 незамкнутых крайних RPC/handler spans.

| Операция | Вызовы | Inclusive await | До handler | Внутри handler | Reply tail |
|---|---:|---:|---:|---:|---:|
| `kv.readLogGroups` | 1644 | 6,979 с | 0,116 с | 6,421 с | 0,441 с |
| `kv.commit` | 681 | 11,560 с | 0,584 с | 10,463 с | 0,512 с |
| `kv.get` | 7411 | 8,986 с | 6,072 с | 0,386 с | 2,527 с |

Семантика такая же, как в предыдущем отчёте: handler включает Dart adapter,
FFI и native; до handler — не исключительно очередь; awaits нельзя
складывать с wall time. Число и размер запросов между прогонами различаются,
поэтому эта таблица не оценивает эффект cache в процентах. Значимым остатком
остаются durable commits и обработка/ожидание большого количества запросов;
общий latency-дефект не закрыт.

Из остальных captures короткий setup прошёл отдельно; trace процесса,
завершённого SIGKILL, не имеет close и отвергнут. Короткий final-reopen
capture также отвергнут из-за несопоставленных spans. Эти два файла не
используются для атрибуции и не объявляются зелёными. Retention приложения
проверен независимо по точным сообщениям, не по этой диагностике.

Mailbox собственных устройств отключён по решению владельца. При offline
всех держателей истории требуется их возвращение. Push, релиза, смены APK,
engine pins и production-реле в этом раунде нет. Android/AOT не проверены.
