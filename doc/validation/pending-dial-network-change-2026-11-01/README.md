# NETCALL-01: отмена dial на прежней сети

Дата: 2026-11-01. База SDK `67e9b1fa`; продолжение
[исправления квитанции NetworkChanged](../network-notification-receipt-2026-11-01/README.md).
**Подтверждён и исправлен отдельный механизм задержки. NETCALL-01 открыт.**

## Механизм и красный тест

Outbound connector слушал force-reconnect notification в sleep/backoff, но
не во время `connect_peer_active`. При смене сети незавершённый dial/transport
handshake продолжал ждать на старом подключении. К моменту входа в backoff
широковещательное Notify уже было потеряно. Отмена по обновлению endpoint в
этой же ветке уже поддерживалась; по смене локальной сети — нет.

Regression использует настоящие NodeRuntime, NodeServices, peer map и
`spawn_outbound_peers`, но транспорт намеренно держит connect pending. Drop
future оставляет свидетельство отмены. После настоящего
`force_reconnect_all_peers` прежний код не отменял первую попытку и не начинал
вторую. Одна секунда paused-clock timeout — только deadlock guard: транспорт
сам не завершится, production-таймауты не сокращались. Первый запуск выполнил
нужный тест и упал по отсутствию отмены, не по ошибке сборки. Финальный fixture
отключает внешнее discovery, PEX и lazy mining.

В select добавлена отмена по force-reconnect, сброс backoff/failure-streak и
возврат к штатным проверкам peer перед новым dial. В private native-журнале
есть отдельная категория `peer.connect.interrupted`, reason=network_changed.
Wire, C ABI, admission, криптография, liveness deadline и сетевые маршруты не
менялись. Это исправление ожидающей connect-ветки, не доказательство покрытия
всех гонок между успешным handshake, публикацией сессии и сменой сети.

## Проверки

- Полный runtime suite: **785 passed / 11 ignored**.
- FFI lib, node-embedded + production-seeds + packet-tunnel:
  **334 passed / 2 ignored**.
- ARM64 Android FFI собрана и проверена по SHA/источникам; external-mount
  watchdog не зафиксировал потери отдельной ФС. Targets относятся к тому же
  checkout, dependency overrides не применялись.

Первый полный runtime suite получил один отказ в старом тесте диагностического
счётчика: ожидалось ровно 9 новых номеров, но другие параллельные тесты тоже
брали номера из общего атомика, и получилось 11. Allocator не менялся. Тест
теперь явно включает вторую операцию на другом потоке и проверяет продвижение
в общей последовательности с учётом wrap. Это исправление предположения теста,
не новый продуктовый дефект. Финальный полный suite прошёл также после
отключения внешнего discovery в новом dial fixture.

## Физический прогон

Изолированные QA Poco ↔ Windows 11. На Android заменена только FFI; AOT,
manifest/wrap, остальные библиотеки и signing certificate прежние. На Windows
зафиксирована прежняя SDK `8eab7507`, SHA загруженного модуля проверен.
Windows 10 и слышимость речи не проверены. Условие одного активного узла на
момент place отдельно не создавалось.

1. Новый вызов сразу после Wi-Fi cut: входящий появился примерно через
   **62 мс после place**, но после ответа телефон ещё ждал signaling. Первый
   connecting/active срез — через 7,260 с после accept, первый fresh RX на
   телефоне — ещё через 4,177 с после этой выборки. Первые fresh-RX срезы
   после cut — 11,642/8,526 с. Устойчивые пять конечных срезов с ростом
   счётчиков появились существенно позже; setup в итоге квалифицирован.
   [Обезличенный агрегат](setup.json).
2. Отдельный активный P2P-звонок: четыре свежих P2P/RX-среза обоих концов до
   cut; после него по 40 срезов за 41,585/41,595 с. Один active call сохранён,
   RX свежий в конце на обоих концах. Но непрерывный fresh-RX guard **не прошёл**:
   максимальные sampled native ages 15,499/14,486 с. Это не верхняя граница всей
   паузы между media epoch. [Обезличенный агрегат](handover.json).

В native-захвате есть новые interruption-события: production действительно
вошёл в добавленную ветку. Их наличие не доказывает, что вся задержка данного
звонка была вызвана ожиданием отменённых dial. В отличие от предыдущего
физического цикла liveness-обрыв здесь не повторился, однако это один прогон
без фиксированного маршрута и A/B. Ни ускорение, ни полное устранение обрыва
не заявлены. Ожидание сигналов, пауза RX и исходный пользовательский случай
остаются в активной очереди.

## Завершение

Оба QA остановлены, процессы и Windows listener проверены отсутствующими.
Прежние Android APK и Windows DLL восстановлены по SHA, остальные DLL/AOT
не менялись. Android-restore сначала остановился на timeout наблюдателя:
после передачи APK появился одноразовый запрос Play Protect, а host installer
уже отсутствовал. Новая установка поверх pending-операции не запускалась.
Для собственного QA выбрано «Не проверять», затем прежний APK независимо
проверен по установленному SHA. Общие настройки Play Protect не менялись.
Для доступа к кнопке временно включалась portrait rotation; исходные настройки
rotation восстановлены и проверены. Main-app PID, Wi-Fi/data/stay-awake
сохранены. Logcat, ADB-forward, SSH-туннель и свои scheduled tasks закрыты.
Нового push/релиза нет. Подготовка отдельного линейного testnet ведётся
[в отдельном учёте](../linear-testnet-2026-11-01/README.md).
