# Windows ↔ Android: контакты и сигнализация — 2026-11-05

Текущий Dart до `971c9d5c`, Veil `b8647716`, hidden-volume `eceb9158`.
Изолированные QA-профили Windows 11 (10.0.26300.0) и Blackview; основное
приложение и прежние QA-контейнеры не менялись. Без push/релиза и обновления
сидов. Это не Windows 10 и не устройство/провайдер автора исходной жалобы.

## Происхождение и границы

Veil/HVS собраны заново на закреплённом Rust: раздельные targets, на Mac
контроль внешнего mount. На Windows заново собраны runner, плагины и AOT;
приватный CMake overlay добавляет пути установленного ATL. Проектный CMake
не менялся. Android — отдельный applicationId и текущий Dart. Gradle удаляет
ELF-символы: packaged native сверены с результатом `llvm-strip --strip-unneeded`
свежих библиотек, затем SHA установленного APK проверен отдельно.

Медиадвижок заморожен на `engine-2026.10.31.2` с проверенными binary SHA.
Его source digest отличается от текущего C++; symbol gate выявляет два
отсутствующих noise-suppression setter. Gate не подавлялся. Поэтому проверены
только контакты, текст и сигнализация: звонки **не принимались**, audioStart=0.
Приём/слышимость речи, шумоподавление, видео и новые C++ правки не квалифицированы.

## Отброшенные прогоны и предположения

Первый source ZIP не содержал игнорируемого операторского сетевого ресурса:
узлы не подключились. Сообщения этого прогона не доказывают продуктовую
недоставку. Ресурс отдельно перенесён в приватную сборку; финальные APK/bundle
проверены до запуска. В код не добавлялись ключи или захардкоженные адреса.

Строгий native bootstrap parser отвергает identity-only URI, но реальный
`RealVeilStack.addContact` намеренно пропускает регистрацию транспорта для
такой ссылки. Первоначальное предположение о дефекте parser отозвано;
Rust не менялся. Контакт добавлен через настоящий GUI-путь со ссылкой.

Пустой clipboard, невидимая плитка настроек, неверная команда window-dump и
проверка GoRouter URL вместо видимого чата — ошибки наблюдателя. Они не
зачтены ни как дефекты, ни как успешные UI-проверки.

## Квалифицированный результат

После восстановления сетевого предусловия оба клиента видели подключения.
У каждого ровно один правильный принятый контакт, `canMessage=true`;
наблюдение согласованного accept заняло 2,833 с. Холодная задержка первого
запроса не измерена: приветствие уже было в очереди раннего прогона.

| Действие | Фактический результат |
|---|---|
| Windows → Android, текст | Один экземпляр с правильным ID; наблюдение 1,215 с |
| Android → Windows, текст | Один экземпляр с правильным ID; наблюдение 1,530 с |
| Windows → Android, вызов | Exact call-ID достиг ringing; отдельная проверка ОС подтвердила видимые caller, «Входящий звонок», «Принять», «Отклонить» |
| Android → Windows, вызов | Exact call-ID и реальный входящий UI; наблюдение 0,595 с |
| Завершение | Четыре тестовых вызова закончены явным действием скрипта; по четыре записи истории на обеих сторонах |

Первый Windows → Android наблюдатель сначала ждал UI восемь секунд; его
8,255 с не являются сетевой задержкой. Дополнительная backend-проверка
ringing с неверным window-dump не зачтена как UI-прохождение; исправленный
наблюдатель использовал окно ОС и accessibility. Телефон foreground/unlocked.
Числа — единичные наблюдения, без A/B и вывода об ускорении.

## Новый подтверждённый дефект

Финальная сверка нашла **разный канонический порядок приветствия** в
`Storage.loadMessages`: три одинаковых logical ID, одинаковые body/timestamp,
все delivered, без дублей, но на Android старое приветствие стоит после
более нового исходящего сообщения Windows. На Windows оно первое.

Это не полная сходимость истории. Причина пока не доказана: debug-проекция
показывает revision seq, но не отдельный birth-order witness. Следующий шаг —
проверить request/retry → обычное сообщение и воспроизвести локально.

Продолжение: [локальное воспроизведение и исправление request/retry](../contact-greeting-order-2026-11-05/README.md).
Эта физическая серия выполнена до последней правки и не квалифицирует её APK.

## Анонимные отчёты и уборка

Получены реальные UI-экспорты обоих клиентов, а не искусственные JSON:
Android — через DocumentsUI; Windows — через видимую плитку копирования.
Проверены точные allowlist событий/полей/числовых метрик и отсутствие известных
QA canaries: ID, паролей, ключей, тел сообщений, путей и имени пользователя.

Android: 192 события / 0 dropped; Windows: 167 / 0 dropped. В обоих errors=[];
`download-resume-read` не наблюдался. Это не исключает другие причины чтения
registry и не атрибутирует исходный пользовательский отчёт.

QA-приложения остановлены; их PID и порты отсутствуют. Удалены только свои
Windows scheduled tasks/runtime, временный SAF-файл, UI dumps и SSH/ADB
forward. Артефакты сверены неизменными; QA-профили оставлены для продолжения,
криптографические контейнеры не откатывались. Сырые журналы, отчёты,
идентификаторы и секреты остаются вне репозитория.
