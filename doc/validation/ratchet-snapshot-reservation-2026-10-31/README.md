# Резерв отправки вместе со снимком ratchet

2026-10-31. Без push/релиза; SDK `c46d94db` не менялся.

## Подтверждённая лишняя запись

Предыдущий [разбор I/O](../ratchet-io-anchor-retry-2026-10-31/README.md)
нашёл 246 из 300 отдельных записей резервов, для которых соответствующая
sending chain уже присутствовала в ранее завершённом снимке. На каждой новой
цепочке контейнер сначала сохранял снимок, затем отдельно — резерв отправки.
Оба действия нужны; две отдельные транзакции нужны не всегда.

Теперь guarded-владелец может добавить резерв к экспортируемому снимку.
`HiddenVolumeStorage` сохраняет chunks снимка, удаление его старого хвоста,
setting резерва и cleanup-budget marker одной транзакцией. Capability объявлена
явно: другим реализациям `Storage` парные записи не передаются.

Позиции непрозрачного blob читает только native ABI. Более высокие durable
marks сохраняются; старые удаляются только вместе с заменой снимка и только
когда цепочки нет ни в этом экспорте, ни в текущем native state.

После успешной записи выполняется прежняя попытка обновить rollback anchor,
затем проверяется актуальность владельца и выдаётся floor для совпадающих
живых цепочек. Native по-прежнему проверяет цепочку, позицию и владельца при
расходовании ключа. Закрытый/заменённый владелец не выдаёт новый permit.
Ошибки записи не подтверждают dirty generation. Ротация во время I/O оставляет
новую generation для следующего сохранения.

Парная запись ограничена 128 операциями, включая резерв, cleanup marker и
удаление старого хвоста; metadata ограничена 2048 UTF-8 байтами. Только явный
отказ этого бюджета разрешает прежний путь: обычный снимок, отдельный резерв,
anchor attempt, permit. Произвольная I/O ошибка не превращается в fallback.
Ранее успешно записанный префикс batch остаётся целой парой. Парные входные
буферы фиксируются до первого ожидания; ABI и wire не менялись.

`reserveAhead=32`, publication poll **200 мс**, ratchet, подписи, durable host
barrier и правила cleanup сохранены. Не добавлены ранние ACK/permits или
приоритеты на реле.

## Проверки безопасности и отказов

Красный контроль на прежнем владельце `4a1145ba`: guarded flush не подготовил
резерв (`pairedSaves`: ожидалось 1, фактически 0). Первый storage-контроль
также был красным: снимок сохранялся, setting резерва отсутствовал.

Набор проверяет:

- запрет seal и удержание dirty ACK до ответа commit и завершения anchor attempt;
- отказ записи, потерю ответа после commit и безопасный повтор;
- ротацию цепочки, замену владельца и закрытие во время парной записи;
- сохранность более высоких marks и fallback только по типизированному бюджету;
- неразрывность нескольких записей, уменьшение снимка, учёт старого хвоста,
  неизменность входных буферов и UTF-8 границу metadata.

На настоящем hidden-volume дополнительно проверены отказ native-транзакции
после staging смешанных операций и потеря ответа после commit. После reopen
в первом случае осталась старая пара, во втором — новая. Повтор и удаление
хвоста корректны. Отдельно прошла парная транзакция на всех 128 операциях.
Эти storage-тесты используют непрозрачные тестовые blob; реальный формат V4 и
native publication ABI проверены четырьмя существующими ABI-тестами, а native
криптографический путь — стендом ниже.

**286 тестов прошли, 0 skipped** в итоговом запуске с обеими native libraries.
Включены общие HVS, ratchet, outbox, rollback anchor и peer authorization
проверки. Scoped analyze: no issues. Ранний запуск без library env имел один
skip; он не засчитан как выполнение ABI-теста и заменён итоговым запуском.

## Чередование A/B на 12 native-узлах

Три пары A/B, свежие encrypted worker-контейнеры в каждом процессе.
A — прежний `RatchetPersistence` из `4a1145ba`; B — новый helper.
В обеих ветках одинаковый новый storage backend: A передаёт только обычные
снимки. Это изоляция изменения владельца, **не сравнение двух полных checkout**.
Все остальные `lib/` и test-support файлы, fixture и native libraries заморожены
по SHA; до/после каждого запуска проверены. После серии восстановлен точный
candidate. Полные агрегаты и source/library SHA — в [summary.json](summary.json).

|---|---:|---:|
| Первое, холодное | 4141 | 3707 |
| Второе | 2932 | 1579 |
| Третье | 2383 | 1714 |
| Четвёртое | 2874 | 2359 |

| Операции в окне измерения, медиана | A | B |
|---|---:|---:|
| Отдельные записи резервов | 302 | 55 |

| Все native container commit | 1381 | 1095 |

Медиана общего числа commit ниже примерно на **21%**, отдельных записей
резервов — на **82%**. Это не точное вычитание 247 из 1381: порядок событий
изменяет batch/coalescing и число сохраняемых снимков. Group-file commits
во всех шести запусках остались равны 144. Не выдаём число API-вызовов за число
fsync; passive API timings включают worker queue и перекрываются между узлами.

Все четыре медианы доставки ниже, но не каждое отдельное наблюдение улучшилось:
третье сообщение пары 3 — 1918 → 2173 мс. Три пары — ограниченная локальная
выборка, не гарантия сетевого SLO. Внешний rollback anchor на стенде не настроен:
попытки быстрые, реальная запись keychain этим сравнением не квалифицирована.

Стенд: один Mac/JIT process, 12 разных production-PoW личностей, локальный
TCP/fullmesh и DHT, настоящий native seal/ratchet/host checkpoint,
MessagingService и fragmentation/ACK. Legacy-группа без epoch encryption,
roster подготовлен отдельно. Это не multi-device, Android/AOT, Windows или
публичные onion-маршруты.

## Остаток и гигиена

24/24 сообщения появились у всех 12 ровно один раз. Во всех шести запусках
host exited, 12 listeners освобождены, cleanup errors=0, timing dropped=0,
временные stand roots удалены. Телефон и production-реле не менялись.
Приватные журнал/ключи/correlation ids в публичные агрегаты не включены.

Долгая доставка ещё открыта. Трасса B оставляет на пути последнего получателя
примерно 1,2–1,5 с в группе «обработка группы до следующего шага»; это включает
ожидания и I/O, не только CPU. У холодного сообщения остаётся около 1,1 с
между локальным handoff и callback по сумме его хопов. Медианы отдельных стадий
нельзя складывать как разложение одного и того же сообщения.

Следующий шаг — разобрать остаток group handling на конкретные ожидания,
затем перейти к полной multi-device матрице по текущему приоритету пользователя.
Исторические невоспроизводимые жалобы не объявляются исправленными этой работой.
