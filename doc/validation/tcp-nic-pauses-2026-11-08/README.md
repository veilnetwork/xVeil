# NETCALL-01: сопоставление секундных пауз с NIC capture

**Подтверждено наблюдение; механизм ниже TCP/телефона/сети пока не разделён.**
Это offline-разбор сохранённой серии SDK `e974cebe`, не новый физический
прогон. Product-код не менялся, новые сборки/клиенты/QA units не запускались.
Предыдущие readiness-фиксы не объявляются причиной устранения всех пауз.

Исходная серия: два Poco → Mac relay-only звонка через два изолированных
Core, четыре Wi-Fi ↔ Cellular handover. 5/6 финальных окон passed, максимум
after-switch native RX age 1202 мс. В ней не воспроизвелись прежние 3158 мс,
но подтверждены пять flats 1038–1078 мс с 77 distinct source RTP cells,
принятыми после соответствующего flat. [Подробности серии](../ready-replacement-calls-2026-11-08/README.md).

## Как связаны данные

Цепочка: source RTP witnesses + полный encrypted-cell hash → opaque record
fingerprint → локальный child ID → явный `tcp_ordered_binding` → TCP port pair
на Core → уникальный flow в PCAP. 20 ссылок из пяти эпизодов соответствуют
**12 различным TCP flows**, из них **7 на участке телефона**. Ссылки/копии
не считаются отдельными соединениями или логическими cells.

Все выбранные Core bindings найдены. Peer-port collisions и повторного
использования выбранного four-tuple нет; для каждого выбранного flow есть
одна пара SYN generations. Корреляция не строится по близким номерам или
случайному совпадению времени. Это связь с TCP-потоком, не побайтовая
разметка obfs4 ciphertext по отдельным клеткам.

Связь monotonic timestamps с PCAP wall clock на каждом Core проверена
предварительными probes и интервалами ISO timestamps всех 133029/185914
trace rows. Они допускают единый offset; расхождение исходного probe с
допустимым интервалом — не более 1,2 мкс. Это проверка согласованности,
не заявление микросекундной точности физического измерения.

Повторно сверены SHA/размеры исходных PCAP/journals с manifest предыдущего
сбора. Декодированы 47942/69767 TCP packets; kernel capture drops = 0 на
обоих Core. Это отсутствие зарегистрированной потери **захвата**, не нулевые
потери сети. В этих PCAP нет UDP packets: UDP-контроль по ним невозможен.

На выбранных Core sockets `TCP_NODELAY=true`. Проверены также все
наблюдаемые source writers endpoints: 5/5 Poco и 2/2 Mac с binding и NODELAY.
Receiver-only endpoint bindings покрыты не полностью, полной observability
всех sockets не заявляется. Нулевых advertised TCP windows в выбранных
окнах не наблюдается; raw window не превращается в байты без window scale.

## Что видно на мобильном участке

У соответствующего TCP-потока на Core возникает интервал примерно 1,1 с
без **входящих TCP packets от телефона**, включая ACK. Затем пакеты приходят
пачкой. Одновременно на известных TCP flows Mac в средней части этих
интервалов наблюдаются 15–17 data packets; общей остановкой server capture
или обработки всего узла это не объясняется.

Ниже приведён максимальный непрерывный интервал без входящих TCP packets
**на всех соединениях соответствующего внешнего адреса телефона, попавших
в этот capture**, внутри связанного с эпизодом окна. Это наблюдение на
443/TCP конкретного Core, не утверждение обо всём трафике телефона.

| Эпизод на Cellular | Distinct source cells | Core A / B: TCP silence |
|---|---:|---:|
| Первый звонок, RX Poco | 18 | 1088 / 1095 мс |
| Первый звонок, RX Mac до команды возврата Wi-Fi | 12 | 1103 / 1150 мс |
| Второй звонок, RX Poco | 18 | 1133 / 1127 мс |
| Второй звонок, RX Mac, первый эпизод | 17 | — / 1142 мс |
| Второй звонок, RX Mac, второй эпизод | 12 | 1126 / 1156 мс |

В строке с 17 cells на Core A видны только 3/17 копий: его отдельный
1272-мс интервал не подставлен как квалификация пути всех 17 cells.
Все 17 приняты через B. Прочерки и отсутствующие stage/clock observations
не заменяются нулями.

Для трёх эпизодов с отправителем Poco первый сопоставленный complete-record
read на Core происходит через 0,9–22,4 мс после возвращения TCP packets
на соответствующем flow. Точность здесь ограничена связью с потоком:
первый вернувшийся TCP packet может содержать другие/частичные records.

В двух эпизодах с получателем Poco на Core продолжаются 17–18 из 18 локальных
record send attempts во время отсутствия ответных TCP packets на выбранном
телефонном flow. На Mac → Core в этих окнах максимальные packet gaps
около 65–66 мс. Пример с Core B содержит повтор того же диапазона TCP bytes
примерно через 734 мс после исходной отправки; наблюдаются SACK/DSACK.
Это packet-level повтор/задержка, не доказательство окончательной потери
оригинала или конкретного теряющего хопа.

## Проверки интерпретации

Первый подсчёт других соединений телефона давал 5/17 data packets внутри
двух длинных интервалов одного flow. Проверка времени показала, что они
приходят по краям: в средней 80% части интервалов data packets на других
известных телефонных flows нет. Поэтому эти количества **не доказывают
наличие исправного запасного канала на всём протяжении паузы**. Aggressive
channel replacement только по этому подсчёту не внесён.

Другие ограничения анализа:

- Длинный idle перед первым использованием flow не считается паузой
  доставки: сравниваются интервалы с обоими концами внутри выбранного окна.
- Повтор TCP bytes/SACK не приравнивается к доказанному packet loss.
  На Core наблюдается преимущественно приход последовательных bytes
  пачками и дубликаты; это не исключает задержку/переупорядочивание в пути.
- SACK ниже cumulative ACK и duplicate first block внутри следующего
  SACK block различаются с обычным SACK; проверено циклическое сравнение.
- Capture interface label, отображённый локальным tcpdump для удалённого
  cooked capture, не используется для вывода о VPN/interface на сервере.
- Нет clock observations для точного совмещения всех remote/phone clocks:
  межхоповые миллисекунды по необоснованному вычитанию clocks не вычислялись.

Sequence parser проверен synthetic positive/negative controls: настоящая
дыра, заполнение, дубликат, переход через u32, незаполненная дыра, idle без
byte hole, DSACK и idle, начавшийся до окна. Отсутствующая measurement
остаётся unknown. Это проверки offline-анализатора; Rust/Flutter test
counts предыдущего раунда здесь повторно не заявляются.

## Вывод и следующая проверка

Для этих пяти flats серия уже показывала короткие source seal/IPC,
Core ingress/selection и earliest-read → RTP stages. Теперь NIC capture
подтверждает секундные разрывы прихода TCP packets на телефонном участке.
Повторное изменение этих быстрых очередей приложения не обосновано.

**NETCALL-01 открыт.** Нельзя назвать виновным именно оператора: по этим
данным ещё не разделены ОС/ядро/модем телефона и промежуточная сеть.
Не доказано и отсутствие всех остальных дефектов Veil. Следующий контроль —
отдельный ограниченный TCP/UDP поток без Veil по тем же адресам, с измерением
собственной cadence отправителя и Wi-Fi/Cellular контролем. Положительное
воспроизведение отделит сетевой/системный механизм от SDK; отрицательный
результат не исключит protocol-specific shaping или зависимость от UID.

Raw IP/port tuples, sequence ranges, RTP metadata и журналы остаются private;
публичен только агрегированный результат. Старый стенд остаётся остановленным
и восстановленным; новых операций на серверах/установок на телефон здесь
не было. Push/релиза нет.
