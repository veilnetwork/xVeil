# Private media: время жизни конкретной TX-регистрации

Продолжение [Poco → Mac / ticket resume](../poco-mac-resume-2026-11-06/README.md).
В Veil `81436bd1` исправлена отдельная ошибка пригодности private media route.
Влияние на физическую паузу NETCALL-01 после этой правки **ещё не проверено**.

Последующая [проверка Poco ↔ Mac](../poco-mac-delivery-reconnect-2026-11-06/README.md)
выявила активный non-onion Delivery path: она воспроизвела NETCALL-01,
но не квалифицирует этот private onion `PinnedRoute`.

## Подтверждение

`PinnedRoute::is_live` проверял наличие любой живой сессии first hop и общий
`session_close_generation`. Этот счётчик увеличивается при выходе старого
runner, в том числе уже заменённого. Отсюда два неверных решения:

1. TX-регистрация уже заменена, но старый runner ещё не вышел: старый маршрут
   остаётся live, хотя его собственный `DataCircuit` больше не принадлежит
   текущей регистрации.
2. Новый маршрут уже создан, затем выходит старый runner: общий счётчик
   меняется и новый маршрут ошибочно объявляется непригодным.

Исправление exact-registration в `DataCircuit` уже было в предыдущих циклах;
здесь оставалась отдельная проверка поверх него. Та же устаревшая проверка
применялась к ограниченным повторам datagram-пробы.

Регрессионный тест использует настоящий offline NodeRuntime / NodeServices,
подписанную локальную relay-directory entry, настоящие TX-регистрации и
`open_data_circuit`. После замены TX при неизменном exit counter старый
`PinnedRoute` ошибочно возвращает live. На baseline получен **один assertion-red**
именно на этом условии. Runtime остановлен до финальных assertions.

Первый запуск с fixture без receive capability завершился `NoIdentity`,
ещё одна попытка не скомпилировалась из-за неверного имени константы теста;
они не считаются воспроизведением дефекта. Засчитанный red получен после
исправления этих предусловий, до изменения production-проверок.

## Изменение

Пригодность маршрута и продолжение probe теперь проверяются через
`NodeServices::data_circuit_session_current`: это конкретная живая
TX-регистрация, сохранённая в circuit при build. Закрытая очередь также
немедленно делает route непригодным. Общий exit counter остаётся только в
диагностическом поле, взятом из исходного snapshot самого circuit.

Сохранены ограничения возраста маршрута/активности, confirmation и probe,
дедлайны, bounded retry, проверки offer revision и repair generation,
сопоставление адресата, ключи/AEAD и wire framing. Проверка непосредственно
при отправке в NodeServices по-прежнему защищает от смены регистрации между
проверкой пригодности и постановкой кадра.

Тест после исправления проверяет старую, свежую и закрытую регистрации.
Отдельно задаёт отличающийся диагностический snapshot и требует, чтобы он
не менял пригодность свежего circuit. Последняя часть — проверка свойства
диагностического поля, не имитация настоящего teardown runner.

## Проверки и границы

- Focused: 1 passed после assertion-red.
- Полный `veilclient-ffi --lib` с
  `testnet-seeds,node-embedded,test-low-difficulty`: **375 passed, 10 ignored**,
  0 failed. Дополнительный запуск child-test внутри suite отдельно не
  прибавляется к итоговому числу прошедших тестов.
- `rustfmt` проверен на изменённых файлах, `git diff --check` чист.
- Release native-библиотеки Mac arm64 и Android arm64/API 24 собраны из
  чистого `81436bd1` с прежними соответствующими feature-наборами.
  SHA отличаются от сохранённых baseline; набор экспортируемых `veil_*`
  C API совпадает. Исходники, команды сборки и SHA записаны приватно.
  Библиотеки сохранены для следующего физического прогона, не устанавливались.
- Rust builds используют внешний target исходного checkout; watchdog
  подтвердил отдельную смонтированную ФС, потери mount не было.

В сохранённой физической серии перед этой правкой телефон продолжал native
enqueue при остановившемся RX на Mac. Enqueue не доказывает отправку в сеть.
Ошибка lifetime подтверждена тестом, но ей не приписывается весь наблюдавшийся
18,458-с интервал. Физический baseline был односторонним из-за ожидающего
разрешения микрофона Mac. Следующая проверка требует телефон с SIM и
заранее разрешённый микрофон Mac.

При начале повторной проверки `adb devices` не показал устройств; запрос на
подключение отправлен владельцу, работа над кодом продолжена независимо.
Приложения и QA-реле предыдущего прогона уже остановлены/восстановлены.
Новые сборки в этом цикле не устанавливались, production-реле не менялись.
Push/публичного релиза нет. В отчёте нет идентификаторов, адресов и сырых логов.
