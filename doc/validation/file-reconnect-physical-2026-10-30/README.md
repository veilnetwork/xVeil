# Физическая серия файлов и reconnect на текущем Dart

Проверен Dart `48a2d436`, включающий исправления назначения, opener и подготовки
запроса. Android profile/AOT, Mac debug/JIT; production network, native test hooks
и пониженной PoW нет. Native намеренно зафиксирован на `c96bd930`, plugin source
checkout `ea7e8388`; изменённые ранее Windows-only части этой серией не проверены.
Источник/артефакты/подписи сверены по SHA из сохранённого provenance.

Два QA-устройства разных личностей, личное основное приложение не менялось.
P2P контакта запрещён с обеих сторон; для файлов наблюдались anonymous native
streams через реле. До запуска Wi-Fi и mobile data были включены; активный
транспорт тогда отдельно не зафиксирован. После восстановления снимок default
network показывает Wi-Fi. Поэтому это не доказанная серия на мобильном провайдере.
Перед запуском временно включена только QA-настройка фоновой службы, OS-whitelist
не менялся. Native rt_trace включён, summary 500 мс; времена не являются A/B и
не отделяют диагностический overhead.

После прогрева 30 с сначала отправлены два контрольных файла, затем два по
32 МиБ+251 байт. Отключались оба радиомодуля телефона, когда наблюдаемый файл
получателя проходил треть размера; Mac всё время оставался online. Через целевые
8 с восстанавливались исходные Wi-Fi/data настройки; реальные интервалы чуть
больше из-за polling/ADB. Повторного пользовательского download не было.

жалобы Windows/Android и не её окончательное закрытие.

## Разложение задержки

У контрольных файлов native receive-prefix продвигался между наблюдаемыми
срезами с максимумами 0,511/0,562 с; consecutive RTO не наблюдался. После
отключения radio старые streams перестали устойчиво продвигаться, новые
streams завершили остаток без повторного запроса пользователя.

| Получатель | Макс. интервал проверенных частей | Dart payload-idle | Ошибка попытки, от начала API | Новый stream открыт | Смещение продолжения |
| --- | ---: | ---: | ---: | ---: | ---: |
| Android | 21,262 с | 20 с | 32,683 с | 33,263 с | 12 845 056 Б, 49 частей |
| Mac | 39,158 с | 20 с | 56,323 с | 57,225 с | 11 272 192 Б, 43 части |

В обоих Dart-журналах непосредственно зафиксирован TimeoutException ожидания
payload **20 с**. После ошибки открытие новой попытки заняло 0,580/0,902 с.
Это подтверждённый вклад локальной политики ожидания, не только предположение
по похожему числу. Почему старый stream после возврата radio не восстановил
устойчивую доставку до этого timeout, ещё не установлено.

Для Mac-получателя файл стоял на 11 272 192 Б — **33,6%**. Но native prefix
старого stream продвинулся ещё примерно на неполную часть; последнее наблюдаемое
продвижение было на 36,629 с. Оно не дало новой целой проверенной части. Поэтому
39,158 с нельзя назвать 39 секундами непрерывной сетевой тишины. У этого stream
интервал между native-срезами доходил до 7,277 с, что также ограничивает точность
вывода. На Android-получателе старая попытка наблюдалась примерно до 13,6 с;
новая затем обслужила оставшиеся байты. Большие интервалы между разными streams
не спрятаны под максимумами продвижения каждого отдельного stream.

Перед сбросом у отправителей наблюдались consecutive RTO 4/3, RTO доходил до
10 с. Новые streams завершились без наблюдаемого consecutive RTO; у них
продвижение prefix между срезами не превышало 0,561/0,564 с. Метрики каждого
stream и интервалы записи частей сохранены раздельно. Выбор больших streams
основан на изолированных временных окнах и продвижении >512 КиБ, не на формальном
CID↔stream join. Android/host clocks выровнены с half-ADB-bound 33,84 мс;
повторная оценка offset изменилась на −9,016 мс. Dart retry durations взяты
относительно его же записи API-запроса, без предположения о timezone.

## Закрытие потоков и endpoint drops

Наблюдались восемь endpoint retire-событий успешных streams с EOF,
FIN requested/sent/acked и linger. Ещё четыре retire относятся к двум
оборванным старым streams: это reset/abort без EOF/FIN, а не успешное закрытие.
Endpoint mux: Full=0, Closed=0, invalid=0. Unknown — по два на каждом конце:
две DATA по 1982 байта на Mac и два ACK на Android. По приватным stream IDs
они совпали с уже сброшенными streams и пришли через 0,142–0,213 с после
retire. Эти четыре кадра атрибутированы; давние сотни unknown из других серий
этим не объяснены. Счётчики реле/per-hop в данной серии не снимались, их потери
нулевыми не объявляются.

Снимки питания и службы сохранены отдельно в summary. Это не Doze-сценарий и
не проверка многосуточного фона. Звонков и микрофона в серии не было.

## Очистка и остаток

Trace выключен на обоих QA-узлах, p2p/anonymous настройки возвращены. Контейнеры
закрыты штатно; Mac/Android приложения и logcat завершены, группы процессов
проверены, ADB-forward удалён, оба API-порта свободны. Debug property восстановлен.
Исходные preferences возвращены побайтно; исходный QA APK переустановлен и
проверен по фактическому установленному SHA. Ratchet/БД не откатывались.
Wi-Fi/data и whitelist проверены. Синтетические удалённые файлы отсутствуют;
на host после SHA-проверки удалено 110 101 986 Б source/result фикстур.

Следующий вопрос — почему после возврата сети зависает именно старая circuit/
stream-попытка и когда можно безопасно признать её непригодной. Обнаруженный
20-секундный idle timeout не уменьшен ради числа без проверки slow-link и
reordering сценариев. Общие причины файловых пауз, исходный «33%», Windows и
полная multi-device матрица остаются открытыми. Push/релиза нет.
