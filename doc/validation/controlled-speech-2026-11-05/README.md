# Контролируемый речевой стимул — 2026-11-05

Продолжение [проверки актуальных движков Windows ↔ Android](../current-audio-windows-android-2026-11-05/README.md).
Production-код не менялся. Windows 11 и Blackview, текущие QA-движки с 107 API;
это не исходная пара Poco/mobile ↔ Windows из пользовательской жалобы.

## Методика

При подготовке обнаружено, что текущий default output Mac — внешние наушники.
Маршрут предыдущего речевого опыта не был записан, поэтому его историческая
причина не устанавливается. Новый операторский `speaker_stimulus.swift`
явно выбирает встроенные динамики для своего потока, проверяет фактическое
устройство до и после запуска и ждёт completion `dataPlayedBack`.
Системные default output, mute и volume не меняются. Встроенная громкость
системы оставалась около 0,125; gain потока — отдельно 0,5 или 1.

Источник — первые шесть секунд WebRTC `audio_long16.pcm`, нормализованные
до пика 0,8. В 40-секундном WAV три одинаковых речевых участка: 5–11,
17–23 и 29–35 с; между ними тишина. Это воспроизведение рядом с телефоном,
а не подмена микрофонного ввода приложения. Сырые записи микрофонов не делались.
Android сообщил встроенный микрофон и источник `VOICE_COMMUNICATION`.

Первая попытка с gain 0,5 дала 128 срезов и завершившийся источник, но не
установленный речевой рисунок. Затем один звонок телефон → Windows использован
для NS on → off → on: три проигрывания с gain 1, 365 срезов. Все источники
завершились; call и media epoch сохранились, AEC/AGC оставались включены.
NS возвращён в on. Native interruption count/duration и discarded packets
равны нулю в этом наблюдении; это не оценка слышимого качества.

## Результат: речевой тракт не квалифицирован

`analyze_stimulus.py` требует завершившегося источника, неизменного звонка и
epoch, фактических native capture/playout и настроек обработки. Повторные
чтения кэшированного stats не считаются независимыми измерениями. Отбрасываются
1,2 с у каждой границы; каждый участок требует минимум двух уникальных срезов.
Все три speech-медианы должны превышать quiet baseline минимум на одну
полосу на входе телефона **и** выходе Windows во всех трёх фазах.

Фактический результат — **exit 2: источник завершён, рисунок не установлен**.
Отключение NS подняло фоновые полосы, но одновременно и в quiet, и в speech
окнах. Это не доказательство захвата речи и не доказательство её подавления.
Числа в `summary.json` — агрегаты порядковых полос, не dB или SPL.

Слышимость человеком, акустическая связь источника с телефоном, эффективность
AEC/NS и исходная жалоба остаются открытыми. Оснований менять production gain
по этому опыту нет. Даже положительный oracle не заменяет прослушивание.

## Проверка инструментов и уборка

Девять тестов oracle прошли: положительный рисунок, постоянный шум, пики вне
окон, повтор кэшированных stats, отсутствие playback completion, смена call,
несовпадение NS, отсутствие рисунка на удалённом выходе и смена media epoch.
Первый вариант oracle пропускал две проверки предусловий; assertion-red
относится к новому инструменту, не к дефекту приложения.

Публичный Swift-вариант компилируется с `-warnings-as-errors`; отдельный
секундный silent probe подтвердил completion, число rendered frames и
неизменность default output. Физическая серия использовала приватную копию
с той же успешной playback-логикой; публичная копия скрывает исходные тексты
ошибок сторонних API. Их побайтовая идентичность не заявляется.

Операторские JSONL содержат локальные часы и остаются приватными. Публичный
analyzer выводит только агрегаты. QA-приложения остановлены, свои Windows
tasks/runtime и ADB forward удалены, процессы и порты проверены. Артефакты
Windows и установленный QA APK сохранили проверенные SHA. Обычные профили,
сиды и engine release pins не менялись; push и релиза нет.
