# Ratchet I/O: повтор неопределённого commit и цена резервов

Проверка 2026-10-31, без push/релиза. SDK `c46d94db` не менялся.

## Подтверждённый дефект повторной выдачи floor

`putSetting` мог успешно закоммитить резерв, но вернуть ошибку после commit
(например, потерян ответ worker). В этой ветке RAM-cache ещё не заполнен,
`advanceRollbackAnchor` не вызван и native floor не выдан — это правильный отказ.

Но следующий `reserveBeforePublish` читал уже durable marks, видел, что они
покрывают позицию, и выдавал floor без попытки обновить rollback anchor:
локальная переменная `wrote` была false. Это не потеря самого резерва при
обычном restart: записанные marks остаются. Пробел касается дополнительной
защиты от отката контейнера между старым anchor и новым резервом.

Красный контроль на `5e416f8b`: injected failure AFTER настоящего вызова
`super.putSetting`, прочитанные marks присутствуют, native permission ещё нет;
после retry ожидается одна anchor attempt, фактически **0**. Это сценарий
на HVS/FakeKvLogStore, не воспроизведение сбоя носителя у пользователя.

Теперь fresh read покрывающих marks также требует anchor attempt перед
выдачей floor. У них нет process witness предыдущей попытки — в отличие
от warm RAM-cache. Изменён предикат, а порядок записи/reservation/anchor/permit
не ослаблен; warm hit не добавляет ни запись, ни anchor attempt.
Возврат `false` из anchor остаётся существующим best-effort режимом с
константным предупреждением; успешная запись anchor не выдумывается.

Итоговый тест дополнен gate: после retry marks durable, anchor attempt
удерживается, **native seal всё ещё запрещён**. Только после завершения
попытки он разрешён. Следующий warm precheck не делает второй attempt.
Исходный тест held-anchor для новой записи, failed/uncertain commits,
retired/superseded владельцы, ротация/sibling и nonce recovery сохранены.

**255 unit/security + 4 native ABI = 259 тестов прошли**, 0 skipped в полном
наборе с обеими library env. Дополнительный warm-cache assertion затем прошёл
в отдельном targeted запуске без изменения production source. В раннем запуске
без library env один ABI тест был skipped и не считался зелёным; полный набор
выше его выполнил. Scoped analyze изменённых файлов: no issues.

## Атрибуция оставшегося ожидания

Пассивный private fixture разделяет reservation settings, anchor attempts
и snapshot writes. Все записи остаются настоящими HVS/worker/native calls.
Значения settings, ключи и blob не попадают в эти тайминги.
В расширенном fixture цепи и conversations получают только synthetic локальные
индексы; positions читаются через существующий native opaque-state ABI.
Публичный отчёт содержит агрегаты, без этих correlation ids.

| Профиль | Резервы: вызовы / медиана / максимум, мс | Snapshot: вызовы / медиана / максимум, мс | Anchor attempts |
|---|---|---|---:|
| До фикса, timing | 311 / 47.794 / 220.746 | 406 / 52.722 / 252.085 | 263 |
| Финальный, timing + positions | 300 / 48.620 / 265.156 | 409 / 49.214 / 224.330 | 254 |

Оба профиля — один Mac/JIT process, 12 разных production-PoW личностей,
свежие encrypted containers, локальный TCP/DHT, реальные ratchet/host
checkpoint и MessagingService fragmentation/ACK. Group legacy без epoch
encryption, roster подготовлен отдельно. Это не multi-device/телефон/Windows
и не публичные onion-реле. Библиотеки те же, их SHA после codesign и
происхождение проверены; финальный source SHA до/после закреплён.

Это **не A/B скорости**: у второго profile дополнительная инструментировка
и другой ход очередей. Всем 12: первый профиль **4322/2984/2177/2724 мс**,
второй **4418/2606/2162/2529 мс**. Этот fix не объявляется ускорением доставки.
Anchor fixture не настроен на внешний keychain: попытки возвращаются быстро,
но измерения **не квалифицируют реальную запись внешнего anchor**. Она
проверяется отдельными rollback-anchor unit/wiring сценариями.

Суммы длительностей reservation writes: 18,34 / 18,46 с; snapshot writes:
24,92 / 23,99 с. Они перекрываются между 12 узлами и не являются долями
одного критического сообщения. Длительность API также включает ожидание
worker; это не чистая длительность fsync и не сетевой RTT.

### Что означает частота резервирования

В первом профиле 311 записей на 263 прохода с anchor attempt. 245 проходов
пишут по одному резерву, остальные — по 2–5. Простое пакетирование только
таких проходов могло бы убрать не более **48** отдельных записей.
Во втором 300 записей / 254 прохода; тот же верхний предел — **46**.
Это не измеренное ускорение и не обещание экономии wall-clock.

Position trace второго профиля показывает **303 новых sending-chain id,
0 расширений ранее наблюдавшейся цепи** среди изменённых marks. Поэтому
увеличение `reserveAhead=32` само по себе не объясняет и не устраняет объём:
записи нужны вслед за сменой цепи, не по исчерпанию 32 индексов одной цепи.

**246 из 300 записей** уже имели ранее завершённый snapshot с каждой
изменённой цепью; позиция snapshot + 32 покрывала позицию при последующей
записи резерва. Это конкретный кандидат для следующей проверки:
сохранять snapshot и относящийся к нему резерв атомарно, а floor выдавать
после commit и anchor attempt. Такой путь пока **не реализован**.

Trace доказывает наличие подходящих ранее сохранённых состояний; он не
доказывает корректность будущего объединения. Потребуется сохранить whole-entry
atomicity, прежние более высокие marks, защиту при меняющемся native state,
retained V4 chains, bounded commits, ACK generation и cleanup. Сокращение
отдельных commit нельзя подменять отменой ratcheting или ранним permit.

## Гигиена и остаток

Оба stand завершили 4/4 сообщения у всех 12 ровно один раз: 44 visible events
каждого запуска, сохранённая единственность строк истории, timing dropped=0.
Итого 8 сообщений, host processes exited, 12 listeners каждого освобождены,
cleanup errors=0, временные stand roots удалены. Телефон/production-реле не
менялись; сторонние untracked отчёты не затронуты.

Долгая доставка и multi-device матрица остаются открытыми. Этот раунд исправил
реальный пропуск защитного действия при retry и уточнил следующий I/O участок;
причиной исторических невоспроизводимых жалоб его не объявляем.
