# Меньше отдельных транзакций для внутренних ID сообщений

Агрегаты: [summary.json](summary.json).

## Подтверждённый расход

Стендовый storage census теперь различает транзакции сообщений, группового
журнала, ratchet, авторизационных чекпоинтов и служебных настроек. Классификация
читает только namespace, фиксированные префиксы ключей и существующий
allowlist контекста файловой операции. Значения, payload и суффиксы ключей
не читаются и не становятся метками. Все новые средства измерения — в `test/`.

Строгое FIFO-сопоставление VM-трассы подтвердило основную стоимость:
в контрольном окне 42,316 с обработка 1142 commit заняла 23,269 с.
Служебному учёту внутренних ID соответствуют 250 commit и 4,876 с обработки.
Handler включает native/FFI и Dart worker adapter; это не чистое время fsync.
Суммы ожиданий параллельных RPC пересекаются и не считаются wall time.

Причина лишних транзакций установлена по коду и публичному storage API:
фиксированный резерв в восемь ID требовал отдельной durable-записи после
каждых восьми выдач. На 256 последовательных сообщениях — 32 записи резерва
как в in-memory backend, так и через настоящий native worker.

## Изменение

После открытия резерв начинается с прежних восьми ID. Только после успешной
durable-записи он увеличивается вдвое, до предела 64. На длинной догрузке
служебная запись требуется реже; новая короткая сессия не наследует большой
резерв. Более крупный явный batch по-прежнему резервируется целиком.

До окончания сохранения диапазона ID никому не выдаются. Проверка storage
session, единственный активный reservation и ожидание записи сохранены.
Message/outbox commits, shard markers, ratchet и authorization barriers
не менялись. Формат контейнера и wire прежние. После прерывания допустимы
неиспользованные внутренние ID из последнего резерва; теперь его предел
для обычной выдачи — 64 вместо восьми. Это не номера сообщений разговора:
их отдельный gap-free cursor остаётся частью транзакции события.

## Проверки

- На точном прежнем production-файле: одна assertion-red и три passed в
  focused in-memory suite; отдельный native тест тоже assertion-red на
  `32 > 8`. Ошибки сборки не засчитаны. Candidate восстановлен побайтно.
- Candidate: четыре focused passed. Проверены малый резерв после reopen,
  сохранность и уникальность ID, непрерывность локальной conversation seq,
  отказ записи, потеря ответа уже записанного резерва, отсутствие публикации
  до его завершения и clamp у последнего message shard.
- Связанные suites: **209 passed / 7 skipped**. В том числе 31 проверка
  счётчиков, приватности и VM-разбора. Эти наборы пересекаются с focused.
- Реальная HVS: **16 passed / 0 skipped** — batch/ordering, отказ и потеря
  ответа commit, maintenance, shard crossing, большой outbox, плюс 256
  последовательных сообщений с двумя реальными перезапусками worker.
  Все старые и новые сообщения сохранились без замены ID.
- Analyzer и diff checks чисты.

Первый измерительный прогон обнаружил пропуск новых меток в collector:
транзакции были `unclassified`. Он не использован для сравнения категорий.
После исправления collector пропускает только фиксированные метки; тест
проверяет сохранение известной категории и удаление произвольной/приватной.
Оба зачтённых окна имеют полное FIFO-соответствие, непрерывную sequence,
один worker и ноль `unclassified`; суммы категорий точно равны всем commit.

## Native A/B/C: догрузка 2000 сообщений

Три Mac/JIT процесса, две личности, три loopback Core; настоящие
transport/ratchet/HVS, provider fixture без полного foreground SessionPipeline.
Сравниваются отдельные прогоны прежнего и нового production-кода с одинаковыми
native artifacts. Identities, caches и scheduling в них свежие.

| Измерение | Прежний резерв | Растущий резерв |
|---|---:|---:|
| Все 2000 строк видны | 32,633 с | 32,231 с |
| Итоговые ID, порядок, позиции и delivered сошлись | 37,860 с | 32,236 с |
| Commit учёта ID, окно census | 253 | 42 |
| Commit учёта ID, закрытое FIFO-окно | 250 | 41 |
| Их worker handler time | 4,876 с | 0,830 с |
| Все commit в закрытом FIFO-окне | 1142 | 915 |
| Их worker handler time | 23,269 с | 18,834 с |

Потерь/дублей нет, все 2000 строк delivered, повторов завершённой истории — 0.
Разные окна census/VM не приравниваются. Уменьшение служебных commit
подтверждено непосредственно. Универсальное end-to-end ускорение не доказано:
по одному прогону, опрос около пяти секунд, count-complete почти не изменился.
Ранняя полная сходимость — наблюдение этой серии, не обещание выигрыша 5,6 с.

Медленная догрузка остаётся активной. В candidate VM-окне наибольшая
оставшаяся цена — 429 message commit / 8,612 с handler; групповые
header/segment/pair вместе — 288 commit / 6,074 с; ratchet — 147 / 3,100 с.
Следующий разбор должен отличить обязательные durable-записи от повторной
обработки и ожидания порций; эти цифры не оправдывают снятие барьеров.

## Границы и очистка

SDK `b9b88bb7` и HVS `eceb9158` не менялись. SHA выбранных immutable FFI/CLI/HVS
проверены до/после; 1504 source/package inputs каждого прогона неизменны,
CPU profiles содержат samples. В baseline OS mappings дополнительно
подтвердили обе выбранные библиотеки у трёх клиентов. В candidate эта поздняя
попытка пришлась на завершённые процессы и дополнительным proof не считается.
Позднее добавлен только native regression test; production-файл тот же,
что участвовал в candidate stand.

Проверены по 22 PID и 35/34 порта соответственно: своих процессов/listeners
нет, runtime roots удалены. Native fixtures закрыты и удалены. Сырые журналы,
адреса и идентификаторы остаются в приватном cache. Телефон отключён;
mobile handover, длительный offline/crash и полный multi-device здесь
не проверялись. Пользовательские контейнеры и production не менялись.
Push/релиза нет.
