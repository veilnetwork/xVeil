# CPU-профиль получателя на 100000 сообщений

## Результат и границы

Продолжен настоящий native-стенд на **100000 архивных сообщениях**, а не
уменьшенная модель. Четыре Mac/JIT процесса, три изолированных Core,
настоящие FFI/ratchet/зашифрованное хранилище. Два устройства одной личности
отдают одинаковый архив третьему. Первые authenticated ответы обоих источников
получены до снятия барьера применения. Прежняя строка получателя сохраняется.

Повторный диагностический прогон прошёл: **100001 строка** совпала по ID,
телу, delivered, canonical positions и порядку, без пропусков, дублей и лишних
строк. Оба cursor завершены; отдельное холодное открытие без всех источников
подтвердило сохранность. Wire/census не обрезаны. Callback count — 200002,
message commits — 1563, cursor commits — 1566, allocator commits — 393.

Apply release → финальная проверка: **236305 мс**. Здесь включён CPU sampler;
это **не A/B и не измерение ускорения или регрессии** относительно прежней
серии без профилировщика. Production-код в этом цикле не менялся.

## Почему нужен потоковый захват

CPU-буфер VM ограничен: выгрузка только при завершении длинного сценария
может сохранить лишь его хвост. Добавлен opt-in witness локального VM endpoint
для внешнего периодического sampler. Witness привязан к PID и origin окна,
пишется через rename, требует инициализированный loopback endpoint и приватный
evidence directory. При рестарте другой PID не подменяет текущий захват.

Endpoint URL — локальная управляющая capability, а не анонимная диагностика.
Witness, VM function metadata, сырые стеки и адреса остаются только в приватном
evidence. Приложение и его экспортёр этот test helper не импортируют.

Sampler читал только VM/isolate metadata, timeline micros и CPU samples;
после первоначального reset worker не очищал буфер между запросами. Окна
перекрывались на секунду. Ответ ограничен 64 МиБ, сериализованный поток —
512 МиБ, compressed — 128 МиБ; сохранена лишь используемая таблица функций
с перенумерацией stack indices. Фактический gzip — около **3,15 МиБ**.

Первый захват **невалиден**: лимит ответа 12 МиБ не вместил таблицу символов,
получилось 0 chunks. Его native-прохождение не засчитано как CPU-профиль.
После завершения и уборки первого стенда лимит исправлен, выполнен новый
полный прогон; исходный отказ сохранён приватно.

Ключ дедупликации — PID/thread/timestamp. Один terminal endpoint error,
нет начального разрыва и samples вне запрошенного окна; лимиты не достигнуты.

а не нулевой расход CPU. Окно VM включает заключительные проверки и отличается
от apply→convergence; эти времена нельзя вычитать как цену sampler.

Inclusive counts перекрываются: их нельзя складывать или объявлять долей
wall time. Это указатели на стек работы, а не доказательство причины всех
ожиданий. Следующая проверка — повторные вычисления control/epoch material при
свежем чтении адресов своих устройств. Сохранять завершённый membership cache
или обходить проверки отзыва ради ускорения нельзя. При пустом материале
проверить возможность устранения вычислений без изменения результата.

## Проверки и уборка

Новый integration test проверяет endpoint/PID живой VM, повторный reset и
атомарную замену witness; отдельно проверяется отказ до инициализации.
VM integration требует `XVEIL_E2E_CPU_PROFILE=1` и `--enable-vmservice`, как
остальные opt-in profiler checks. Обычный Flutter runner отключает VM service:
ранняя попытка без opt-in упала и не засчитана как прохождение. После разделения
проверок обычный режим: **23 passed / 1 явно skipped**; opt-in: **24 passed**.
Analyzer трёх изменённых Dart-файлов чист.

На время прогона заморожены **1532 inputs**; cleanup подтвердил исходники,
те же закреплённые native-библиотеки и ABI, чистый SDK. Позднее изменён только
тест нового witness, чтобы штатный CI не требовал VM service; production,
worker и helper соответствуют профилированному варианту.

Проверены 49 owned PIDs и 94 порта, живых процессов/слушателей не осталось,
синтетический runtime удалён, sampler завершился с кодом 0. Сырой профиль
ограничен по размеру и остаётся вне Git. Push/релиза нет. Latency, физическая
AOT-квалификация, NETCALL-01 и оставшаяся multi-device matrix остаются открытыми.
