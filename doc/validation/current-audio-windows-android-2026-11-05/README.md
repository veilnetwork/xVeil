# Текущий медиадвижок: Windows ↔ Android — 2026-11-05

База xVeil `3e8cea24`, Veil `b8647716`, hidden-volume `eceb9158`.
Изолированные QA-профили Windows 11 (10.0.26300.0) и Blackview; обычные
приложения и чужие QA-профили не менялись. Это квалификация ранее написанных
аудиоправок, без новых изменений production-кода, push, релиза и обновления сидов.

## Сборки

Предыдущий [signaling-прогон](../windows-android-signaling-2026-11-05/README.md)
использовал старый release engine и не квалифицировал аудио. Теперь оба
медиадвижка собраны заново из текущего дерева C++, с WebRTC pin
`4ef980bc2c70834276c791e71e7834b8809f24ad`. DLL/ELF содержат все **107** функций,
которые использует Dart, включая оба noise-suppression setter. Проверены
source digest, исходники после сборки, binary SHA и опубликованный SHA SDK.
Test hooks не включались; новый immutable release pin не публиковался.

Windows использует SDK compiler/flags и новый AOT с текущим Dart. Приватная
адаптация SDK setup устраняет вложенный JSON-массив на PowerShell 5.1; C++ и
проектный build script не менялись. Android собран на macOS Chromium clang
той же revision, с target/headers/flags SDK, его Chromium libc++ objects и
NDK 28.2 link driver. Наличие одних заголовков в старом очищенном кэше не
считалось готовым SDK: получен полный закреплённый bundle.

APK проверен **до установки**: все три библиотеки совпадают с выбранными
исходными артефактами после штатного ELF strip; Dart inputs и операторский
ресурс проверены отдельно. SHA установленного APK совпал. Windows bundle
сверен по exe/AOT/Veil/HVS/media SHA перед запуском и после остановки.
Veil/HVS использованы из ранее квалифицированных отдельных targets.

Незачтённые попытки сборки: неверный cwd в подготовке Android; затем
непреднамеренный automatic multi-ABI Cargo при сборке frontend. Они не
устанавливались как аудиокандидаты. Финальная сборка явно использует
`VEIL_SKIP_CARGO=true`, заново поставленные проверенные FFIs и mount-watchdog.
Ошибка имени Android activity, неверные адреса debug endpoints и ошибки
наблюдателя UI также не засчитаны как продуктовые находки.

## Физические вызовы

Оба профиля открыли прежние QA-контейнеры, настоящую сеть и принятый контакт.
Микрофон Android заранее разрешён только QA-пакету: это не проверка первого
диалога разрешений, экрана блокировки или фоновой работы.

| Инициатор | Интервал наблюдения | Результат |
|---|---:|---|
| Blackview → Windows | 39,905 с, 20 срезов | connecting → active; capture/playout стартовали на обеих сторонах, RTP в обе стороны |
| Windows → Blackview | 81,450 с, 40 срезов | connecting → active; те же положительные результаты, без самопроизвольного завершения |

Завершения выполнены явным `diagnosticApi` hangup; обе стороны зафиксировали
`hangup`. На последнем срезе каждого вызова capture/playout result=1,
AEC/NS/AGC=1. Native interruption count/duration и discarded packets равны
нулю. Это значения конкретных счётчиков, **не доказательство отсутствия
каждого слышимого пропуска**, MOS или пригодности нестабильного мобильного пути.

В первом вызове входная полоса уровня телефона и выходная полоса Windows
достигли 3; наблюдались ненулевые цифровые уровни и emitted samples. Это не
SPL, проверка выхода из конкретного динамика или прослушивание человеком.

Попытка стимуляции speech fixture через обычный выход Mac **не квалифицирована**:
пики пришлись за пределами ожидаемых восьми секунд проигрывания; его exit code
не записан. Причина не доказана (в том числе не измерены выходной маршрут и
акустическая связь с телефоном). Раннее предположение о прохождении именно
этой речи отозвано после проверки timeline. Успешное выполнение отдельного
playback-задания Windows также не доказывает захвата его речи микрофоном.
Передача контролируемой речи и слышимость в обоих направлениях остаются
непроверенными.

В обратном вызове через настоящий UI настроек Android переключено
**NS on → off → on**. Native `audio_ns_enabled` следовал выбору; AEC/AGC
оставались включёнными, call-ID и media epoch не менялись. Это первая
физическая квалификация данного переключателя на актуальном Android engine.
Эффективность подавления эха/шума в комнате и double-talk здесь не измерялись;
их модельные результаты описаны в
[проверке обработки речи](../call-audio-processing-2026-11-02/README.md).

## Реальные анонимные отчёты

Получены UI-экспорты после вызовов: Android через DocumentsUI, Windows через
видимую плитку копирования. Первый pull Android попал в ещё пустой открытый
документ и исключён; после завершения записи получен полноценный JSON.
Ограничение наблюдателя Windows проверено по фактической геометрии окна;
невидимая плитка не считалась нажатой.

| Отчёт | События / dropped | audioStart / callEnded | mediaSample | Ошибки |
|---|---|---|---:|---|
| Android | 251 / 0 | 2 / 2 | 123 | нет |
| Windows | 289 / 0 | 2 / 2 | 123 | один `transport-send / TransportUnavailable` |

Последняя запись имеет frames `fail_closed_transport` → `messaging_peer_sync`.
По этим данным её момент и связь с пользовательским случаем не установлены;
она не переименована в аудиосбой или исправленный дефект. Потери сообщений
этим событием не доказаны.

Оба отчёта прошли строгий allowlist событий, полей и конечных числовых метрик.
Проверено отсутствие известных QA паролей/ключей, полных ID и коротких
префиксов, текстов сообщений, операторского ключа, путей, имени пользователя
и raw microphone metadata. Аудиозапись из микрофонов не экспортировалась.
Сырые JSON, журналы и идентификаторы остаются вне репозитория.

## Остаток и уборка

Исходный Poco/mobile ↔ Windows случай, слышимость человеком, громкость,
акустическое эхо и шум **не закрыты**. Это другой телефон, Windows 11 и другой
сетевой сценарий. Новые движки остаются QA-кандидатами; опубликованные engine
pins старее текущего C++ и перед релизом требуют отдельного обновления всех
целевых платформ с source-digest guard. Видео и handover в этом прогоне не
проверялись; A/B ускорение не заявляется.

Приложения остановлены, PID и порты проверены. Все свои Windows scheduled
tasks и runtime, SSH/ADB forward, SAF-файл, UI dumps, стимул речи и лишние
копии/архивы удалены. Первая проверка остановки Windows увидела ещё выходящий
процесс; повторная проверка того же PID подтвердила завершение, перезапуска
не было. Зашифрованные QA-профили и по одному rollback для каждой платформы
оставлены; контейнеры не откатывались. На телефоне
оставлена остановленная изолированная QA-сборка.
