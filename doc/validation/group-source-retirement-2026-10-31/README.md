# Очередь первой отправки после ACK — 2026-10-31

**Подтверждено и исправлено:** ожидающая первая отправка group-sync оставалась
в очереди после подтверждения того же кадра другой копией. Outbox уже удалял
сохранённый кадр, но после освобождения полосы адресата source queue отправляла
его снова. Это лишняя работа отправителя, транспорта и получателя; её вклад
в ранее наблюдавшуюся минутную догрузку пока не измерен.

## Воспроизведение и исправление

Тест удерживает первую отправку одному адресату, ставит следующую в очередь,
подтверждает следующую и только затем освобождает первую. На исходном коде
после ACK отправлялся ещё один целый кадр либо четыре части snapshot.
Отдельный сценарий получает ACK через настоящий повтор Outbox, пока первая
отправка удержана. Барьер в конце той же полосы доказывает, что наблюдение
сделано после обработки очереди, а не после её удаления при shutdown.

`PostReceiptQueue.cancelPending` удаляет только ожидающее задание, завершает
его waiters и освобождает учтённые job/bytes. Поиск ограничен существующим
лимитом очереди — 128 заданий. Активный transport future сохраняет полосу и
бюджет до фактического завершения. Новых таблиц ACK/tombstone нет.

Обычное retirement отменяет ожидающую первую попытку по существующему ключу
epoch/адресат/frame. Даже если последующее удаление из хранилища откажет,
сохранённая строка остаётся для обычного повтора. Для ACK всего составного
snapshot отмена выполняется после успешного атомарного удаления строк.
Поштучный ACK отменяет только соответствующую ожидающую попытку: полная копия
составного snapshot сохраняется, и последующий Outbox retry может её отправить.
Авторизация ACK, привязка адресата, ratchet и durable apply не менялись.
