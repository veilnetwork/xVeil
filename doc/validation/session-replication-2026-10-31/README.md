# Первая сетевая публикация и досылка ключевых записей

Исправлены два подтверждённых механизма холодной доставки: первая сессия не
давала надёжного wake-up для сетевой публикации, а новые реплики ждали полного
republish до 60 с. В повторном чередовании финальной библиотеки медиана первого
сообщения всем 12 узлам: **5369 → 4495 мс**. Многосекундная доставка в целом
ещё не устранена; следующие сообщения не показали устойчивого ускорения.

## Механизмы и исправление

`route_updated` — общий Notify, который также обслуживает обычные ответы;
полагаться на него как на событие первой сессии нельзя. Резервный poll был
раз в 5 с. Во всех трёх новых контролях шесть первых полных сетевых публикаций
начинались уже после первой отправки приложения.

Теперь maintenance-задача подписывается на EventBus до spawn, реагирует на
`SESSIONS_CHANGED` и Lagged, а уже существующие живые сессии проверяет при
старте. Пятисекундный poll остаётся backstop. Startup и reload используют
один production-сервис; deferred placeholder по-прежнему ничего не публикует.

Первый ранний publish может застать только одного соседа. Простое ускорение
его запуска без исправления размещения оставляло бы остальные реплики за
60-секундным debounce. Поэтому добавлена ограниченная досылка уже опубликованных
**собственных публичных** записей новым пригодным сессиям:

- те же signed bytes, без новой подписи/авторизации из непроверенного кэша;
- до 64 ключей и 512 КиБ payload; lease для допуска досылки 60 с, удаление ленивое;
- максимум существующий K на один текущий набор targets; история admission
  хранится только для текущего набора, с witness конкретной TX-регистрации;
- неизменившаяся сессия не получает повтор полного набора; смена регистрации
  требует новой отправки, неизвестные capabilities разрешены, NO_DHT_SERVICE
  исключён тем же селектором;
- для новой волны STORE создаётся свежий query ID: старый dedup не должен
  подавить размещение на узле, который раньше ещё не был пригодной репликой;
- события объединяются в 100-мс окно без продления установленного дедлайна;
  в быстрой досылке отказ очереди не ставит witness; повтор — через 1 с;
  после полного publish такая проверка запускается отдельно;
- полный publish очищает предыдущий набор, поэтому удалённые из очередного
  bundle ключи не остаются в быстром repair; переполнение tracking оставляет
  обычный путь публикации;
- при обнаруженной замене значения в локальной DHT прежний snapshot удаляется:
  новые байты не считаются авторизованными и автоматически не перепубликуются.

Последний пункт пойман отдельным красным тестом собственного кандидата:
старый lease повторно отправлял прежний payload после локальной замены другим
писателем. Это не приписывается пользовательской жалобе. Уже поставленные
в очередь кадры этим не отзываются; подписи и monotone authorization floors
проверяются принимающей стороной по прежним правилам.

Все отправки идут через прежний aggregate paced BACKGROUND queue:
**8 КиБ/с, 64 pending frames, 512 КиБ, MAX_WAIT 60 с**. Приоритеты и ограничения
реле не менялись. Admission — локальная очередь, не подтверждение хранения или
доставки. Обычные полные публикации, on-change/key rotation и topology debounce
сохранены как backstop; быстрый lease не заменяет их и не хранит приватные ключи.

## Тесты

Два случая воспроизведены на прежнем сервисе в виртуальном времени:
первая сессия не публикует до fallback, новый сосед не получает запись внутри
полного debounce. Первая попытка второго теста не достигла control-публикации
и не зачтена; control исправлен, затем тест упал именно по отсутствию досылки.
Финальные проверки события опираются на EventBus без дополнительного Notify.

Шесть тестов placement проверяют реальные FrameOutbox/RecursiveQuery STORE:
новые и заменённые регистрации, отсутствие повторов старым, свежие query ID,
отказ/повтор после наполнения настоящей очереди, замену payload, reset bundle,
лимиты ключей/байтов/lease, fallback, capabilities и локальную замену записи.
Отдельный прежний тест искал строку ветки в исходнике; он заменён проверкой настоящего сервиса:
оба соседа получают document, registry и certificate, проверяются подпись
документа, полный реестр, instance, ML-KEM/X25519 против реально удерживаемых
ключей. Это не ослабление старого guard до проверки наличия метода.

Финальная совместная проверка: **778 runtime + 286 dispatcher + 196 IPC +
671 session = 1931 passed**. **24 ignored отдельно**. Release собран без
`test-low-difficulty`; sentinel-имена новых тестов отсутствуют в фактической
квалифицированной библиотеке. Cargo target на внешней ФС проверялся watchdog,
mount не терялся. SHA библиотеки проверен после codesign; финальный бинарник
отличается и от контроля, и от промежуточного кандидата до snapshot-guard.

## Чередование финальной библиотеки

Одна и та же fixture, tracing policy и 12 production-PoW личностей; свежие
контейнеры/instance ID в каждой фазе. Native TCP-loopback/full mesh на одном
Mac/JIT host, все 12 leaf обслуживают DHT. Настоящие GroupService,
MessagingService, ratchet и peer-authorization persistence, encrypted stores.
Legacy-группа без membership-epoch encryption; roster provisioned без парного
контактного handshake. Это не полная multi-device матрица и не mobile-ISP стенд.

Сборка и общие тесты завершены до начала A/B; одновременно с native-фазами
Cargo не работал. Контроль заморожен по SHA; финальный snapshot-guard включён
во все три B. Промежуточные измерения до него не смешиваются с таблицей.

|---|---:|---|---:|
| A1 | 5785 | 2680 / 3423 / 3064 | 80 |
| B1 | 4720 | 2992 / 2717 / 3435 | 0 |
| A2 | 5290 | 2660 / 3621 / 2934 | 80 |
| B2 | 4252 | 2526 / 2573 / 2821 | 0 |

Timeout — истечение ожидания одной независимо опрашиваемой реплики в поиске,
связанном с отправкой приложения (op>0); не число потерянных сообщений и не
обязательно провал всего lookup. В каждом прогоне все 4 сообщения пришли на
каждый узел ровно один раз. Все три B по первой доставке быстрее каждого A в этой серии;
выборка мала, instance-key placement различается. Медиана первого сообщения
5369 → 4495 мс; следующая тройка медиан 2660/3423/2934 → 2992/2573/3331 мс.
Устойчивого выигрыша следующих сообщений не заявляется, они меняют отправителя.

До первой отправки число записей, оставшихся только у владельца:

| Набор | Document | Registry | Certificate |
|---|---:|---:|---:|
| A1 / A2 / A3 | 6 / 6 / 6 | 8 / 8 / 6 | 8 / 8 / 8 |
| B1 / B2 / B3 | 0 / 0 / 0 | 0 / 0 / 0 | 0 / 0 / 0 |

Считаются точные байты текущей записи владельца в снимках локальных DHT,
без усечения; совпадения prefix-классификации проверены на единственный полный
ключ. Это наблюдаемая копия, не STORE ACK. В контролях по шесть полных publish
начинались после post; у B — ни одного. Квалификация показывает и время запуска,
и фактическое появление копий, не только вызов publisher.

## Состав с локальными Core

Отдельная финальная фаза: **3 Core DHT/onion-relay + 9 leaf без DHT**.
Входящие PublishedRendezvous circuit подтверждены у всех девяти leaf.
4/4 сообщения всем без дублей: **5205 / 2911 / 2112 / 3158 мс**. В этой фазе
перед первым post все собственные doc/registry/cert имеют удалённые копии.
С all-DHT A/B времена не сравниваются из-за разных ролей.

В этом составе остаются **34 app-triggered replica timeout**, без наблюдаемого
приёма в qtag/walk-tag трассе; три сопоставлены с sampled refusal лимитера.
Причина остальных не установлена. Ноль таймаутов в основной серии не означает
их устранения на всех топологиях. Это один из следующих участков разбора.

Во всех семи финальных фазах nodes stopped, 12 listeners freed, host process
exited проверены; собственные временные контейнеры удалены. Телефон и
production-реле не менялись. Сырые ID, документы и журналы приватны; здесь
агрегаты: [summary.json](summary.json). Без push и релиза.

## Остаток

Холодные 4,3–4,7 с основной серии и примерно 2,3–3,4 с последующих сообщений
не закрыты. В B3 первый native transport callback был через 194 мс; дальнейший
путь включает сохранение/ratchet и несколько пересылок. Есть native seal
1,0–1,55 с без истечения DHT-реплик: этот этап ещё надо разделить на resolve,
ожидание host checkpoint и собственно seal, не объявляя разницу ping/loss.
В составе с тремя Core отдельно остаются молчащие/отказанные DHT-ветви.

Затем — multi-device матрица по очереди владельца. Совместимость со старыми
версиями отложена; случаи 25 с / 120 с / «33%» не возвращены в активную очередь
без нового воспроизведения.
