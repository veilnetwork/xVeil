# NETCALL-01: уведомление терялось при закрытии временного клиента

Дата: 2026-11-01. База SDK `8eab7507`. Продолжение
[разложения задержки сигналов](../call-signaling-delay-2026-11-01/README.md).
**Подтверждён и исправлен отдельный дефект доставки локального уведомления.
NETCALL-01 остаётся открытым; физический active-handover этого цикла не прошёл.**

## Подтверждённый механизм

`VeilFlutterTransport.networkChanged` создаёт отдельный VeilClient, отправляет
уведомление и немедленно закрывает его в `finally`. Это изолирует управление
от занятых mailbox/media writer. Но `notify_network_changed` возвращал успех
сразу после enqueue в SharedWriter. При закрытии последнего FFI handle
уничтожается его RuntimeBundle; Tokio отменяет ещё не завершённые задачи,
включая writer. Наличие кадра в локальной очереди не гарантировало даже запись
в IPC-сокет, тем более вызов MobileEventForwarder.

Два regression упали на прежней семантике, без временных порогов:

1. На current-thread scheduler первая проверка future возвращала Ready до
   обработки узлом; новый контракт требует дождаться dispatch.
2. Настоящий VeilClient в отдельном временном current-thread runtime делает
   connect → notify → drop client → drop runtime. Настоящий IpcServer независимо
   обслуживается основной задачей. Прежде callback получил **0 уведомлений
   вместо 1**. Это воспроизводимый порядок выполнения, допустимый также для
   очереди многопоточного FFI runtime; не утверждение, что каждый такой FFI-вызов
   на телефоне обязательно терялся.

Для второго красного контроля временно отключалась только новая barrier-строка;
исходник кандидата восстановлен побайтово в `finally`. Во время этого контроля
сборок Android/других Rust-библиотек не выполнялось. Физический тест использовал
уже собранную и проверенную библиотеку кандидата.

## Исправление и границы

После enqueue SDK выполняет существующий `node_identity` RPC **на том же
соединении**. Обработчики NetworkChanged и GetNodeIdentity идут inline по FIFO;
ответ второго свидетельствует обработку первого. Новой wire-команды, C ABI,
обхода авторизации, дополнительного сетевого маршрута и sleep не добавлено.
RPC использует штатный пятисекундный предел ожидания ответа. Отказ не объявляется
успехом; временный клиент закрывается в прежнем `finally`.

Успех означает прохождение локального dispatch, **не восстановление удалённых
соединений**. В production IPC mobile sink установлен; сервер без такого sink
по-прежнему не приобретает эту возможность от самого barrier-запроса.
В тесте mode-updates удалено прежнее ожидание 50 мс: последующий network barrier
свидетельствует обработку предшествующих команд того же соединения.

## Физический прогон: Poco ↔ Windows 11

На Poco заменена только FFI в прежнем изолированном QA APK. AOT, manifest,
wrap, медиадвижок и остальные ZIP entries проверены неизменными; signing
certificate прежний. На Windows — SDK `8eab7507` предыдущего цикла; SHA реально
загруженной DLL проверен. Windows frontend также заморожен. Это квалификация
нового поведения отправителя уведомления на Android; Windows 10 не проверена.
Оригинальное условие одного активного узла **на момент place** не создавалось.

### Новый вызов сразу после Wi-Fi cut

Входящий появился на Windows через **7,281 с после place**. Первый fresh-RX
срез — через 11,493/11,503 с после cut; пять конечных свежих срезов с ростом
счётчиков получены с обеих сторон. Первый connecting/active срез телефона —
через 1,021 с после callee accept; первый свежий RX — ещё примерно через
3,101 с после этой выборки. Это sampled state/RX, не измерение слышимости речи.
В native-захвате есть `NetworkChanged(Cellular)`.

Один прогон, без фиксированного маршрута и A/B: разницу с прежними 16,652 с
доставки приглашения нельзя объявлять причинным ускорением.
[Обезличенный агрегат setup](setup.json).

### Смена сети внутри активного P2P-звонка — НЕ ПРОЙДЕНО

Предусловие: четыре подряд свежих P2P/RX-среза обоих концов. После cut приём
замер, через **21,186/21,208 с** наблюдатель увидел отсутствие вызова на
обоих endpoint. Полных 40 с наблюдения нет: звонок исчез раньше. Это отказ,
а не успешная проверка с короткой выборкой. В обоих devlogs причина завершения
— `livenessTimeout`, phase=active, route=p2p, 20 с тишины. Скрипт вызывает
hangup только в `finally` после фиксации исчезновения; ручной отбой этим
завершением не объясняется. [Обезличенный агрегат handover](handover.json).

Новый захват связал OS cut с реальной обработкой уведомления: примерно через
**0,696 с после cut** MobileEventForwarder получил Cellular и снял **одну**
живую TX-регистрацию. Часы телефона сопоставлены тремя ADB-пробами; лучшая
неопределённость полупрохода ~22 мс, это не точность сетевого измерения.

После этого в захвате наблюдались четыре `connect.fail` с `Network unreachable`
/ errno 101 около +3,15 с, затем таймауты подключения и один handshake timeout.
Первый наблюдаемый session.open другого peer — +16,300 с; session.open peer
звонка — +22,452 с, уже после завершения вызова. `session.open` не является
свидетельством пригодного media channel. Полнота всех console-событий не
заявляется. Relay recovery предпринималась, но проверка доставки кандидатов
не прошла; переключение вслепую и увеличение liveness timeout не добавлялись.

Это подтверждает, что в данном неуспешном handover уведомление **было обработано**;
вся оставшаяся пауза не объясняется его потерей. Появление отказа после правки
само по себе не доказывает её причинную регрессию: нет фиксированного маршрута
или A/B, а liveness-отказ уже наблюдался в более ранних циклах.

Следующая граница — dial/handshake при смене сети. В production select,
ожидающем `connect_peer_active`, есть отмена по обновлению endpoint, но нет
отмены по force-reconnect notification. Уведомление может прийти во время dial,
когда последующая backoff-ветка ещё не слушает Notify. Это **кандидат**, не
доказанная причина данного захвата; в этом цикле код connector не менялся.

## Завершение

Запущенные QA закрыты; процессы проверены завершёнными. Android QA APK и
Windows DLL восстановлены с проверкой SHA; другие библиотеки/AOT/runner
не изменились. Сетевые настройки и stay-awake телефона возвращены; PID
основного приложения совпадает с начальным. Собственные logcat, ADB-forward,
SSH-туннель, QA scheduled task и listener закрыты. Реле в этом цикле не
изменялись. Приватные журналы, идентификаторы, ключи и пути остаются вне
репозитория. Push и релиза нет.
