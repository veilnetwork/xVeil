# Ссылки master после прерывания сжатия — 2026-11-12

**Подтверждено:** новый контейнер может быть опубликован до обновления ссылок
master→child. После прерывания master-пароль открывает свою личность, но ключи
дочерних пространств в roster уже не работают. Собственный пароль child и его
данные остаются исправны. Это отдельный механизм; исходный пользовательский
отказ обоих паролей им не воспроизведён и не объяснён.

## Воспроизведение на выпущенной библиотеке

macOS arm64, production `AppController.compactStorageKeeping` и настоящие
`HiddenVolumeStorage`/worker-isolates, hidden-volume 2.7.1 из опубликованного
релиза. Перед запуском проверены загрузка и SHA-256 dylib:
`96d601a2ed4be5db8022a8502f3071082d7424ab89810da5f6697669487094cb`.
Код приложения соответствует `c3896f5f` (последнее изменение — документация).

Созданы два отдельных тестовых пространства с разными паролями; master хранит
реальные экспортированные ключи child. В child записан файл 70000 байт. Без
прерывания обычное сжатие и последующий вход через сохранённый roster проходят.

На границе compactor provider после настоящего native rewrite, но до возврата
в приложение сначала введён контролируемый отказ. Нормальный контроль проходит,
прерванный — assertion-red при открытии child по ключам master. Это проверяет
окно, но само по себе не является process-crash проверкой.

Затем тот же AppController/worker-путь запущен в отдельном Flutter test process.
После завершения native rewrite actor останавливается на управляемом барьере.
Его собственная группа процессов получает настоящий SIGKILL. Новый процесс
чтения подтверждает: master открывается, ссылка child не открывается, собственный
пароль child открывается и все 70000 байт совпадают. Нет повторного использования
открытого handle или данных из памяти actor. В первом запуске ошибся только
cleanup harness: повторный сигнал уже завершённой группе не засчитан как
квалификация; после исправления запуск выполнен целиком заново.

Это host-проверка production controller/storage с управляемой границей native
вызова, а не полный GUI-прогон, Android или потеря питания. Пользовательские
контейнеры, приложения и реле не использовались. Actor, reader и workers
завершены, отдельные тестовые контейнеры удалены.

## Нативная основа исправления — пока без интеграции приложения

В отдельной локальной ветке hidden-volume, коммит `f1cfe2a`, добавлен Rust API
`Container::prepare_compact_known` и отменяемый вариант. Они готовят новый
зашифрованный контейнер, удерживая прежний read-only под эксклюзивным lock.
Host может аутентифицированно исправить ссылки внутри подготовленного файла,
закрыть его handles и только затем вызвать commit. Abort ожидает cleanup;
Drop запрашивает отмену и не даёт разрешения на публикацию.

Используется прежний atomic rewrite helper: проверки исходного файла,
владение временным файлом, последний cancellation gate, inode/header pin,
rename, durability и типизированные предупреждения сохраняются. Копия паролей
native writer очищается перед ожиданием host. Журнал паролей или резервная копия
старого контейнера не добавлены. Ключи пространств по-прежнему меняются.

Проверены **38 integration tests и один отдельный lifecycle unit test**,
без skipped: десять новых prepared-сценариев и прежние repack/cancellation/
posture проверки. Среди новых — реальный SIGKILL подготовленного процесса
перед публикацией и после полного commit; свежий reader в обоих случаях
открывает child по сохранённым ключам master. Перед commit дополнительно
проверяется удержанный source lock и наличие непубликованного файла.
Также проверены abort после правки metadata, pre-fired/поздняя отмена, отказ
пароля, незакрытый staged handle, испорченный header, Drop и предупреждение
о hard-link alias. Исходные байты на путях отказа сравниваются до открытия.

Rustfmt и clippy для всех targets пакета проходят. Использованы отдельный
checkout и собственный Cargo target, не общий кэш другой версии. Первый
ошибочно отфильтрованный integration-запуск с нулём тестов исключён из счёта.

**Открыто:** C/foreign bindings и Dart/AppController ещё не переведены на этот
протокол. Этот коммит сам по себе не исправляет путь xVeil 0.13.98. Следующий
шаг — владение prepared handle на FFI-границе и перенос remap до публикации,
с проверками lock/wipe/cancel и повтором исходного SIGKILL-сценария.
Новая функциональность не запушена и не выпущена.
