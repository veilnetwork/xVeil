# Ссылки master после прерывания сжатия — 2026-11-12

**Подтверждено на выпущенной версии, исправлено локально:** новый контейнер мог
быть опубликован до обновления ссылок
master→child. После прерывания master-пароль открывает свою личность, но ключи
дочерних пространств в roster уже не работают. Собственный пароль child и его
данные остаются исправны. Это отдельный механизм; исходный пользовательский
отказ обоих паролей им не воспроизведён и не объяснён.

## Воспроизведение на выпущенной библиотеке

macOS arm64, production `AppController.compactStorageKeeping` и настоящие
`HiddenVolumeStorage`/worker-isolates, hidden-volume 2.7.1 из опубликованного
релиза. Перед запуском проверены загрузка и SHA-256 dylib:
`96d601a2ed4be5db8022a8502f3071082d7424ab89810da5f6697669487094cb`.
Код приложения соответствует `c3896f5f` (последнее изменение — документация).

Созданы два отдельных тестовых пространства с разными паролями; master хранит
реальные экспортированные ключи child. В child записан файл 70000 байт. Без
прерывания обычное сжатие и последующий вход через сохранённый roster проходят.

На границе compactor provider после настоящего native rewrite, но до возврата
в приложение сначала введён контролируемый отказ. Нормальный контроль проходит,
прерванный — assertion-red при открытии child по ключам master. Это проверяет
окно, но само по себе не является process-crash проверкой.

Затем тот же AppController/worker-путь запущен в отдельном Flutter test process.
После завершения native rewrite actor останавливается на управляемом барьере.
Его собственная группа процессов получает настоящий SIGKILL. Новый процесс
чтения подтверждает: master открывается, ссылка child не открывается, собственный
пароль child открывается и все 70000 байт совпадают. Нет повторного использования
открытого handle или данных из памяти actor. В первом запуске ошибся только
cleanup harness: повторный сигнал уже завершённой группе не засчитан как
квалификация; после исправления запуск выполнен целиком заново.

Это host-проверка production controller/storage с управляемой границей native
вызова, а не полный GUI-прогон, Android или потеря питания. Пользовательские
контейнеры, приложения и реле не использовались. Actor, reader и workers
завершены, отдельные тестовые контейнеры удалены.

## Нативная основа исправления

В отдельной локальной ветке hidden-volume, коммит `f1cfe2a`, добавлен Rust API
`Container::prepare_compact_known` и отменяемый вариант. Они готовят новый
зашифрованный контейнер, удерживая прежний read-only под эксклюзивным lock.
Host может аутентифицированно исправить ссылки внутри подготовленного файла,
закрыть его handles и только затем вызвать commit. Abort ожидает cleanup;
Drop запрашивает отмену и не даёт разрешения на публикацию.

Используется прежний atomic rewrite helper: проверки исходного файла,
владение временным файлом, последний cancellation gate, inode/header pin,
rename, durability и типизированные предупреждения сохраняются. Копия паролей
native writer очищается перед ожиданием host. Журнал паролей или резервная копия
старого контейнера не добавлены. Ключи пространств по-прежнему меняются.

Проверены **38 integration tests и один отдельный lifecycle unit test**,
без skipped: десять новых prepared-сценариев и прежние repack/cancellation/
posture проверки. Среди новых — реальный SIGKILL подготовленного процесса
перед публикацией и после полного commit; свежий reader в обоих случаях
открывает child по сохранённым ключам master. Перед commit дополнительно
проверяется удержанный source lock и наличие непубликованного файла.
Также проверены abort после правки metadata, pre-fired/поздняя отмена, отказ
пароля, незакрытый staged handle, испорченный header, Drop и предупреждение
о hard-link alias. Исходные байты на путях отказа сравниваются до открытия.

Rustfmt и clippy для всех targets пакета проходят. Использованы отдельный
checkout и собственный Cargo target, не общий кэш другой версии. Первый
ошибочно отфильтрованный integration-запуск с нулём тестов исключён из счёта.

Сам Rust-коммит не исправлял путь xVeil. Интеграция выполнена следующим раундом,
описанным ниже; в опубликованной 0.13.98 этого изменения нет.

## FFI, Dart и приложение

В hidden-volume `293792d` добавлен UniFFI `PreparedCompactionHandle`. Пустой
owner создаётся до дорогой работы, сохраняется вызывающей стороной; workers
перед каждым consuming-вызовом получают свой Arc clone. Объект Dart запрещено
копировать между isolates. Отказ или потеря ответа worker не отдают ему
исключительное владение: scoped helper в finally вызывает abort, ждёт завершения
и лишь затем освобождает owner. Native mutex удерживается через весь prepare,
commit или abort, включая join; abort не может ложно сообщить завершение,
пока другая операция ещё способна выполнить rename. Отмена до начала запрещает
поздний prepare. Future timeout сам по себе отменой не объявляется.

`AppController` теперь исправляет все masters через отдельный storage facade
подготовленного файла. Главный файл остаётся закрыт и удерживается native.
Повтор после ошибки относится только к metadata, не к repack. Неисправленные
ссылки, отказ закрыть staged handle или потеря session lease до выдачи разрешения
на публикацию сохраняют исходный файл. Финальные типизированные предупреждения
не запускают повторную перезапись или post-publication repair. Сообщение об
ошибке metadata теперь прямо говорит, что исходное хранилище не изменено.

Проверены **52 FFI-теста, 126 тестов Flutter-плагина и 144 app-теста**, без
пропусков в этих запусках. В app-набор включены реальные native-сценарии:
обычный commit, исключение непосредственно после commit, lock после repair до
commit, два разных master с сохранённым anonymous-флагом и child с файлом
70000 байт, а также прежние wipe/probe/auto-compaction/lifecycle/repair проверки.
При lock исходные байты сравнивались до нового открытия. Незакрытый staged
handle и ошибка callback проверены также через реальный Dart/FFI helper.
Rustfmt, clippy с `-D warnings`, targeted Dart analyze и сверка всех 49 UniFFI
checksum проходят. Неполный первый expanded-запуск с устаревшей подменой
compactor provider не зачтён; после исправления fixture весь набор запущен заново.

Повторён исходный процессный сценарий на исправленном production controller:
отдельная собственная группа Flutter actor получает **SIGKILL** после repair,
до публикации, и в другом запуске — после commit, до возврата в controller.
Свежий процесс-reader в обоих случаях открывает master, затем child его
сохранёнными ключами; собственный пароль child и все 70000 байт также исправны.
До публикации источник побайтно неизменен. Использована отдельная host-сборка
именно этого checkout, SHA-256 dylib:
`60dcface58cf5e5bc710e3587d9340208618047fa39eae72924ac73fd8be05ac`.
Actor, reader и workers завершены, тестовые контейнеры удалены.

**Границы host-серии:** это macOS arm64, native storage и Flutter/JIT controller-тесты,
а не Android GUI/crash, AOT или потеря питания. Android-серия описана ниже.
Исходный случай отказа обоих
паролей не воспроизведён и этим исправлением не объясняется. Новые изменения
локально закоммичены, не запушены и не выпущены. Перед следующей публикацией
потребуются новые сборки hidden-volume и последующая сборка приложения с ними.

## Подготовка Android проверки

Из `293792d` собрана arm64 native-библиотека для Android API 24, с отдельным
Cargo target и NDK 28.2.13676358. Проверены шесть prepared lifecycle exports
и четыре checksum exports. В отдельном profile AOT APK сохранены production
`AppController` и providers из `74277174`; SDK и медиадвижок взяты из
опубликованного arm64 APK 0.13.98, digest которого повторно сверен с GitHub.
В итоговом QA APK native bytes точно соответствуют подготовленным inputs.

QA использует отдельный application ID и синтетические личности. Штатные
onboarding, collection, password probe и compaction вызываются через приватный
package-gated fixture; barriers дают остановиться до или после публикации.
У fixtures явно выключены bundled seeds, meeting points и system bootstrap
DNS. Первый неустановленный APK с неявными настройками discovery заменён
сборкой с явным отключением до какой-либо проверки на телефоне.

Финальный APK собран и проверен по package/ABI, source hashes и native inputs;
статический анализ QA-области проходит. Состояние компилятора после сборки
восстановлено, его bytes не менялись. Собственные Android Cargo/APK build
intermediates удалены, финальные APK и native inputs сохранены отдельно.

## Проверка на Android

Телефон Blackview BV6600Pro, Android 11 (API 30), arm64. Проверен именно
подготовленный profile AOT APK: SHA-256 установленного APK совпал со сборочным,
новая native-библиотека присутствовала в maps свежего процесса-reader.
Основное приложение не заменялось. Две синтетические личности созданы
штатным onboarding: сначала скрытая, затем через «Начать заново» открытая.
У каждой свой пароль и файл 70000 байт; открытое пространство хранит roster
с ключами скрытого. Сжатие запускается настоящим controller после collection
и проверки обоих паролей, metadata исправляет production callback.

| Сценарий | Проверка результата |
|---|---|
| Обычное сжатие | Оба пароля, профили и файлы исправны; child открывается ключами master |
| Полный перезапуск после обычного сжатия | Новый процесс-reader повторил все проверки |
| Завершение после repair, до публикации | Исходный файл побайтно неизменен на барьере и после остановки; новый процесс-reader открыл оба пространства и child через master |
| Завершение после commit, до возврата в controller | Новый файл уже опубликован; после остановки новый процесс-reader открыл оба пространства и child через master |

В двух последних сценариях использован `am force-stop` только отдельного QA
package. До нового запуска подтверждено отсутствие его процесса. Файлы
сравниваются целиком, включая открытие child сохранёнными ключами, а не только
факт успешного ввода пароля. Не используются handles или кэш предыдущего
процесса. После проверки QA-приложение и его синтетический контейнер удалены,
его log reader остановлен, собственный ADB forward снят; пути и SHA-256 APK
основного приложения совпадают с исходными. Пользовательский контейнер
не читался и не изменялся.

Это физическая AOT-проверка controller/storage с управляемыми границами
вызова, не полный GUI-прогон сжатия и не потеря питания. Поведение Android при
lock во время repair отдельно не квалифицировано: подготовленный barrier
находится после возврата production callback и не проверяет его последний
session guard. Такой сценарий не запускался и не засчитан; host-проверка
правильной границы описана выше. Исходный отказ обоих паролей по-прежнему
не воспроизведён. Исправление локальное, не опубликовано.
