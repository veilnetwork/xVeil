# NETCALL-01: закрытие исходящей очереди при смене сети

Дата: 2026-11-01. SDK `5ded5aca` (на базе `8e3fe2ce`).
Исправлен подтверждённый дефект ожидания в SessionRunner.
**Пауза аудио при Wi-Fi → cellular остаётся открытой.** На исправленной Android
QA она снова наблюдалась; найденному механизму не приписывается вся пауза.

## Подтверждённый механизм и исправление

Mobile NetworkChanged удаляет старые TX-регистрации и уведомляет connector о
переподключении. Connector в это время может ждать завершения `runner.run()`.
При отсутствии других владельцев sender удаление регистрации закрывает outbox.
В начале runner-loop уже существовал штатный teardown по EOF этого канала.
Однако внутри `await_next_input` select-ветка `Some(frame) = recv()` игнорировала
EOF: закрытый канал выключал ветку, и задача ждала peer input, таймер или другое
событие. Само удаление регистрации не возвращало её к имеющемуся teardown.

Теперь EOF представлен отдельным `OutboxClosed`, после которого loop немедленно
возвращается к прежнему drain/EOF teardown. Отсутствующий outbox (`None`, режим
приёма без этой очереди) по-прежнему остаётся pending. Wire, C ABI, ключи,
авторизация, независимость локальных источников и таймауты не менялись.
Это не принудительная отмена при живых внешних клонах sender и не новая гарантия
доставки кадров во время teardown.

Три детерминированных теста используют настоящий SessionTxRegistry и тихий
живой duplex, без временных порогов. Проверены unregister при ожидании, отсутствие
outbox и порядок «последний queued frame → EOF» именно в helper. Последний тест
не обещает отправку кадра на wire при принудительном закрытии. На прежнем коде
два теста падали по оставшемуся pending, отрицательный контроль проходил. После
фикса тесты также проверяют точный `OutboxClosed`; отдельный waker подтверждает
планирование ожидающей задачи при закрытии канала.

| Проверка | Passed | Ignored |
|---|---:|---:|
| veil-session | 674 | 8 |
| veil-session-integration-tests | 119 | 1 |
| FFI, node-embedded + production-seeds + packet-tunnel | 334 | 2 |
| Уточнённые outbox regression, отдельный повтор | 3 | 0 |

Повторные три regression входят в session-suite и не прибавляются к ней как
новое покрытие. Android ARM64 FFI собрана с теми же production-фичами. Cargo
targets находятся на отдельной внешней ФС; mount-watchdog не зафиксировал её
потери. Rustfmt и diff check чисты.

## Диагностика до исправления

Продолжение [предыдущего захвата](../call-probe-first-hop-2026-11-01/README.md)
проверило фактический результат source admission. В отдельный QA APK добавлен
штатный Android wrap.sh с существующими opt-in диагностическими gates. Manifest,
AOT, native-библиотеки и несигнатурные ZIP entries при добавлении wrapper не
менялись; debuggable/extractNativeLibs уже были включены. Первая серия работала
без изменений реле, вторая — с временными диагностическими gates на шести реле.

Две ранние контрольные клетки второй серии прошли `relay_queued`, `budget_admit`
и `datagram_accepted` на телефоне, но matching opaque witness в выбранных хвостах
шести relay sinks не наблюдался. Их transport trace ID равен нулю: это admission
в очередь независимого ordered record-канала, **не свидетельство QUIC, записи
на NIC или доставки**. В выбранных receiver-срезах к QA peer не наблюдалось
роста decode/eligibility/violation/rate-limit/unexpected rejects; это не полный
учёт всех пакетов и не доказательство отсутствия потерь.

Поздняя успешная проба имеет точные witnesses на одном реле, в Windows dispatcher
и SDK. На телефоне ответ квалифицирован примерно за 341 мс, повтор наблюдался
примерно за 513 мс по тем же локальным монотонным часам. Следовательно,
600-мс budget сам по себе не объясняет весь перерыв. Межхостовые часы не
вычитались. Причина отсутствия ранних witnesses не установлена.

При разборе учтены preflight-пробы: у ранних failed-кандидатов контрольная клетка
имела sequence 4, а у позднего — 1. Выбор только `seq=1` пропускал бы ранние
попытки и не считается полным инвентарём control. Корреляционные данные хранятся
приватно; публичный aggregate не содержит адресов, peer ID, epoch, CID или
хешей зашифрованных payload.

## Физическая проверка исправления

Poco ↔ Windows 11, отдельные профили. В замороженном Android AOT заменена только
FFI; wrapper, manifest, медиадвижок, остальные библиотеки и signing certificate
проверены неизменными. Windows оставлена на прежних опубликованных библиотеках.
На этапе проверки фикса настройки реле больше не изменялись.

1. Перед Wi-Fi cut — четыре последовательные свежие P2P-выборки на обоих концах.
   После cut — 40 выборок каждого конца за 41,8 с: один и тот же active call во
   всех срезах, свежий audio RX в конце. Но максимальный sampled native age
   достигал **14265/14338 мс**: непрерывный свежий приём не квалифицирован.
   Значения относятся к отдельным media epoch и не образуют верхнюю границу
   полного перерыва. Это не A/B и не доказанное ускорение.
2. Отдельный новый вызов сразу после отключения Wi-Fi дошёл до Windows примерно
   за **1,1 с после place**; пять последовательных свежих RX-выборок обоих концов
   получены примерно через **10,4 с после cut**. Подтверждён cellular default.
   Условие ровно одного активного узла специально не создавалось.

Живую речь/слышимую громкость не проверяли. В сохранённом захвате отсутствует
отдельный witness срабатывания исправленной EOF-ветки на телефоне; эта серия
проверяет поведение собранного кандидата, но не доказывает, что именно EOF-fix
сократил конкретное ожидание. Полный NETCALL-01 и жалоба об отсутствии слышимого
звука остаются открытыми.

Следующий участок — жизнь независимого ordered source-канала и его реальная
запись/ошибка после смены parent session: раннее локальное принятие уже видно,
поступление этих клеток на первом хопе пока не подтверждено. Ослаблять изоляцию
источников или увеличивать таймауты по этим данным оснований нет.

## Завершение

Все шесть реле возвращены к прежней среде, gate выключен, временный drop-in
удалён, rollback timer неактивен. Независимая postflight подтвердила 6/6 healthy,
исходные loaded binaries/config и отсутствие autorestart. Постоянного обновления
сидов не было.

Телефонный QA возвращён к исходному APK с проверкой SHA и оставлен остановленным;
Wi-Fi/mobile data/stay-awake восстановлены, PID основного приложения не изменён,
его контейнер не открывался. Собственный logcat остановлен, forward и SSH-туннель
закрыты. Windows QA и scheduled tasks отсутствуют; окончательный listener-check
через IPGlobalProperties подтвердил отсутствие listener. Ранний проверяющий
скрипт временно сигнализировал о порте после остановки; независимая проверка
нашла только TCP-остатки с owner 0, без QA-процессов или активного listener.
Mac-стенд не запускался. Push/релиза нет.
