# Аватар и закрытый владелец хранилища — 2026-11-11

## Подтверждённый дефект

`setSelfAvatar` и `applySelfAvatar` читали предыдущее значение, затем допускали
запись без проверки, что MessagingService ещё принадлежит живой сессии.
`loadAvatar` также позволял закрытому сервису читать пространство, на которое
уже переключён общий Storage facade.

Управляемый стенд задерживает ответ на чтение после получения настоящего
значения. Пока вызывающий метод ждёт, закрываются MessagingService и storage,
тот же facade открывает другое независимое пространство. Затем отдаётся
прежний ответ. На старом коде запрос изменения первой личности записывает
картинку в пространство второй. Сравнивается само сохранённое значение, а не
только возвращённая ошибка. Идемпотентный apply отдельно объявлял успех
закрытого владельца без изменения данных.

Это конкретная API/lifecycle гонка на управляемой границе ответа, не
естественное воспроизведение пользовательского UI на Windows 10. Реальный
native backend используется под обёрткой задержки; собственное планирование
backend не объявляется причиной пользовательского случая. Сценарий относится
к повторному использованию facade после закрытия владельца; он не меняет
модель отдельных storage views в all-online.

## Исправление и сохранённые границы

- Мутирующие API проверяют владельца на входе и после чтения, перед решением
  no-op и допуском записи. Завершённая сессия даёт `StateError` без обращения
  к новому пространству.
- Cache/backfill чтение закрытого владельца возвращает `null`: новая личность
  не читается, успешный поздний результат прежнего чтения не выдаётся наружу.
  Фоновое чтение таким образом не создаёт новую ошибку обычного завершения.
  Ошибки самого storage не подменяются пустым значением.
- Уже завершившаяся запись остаётся в прежнем пространстве и может вернуть
  поздний успешный ответ. Она не переносится в новое пространство. Действующие
  storage admission/drain barriers сохранены, дополнительное правило отмены
  после состоявшегося commit не добавлено.

Это проверки владельца MessagingService. Формат аватара, ключи пространств,
LWW-порядок device journal, ratchet/ACL и транспорт не менялись.

## Проверки

Один тестовый контейнер содержит два пространства с разными паролями и
разными JPEG-аватарами. Проверены:

- Продолжение apply, idempotent apply и обе точки чтения set после закрытия.
- Собственный и peer cache read, начатые до закрытия.
- Все четыре API-входа закрытого сервиса: отсутствие чтения/записи нового
  пространства подтверждают счётчики storage calls.
- Фоновое чтение под настоящим AsyncTasks и registerShutdownTask: закрытие
  ждёт чтение и завершается без ошибки, старые данные не публикуются.
- Поздний ответ уже завершённого commit: первая личность сохраняет обновление,
  вторая — своё значение. Обе открываются заново независимыми handles/worker.

На прежнем исходном коде итоговые сценарии дают **22 assertion-red и два
успешных commit-контроля** на macOS, с тем же результатом на Windows 11.
Часть сценариев использует FakeHvContainer, часть — настоящие два пространства
с worker; native input проверен по SHA. Эти числа не означают 22 разных бага:
это варианты одной отсутствующей границы владельца.

После исправления **115 related tests на macOS и те же 115 на Windows 11
прошли без skips**. Включены новые lifecycle-сценарии, paired avatar exchange,
виджеты, consent races, обычная переписка, shutdown tasks и settings backfill.
Анализ двух Dart-файлов чист; источники проверены до и после запуска.

Промежуточный вариант выбрасывал ошибку также из cache read после закрытия.
При проверке его callers обнаружена несовместимость с background backfill;
вариант снят до commit. В окончательном варианте read отменяется мягко,
mutation отказывает явно; для background shutdown добавлен отдельный контроль.
Результаты промежуточной серии не считаются квалификацией окончательного кода.

## Сохранность и остаток

Windows-серия временно использовала 15 явно учтённых файлов собственной QA-
копии, проверила baseline и исправленный код, затем восстановила прежние SHA
и удалила добавленные файлы. Canonical frontend, packaged DLL и оригинальные
QA-контейнер/prefs повторно сверены. Owned app/task count равен нулю.
Временные контейнеры закрыты и удалены; реальные приложения не запускались.

Это отдельный дефект изоляции профильного значения. Он не объясняет исходную
жалобу Windows 10/Android или потерю доступа после сжатия. AppController GUI,
полный all-online/master lifecycle и power-loss не объявлены проверенными.
Новая AOT-упаковка ещё нужна; ранее проверенные AV bundles предшествуют правке.
Пользовательские данные и production-реле не менялись; push/релиза нет.
