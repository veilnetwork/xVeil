# Камера остановилась после успешного открытия

Подтверждён интеграционный пробел desktop-звонка: нативный capturer мог завершить
чтение после успешного `Start`, но приложение не наблюдало его `Capturing()`.
CallService продолжал показывать и объявлять `cameraOn=true`. Windows MF backend
уже очищает свой running flag при выходе CaptureLoop; V4L2 также хранит running
отдельно от существования объекта. Повторный start умеет заменить остановленный
объект, однако до пользовательского переключения UI не отражал отказ.

Новая native-метрика `camera_capturing`: `1` — capturer считает себя работающим,
`0` — сохранённый capturer остановлен, `-1` — объекта нет. Последнее не считается
ошибкой: камера ещё не запрошена, выключена или поставляет кадры вне этого
backend, как на Android. Отсутствие поля в старом engine также не является отказом.
Новый C ABI export или сетевой формат не добавлялись.

Существующий секундный stats poll теперь обрабатывает только целое `0`, когда
эта desktop-камера всё ещё нужна текущему звонку. Он сообщает cameraUnavailable
один раз, выключает локальную/объявленную камеру через действующий CallService,
сохраняет звонок и позволяет повторное включение. Screen sharing/переход к нему,
намеренный OFF, другой engine и неизвестные значения не считаются отказом.
Таймаут по отсутствию кадров не введён: пауза кодирования и медленная сеть
не доказывают смерть камеры.

## Проверки

Baseline: **5 PASS / 1 FAIL**. При явном terminal state `0` камера оставалась
включённой; известный работающий state, отсутствие данных, `-1` и неверные типы
не давали ложных отказов. Проверяется настоящий controller + CallService с
подставленным engine, состояние активного звонка и исходящий capture-сигнал.
После исправления проверены единственность события, успешный повтор без замены
engine и отсутствие нового отказа после намеренного OFF.

Набор с диагностикой выключенной — **419 PASS / 0 skipped**. С включённой
диагностикой повторяется тот же набор; результаты приведены в summary.json.
Проверки охватывают CallService, старт media, camera/screen state, route lifecycle
и Android camera ownership. Не объявляются проверкой физического звонка новой AOT.

Ранние попытки baseline не засчитаны: fake clock не завершал подготовку media,
затем fixture ошибочно отклонял default camera ID как совпавший с unset rejected ID.
Зачтённый baseline выбирает явную фиктивную камеру, сначала доказывает её запуск
и active call. Реальные секундные callbacks вызываются управляемо после открытия,
без ожидания временного порога и без изменения production API ради теста.

В Windows 11 собрана новая production DLL из 78 проверенных исходных файлов,
с зафиксированным WebRTC и SHA до/после сборки. Native source digest:
`2bb485cfca4f665fe9c03d30f4dc434e4407b38c7cd11a7d9438fa8d84364dfe`.
DLL SHA: `1b03f17b4e4e37fb3f275e42e398ac437a8fe1958e20afb60f92fd1b4de06b76`.
Test hooks при этой сборке выключены.

Реальный C ABI capture/codec probe дал **47 preview-кадров / 47 encoded**.
JSON bridge подтвердил состояния:

| Действие | camera_capturing |
|---|---:|
| До запроса камеры | -1 |
| Камера захватывает | 1 |
| Кодирование намеренно приостановлено | 1 |
| Камера остановлена через API | -1 |
| Камера повторно запущена | 1 |

API-stop удаляет объект, поэтому этот контроль ожидает `-1`, а не `0`.
**Асинхронное аппаратное отключение не выполнялось.** Потребление terminal `0`
доказано моделью backend в Dart-тесте; физическая проверка доказывает producer,
разбор JSON и независимость от намеренной паузы кодирования. Это callback-петля
codec probe, не новый сетевой звонок. Кадры и звук на диск не записывались.
Apple backend в этом раунде физически не проверялся.

## Анонимность и выпуск

Добавлены только source-owned event `cameraStopped` и ограниченная метрика
`cameraCapturing` (-1..1). Событие сохраняется среди bounded last evidence.
Unit и compiled-AOT проверки отвергают camera ID, driver path, неверные типы
и частные canary-значения; disabled journal остаётся выключенным. В тесте AOT
проверены оба значения флага диагностики, raw developer log sink не включается.

Анализ затронутого Dart-кода: 0 issues. Native provenance: 6 PASS;
compiled diagnostic artifact test: 1 PASS. Первое ожидание mediaSample в AOT-тесте
не было дополнено новой разрешённой метрикой; исправлено как ожидание теста,
не как обнаруженная утечка.

Свой native probe завершился, его PID/время запуска проверены. Удалены временные
исходники/объекты сборки и executable probe; сохранены DLL, provenance и закрытые
доказательства. Пользовательские приложения, контейнеры и серверы не менялись.
Изменения локальные. Требуются новые media pins и обычная release-квалификация.

Исходная Win10-жалоба «видео не идёт» остаётся открытой: её камера и прекращение
захвата после старта на ней не проверены. Эта правка закрывает конкретный
наблюдаемый контракт, а не устанавливает причину пользовательского случая.
