# Проверка хеша DataBatch во всех путях чтения журнала

2026-11-04. Остаточный пробел проверки целостности R27-H01 найден при разборе
стоимости чтения журналов. Изменение относится к hidden-volume и его использованию
в xVeil, а не к сетевой доставке или mailbox.

## Подтверждение

Текущая запись индекса журнала v2 хранит slot и BLAKE3 сжатого payload DataBatch.
AEAD подтверждает подлинность chunk, но сама по себе не доказывает совпадение
с хешем, записанным в ссылке индекса. Внешний root должен связывать содержимое,
а не только адрес chunk.

В исходниках были три пробела:

1. `Space::read_log` проверял тип chunk и наличие log ID, но не хеш v2 ссылки.
2. `iter_log_*` сравнивал хеш при decode miss, а следующая ссылка на уже
   закэшированный batch могла задавать другой хеш без отказа. То же после
   первого legacy reference без хеша.
3. Полный `verify_integrity` сохранял slot/log ID, теряя ожидаемый хеш ссылки;
   мог вернуть успешный отчёт для такой несогласованности.

Контрольный контейнер синтетический: корректные AEAD/index/commit/superblock,
но одна из ссылок v2 не совпадает с настоящим payload. На исходном коде три
теста чтения падали с фактическим возвратом bytes. После исправления чтения
два дополнительных теста полного integrity walk оставались красными:
взаимно противоречивые хеши и согласованные между собой, но неверные хеши.
Это не доказательство способа получить такой контейнер внешней атакой;
подтверждён именно нарушенный контракт проверки уже имеющихся данных.

## Исправление

- Точечное чтение сравнивает v2 commitment до декодирования/возврата записи.
- Iterator cache хранит digest настоящего сжатого payload и сравнивает
  **каждую** ссылку, включая cache hit после v1. Digest входит в byte budget;
  прежние LRU/entry cap и self-scrubbing payload buffers сохранены.
- Полный integrity walk проверяет все v2 commitments и фактический digest
  один раз на batch. Expected hashes хранятся один раз на distinct batch,
  очищаются после namespace и ограничены числом owned chunks до вставки.
- Корректные v1 ссылки без хеша и корректные v2 данные остаются читаемыми.
  Публичные Rust/FFI API, криптопримитивы и раскладка контейнера не меняются.
  Описание уже существующих 8-/40-байтовых ссылок исправлено в EN/RU документации.

## App-facing контроль

[Native-регрессия](../../../test/native/log_hash_integrity_live_test.dart)
каждый раз открывает отдельную копию неподвижного частного fixture. Сначала
обязано пройти чтение честной ссылки; затем проверяется конкретный отказ
`Malformed`/`IntegrityFailure` с причиной о hash. Исходный fixture не меняется.

На прежней замороженной HVS dylib стенда xVeil **все три теста красные**:
точечное чтение возвращало запись, range возвращал обе строки, integrity
возвращал здоровый отчёт. Это воспроизведение через настоящий Dart → FFI →
storage, а не только вывод по Rust-коду. Реальные пользовательские контейнеры
не открывались; в fixture нет личных данных, ключей или сертификатов пользователя.

## Проверки и границы

Шесть целевых Rust-контролей включают случаи выше и bounded metadata tracking;
каждый соответствующий дефект воспроизведён до его исправления. Финальная
полная crate-серия: **656 passed / 2 ignored**, 73 test suites с doctests.
Clippy `-D warnings` по all-targets core crate и fmt всего workspace прошли.

Исходники hidden-volume закоммичены как `285ecda` и перенесены fast-forward
в основной checkout. FFI собрана после этого из отдельного checkout в отдельный
Cargo target на проверенном внешнем filesystem; watcher следил за mount и
свободным местом. Source/lock и фактический SHA dylib зафиксированы. После
проверки зависимостей сохранена одна библиотека, собственный Cargo target очищен.

На **том же неподвижном fixture** новая библиотека прошла все три FFI-кейса,
а также контроль корректных файлов, отказов и замены содержимого. Все четыре
теста повторно прошли после удаления build target: выбранная библиотека
самодостаточна и не изменилась; SHA fixture совпадает с красным контролем.
Тестовый producer находится только в cfg(test), его маркеров в dylib нет.

Совместная проверка с history read batching завершена на новой HVS dylib:
native-процессы A/B/C, 2000 сообщений, SIGKILL B посреди первичной догрузки.
До подключения к сети B сохранил 1594 строки при одновременно offline A/C;
затем вернулся только A. Все 2000 ID, итоговый порядок, source positions и
delivered сошлись без дублей, пропусков и повторов уже завершённой истории.
После нового запуска без A/C полная история сохранилась. Sparse-копия после
crash и проверка нескольких prefix candidates действительно наблюдались;
это не прохождение на пустом snapshot.

Сходимость заняла 98,952 с от первого запуска догрузки, включая crash и
отключение источников, либо **51,111 с после готовности вернувшегося A**.
Это совместная проверка корректности, не строгий performance A/B новой HVS:
предыдущие два grouped-read прогона с прежней dylib дали 51,213/51,221 с,
poll около пяти секунд. Общий latency-дефект остаётся открытым.
Стенд Mac/JIT не квалифицирует Android/AOT, реальную сеть или всю матрицу.

Драйвер и независимый teardown завершились успешно: 27 собственных PID
и 31 порт проверены, процессов/listeners не осталось, runtime-каталог удалён.
1406 frozen source/dependency files и выбранные native artifacts не изменились.

Находка локально исправлена и проверена, но **не выпущена пользователям**.
Релиз/push/engine pins и production-реле не меняются.
