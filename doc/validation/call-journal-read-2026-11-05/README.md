# Отказ чтения журнала звонков и граница личности — 2026-11-05

Два подтверждённых механизма в текущем приложении. Связь с пользовательской
жалобой ПК ↔ Android на отсутствие звонков/звука не установлена. Настройки
media, транспорт, own-device mailbox, сиды и release pins не менялись.

## 1. Неудачное чтение выдавалось за пустой журнал

`HiddenVolumeStorage._readCallLogNamespace` перехватывал отказ всего
`iterLogRange` и возвращал пустой список. Это имело три разных последствия:

- Legacy publisher сохранял `call.sync.migrated.v1=1`, не прочитав старые
  результаты и не поставив их на публикацию. Обычный повтор и следующий boot
  уже считали этот этап законченным.
- Finished-call restore экспортировал `success=1, sources=0` вместо отказа.
- Append принимал новую запись без прочитанного состояния журнала и его
  актуального winner/cap; UI объявлял историю пустой.

Ошибка чтения namespace теперь проходит к вызывающему коду. Publisher
оставляет migration marker незавершённым, диагностирует отказ и повторяет
работу. Append сообщает отказ до новой записи и sync intent. Экран показывает
«Не удалось загрузить историю звонков» и кнопку повтора; исходный exception
не отображается. Переводы добавлены для ru/en/es. Прежняя обработка отдельной
некорректной строки сохранена: она не скрывает остальные читаемые записи.

Политика `CallService` при недоступном журнале не менялась: диагностика получает
отказ, но свежие звонки не блокируются. **Защита от replay при непрочитанном
журнале этим не гарантируется.** Старый ошибочный migration marker не
сбрасывается массово: это могло бы заново публиковать намеренно состаренные
записи. Исходный физический I/O-сбой не воспроизводился; тесты отказывают
ровно чтению namespace через тестовый декоратор, без production fault-switch.

### Доказательства

На старом storage-коде — восемь assertion-red: read, append, migration marker
и restore diagnostics, каждый на ordinary и настоящем worker/native HVS.
Два положительных malformed-row controls проходят и до исправления.
Итоговый `call_journal_read_failure_test.dart`: 10 passed / без skip.
После отказа проверены cold reopen, публикация сохранённой записи один раз,
неизменность старых данных и отсутствие приватного canary в отчёте.

Отдельный UI-red подтвердил ложное «пусто»; после повтора сохранённый звонок
снова виден. Первая попытка widget-теста зависла при закрытии fake storage
в teardown после assertion-red; свой runner прерван. Cleanup перенесён
в `finally` внутри widget zone, повтор baseline завершился штатным assertion-red.
Это исправление теста, не продуктовый crash или успешный прогон.

## 2. Экран сохранял данные прежней личности

Два дополнительных assertion-red с управляемыми futures:

1. A уже загружена, B выбрана и ещё загружается: FutureBuilder продолжал
   отображать строки и имя контакта A.
2. Чтение A ещё не завершилось, пользователь выбрал B: позднее продолжение
   A разрешало свои peer labels через storage B, хотя его результат уже не
   должен был отображаться.

Проекция экрана теперь получает `ObjectKey(store)` и сбрасывается при смене
владельца. Storage для labels захватывается вместе с исходным store до await.
Оба сценария проверяют отсутствие прежних строк, отсутствие чужих contact
lookups и окончательное пустое состояние B. Все пять widget-тестов прошли.

## Контроль и аварийное завершение

- Scoped storage/publisher/replay/UI/native: **67 passed / без skip** до
  добавления двух последних UI isolation случаев.
- 12 файлов потребителей call journal, с диагностикой: **811 passed / 3 skipped**.
  Пропущены три XVSB/XVRC native случая без `VEIL_FFI_DYLIB`; они не зачтены.
- После последних UI-правок повторены все пять widget-тестов и analyzer.
  Analyzer для пяти затронутых production/test файлов — без замечаний.

Дополнительно выполнен `call_journal_publication_e2e_test.dart`: три отдельных
native процесса в локальной TCP-сети, A/B одной личности, C другой. Сначала
обычная публикация результата B → A с duration 0 → 1. Затем A остановлен,
отдельный writer сохраняет duration 75 и немедленно получает SIGKILL после
commit, до запуска publisher. После запуска A результат 75 появился у A и B
и в обоих подписанных журналах, дублей нет. Ещё один обычный restart сохраняет
результат и не меняет уже опубликованную запись B. **1 passed**, весь suite
81,898 с; это не измерение задержки доставки. Media не запускалась.

Native suite квалифицирует crash/publication на исправленном storage; он не
инъецирует namespace-read отказ. Он выполнен до двух финальных UI isolation
правок; код storage/publisher между ними не менялся. Последние UI-изменения
проверены отдельно widget-тестами и не объявляются частью этого headless прогона.

## Происхождение и cleanup

Veil `b8647716`, hidden-volume `eceb9158`; существующие квалифицированные
библиотеки сверены по SHA, Rust не собирался. Worker/native fault cases
используют настоящий HVS через async-декоратор, а не замену контейнерных commit.
Для process suite заморожен 1481 lib/test/plugin input, проверены SHA CLI/FFI/HVS
и чистота SDK до/после. External target проверен как отдельная от `/` FS.
Все Flutter-прогоны использовали `TMPDIR=/private/tmp/`.

Проверены завершение 26 собственных PID, освобождение 24 портов и удаление
runtime. Временные native контейнеры fault-тестов удалены. Raw logs, ID и
пути не добавлялись в репозиторий. Полная crash-матрица, слышимость речи и
физическая квалификация Windows/Android остаются отдельными задачами.
Коммит локальный, без подписи, push и релиза.
