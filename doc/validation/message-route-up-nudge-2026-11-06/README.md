# Повтор сообщения после восстановления прямого соединения

Подтверждён и исправлен отдельный дефект обычной очереди сообщений:
входящая активность могла расходовать cooldown, необходимый для обработки
`onDirectSessionUp`. В результате уже пригодное прямое соединение не
освобождало сообщение от текущей задержки повторов, достигающей 24 секунд.
Это не установленная причина задержки автоматической сходимости partition.

## Механизм и изменение

Обычный authenticated inbound обновлял `_lastNudgeAt`, даже когда не
заканчивалась тишина и retry обычных сообщений не сдвигался. Следующее
`nudge(force: true)` читало тот же timestamp и возвращалось в пределах 3 с.

Теперь сообщения о восстановлении используют timestamp последнего
допущенного recovery-события. Обычный поток входящих кадров его не расходует.
Завершение тишины и direct-session-up разделяют этот cooldown: два сигнала
одного восстановления не порождают немедленно две повторные отправки.
Новый transient map очищается вместе с остальными per-contact throttle maps.

Сохраняются существующие интервалы и счётчики backoff, ACK retirement,
разделение адресатов и durable/ratchet проверки. Формат данных и mailbox
собственных устройств не меняются.

## Проверка

`test/message_retry_route_up_test.dart` использует настоящий MessagingService,
in-memory контейнер и authenticated ingress. Periodic timers остановлены;
все поведенческие проверки проходят без продвижения timer clock.
Тест не добавляет production hooks и проверяет фактические сообщения transport.
Service, transport и storage закрываются с ожиданием их работы.

- Сообщение доведено до capped retry; steady inbound не повторяет его,
  последующий direct-route-up должен повторить тот же message ID.
- Silence-ending inbound и direct-route-up не дублируют восстановление.
- Повторные route notices ограничены, другой peer сохраняет свой backoff,
  настоящий ACK переводит строку в delivered и прекращает повторы.

Законченный baseline run всех трёх проверок: 1 assertion-red / 2 passed.
После побайтного восстановления candidate: 3 passed. Более ранние попытки
с незавершённым teardown fixture не засчитаны как доказательство.
Новый механизм и связанные reconnect/control/loss/spread suites:
22 passed, включая три новых теста; наборы не складываются.
Analyzer трёх затронутых Dart-файлов чист.

Расширенный запуск дополнительно обнаружил четыре отказа в старом
`durable_redrive_test.dart`: oldest-frame probe после restart, ACK/enqueue,
drain backlog после restart, retirement после удаления conversation.
Тот же полный файл на побайтно восстановленной production-базе даёт те же
четыре отказа (38 passed / 4 failed). Candidate со связанными файлами:
60 passed / те же 4 failed. Этот набор не объявляется зелёным; причины его
несогласованностей требуют отдельного разбора и не выданы за новые дефекты
приложения. Например, часть fixtures ждёт ACK звонка без подключённого
call consumer, тогда как production намеренно не подтверждает такой dispatch.

## Native regression: четыре устройства после partition

Повторён [сценарий автоматического healing](../multi-device-partition-2026-11-06/README.md):
те же четыре устройства двух личностей и три изолированных loopback Core;
настоящие контейнеры, OVL1, SDK/CLI `bbeaf3a9`, HVS `eceb9158`.
Сняты только native bans, повторный debug join не выполнялся.

Все 17 ожидаемых строк, удаление, реакции и read position сошлись; десять
секунд устойчивости и restart B при остановленных A/C/D также прошли.
Первая сходимость **45,455 с**, стабильность **10,373 с**, полное recovery
**55,829 с**. Предыдущий automatic run давал 44,772 с: причинного ускорения
нет, задержка остаётся активной. Стенд не инжектирует `onDirectSessionUp`,
поэтому проверяет общую корректность, а не эффект новой ветки retry.

Зафиксированы и проверены 1496 исходных файлов и хэши native-артефактов.
После теста проверены 28 owned PID и 35 портов: своих процессов/listeners
нет, runtime root удалён, SDK/HVS и выбранные библиотеки не менялись.
Сырые журналы и адреса остаются в приватном cache.

## Границы

Мобильная квалификация отсутствует: Poco отключён владельцем. Подтверждение
локального механизма не закрывает NETCALL-01 или медленную multi-device
догрузку. Production-реле и пользовательские контейнеры не изменялись.
Push и релиза нет.
