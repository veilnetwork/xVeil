# NETCALL-01: контроль QUIC и ранняя проверка UDP-конфликта

## Что сравнивали

На возвращённом Poco и Mac использованы полные AOT из f36a472d:
runtime source/digest и фактические mappings/APK проверены до звонка.
Нативные SDK и CLI двух Core оставлены прежними (Mac c8f4929b,
Android bbcd967a, Core e974cebe). Новый фикс конфигурации в этот прогон
не входил. Адреса/личности двух QA-Core сохранены, их входной транспорт
и bootstrap descriptors переключены с obfs4/TCP на QUIC, порт — 443.
У Android изменены только два seed assets и подпись APK: AOT, native
libraries и остальные payload entries побайтно сверены. У Mac изменён
внешний bootstrap-конфиг, бинарники приложения сохранены.

Потребовалось ещё одно отличие: NAT-reflector у QA-Core перенесён с
UDP443 на UDP19569, иначе он конфликтует с QUIC-слушателем. Дополнительный
порт включён в preflight/cleanup. Поэтому это **контроль альтернативного
транспорта, не строгое A/B**. Production-конфигурация не менялась.

## Физический результат: восстановление не прошло

Перед вызовом оба Core видели аутентифицированные сессии обоих клиентов
и QUIC transport. Вызов начинался с фактического двустороннего P2P-приёма:
20,33 с baseline, native RX на конце фазы продвигался с обеих сторон.
После Wi-Fi off проверена валидированная Cellular-сеть; затем наблюдение
шло без host polling телефона. Ожидаемые 120 с Cellular не выполнены:
**Mac завершил звонок по livenessTimeout примерно на +24,533 с**.
В частичной фазе (21,459 с после проверки сети) epoch оставался 1 на обоих
концах, missing-native срезов нет, финальный прирост audio RX равен нулю;
max observed RX age — 23994 / 24115 мс. Возврат Wi-Fi и второй звонок
не выполнены, не засчитаны как пройденные.

На Poco старые сессии закрылись около +0,33 с; новых Core session.open в
окне звонка не наблюдалось. Есть шесть reconnect scheduling events около
+10,33 и +21,34 с с **connection timed out after 10s**. Это именно
TransportError::ConnectTimeout: connect_native_quic выдаёт его при
истечении ожидания QUIC connection. Начало node handshake на телефоне
после cut отсутствует (до cut четыре stage.begin, то есть gate работал).
Промежуточное описание о завершённом транспорте и отказе node handshake
было неверно и здесь явно исправлено. Физическое место потери UDP,
фильтрация провайдером или дефект ОС этим контролем не установлены.

30 локальных relay probe samples не имеют matching удалённого наблюдения,
но без пригодных новых parent sessions это не доказывает ошибку media
mux/дешифрования. Relay-only baseline на QUIC отдельно не выполнялся.
Смена транспорта сама по себе не дала восстановления в этом сценарии;
ни общее устранение NETCALL, ни единственная общая причина с TCP не заявлены.
Следующий полезный контроль — сохранить захват и сравнить старый процесс
после handover с новым запуском QA на уже валидированной Cellular-сети.

Исходный driver result **probeExit=1, cleanupExit=0** сохранён. Final owner
checks прошли: два временных Core/наблюдатели/процессы/порты закрыты,
production PID/binary/config неизменны, исходные APK/QA-контейнер/сеть/
permissions/debug properties восстановлены. Результаты без сырых данных:
[qualification.json](qualification.json). Слышимость человеком не проверялась.

## Устранённый дефект: позднее обнаружение UDP-конфликта

Первый запуск QUIC-стенда дал отдельное точное воспроизведение: прежний
config validate принял QUIC listener и NAT-reflector на одном UDP443,
после чего узел остановился с Address in use ещё до admin readiness.
Это ошибка проверки конфигурации, не доказанная причина пользовательского
NETCALL. Неудачный setup удалён по owner marker/SHA; повтор запуска
использовал отдельный reflector port. Приложения до этого отказа не запускались.

В SDK **2f747ac0** структурная валидация заранее отклоняет известное
пересечение числовых bind-адресов одной IP-семьи: одинаковые IP или
wildcard и конкретный IP на одном ненулевом UDP-порту. Сообщение указывает
nat.udp_reflector_bind и необходимость выбрать отдельный адрес/порт.
Автоматический repair не переносит настроенные endpoints. TCP443 рядом
с UDP443 допустим; другой UDP-порт/адрес, отсутствие reflector и QUIC
port 0 сохраняют прежнее поведение. DNS не выполняется; поведение разных
IP-семей с IPv6 dual-stack не угадывается и этим правилом не блокируется.

До фикса: новая проверка падала по assertion (2 passed / 1 failed).
После фикса: три целевые проверки прошли; после добавления контроля
реального structural repair прошла вся veil-cfg: **237 passed, 0 ignored**.
Formatting check чистый. Source hashes полного прогона совпадают с
закоммиченными файлами. Rust выполнялся в основном checkout с watchdog
внешней ФС и свободного места; новые FFI/CLI не устанавливались.
[config-validation-proof.json](config-validation-proof.json) содержит границы
и команды. Push, релиз и изменения production-сидов не выполнялись.
