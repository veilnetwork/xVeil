# История: повторные delivered и сравнение на 10 000 сообщений

## Исправление

Дубликат исходящего mirror вызывал `markMessageStatus(delivered)`, даже когда
свежее адресное чтение уже вернуло delivered. Хранилище отказывалось менять
состояние, но вызов входил в scan-очередь и искал сообщение в общей
материализованной истории.

Теперь такой caller пропускает только заведомый status no-op. Остальная
обработка дубликата, включая принятие исходной device-позиции вместо
предварительного peer echo, продолжается. `sending/sent/failed → delivered`
по-прежнему восстанавливается; очередь pending receipt и гонки с append
сохранены. Нового кеша статусов или authorization не добавлено.

Сам status API теперь использует `loadMessageById(chat, id)`. Этот helper
обновляет тот же incremental fold и применяет тот же scoped/legacy status
и signature overlay. После актуализации fold выбор по составному ключу —
map lookup, вместо перебора общего списка; холодное чтение всё ещё может
читать журнал. Отсутствующая/удалённая/нечитаемая строка по-прежнему даёт
false без orphan status write, а terminal delivered не понижается.

## Регрессии

На финальных условиях fixture старый caller дал **6 assertion failures**:
дубликаты с явным delivered или ранее полученным receipt; повтор после
восстановления каждого из sending/sent/failed; canonical-position adoption.
Новый caller проходит их. Контроль возвращал только старый caller, сохраняя
новое адресное чтение в API, поэтому исчезновение вызовов отнесено именно
к caller-guard.

Проверено, что no-op не меняет тело, время, число сообщений и не запускает
retry; исправление позиции всё ещё выполняется. Добавлены warm/cold проверки
одинакового ID в разных чатах, удалённой/отсутствующей строки и ошибки decode
без status-коммита. Сохранены прежние тесты ACK до mirror, ACK во время append,
потерянного ACK, erase и pending retry.

Две ошибки первоначальной fixture исправлены до финального red-control:
доверие к sibling задаётся `isOwnDevice`, а не routing-списком; timestamp
сравнивается по epoch, а не флагу локального/UTC представления. Это не новые
дефекты продукта.

Финальная серия: **247 passed / 0 skipped**, с native SDK/HVS gates.
Полный analyzer и diff checks чисты.

## Увеличение стенда по запросу владельца

Основная серия содержит **10 000 архивных + 1 прежнюю строку** у получателя.
A/B/E — одна личность, C — другая; четыре независимых Mac/JIT процесса и три
изолированных Core на loopback. A/E имеют одинаковые полные архивы; оба первых
authenticated ответа получены до release первого apply.

Общий для controller/worker лимит fixture расширен до 10 000. Небольшой
smoke-default остаётся 512; в этих трёх запусках явно выбран 10 000. Все ID,
тела, delivered, canonical positions и порядок сверяются, а не выборка/хвост.
Равенство двух неполных историй не является успехом.

Подготовка источников использует существующий `appendMissingMessageBatch`
по 16 строк через реальный encrypted store, вне измеряемого интервала.
Дубликат/отказ/неполная вставка останавливают fixture. Это не изменение
размера production-публикации. Seed timeout увеличен только для setup;
обычный срок ожидания сходимости остаётся 3 минуты.

Overlap wire observer ограничен 16 384 записями, census — 20 000 append keys:
10 000 плюс прежние строки помещаются целиком. Каждый запуск отдельно
подтвердил dropped=0 в закрытых probes и отсутствие census keyLimitReached.
Другие wire-probe режимы сохраняют прежний лимит 2048. Production-диагностика
и анонимный экспорт не расширялись.

## Native A/B/A

Контроли A₁/A₂ используют два production-файла из родительского коммита,
B — candidate. Остальные 1522 frozen input и native библиотеки одинаковы;
всего проверены 1524 frontend/test/dependency inputs в каждой фазе. CLI/FFI/HVS
SHA проверены до/после, FFI/HVS подтверждены в OS mappings минимум трёх
одновременно живых worker. Candidate после контроля восстановлен побайтно.

CPU sampling/VM timeline выключены во всех фазах, census и 1000-мс опрос
одинаковы. Setup, намеренные encode/apply gates и добавление устройств не
входят в apply-release→convergence; это не полное offline→reconnect время.

| Метрика | A₁: прежний код | B: candidate | A₂: прежний код |
|---|---:|---:|---:|
| Apply release → сходимость, мс | 48633 | 48769 | 48943 |
| Encode release → сходимость, мс | 49186 | 49264 | 49602 |
| HistoryApply callbacks | 20002 | 20002 | 20002 |
| Status API calls / changed | 10000 / 0 | 0 / 0 | 10000 / 0 |
| Message commits | 625 | 625 | 625 |
| History cursor commits в окне | 314 | 316 | 316 |
| Allocator reservations | 157 | 157 | 157 |
| Строк после boot без источников | 10001 | 10001 | 10001 |

Все три сценария прошли: точный полный состав и порядок, нет дублей, пропусков
и посторонних строк; проверяемые conversation cursors завершены, история
пережила cold boot при offline A/E/C. Это не обещание завершения всех фоновых
inventory-запросов: курсор after-peer допустим ещё до следующего empty-list.
Поэтому в окно census могут попадать дополнительные завершающие checkpoint.

**Сокращение status-вызовов доказано; общего ускорения нет.** Worker RPC в
окне тоже не уменьшились устойчиво: 61167 / 61498 / 60983. Неизменившийся
результат не объявляется исправлением всей задержки. Предварительная серия
на 2000 дала 10,346 / 10,452 / 10,456 с с тем же исчезновением no-op;
она приведена отдельно. Размер и способ подготовки архива различаются,
отношение времён этих двух серий не является причинным A/B-результатом.

## Где осталось ожидание

Существующий passive wire probe связал по private request ID все **157 страниц
каждого источника** с полным набором индексов ответа у B. Общий authenticated
requester совпадает на A/E; IDs двух источников не пересекаются. Все часы —
DateTime одного Mac. Первый gate-crossing query/reply и следующий интервал
каждого источника исключены; осталось по 156 наблюдений каждой стадии.

В candidate медиана «source получил query → B получил весь reply»:
**74,0 / 80,8 мс** для A/E. Медиана «B получил весь reply → source получил
следующий query»: **195,2 / 197,3 мс**. На контролях картина похожая.
Вторая стадия включает очередь/применение/durable checkpoint у B **и**
подготовку, отправку и доставку следующего query. Это ещё не B-exclusive CPU
или disk time: outbound timestamp не записывался.

Объединение интервалов второй стадии у двух потоков — 40,30 с, первой —
26,39 с; они **пересекаются**, складывать их или считать долей точного
apply-window нельзя. Сводка описывает повторяющиеся ожидания страниц,
а не один 40-с сетевой стоп. Следующая проверка — цена публикаций по 16 и
служебных page/checkpoint границ при сохранении fresh admission, ratchet и
ACK только после durable apply. Модель mailbox не меняется.

## Завершение

Cleanup большой серии A₁/B/A₂: **39/36/37 PID**, **55/56/62 порта**. Своих
живых процессов/listeners нет, runtime-контейнеры удалены. Переиспользованы
проверенные Veil 0.11.48 CLI/FFI с `allow-empty-seeds` и HVS 2.7.0.
Текущий SDK delta — Windows VPN helper; Mac runtime не менялся, новых
Rust-сборок нет.

**Большая догрузка и NETCALL-01 остаются открытыми.** Это Mac/JIT, не
Android/AOT/WAN или полная multi-device/crash/revoke матрица. Новый SIGKILL
этим циклом не квалифицировался. Телефон, реальные контейнеры и production
не затронуты, sibling mailbox отключён по решению владельца. Raw IDs, адреса,
ключи, машинные пути и payloads не включены; публичные агрегаты —
[summary.json](summary.json). Push/релиза нет.
