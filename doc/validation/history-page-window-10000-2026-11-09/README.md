# Догрузка 10 000 сообщений: меньше последовательных страниц

## Изменение и границы

Клиент запрашивал не больше 64 коротких сообщений за один раз. После каждого
ответа требовались применение, durable cursor и следующий запрос. В прошлой
серии путь от полного ответа до следующего запроса занимал P50 127–138 мс;
157 последовательных страниц каждого источника сохраняли заметную задержку.

Теперь `page` запрашивает `rows: 128`. Источник принимает только целые 1..128;
отсутствующее поле сохраняет предел 64, некорректное отклоняется до чтения
snapshot. Получатель проверяет число событий относительно собственного
запроса. Это bounded планирование страницы, не разрешение записать данные.

**128 КиБ ответа, 64 части, 1500 символов query, admission и один outstanding
request на sibling не увеличены.** Большие сообщения по-прежнему заканчивают
страницу раньше либо используют существующий record-путь. Сохранение готовых
строк остаётся по **64**, обычный live coalescing — по **16**. Страница из
128 новых коротких строк проходит две публикации, каждая со свежими проверками.
Курсор сохраняется только после всей страницы. Revoke, binding, visibility,
ratchet и host authorization не обходятся; sibling mailbox не включён.

Missing-field default проверен отдельно, но полной mixed-квалификации нет:
совместимость со старыми версиями исключена владельцем из условий выпуска.

## Проверки корректности

Две новые проверки 128 сообщений (incoming/outgoing) assertion-red на родителе:
нужны две страницы вместо одной. С исправлением обе проходят и фиксируют
ровно две 64-row публикации, полный порядок, тела, delivered и canonical slots.

Отказ второй публикации проверен отдельно для revoke и ошибки хранилища:
первые 64 строки остаются, cursor не продвигается, после перезапуска и возврата
доступа недостающее восстанавливается без дублей. Проверены запросы на
1/64/128 строк и без поля; null/zero/negative/over-cap/string/bool/fraction
не запускают чтение истории или encode. Valid fence доказывает завершение
предыдущего запроса, а не опирается на паузу по времени.

Регрессии перенесены на новые настоящие границы: over-cap ответ 129,
129 строк с отказом cursor, restart с cursor на 128-й строке. Growing-source
fixture теперь имеет 2048+tail: первая страница не может подтвердить минимальный
256-row hint, вторая может; сохранены проверки edits, revoke, отказа checkpoint
и удаления уже отвергнутых подсказок. Полный source с изменением проверяется
на трёх 128-row страницах. Предыдущие byte-budget, record, reordering,
visibility, batching, shutdown и slot-concurrency проверки также прошли.

**260 passed / 0 skipped**, включая **16 native HVS**. После единственной
стилевой правки фикстуры повторены все четыре requested-limit проверки;
анализатор чист. Первые запуски новых ручных запросов имели ошибку фикстуры
(невалидный request ID и отправка до readiness); они не считаются результатом
production-проверки. Остальные изменения после финального набора — документы.

## Native A/B/A

Родитель `02341080`, новый вариант, снова родитель. A/B/E — одна личность,
C — другая; четыре независимых Mac/JIT процесса, три изолированных Core,
loopback TCP, настоящий SDK/FFI/ratchet/контейнер. A/E имеют одинаковый полный
архив; первые authenticated ответы обоих получены до первого apply release.
Seed по 16 и искусственные gates вынесены из измеренного apply-window.
VM sampling/timeline выключены, наблюдение каждые 1000 мс одинаково во всех фазах.

| Метрика | Parent A₁ | Candidate | Parent A₂ |
|---|---:|---:|---:|
| Apply release → сходимость, мс | 33552 | 25584 | 34990 |
| Page queries каждого источника A / E | 157 / 157 | 79 / 79 | 157 / 157 |
| Коммиты cursor получателя | 316 | 160 | 316 |
| Коммиты сообщений получателя | 157 | 157 | 157 |
| HistoryApply callbacks | 20002 | 20002 | 20002 |
| Worker RPC в окне догрузки | 33963 | 25385 | 34357 |

Все 10000 архивных плюс одна прежняя строка совпали по IDs, телам, delivered,
canonical positions и итоговому порядку, без пропусков/дублей/лишних строк;
оба cursor завершены. Отдельный cold boot без A/E/C сохранил все 10001 строку.
Сравнение не ограничено счётчиком видимых сообщений. Wire capture и census
не обрезаны; все forward запросы связаны по private ID с полными ответами.

Новый вариант в этой серии быстрее обоих контролей примерно на 8–9 с.
Это измерение локальной JIT-догрузки, не обещание такого же процента в мобильной
сети/AOT. Наблюдение раз в секунду не позволяет сравнивать субсекундные отличия.
**Вся проблема latency не закрыта: остаётся около 25,6 с на 10000 сообщений.**

Страница стала дороже, но их меньше. У candidate query-at-source → full-reply
P50 102–104 мс (78 наблюдений на источник), full-reply → next-query-at-source
P50 174 мс (77). Первый gate-crossing ответ и переход от него исключены.
Вторая стадия включает apply/checkpoint, подготовку и доставку следующего
запроса; это не чистое время CPU или диска. Встречные application-frame bytes
сходны: 1,29 / 1,26 / 1,32 МБ, а не двукратное уменьшение сетевого трафика.
Следующий участок — стоимость этих стадий и физическая квалификация.

## Происхождение, место и уборка

Во всех фазах проверены **1525 frozen inputs**: два различных production-файла
(один поведенческий, второй — уточнение комментария о cohort), остальные 1523
одинаковы. CLI/FFI/HVS SHA и OS mappings проверены; Rust не собирался.
Фактические page counts 157/79/157 дополнительно исключают зачёт stale worker.
После каждой фазы проверены исходники и cleanup; candidate восстановлен.

Kernel cache **92 → 92** во всех фазах, новых entries **0**; место во время
измерений не чистилось. Свободно примерно 150,6 ГиБ, cache по-прежнему 9,5 ГиБ.
Проверены 39/36/44 owned PID и 54/58/58 портов: процессов/listeners не осталось,
synthetic runtime удалён. Телефон, пользовательские контейнеры и production
не затронуты. NETCALL-01 и остальная multi-device матрица этим не закрыты.

Только агрегаты находятся в [summary.json](summary.json); raw capture, ID,
пути и ключи остаются частными. Коммит локальный unsigned, push/релиза нет.
