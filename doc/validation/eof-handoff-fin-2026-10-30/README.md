# Удаление маршрута до ответного FIN после read handoff — 2026-10-30

Диагностическая SDK `9f3affd9`, исправление `07802a08`. Найден конкретный
механизм [восьмибайтовых хвостовых RTO](../family-send-stages-2026-10-30/README.md).
Он подтверждён на физической трассе и воспроизведён без сети. Это не доказательство
устранения всех причин низкой скорости файлов или прежнего «33%».

## Физическое свидетельство до исправления

На Mac/Blackview по Wi-Fi переданы десять новых файлов по 3 145 979 байт, пять
в каждом направлении. Все SHA-256 совпали. Медианы Android → Mac / Mac → Android:
11,662 / 6,842 с; максимум 49,435 с. После файлов стенд оставался активен ещё
45 с. Эти времена не являются контролируемым сравнением с предыдущими сериями.

В одном логическом stream Android принял последний восьмибайтовый DATA и FIN,
затем завершил driver с таким состоянием:

| Поле | Состояние при удалении |
| --- | --- |
| Phase | Established |
| Входящий EOF | true |
| Pending / in-flight байты | 0 / 0 |
| Собственный FIN requested / sent / acked | false / false / false |
| Финальный ACK responder (linger) | false |

После удаления маршрута туда пришли пять повторов DATA длиной 8 и пять повторов
FIN. У всех DATA конец равен `close_rcv_nxt − 1`, у FIN sequence равен
`close_rcv_nxt − 1`: это повторы уже принятых байтов/FIN. Mux сообщил `sid_route=false`.
У Mac тот же stream дошёл до retry count 6 с девятью in-flight sequence bytes
(8 DATA + FIN), без входящего EOF. Установлено преждевременное удаление состояния;
конкретный участок неполучения первоначального ACK этим не устанавливается.

SDK этого прогона уже включала [C-close fix](../anon-close-read-2026-10-30/README.md).
Следовательно, это отдельный дефект driver, а не повторная атрибуция C-handle.
Идентификатор stream сопоставлялся только в приватных журналах; публично сохранены
counts, признаки и относительные sequence offsets.

## Причина

`engine.is_eof()` означает, что peer FIN уже принят **и engine read-buffer пуст**.
В начале loop read-buffer ещё содержит последние восемь байт, поэтому прежняя
проверка не вызывает `engine.finish()`. Далее read handoff переносит байты в
канал приложения и делает EOF видимым.

В том же loop проверка завершения видит пустую отправку и EOF. `is_send_complete`
допускает пустую ещё не закрытую write-half; поэтому driver выходит до следующей
проверки courtesy FIN. `completed_close_ack` не создаёт responder без собственного
FIN exchange, и Mux снимает маршрут. Приложение может получить весь файл/EOF,
но другой конец остаётся ждать завершения протокола.

## Исправление и модель

Проверка courtesy FIN перенесена **после read handoff, до transmit и проверки
выхода**. Когда последний read опустошает буфер, FIN запрашивается в этом же loop,
идёт за уже принятыми данными и должен быть подтверждён до нормального retirement.
Существующий ограниченный ACK responder теперь достигается и в этом случае.
Порядок ARQ/ACK, retry limits, длительность linger, криптография, wire/C ABI,
mailbox и relay QoS не менялись.

Две регрессии используют настоящий `OnionStream` driver и контролируемый cell
peer. Peer принимает 73 payload bytes, затем одной входящей пачкой отдаёт ACK,
восемь credit bytes и FIN. Приложение читает credit и EOF, сохраняя свой writer
живым; **ни `finish()`, ни drop не могут создать проверяемый FIN**.

Первый тест проверяет courtesy FIN и переход в linger без потерь. Второй теряет
первый финальный ACK и повторяет DATA/FIN через 50 виртуальных миллисекунд:
сохранённый маршрут должен подтвердить их. Оба упали на `9f3affd9` из-за
отсутствующего собственного FIN, оба проходят после переноса проверки. Часы
виртуальные; секундный timeout — watchdog, не требование производительности.

Полный stream suite: **223 passed, 0 ignored**, включая две новые регрессии.
Полный FFI suite: **328 unit passed, 2 ignored**; внутренний subprocess не
прибавлен, 5 ignored doctests отдельно. FFI features: `--no-default-features
--features node-embedded,production-seeds,packet-tunnel`. Clippy обоих пакетов
`--lib --tests -- -D warnings`, rustfmt и diff-check прошли.

## Проверка исправления на устройствах

Отдельная серия `07802a08`: пять новых файлов по 3 145 979 байт в каждую сторону,
все десять SHA-256 совпали. После последнего файла выдержано ещё 45 с.

| Направление | Целые файлы | Загрузка min / median / max |
| --- | ---: | --- |
| Android → Mac | 5/5 | 7,086 / 8,630 / 12,668 с |
| Mac → Android | 5/5 | 6,782 / 8,047 / 11,328 с |

Во всех **20 endpoint-завершениях десяти логических stream** подтверждены EOF,
`fin(req=true,sent=true,ack=true)` и `linger=true`. Затем для всех 20 записано
окончательное снятие маршрута. До исправления было 18 таких завершений, один
выход без собственного FIN и один соответствующий peer timeout.

После исправления mux unknown counters равны нулю на обоих концах. В sampled
driver summaries RTO не зафиксирован; это не доказательство отсутствия любого
краткого RTO между срезами. Прежняя сигнатура выхода без FIN не повторилась.
Маршруты между сериями не закреплялись: ускорение всей загрузки этим сравнением
не доказывается. Причинная проверка исправления — состояние завершения и два
контролируемых регрессионных сценария, а не разница секунд.

Анонимные числа, признаки пойманного случая и результаты: [summary.json](summary.json).
Стенд содержит две активные личности/устройства, Mac и Blackview по Wi-Fi;
второй Mac личности телефона оставался offline. Это не полная multi-device
матрица. Звонки и звук не запускались, реле не менялись.

Обе серии использовали один и тот же проверенный Dart snapshot (Mac JIT /

соответствующих SDK с production features и без test-low-difficulty/native
test hooks. SHA и диагностические markers проверены, фактически загруженный
Mac dylib сверён через `lsof`, установленная APK — по SHA. Подпись QA и все
остальные Android ZIP payloads сохранены. Это не опубликованный release APK.

Исходная QA APK после каждой серии восстановлена и сверена по SHA. Основной
клиент/его данные не менялись. Свои Mac/Android приложения и logcat остановлены,

## Диагностика и границы

`9f3affd9` добавляет только opt-in endpoint-наблюдения: состояние driver перед
retirement, начало/конец ACK responder и до 64 unknown-cell записей на mux за
всё его время жизни. Последние содержат тип, stream sequence metadata и размер,
без payload, node/device/content ID или адреса. Raw stream IDs и sequence values
используются только в приватной трассе; в публичные артефакты не выносятся.
Отдельная проверка demux с включённой диагностикой прошла.

Все 343 unknown из старых серий ретроспективно не атрибутированы. Не объяснены
этим исправлением 49-секундная загрузка до завершения данных,
остальные bulk RTO, все случаи «33%», Windows 10 one-way/audio, тихий звук,
естественное завершение звонка около 25 с, sleep Android и оставшаяся multi-device
матрица. Это устранение доказанного механизма преждевременного закрытия.
