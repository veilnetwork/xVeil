# Ограничение уникального приёмного payload — 2026-10-30

Veil `3bea8780`, предыдущий вариант `9f2456d1`. Закрытие находки из
[проверки persist](../persist-replies-2026-10-30/README.md).

## Исправление

Прежний `RxState::accept` принимал последовательные DATA сверх `recv_window`.
`store_oo` сохранял перекрывающиеся участки несколько раз. Предел 8192 entries
ограничивал metadata, но не обеспечивал byte-limit. In-order DATA также мог
заменить содержимое уже обещанного SACK при перекрытии.

Теперь граница разрешённых позиций равна
`rcv_nxt + (window - unread_bytes)`. Без чтения приложением она не сдвигается:
продвижение `rcv_nxt` лишь переносит байты в unread buffer. OO-байты здесь не
вычитаются повторно — место под недостающий префикс должно оставаться доступным.
Ранее выданные SACK не отзываются.

DATA обрезается по этой границе; подтверждается только принятый префикс.
OO-вставка сохраняет лишь недостающие фрагменты. In-order путь заполняет
настоящую дыру, затем переносит старые части в read buffer, сохраняя первое
принятое содержимое. Перекрытия ищутся через predecessor и ограниченные
диапазоны BTreeMap с учётом wrap: `O(log n + overlaps)`, без полного просмотра
карты на каждый следующий пакет хвоста.

Предел 8192 записей сохранён. Непоместившиеся новые фрагменты не обещаются
через SACK; заполнение head-gap работает и без свободной metadata-entry.
Фактическое Rx-окно ограничено прежним Tx-пределом `2^31 - 1` для корректного
циклического сравнения. Штатные меньшие окна не изменены. Duplicate-prefix
теперь обнаруживается и внутри сохранённого интервала; корректный D-SACK
может сопровождать объединённый обычный SACK.

Гарантия: **уникальные удерживаемые payload-байты**, unread + OO, не превышают
окно. Это не обещание точного RSS: отдельно остаются ограниченная metadata,
округление аллокатора и временные объекты одного кадра. Wire/C ABI, ratchet,
ACK приложения, mailbox и приоритеты реле не менялись.

## Регрессионные проверки

На `9f2456d1` с теми же финальными integration-test sources упали шесть
capacity-проверок и одна проверка async-драйверов. Статическое нулевое окно и
прежнее уведомление о чтении уже проходили. Это не семь независимых дефектов.

| Сценарий | Прежде | После |
| --- | --- | --- |
| Окно 64, пять DATA по 16 без чтения | 80 unread bytes | 64; хвост принимается после чтения/повтора |
| Окно 32, DATA на 48 | Принимались все 48 | 32; остальные 16 не ACKed до повторного приёма |
| Окно 128, 64 перекрывающихся OO по 64 | 4096 OO bytes | 127 уникальных OO bytes, один byte для head-gap |
| SACK-tail, чтение и новые DATA | Превышение byte-limit | SACK сохранён, край движется только с чтением |
| Новый payload перекрывает обещанный SACK | Старое содержимое заменялось | Первое принятое содержимое сохранено |

Независимая bitmap-модель проверяет **54 000 шагов**: три sequence-позиции
(две около wrap), 12 seeds, по 1500 шагов с разными размерами, порядком пакетов
и чтениями. После каждого шага проверяются сумма payload, отсутствие
перекрывающихся копий и совпадение множества известных байтов. Уже принятые
позиции не исчезают, неизвестные не появляются. Финальное заполнение дыр
возвращает все 1024 байта в порядке. Прежний стресс 8192 tiny entries проходит.

## Два настоящих драйвера

Два `OnionStream` обмениваются через FIFO `CellDuplex`, оба с новым кодом.
MSS 16, окно 32, RTO 50/50/400 мс, retry-limit 2, RACK и rewind включены.
Приложение не читает две виртуальные секунды: заполняются 16 app-channel slots,
затем буфер движка. Полный получатель **39 раз** отвечает прежним cumulative
ACK и нулевым окном, не принимая probe-byte. Отправитель с persist-правкой
остаётся живым. После чтения все **2048 байт** совпадают, получены EOF и оба
callback закрытия, `DataRto` нет.

Прежний получатель принимал пробы сверх полного буфера и менял cumulative ACK;
новая проверка распознала это. Прошли **216 stream-тестов, ignored нет;
326 FFI-тестов, два ignored** с `--no-default-features` и
`node-embedded,production-seeds,packet-tunnel`. Внутренний subprocess не
прибавлен к 326. Clippy `--lib --tests -- -D warnings` и rustfmt прошли.
Предположение промежуточного теста об отсутствии D-SACK уточнено: дополнительный
duplicate-range допустим, обычный SACK-range остаётся обязательным.

## Смешанные версии

В прежнем [mixed-probe](../bbr-flow-limited-2026-10-29/mixed_probe.rs) выполнен
A/B/A: A — `9f2456d1`, B — `3bea8780`, legacy — `04eb1c1d`. Исходники probe
одинаковы, targets разделены. Все **16 профилей** (две версии с каждой стороны,
RACK on/off, потеря первого открытия окна on/off) сохранили байты и EOF.
Числовые строки A₁/B/A₂ совпали, включая прежние смешанные ожидания.
App-pause тут только 25 мс; это не квалификация длительного полного окна.

Отдельный стресс: app-pause 2000 мс, RTO 50/50/400 мс, retry-limit 2.
Отправитель `04eb1c1d` с новым ограниченным получателем завершился на
**412 мс** по старому retry-пути. Актуальный код на обеих сторонах передал
по 4096 байт с EOF за **2319 мс** виртуального времени. Эти намеренно короткие
таймауты не являются production-измерением.

Для длительного нулевого окна отправителю нужна persist-правка `9f2456d1`;
обновление получателя не обновляет чужой старый бинарник. Это нужно учитывать
при раскатке. Корректный отказ полного буфера больше не маскируется приёмом
новых байтов сверх настроенного лимита.

## Границы и гигиена

Находка локально закрыта. Связь с физическим «33%» не доказана: в прежних срезах
окно оставалось большим. Остаток смешанных persist-ожиданий, per-hop задержки,
unknown cells, другие пользовательские жалобы и multi-device матрица открыты.

Телефон, GUI, реальные реле и звонки не запускались/не менялись. Async-драйверы
завершились до удаления handles, build/test/probe процессы проверены после
выполнения. Mount непрерывно проверялся, targets разделены; логи приватные.
Push, релиз и установка не выполнялись. Числа и хеши: [summary.json](summary.json).
