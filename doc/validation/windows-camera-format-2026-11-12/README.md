# Windows: камера перечисляется, но исходящего видео нет

Пользователь Windows 10 подтвердил исправление аватарок и звука с ПК после
обновления, но сообщил об отсутствии исходящего видео. В списке одна активная
камера. Наличие собственного превью пока неизвестно. Это **открытая жалоба**;
её точная причина на исходном ПК ещё не установлена.

## Подтверждённый механизм

Windows backend просил только NV12 с точными размерами профиля: 352×198 или
640×360. При отказе он читал прежний формат Source Reader. Если это MJPEG,
существующий uncompressed→I420 конвертер его отвергает, хотя камера доступна.

Атрибут basic video processing не обещает произвольное преобразование в NV12
или изменение размера: Microsoft описывает YUV→RGB32 и deinterlacing.
Source Reader позволяет запросить uncompressed subtype без фиксированной
геометрии, затем прочитать фактический тип.
Источники: [basic processing](https://learn.microsoft.com/en-us/windows/win32/medfound/mf-source-reader-enable-video-processing),
[настройка выходного формата](https://learn.microsoft.com/en-us/windows/win32/medfound/processing-media-data-with-the-source-reader).

Теперь после отказа точного NV12 приложение ограниченно пробует NV12, YUY2,
RGB32 без требования размера. Выбранное устройство остаётся тем же. Фактические
размеры и stride читаются как прежде, scaling выполняет существующий libyuv-путь.
Если все запросы отклонены, прежняя проверка поддерживаемого native-формата
сохраняется. Сжатые байты не передаются uncompressed-конвертеру. ABI, wire,
privacy-политика маршрутов и разрешения не менялись.

## Проверка и пределы

- Пять Windows native regression checks: exact NV12, отказ геометрии,
  YUY2, RGB32 и ограниченный отказ. Извлечённая прежняя стратегия дала
  **1 PASS / 4 FAIL**; финальная — **5 PASS / 0 FAIL**.
  Ранние ошибки сборочной проводки не засчитывались как red продукта.
- Настоящий Media Foundation и USB-камера: оба используемых профиля отклоняют
  точный размер. В контроле у reader предварительно выбран объявленный камерой
  MJPEG-режим. Старый запрос оставляет MJPEG, новый получает NV12 и непустой
  uncompressed sample. Это две пары old/new, без изменения системной камеры.
  Исходный default камеры стенда — NV12: сам по себе пользовательский симптом
  на этой камере не воспроизведён.
- Полный Windows x64 DLL собран из зафиксированных исходников с pinned WebRTC.
  SHA архива, входной библиотеки, дерева исходников и выбранного DLL проверены.
- Через настоящий C ABI движка: живая камера → encode → RTP → второй engine →
  decode/render buffer. Для 352×198 при 150 kbps/15 fps — **47 encoded / 47
  delivered**; для 640×360 при 900 kbps/60 fps — **94 / 94** за примерно 5 с.
  `tx_drops=0`, превью и receive-frame sequence растут, остановка и destroy
  завершаются. Сами кадры не записываются. Пакеты передаёт локальная тестовая
  callback-петля; это **не** сетевой звонок, шифрование или P2P/relay-проверка.

Стенд — Windows 11 x64 с одной физической камерой. Windows 10 исходного
пользователя этим не квалифицирована. Первый изолированный capture probe
ошибочно возвращал длину вместо нулевого success-кода из transport stub;
его сбросы не считаются дефектом приложения, transport-результат не засчитан.
Финальная callback-петля использует штатный контракт.

Все запущенные probes завершены, временные каталоги smoke удалены. Установленный
xVeil, пользовательские контейнеры и production-серверы не менялись. Исправление
локальное: перед выпуском требуется пересобрать и обновить media pins; прежний
пин не содержит этот код. Жалоба снимается только после проверки исходного случая.
