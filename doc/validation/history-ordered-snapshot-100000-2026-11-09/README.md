# Свежий snapshot без лишней полной сортировки

## Механизм и границы

Own-history на каждом запросе сортировала все текущие строки разговора,
даже если они уже идут в wire order либо состоят из двух отсортированных
частей с одним небольшим смещённым блоком. Простая проверка «всё упорядочено»
не покрывает исходный native-кейс: перед старым архивом в нём уже записано
новое сообщение. Порядок fixture не менялся ради быстрого пути.

`sortMessageHistory` читает текущие координаты (миллисекунды/ID) один раз,
чтобы определить порядок частей. Если инверсий нет, сортировка не выполняется.
При одной инверсии две отсортированные части сливаются на месте, если меньшая
содержит не больше 128 строк. Буфер — не больше **128 Message references**,
без копирования содержимого сообщений и без сохранения между вызовами.
Два и более разрыва либо обе большие части используют прежний comparator sort.

Это O(n) для упорядоченного/малого displaced-run случая. Fallback сохраняет
O(n log n), с добавочным проходом максимум O(n). **Не заявляется ускорение
произвольной перемешанной истории.** Полный свежий fold, visibility scan и
paired edit-frontier reads остаются; кэша авторизации или старых rows нет.
Сами сообщения, raw timestamps и UI display order не меняются.

Wire cursor order прежний. Page cap 128, byte cap 128 КиБ/64 части, публикации
по 64 и live coalescing по 16 не менялись. Fresh auth/visibility/publication
checks и durable cursor сохранены. Sibling mailbox не включён.

## Регрессионные проверки

Добавлены проверки самого пути выдачи страницы, а не только helper:

* 100000 уже упорядоченных строк: parent **2451250 timestamp reads**,
  candidate укладывается в проверяемую границу **201000**;
* одно новое головное сообщение + 100000 строк архива: parent **2602491**,
  candidate укладывается в **401000**.

Оба source controls assertion-red на parent. Счётчик включает visibility,
сортировку, lookup, кодирование и metadata; проверяется также содержимое
всех 128 строк ответа и terminal cursor. Это work bounds contract fixture,
не runtime-счётчик реального HVS и не измерение CPU/fsync/wall time.

Наивный helper со стандартной сортировкой отдельно assertion-red:
996726 индексных чтений вместо 100000. Быстрый упорядоченный путь делает
ровно 100000 чтений и ноль записей. Проверены обе стороны буфера, cap 128/129,
большие части с fallback, перекрывающиеся диапазоны, одинаковая миллисекунда,
поздняя инверсия, новые вставки, смена timestamps, reversed/shuffled входы
и independent order oracle. Buffer size проверен на малых и 100000-row lists.

Setup-only census в native worker независимо считает разрывы **фактического
append/fold order**, до измеряемого окна, без ID/текстов/значений timestamps.
Он не сортирует строки и не меняет fixture; shape сверяется между фазами.

**235 related passed / 0 skipped**, отдельно **16 native HVS**; analyzer чист.
Прежние edit/revoke/publication/crash/byte-budget guards выполнены.

## Native A/B/A

Parent `4ffa14e6` → candidate → parent. Во всех фазах одинаковые test
instruments, четыре Mac/JIT процесса, три изолированных Core и настоящий
FFI/ratchet/HVS. Два полных источника, первый apply удержан до authenticated
ответов обоих. Compact observer каждые 5000 мс; sampling, work trace и
VM timeline выключены. Seed и shape census — до измеряемого окна.

Независимый setup census подтвердил у **обоих источников во всех трёх фазах**:
100001 строка, одна инверсия, первая часть длины 1, вторая — 100000.
Порядок append/fold одинаков; fixture не переставлялась и не уменьшалась.

Все **100000 архивных плюс одна прежняя строка** совпали по ID, телу,
delivered, canonical positions и порядку, без пропусков/дублей/лишних строк.
Оба cursor завершены. Cold boot без A/E/C сохранил полный набор. Не засчитано
равенство только счётчиков или пустых наборов. Wire/census не обрезаны.
Повторных page queries нет; каждый источник передал одинаковые **54217516
application-frame bytes** во всех фазах. Это не полный сетевой трафик.

На данном стенде candidate быстрее обоих контролей на **11–16 с**. Observer
имеет шаг 5000 мс и включает финальную проверку. Passive post-page witness
отдельно показывает сокращение этапа примерно на 10–12 с; он включает
доставку следующего inventory, не является точной меткой UI convergence.
Это одна локальная JIT серия, не универсальный коэффициент для AOT/телефонов
или произвольной перемешанной истории.

**Latency остаётся активной: около 3 мин 50 с на 100000 сообщений.** Интервал
полный reply → следующий query по-прежнему P50 около 167 мс в candidate,
а у контролей 164–169 мс. Он включает очередь, применение, cursor и доставку;
его нельзя называть чистым I/O. Worker RPC totals варьировались и не являются
доказательством устранения disk/authorization work. Следующий участок —
подготовка/apply и сохранение на получателе, плюс оставшийся свежий source scan.

## Происхождение и уборка

Candidate восстановлен; все исходники совпали с квалифицированной фазой B.
Native SHA/mappings проверены до/после, Rust не собирался.

нет, synthetic runtime удалён. Cache **92→92** во всех фазах, новых entries 0;
место во время измерений не чистилось. Свободно около **149 ГиБ**. Приватные
данные проверяются по полным изменённым файлам и новым reachable Git objects.

Только агрегаты в [summary.json](summary.json); raw captures/IDs приватны.

не закрыты. Коммит локальный unsigned, push/релиза нет.
