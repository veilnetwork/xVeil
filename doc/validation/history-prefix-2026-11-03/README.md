# Подтверждение уже сохранённого начала истории

2026-11-03. Продолжение [crash-квалификации 2000 сообщений](../history-initial-migration-crash-2026-11-03/README.md).
Mailbox собственных устройств остаётся выключенным.

## Два подтверждённых источника лишней работы

После рестарта B сравнивает inventory с полной историей A. Если у B уже есть
неполное начало разговора, несовпадение общего хэша ранее запускало пересылку
с первой страницы. В прошлом физическом опыте прошла 251 уникальная page,
а видимое число сообщений B стояло до 117,662 с. Это был повторный обход,
не доказанная сетевая тишина.

Второй путь работает в обратную сторону: A, имея весь разговор, видел меньший
inventory B и тоже просил его страницы. В изолированном тесте A сделал пять
page-запросов, хотя ни одной новой строки ему не требовалось.

## Изменение

Если меньший inventory полностью совпадает с началом локальной истории по
количеству и digest, он уже сохранён: страницы не запрашиваются. Это проверка
содержимого, не предположение «у меня больше строк, значит всё есть».

Для недостающего конца разговора первая page может содержать короткий
`prefix`: endpoint, count и SHA-256 уже сохранённых строк. Fingerprint учитывает
ID, канонический порядок, текст/emoji/edit frontier, shared delivered/reflected
state, а также временные координаты и направление. Источник сопоставляет
**полное** собственное начало до endpoint; только точное совпадение разрешает
отдать страницу после него. При несовпадении идут обычные страницы с начала.

Получатель требует совпадения подтверждения со своим outstanding request,
повторно проверяет текущее локальное начало и актуальное разрешение устройства.
Если данные изменились, ответ отбрасывается и запрашивается обычная страница.
Только затем выполняется durable checkpoint уже сохранённого, подтверждённого
начала. Ошибка записи не разрешает применить следующую страницу. Hint не
сохраняется; после рестарта нельзя восстановить неподтверждённый пропуск.
Курсор может указывать и на oversized record вслед за подтверждённым началом:
для него сохранены прежние digest, budget и запись после полного apply.

Authentication, device roster, binding, expiry, ratchet и ACK не ослаблялись.
Остаются прежние 128-КиБ/64-slice page, один outstanding request на sibling,
reply cache и admission bounds. Hint, не помещающийся в прежний лимит query,
не отправляется. Новый storage/relay mailbox, отдельная очередь и более долгий
timeout не добавлялись. Оптимизация не обходит обычный repair при разрыве,
отличии edit/delivery/ordering или изменении локальной копии.

## Проверки без сетевых порогов

До изменения тест с 32 сохранёнными строками из 40 получил **40 apply вместо 8**.
После первой правки этот участок стал зелёным, но добавленная проверка обратного
направления выявила **пять page у A вместо нуля**. Содержимое smaller inventory
теперь проверяется отдельно; итог — только восемь недостающих apply и одна
page у B, ни одной page у A. Это независимое доказательство снятия работы,
не тест «уложиться в N миллисекунд».

Проверены также:

- Дыра в середине, edit frontier, недоставленный статус и provisional order:
  начало не пропускается, обычный repair восстанавливает строки/состояние.
- Локальная правка во время запроса: нет checkpoint по устаревшему hint,
  сохранена более новая правка, выполняется обычная догрузка.
- Отзыв при повторном чтении локальной копии и неподтверждённый digest:
  ни apply, ни продвижения cursor.
- Отказ durable checkpoint: cursor остаётся до hint; новый экземпляр сервиса
  завершает обычную догрузку. Сам hint в settings не попадает.
- Oversized record после девяти уже сохранённых больших строк: доставляется
  только одна недостающая запись с прежними record-проверками.

Общая серия после добавления resume-проверок — **153 passed**, включая
private-probe проверку. Probe сохраняет только количество строк hint, без его digest,
endpoint, message ID, текста или sender ID. Его прежний private request ID
остаётся только в закрытом стендовом trace. Analyzer четырёх изменённых Dart
файлов и форматирование чистые.

Первый запуск проверки in-flight изменения не зачтён: oracle выбрал повтор
того же request, допустимый существующим retry-таймером, вместо нового
fallback request. Проверка исправлена по ID запросов; таймеры не менялись.

## Native-квалификация

Изолированные Mac/JIT процессы A/B одной личности и C другой. Каждый прогон
создаёт 2000 настоящих A→C сообщений, проверяет их delivered, добавляет B и
делает SIGKILL B посреди догрузки. При его запуске оба источника offline:
отдельный закрываемый inspector проверяет неполную копию на диске до сети.
Затем возвращается только A, C остаётся выключенным. Итоговый oracle — точные
ID, порядок, source positions и все delivered, без дублей/пропусков/повторов
завершённой истории. В конце B ещё раз запускается без A/C.

Первая серия закончена с точной сохранностью во всех трёх случаях:

| Фаза | На диске после SIGKILL | Все ID/порядок/status от возврата A | Page B → A после рестарта A | Page A → B после рестарта B |
| --- | ---: | ---: | ---: | ---: |
| Первый candidate | 1522 | 41,003 с | 57 | 0 |
| Контроль `55edf750` | 1522 | 153,866 с | 251 | 189 |
| Повтор того же candidate | 1522 | 148,314 с | 251 | 192 |
| С исправленным resume | 1522 | 148,422 с | 251 | 195 |

В первом candidate предложен hint на 1548 строк; количество page соответствует
оставшемуся концу разговора. В контроле счётчик видимых backlog-строк стоял
102,543 с. Но повтор того же candidate тоже вернул долгий обход. Поэтому
первая быстрая серия **не объявляется устойчивым устранением задержки**.
Все три запуска завершены, библиотеки неизменны, runtime удалены; оставшихся
owned процессов/listeners нет. В паре первый candidate/контроль среди 1400
source hashes отличался только production `messaging_own_history.dart`.

### Пробел возобновления сохранённого курсора

В медленном повторе source A после перезапуска не делал нового list к B:
сохранённый page cursor сразу запускал страницы из неполной копии B. Новая
проверка меньшего inventory в этой ветке не выполнялась. Дополнительно receiver
со старым cursor не мог подтвердить уже полученные по другому пути строки
впереди него. Два red-теста показали четыре лишние page вместо нуля и 32 apply
вместо восьми. После исправления оба зелёные. Отдельно проверено: меньший
inventory с новой правкой не пропускается.

Теперь восстановленный pull один раз проверяет текущий inventory. Если нужны
страницы той же беседы, прежний durable cursor сохраняется. Подтверждение
локального начала может продвинуть его дальше только после прежних проверок
source/receiver, причём endpoint обязан быть строго больше старого cursor.
Blind skip, сброс timeout и сохранение неподтверждённого hint не добавлены.
Две корректировки fixture не считаются доказательством production дефекта:
после неудачного checkpoint новый сервис теперь вправе заново подтвердить
локальные строки (восемь apply вместо 24), а ручной источник budget-теста
должен ответить на новый list перед record. Четыре MiB budget не менялись.

Native-серия с resume-проверкой тоже завершена: все 2000 сохранились, но долгий
обход остался. Теперь source A действительно делает list после перезапуска,
так что установленный пробел возобновления устранён; совпадающая часть всей
локальной копии по-прежнему не подтверждается. Предложенный hint на 1573 строки
не позволил сократить обход 251 page. Счётчик B стоял в последовательных
выборках 97,202 с. Точное место отказа hint — source или повторная проверка B —
этот passive trace не различает. Поэтому общий latency-дефект остаётся активным.

В final positions медленных candidate обнаружено 100 строк с repaired ordering
в конце исходной истории (индексы 1900–1999); в быстром candidate таких строк
нет. Итоговые canonical positions и timestamps всех 2000 совпадают с A.
Это направление следующей проверки, не доказательство состава частичной копии:
требуется read-only захват уже существующего worker snapshot во время плато,
чтобы отличить непрерывное начало от копии с дырой и ранним поздним хвостом.
Число видимых сообщений само по себе этого не доказывает.

[Следующий цикл](../history-sparse-prefix-2026-11-04/README.md) подтвердил
частичную копию с дырой и поздним provisional tail. Отказ полного hint оказался
правильным; добавлен выбор среди нескольких меньших совпадающих начал.

Каждый native прогон завершён кодом 0 с независимым cleanup. Проверены owned
PID/порты: 26/27, 27/32, 26/30, 27/34; оставшихся процессов/listeners нет,
runtime удалены, native/HV SHA неизменны. Во время каждого запуска неизменны
те же 1400 frontend/test/dependency файлов. После первой тройки production
resume и его unit tests изменены, четвёртая серия квалифицирует именно эту
версию. Эксперименты не суммируются как четыре повтора одной версии.

Android/AOT, сутки offline и полная multi-device матрица этим сценарием
не объявляются проверенными. Совместимость старых версий не является гейтом
по указанию владельца; соответствующей физической квалификации здесь нет.

Нативный SDK не менялся (`b8647716`), Rust не пересобирался. Проверяются SHA
выбранных CLI/FFI/HV и source manifest каждого запуска. Сырые пути, ключи,
идентификаторы и wire traces в публичную запись не включаются. Push, релиза
и изменений публичных сидов нет.
