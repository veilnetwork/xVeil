# Poco ↔ Mac: длинное наблюдение после возврата Wi-Fi

**NETCALL-01 открыт.** Два разговора сохранились при cellular → Wi-Fi и
последующих 60 секундах наблюдения; последние пять срезов обоих endpoints
содержат свежий аудиоприём. При этом наблюдались разрывы приёма до **6,037 с**.
Во втором разговоре разрыв появился через **35–40 с после переключения**,
поэтому его нельзя выдавать за непосредственную длительность handover.
Агрегаты: [summary.json](summary.json).

## Условия и oracle

Та же SDK `4f441329`, три ранее проверенных native-артефакта и прежний
подписанный QA AOT/media/HVS из [предыдущей серии](../binding-handover-2026-11-07/README.md).
Происхождение и SHA повторно проверены; Rust builds в этой физической серии
не было. 1533 frozen SDK inputs соответствуют исходному checkout; новые
изменения writer сделаны **после** этой серии и ею не квалифицированы.

Poco / Android 16 с SIM и Mac, один отдельный Core через obfs4/TCP.
Точный transport peer каждого клиента подтверждён active, P2P запрещён
с обеих сторон, discovery/builtin seeds выключены. Это non-onion Delivery
relay, не private onion и не проверка Windows или последнего Dart frontend.

Каждый разговор начинается на OS-validated cellular. Перед включением Wi-Fi:
пять последовательных свежих RX-срезов обоих endpoints, затем 15 с контроля
и ещё проверка последних пяти срезов. После Wi-Fi on — не менее 60 с,
проверка прежнего call ID на каждом срезе и пяти конечных свежих RX-срезов.
Свежесть: active/running, worker stall 0, положительный audio RX counter,
native RX age 0–1000 мс. Это автоматическая проверка потока, не слышимость речи.

| Направление вызова | Входящий от запроса | Пять fresh RX от запроса | Max RX age Poco / Mac после Wi-Fi on |
|---|---:|---:|---:|
| Poco → Mac | 1,202 с | 6,615 с | 728 / 5358 мс |
| Mac → Poco | 1,628 с | 7,777 с | 5410 / 6037 мс |

По 301 срезу каждого endpoint, API errors 0, максимальный интервал между
срезами одного case 704 мс. Падений RX counters нет; во всех наблюдавшихся
срезах каждого разговора один media epoch. Это не доказывает непрерывность
между срезами и не измеряет акустическую задержку. Нет A/B и оснований
приписывать различие с прошлой серией ACK-фиксу или объявлять ускорение.

## Атрибуция остатка

В первом разговоре возраст RX на Mac рос в начале возврата Wi-Fi; на Poco
приём продолжался. В том же окне телефон отметил local-source drops.
Существующий счётчик объединяет `child_unavailable` и `source_budget`:
семь записей за серию сами по себе не различают причины потерь.

Во втором разговоре есть другой механизм: уже после восстановления медиа
основной writer достигает **30-с таймаута flush**, затем primary read
закрывается. `session.close` наступает ещё через **5,003 с**, новая session
открывается приблизительно через 0,36 с после close (все интервалы — по
часам телефона). Этот участок совпадает с поздним разрывом аудиоприёма.
Причина первоначально зависшего flush не установлена.

По коду `writer_task` после write error / idle timeout переходил к общему
`shutdown().await`. У буферизованного obfs4 shutdown снова сбрасывает
оставшийся шифртекст; он мог зависнуть на том же неисправном канале.
Runner продолжал ждать graceful drain до пяти секунд, прежде чем abort
освобождал writer и разрешал reconnect. Это отдельно воспроизведённый
дефект; [исправление и красные тесты](../failed-writer-shutdown-2026-11-07/README.md).
Физическая серия описывает прежний код, эффект исправления ещё не измерен.

### Полный захват вместо прежнего неполного

Перед удалением QA-stage захват остановлен; удалённый файл сжат, копирование
дождалось терминального успеха, после распаковки совпали полный размер и SHA.
Cleanup требует этот successful-copy marker. Полный PCAP разобран до EOF:
28 697 пакетов, 177 TCP flows с разделением повторного использования tuple
по новому SYN sequence. 148 имеют наблюдаемый новый SYN; у 81 наблюдаются
клиентские payload bytes, и у всех 81 есть server payload bytes.

Это **не** доказательство успешной аутентификации каждого потока или доставки
медиа. Среди flows есть ранее открытые соединения, Mac, отменённые кандидаты
и возможные внешние подключения; без socket/canonical-child attribution
нельзя объявлять их все попытками телефона. Отсутствие клиентских bytes
также не считается потерей сети: попытка могла отмениться до отправки.

Для позднего flush timeout process-local TCP connection number связан с
local port, а тот — с единственным подходящим flow захвата. Последний
наблюдаемый клиентский пакет — через 506 мс после SYN; затем в захвате
остаются повторные server payload packets, но ACK клиента уже не движется.
Это показывает, почему один начальный server response не доказывает здоровье
последующей сессии. Связь установлена по port/time, без расшифровки содержимого;
точка потери между NIC сервера и сокетом телефона не определена.

OS-default-network и QA-target TCP sockets снимались примерно раз в секунду.
392 строки сокетов со старыми Wi-Fi адресами при cellular были FIN-WAIT-1,
**не ESTAB**. Они не доказывают отправку через старый Wi-Fi. Clock probes
телефона ограничивают ошибку привязки времени; cross-host PCAP не выдан за
покадровую атрибуцию аудио. Raw sockets/логи/PCAP остаются приватными.

## Очистка и следующий шаг

Проверены SHA восстановленного QA APK, неизменность обычного APK и прежнего
root QA-контейнера. P2P values и stored values, Wi-Fi/mobile/awake settings
возвращены; исходный validated Wi-Fi подтверждён. Свои Mac/Android apps,
logcat и probe завершены, локальные QA-порты освобождены. Mac потребовал
SIGKILL после grace. Подпись собственной Mac-копии после уборки проверена.
QA capture/Core/unit/state/config/binary/ports удалены; production PID,
executable/config SHA и NRestarts не изменились. Windows не использовалась.

Следующая физическая проверка — повтор этих двух длинных сценариев на
исправленном writer: отдельно измерить исчезновение пятисекундного drain
и проверить, остаётся ли сам 30-с flush timeout. Короткую начальную паузу
первого разговора нужно атрибутировать отдельно. Смена аудиобуфера, ослабление
авторизации и уменьшение liveness timeout по этим данным не требуются.
Push, релиза и обновления production-сидов нет.
