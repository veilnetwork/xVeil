# Порядок приветствия при повторах запроса — 2026-11-05

База `c51e12ca` (runtime source `971c9d5c`). Локальная правка Dart, без
push/релиза, изменений native/ABI, сидов и mailbox собственным устройствам.

## Подтверждение

[Физическая Windows ↔ Android серия](../windows-android-signaling-2026-11-05/README.md)
нашла одинаковые три сообщения без дублей, но разный канонический порядок
старого приветствия. Это отдельный дефект; исходную пользовательскую
недоставку контактов/звонков он не объясняет.

`sendRequest` сохранял приветствие с авторским seq, но request не передавал
его на wire. Каждый повтор до принятия контакта снова вызывал `_store` без
seq и выделял очередной локальный номер. Уже принятая обычная копия сообщения
затем дедуплицировалась по ID и не исправляла позицию. Author-monotone floor
поднимал старое приветствие после более нового сообщения. Ручной resend
также терял исходный timestamp.

Воспроизводитель использует настоящие MessagingService и Storage: четыре
доставки одного undecided request → принятие → новое текстовое сообщение.
На исходном коде canonical `loadMessages` даёт противоположный порядок
приветствия и нового текста; событие не создаётся искусственной правкой seq.
Это тот же механизм и симптом; точные birth-order witnesses старого
физического профиля отдельно не извлекались.

Всего **10 assertion-red**, включая worker с настоящим HVS-контейнером:
initial wire, durable/fallback resend после reopen, порядок, legacy повтор.
Первая попытка fixture имела два compile error и в red не засчитана.

Graphify указал существующий ordering regression, CodeGraph вернул low
confidence общий поиск без нужного потока. Причина установлена по коду и
тесту, а не по эвристическим связям графа.

## Исправление

- Request передаёт seq фактически сохранённого приветствия через существующее
  optional wire-поле. Автор по-прежнему определяется аутентифицированным peer.
- Resend сохраняет исходные seq/timestamp из durable request; для старой
  очереди или её отсутствия использует собственную сохранённую строку.
- Повтор legacy request без seq сохраняет первую локальную позицию и время.
  Обновление текста pending intro с тем же ID остаётся допустимым.
- Пустой запрос не создаёт сообщение или фиктивную позицию. Consent, ранний
  ACK, anti-spam cap и удаление истории не обходятся.

## Квалификация и границы

14 новых тестов, семь с worker/native HVS. Включены sender reopen,
receiver cold fold, восстановление старого durable request и пустой запрос.
**154 scoped passed** в шести файлах; расширенный контроль с diagnostics:
**940 passed / 43 файла / без skip**. Analyzer трёх файлов и diff check чистые.
HVS `eceb9158`, библиотека сверена по SHA с прежним source/build proof;
Rust не пересобирался, исходники submodule не менялись.

Повтор физической серии с этой последней правкой ещё не выполнялся: текущие
QA APK/Windows bundle относятся к предыдущему signaling-прогону. Старые
уже искажённые позиции автоматически не мигрируются; legacy request без
авторского seq сам по себе не доказывает канонический номер отправителя.
Обычная сетевая недоставка и звук требуют своей квалификации.

Все свои физические приложения, задачи и forward остановлены до локальных
тестов. Сырые отчёты/журналы, адреса и идентификаторы не добавлялись в репозиторий.
