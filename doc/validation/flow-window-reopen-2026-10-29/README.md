# Окно из DATA и возобновление чтения — 2026-10-29

## Исправленные механизмы

Veil `524112a2`, предыдущая версия `04eb1c1d`.

| Механизм | Воспроизведение | Исправление |
| --- | --- | --- |
| DATA перезаписывал более свежее окно ACK | Обратный DATA с устаревшим нулём останавливает отправку после свежего ACK; старое положительное значение открывает уже закрытый буфер. Воспроизведено и на первом получении, и на повторе DATA. | Кредит задают handshake и проверенные ACK. Поле DATA не заменяет окно. |
| Освобождение буфера приложением не сообщалось отправителю | После ACK с нулём `read()` освобождает место, но не создаёт обновление. Отправитель ждёт persist-пробу даже при работающем соединении. | Чтение после закрытого/малого окна планирует ACK с текущим свободным местом. |
| Обновление окна считалось признаком потери | Три ACK с неизменным cumulative ACK, меняющимся окном и без новых SACK запускают fast retransmit. | Такое обновление не увеличивает dup-ACK count. Обычные дубли и новые SACK остаются доказательствами потери. |

DATA содержит sequence своей стороны, но не cumulative ACK другой стороны.
Поэтому даже первый, правильно упорядоченный DATA невозможно сравнить по
возрасту с ACK встречного потока. Проверка только `seq >= rcv_nxt` не решает
первый случай. Удаление устаревшего window update не удаляет payload,
подтверждение, SACK или D-SACK повторившегося DATA.

`read()` объединяет мелкие чтения. Порог — `min(max(window/2, 1), max(MSS, 1))`:
обновление нужно после ранее объявленного окна не больше порога, когда
освободилось не меньше порога. Значение снимается при кодировании ACK; несколько
чтений до отправки дают одно обновление. При достаточном свободном окне
дополнительные window-only ACK не создаются. Нет уведомления от пустого чтения,
после EOF или в закрытой фазе.

Это соответствует разделению flow control и признаков потери в
[RFC 5681 §2](https://www.rfc-editor.org/rfc/rfc5681.html#section-2): для dup-ACK
важно неизменное окно либо новая SACK-информация. Полного соответствия TCP
этому transport-agnostic движку не заявляем.

## Старые получатели и ограниченная проба

Просто игнорировать DATA-window оказалось недостаточно для смешанного обмена:
старый получатель не создаёт ACK при чтении и может сообщить об освобождении
буфера только обратным DATA. Первый кандидат увеличивал ожидание в части
смешанных профилей. Он не считается окончательным результатом.

В окончательном варианте положительное поле DATA может только подсказать
существующую однобайтовую persist-пробу, когда окно равно нулю, outstanding
сегментов нет, а приложение ещё ждёт отправки. Она не выдаёт кредит обычному
flight. Не более одной такой подсказки используется до следующего проверенного
ACK с ненулевым окном. Повторные/задержанные DATA не создают поток проб.
Свежий ненулевой ACK отменяет ещё не отправленную пробу: обычный DATA не
дробится на один байт без необходимости. Пустой DATA не вызывает пробу.

Если обновление потеряно или старый узел не прислал подсказку, сохраняется
прежний persist/retransmit путь. Пределы таймаутов и retries не менялись.
DATA-window по-прежнему кодируется для старых узлов; формат v1, wire version,
C ABI, mailbox, ratchet, durable ACK приложения и политика реле не менялись.

## Проверки

На прежнем движке с теми же исходниками тестов упали **10 window-тестов и
один async driver-тест**; восемь проверок того набора уже проходили. Эти 11
падений не называются 11 независимыми дефектами. Проверены оба значения RACK,
циклический переход sequence через `u32::MAX`, первое/повторное получение DATA,
пустой DATA, read-coalescing, потеря обновления, одноразовость подсказки и
сохранение настоящего dup-ACK/SACK loss detection.

В async-тесте реальный `OnionStream` заполняет 16 слотов канала приложения и
буфер движка. Чтение одного байта освобождает слот и будит уже существующий
`reserve()` драйвера. На прежнем коде ACK с открытым окном появлялся через
**10 000 мс виртуального времени**, только после новой однобайтовой пробы.
В окончательном варианте — **0 мс** дополнительного виртуального времени,
с тем же cumulative ACK, без нового DATA. Все 4096 байт и EOF проверены;
оба драйвера сообщили завершение до удаления handles.

Первый вариант read-notification отправлял дополнительные ACK и при большом
свободном окне. Полный существующий тест двух маршрутов 100/500 мс выявил
лишний RTO без реальных потерь. Уведомления ограничены малым окном; исходный
тест, включая запрет RTO, не ослаблен и проходит. Добавлен отдельный запрет
лишнего ACK при достаточном окне.

Окончательная проверка: **197 stream-тестов прошли, ignored нет**; **326 FFI
прошли, два ignored** при `--no-default-features` и
`node-embedded,production-seeds,packet-tunnel`. Дочерняя проверка subprocess
не прибавляется к 326. Clippy `--lib --tests -- -D warnings` и rustfmt прошли.
В production не добавлялись тестовые hooks или экспериментальные флаги.

## Обмен старого и нового движков

[mixed_probe.rs](mixed_probe.rs) использует обе настоящие версии `StreamEngine`
в одном процессе, обмениваясь v1-кадрами. В обе стороны по 4096 разных байт,
MSS 64, receive-window 128, initial cwnd 128, BBR включён. Оба приложения
сначала не читают 25 мс, затем читают с разным тактом 3/5 мс. Два FIFO дают
3 мс доставки каждый; сериализация полосы, DHT, crypto и circuit не моделируются.
Одна сторона проходит wraparound. Для каждого сочетания выполнены RACK on/off
и вариант потери первого открытия окна в каждом направлении: **16 профилей**.

Все профили сохранили каждый байт и дошли до EOF в обе стороны. Время ниже
виртуальное, до полного закрытия; совпало для RACK on/off в этом наборе:

| Отправляющий opener | Принимающий acceptor | Без потери, мс | С потерей двух window updates, мс |
| --- | --- | ---: | ---: |
| Старый | Старый | 4130 | 4237 |
| Старый | Новый | 344 | 5935 |
| Новый | Старый | 4540 | 13 872 |
| Новый | Новый | 344 | 349 |

**Задержка части смешанных профилей хуже old/old.** Целостность не доказывает
равную скорость. Ожидания смешанного пути остаются открытым остатком совместимости;
не объявляем их устранёнными и не выдаём этот опыт за измерение телефона или
публичного onion-маршрута. Отдельные подсказки уменьшают часть ожиданий первого
кандидата, но не дают общего улучшения всех смешанных профилей.

Для повторения нужен отдельный Cargo binary с зависимостями `old` и `new`,
обе с `package = "veil-onion-stream"` и `path` на соответствующие исходники.
В приватной standalone-копии old сохранены production-исходники `04eb1c1d`;
только package-version переименован в `0.1.0-validation-old`, чтобы Cargo различал
два path-package, и снято наследование workspace lints. Для старой копии,
смешанного воспроизводителя и основного checkout использованы разные external
target. Команда — `cargo run --offline --release`; исходник `src/main.rs` совпадает
с опубликованным воспроизводителем. Результаты без приватных путей —
[summary.json](summary.json).

## Границы и гигиена

Паузы проблемного провайдера, прежние «33%», 343 unknown cells, per-hop
атрибуция и все причины больших RTT этим опытом не закрыты. Начальное окно
64 MSS и холодная очередь из прошлого отчёта не менялись. Остальные открытые
пользовательские жалобы не перепроверялись.

Это модель/driver/FFI-проверки. Телефон, macOS GUI, реальные реле и звонки не
запускались; установленные приложения не заменялись. Тестовые процессы
завершились, а проверка async-драйвера дождалась обоих callbacks закрытия.
Каждая Rust-сборка проверяла фактический внешний mount и непрерывно следила
за его сохранением. Логи и исходные трассы остаются в приватном каталоге.
Push, релиз, установка и обновление серверов не выполнялись.
