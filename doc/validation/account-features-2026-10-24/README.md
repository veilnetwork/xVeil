## Пользовательские изменения

* [Подробный гайд по узлу](../../NODE-SETUP-RU.md): Linux/systemd и Windows 10,
  ключи и PoW, TCP/QUIC, приглашения, резервная копия, диагностика и обновление.
  Восемь команд CLI выполнены на временном конфиге; сервер в этом прогоне не
  запускался. Обнаружено, что проверенный CLI `config init` требует отдельного
  аргумента PATH: один глобальный `-c` не задаёт место создания нового файла.
* Меню, карточка настроек и центр безопасности читают публичное имя из
  контроллера реального claim, включая его живое обновление и перенос с другого
  устройства. Под именем виден ID узла; в карточке аккаунта он доступен для
  выделения. Подтверждённо перехваченное имя не используется как собственное.
  В разделе никнейма объяснено применение `@имя` в добавлении контакта.
* Своё фото выбирается в «Настройки → Личности и аккаунт». Принятые контакты
  видят его в списке чатов и заголовке переписки. Своим устройствам фото и его
  удаление передаются существующим журналом настроек, с backfill при привязке.
  Контактам — только живым аутентифицированным каналом, с обновлением кэша при
  следующем запросе, если они были offline. В mailbox фото не записывается.
* «Настройки → Конфиденциальность → Быстрая разблокировка»: графический ключ
  3×3, 4×4, 5×5, минимум четыре разные точки; системная аутентификация на
  поддерживаемом устройстве. Для открытия контейнера после перезапуска есть
  отдельный, выключенный по умолчанию переключатель. Обычный пароль остаётся.

## Защита данных

Аватар — JPEG не более 1300 байт и 128×128 пикселей. Файл перед выбором ограничен
8 МиБ, исходное изображение — 40 млн пикселей. Сохраняются заново закодированные
пиксели без исходного пути, EXIF и имени файла. Формат помещается в реальное
ограничение setting 2048 байт и authenticated frame 6144 байта. Получатель
проверяет размер/формат/габариты до декодирования изображения. Новый wire kind
добавлен в конец протокола перед `unknown`, старые индексы сохранены. Чужая
заявленная identity, неизвестный или заблокированный отправитель фото не меняют.
Запросы/ответы ограничены по частоте, таблицы ограничены 512 пирами.

Экранная блокировка оставляет контейнер открытым и сеть работающей. В её памяти
только проверочные значения; она не сохраняет пароль. Пароль и графический
ключ используют общий монотонный throttle. Поздний ответ ОС не открывает другой
сеанс или другую личность. Системный диалог не считается обычным уходом в
`inactive`, но настоящий background продолжает включать блокировку.

Вход после перезапуска — отдельная модель с явным согласием. Исходный пароль
контейнера сохраняется в хранилище ОС, а не заменяется коротким ключом:

* Для графического входа пароль обёрнут AES-256-GCM с привязкой к профилю через
  AAD. Ключ получается из последовательности, случайного секрета в OS vault и
  PBKDF2-HMAC-SHA256 с 210000 итераций. Одной копии контейнера и обычных файлов
  профиля для быстрого входа недостаточно. OS vault остаётся частью доверенной
  среды: доступ к его секретам позволяет атаковать короткий графический ключ.
* Android использует принудительную strong-biometric защиту записи Keystore;
  iOS — `biometryCurrentSet` и несинхронизируемую запись текущего устройства.
  Перенастройка создаёт новый защищённый слот и удаляет прежний, включая случай
  изменения набора биометрии. Реальные биометрические операции на этих ОС здесь
  не выполнялись.
* На macOS используется обычный локальный Keychain, совместимый с ad-hoc сборкой;
  Touch ID проверяется отдельно перед выдачей сохранённого входа. На Windows
  используется защищённое ОС хранение и отдельное подтверждение Windows Hello;
  Hello может предложить PIN. Эти две схемы не заявляются криптографической
  привязкой каждой записи к отпечатку.
* xVeil не получает шаблоны отпечатков или лица. Запись для быстрого входа
  оставляет след вне скрытого контейнера; это объяснено перед включением.
  Это удобство на доверенном устройстве, с дополнительной зависимостью от
  хранилища ОС. Оно не обещает стойкости к компрометации ОС/учётной записи или
  удаление ранее сделанных внешних копий.

По умолчанию xVeil даже не читает OS vault: сначала проверяется сохранённое
явное согласие. Перед записью биометрического секрета сохраняется намерение
очистки. Оно остаётся до подтверждённого удаления, в том числе после отказа ОС.
Сохранение проверяется повторным чтением. После десяти неудачных графических
попыток нужен пароль и перенастройка; счётчик переживает пересоздание сервиса.
Это ограничение приложения, без обещания защиты от отката всей ОС.

«Начать заново» удаляет сохранённый вход до сброса onboarding; при отказе
приложение блокируется и сброс не считается успешным. Wipe продолжает удаление
остальных данных и отдельно показывает оставшуюся OS-запись. Завершение сеанса
по-прежнему инвалидирует незавершённые unlock до первого await. Данные быстрого
входа не входят в allowlist multi-device и не переносятся на другие устройства.
Ошибки OS vault не передают пароли в журнал или отчёт.

  Xcode, и Android build наблюдались с проверкой внешней файловой системы;
  исчезновения `/Volumes/cfb` не было. Flutter/macOS запускались с `/private/tmp/`.
* Проверка готового APK обнаружила старый локальный prebuilt hidden-volume:
  значение ABI для `vacuum_data_batches` было 48307 вместо 56095. Библиотека
  arm64 пересобрана из текущей HV `47c28bc`, APK собран повторно. На библиотеке,
  извлечённой именно из финального APK, совпали **43 из 43** UniFFI checksum;
  у Veil присутствуют **203 из 203** объявленных в текущем C-заголовке символов.
  Это проверка совместимости локального артефакта; она не устанавливает причину
  сообщения пользователя о Windows 10 или старого опубликованного релиза.
