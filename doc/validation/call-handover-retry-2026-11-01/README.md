# Звонки после смены сети: повторы signaling и физический контроль

Дата: 2026-11-01. NETCALL-01 остаётся открытым. Подтверждён и исправлен
дополнительный механизм задержки: после быстрых повторов неподтверждённый
сигнал звонка наследовал длинный экспоненциальный backoff. Пауза аудио при
смене сети внутри разговора по-прежнему воспроизводится.

## Механизм и исправление

На Poco → Windows предложение дошло сразу после отключения Wi-Fi, Windows
ответил, но телефон получил ответ значительно позже. В журнале отправителя
попытки ответа были разнесены примерно на 9-ю и 18-ю секунды после начала
проверки. Получатель сообщил возраст ответа около 17 с; это поле зависит от
часов двух устройств и не используется как точное измерение one-way latency.
До ответа приходили более новые health-кадры. Поэтому первоначальное объяснение
«все 20 секунд занял выбор P2P» отозвано: медиастарт начался после позднего
ответа и занял около двух секунд. Пригодность маршрута в каждый момент между
попытками этим захватом не установлена.

Детерминированный regression использует настоящие MessagingService и хранилища:
сохранённый answer семь раз локально отправляется в недоступный маршрут, затем
маршрут восстанавливается. На прежнем коде flush через три виртуальные секунды
после восстановления не отправлял ответ: следующий интервал достиг 16 секунд.
Это отдельное доказательство механизма backoff, не атрибуция всей физической
задержки. После исправления B получает ровно один answer, его настоящий ACK
удаляет исходную строку, следующий flush больше её не отправляет.

Для call-control backoff ограничен двумя секундами в обоих путях — короткой
лестнице и последующих проходах Outbox. Это интервал готовности к следующей
попытке, **не гарантия доставки за две секунды**: остаются cadence планировщика,
admission, очереди и доступность сети. Обычный backoff, fairness/лимит прохода,
персональные lanes, ACK/dedup и срок жизни сигналов не менялись. Повторов при
потерянном ACK может стать больше; срок жизни и имеющиеся лимиты остаются
границами этой работы. Криптографические и durable-барьеры не обходятся.

Проверки: regression был красным по оставшейся строке Outbox; затем 130 связанных
тестов прошли. После усиления oracle проверкой единственного входящего answer
этот же тест повторно прошёл; это не дополнительный уникальный тест. В набор
входили истечение call-control, ACK retirement, обычный backoff, peer lanes,
инвалидация flush, retention и наблюдатель смены сети. Analyzer двух файлов чист.

## Физические результаты

Отдельные QA-профили: настоящий Poco с Wi-Fi и мобильными данными и компьютер
Windows 11. Это не Windows 10 из прежней пользовательской жалобы. В сценариях
активного разговора и двух последних немедленных вызовах проверялось, что
default network перед отключением действительно Wi-Fi; после переходов — cellular.
Сеть production; маршруты/реле не фиксировались и не обновлялись.

Вызов сразу после команды отключения Wi-Fi; времена от начала этой команды:

| Сборки | Входящий на Windows | Оба конца `active` |
|---|---:|---:|
| Android до новой правки, прежний Windows QA | 0,82 с | 20,05 с |
| Android до новой правки, текущий Windows QA | 0,77 с | 2,84 с |
| Текущие QA на обоих концах | 0,83 с | 5,31 с |

Во всех трёх случаях после соединения наблюдались полученные аудиопакеты на
обоих концах. Полная недоставка входящего из исходного репорта не воспроизвелась.
Условие «ровно один активный узел» специально не создавалось. Это отдельные
прогоны с меняющимися маршрутами/кэшами и рестартами, **не A/B доказательство
ускорения** и не доказательство устранения исходного случая.

Во всех трёх проверках Wi-Fi отключался также внутри установленного разговора.
Один call ID сохранялся на каждом конце, все последующие выборки оставались
`active`; после перехода наблюдение продолжалось около 40 секунд. Но максимальный
выбранный `audio_rx_native_age_ms` достигал 12,4–14,7 с. Это возраст последнего
полученного audio payload, не гранулярность файловых частей и не средняя задержка
звука. Пауза остаётся подтверждённой на текущих QA. Сырые счётчики пакетов между
разными media epoch не сравниваются как непрерывный счётчик; итоговый маршрут
мог быть P2P либо relay. Новая политика повторов не объявляется решением этой
паузы. Следующий участок — время от события ОС до пригодной сессии, fallback
медиа и появления payload на новой сети.

Слышимость речи не проверена человеком. Android показывал запуск capture/playout,
но sampled input band оставался 0; Windows output band был 1. Это не проверка
разборчивости: ненулевой выход может включать comfort noise. Системный AudioRecord
во время контроля был активен и принадлежал именно QA; конкуренция с записью
основного приложения в этом срезе не обнаружена. Внешний тестовый тон на Mac не
дал контролируемого возбуждения микрофона и не считается аудио-калибровкой.
Жалоба «телефон → Windows не слышно» остаётся открытой.

## Происхождение и завершение

Android — profile/AOT. Windows — profile/AOT с опубликованными runner/plugins и
native DLL; полная пересборка Windows C++ здесь не проводилась. Все 590 переданных
исходных файлов Windows сверены по SHA после сборки. Android APK после установки
сверен с локальным артефактом; три native-библиотеки совпадают с предыдущей
проверенной сборкой и опубликованными библиотеками. Хеши и числовые результаты —
в [summary.json](summary.json). Native Rust не пересобирался. Flutter Android
собирался под mount-watchdog: внешний target оставался на отдельной ФС.

QA-приложения остановлены, собственные порты/ADB-forward/SSH-туннель освобождены,
Windows scheduled task удалён. Вспомогательный Mac QA после lock не вышел по
SIGTERM за 15 секунд и остановлен SIGKILL только своей группы; выход проверен.
Новые QA-профили/резервная сборка сохранены для продолжения. Wi-Fi, mobile data
и временно изменённый stay-awake возвращены в исходное состояние; основной
Android-процесс сохранил PID, его контейнер не открывался и не заменялся.
Частные журналы, адреса, идентификаторы и recovery-материал в отчёт не включены.
Push, релиза и обновления сидов нет.
