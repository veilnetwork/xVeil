# Получатель в ID доставки disappearing policy — 2026-11-05

База `2fa3a8af`. Локальный шаг, без push/релиза, изменения native ABI,
APK/engine pins/сидов или добавления mailbox собственным устройствам.

## Подтверждено

`_announceDisappearing` строил ID только из версии policy и её автора.
Outbox хранит ключ frameId глобально для активной личности, а не отдельно
по получателю. Поэтому два разных контакта с одинаковыми setAtMs/setBy
делили один ID: второй enqueue считался повтором первого и не сохранялся.
Успешная начальная live-попытка не означала наличия обязанности повторить
доставку второму контакту после потери сети/перезапуска.

Два assertion-red на исходном коде: ordinary HVS и worker/native HVS.
Публичные setters вызываются с фиксированными часами для двух accepted
контактов, TTL различны. Из двух адресатов в pending Outbox оставался один.
Это воспроизведение механизма; частота совпадения времени на реальных
устройствах не измерялась, связь с Windows-репортом не доказана.

## Исправление и границы

ID теперь включает получателя, версию и автора. Повтор прежней версии
тому же получателю по-прежнему использует тот же ID. Payload, проверка
автора/свежести, durable enqueue и привязка ACK к отправителю не менялись.
System marker хранится в своём разговоре и его ID не меняется.

Уже существующая legacy-запись Outbox не удаляется и не переписывается.
Байты второй, ранее не сохранённой записи этим изменением не восстанавливаются.
Общая модель хранения/сходимости и правила disappearing messages не меняются.

## Проверка

Расширенные два случая используют три storage/messaging endpoint на backend:

- две разные policy с одинаковой версией сохраняются независимо;
- повтор той же версии одному адресату оставляет две записи, не три;
- после закрытия и повторного открытия контейнера обе записи присутствуют;
- настоящая inbound-обработка каждого сохранённого wire применяет его policy;
- двукратная доставка даёт один system marker на разговор;
- настоящий ACK первого получателя, выданный другим accepted контактом,
  не удаляет запись; правильный ACK удаляет только свою;
- оставшаяся обязанность переживает второе открытие контейнера и удаляется
  после ACK своего получателя.

Доставка wire и ACK в тесте управляется явно через production inbound port.
Это не физическая сеть, автоматический reconnect или relay qualification.
Native-кейс использует worker-backed HVS для всех трёх endpoint. Сервисы,
worker-контейнеры и синтетические файлы закрываются/удаляются в teardown.
