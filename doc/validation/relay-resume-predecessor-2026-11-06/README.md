# Возобновление сессии после смены сети: stale duplicate и общий ID

Продолжение [Poco Wi-Fi → cellular](../bootstrap-join-dial-isolation-2026-11-06/README.md).
В сохранённой relay-only серии найдено отклонение новых соединений телефона
как дубликатов. Исправлены два native-механизма: отсутствие адресной замены
собственного predecessor у no-row Leaf и повторное использование session ID
при ticket resumption. Время восстановления реального звонка **после этих
изменений ещё не измерено**; NETCALL-01 остаётся открытым.
Исправления закоммичены в Veil `ade3130a` поверх `c65a8d0c`.

## Что показали существующие журналы

При обрыве Wi-Fi телефон быстро завершил прежние подключения и снова прошёл
рукопожатие с несколькими реле. Но новые session.open заканчивались почти
сразу: lifetime 94–114 мс, затем ещё два подключения к одному реле прожили
по 1 мс. Последующее соединение сохранялось, и в том же интервале вернулся RX.

Журналы шести production-реле прочитаны **без изменения сервисов/бинарников**.
Сначала проверен journalctl; unit пишет в отдельный append-файл, поэтому
пустой journal не принят за отсутствие событий. Из ограниченного хвоста файла
выбраны только строки с локально установленным префиксом транспортного ID QA.
В окне relay-only handover три реле зарегистрировали `session.dedup` для этого
префикса: соответственно 1, 3 и 1 отказ. Два затем приняли соединение.

Это сопоставление журналов рукопожатия, **не** поклеточная атрибуция аудио.
Поле dedup содержит короткий префикс, а не полный криптографический witness;
часы серверов с телефоном здесь не откалиброваны. Всем 10,296 с перерыва не
приписывается одна причина. Исходная метрика validated cellular ~1,049 с и
fresh RX ~10,296 с взята из прежнего физического прогона, не из нового A/B.

## Исправление допуска

`inbound_may_replace_live_session(None)` намеренно запрещает незнакомому
повторному подключению вытеснять живую запись. Этот общий запрет сохранён.
Но телефон обычно отсутствует в dial-таблице Core, поэтому его корректное
возобновление также попадало в first-wins dedup до удаления старой записи.

Новый узкий путь требует одновременно:

- принимающая сторона Core, входящая сторона Leaf, нет совпавшего dial row;
- собственный проверенный ticket, привязанный к этому peer и predecessor;
- успешный MAC свежего ATTACH, доказывающий знание ключей, а не владение
  одним лишь непрозрачным ticket blob;
- текущий TX owner всё ещё совпадает с predecessor из ticket.

Проверка владельца и замена выполняются под одним write-lock. Старый ticket
не может заменить уже более нового owner. Configured/Bootstrap/Rendezvous,
прочие известные строки и обычный full handshake не получают нового права.
Действующие learned-peer правила сохранены. Allowlist, ban/cap/admission,
проверки приглашений, device binding и crypto не обходятся. Новые поля не
передаются по сети и не добавляют логируемых ключей или session IDs.

`authenticated_resume_parent` формируется только на server-side fast path
после проверки свежего ATTACH MAC. Full handshake, client-side resume и legacy
resume без такого доказательства возвращают None.

## Вторая проблема: ключи свежие, ID старый

Промежуточная правка уже принимала reconnect, но тест late teardown оставался
красным: `derive_resume_keys` сохранял исходный session_id. TX owner,
SessionRegistry и другие регистрации различают поколения по этому ID.
Поздний старый guard поэтому совпадал с новым owner и удалял его запись.
Одного нового локального счётчика circuits для этой проблемы недостаточно.

Ticket resumption теперь получает свежий публичный session_id через
domain-separated BLAKE3 от predecessor ID, обоих resume nonces и
канонически упорядоченных peer IDs. Стороны вычисляют одно значение; свежий
nonce любой стороны отделяет новую сессию от старой. Вывод directional
tx/rx keys не менялся, свежесть ключей и nonce/counter-защита сохранены.
Это идентификатор соединения, не новый способ получения cipher keys.

HandoffAttach переносит **тот же живой runner** и сохраняет ID/AEAD-состояние
как раньше. Новый ID относится к полноценному ticket resumption с новым
runner и свежими ключами. Для resumed aliases/handoff обе стороны должны
использовать новую derivation; совместимость со старыми версиями исключена
из условий владельцем. Обновление production-узлов в этом цикле не выполнялось.

## Проверки

Регрессия допуска использует настоящий NodeRuntime, transport registry,
TCP-loopback, полное OVL1-рукопожатие и ticket issuer. Старый server admission
удерживается после исчезновения клиента; ожидание idle/reaper в oracle не
используется. После нового допуска старый guard уничтожается, затем проверяется
сохранность новой TX-регистрации. Отдельные случаи защищают более нового
owner от старого ticket и сохраняют отказ plain duplicate.

Baseline: **1 assertion-red / 2 passed** — корректное возобновление отвергнуто
собственным stale predecessor. Промежуточный кандидат выявил второй
assertion-red — late guard удалил replacement с тем же session ID. Отдельная
crypto-регрессия исходной derivation: **1 assertion-red**, resumption сохранил
predecessor lifetime token. Ошибочные предварительные варианты fixture не
считаются подтверждениями: для resumption нужны разные ключи двух узлов.

Контроль cloned producers прошёл уже на baseline: retirement старого outbox
работает, дополнительный production-фикс этому механизму не добавлялся.
Проверены классификатор всех PeerSource/ролей, HMAC/legacy fallback,
согласование свежих ID и ключей между сторонами. Итоги полной серии указаны
в [агрегатах](summary.json): veil-crypto **172 passed**, veil-node-runtime
**805 passed / 11 ignored**, veil-session **687 passed / 8 ignored**. Итого
**1664 passed / 19 ignored**; ignored не считаются пройденными.
После усиления oracle до обязательного `Ok(Some(session))` повторно прошли
три admission-сценария. Три focused crypto-теста также прошли, включая
привязку нового ID к predecessor и обоим nonces. Production-исходники после
полной серии не менялись; финальные source hashes сохранены локально.

Rust использовал существующий target только этого checkout на внешней ФС;
mount/device/free-space watchdog работал до и во время сборок. Сырые журналы,
адреса, ключи и идентификаторы остаются в private cache. Публичный JSON содержит
только агрегаты. Тестовые runtime остановлены; source/format/diff checks
выполнены. Новые телефонные/desktop-приложения в этом цикле не запускались.
После указания владельца дальнейший физический стенд — телефон и MacBook;
Windows не используется. Основной xVeil/контейнер/сетевые настройки телефона,
сиды, APK и engine pins не менялись. Коммиты локальные, без push и релиза.

## Остаток

Проверить изменённые обе стороны на изолированном стенде телефон ↔ MacBook
с настоящим Wi-Fi → cellular и обратным переходом. Допуск ещё не доказывает
доставку по выбранному media route. Plain reconnect без пригодного ticket,
повторный обрыв до получения нового ticket, QUIC/full-handshake пути и пауза
при проверке replacement channel требуют отдельной квалификации.
Прежние 19–20 с auto и 10,3 с relay-only не переобъявляются устранёнными.
