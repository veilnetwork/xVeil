# Атомарное удаление заменённых сегментов группы

Проверка 2026-10-31, без push и релиза.

При замене хвостового сегмента прежний путь отдельно коммитил новый сегмент,
замену заголовка (append, затем publication) и удаление старого сегмента.
Теперь `Storage.storeFile(..., retireHints: ...)` может включить полное удаление
небольшого старого файла в финальный metadata commit заголовка.

Новые сегменты по-прежнему durable до заголовка. Старый заголовок и нужные ему
сегменты сохраняются при отказе publication; после успешного commit заголовок
и удаления меняются вместе. Неподтверждённые записи не ACK-аются раньше.
`gd` остаётся устойчивым crash/retry descriptor. GroupService всегда выполняет
идемпотентный `deleteStoredFile` после публикации, даже при принятой подсказке.
Реальные отказы этой очистки остаются pending и повторяются после restart.

## Ограничения операции

Не более 64 hints, без повторов; удаляется только целый файл, помещающийся
в оставшийся бюджет финальной публикации (64 ops, включая metadata и GC).
Крупные, streamed и повреждённые кандидаты остаются прежнему пути очистки.
HVS проверяет само присутствие on-disk metadata, а не успешность её decode:
такие файлы не объединяются, чтобы не обойти key scrub и ciphertext cleanup.
Очередь HVS фиксирует список до первого await; публикация и cleanup не могут
пересечься с другим file writer и расходованием общего log cursor.

AppendLog и DeleteLog одной namespace не объединяются: новые chunks
сначала записываются отдельным commit, затем публикуется metadata с удалениями.
Уже идентичный файл не переписывается ради hints; обязательный fallback
заканчивает очистку. Самоудаление target запрещено до записи.
Ошибка чтения необязательного кандидата не блокирует публикацию, но ошибка
самого commit распространяется; повтор без удалений не выдаётся за успех.

## Проверки корректности

Красный тест на AsyncFileStore прежнего HEAD с объявленным, но игнорируемым
optional argument: старый хвост остаётся после replacement. После исправления
он удалён в publication; отдельный cleanup не имеет операций.

Проверены отказ финального commit, повтор, бюджет ровно 64 и превышение на
одну операцию (без частичного удаления файла), dedup, 64-hint limit,
streamed/нечитаемая/повреждённая/огромная legacy metadata, идемпотентный store,
самоудаление, сохранность соседнего файла и hint-list mutation после вызова.
Потеря ответа уже успешного commit отдельно оставляет целое новое состояние;
повтор через новый AsyncFileStore и explicit cleanup идемпотентны.
Gate/failure overrides существующих storage fixtures не обходятся: optional
argument явно прокинут через них. Fixture с failed deletes намеренно отклоняет
эти optional hints и сохраняет прежние проверки durable retry.

668 тестов приложения прошли в итоговом общем запуске на финальных исходниках,
0 skipped. В раннем запуске 3 sovereign/XVRC были skipped; они отдельно прошли
с native SDK, а затем вошли и в итоговые 668 без пропусков.
3 native file-store теста прошли: настоящий контейнер отвергает metadata commit
с уже включёнными удалениями, после reopen старые файлы читаются; повтор и
следующее reopen показывают новый заголовок, удалённый хвост и целый новый
сегмент. Это JIT/host qualification, не Android/Windows или AOT.

Тест отказа выявил ограничение прежнего chunk accounting: после неудавшегося
publication повтор использует orphan log id, а GC считает обе append-попытки.
Для одного orphan проверено консервативное завышение на 1 (не недосчёт).
Это не объявляется точным счётчиком после отказов и не скрывается изменением
порогов. Без отказа объединённые удаления учтены точно.
Также прежний explicit cleanup не интерпретирует повреждённый on-disk JSON;
подсказка не превращает failed decode в отсутствие tier key.

## Native сравнение

A — AsyncFileStore исходного `3aad13c5` с объявленным, но игнорируемым
`retireHints`; B — объединение удалений. Остальные исходники одинаковы,
в том числе HVS prefilter и GroupService hint/fallback. Это изоляция механизма,
**не A/B всего API patch против старого frontend**: добавленные HVS metadata
reads присутствуют в обеих фазах. Native SDK `c46d94db` и hidden-volume
одинаковы во всех шести запусках; после codesign проверены SHA и происхождение.
Production source/fixture SHA фиксированы; после временных замен восстановлен
ровно кандидат. Динамические библиотеки не пересобирались.

12 разных cached production-PoW личностей; свежие encrypted containers,
TCP loopback, все обслуживают DHT, настоящий ratchet и host authorization.
Один JIT host/Mac/shared disk; legacy group без epoch encryption, roster
подготовлен отдельно. Это не multi-device, не публичные onion-реле и не
контроль одного дерева доставки/одинакового планирования очередей.

коммитов не создают и по-прежнему не стирают устойчивый `gd`.

Медианы A/B по четырём сообщениям: **4282/4301, 2454/2373, 2005/2115,

Снижение числа commit доказано; равного ему ускорения wall-clock не обещаем.
Первое сообщение ещё занимает около 4,3 с, следующие — около 2,1–2,7 с.

Точная трасса каждого logical group hop связывает enqueue/send/callback и
вход обработчика с последующей пересылкой/видимостью. Сумма интервалов
совпадает с полной задержкой до микросекунд; это не per-hop измерение onion.
В холодной критической цепи handoff→callback: A **1,423–1,682 с**, B
**2,005–2,263 с**; ожидание очереди/preflight: A **0,421–0,574 с**, B
**0,124–0,172 с**; group handling: A **1,419–1,506 с**, B **1,050–1,374 с**.
Это не независимые цены и не сетевой ping: сюда входят native resolve/seal,
checkpoint, общий worker и планировщик; перенос ожидания между стадиями
нельзя считать доказательством отдельного ускорения/замедления транспорта.
На следующих сообщениях в B queue/preflight суммарно **0,362–0,926 с**,
group handling **0,774–1,379 с** по критической цепи. Эти ожидания и холодная
подготовка остаются следующим направлением разбора.

В A/B-серии все 24 сообщения дошли всем 12 по одному разу: проверены по одной строке
истории на устройстве и все 44 входящих visible events каждого запуска,
включая поздние до teardown. Timing dropped = 0. У всех шести stand:
процессы host вышли, 12 listeners переоткрылись, временные контейнеры удалены,
cleanup errors = 0. Телефон и production-реле не менялись.

После A/B дополнительно ужесточено планирование повреждённых legacy runs:

которое при MAX_I64 переполняется. Красный тест начального planner подтвердил

проверен после защиты, без попытки заведомо огромного выделения на старом коде.
