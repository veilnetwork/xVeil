# Сохранение проверенного дескриптора для выдачи файла — 2026-10-30

При разборе [начального ожидания большой загрузки](../rack-delivery-rtt-2026-10-30/README.md)
подтверждены два отдельных дефекта durable-source path. Базовая ветка xVeil —
`384f69ff`, SDK `c96bd930` не менялась. Это не объявление об устранении всех
причин файловых задержек, старого «33%» или всех гонок изменения источника.

## Воспроизведение и исправление

| Случай | Прежнее поведение | Проверка исправления |
| --- | --- | --- |
| Закрытие проверенного handle и повторный open pathname | `_openVerifiedServedSource` хешировал временный handle, закрывал его, затем открывал имя ещё раз. Замена файла при первом close приводила к выдаче байтов замены под старым content ID. | Тест заменяет файл именно в close, без гонки по времени, и проверяет байты на выходе отправителя. До исправления в сеть ушли байты замены. Теперь оригинал получен целиком, открыт один handle, его владение сохранено до конца serving. |
| Изменение имени, замеченное во время проверки | `_verifyServedSource` видел разные before/after stamps, но возвращал `ok`, запрещая только кэширование. Group API возвращал путь, который уже называл другой файл. | Во время чтения старого snapshot имя заменяется файлом с отличающимся stamp. До исправления API возвращал путь; теперь возвращает null. |

Оба окончательных теста упали на исходных production-файлах `384f69ff`, затем
прошли с исправлением. Snapshot во втором случае позволяет проверять смену
имени и на файловых системах, запрещающих rename поверх открытого OS handle;
первая регрессия действительно использует файловый дескриптор.

Теперь serve сначала открывает свой handle, проверяет его и передаёт дальше
тот же объект. Обнаруженная смена stamp вокруг open/проверки отклоняет источник;
непереданный handle закрывается в finally. После долгой проверки повторно
проверяются действующая авторизация и состояние сервиса.

Стабильный verdict cache сохранён. Незавершённая проверка разделяется только
для одного pathname и stamp, а не для любого источника с тем же CID. Отдельный
положительный тест заменяет файл идентичными байтами, пока предыдущая проверка
ещё ждёт: новое поколение получает собственный успешный результат, старое — отказ. Источник
без доступного stamp проверяется самостоятельно. Cleanup удаляет только свою
запись Future. Полный проход и сравнение content ID сохранены: новая оптимизация
не разрешает передавать непроверенные куски и не меняет wire, ACK, ratchet,
mailbox или приоритет реле.

## Что известно о начальном ожидании

В предыдущей физической серии Android → Mac 64 МиБ журнал приложения содержит
запись запроса на 891 мс после старта download API и окончание повторного
хеширования источника на Android на 6219 мс. Mac сообщил ожидание манифеста
на 5895 мс. В обратном направлении окончание проверки источника — на 1760 мс.
Относительные события: [initial-timeline.json](initial-timeline.json).

Начало самого хеширования не измерено, поэтому нельзя назвать весь промежуток
между запросом и ответом временем SHA-256/диска. В обеих сборках был включён
native SHA-256; это не доказанный fallback на Dart hash. Полная повторная
проверка в этом исправлении остаётся, и сокращение прежних 5,5 с не заявляется.

## Проверки и ограничения

Прошёл **131 тест** из девяти связанных файлов: source verification, stream
transfer, content service, gone, manifest, pinned send source, descriptor send,
reverse pull и file-range source. Окончательный прогон 11
source-verification тестов прошёл: десять повторных и одна дополнительная
проверка нового поколения файла. Счётчики не складываются. Analyze двух production-файлов и изменённого теста — без замечаний.
Новые тесты и числовые результаты: [summary.json](summary.json).

Физические 14 файлов из прошлого цикла предшествуют новой Dart-правке и не
засчитываются её проверкой на Android/Windows. Здесь использованы настоящие
локальные файлы и in-memory transport, TMPDIR `/private/tmp/`. Сборки приложений,
звонки и стендовые GUI не запускались. Native SDK и серверы не менялись.

Сохраняется ограничение Dart filesystem API: нет атомарного `openat`/`fstat`
связывания имени и дескриптора. Этот фикс не обещает защиты от всех последующих
in-place writes или изменений, неразличимых доступным stamp. Path-returning
group API также не превращается в API владения дескриптором. Все причины «33%»,
Windows 10 и остальные открытые случаи не объявляются закрытыми.

Raw traces и тестовые логи сохранены приватно. В отчёт вынесены относительные
события, общие имена тестов и хеши исходников, без реальных путей, peer/content IDs
и абсолютных времён. Коммит локальный, без подписи, push/релиза нет.
