# Poco ↔ Mac: Delivery relay после смены сети

**NETCALL-01 воспроизведён и остаётся открытым.** Контрольный звонок с
двусторонним аудио прошёл. Первый переход Wi-Fi → cellular → Wi-Fi внутри
разговора сохранил медиадвижки, но следующие сценарии выявили односторонний
приём и автоматическое завершение по liveness timeout.

Это продолжение [проверки SDK resume](../poco-mac-resume-2026-11-06/README.md)
и [исправления private media lifetime](../private-media-tx-lifetime-2026-11-06/README.md).
**Последнее исправление здесь физически не квалифицировано:** actual route
этого стенда — non-onion Delivery relay, а не onion `PinnedRoute`.

## Стенд

- Poco / Android 16, мобильная связь и Wi-Fi; MacBook. Windows отключена
  владельцем и не использовалась. Независимые QA-профили из предыдущего
  прогона, настоящие скрытые контейнеры, ранее подтверждённый контакт.
- Клиенты используют release native FFI из чистого Veil `81436bd1`.
  Android profile/AOT пересобран из `5dca2c7f` для отдельного диагностического
  порта. Tracked Dart-файлы сверены с исходником; QA отличия — application ID,
  label, defines и собственные seed/PSK assets. Native SDK, media и HVS
  проверены по SHA после упаковки; подпись совпадает с исходным QA APK.
- Mac profile/AOT с теми же Dart/media/HVS, что в предыдущем стенде, и новой
  FFI. Пользователь разрешил микрофон macOS; фактические TX и свежий RX
  подтверждены **на обоих** устройствах до переключения сети. Слышимость
  человеком не проверялась.
- Один отдельный QA-Core через obfs4/TCP, P2P заранее запрещён с обеих сторон.
  Core — сохранённый `ade3130a`: diff runtime/session/crypto/CLI до `81436bd1`
  пуст, последний коммит менял только клиентский private media path.
  Собственные unit, порты, конфиг, PSK, state, ограничение работы 30 минут.
  Production PID, executable/config SHA и NRestarts сверены до/после.

## Результаты

| Сценарий | Фактический результат |
|---|---|
| Контроль телефон → Mac на Wi-Fi | Пять последовательных свежих срезов RX на обоих концах; TX обоих растёт |
| Телефон → Mac: Wi-Fi → cellular в активном звонке | ОС validated cellular через 1,523 с; двусторонний RX продолжился, media epoch остался 3 на обоих концах |
| Возврат того же звонка на Wi-Fi | ОС validated Wi-Fi через 3,219 с; 30-с наблюдение завершено, epoch также 3 |
| Новый телефон → Mac сразу после Wi-Fi off | Входящий на Mac через 1,173 с, но за 50 с не получен двусторонний baseline: Mac принял 5 пакетов в первом media epoch, затем RX остановился; после двух rebuild epochs RX оставался 0. Телефон продолжал принимать Mac |
| Mac → телефон: Wi-Fi → cellular в активном звонке | До переключения двусторонний baseline прошёл; validated cellular через 1,254 с. Затем приём пропал с обоих концов; потеря call state зафиксирована через 22,975 с после Wi-Fi off |

В последнем случае оба devlog явно содержат
`reason=timeout origin=livenessTimeout`, около 22 с отсутствия активности
собеседника. Это произошло **до** cleanup/hangup стенда. В предыдущих звонках
завершение было явной командой diagnostic API. Второй новый звонок обратной
серии не выполнялся после первого сбоя; он не считается пройденным.

Первый длинный разговор не объявляется идеальным по качеству звука:
максимальный наблюдаемый native RX age был 1301/1417 мс, отдельные срезы
превышали критерий fresh в 1000 мс. Это метрики прихода пакетов, не измерение
акустической задержки или слышимой тишины. В первом длинном разговоре не
наблюдались прежние многосекундные rebuild-паузы, однако вся серия не прошла.
Нет A/B; сравнение с прежним односторонним Mac-контролем причинно некорректно.

## Локализация

В Dart `_openCallMediaChannel` выбирает `relay: true`, SDK вызывает
`veil_media_open_relay_channel`, затем IPC с
`RELAY_REALTIME | RELAY_MEDIA_SEALED`. В endpoint trace действительно есть
`stage=relay_send`. Это путь Delivery, а не private onion circuits.
Исправление `PinnedRoute` подтверждено отдельным red/green-тестом, но не
может объявляться решением этих физических сбоев.

В обратном прогоне включалась endpoint rt-trace. У телефона сохранены
23 отсчёта `ipc.rt_trace.relay_admission`; все с `refused=0` и
`datagram_transport=true`. Это локальный допуск в нейтральный ordered child,
**не доказательство доставки на Core или конечный клиент**. Обнаруженные
`route.discovery.miss` и status 2 у отправки управляющих сообщений также не
атрибутируют каждый потерянный медиапакет.

Native `NetworkChanged(kind=Cellular)` получен в окне переключения;
объяснение «приложение вообще не уведомило SDK» для обратного прогона
исключено. Строка force-unregister с положительным счётчиком для этого
уведомления не найдена. По коду она появляется только при снятии хотя бы
одной TX-записи; отсутствие строки — кандидат уже исчезнувшей регистрации,
а не самостоятельное доказательство без учёта возможных потерь логирования.
После возврата Wi-Fi unregister снял одну запись; на собственных часах
телефона resume завершился и session.open появился через 0,238 с после
этого уведомления. Это не доказывает скорость восстановления именно на
cellular: возврат Wi-Fi был уже cleanup после отбоя.

Приблизительное сопоставление с Core даёт первое зарегистрированное в
сохранённом журнале новое parent session.open телефона около +23,45 с от
Wi-Fi off — в окне завершения звонка (+22,975 с).
Погрешность только SSH clock interval здесь ±0,91 с плюс дискретность
endpoint-срезов; порядок этих двух близких событий не установлен.
Нет поклеточной атрибуции. Следующий участок — восстановление родительской
сессии/ordered child и Delivery routing после native network notification,
включая случай уже отсутствующей TX-записи. Таймаут звонка не увеличивался.
Это новый воспроизведённый handover-timeout, а не установленная причина
исторической жалобы об обрыве примерно через 25 с.

## Проверка предусловий стенда

Первоначальный QA hook-port был занят Dart VM другого UID; собственный VM
QA-приложения слушал другой порт. Чужое приложение не останавливалось.
Порт QA перенесён в отдельную AOT-сборку, после чего проверены авторизация,
testnet, ready и realStack обоих клиентов. Ошибка порта не считается сетевым
прогоном. Ошибочный `VEIL_SKIP_CARGO=1` запустил лишние ABI builds; они
остановлены, финальный frontend собран с требуемым `true`. Эти native outputs
не устанавливались: в APK вставлены отдельно проверенные кандидаты.

Отдельный Core был active в read-only captures **после обоих сбоев**.
Позже сработал его RuntimeMaxSec=30min; Result=timeout, peak memory около
9,7 МБ. Автоостановка не является причиной снятых сбоев. Перед удалением
failed-state сброшен, затем удалены только принадлежащие QA файлы/сервис.

## Завершение

Прежний QA APK восстановлен по SHA. SHA основного APK и старого QA-контейнера
не изменились. Восстановлены Wi-Fi/mobile/awake settings, проверен validated
Wi-Fi. Свои приложения закрыты, ADB forward удалён, listener ports свободны.
TIME_WAIT у завершённых HTTP-соединений не считается живым listener:
доступность порта проверена с SO_REUSEADDR и отсутствием процессов.

QA-Core/config/state/binary/unit/upload staging удалены; production
PID/бинарник/конфиг/NRestarts прежние. Собственные frontend staging,
лишний native target этого frontend и промежуточные unsigned APK удалены.
Подписанные кандидаты, SHA/provenance и сырые журналы остались приватными.
В этом отчёте нет node/device/call IDs, адресов, ключей и сырых логов.
Новых production-правок, push или релиза в этом физическом цикле нет.
