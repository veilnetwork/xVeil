# Повторы recursive DHT и бюджет новой работы

Подтверждён и устранён отдельный механизм отказов: уже обработанная копия
recursive query списывала per-peer token и часовой service budget, затем
отбрасывалась dedup. Замыкающиеся ветви поиска могли лишить следующий новый
запрос допуска, хотя повтор не выполнял полезной работы. Это **не полное
устранение долгой доставки**: таймауты и несколько секунд распространения
остаются на финальной библиотеке.

## Изменение

Перед admission выполняется только O(1) read-only peek фиксированного ID:
если запись ещё жива, кадр сразу отбрасывается без ответа и пересылки.
Проверка не добавляет записи, не чистит весь cache и не продлевает TTL.
Дедуп после admission сохранён для одновременных первых поступлений.

Неизвестные ID, включая некорректные кадры с неизвестным ID, по-прежнему
проходят оба бюджета **до decode**. Исчерпавший квоту поток уникальных ID
не может наполнить seen-cache. Численные лимиты **5/s, burst 20**, часовой
бюджет, wire, подписи, ratchet и авторизация не менялись. Семантика списания
уточнена: уже известный и немедленно отброшенный повтор больше не считается
новой работой. Приоритетов приложений, медиа или отдельных соседей нет.

Для peek ExpiryCache хранит deadline вместе с ключом в HashMap; heap,
ограничение числа записей, lazy expiry и oldest-entry eviction сохранены.
Это дополнительный timestamp на запись, а не отдельный неограниченный cache.
Дубликаты с уже известным ID не декодируются, в том числе если остальное
тело отличается или некорректно; никаких полномочий или ACK это не даёт.

Операторский rt_trace содержит только разреженный power-of-two счётчик
ранних отбрасываний и приватный walk fingerprint. Счётчик process-wide,
последний sample — нижняя граница, не полное число повторов. В обычный
анонимный отчёт эти поля и сырые строки не экспортируются; тест allowlist
дополнен именно новым диагностическим случаем.

## Тесты

Реальный dispatcher с двумя токенами: первый запрос, 64 его копии, ещё два
новых запроса. На исходном коде второй уникальный запрос не достигал dedup;
на кандидате он допущен, третий по-прежнему ограничен. Контроль некорректных
и уникальных кадров проверяет отказ до decode и отсутствие новых seen-entry.
Первый запуск теста не скомпилировался из-за неверной мутации Arc в fixture;
он не засчитан как воспроизведение. Исправленный control дал **1 fail / 1 pass**
по нужному условию. Отдельный тест expiry без sleep проверяет peek без
вставки/refresh/prune, старую истёкшую запись рядом с живой и eviction.

Финально: **289 dispatcher + 196 IPC + 778 runtime + 671 session = 1934 passed**,
**24 ignored отдельно**. Диагностика: **13 passed**. Release построен с
node-embedded, production-seeds, packet-tunnel, без test-low-difficulty.
Mount-watchdog внешнего target не обнаружил потери ФС. Исходники сверены с
манифестом; фактическая библиотека после codesign отличается от контроля,
sentinel нового unit-теста в release отсутствует.

## Native A/B: три Core и девять non-DHT leaf

Контроль — SDK `516ac549`; кандидат `081bb6d1` содержит только этот dispatcher-фикс.
Чередование A1/B1/A2/B2/A3/B3, одинаковый fixture и набор 12 производственных
PoW-личностей; контейнеры и instance keys свежие в каждом запуске.
Четыре сообщения от разных отправителей 0/6/5/11. Время — видимость всем 12,
таймаут — отдельная app-triggered replica branch, **не потеря сообщения**.

| Фаза | Сообщение 1, мс | 2, мс | 3, мс | 4, мс | Replica timeout |
|---|---:|---:|---:|---:|---:|
| A1 | 4454 | 2575 | 2527 | 3052 | 30 |
| B1 | 4471 | 2346 | 2998 | 3468 | 29 |
| A2 | 7470 | 3096 | 2553 | 3247 | 42 |
| B2 | 4555 | 2271 | 2607 | 3051 | 25 |
| A3 | 7362 | 2772 | 3146 | 3239 | 27 |
| B3 | 4466 | 2240 | 3066 | 2892 | 38 |

Медианы: **7362 → 4471**, **2772 → 2271**, **2553 → 2998**,
**3239 → 3051 мс**. Первая доставка в этой небольшой серии ровнее/быстрее,
но B1 близок к A1, последующие сообщения не имеют общего выигрыша.
Медиана количества timeout **30 → 29**: общая проблема молчащих ветвей
не устранена. Это один Mac/JIT host, native TCP full mesh, legacy-группа
без epoch encryption, roster передан вне сети; genuine MessagingService,
GroupService, контейнеры, peer authorization и native crypto/ratchet.
Порядок реле и свежие instance keys не фиксировались побитово. Эти числа
не являются гарантией ускорения в публичной сети или на телефоне.

Все шесть запусков: 4/4 сообщения у всех 12 **ровно один раз**, все девять
leaf имеют подтверждённые PublishedRendezvous inbound circuit. В B2 один
повтор дошёл до второго dedup после admission: этот guard действительно
нужен и не заменён ранним peek. В B1/B2/B3 разреженный ранний счётчик достиг
как минимум 128 повторов; это не сравнивается напрямую с post-admission
duplicate count контроля, где quota уже скрывала часть повторов.

Отдельный positive состава all-DHT на финальной библиотеке:
**5131 / 2838 / 3661 / 2688 мс**, все сообщения у всех 12 без дублей.
Это функциональная квалификация другого состава, не дополнительная A/B-пара.
Во всех семи запусках host вышел, все 12 узлов остановлены, listeners закрыты.
Телефон и production-реле не менялись. Без push и релиза.

## Остаток и следующий разбор

В all-DHT первый native callback приходит через **125–512 мс**, но видимость
всем — через **2,69–5,13 с**. Наблюдаемые интервалы receiveGroupFrame
(от входа до завершения, пары по sample/member/peer) имеют медианы
**378–624 мс**, максимумы **1179–2063 мс**. Durable enqueue пересылок:
медианы **46–88 мс**, максимумы **157–268 мс**. Эти интервалы могут
перекрываться и включать дубли; их нельзя сложить в полное время доставки
или объявить каждый из них критическим путём.

Следующий шаг — разложить локальный групповой приём: загрузку/проверку
состояния, durable apply и постановку пересылок, с привязкой к первой
видимости, отдельно от новых/повторных копий. В частичной DHT-топологии
также остаются молчащие ветви и конкуренция уникальных запросов. Прошлые
неповторяющиеся жалобы остаются отложенными по решению владельца;
multi-device матрица этим раундом не проверялась.
