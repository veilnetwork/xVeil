# Multi-device: конфликт и сходимость после partition

Последующее уточнение скорости: [operator-unban wake](../operator-unban-wake-2026-11-06/README.md)
объяснил первые 25–26 с automatic healing отсутствием уведомления после
явного снятия bans. После исправления этот же сценарий сходится за
13,1–13,4 с. Исторические времена ниже сохранены; они не измеряют обычную
скорость мессенджера или мобильного reconnect.

**Текущая сборка прошла проверку четырёх native-процессов двух личностей:**
A/B — X, C/D — Y. После разделения обе части продолжают обмениваться данными;
после объединения сообщения, конфликт edit/delete, реакции и read position
сходятся. Состояние B сохраняется после его перезапуска при остановленных
A/C/D. Это частичная квалификация матрицы, а не закрытие всех её сценариев.

Агрегаты: [summary.json](summary.json). Фазы: [cases.csv](cases.csv).

## Стенд и проверяемое состояние

Mac/JIT, реальные контейнеры и OVL1-узлы, SDK/CLI `bbeaf3a9`,
обычная HVS `eceb9158`, frontend после `0c8ce867`. Четыре устройства и три
loopback Core. Публичные seeds/meeting points выключены. Mailbox собственных
устройств не добавлялся.

До разделения на всех четырёх устройствах имеются два контрольных сообщения
и реакция X. Native admin bans удаляют все поперечные сессии семи узлов.
Тест читает настоящие session tables и требует нулевых межчастных соединений.
Половины: A/C с одним Core; B/D с двумя Core. Процессы продолжают работать.

Одновременно каждый из A/B/C/D отправляет четыре сообщения; A редактирует
один исходный текст, B удаляет его для всех; A меняет реакцию, B удаляет свою
конкурирующую реакцию, D добавляет реакцию Y. До healing отдельно подтверждены
связность внутри половин и отсутствие сообщений другой половины.
В A/C видна правка, в B/D — удаление. Read position обновляется на всех.

После healing проверяются:

- 17 ожидаемых строк на каждом устройстве: 16 новых и reaction target;
  удалённый message ID отсутствует везде. Каждый ожидаемый body ровно один,
  неизвестные лишние строки не могут заменить недостающие.
- Одинаковая отображаемая история внутри X и внутри Y, включая IDs,
  direction/body/edited и порядок. Это не отдельная сверка source positions
  или delivered каждого сообщения.
- Одинаковые реакции у всех; Y имеет 💡, конкурентный исход X допускает
  отсутствие реакции либо 🚀. Точное одинаковое значение X в публичный
  отчёт не восстанавливается из одного только PASS-маркера.
- Read markers внутри каждой личности одинаковы и не ниже максимума
  двух исходных marks. Критерий устойчив 10 секунд наблюдения.
- До завершения live merge исходные post-link process PID lists неизменны.
  После этого A/C/D остановлены, B перезапущен: все 17 строк, удаление,
  реакции и read position сохранены. Core продолжают работать — это не
  перезапуск без какого-либо сетевого подключения.

## Исправлен недостаток тестового oracle

Старый normalizer учитывал только локальный device alias. Он не запрещал
лишнего одинакового автора на всех replicas: одинаковая ошибочная карта
могла пройти сравнение, если значения X/Y при этом оставались допустимыми.
Также не все известные sibling aliases участвовали в проверке дублей личности.

Новый stand-only normalizer знает A/B/C/D → X/Y, отказывает неизвестному
актору и двум raw slots одной личности; дубль не схлопывается в один.
Production appliers и формат реакций не менялись. Пять unit-проверок прошли.
Удаление unknown-actor guard даёт 1 assertion-red на четырёх одинаковых,
но ошибочных replica maps; fixture затем восстановлена побайтно.
Analyzer трёх изменённых тестовых файлов — замечаний нет.

Начальный native PASS с прежним oracle сохранён как более узкое свидетельство,
а не как проверка новых требований. Затем сценарий повторён с усиленным oracle.

## Автоматическое восстановление проверено отдельно

Исторический сценарий после unban повторял `/add_peer` для уже известных
siblings. Он восстанавливал native связность, а не импортировал историю,
но не доказывал healing без дополнительного join.

Добавлен test-only режим `XVEIL_E2E_PARTITION_AUTOMATIC_HEAL=1`. В нём после
снятия bans нет повторного join, restart или изменения journal: reconnect,
discovery и anti-entropy должны сработать сами. Этот режим также прошёл
усиленный oracle, устойчивость и последующий offline-sources restart B.

| Режим | Первое наблюдение сходимости | Устойчивое окно | Всего recovery |
|---|---:|---:|---:|
| Прежний oracle, повторный join | 16,788 с | 10,418 с | 27,207 с |
| Усиленный oracle, повторный join | 15,851 с | 10,227 с | 26,079 с |
| Усиленный oracle, unban без join | **44,772 с** | 10,226 с | 54,999 с |

Это отдельные свежие серии, не causal A/B эффекта join. Таймер начинается
перед последовательными admin unban-командами; он не равен точному моменту
восстановления пригодного native пути.

**Медленный автоматический recovery остаётся открытым.** В диагностическом
срезе около 15 с ожидания после unban каждой стороне ещё не хватало восьми
новых сообщений. Около 30 с A/D уже имели все 17 строк, B всё ещё не хватало
восьми, C — четырёх. Около 45 с все четыре состояния совпали. Это шкала
waitUntil после admin-команд, отдельно от общего recovery timer выше.
Это последовательные API-чтения,
не атомарный одновременный snapshot. Задержка действительно включает
недоставленные строки, а не только десятисекундный stability detector.
Причина ожиданий — очереди/повторы/восстановление маршрутов — ещё не атрибутирована.

## Границы и cleanup

Проверены выбранные части сценариев 20/31/32 и двух multi-device личностей.
Не проверены этим запуском часы/сутки offline, clock skew, revoke,
другие виды конфликтов, файлы, звонки или Android/AOT.

Все три driver и cleanup завершились с 0. Собственные PID/ports:
27/35, 26/42, 28/32; процессов/listeners не осталось, runtime удалены.
1493/1495/1495 выбранных source inputs и native/HVS bytes сохранялись
во время своих серий. Raw logs, адреса, keys и подробные replica maps
остаются в приватном кэше. Телефон/Windows/production-сиды не менялись.
Push и релиз не выполнялись.
