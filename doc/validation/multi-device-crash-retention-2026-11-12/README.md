# Сохранность истории после аварийного завершения устройства

На текущем коде B сохранил проверенные сообщения после SIGKILL во время
первой догрузки. При выключенных A и C свежий B прочитал все 253 уже принятые
записи. После возврата только A история сошлась до 2000 сообщений; следующий
запуск B без обоих источников сохранил все 2000.

Это частичное покрытие переноса истории и crash-сценариев пунктов 21/63
multi-device матрицы. Точные границы receive/decrypt/DB/ACK из пункта 62
этот запуск не фиксирует. Результаты: [summary.json](summary.json),
этапы: [cases.csv](cases.csv).

## Стенд

macOS arm64, три отдельных native-процесса клиентов: A/B одной личности X,
C другой личности Y; три loopback Core. Использованы настоящие контейнеры,
production messaging/device-sync providers и обычные worker isolates.
Fixture задаёт начальное разблокированное состояние, не подменяет доставку
или применение истории.

Приложение `74277174`, SDK/CLI 0.11.50 из `e963fbdb`, hidden-volume
`293792d`. SDK dylib взят из проверенной локальной сборки 0.13.98; CLI сверен
с текущим digest опубликованного артефакта. Hidden-volume — отдельная host
debug-сборка с prepared API. Исходники и выбранные native bytes не менялись
во время прогона. Это JIT-проверка корректности, не замер скорости релиза.

Использован обычный опубликованный CLI: конфигурации острова явно задают
`builtin_seed_policy = "never"` и `meeting_points = "off"`. Fixture проверяет
эти значения в файлах. Клиенты получают только loopback peers, с выключенными
bundled seeds и пустым списком meeting points. Политика own-device mailbox
не менялась.

## Проверенные этапы

1. A и C установили контакт, A отправил C 2000 разных текстовых сообщений.
   До привязки B A получил durable delivery confirmations для всех строк.
2. B привязан к X штатной церемонией. При переносе истории observer увидел
   253 строки и сохранил witness их IDs, тел, delivered и canonical positions.
   Процесс B завершён настоящим SIGKILL; exit code проверен как `-9`.
3. A и C остановлены до запуска нового B. Cold-read witness выполняется
   до старта его сетевого узла: все 253 ожидаемые строки присутствуют ровно
   один раз, тела, delivered и canonical positions сохранены. После запуска
   узла при выключенных источниках B по-прежнему имеет 253 из 2000 строк.
4. Возвращён только A. B получил все 2000 сообщений, их IDs, порядок,
   canonical positions и тела совпали с источником; все статусы — delivered.
   Отправок завершённой истории повторно не зарегистрировано.
5. A снова остановлен, C не возвращался. B перезапущен ещё раз: до сети
   прочитаны все 2000 ожидаемых строк, тел, delivered и canonical positions;
   пропущенных, лишних, повторяющихся или некорректных строк нет.

Сравнение не ограничено tail API или равенством двух пустых списков:
исходный набор содержит ровно 2000 ожидаемых IDs, частичный witness — 253,
и оба количества проверены отдельно от равенства replicas.

## Границы и очистка

Один полный e2e-тест прошёл, пропусков нет. Это crash во время переноса
истории с недоступными источниками при cold-open, а не часы offline,
принудительная потеря питания, file/link/revoke crash, Android или Windows.
Полная матрица не объявляется закрытой; исторический CSV не переписан.

Все 10 собственных процессов клиентов/Core завершены. Проверены 10 выбранных
TCP listen ports, listeners не осталось; временный runtime с контейнерами
удалён. Подробные logs и witnesses остаются в приватном кэше. Телефон,
Windows и production-реле не использовались. Нового push или релиза нет.
