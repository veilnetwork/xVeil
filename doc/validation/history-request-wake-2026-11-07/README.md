# Обратный history-запрос ускоряет текущий повтор

База — `926d91f2`. При разборе [предыдущей native-серии](../device-protocol-view-2026-11-07/README.md)
найден отдельный крупный интервал до страниц. После открытия источника A
первый `list` пришёл на его transport через 601 мс, повтор того же запроса —
через 16 604 мс; ответ наблюдался только после повтора. При этом A уже через
1032 мс сам запрашивал историю у B, затем получал страницы. Второй, отдельно
профилируемый прогон дал тот же порядок: 582 → 16 568 мс, обратный запрос
через 1624 мс. Почему первый запрос остался без ответа, не установлено.

Прежний код ускорял retry после presence, но первая ранняя presence занимала
30-секундный wake throttle. Обратный authenticated history request не давал
нового сигнала. На виртуальных часах воспроизведено: запросы t=0,2,6;
presence t=0; валидный обслуженный обратный запрос t=9; следующий собственный
запрос по-прежнему ждал t=14.

## Изменение и границы

Перед первой частью **уже подготовленного валидного ответа**, после fresh
проверки устройства и текущего binding, существующий незавершённый pull
получает отдельный сигнал готовности. Его retry использует прежние ID,
query/cursor и attempt budget. Новый pull при отсутствии pending не создаётся;
обработка страницы не прерывается. Минимальный интервал отправок — прежние
две секунды, сигналы от обслуженных запросов ограничены разом в 30 секунд
на pull независимо от presence. Ранний уже назначенный timer не откладывается.

Повтор проходит прежний fresh `_allowed`, request-send lease и лимит 32.
Malformed/claimed/отозванные запросы не обходят admission. Cursor checkpoint,
durable commit, подписи/ratchet, visibility/expiry, служебная модель и отсутствие
sibling mailbox сохранены. Это устранение лишнего backoff при обратном
протокольном трафике; не объяснение первоначального отсутствующего ответа
и не исправление NETCALL-01.

## Проверки

Пять новых сценариев на FakeAsync с реальным MessagingService/codec и
in-memory storage: ранняя presence, точная двухсекундная граница, повторные
обратные запросы, malformed/claimed input, отзыв перед назначенным retry.
Проверяются счётчик настоящих отправок, тот же ID/query, неизменный cursor,
throttle и fresh revoke. Сохранены существующие held-send/serving credit,
replacement binding и 32-device контроли.

На прежнем production-файле **четыре assertion-red**, без timeout. Независимые
mutations минимального интервала, request throttle и переноса wake до валидации
дали по одной assertion-red; candidate восстановлен побайтно. Связанные suites:
**142 passed / 1 skipped**; analyzer трёх файлов чистый. Пропущенная проверка
не считается прошедшей. [Агрегаты](summary.json).

## Стендовая диагностика

В первой profile-серии финальный краткий boot B перезаписал файл предыдущего
boot той же метки: остались 0,132 с и 15 сэмплов вместо догрузки. Поэтому этот
CPU snapshot исключён из выводов о горячих функциях. Wire и correctness
результаты той серии остаются независимыми наблюдениями.

Test worker теперь сохраняет CPU snapshot каждого PID отдельно, затем
обновляет прежний latest-file для инструментов чтения. Это только `test/`,
не диагностический экспорт приложения. Профили содержат приватные метаданные
изолятов и остаются в cache; в публичном отчёте только агрегаты.

## Native qualification

Три Mac/JIT процесса A/B одной личности и C другой; private loopback Core
island, SDK `c6699c28`, прежний native HVS, public seeds/discovery отключены.
Весь прогон выполнен на frozen исходниках с включённым CPU profiling.

После настоящего SIGKILL B все **751** наблюдавшиеся строки сохранились до
сети при offline A/C: ID, тела, delivered и уже наблюдавшиеся canonical
positions. Вернулся только A. Затем **2000/2000** ID/тел/delivered/позиций
и порядок сошлись без дублей и completed-history retries. Повторный cold boot
B при выключенных источниках до сети подтвердил сохранность всех 2000.

После открытия A первый `list` пришёл через 581 мс, повтор **того же ID** —
через 2563 мс; обратный `list` наблюдался через 1430 мс. Прежний 16-секундный
интервал в этом прогоне не появился. Это наблюдение согласуется с двухсекундной
границей retry; отдельной записи вызова wake в native trace нет, поэтому
исключительная причинная атрибуция этому hook не заявлена.

После возврата из `start(A)` до полной сходимости — **25,683 с**; от начала
наблюдения с crash/restarts — 56,413 с. Серия одна, с profiling; сравнивать
эти числа с прежними как доказанный общий выигрыш нельзя. Из 43 полных
неповторённых ответов 42 — страницы: query→last part median 123,967 мс,
last part→next query median 349,677 мс. Один повторённый request ID исключён
из этих медиан, его начальный интервал описан отдельно выше.

Три per-boot receiver CPU-файла сохранены. Выбран полный 40,513-секундный
window с **5444 samples**, а не последний короткий boot. В 2780 samples есть
`_deviceSyncStateOfBundle`, в 2496 — `_messagesOfBundle`, в 2295 —
`_canonicalRetainedMessageView`, в 2018 — `verifyGroupMessage`. Это inclusive
frames: они перекрываются, их нельзя складывать или выдавать за доли wall
time. Следующий предмет разбора — цена повторного validated device-journal
view при roster lookup; fresh authorization/chain checks не объявлены лишними
и этим раундом не отключались.

**1509 frozen inputs** и native SHA неизменны, две реальные worker mappings
после restart подтвердили выбранные FFI/HVS. Cleanup exit 0: **34 PID / 57
портов**, owned процессов/listeners нет, runtime и одноразовые контейнеры
убраны. SDK/HVS исходники, телефон, Windows и production прежние. Сквозной
прогон не проверяет Android/AOT, WAN/mobile handover, часы offline или полную
multi-device матрицу. Push/релиза нет.
