# Постоянное отставание видео не является продолжающимся ростом очереди

2026-11-03. Завершение незакоммиченного раунда 2 ноября. Push/релиза нет.

## Дефект и финальное изменение

В [прошлом прогоне](../video-jitter-native-2026-11-02/README.md) decoder RTP-time
однократно отстал примерно на 140–160 мс, затем шёл ровно или быстрее часов.
Отклонение от старого минимума сохранялось три секунды, и контроллер объявлял
его продолжающимся ростом очереди. При разогнавшемся FPS уменьшалась допустимая
квантизация кадра, что дополнительно проявляло старую ступеньку. Лимит видео
снижался даже при здоровом аудио. Из прежних полей нельзя доказать, какую часть
именно той ступеньки создал adaptive target: сам target тогда не передавался.

Финальный контроллер сохраняет две независимые проверки:

1. При наличии нового receiver-report учитывает target, ограниченный текущей
   оценкой задержки и поддерживаемым пределом 400 мс. Не меняет raw RTP-время,
   счётчики/telemetry или causal frame barriers. Не переносит вычет на старые
   точки, у которых target неизвестен.
2. Через три секунды повышенного отставания требует **продолжения роста raw
   RTP-lag** ещё хотя бы на один период кадра либо 40 мс (что больше). Если
   отставание стало постоянным/уменьшается, перебазирует только окно измерения,
   без урезания producer budget. Свежие ACK остаются обязательны для пробы.

Без нового target работает вторая проверка. Предельные 500 мс по сообщаемому
`current_delay_ms`, остановка декодирования, рост очереди другого участника,
потери, audio protection, source pressure и ограничения роста не отключены.
Это порог timing estimate, **не** измерение акустической end-to-end задержки.

## Почему первый кандидат не принят как финал

Простое вычитание instantaneous target прошло 521 тест, но новый native-захват
показал падение target/current примерно с 360/371 до 159/170 мс, пока media-time
почти не догнало прежнее отставание. Вычитание меньшей цели само создавало
положительный остаток и новый ложный queue-pressure. По закреплённому WebRTC
current/target — estimates VCMTiming, а не количество байтов/кадров в очереди;
их изменение не доказывает ни заполнения, ни освобождения реального пути.
Поэтому одной цели недостаточно: добавлена независимая raw-time continuation.

Первая попытка Flutter-red для target-lowering пересеклась по времени с правкой
и не засчитана. Для доказательства восстановлен предыдущий Dart-кандидат;
**его SHA совпал с source-proof первого native-запуска**. Независимые копии
A/B/A показали: снижение target создаёт pressure начиная с десятого sample
только до continuation-фикса; стабильная legacy-ступенька — с шестого. После
фикса оба случая без pressure. На продолжающемся росте обе версии начинают
защиту на девятом sample. A₁=A₂ побитово, candidate AOT=JIT.

## Передача timing target

Новый optional RTCP APP `VVD2` передаёт `target_delay_ms` из того же GetStats,
что и current delay, для direct/group. 64-байтовый размер, cadence, endpoint
шифрование и C ABI сохранены. Старый `VVD1` декодируется, неизвестный target
не заменяется нулём. Поля защищены прежним authenticated channel/target SSRC,
monotone origin/counters, replay/freshness и atomic compound parsing.

[Описание формата](../../../third_party/veil/flutter/veil_media/VIDEO_DELIVERY_FEEDBACK.md).
Это endpoint timing metadata; реле не получают нового назначения/приоритета.
Совместимость производительности со старыми клиентами не квалифицировалась.

## Проверки

- **525 Flutter tests passed**: 12 файлов аудио/видео-политики, startup/RTT,
  delivery model, direct/group controllers. Плюс **19 diagnostic tests**.
- Два первоначальных model-контрпримера на target fill/drain были красными.
  Добавлены plateau/target-lowering, медленный рост 15 мс/с, остановка decoder,
  несколько получателей, replay/stale ACK, RTP wrap, malformed/unfilled/unknown
  target и независимый reported-delay потолок. Старые проверки постоянного
  backlog уточнены: продолжающийся рост должен снижать лимит, стабильная
  ступенька ниже потолка — после подтверждения освобождать пробу.
- Native shim: настоящий Get/SetLocalVideoDelivery → RTCP compound → parser →
  JSON. VVD1/VVD2, target 0/60000, отказ 60001, reserved/subtype, 120 усечённых
  вариантов и mixed-version duplicate. В первой попытке тест задавал время
  из будущего и ожидаемо не отправлял sample; исправлен сам тест с соблюдением
  существующего 950-мс таймера. Продуктовый freshness-барьер не изменялся.
- Analyzer чистый. Diagnostic AOT gate прошёл в двух режимах; target вместе с
  private peer/origin/sample canaries не попадает в анонимный report. В тесте
  проверяется настоящий скомпилированный journal, raw log sink отсутствует.
- Исправлена ошибка квалификации smoke: копия executable сохраняла RPATH к
  прошлой media. Тот запуск исключён. Контроль пересобран с `@loader_path`,
  реально загруженная текущая dylib проверена через loader trace + SHA;
  direct/group AEC/NS/AGC controls прошли. ABI и аудиообработка не менялись.

## Native-квалификация

Повторяется прежний owned loopback: три узла, нейтральный QUIC relay, Opus/VP8,
320×240 synthetic source, opaque 250-мс holds каждую секунду. Транспортная SDK
заморожена; media source/binary digest и текущая Dart-политика проверены отдельно.
Оба захвата с `--codec-only-tones`: AEC/NS выключены только для тонального oracle,
AGC сохранён; это **не** физический звонок или проверка речи с DSP.

| 70 секунд | Target-only кандидат | Финальный кандидат |
| --- | --- | --- |
| Queue-pressure samples, стороны 0/1 | 0 / 1 | 0 / 0 |
| Persistent-video-loss signals | 2 / 1 | 1 / 2 |
| Первый лимит 60 FPS от включения видео | 22 с / не достигнут | 14 с / 40 с |
| Средние decoder counters в фазе, FPS | 8,84 / 17,79 | 15,96 / 22,50 |

Это две серии с отличающимися session/scheduling и временем loss reports,
**не** статистическая оценка ускорения или native A/B/A. Реальные FPS не равны
разрешённому лимиту. Финальный sender 1 снизил лимит до 30 FPS в конце по
persistent-loss report. Ложный queue-pressure не повторился; весь разгон не
объявляется исправленным.

В финале 50/50 tone edges на каждой стороне, quiet PCM 0/4999, audio
interruptions в video-фазе 0; максимумы tone latency около 322 мс. Шейпер не
зарегистрировал drops, но имеет оставшиеся пакеты при teardown: отсутствие всех
сетевых потерь этим не доказывается. **Полный прежний гейт остаётся красным**
из-за 200-мс лимита. Порог не ослаблялся и результат не переименован в pass.

[Числовая сводка](summary.json); исходники, хеши, loader trace и raw synthetic
логи сохранены только приватно. Стенды остановлены, sockets/processes проверены.
Пользовательские профили/телефоны/публичные реле не тронуты. Engine pins старые,
релиза нет. Poco ↔ Windows, слышимость речи и весь NETCALL/NETLINE/multi-device
набор остаются отдельно открытыми. Следующий участок — persistent-video-loss:
нужно различить фактическую потерю, позднюю доставку и уже восстановленный кадр.
