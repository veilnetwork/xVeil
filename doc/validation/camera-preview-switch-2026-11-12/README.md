# Собственное превью при переключении камер Android

Жалоба относится к собственным превью двух участников. По правилам проекта
фронтальное self-preview зеркально, основная камера — нет; удалённый видеокадр
не должен получать отражение собственного превью. Само зеркальное изображение
себя на фронтальной камере не является дефектом.

В проверке найдены три отдельных механизма, присутствующие и в исходниках
выпущенной 0.13.98. Они исправлены локально. Причина конкретного переключения
на исходном телефоне не установлена: исправленный APK на нём ещё не проверялся.

| Находка | Подтверждение | Изменение |
|---|---|---|
| Старый stats-ответ стирает новое превью | Три управляемых interleaving-теста падают; текущий stop-control проходит | Ответ применяется только к тому же активному и опубликованному объекту превью |
| Лишнее отражение нативного Camera2-превью | Producer-матрицы на устройстве и код Dart/Kotlin показывают повторное отражение фронтальной текстуры | Kotlin сообщает отсутствие **дополнительного** Dart flip; системное отражение сохраняется |
| Резервный захват игнорирует выбранный объектив | Реальный CameraController с подменённым CameraPlatform открывает front вместо back; отсутствующий/rejected back тоже подменяется front | Fallback получает точный camera ID, не заменяет недоступную камеру, возвращает фактически открытый ID |

## Статистика старой камеры

MethodChannel управляется gates: запрос статистики front уже начат, затем
включается back с `mirror=false`, и только после этого старый запрос сообщает
`camera_running=false`. Проверяются повторное использование capturer, новый
capturer после stop и новый владелец без предварительного stop старого.
До фикса новый global preview становился null; в одном случае также сбивалось
состояние самого нового capturer. Контроль подтверждает, что актуальное
`camera_running=false` по-прежнему удаляет текущее превью.

Guard проверяет объект `_preview` после await и его тождественность опубликованной
текстуре. Старый ответ не меняет diagnostics и не останавливает timer новой
камеры. Это проверка stats-гонки, не всех возможных гонок start/stop.

## Отражение SurfaceTexture

Camera2 уже отражает front-preview в producer transform, который потребляет
Flutter. Дополнительный горизонтальный flip отменял системное отражение.
Резервный `CameraPreview` не имел этого дополнительного Dart flip: переход между
backend мог давать разные self-preview. Это возможное объяснение жалобы,
а не доказанная атрибуция её конкретного случая.

Контракт описан в [Android OutputConfiguration](https://developer.android.com/reference/android/hardware/camera2/params/OutputConfiguration#setMirrorMode(int)):
AUTO отражает front для SurfaceTexture, ImageReader это преобразование не меняет.
Передаваемые ImageReader/YUV кадры и их поворот этим preview-исправлением
не затрагиваются. Kotlin metadata `mirror` означает только дополнительный flip.

Отдельное QA-приложение на Android 11/API 30 чередовало front/back восемь сессий,
то есть семь переходов. Оно использовало Camera2, TEMPLATE_RECORD и настоящий
SurfaceTexture/EGL consumer. В каждой сессии пять начальных кадров пропущены,
затем прочитаны **только матрицы** пятнадцати кадров. Все 60 front-определителей
положительны, все 60 back — отрицательны. Вращение сохраняет знак определителя;
различие соответствует отражению producer. Дополнительный front flip делает
его знак таким же, как у back, что и показывает повторное отражение.

Фото, видео, pixel buffers для анализа и звук не записывались. Это проверка
платформенного преобразования, **не запуск исправленного xVeil APK** и не
сквозная проверка его Flutter-рендера. Первый сбор логов был неполным, один
ранний старт QA получил CameraAccessException. Они не зачтены как
полная серия; финальная серия ждёт window focus, собирается непрерывно и
содержит все восемь стадий. Причина отдельного CameraAccessException в раннем
запуске не атрибутирована. QA force-stopped, процесс вышел, пакет удалён,
SHA всех APK основного xVeil до/после совпали.

## Выбор камеры в резервном захвате

`AndroidCameraCapture` теперь принимает `requestedCameraId`. При null сохраняется
front-first поведение. Если ID задан, отсутствие или отказ этого объектива
завершают старт отказом; FPS-повтор использует тот же объектив. Реальный controller
публикует выбранную description, а orchestration передаёт выбранный ID и
учитывает успешный plugin capture при ответе на переключение.
Converter isolate создаётся после выбора доступного объектива: отсутствующая
камера не оставляет неиспользуемый worker в I420-пути.

Пять тестов используют настоящий CameraController и Fake CameraPlatform для
фактов о наличии/отказе устройства. Новый API передачи выбора сначала был
добавлен без изменения старого селектора: back/missing/rejected-back дали
три поведенческих падения, два front-controls прошли. Контрольное возвращение
старого front-first селектора при сохранённом новом API также даёт те же три
падения. Временный контроль восстановлен побайтно. Это не запуск старого APK
и не аппаратный отказ камеры. Проведение ID через media-controller проверено
review и компиляцией; полного native-failure→plugin теста на телефоне пока нет.

ID Camera2 и plugin name совпадают по Camera2CameraInfo.getCameraId в закреплённой
Android CameraX зависимости проекта. Новый default не меняет групповые звонки,
которые не задают отдельный объектив. При смене backend выбор не теряется.

## Продолжение: владение камерой при запоздавших start/stop

На исходниках `d0b955aa` подтверждено ещё одно семейство гонок. У Activity одна
Camera2-камера, а Dart создаёт новый bridge при переключении. Старый ответ start
мог опубликовать прежнюю текстуру после нового запуска. Старый stop, включая
cleanup некорректного ответа, останавливал уже новую камеру. Кроме того, start
после await собственного начального stop мог продолжить работу, хотя пользователь
успел отменить или заменить этот запуск.

Это не требует нарушения FIFO запросов MethodChannel. В `NativeCallCamera.stop`
поля захвата отсоединяются сразу, но ответ приходит после fence обоих обработчиков
Camera2/copy. Следующий stop уже не видит старых ресурсов и может ответить раньше.
Также ответ уже открытой камеры может быть доставлен после смены владельца.

Теперь запрос получает владение до первого await. После каждого ожидания и после
синхронного уведомления превью проверяется тот же запрос; устаревший ответ не
публикует текстуру и не отправляет глобальный stop. Замена отменяет старый stats
timer и очищает его локальное состояние. Остановка неактивного bridge не выключает
чужой захват. Состояние и timer готовятся до публикации превью: listener, сразу
выключающий или заменяющий камеру, больше не оставляет воскресшее состояние.

При этом старый владелец **продолжает ждать нативный stop fence**, даже если stop
за него уже отправил новый владелец. То же ожидание выполняет отменённый start
перед возвратом false: вызывающий код после этого может освобождать медиадвижок.
Промежуточный кандидат возвращал false слишком рано; отдельный тест воспроизвёл
этот пробел, и финальный вариант его закрывает. Новый владелец не обязан ждать
поздний старый start-ответ. Сообщения платформенного канала, Kotlin и ABI не
изменялись; новый идентификатор владения существует только в Dart.

Новый набор содержит 18 управляемых сценариев. Подменён только MethodChannel:
модель меняет аппаратное состояние при получении команды, а не при завершении
её ответа. Gates удерживают ответы, сохраняя порядок команд. Проверяются поздние
success/malformed/error, один и разные bridge, начальный stop, отмена, неактивный
stop, синхронные preview-listeners, текущие отказы и ожидание старых обработчиков.
Для отрицательных проверок незавершённого fence дренируются готовые события без
продвижения часов; пороги длительности не используются.

На точном baseline `d0b955aa` **15 тестов падают, 3 контроля проходят**. Исходник
после контрольного запуска восстановлен побайтно. Финальный набор из девяти
файлов — **133 passed, 0 skipped**, включая прежние 115 проверок. Targeted analyze
и `git diff --check` проходят. Снимок исходников до/после финальной серии совпал.

Это квалификация порядка событий в Dart с моделью native-команд, не аппаратное
воспроизведение исходного случая Poco. Исправленный APK и быстрые переключения
в настоящем звонке на нём ещё нужно проверить. Фронтальное собственное превью
по-прежнему намеренно зеркальное, основное и удалённое — без дополнительного
отражения self-preview. Установленные приложения и серверы в продолжении цикла
не менялись.

## 2026-11-19. Превью в промежутке между двумя источниками

Когда текстура Camera2 исчезала раньше, чем появлялась текстура выбранного
объектива или резервный `CameraPreview`, окно камеры читало `localVideoFrame`.
Этот кадр мог оставаться от предыдущей камеры или демонстрации экрана.
Новый экземпляр виджета принимал сохранённый кадр сразу и мог показать его
с ориентацией, отличной от превью выбранной камеры.

Теперь в этом промежутке показывается состояние ожидания камеры. Кадр
для собственного превью появляется вместе с текущей текстурой Camera2
или при готовности контроллера резервного захвата. Новый widget-тест
оставляет предыдущий RGBA-кадр в `localVideoFrame` и проверяет переходы
front → ожидание → back → ожидание → front. На старой реализации
тест обнаружил показ кадра вместо ожидания.

Отдельная проверка русской локализации при масштабе 200% выявила
пересечение заголовка видеозвонка с меткой реле. Метка начиналась на 66-м
логическом пикселе, хотя заголовок заканчивался на 102-м. Сведения о
маршруте, предупреждение о связи и кнопка возврата превью теперь
располагаются под заголовком по его фактической высоте.
Обе регрессии воспроизведены отдельными widget-тестами. Итоговая серия
из 196 связанных Flutter-тестов прошла без пропусков, анализатор чист.

Геометрический Camera2 QA-пакет пересобран для физической проверки на Poco.
Потоковая и непотоковая установки не завершились. Android оставлял
сессии установки без финального статуса, поэтому камера QA не запускалась.
Обе сессии закрыты, отсутствие QA-пакета и его процесса проверено.
Хеши основного xVeil совпали. Исходная зеркальность на Poco остаётся
неподтверждённой в физическом звонке.

## 2026-11-19. Состояния миниатюры в видеозвонке

На виджете размером 118 × 88 русская подпись ожидания при масштабе 200%
переполняла колонку на 64 логических пикселя. Если в миниатюре мало места,
она отдаёт его тексту. Полная подпись передаётся экранному диктору.

При выключении камеры собственная миниатюра продолжала рисовать
старый кадр под полупрозрачной плашкой. Та же плашка накладывалась
на собственный показ экрана, когда камера была выключена. Теперь отключённый
источник освобождает декодированный кадр, а при повторном включении
превью ждёт следующий кадр. Активный показ экрана виден независимо
от состояния камеры.

Оба теста воспроизводят ошибки до правки. Вызов проходит настоящий
`CallService` с подменённым медиаконтроллером и тестовыми кадрами.
Прошли 453 связанных Flutter-теста без пропусков, анализатор чист.
Аппаратное переключение объективов этим прогоном не проверялось.

## 2026-11-19. Возобновление камеры в сетке группового звонка

При выключении камеры плитка участника убирала виджет видео. При
повторном включении новый виджет сразу декодировал кадр, который сохранялся
в источнике видео с прошлого включения. Теперь плитка сохраняет виджет,
пока камера выключена. На это время виден аватар. После включения появляется
подпись ожидания до прихода нового кадра. Проверка застывшего изображения
запускается при получении кадра и останавливается при выключении источника.

Widget-тест проверяет показ исходного кадра, аватар после выключения,
ожидание и появление следующего кадра. На прежнем коде он находил исходный
кадр после повторного включения. Итоговая серия дала 533 пройденных
Flutter-теста без пропусков. Анализатор по затронутым файлам чист.

Poco с Android 16 снова был доступен по ADB. Повторная попытка установить
отдельный геометрический QA-пакет завершилась по таймауту. Сессия установки
отменена, QA-пакет и его процесс отсутствуют, хеши установленных APK
основного xVeil совпали. Исходная жалоба о зеркальности при смене
объективов всё ещё требует физического воспроизведения.

### «Картинка в картинке» в групповом звонке

В окне PiP воспроизведены две отдельные ошибки. При открытии Flutter
обнаруживал два `Positioned`, которые задавали положение одного окна.
Когда последний удалённый источник выключался, виджет удалялся, а после
возврата видео показывал прежний кадр. Теперь PiP позиционируется один раз.
При отключении последнего источника окно закрывает непрозрачная заглушка,
при возврате видео оно ждёт нового кадра. Уже полученный статичный кадр
активной демонстрации экрана по-прежнему виден при первом входе в PiP.

Тест проходит через общий `GroupCallOverlay` в окне 180 × 110 логических
пикселей. Обе ошибки наблюдались до правки. После неё прошли 534 связанных
Flutter-теста без пропусков, анализатор чист. Системное окно Android этим
прогоном не проверялось.

### Камера собеседника в прямом звонке

Когда собеседник сообщал об отключении камеры, окно продолжало показывать
его последний кадр. Успешное переключение камеры также не отправляло
состояние до следующего периодического сигнала. Теперь xVeil сообщает
о смене камеры сразу по завершении операции. При выключении кадр скрывается,
а при повторном включении окно ждёт свежего кадра. Активный показ экрана
остаётся виден при выключенной камере. Его состояние передаётся вместе
с сообщением об изменении состава медиа.

Проверки через `CallService` воспроизвели старый кадр для RGBA и Android
Texture, а также отсутствие немедленного сигнала. После правки проверены
переход к показу экрана, резервный RGBA-путь и новая текстура со своим
счётчиком кадров. Тест запоздалого отказа камеры подтверждает, что только
намеренное выключение отправляет состояние «выкл». Прошли 1818 связанных
Flutter-тестов, 8 пропущены. Android-проверка использует тестовую текстуру,
физический звонок и зеркальность при смене объективов ещё открыты.

### Переходы между окнами прямого звонка

После повторного включения камеры новое окно PiP могло принять сохранённый
кадр. Тот же кадр мог остаться в открытом окне, если сигналы выключения и
включения приходили до следующей отрисовки Flutter. Оба сбоя воспроизведены
для RGBA и Android Texture. Теперь общий экран звонка отслеживает смену
источника, в том числе когда миниатюра скрыта, и передаёт её состояние
полному окну, миниатюре и PiP. Уже полученный кадр активной демонстрации
можно перенести между окнами без ожидания ещё одного кадра.

Тесты охватывают сворачивание, скрытие миниатюры, смену источника в скрытом
состоянии, быстрое выключение и включение, PiP и возврат в полное окно.
Прошли 1818 связанных тестов, 8 пропущены. Анализатор чист. Android Texture
подставляется стендом. Системное окно и объективы на физическом устройстве
по-прежнему требуют проверки.

### Первый кадр после смены источника в прямом звонке

При смене источника уже открытое окно заново снимало текущий кадр во время
отрисовки и считало его старым. Если первый кадр демонстрации пришёл между
сигналом о смене и отрисовкой, окно оставалось в ожидании до второго кадра.
Это воспроизведено с RGBA и Android Texture при одном кадре демонстрации.
Оба пути теперь сравнивают с кадром, доступным при получении сигнала.
Проверен также первый кадр после смены источника без предыдущего кадра.
Прошли 1818 связанных Flutter-тестов, 8 пропущены. Анализатор чист.
Android Texture проверена на стенде с подставленными кадрами.

### Диагностика переключения объективов на Android

Отладочный отчёт `XVEIL_DIAGNOSTICS` получает `androidCameraPreview` при
успешном запуске текущего источника. `previewBackend` принимает 0 для
Camera2 и 1 для CameraX. `previewLens` принимает 0 для неизвестного
объектива, 1 для фронтального, 2 для заднего и 3 для внешнего. Для Camera2
также записываются `previewQuarterTurns` (поворот Flutter с шагом 90°)
и `previewExtraMirror` (0 или 1). Последняя конфигурация остаётся доступна
при заполнении журнала. Отчёт хранит настройки предпросмотра без ID камер,
текстур и кадров. Для проверки отражения самого изображения нужен звонок
на телефоне.

На Poco Android отклонил установку отдельного QA-пакета с
`INSTALL_FAILED_USER_RESTRICTED`. Измерение матрицы предпросмотра с двумя
выходами Camera2 не запускалось. QA-пакет и процесс отсутствуют,
хеши APK основного xVeil и настройки Wi-Fi и мобильной сети совпали.
С включённой диагностикой прошли 202 связанных Flutter-теста. Проверены
обе ветки предпросмотра, отсутствие событий от отменённых запусков
и сохранение последней конфигурации после заполнения журнала.

### Запоздалый список объективов при переключении одной кнопкой

Запрос списка камер мог завершиться после выключения и повторного включения
камеры, запуска демонстрации экрана, перехода к следующему звонку или ручного
выбора другого объектива. Быстрое переключение тогда применялось к уже
изменившемуся состоянию. Теперь после перечисления проверяются исходный
звонок, состояние захвата и актуальность выбора.

Четыре сценария подтверждены через `CallService` с задержанным ответом
медиаконтроллера. Обычное переключение с фронтальной на заднюю камеру
проходит до и после правки. Проверка касается отмены устаревшего выбора.
В общей серии 1841 тест прошёл, 8 пропущено. Анализатор чист. Причина
исходной зеркальности на Poco остаётся открытой.
