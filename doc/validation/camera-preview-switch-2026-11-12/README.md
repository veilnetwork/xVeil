# Собственное превью при переключении камер Android

Жалоба относится к собственным превью двух участников. По правилам проекта
фронтальное self-preview зеркально, основная камера — нет; удалённый видеокадр
не должен получать отражение собственного превью. Само зеркальное изображение
себя на фронтальной камере не является дефектом.

В проверке найдены три отдельных механизма, присутствующие и в исходниках
выпущенной 0.13.98. Они исправлены локально. Причина конкретного переключения
на исходном телефоне не установлена: исправленный APK на нём ещё не проверялся.

| Находка | Подтверждение | Изменение |
|---|---|---|
| Старый stats-ответ стирает новое превью | Три управляемых interleaving-теста падают; текущий stop-control проходит | Ответ применяется только к тому же активному и опубликованному объекту превью |
| Лишнее отражение нативного Camera2-превью | Producer-матрицы на устройстве и код Dart/Kotlin показывают повторное отражение фронтальной текстуры | Kotlin сообщает отсутствие **дополнительного** Dart flip; системное отражение сохраняется |
| Резервный захват игнорирует выбранный объектив | Реальный CameraController с подменённым CameraPlatform открывает front вместо back; отсутствующий/rejected back тоже подменяется front | Fallback получает точный camera ID, не заменяет недоступную камеру, возвращает фактически открытый ID |

## Статистика старой камеры

MethodChannel управляется gates: запрос статистики front уже начат, затем
включается back с `mirror=false`, и только после этого старый запрос сообщает
`camera_running=false`. Проверяются повторное использование capturer, новый
capturer после stop и новый владелец без предварительного stop старого.
До фикса новый global preview становился null; в одном случае также сбивалось
состояние самого нового capturer. Контроль подтверждает, что актуальное
`camera_running=false` по-прежнему удаляет текущее превью.

Guard проверяет объект `_preview` после await и его тождественность опубликованной
текстуре. Старый ответ не меняет diagnostics и не останавливает timer новой
камеры. Это проверка stats-гонки, не всех возможных гонок start/stop.

## Отражение SurfaceTexture

Camera2 уже отражает front-preview в producer transform, который потребляет
Flutter. Дополнительный горизонтальный flip отменял системное отражение.
Резервный `CameraPreview` не имел этого дополнительного Dart flip: переход между
backend мог давать разные self-preview. Это возможное объяснение жалобы,
а не доказанная атрибуция её конкретного случая.

Контракт описан в [Android OutputConfiguration](https://developer.android.com/reference/android/hardware/camera2/params/OutputConfiguration#setMirrorMode(int)):
AUTO отражает front для SurfaceTexture, ImageReader это преобразование не меняет.
Передаваемые ImageReader/YUV кадры и их поворот этим preview-исправлением
не затрагиваются. Kotlin metadata `mirror` означает только дополнительный flip.

Отдельное QA-приложение на Android 11/API 30 чередовало front/back восемь сессий,
то есть семь переходов. Оно использовало Camera2, TEMPLATE_RECORD и настоящий
SurfaceTexture/EGL consumer. В каждой сессии пять начальных кадров пропущены,
затем прочитаны **только матрицы** пятнадцати кадров. Все 60 front-определителей
положительны, все 60 back — отрицательны. Вращение сохраняет знак определителя;
различие соответствует отражению producer. Дополнительный front flip делает
его знак таким же, как у back, что и показывает повторное отражение.

Фото, видео, pixel buffers для анализа и звук не записывались. Это проверка
платформенного преобразования, **не запуск исправленного xVeil APK** и не
сквозная проверка его Flutter-рендера. Первый сбор логов был неполным, один
ранний старт QA получил CameraAccessException. Они не зачтены как
полная серия; финальная серия ждёт window focus, собирается непрерывно и
содержит все восемь стадий. Причина отдельного CameraAccessException в раннем
запуске не атрибутирована. QA force-stopped, процесс вышел, пакет удалён,
SHA всех APK основного xVeil до/после совпали.

## Выбор камеры в резервном захвате

`AndroidCameraCapture` теперь принимает `requestedCameraId`. При null сохраняется
front-first поведение. Если ID задан, отсутствие или отказ этого объектива
завершают старт отказом; FPS-повтор использует тот же объектив. Реальный controller
публикует выбранную description, а orchestration передаёт выбранный ID и
учитывает успешный plugin capture при ответе на переключение.
Converter isolate создаётся после выбора доступного объектива: отсутствующая
камера не оставляет неиспользуемый worker в I420-пути.

Пять тестов используют настоящий CameraController и Fake CameraPlatform для
фактов о наличии/отказе устройства. Новый API передачи выбора сначала был
добавлен без изменения старого селектора: back/missing/rejected-back дали
три поведенческих падения, два front-controls прошли. Контрольное возвращение
старого front-first селектора при сохранённом новом API также даёт те же три
падения. Временный контроль восстановлен побайтно. Это не запуск старого APK
и не аппаратный отказ камеры. Проведение ID через media-controller проверено
review и компиляцией; полного native-failure→plugin теста на телефоне пока нет.

ID Camera2 и plugin name совпадают по Camera2CameraInfo.getCameraId в закреплённой
Android CameraX зависимости проекта. Новый default не меняет групповые звонки,
которые не задают отдельный объектив. При смене backend выбор не теряется.

## Проверки и остаток

Три stale-stats регрессии и три selection-регрессии воспроизведены отдельно.
Итоговый набор — **115 passed, 0 skipped**. Он включает capture,
preview/frame view, camera state, device picker и запуск медиаконтроллера.
Выбранные исходники до/после финального прогона совпали; targeted analyze и
`git diff --check` проходят. Изменённый NativeCallCamera и его size policy
компилируются с Android SDK и Flutter embedding, 9 class files; media engine
и JNI/wire интерфейсы не менялись. Полный Android APK в этом цикле не собирался.

Остаётся проверить исходный телефон на исправленной сборке и быстрые повторные
нажатия, включая возможные другие start/stop-гонки. В multi-device матрице
прерывание target adoption остаётся отдельным следующим участком. Установленные
пользовательские приложения и production-серверы не обновлялись.
