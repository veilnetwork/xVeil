# Больше коротких строк в прежнем byte budget страницы

## Причина и изменение

После сокращения лишних reads общий native-прогон всё ещё занимал около
195 с на 100000 сообщений. Страница ограничивалась 128 строками даже тогда,
когда короткие строки оставляли место в независимом лимите 128 КиБ. Каждый
следующий запрос снова требовал свежий snapshot источника, проверку/приём,
применение и durable cursor.

Потолок явно запрашиваемых строк увеличен **128→256**. Byte ceiling **128 КиБ**,
slice **4096 bytes**, максимум **64 части**, frame/admission/record budgets
не менялись. Prepared-подготовка и атомарная публикация остаются **по 64 строки**;
одна страница не превращается в одну большую транзакцию. Consent, fresh
membership/visibility, revoke, binding/erasure guards и durable cursor прежние.
Кэш авторизации/истории и sibling mailbox не добавлены.

Источник соблюдает меньший запрошенный лимит; отсутствие `rows` сохраняет
default 64. Получатель проверяет ответ против собственного запроса. Старый
клиент с максимумом 128 отклонит новый запрос 256: для такой пары нужно
обновить обе стороны. Mixed-совместимость ранее исключена владельцем из
обязательных условий, новый fallback в этом цикле не добавлялся.

## Регрессионные проверки

Два новых parent assertion-red: 256 коротких incoming/outgoing сообщений
потребовали **2 страницы вместо 1**, без таймингового порога. На candidate:
одна страница, четыре публикации по 64, три cursor commits всего сценария;
полные ID/body/status/direction/order совпадают.

Отдельные новые проверки отказывают **четвёртой публикации** через storage error
или revoke. Первые 192 строки durable, курсор не перескакивает неприменённые
строки. После рестарта/восстановления membership приходят все 256 без дублей;
в сумме четыре успешные публикации по 64. Проверки меньшей 128-row страницы
и отказа второй публикации также сохранены.

Проверены `rows` absent/1/64/128/256, отказ 257 и неверных типов до snapshot,
отказ ответа с 257 событиями до первого apply, точные UTF-8/JSON byte-boundary
пробы 128 КиБ −1/0/+1 с текущим requested cap, включая prefix metadata;
partial records, TTL, правки, reorder/replay, admission/shutdown, durable cursor
failure и cold restart.

Сценарии, которым нужны несколько страниц, перенесены на новую границу:
restart после 256 из 384, отказ cursor после 256 из 257, sparse source 4096
строк с непроверяемой первой и проверяемой второй prefix-подсказкой. Их
ожидаемые данные/ревизии/курсоры проверяются полностью. Первоначально три
старых ожидания были перенесены не полностью (ID ожидаемой правки и количество
страниц). Эти отказы сохранены, исправлены именно fixtures/expectations;
отдельные шесть sparse-сценариев и весь набор выполнены повторно.

**321 checks passed / 0 skipped**, включая native expiry и приватный wire probe;
analyzer четырёх изменённых Dart-файлов чист. Probe записывает только bounded
числовой `requestedRows` вместе с прежней приватной метаинформацией; payload
не сохраняется, production exporter этот test helper не импортирует.

## Native A/B/A на 100000 сообщений

Parent `f1f04360` → candidate → parent. Четыре Mac/JIT процесса, три
изолированных Core, настоящий FFI/ratchet/HVS. Два полных источника; оба
первых authenticated ответа получены до apply release. Seed вне измеряемого
окна, compact observer каждые 5000 мс; CPU sampling/work trace/timeline выключены.
Источник во всех фазах сохраняет исходный append order: одна новая строка
перед 100000 архивными, без перестройки fixture ради быстрого пути.

На этом стенде candidate быстрее обоих контролей на **45,45–45,81 с**, около
**23%**. Независимый passive witness сокращён на **47,39–48,63 с**, но включает
доставку следующего inventory и не является точным временем UI. Это локальная
JIT-квалификация, не универсальный коэффициент для Android/AOT/интернета.

Страницы стали крупнее: query→full reply P50 около 91–93 мс вместо 69–74;
reply→next query P50 около 238–239 мс вместо 137–141. Эти интервалы относятся
к вдвое большей порции с четырьмя вместо двух cohorts. Их рост не означает
задержку одной строки или сетевую тишину: страниц вдвое меньше, весь архив
завершается быстрее. Медианы разных стадий нельзя складывать в wall time.

Данные одинаковы, protocol overhead различается. В bytes учтены app frames,
а не весь сетевой трафик. RPC total — наблюдение всего measured window,
включая фоновые операции; уменьшение каждого RPC не приписывается одному
cursor commit. Сохранён прежний размер data publications и барьеры записи.

Все **100000 архивных + 1 прежняя строка** совпали по ID, body, delivered,
canonical positions и порядку, без пропусков/дублей/лишних строк. Оба cursor
завершены. Холодное открытие до сети, при offline всех источников, сохранило
полный набор. Wire/census не обрезаны; actual requestedRows различает runtime
варианты независимо от чистоты checkout и состояния compiler cache.

## Происхождение, уборка и остаток

**1532 frozen inputs**, один production variant и 1531 общий input. SHA
native-библиотек/ABI и реальные worker mappings сверены; Rust не собирался.
Candidate восстановлен, его frozen inputs проверены после всех фаз.

Cleanup проверил **38/37/40 PIDs** и по **57 портов**: owned процессов и
слушателей нет, synthetic runtime удалён. Cache **92→92** во всех фазах,
новых kernel entries 0, около 9,5 ГиБ; свободно около 149 ГиБ. Raw evidence
приватен, публичная сводка не содержит адресов, ID или пользовательских путей.

Latency остаётся активной: около 149 с на 100000 на этом стенде. Физическая/AOT
квалификация, NETCALL-01 и оставшаяся multi-device matrix не закрыты.
Push/релиза нет.
