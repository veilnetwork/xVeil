# Замена завышенного BBR cache hint — 2026-10-30

Продолжение [проверки первого pacing](../warm-first-flight-2026-10-30/README.md),
базовая SDK `de39e9b6`, исправление `e8e54d42`. В той модели после ухудшения пути seed 1 МиБ/с
на реальном FIFO 32 КиБ/с удерживался в десятисекундном max-filter и создавал
очередь до 16,069 с. Это модельный механизм, не доказанная причина прежнего
пользовательского зависания «33%».

## Исправление

Cache hint теперь может уступить пригодному измерению текущего потока раньше
обычного expiry. Сохраняются прежние минимальный span 300 мс, byte floor,
проверка непрерывного прикладного backlog и разделение flow/app-limited эпох.
Удаляется только cache entry с timestamp zero: настоящий rate sample не может
иметь такой timestamp, поскольку требует положительного span. Независимые live
highs остаются в прежнем десятисекундном max-filter; delivered не обнуляется.

Более низкое измерение дополнительно требует устойчивого delivery clock:
не меньше трёх интервалов между checkpoints, кратчайший не больше половины
наблюдаемого SRTT (либо seeded RTT до его появления), длиннейший не больше
четырёх кратчайших. Это локальный эвристический фильтр ограниченного окна
наблюдений, не доказательство ёмкости сети. Если данные неоднозначны, сохраняется
прежнее expiry. Измерение выше seed может заменить hint без этого дополнительного
условия. Для свежей основы STARTUP сбрасывается только plateau anchor/счётчик;
завершённый STARTUP повторно не включается. Gains, pacing quantum, RTT/drain,
RACK/RTO, retry limits, wire/C ABI, mailbox и relay QoS не менялись.

## Пойманная регрессия промежуточного варианта

Первая версия заменяла hint по любому пригодному backlogged average. Этого
оказалось недостаточно: при недостаточном flight на большом RTT ACK приходят
короткими поездами, разделёнными ожиданием следующего раунда. Среднее по таким
паузам не является надёжной оценкой меньшей полосы.

На 16 МиБ/с, propagation 250 мс в каждую сторону и cached RTT 50 мс время
3-МиБ передачи выросло **2803 → 5897 мс**. Этот кандидат не закоммичен.
С фильтром delivery clock результат снова **2803 мс**. Также исчезла регрессия
15164 → 18285 мс на 1 МиБ/с с тем же рассогласованием RTT. Все числовые варианты
проверялись на том же исходнике модели, не на таймингах настоящей сети.

## Контролируемый результат

Тот же [queue_probe.rs](../warm-first-flight-2026-10-30/queue_probe.rs),
SHA проверен: реальные sans-I/O engines, 3 МиБ + 251 байт, MSS 1982,
фиксированные 2048 wire bytes, начальное окно 64 MSS, recv-window 8 МиБ,
ACK every 16 / 5 мс, RACK/BBR on. FIFO без потерь/переупорядочивания.
Baseline-бинарник из предыдущей квалификации проверен по опубликованному SHA;
candidate собран отдельно из канонической SDK. Targets не смешивались.

| Seed / полоса FIFO | A₁ | B | A₂ |
| --- | ---: | ---: | ---: |
| Seed 1 МиБ/с, FIFO 32 КиБ/с: максимальная очередь | 16069 мс | **6819 мс** | 16069 мс |
| То же: максимальный flight | 514566 Б | **219625 Б** | 514566 Б |
| То же: полное время, включая handshake/EOF | 99732 мс | 99732 мс | 99732 мс |

Меньший flight уменьшает очередь; полное время FIFO всё равно определяется
сериализацией того же числа wire cells. Это не ускорение всей загрузки.
Первоначальные **6,819 с** до пригодной оценки ещё остаются; в том числе
seeded BDP может увеличить первое окно до измерения текущего пути.
Обычный cold-профиль 32 КиБ/с сохраняет прежний максимум 4,194 с.

Матрица: четыре полосы (32/128 КиБ/с, 1/16 МиБ/с), три propagation
(25/100/250 мс в одну сторону), три cached RTT (50/200/500 мс) плюс специальные
overseed/no-RTT. Это **50 различных профилей × A/B/A** после исключения
повторяющихся cold-контролей. Фактически выполнено 114 запусков конфигурации,
228 наблюдений фаз/профилей, из которых 150 относятся к уникальным 50 профилям.
Повторные cold-контроли не объявляются дополнительными разными сценариями.

A₁/A₂ дали побитово одинаковый stdout для каждой конфигурации. Каждый payload
byte и оба EOF проверены assertions, RTO нет. Во всех 50 профилях время B не
выросло, число wire cells совпало; все cold-результаты совпали целиком.
Числа: [comparison.csv](comparison.csv), происхождение и счёт проверок:
[summary.json](summary.json).

## Проверки и ограничения

Два теста упали на прежней SDK: seed продолжал маскировать измеренные
32 КБ/с; отдельно seed не удалялся при сохранении независимого live-high.
Контроли проверяют sparse/app-limited traffic, короткие ACK-поезда с паузами,
один checkpoint на RTT, возобновление пригодного clock после ухода старых пауз
из окна, сохранение живых максимумов и нового STARTUP anchor.

Прошли **221 stream-тест**, ignored нет; **326 FFI unit-тестов**, 2 ignored.
Внутренний subprocess не прибавлен; 5 ignored FFI doctests указаны отдельно.
FFI flags: `--no-default-features --features node-embedded,production-seeds,packet-tunnel`.
Clippy `--lib --tests -- -D warnings` и rustfmt прошли. Проверки mount внешнего
target действовали всё время сборок; процессы build/test/probe завершены.

Это не физическая квалификация Android/AOT/мобильного провайдера, параллельных
bulk-потоков или потерь. При нерегулярных ACK hint может дожить до прежнего expiry;
заниженный cached RTT остаётся отдельным ограничением. Полное устранение «33%»,
холодного resolve и всех первоначальных очередей не заявляется. Телефон,
GUI и реле не запускались/не менялись. Push/релиз не выполнялись.
