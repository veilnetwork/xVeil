# Аватары: блокировка во время чтения — 2026-11-11

## Подтверждённый дефект

Проверка аватарного пути выявила четыре окна использования устаревшего
разрешения контакта. Это воспроизводимые гонки, но не установленная причина
пользовательской жалобы «аватарки на ПК обновляются через раз».

| Операция | Контролируемое ожидание | Прежний результат после завершённой блокировки |
|---|---|---|
| Запрос чужого аватара | Чтение принятого контакта | Уходил запрос `?` |
| Ответ своим аватаром | Чтение собственной картинки | Уходил ответ |
| Объявление обновления | Чтение списка разговоров | Ответ уходил контакту из старого списка |
| Приём чужого обновления | Чтение предыдущего аватара | Новое значение сохранялось |

Во всех четырёх случаях ожидание управляется gate, без порогов времени:
чтение уже получило старые данные, затем обычный `blockContact` завершает
запись решения, и только после этого исходное чтение возвращается вызывающему.
До исправления три transport assertions обнаруживают лишний avatar frame,
четвёртый — реальную замену значения в хранилище.

## Исправление

Аватарный путь использует существующий revision witness разрешений контакта,
который уже применяется для call/control. Устаревшее чтение контакта не
авторизует запрос; каждый адресат объявления проверяется заново. Ответ и
обновление сверяют исходное разрешение после чтения картинки, перед допуском
отправки или записи. Закрытый MessagingService также не продолжает этот путь.

Это проверка на границе допуска операции. Уже принятые сетью кадры не
отзываются, а уже допущенная запись не объявляется отменяемой транзакцией.
Прежние authenticated ingress, блокировка незнакомых контактов, image caps,
timestamp/tie-break, live-only доставка и rate limits сохранены. Outbox,
mailbox и присутствие/периодический опрос для аватаров не добавлены.

## Проверки

- Четыре сценария дали assertion-red на прежнем коде как с контролируемым
  KV-store, так и с настоящим контейнером через worker: **8 ожидаемых отказов**.
- После правки **50 related tests прошли без skips** на macOS: новые гонки,
  существующие avatar/widget tests и contact-consent races. Путь к HV и SHA
  реально загруженной библиотеки проверены; нативный режим не заменён fake.
- На Windows 11 **16 tests прошли без skips**: те же четыре сценария в обоих
  storage режимах и прежние avatar/widget tests. Это включает Flutter
  `MemoryImage` обновление, переиспользование widget и смену identity service.
- Анализ двух новых/изменённых Dart-файлов чист, `git diff --check` проходит.

Windows-тесты временно использовали пять явно учтённых файлов собственной
QA-копии исходников. После проверки каждый прежний файл восстановлен по SHA,
добавленные файлы удалены. Подключена настоящая packaged HV DLL с проверенным
хешем. Контейнеры тестов создаются отдельно и закрываются/удаляются teardown;
приложения и звонки в этом раунде не запускались.

## Что этим не доказано

Стенд работает на Windows 11. Исходные Windows 10/Android, реальная доставка
нового аватара через сеть и его показ в работающем GUI по-прежнему не
квалифицированы этим тестом. Fake transport проверяет точное решение об
отправке; он не является свидетельством доставки. Предыдущие сетевые
AV-звонки не включали смену аватара.

Пересборка AOT после этой Dart-правки ещё нужна: ранее проверенный desktop
bundle ей предшествует. Public media pins остаются отдельной задачей до
выпуска. Пользовательские контейнеры и реле не изменены, push/релиза нет.
