# После явного unban не ждать очередного ban poll

Агрегаты: [summary.json](summary.json).

Трасса разделила прежнее ожидание automatic healing: первые 25–26 с
соединения между половинами не открывались. Причиной на этом стенде оказался
способ разрыва сети через admin bans: `unban_node` удалял запрет и сохранял
файл, но не будил ожидающий connector. Он продолжал ждать 30-с poll.
Это отдельный дефект операторского API, не доказанная причина мобильных пауз.

## Проверка границы

В test-only partition harness добавлена пара same-host wall-clock отметок
до/после снятия bans. Она связывает native session events с Dart-логами;
в публичный отчёт входят только относительные интервалы и роли A/B/C/D.

На SDK `bbeaf3a9`:

| Устройство | Первая сессия с другой половиной | Первый own-identity group frame |
|---|---:|---:|
| A | 25,438 с | 28,460 с |
| B | 25,438 с | 33,232 с |
| C | 25,773 с | 34,460 с |
| D | 25,902 с | 28,539 с |

В журнале A session ended за 4,569 с до начала unban; следующий dial — через
25,433 с после начала. Между ними **30,002 с**, что соответствует ban guard.
Снятие всех bans заняло 552 мс. Это не измерение ping или задержки DATA.
Первый group frame может быть повтором: таблица не приравнивает его к
появлению конкретного недостающего сообщения.

В наблюдаемых native send samples к sibling/своей identity максимальные
`total_ms` — 502 мс, `source_wait_ms` — 494 мс. Здесь 25-с ожидание не
объясняется долгим отдельным seal/resolve; это ограниченный warm-сценарий,
а не отрицание холодных задержек в остальных случаях.

## Исправление SDK `b9b88bb7`

После удаления запрета и сохранения прежнего `PersistOutcome` runtime меняет
generation существующего watch только нужного node ID. Этот retained hint
пробуждает ban/backoff wait. Он не создаёт новый connector, не закрывает
здоровые сессии и не отменяет чужие pending dials глобальным уведомлением.

Все прежние ban/role/handshake/admission checks выполняются заново.
Семантика неудачного persist прежняя: изменение действует в памяти,
а caller получает volatile outcome. Автоматический срок ban и 30-с poll
не сокращались. Identity revocation/floors не затрагиваются.

Тест использует настоящий reconnect loop и Transport boundary. Отказ dial
в точном formatting gap устанавливает ban и будит цикл, который паркуется
по ban guard. Затем настоящий `NodeRuntime.unban_node` должен начать второй
dial без продвижения остановленных часов. Проверяются durable outcome,
сохранность другого ban, отсутствие изменения чужого watch и глобального wake.
Cleanup выполняется до итоговых assertions.

- База: **1 assertion-red**, отсутствие немедленного второго dial.
- Полный runtime: **812 unit + 8 integration passed**.
- Отдельно: **11 unit ignored + 2 doc ignored**; они не считаются passed.
- Rustfmt/diff checks чисты. Внешняя ФС проверялась до и во время Cargo.

## Native квалификация

Те же четыре процесса двух личностей, три loopback Core, реальные контейнеры
HVS `eceb9158`; снятие bans без дополнительных debug joins. Это Mac/JIT
provider fixture с настоящим transport/ratchet/group service, но без полного
foreground SessionPipeline, Android и UI квалификации.

| SDK / режим | Первая сходимость | Устойчивость | Полное recovery |
|---|---:|---:|---:|
| `bbeaf3a9`, trace | 35,568 с | 10,244 с | 45,812 с |
| `b9b88bb7`, trace | 13,070 с | 10,273 с | 23,344 с |
| `b9b88bb7`, обычный logging | 13,396 с | 10,311 с | 23,708 с |

На новой SDK первые межчастные сессии A/B/C/D — **1107/1116/304/304 мс**
от начала unban; снятие bans заняло 502 мс. Все 17 ожидаемых строк,
global delete против edit, реакции и read position сходятся; restart B
при остановленных A/C/D тоже прошёл. Проверки функциональной матрицы
из [partition-сценария](../multi-device-partition-2026-11-06/README.md)
не ослаблялись.

Повтор без `VEIL_RT_TRACE`: первые межчастные сессии —
**978/978/375/375 мс**, unban — 603 мс. Native send-stage samples в этом
режиме отсутствуют и в агрегатах помечены `null`, а не нулевой задержкой.
Повторное прохождение с обычным logging не объявляется отдельным A/B
эффектом трассировки: в каждом прогоне свои идентификаторы и cache state.

Прогоны — свежие процессы/адреса/кэши, не замороженная packet schedule.
Снижение всей задержки нельзя полностью приписывать одному изменению.
Доказан конкретный потерянный wake; оставшееся ожидание доставки открыто.
Предыдущие 35–45 с следует читать в контексте admin-ban стенда, а не как
общую скорость приложения или причину исходных пользовательских жалоб.

FFI и CLI пересобраны после чистого SDK commit; runtime действительно
перекомпилирован. Проверены SHA после codesign, подписи, CLI version,
208 неизменных C-экспортов и фактический вызов ABI-contract getter.
Выбранные immutable библиотеки проверены до/после stand; обычная HVS прежняя.
В прогоне с обычным logging OS mappings подтвердили выбранные FFI/HVS во
всех четырёх живых workers. Поздняя разовая попытка снять такие mappings
в trace-прогоне пропустила окно живых процессов и не засчитана как проверка.
Сырые IDs, адреса и журналы остаются в приватном cache.

До правки: очищены 27 PID / 32 порта; после правки с trace — 27 / 34,
с обычным logging — 26 / 30.
Своих процессов/listeners нет, runtime roots удалены. Мобильный провайдер,
NETCALL-01 и полная multi-device матрица этим не закрываются. Телефон,
production-реле и пользовательские контейнеры не менялись; push/релиза нет.
