# Владение автоматической попыткой во время задержанного открытия назначения

Подтверждена гонка подготовки auto-resume. Пока `plainFileSinkOpener` ждал,
пользователь мог отменить загрузку и выбрать другой путь, просто создать новый
запрос, очистить реестр либо закрыть личность. Возвратившийся старый sink
передавался в download engine без проверки владельца. Флаг отмены не защищал
новый запрос: он уже был очищен новым действием пользователя. Старый путь
перезаписывал реестр или восстанавливал удалённый запрос; после dispose
продолжение начинало читать хранилище и могло оставить sink незакрытым.

Вместо CID-only Set каждая активная автоматическая попытка имеет identity token
в Map. Отмена, замена явным запросом, clear и dispose снимают этот token.
Поздний opener закрывает только собственный handle; null/exception старой
попытки не меняют backoff замены. Освобождение слота в finally также сравнивает
identity: старое продолжение не снимает token новой попытки того же CID.
Проверки после чтения реестра, наличия blob/saved path, eligibility и manifest
не позволяют старой подготовке удалить/припарковать новый запрос или перейти
к выдаче. Уже существующие active-pull счётчики/abort и защита sink сохраняются.

Token живёт только в RAM у активной подготовки, не является ключом шифрования
или разрешением. Durable-схема, ratchet, подписи, ACL, file hashes, wire,
mailbox и сетевые приоритеты не изменялись. Повторная пользовательская загрузка
через четыре обычных entry points снимает прежний resume token; автоматическая
передача использует существующий `userInitiated: false` и не отменяет себя.
Обычная обработка текущего отказа открытия из предыдущего исправления остаётся:
сохранить запрос, bounded backoff, parking. Бесконечный opener не блокирует
отмену ожиданием самого callback; отменить системный open нельзя, его возможный
поздний дескриптор остаётся обязанностью продолжения.

## Проверка на исходном коде

На `2ffccc93` пять сценариев управляли моментом возврата opener через Completer.
Никакая сетевая задержка не определяла порядок событий. Наблюдались реальная
запись JSON-реестра через HiddenVolumeStorage/FakeKvLogStore и обращения к
хранилищу после закрытия службы; sink имел счётчики write/close.

| Действие во время ожидания opener | Исходный результат |
| --- | --- |
| Отмена без нового запроса | Контроль проходил: старый sink закрывался |
| Отмена и новый путь | Красный: старый путь записан обратно |
| Новый путь без предварительной отмены | Красный: старый путь записан обратно |
| Очистка очереди | Красный: удалённый запрос создан заново |
| Dispose | Красный: чтение хранилища после shutdown вместо закрытия sink |

После исправления все пять проходят. Три дополнительных interleaving-контроля
с sink/null/exception от старого opener запускают новую автоматическую попытку
ещё до его завершения. Старый finally заканчивается первым; новый opener затем
возвращается и действительно передаёт запрос дальше (наблюдается новая запись
реестра), а не только закрывается как ошибочно устаревший. Ненужных payload
записей у старого sink нет, close вызван один раз.

Итого прошли **108 тестов** auto-resume, registry persistence и stream transfer,
без skipped/ignored. Восемь сценариев добавлены этим раундом; четыре исходных
красных результата — варианты одной гонки, не четыре независимых сетевых бага.
Analyze четырёх затронутых файлов не нашёл замечаний.

## Настоящее хранилище и файловый sink

Отдельно прошли **3 native-storage теста без пропусков**. Новый сценарий
сохраняет запрос в настоящем hidden-volume контейнере, задерживает opener,
завершает службу и закрывает контейнер. Только затем возвращается настоящий
`veilPlainFileSinkOpener` с write/read файловыми дескрипторами временного файла.
Продолжение вызывает настоящий close один раз, write не вызывается, файл
остаётся пустым. Повторное открытие контейнера сохраняет исходное намерение:
shutdown не является отменой. Использована прежняя библиотека hidden-volume
с проверенным SHA-256; Argon min относится только к временной фикстуре.
Ранний прототип этого сценария использовал счётный sink; приведённые итоги
native-выполнения относятся к окончательной версии с настоящим файловым sink.

## Границы

Это проверка владения auto-resume до передачи sink в общий download engine,
а не доказательство устранения всех гонок уже идущих payload-передач. Interleaving
после этой передачи и другие асинхронные entry points остаются отдельным
предметом проверки. В основном наборе транспорт — in-process reliable stream;
native-storage набор работает offline. Android/Windows, OS grant loss, живые
реле, поздние callbacks настоящей файловой системы и исходный пользовательский
«33%» физически не воспроизводились. Срок реестра и таймауты не увеличены.
GUI-стенд не запускался. Временные native-фикстуры удалены, собственные группы
тестовых процессов завершены. Коммит без подписи; push/релиза нет.
