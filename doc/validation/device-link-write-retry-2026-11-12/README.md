# Публикация документа при повторе привязки устройства

**Подтверждён дефект:** материал с новым устройством уже сохранён, но операция
получила отказ вместо завершения записи. Повтор выдаёт токен привязки,
а работающий узел источника продолжает публиковать старый документ.
Проблема воспроизведена с обоими видами приглашения: с документом и без него.
Условия, пропускающие refresh, присутствуют в исходниках выпущенной 0.13.98.
Потеря сообщений после завершённой привязки на исходном коде этим опытом
не доказывается: red останавливается на несогласованной публикации до adoption.

## Воспроизведение

X=A+B, Y=C; отдельные процессы, реальные контейнеры, native узлы и ratchet,
три локальных Core. A и C обмениваются контрольным сообщением до привязки B.
Публичные seeds/meeting points выключены, собственный mailbox не добавляется.

Приватная обёртка `PrivateSovereignWriteFault` из предыдущего
[отзывного сценария](../revocation-retry-publication-2026-11-12/README.md)
выполняет настоящий `storeFile`, затем бросает отказ вместо возврата вызывающему
коду. Копируются только подписанный документ и marker успешного storage call;
секреты и полный material в marker не записываются.

Для варианта с документом fixture готовит его настоящей native-делегацией
ключа B на отдельной копии материала A в памяти. Helper сверяет неизменность
живого материала A и возвращает только подписанный публичный документ.
Таким образом документ действительно принадлежит тому же мастеру и называет
оба ключа; это не подмена crypto verifier. Без документа этот шаг пропускается.
После сериализации приглашение повторно разбирается: наличие непустого
документа должно точно соответствовать выбранному варианту. Истории на B
до привязки быть не должно, физические IDs A и B обязаны различаться.

Первая prepare-попытка отвечает отказом; device group ещё не создана.
Сохранённый документ отличается от прежнего, а локальная DHT источника пока
содержит прежний. Повтор prepare успешен, но до исправления документ DHT
не меняется: оба регрессионных сценария падают на проверке публикации.

При приглашении с документом потеря завершения возникает после merge,
без документа — после delegation. Повтор находит уже сохранённый материал
и не считает его новой записью. Ни merge-guard, ни накопленный `delegated`
не требовали refresh: token читал новый storage, node продолжал читать runtime.

## Исправление

В UI источника и debug caller узел перечитывает документ перед созданием токена
после успешной проверки, что документ удостоверяет целевое устройство,
и успешного добавления в группу. Refresh выполняется и для уже сохранённого
результата. Удалён boolean-аккумулятор, отражавший только новые delegation.
Ретро-delegation прежних членов по-прежнему выполняется в том же порядке.

Отказ удостоверить target, неверный секрет и tombstone по-прежнему прекращают
ceremony. Refresh не переоткрывает узел или IPC. Формат token, сертификаты,
ACL, ratchet и формат контейнера не меняются; пароль для повтора не сохраняется.

## Сквозная проверка

`test/e2e/device_link_write_retry_e2e_test.dart` использует ту же приватную
storage-обёртку; новых product hooks или fault flags в `lib` нет.
На исправлении для обоих видов приглашения проверяются:

- публикация точного сохранённого документа источником до продолжения adoption;
- неизменные PID источника, identity и физический device ID целевого устройства;
- завершение обычных adoption/snapshot, перенос контрольной истории без дублей;
- новое сообщение B→C и ответ C, доставленный обоим устройствам X.

Ранний стенд не вкладывал документ в приглашение B, поэтому два его параметра
не доказывали два разных пути. Усиленный guard обнаружил ошибку. Эти ранние
серии не учитываются как квалификация двух вариантов. Отдельный некорректный
документ также был отклонён штатной crypto-проверкой; его отказ не считался
дефектом продукта. Red и green с корректным подписанным документом учитываются
отдельно.

**Зачтённый результат:** корректный red — 2 ожидаемых падения на публикации;
финальный native green — **2 passed, 0 skipped**. **108 unit/widget-проверок**
экрана устройств, token/invite, материала личности, credential-проводки и
авторизации прошли на тех же production и unit sources. Позднее менялись
только native fixtures и их предусловия, отдельно квалифицированные финальным
native-прогоном. Targeted analyze и `git diff --check` проходят.

Во время финального native-запуска 1562 выбранных source inputs и три native
библиотеки/CLI не менялись. После teardown подтверждены выход 15 учтённых
процессов/групп, освобождение 14 зарегистрированных портов и отсутствие test VM.
Синтетические контейнеры удалены. Остальные серии очищены независимо.

## Границы

macOS arm64, JIT, CLI/SDK `e963fbdb`, локальная hidden-volume `293792d`.
Это потеря завершения после настоящего storage API, не аппаратный сбой диска.
Сценарий выполняется через debug caller; симметричная UI-правка проверяется
review diff, анализатором и существующими widget-проверками экрана устройств.
GUI-нажатие на реальном телефоне этим прогоном не квалифицируется.

Другие окна crash во время link/adoption, часы/сутки offline и вся multi-device
матрица остаются отдельными проверками. Установленный пользовательский релиз
не заменяется; push и нового выпуска в этом цикле нет.
