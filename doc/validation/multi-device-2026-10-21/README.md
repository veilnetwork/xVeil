## Стенд и границы доказательства

A/B — одна личность X; C — другая Y. Дополнительно проверялись C/D личности Y
и A/B/E личности X. Использованы настоящие native-узлы Veil, зашифрованные
контейнеры, production providers/services xVeil и изолированный остров из трёх
relay-процессов. Готовая тестовая личность экономит PoW; ключи этих fixtures
публичные и разрешены только на loopback-острове. Публичные seeds и meeting
points отключены. Физический телефон и установленное пользовательское приложение
в этом аудите не менялись.

Основные проверки отзыва ключей, аварийного завершения и гонки ответов также
выполнены с **отдельным OS-процессом на устройство**. Native registry и
SharedPreferences между ними не общие. Положительные проверки revoke из общего
процесса не выдаются за доказательство межустройственной безопасности.

Это проверки доставки и native media packets, **не оценка разборчивости живой
речи, громкости наушников или качества изображения на физических устройствах**.
Обрыв процесса не выдаётся за настоящий сетевой split-brain. Пятиминутное offline
не выдаётся за час/сутки/дни; короткий TTL не выдаётся за замер 5/10 минут.

## Дефекты, обнаруженные исходным прогоном

| ID | Сценарий и факт | Доказательство |
| --- | --- | --- |
| MD21-01 | **Revoke не закрывает прогретый сеанс.** При online C, уже принимавшем доказанный B→C до revoke, старый B после отзыва снова инициировал звонок и передал текст. Зафиксировано через 2049/2054 ms от попытки в минутном окне. Cold/offline C вариант прошёл. | `process-recovery.log`, второй тест; пункты 26/28. |
| MD21-02 | **Гонка ответов оставляет два active endpoint X.** A/B одновременно приняли один call ID, оба оставались active >30–40s. В независимых процессах A rx=874, B rx=0, C rx=428. Ранее тот же тест мог проходить. | `campaign.log`, `process-recovery.log`; пункт 40. |
| MD21-03 | **Создание группы до первого sibling падает.** `createGroup` при A/C online и ещё не привязанном B завершается `mailbox_seal … PeerUnresolved` на epoch envelope. Воспроизведено дважды, включая финальный SDK. Поздний перенос группы заблокирован этим шагом. | `campaign.log`, `failure-confirmation.log`; 52/53. |
| MD21-04 | **Пропадает ответ D→X при A/D online и B/C offline.** A→Y приходит на D; обратное сообщение не появляется на A за 180s в двух прогонах. Видны authenticated `peer_cannot_open`, повторные re-key и claimed-drop. Точное расхождение recipient instance/ключа ещё не устранено. | `supplementary.log`, `failure-confirmation.log`; 45. |
| MD21-05 | **Звонок между двумя парами устройств нестабилен.** A вызывает Y, отвечает D: первый прогон не получил двустороннее native media за 30s, повтор на том же production-коде прошёл целиком за 57s. Успешный повтор не закрывает дефект. | `supplementary.log`, `two-identity-call-confirmation.log`; 46 FLAKY. |

Отдельное наблюдение: B, пропустившее удаление всей X из группы, **сохраняет старый
список участников более 120s**. Проверка доступа к новым данным прошла: эпоха и
commitment изменились, оставшееся D читает новый текст, B его не получает в
20s наблюдении. Старое B локально принимало свой post, но C не показало его.
Последний факт не сертифицирует все способы обхода групповой авторизации.

После неуспешной гонки ответов общий процесс также выдал позднюю ошибку
`storage is locked` при teardown heartbeat. Она сохранена в журнале как вторичная
ошибка остановки; отдельно как crash обычного приложения не воспроизводилась.

## Что прошло на стенде

- Входящий C→X звонит A/B; ответ A или B соединяется с C и убирает соседний ring.
  B отвечает без заранее готового B↔C session. Отказ любого X завершает весь вызов.
- Входящие и исходящие тексты зеркалируются один раз; прежняя A↔C история приходит
  на новое B, в том числе при независимых процессах.
- После **300 реальных секунд offline B** история пришла при C offline/A online.
- В backlog из 100 сообщений B остановлено на **41/100**. После reconnect и
  одновременной новой отправки все **101 ID и порядок** совпали на A/B/C.
  Offline вместе с восстановлением заняло **83 793 ms**.
- Read markers в обоих направлениях, реакции/отмена, edit, reply target,
  forwarding attribution, pin, alias/archive/mute/block и persistence выбранных
  prefs после restart B. Конфликт sibling delete/edit сошёлся, включая restart.
- PNG 68 B, файл 150 KiB и 4 MiB сверены побайтно. B получает файл от A при offline
  C, отдельно от единственного C при offline A; ранее загруженный кеш B переживает
  выключение A/C и restart B. Удаление только кеша B не стирает копии A/C.
- SIGKILL отправителя около завершения send не потерял проверенную запись;
  последующая доставка, восстановление B и новый ratchet traffic прошли.
- Reconnect B во время ring работает; после ответа A повторного ring не было
  за 15s. Исчезновение A в соединённом вызове завершило его на C по liveness;
  B не держало orphan live-call.
- Одно сообщение X=A+B → Y=C+D пришло всем четырём; C→X пришло всем A/B/E.
- После удаления X из группы оставшиеся C/D продолжают обмен на новой эпохе,
  вернувшееся B не получает новый текст в проверенном окне.

**Согласованный LIMIT #10:** при выключенных A и C и одном online B исходящее
не появляется за 180s; при возврате A приходит ровно один раз. Mailbox для
копий своим устройствам не добавлялся. Это не объявлено новым дефектом.
`mailbox_seal` в ошибке группы — имя криптографического seal-примитива, само по
себе оно не доказывает использование mailbox для сигнализации звонков.

## Ещё не покрыто полностью

Часы/сутки/дни offline и длительный TTL; первая привязка при offline source;
первый send C со старым списком до нового контакта с A; новая установка после
revoke с новым ID; настоящее сетевое разделение с параллельными действиями;
5–10 устройств; очень большие файлы и обрыв скачивания ровно на 50%; все
комбинации ротации групповых ключей; независимый clock skew; принудительный
packet replay через разные пути; crash на каждой границе receive/decrypt/DB/ACK
и при file/link/revoke. Нужны отдельные прогоны; они не помечены PASS.
