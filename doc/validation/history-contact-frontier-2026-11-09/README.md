# История: совместное ожидание одного незавершённого чтения контакта

При параллельном применении истории несколько callers запрашивают одну
контактную запись до завершения первого storage RPC. Они создавали отдельные
команды worker, хотя между ними не было другой команды хранилищу.

Теперь `getContact` может разделить **только незавершённое** чтение одного
контакта. Worker предоставляет монотонный номер принятой команды. Для
повторного использования должны совпасть конкретный store, peer и номер
очереди. После исходного `get` номер должен увеличиться ровно на один: proxy,
поставивший ещё одну команду, не получает право разделить старое наблюдение.
Любая последующая команда, включая обычное чтение, завершает это окно.

В памяти не кешируются завершённая запись, consent-решение или ошибка.
Pending очищается до возврата результата caller. Каждый caller отдельно
декодирует контакт; входной NodeId копируется до async-границы. Запоздалое
завершение старого владельца не очищает flight нового контейнера. Store без
такого свидетельства сохраняет отдельные чтения. У multi-space worker
счётчик общий для всех пространств, а объект view остаётся частью проверки.

Проверки block/retention/TTL, roster/revoke, ratchet, durable publication,
checkpoint и порядок storage-команд не удалены. Это не долговременный кеш
авторизации и не перенос ACK до сохранения. Wire, native ABI и media pins
не менялись.

## Воспроизведение и безопасность

- Gated-регрессия на старом HVS: 32 одновременных вызова дали 32 чтения
  вместо одного; candidate даёт одно, с одинаковыми данными и разными
  возвращёнными объектами контакта.
- Отдельная проверка ставит block между двумя чтениями. Первое видит accepted,
  второе — blocked. Отрицательный контроль с удалением проверки frontier
  возвращает второму accepted и падает на проверке фактического статуса;
  исходный candidate затем восстановлен побайтно.
- Проверены барьер от любого другого запроса, разные peer, завершение/ошибка
  без кеша, повтор после ошибки, proxy с двумя командами, мутируемый NodeId,
  закрытие/смена владельца и одинаковый числовой frontier у разных store.
- Native: синхронное увеличение frontier у настоящего single-space worker;
  общий счётчик и изоляция двух личностей у настоящего multi-space worker.

Компонентный native A₁/B/A₂ использует один неизменный зашифрованный файл:
64 измеряемые волны по 16 callers после двух warmup-волн. Для одного контакта
RPC: **1024 → 64 → 1024**, медиана волны **982 → 197 → 597 мкс**.
Для 16 разных контактов — по 1024 RPC во всех фазах (медианы 783/696/547 мкс).
Проверены все возвращённые значения и SHA файла до/после каждой фазы.
Разброс контролей не позволяет объявлять универсальный коэффициент ускорения.

## Профиль большой истории

Архивная fixture теперь явно выбирает 32–3000 строк (default 512); и seed
worker, и контроллер используют одинаковые границы. Основной сценарий —
2000 строк у двух источников одной личности, одна прежняя строка у получателя,
четвёртое устройство другой личности. Все процессы и три Core изолированы
на loopback, реальные MessagingService/ratchet/контейнеры.

Первый большой прогон был функциональным контролем: storage census не был
запрошен контроллером, поэтому он **не зачтён как CPU-профиль**. Проводка
исправлена: opt-in census включает захват, окно сбрасывается перед release
apply, snapshots сохраняются отдельно от перезаписанного последнего boot.

Квалифицированный профиль получателя до candidate: 4232 main и 4427 worker CPU-сэмплов,
окно 18,243 с; закрытая FIFO-трасса — 14197 RPC и столько же worker handlers,
без trimming. Коммиты занимали 5,020 с времени handler; это не исключительное
время диска. Горячие product-стеки: `_readOwnDeviceAddresses`, `foldControlLog`,
`GroupService.load`, разбор device announcement/sync и bundle messages.

Добавлены test-only stage-события `ownDevices`, `historyApply`,
`historyEncode`, `historyPublish`, связанные с теми же VM-часами. Их ожидания
и CPU-попадания могут пересекаться: **сумма не является временем догрузки**.
Collector отбрасывает неизвестные стадии и произвольные поля. Stage-код
находится только в test support; обычный анонимный экспорт не расширялся.

## Полная native A/B/A

Во всех фазах одинаковые Dart/native байты; единственная переключаемая
возможность — передача queue witness test-адаптером. Это отдельные свежие
синтетические профили с одинаковым сценарием, а не один детерминированный
контейнер/расписание. CPU sampling отключён, одинаковый timeline включён;
интервал наблюдения 1000 мс. Gate удерживает оба полных authenticated ответа
до первого apply, его ожидание исключено из apply→convergence.

| Метрика | A₁: отдельные чтения | B: pending sharing | A₂: отдельные чтения |
|---|---:|---:|---:|
| Чтения контактов в окне census | 3260 | 1394 | 3255 |
| Все get RPC в окне census | 6908 | 5027 | 6814 |
| Вызовы historyApply | 4002 | 4002 | 4002 |
| Коммиты сообщений / cursor | 125 / 66 | 125 / 66 | 125 / 66 |
| Apply release → сходимость, мс | 12316 | 12343 | 12093 |
| Encode release → сходимость, мс | 12818 | 12783 | 12531 |
| Все RPC закрытой boot-трассы | 14249 | 12330 | 14025 |

Окна census и полной boot-трассы различаются, их счётчики не подменяют друг
друга. Чтений контактов меньше примерно на 57% в этом сценарии; полного
ускорения догрузки **не доказано**. 125 message-коммитов, 66 cursor-коммитов,
32 durable allocator reservation и остальные security-записи не объединялись
ценой ослабления подтверждения/публикации.

Каждый прогон сверил все 2000 архивных + прежнюю строку: точные ID, тела,
delivered, canonical positions, порядок, отсутствие дублей/посторонних строк,
завершение обоих source cursors. Cold boot без A/E/C сохранил все 2001 строку.
Равенство двух неполных историй не считается успехом.

## Аварийное восстановление

На финальном candidate B получил два полных authenticated ответа A/E,
но первый apply удерживается: архивных строк 0. SIGKILL B (exit −9),
A/E/C offline. Первый boot без сети сохранил прежнюю строку, архивных 0.
Вернулся только A: **все 2000 архивных + 1 прежняя строка** сошлись за
22,856 с от начала `start(A)`; следующий cold boot без A/E/C сохранил все
2001 строку. Точные ID/тела/delivered/positions/порядок совпали, дублей нет.
Это один дополнительный crash-момент, не вся crash-consistency матрица и
не сравнение времени с normal A/B/A.

## Проверки и границы

Финальная серия: **241 related tests passed, 0 skipped**, включая
контактные frontier-гонки, own history/TTL/block/revoke, multi-space,
worker close/death, census/timeline, границы архива, private wire/gates,
три native frontier/A/B/A теста, snapshot admission/expiry и проверку
Flutter-free headless dependency closure. Полный analyzer и diff checks чисты.
Три normal native A/B/A и один native SIGKILL сценарий — **4 passed**,
без skipped; они учитываются отдельно от component-тестов.

Проверены 1524 frozen frontend/test/dependency inputs в каждой A/B/A-фазе,
одинаковые между фазами. Использована проверенная CLI/FFI-пара Veil 0.11.48
с `allow-empty-seeds` и опубликованная HVS 2.7.0, SHA и OS mappings сверены.
Текущий SDK дополнительно содержит Windows-only VPN-helper правку; Mac
runtime в данном source delta не изменён. Новых Rust-сборок нет.

Cleanup A₁/B/A₂/crash проверил соответственно **43/43/48/51 PID** и
**70/69/68/89 портов**: своих живых процессов/listeners нет, временные
runtime-контейнеры удалены. Frozen inputs, native SHA и чистота SDK/HVS
проверены после каждого запуска. Raw captures в коммит не включены.

**Большая догрузка и NETCALL-01 остаются открытыми.** Следующий участок
истории — повторные roster/group-journal обходы и цена durable публикации,
с обязательным сохранением свежих проверок отзыва/блокировки. Это Mac/JIT,
не Android/AOT/WAN и не полная multi-device матрица. Sibling mailbox не
включён. Телефон, реальные профили и production не менялись; push/релиза нет.
Raw IDs, тела, локальные пути, VM service и ключи находятся только в private
captures. Публичные агрегаты — [summary.json](summary.json).
