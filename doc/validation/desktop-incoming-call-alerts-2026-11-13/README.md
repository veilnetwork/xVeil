# Входящие звонки: системное уведомление desktop

## Вердикт

Пользователь Windows 10 сообщает, что входящий звонок не вызывает уведомление
или всплывающее окно. Видимость самого вызова внутри приложения пока неизвестна.
Отсутствие доставки сигнала этим сообщением не доказано.

Отдельно подтверждён пробел приложения: `CallLifecycleBridge` поддерживал
Android call notification, desktop-ringer и внутренний экран, но не публиковал
системное уведомление входящего desktop-звонка. Регрессионная проверка через
настоящий `CallService` воспроизвела ringing без кадров Flutter при нулевом
числе OS-post вместо одного. Это не проверка настоящей Windows notification UI.

## Изменение

В фоне прямой или групповой ringing публикует уведомление через существующий
`NotificationService`, с учётом включения уведомлений и режима preview.
В скрытом preview отсутствуют имя и идентификатор собеседника. Payload всегда
фиксированный `incoming-call`, без call ID, адреса или возможности ответить.
Клик показывает существующее окно; ответ остаётся явным действием пользователя.
Tray и notification activation используют общий guard show/focus, сохраняющий
защиту от наблюдавшегося macOS crash при перекрывающихся показах окна.

Окончание вызова, возврат приложения на экран, смена личности и выключение
уведомлений снимают alert. Постановка и снятие упорядочены; завершившийся поздно
старый post не удаляет alert следующего звонка. Перед post повторно проверяется
конкретный сервис, call ID, startedAt и поколение запроса.

Найдены и исправлены две дополнительные ошибки готовности backend:

- `initialize(false)` больше не считается успешной инициализацией.
- Барьер готовности включает отложенный startup-clear и уже выполняющийся
  native clear. Новый звонок не публикуется посреди этой очистки.

Анонимный отчёт сохраняет последний числовой исход `callAlert` даже после
завершения звонка и вытеснения обычного кольца сетевыми событиями. Снятие записано
отдельно; имена, call ID и исходные исключения в эти события не передаются.
Успешный post означает приём вызова plugin API, а не доказанную видимость баннера
при любых настройках Windows, Focus Assist или разрешениях ОС.

## Проверки и границы

- 127 выбранных Flutter-проверок прошли без skips: call notification actions,
  startup, policy, opaque payloads, reply ownership, post races, tray, window
  activation и диагностические allowlist/retention.
- Отдельный Python-верификатор диагностического artifact: 1 PASS.
- Focused analyzer: 11 файлов, замечаний нет.
- Тесты readiness используют completer gates, не временные пороги.
- Mock native window channel проверяет restore → show → focus и защиту от
  перекрывающихся запросов. Настоящее окно этим тестом не открывается.
- Прямой backend проверен настоящим `CallService`; групповой alert — через
  подменённый источник событий, не сквозным групповым сетевым звонком.

Доступная Windows 11 отвечает по SSH, приложение там не запущено. Физическая
проверка нового alert в этом раунде не выполнялась. Исходная Windows 10,
отдельный отказ камеры и доставка сигнала остаются непроверенными. Native media,
Android call-service, транспорт, релизные теги и production-сиды не менялись.

Изменение локальное: не входит в опубликованный 0.13.101. Stand-приложения
этого раунда не запускались; процессы после физического теста останавливать
не требовалось.

Продолжение: [ограниченные повторы после отказа native post](../desktop-call-post-retry-2026-11-16/README.md).
Исправлена потеря alert после первой неудачи, добавлен mock close-to-tray/call
контроль. Настоящая видимость уведомления Windows 10 остаётся непроверенной.
