## R31-01: граница авторизации

Тесты удерживают настоящий DHT-ответ сертификата после получения проверенного
документа, принимают более новый подписанный документ с отзывом, затем отпускают
старый ответ. Используются реальные pending-query, registry, подписи и resolver;
нет порогов времени. На прежнем коде оба негативных сценария возвращают
сертификат отозванного устройства. После правки оба возвращают `None`, ключи не
публикуются в RAM-кэши, pending-запросы освобождены. Два положительных контроля
отзыва *другого* устройства сохраняют пригодный сертификат.

Первый запуск новых node-тестов использовал неверное число ожидаемых запросов
и не является доказательством дефекта. Зачтённый red выполнен с исправленным
fixture при удалённых только двух production-гейтах: **0 passed / 2 failed**,
обе ошибки именно на возврате отозванного сертификата. После восстановления
гейтов — **14 passed** в наборе `revocation`.

Повторяется существующая family-политика. Не меняются подписи, ratchet,
durable host checkpoint, monotone floor или правила partition. Финальная
проверка не делает отзыв мгновенно известным ещё изолированному узлу. Хранилище
сырых проверенных cert-кандидатов само по себе не авторизует seal: возвращаемый
сертификат и повторное использование материала подчиняются current floor.

## R31-04: независимые обязательства

Красный тест: локальное изменение сохранено, mirror выбрасывает `StateError`,
а Outbox не содержит правки. После исправления в Outbox ровно один правильный
peer-edit, и он переживает закрытие/повторное открытие контейнера. Ошибка mirror
по-прежнему возвращается, успешная публикация не выдумывается.

Первый вариант peer-first обнаружил симметричный край: отказ enqueue мешал
mirror. Дополнительный red зафиксировал отсутствие вызова mirror. Финальный
код предпринимает оба эффекта и сохраняет первую ошибку. Схема хранения,
ID операций и конфликтное разрешение правок не изменены. Входящие edit ACK
по-прежнему ждут требуемой durable-публикации. Автоматический retry именно
отказавшего device-journal edit этим изменением не добавлен: его ошибка явная,
а не ложно объявленный успех.

## R31-05: повторы без лишних reconnect

Таймеры проверены на виртуальных часах: временный отказ → успех без OS-события;
постоянный отказ → ограниченный backoff и ровно один timer; dispose → ноль
таймеров; новое attachment отменяет старое ожидание. Provider-тест с двумя
личностями проверяет частичный отказ: успешная личность не получает повтор,
неудачная получает. Wi-Fi → mobile → Wi-Fi создаёт новое поколение и повторно
уведомляет обе личности, даже если итоговая категория совпала с прежней.

Это исправление потерянного retry, не физическое доказательство устранения
12–20-с паузы звука NETCALL-01 или холодной задержки NETLINE-01.

- Proto **843 passed**, routing **125 passed**, onion-stream **116 passed**.
- Отдельно `walk_` с `production-seeds`: **19 passed** (повторная feature-

- Анализ четырёх изменённых Dart-файлов: **No issues found**. Форматирование
  трёх изменённых Rust-файлов и `git diff --check` прошли. Общий fmt-check
  дополнительно указывает на прежний порядок двух module declarations в
  неизменённом `veil-routing/src/lib.rs`; этот несвязанный файл не менялся.
- Первые ошибки fixture/компиляции новых тестов и ошибочный Python import-path
  не засчитаны ни как red, ни как green. Зачтённые отрицательные проверки
  воспроизводят конкретные неверные результаты; итоговые проверки успешны.
- Rust использовал отдельный внешний target с проверкой файловой системы и
  watchdog остановки при потере mount. Stand-приложения в этом цикле не
  запускались; production-реле, телефон и Windows не менялись. hidden-volume
  остался без правок. Сырые журналы остаются приватными.

Проверка R31 не закрывает холодный OVL1/NETLINE, мобильный handover, слышимость
звука или миграцию большой истории. Физическая квалификация новых R31-изменений
не проводилась; результаты выше относятся к указанным тестам.
