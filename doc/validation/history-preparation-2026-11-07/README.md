# Параллельная подготовка истории с упорядоченной публикацией

Агрегаты: [summary.json](summary.json). База — `d646f2d5`,
[предыдущая серия](../history-page-slices-2026-11-07/README.md).

## Подтверждённое последовательное ожидание

Подготовка очередной записи ждала предыдущую даже до её write boundary.
Это сериализовало fresh roster reads и другие независимые чтения внутри
страницы. Gate-тест удерживает первую подготовку: база запускает **одну**,
candidate — **четыре**, при этом **ни одной публикации** до освобождения
барьера нет. Baseline assertion-red: 1 вместо ожидаемых 4.

Новая волна готовит до четырёх **различных, заранее валидированных ID**.
Результаты собираются в исходном порядке; durable-пачка остаётся не более
16 записей. Смешанные insert/ordering publications сохраняют порядок.
Проверки устройства перед каждой строкой и publication не убраны. Уже
существующее sharing только незавершённого roster lookup теперь может
обслуживать несколько подготовок; нового кэша прав/TTL нет.

Отмена помечает и ещё читающие строки: их поздний write boundary должен
бросить ошибку, а все начатые continuations — завершиться до возврата abort.
Иначе подготовка, ещё не достигшая boundary в момент отмены, ждала бы
publication promise, которую отменяющий код уже не увидит.

## Пойманная регрессия промежуточного кандидата

Первый параллельный вариант прошёл native A/B/C, но дополнительная проверка
**двух источников одной истории** нашла взаимную блокировку: одна страница
удерживает mirror slot первого сообщения, другая — второго, обе ждут
оставшийся slot до публикации. Этот вариант **не принят и не закоммичен**.
Тот же контроль на исходной последовательной базе проходит.

В окончательном коде страницы **одного разговора** применяются по очереди.
Внутри страницы сохраняются четыре подготовки; другие разговоры независимы.
После ожидания очереди заново проверяются binding, действующий pull и
принадлежность устройства. Ошибка одного turn отчётно завершается, но его
settled future не отравляет следующую страницу другого активного источника.
Это очередь только own-history apply; основной ingress/звонки/обычные
сообщения через неё не проходят. Wire, page/record/admission budgets,
ratchet, cursor и sibling-mailbox модель не менялись.

## Проверки

**103 related tests passed, skipped 0; analyzer/format/diff checks чисты.**
Семь новых регрессий покрывают:

- Четыре подготовки при удерживаемой первой и отсутствие ранней публикации.
- Отзыв устройства во время подготовки: ни записи, ни cursor advance.
- Ошибку подготовки и join позднего writer после abort.
- Готовую позднюю ordering correction: раньше неё durable-публикуется insert.
- Два источника с пересекающимися страницами без opposite-slot deadlock.
- Отзыв первого источника: второй получает свой turn и завершает историю.
- Отдельный разговор продолжает применяться при удерживаемой странице первого.

Пять mutations (нет late-abort guard, обратный порядок публикации, нет
исключения для пересекающихся страниц, глобальная очередь, poisoned tail)
дали **assertion-red без timeout**; исходники восстановлены побайтно.
Первая проба late-abort mutation завершила assertion-red, но её test cleanup
не покрывал все поздние строки и дошёл до timeout. Она не зачтена как чистая:
cleanup усилен, повтор завершился без зависания. Новый early publication-order
probe также сначала считал обратную reconciliation стенда; исправлена его
изоляция, production ради этого не менялся.

Header-read RPC — `ownDevices/kv.readLogBatch` в фиксированном census context,
не все RPC приложения и не сумма эксклюзивного wall time. В B/A2 совпали
объёмы apply/encode и число page replies; после reopen было по 637 строк.
Это более сопоставимая пара, чем A1 с обратной догрузкой. Измерение не является
побитово детерминированным: ключи/IDs, runtime state, caches и scheduling
различаются. Первый сетевой readiness, pure CPU и WAN-ускорение из таблицы
не выводятся. Путь ответа источника немного медленнее в B; выигрыш наблюдается
на последующем интервале у получателя. Догрузка остаётся активной задачей.

Сценарий каждой фазы: partial receive → настоящий SIGKILL B → остановка A/C →
boot inspection B **до создания сети** → возврат только A → полные 2000 →
снова offline источники → повторный boot inspection B. Все наблюдавшиеся
до kill ID, тела/delivered и уже canonical positions сохранены. Дополнительные
in-flight строки разрешены только из исходного полного набора; дублей нет.
Во всех трёх фазах **2000/2000** ID, тел, итоговых позиций/порядка и delivered
сошлись и сохранились при финальном старте до сети. Completed-history retries 0.

Два-source overlap — in-process protocol regression с fake transport/KV и
настоящими MessagingService/codec/mirror/cohort. Native A/B/C имеет только
один sibling-source на storage; реальная многопроцессная серия с двумя
одновременными источниками, мобильная сеть и AOT остаются для квалификации.
