# Повторное открытие контейнера: допуск, отметка и отмена

Продолжение [создания личности после startOver](../onboarding-maintenance-session-2026-11-11/README.md).

## Что подтвердилось

`reopenExistingContainer` сначала записывал onboarded-маркер, затем вызывал
публичный `unlock`. Занятый unlock возвращается без действий; оболочка при этом
могла вернуть true. Неверный пароль также сначала записывал маркер, а затем
удалял его, в том числе при наличии прежнего true. Отказ записи маркера мог
оставить готовую сессию с результатом false либо исключение с изменённым
SharedPreferences RAM-кэшем.

Lock/startOver/wipe во время opener или записи маркера не были согласованы
с этой оболочкой. Старое завершение могло объявить вход успешным либо снова
изменить phase после отмены. Первые **17 сценариев — 0 passed / 17 failed**
на прежнем контроллере, без ошибок компиляции.

## Исправление

Повторное открытие получает обычный unlock-допуск до первого await.
Непринятая попытка возвращает false и не меняет prefs. Успех теперь требует
реальной проверки пароля, сохранённого маркера и допустимой конечной phase.
Повреждённая identity-запись сохраняет прежний отдельный экран повреждения;
она не превращается в новую личность.

Приватный post-open callback сохраняет маркер после успешного open, до
публикации сессии. Неверный пароль не записывает и не удаляет маркер.
При отказе/исключении восстанавливается его точное прежнее значение, включая
отсутствие и явный false; учитывается опережающее изменение RAM-кэша
SharedPreferences. Неудачный rollback не объявляется сохранённым.

StartOver ждёт уже принятую запись маркера перед собственным удалением prefs.
Wipe ждёт весь принятый reopen, включая закрытие worker. Lock сразу отменяет
авторизацию: поздние результаты не меняют его phase. Успешно открытый пароль
может оставить маркер true после lock; startOver/wipe удаляют его после
завершения записи. Ошибка записи не публикует ready и закрывает handle.

## Дополнительные окна

- Из четырёх промежуточных profile-проверок два обычных результата уже
  сохраняли конечную phase; два поздних `CorruptIdentityRecord` возвращали
  `identityDamaged` после lock/startOver. Они были красными на первом кандидате.
  Чтение и cleanup повреждения теперь проверяют lifecycle перед следующими
  действиями и публикацией phase.
- Уничтожение ProviderContainer при незавершённых open/profile оставляло
  принятый handle открытым. Два теста отвергли промежуточный кандидат;
  cleanup использует захваченное хранилище, без чтения уничтоженного provider.
  Первый запуск этих тестов не компилировался из-за отсутствующего в
  закреплённой Riverpod getter; это ошибка fixture, не красное воспроизведение.
  После исправления fixture оба сценария действительно упали по открытому
  handle, затем прошли с правкой.

В native-файле `test/native/onboarding_maintenance_lifecycle_test.dart`
сохранены два прежних create-контроля и добавлены три reopen-контроля:

1. Native-worker уже открыл существующее пространство под exclusive flock;
   ответ ещё не принят фасадом. Lock отменяет попытку, Future возвращает false,

3. Без отмены повторное открытие возвращает true, phase ready и маркер true;

## Границы и очистка

Исходная потеря доступа сразу обоими паролями после сжатия остаётся
невоспроизведённой. Текущий результат не объявлен её причиной или полной
Android/crash/multi-device квалификацией. Полная master/all-online матрица
остаётся отдельной проверкой; это не утверждение о дефекте всех этих путей.

Телефон, пользовательские контейнеры и production-реле не использовались.
Тестовые handles/processes завершены, собственные временные контейнеры удалены;
приватные журналы вне репозитория. Push и публикации нет.
