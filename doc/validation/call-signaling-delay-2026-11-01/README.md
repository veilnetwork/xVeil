# NETCALL-01: ожидание сигналов и запуск медиа — разные интервалы

Дата: 2026-11-01. Продолжение [предыдущего цикла](../registry-retirement-2026-11-01/README.md).
**Дефект остаётся открытым.** Уточнена локализация задержки нового вызова после
Wi-Fi → cellular и исправлена потеря этапов звонка в диагностическом отчёте.
Нового SDK-исправления, push или релиза в этом цикле нет.

## Разложение прежнего запуска

В сохранённой серии предыдущего цикла Windows получила входящий за 1,085 с,
но после принятия телефон ещё оставался в `dialing`: последний такой срез —
через 16,557 с после ответа, первый `connecting/active` — через 17,614 с.
Первый свежий RX на телефоне наблюдался примерно через 1,052 с после первого
наблюдаемого перехода в connecting. Поэтому прежние ~20 с до RX нельзя считать
20 секундами запуска аудиодвижка.

Для того же call ID журнал телефона содержит входящий `answer` с
`receipt_age=16877 ms`, `queue=0 ms`, `handler=4 ms`. Возраст использует часы
двух устройств и сам по себе не является калиброванным сетевым RTT. Наблюдаемое
ожидание dialing посчитано по одной монотонной шкале сборщика.

Быстрые повторы ответа на Windows реально запускались примерно через
0,264 / 0,744 / 1,728 / 3,708 с после принятия. Двухсекундный предел backoff
присутствует в исходниках Windows-стенда; версия «здесь ещё старая длинная
лестница повторов» не подтверждается. Native-исходы `source_accepted` означают
приём локальной очередью, а не доставку ответа. Совпавшие по времени медленные
`relay_device_fanout` не приписываются ответу без связи между операциями.

## Одинаковая SDK на обоих концах

На Windows 11 собрана SDK `8eab7507` из проверенного экспорта 1508 файлов.
Использован отдельный source/target, production Windows-набор фич builder:
`node-embedded`, `production-seeds`, `tls-boring`, без packet-tunnel.
После завершения сборки отдельно подтверждён exit code Cargo 0. Промежуточный
offline-запуск остановился из-за отсутствующей зависимости и успехом не считался.
Обёртка первого online-запуска ждала дочерние процессы после завершения Cargo;
финальный статус проверен непосредственным повторным вызовом Cargo.

DLL x64 загружена, SHA-256 ABI smoke прошёл, набор 197 экспортов `veil_*`
совпадает с прежней DLL. CLI version smoke также прошёл. Затем проверены SHA
фактически загруженного приложением модуля и неизменность runner/AOT/остальных
DLL. Это сборочная и физическая квалификация; полный Windows Rust suite здесь
не выполнялся. Windows 10 этим стендом не проверена.

Poco использовал ту же SDK `8eab7507`. Оба frontend AOT заморожены для изоляции
native-изменения; новая правка диагностического журнала в эти приложения ещё
не включена. Наличие файлов исходников само по себе не использовалось вместо
проверки выбранных бинарников.

## Два физических сценария

| Сценарий | Наблюдение |
|---|---|
| Новый вызов сразу после Wi-Fi cut | Входящий на Windows за 16,652 с после place. Ответ пришёл быстро; первый sampled connecting/active телефона — через 1,022 с после callee accept. Первый свежий RX — ещё примерно через 1,038 с после этой выборки. |
| Смена сети внутри активного P2P-звонка | Перед cut четыре подряд свежих P2P/RX-среза обоих концов. После cut по 40 срезов за 41,58/41,59 с, один active call сохранён. Максимальный sampled native age 10,288/13,507 с. На последнем срезе телефон не прошёл fresh-RX guard, Windows прошла. |

Первый сценарий снова подтверждает длинную доставку call-control, теперь
на участке приглашения, а не ответа. В журнале Windows у того же `offer`:
`receipt_age=16660 ms`, `queue=0 ms`, `handler=1 ms`; у ответа на телефоне —
`receipt_age=260 ms`, `queue=0 ms`, `handler=2 ms`. Эти межхостовые возраста
приведены как журнальные поля, не как точная разбивка сетевой задержки.

Второй сценарий квалифицировал сохранение состояния звонка, **не непрерывный
звук**. Возраст относится к отдельному media epoch и не ограничивает весь
перерыв; подмена его верхней границей паузы запрещена анализатором. Слышимость
речи, громкость и оригинальное условие ровно одного активного узла не проверены.
Переход default network на cellular и QA foreground проверены отдельно.
Маршруты не фиксировались, A/B нет: ускорение или регрессия от SDK не заявлены.

## Диагностический дефект и проверки

Частые транспортные события вытесняли `callState` из основного кольца до
копирования отчёта в Settings. Это лишало отчёт способа отличить ожидание
ответа от активного медиа. Красный regression воспроизвёл потерю трёх этапов.
Теперь отдельно сохраняются последние 12 таких событий за процесс: только
enum/числа и монотонные смещения, без call ID, peer, имён, адресов, путей,
содержимого или сырых журналов. Экспорт — копии, `clear` удаляет историю,
без opt-in диагностики история не создаётся. Автоматической отправки нет.

- 17 journal-тестов и 27 связанных diagnostic/error-report тестов прошли.
- Flutter analyze затронутых Dart-файлов: без замечаний.
- 14 тестов нового анализатора setup и 8 существующего handover прошли.
- AOT-проверка journal с включённым и выключенным diagnostic-флагом прошла,
  включая новый хвост этапов и privacy canaries.

Новый анализатор не засчитывает пустые списки, чужой/исчезнувший звонок,
застывшие счётчики, нулевой RX, пропуски наблюдений или менее пяти свежих
конечных срезов. `sampledSetupQualified` означает наблюдаемое завершение setup,
не прохождение требования к задержке и не слышимость. Ошибка входного файла
не печатает его путь или содержимое. Рядом сохранены только агрегаты:
[предыдущий setup](previous-setup.json), [текущий setup](paired-setup.json),
[активный handover](paired-handover.json).

## Остаток и завершение

Следующая граница — прохождение конкретного call-control от source admission
до удалённого callback и фактическое применение OS network-change к живым
сессиям. Отсутствие `ipc.mobile.network_changed` в console capture не доказывает
отсутствие уведомления: полнота этого info-канала не квалифицирована.
В ходе чтения reload-пути не найдено замены registry/force-reconnect Notify,
которая сама подтверждала бы гипотезу об устаревших Arc у mobile sink.

Оба запущенных QA остановлены. Телефонный QA APK восстановлен с проверкой SHA;
Wi-Fi/mobile/stay-awake возвращены, PID основного приложения не изменился.
Windows DLL восстановлена по SHA, остальные DLL/AOT/runner неизменны.
Задачи сборки и QA, собственные logcat, ADB-forward и SSH-туннель закрыты.
Первый listener-check cleanup не прошёл; независимая проверка явным обходом
IPEndPoint и Get-NetTCPConnection подтвердила отсутствие listener, повторный
postflight проверил отсутствие QA-процесса и восстановленную DLL.
Реле в этом цикле не изменялись. Приватные захваты не входят в репозиторий
и не называются анонимными отчётами.
