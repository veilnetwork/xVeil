# Встречная выдача: повтор только ещё недоступных prefix hints

## Подтверждённый дефект и исправление

После первой обычной страницы клиент отбрасывал все сведения о собственном
уже имеющемся префиксе. Если источник параллельно наполнялся, он не мог
подтвердить ставшую подходящей подсказку в следующем запросе; владелец полного
архива повторно получал свои строки из догружающегося sibling.

Новый optional `prefixPending` — битовая маска максимум восьми предложенных
в конкретном запросе hints. Источник отмечает лишь те, для которых пока
недостаёт строк до соответствующего endpoint. Если строк достаточно, mismatch
не сохраняется для повторного digest-сравнения на следующих страницах.
При count больше всего snapshot отсутствует даже обход строк; иначе в буфер сравнения отбирается
не больше count+1 подходящих строк, а digest нужен лишь при точном count.

Клиент сохраняет только указанные уже предложенные hints в текущем pull.
Позиции позади cursor отфильтровывает существующий request builder; окончание
разговора очищает остаток. Нет новых кандидатов из ответа и нет сохранения
hints на диск. Нулевой/отсутствующий/неправильный mask, в том числе лишние биты,
оставляет прежний plain-page путь. Старый peer может игнорировать optional
поле; без него клиент ведёт себя как раньше.

Mask — только планирование повторной проверки. Он не разрешает применение,
ACK или jump: источник должен подтвердить один предложенный префикс, получатель
заново сравнить свой текущий snapshot, пройти current-device/binding gates и
сохранить durable checkpoint. Все прежние ratchet/visibility/erasure барьеры,
page/reassembly/admission пределы и один outstanding request на sibling сохранены.
Sibling mailbox не включён.

## Управляемый контроль и регрессии

Получатель заранее имеет 1024 сообщения плюс поздний tail. Источник начинает
с 32+tail и увеличивает непрерывный prefix по номеру запроса, без ожиданий по
времени. В первом ответе 128-row hint ещё недоступен, во втором уже пригоден.
Прежний код делает **17 page-запросов**, новый — **2**; точный полный набор
получателя, тела/delivered/canonical positions сохранены. Обратный pull в этой
пробе выключен для изоляции; она не доказывает сходимость всех устройств.

Проверены local/source edits, rejected hints с endpoint ещё впереди cursor,
revoke во время свежего recheck и отказ сохранить prefix checkpoint. Последние
два оставляют старый durable cursor; local mismatch запрашивает plain page
от прежней позиции, source mismatch не подтверждает skip. Полный изменённый
источник больше не получает те же отвергнутые hints на каждой странице.

Mask-пробы включают отсутствие, 0, отрицательное, строку, bool, дробное,
несуществующий бит с установленным младшим, общий overflow и допустимые
один/два бита. Сохраняются только соответствующие уже предложенные кандидаты;
сам mask не продвигает cursor дальше последнего проверенного события.

Old-code control: **3 assertion-red**, включая 17 запросов вместо двух.
Простой unbounded-retention прототип предыдущего раунда: **2 assertion-red**
на повторной передаче отвергнутого hint и обработке mask. Эти контроли не
считаются проблемами сборки или skipped-проверками.

**245 related passed / 0 skipped**, включая **16 native HVS**, analyzer чист.
После замечания о null-aware синтаксисе фикстуры отдельно повторены все 17
новых проверок. Семантика и production-код финальной серии не менялись.

## Native A/B/A на 10 000 сообщений

A/B/E — одна личность, C — другая; четыре независимых Mac/JIT процесса,
три изолированных Core. Источники A/E заранее имеют полные одинаковые архивы.
Оба первых authenticated ответа получены до release первого apply. Setup
seed по 16 и искусственные gates вне apply-window; publication limit 64,
page limit 64/128 КиБ одинаковы во всех фазах. VM sampling/timeline выключены,
наблюдение раз в 1000 мс.

Вариант различается одним production-файлом; остальные **1524 из 1525 frozen
inputs** одинаковы. CLI/FFI/HVS SHA и OS mappings проверены, Rust не собирался.
Во всех трёх сценариях полные 10000 архивных плюс одна прежняя строка совпали
по ID/телам/delivered/canonical positions/порядку, без дублей/пропусков; оба
проверяемых cursor завершены. Cold boot при offline A/E/C сохранил 10001 строку.

Все встречные запросы связаны по private ID с полными ответами на A либо E;
один ID не относится к обоим адресатам. Индексы 0..n-1 полны, provenance
аутентифицирован, capture/census не обрезаны. Наблюдались обе ветки встречной
выдачи, поэтому нельзя приписывать все ответы только A. В candidate hints
действительно сохраняются на следующих страницах.

В этой серии встречный объём меньше примерно в 5–6 раз. Это bytes
расшифрованных application frames, не весь трафик circuit/TCP/UDP и не
универсальный коэффициент для всех сетей. Родительские фазы различаются по
распределению встречных страниц; доказательство механизма отдельно даёт
управляемый 17→2 контроль.

**Общего ускорения догрузки не доказано.** Candidate на 0,92–0,93 с дольше
двух контролей при 1000-мс опросе. Такой серии недостаточно для атрибуции
разницы точнее интервала наблюдения или утверждения полной latency-квалификации.
Этот фикс устраняет лишнюю встречную выдачу, а оставшиеся ~35 с активны.
Перед выводом о более мелких изменениях времени нужен более точный момент
окончания apply/checkpoint, без тяжёлого частого опроса всей истории.

## Следующий измеренный участок

По 157 основных page replies каждого источника связаны с получением у B.
Исключены первый gate-crossing query/reply и интервал до следующего запроса:
156 наблюдений первой стадии, 155 межстраничных интервалов на источник.
Все часы — DateTime одного Mac.

В candidate query-at-source → full-reply-at-B: медианы **68,25 / 76,52 мс**
для A/E. Full-reply-at-B → next-page-query-at-source: **137,56 / 126,76 мс**.
Вторая стадия содержит очередь/apply/checkpoint B **и** подготовку, отправку
и доставку следующего запроса. Она не является CPU/disk-only замером; стадии
двух потоков пересекаются, их await-времена нельзя просто складывать.
Детальные p95/max/count есть в summary. Следующий разбор — page-cycle и
316 cursor commits, с сохранением fresh authorization и durable apply.

## Ресурсы и статус

Исправление runtime hook-port используется во всех фазах. Kernel cache
**92 → 92**, новых entries **0** в каждой фазе; свободное место около 150 ГиБ,
очистки кэша во время измерений не было. Это дополнительное подтверждение
устранения прежнего роста по одному большому kernel на случайный порт.

Cleanup: **38/36/37 PID**, **58/54/59 портов**; своих процессов/listeners нет,
runtime удалены, native artifacts не менялись, candidate восстановлен побайтно.
Новых SIGKILL/Android/AOT/WAN проверок нет; полная multi-device matrix и
NETCALL-01 не закрыты. Прежние отложенные жалобы не объявлены исправленными.
Телефон, пользовательские контейнеры и production не затронуты. Commit
unsigned/local, push и релиза нет. [summary.json](summary.json) содержит только
агрегаты, без machine paths, raw IDs/ключей/адресов/payloads.
