# Проверенный сертификат восстанавливает ключ до открытия первого кадра

2026-11-03. Продолжение [ранних claimed history-запросов](../history-inbound-stop-2026-11-03/README.md).

## Подтверждённый механизм

Кэш проверенных сертификатов и receive-key cache ограничены независимо.
Receive-key может исчезнуть при ещё доступном проверенном сертификате.
Dispatcher обновлял document floor перед ratchet.open, но точный локальный
сертификат sender-instance спрашивал только через warmer **после** unproven
open. Cached-ветка warmer синхронно восстанавливает receive-key. Однако текущий
кадр уже открыт, его message key израсходован, и он уже оценён как claimed.
Приложение правильно отказывает privileged history-кадру; подписанным
получается лишь следующий retry, хотя сеть для проверки ключа не требовалась.

Перед direct AppSendSealed и terminal Forward ratchet-open теперь передаётся
sender-instance из ограниченно разбираемого заголовка в revalidator. Он сначала
применяет current document floor. Если живого ключа именно этой instance нет,
использует существующий resolve_cert_for_instance_cached: проверенные кэши и
локальные DHT bytes, прежние полные проверки документа/сертификата и durable
floor. Само восстановление не ждёт сеть и не запускает cert-walk. Прежний bounded
background document-revalidator сохранён; после восстановления ключа он может
запуститься уже на первом кадре вместо следующего, с прежними budget/cooldown.
Наличие ключа другого sibling не подавляет восстановление нужной instance.

При cache miss действует прежний ограниченный async warmer после unproven
open. Истёкший/отозванный сертификат не восстанавливается, аутентификация
по заголовку не выдаётся. Ratchet по-прежнему должен открыть кадр под ключом,
который текущий сертификат связывает с отправителем. Claimed не повышается
в приложении и не передаётся как Signed без этого условия. Wire/ACK/mailbox/
таймеры и лимиты не менялись.

## Изолированная проверка порядка

Два теста проходят настоящие dispatch/decode/ratchet-open/endpoint paths:
прямой кадр от физического устройства другой sovereign identity и Forward
через посторонний relay. В receive-key cache изначально пусто. Callback
моделирует только write-through **уже проверенного** сертификата, когда ему
передана точная sender-instance, и проверяет эту привязку. Сам verifier этим
stub не заменяется в production; его реальные проверки покрывает runtime suite.

При старом порядке обе ветки дали Claimed вместо Signed: **0 passed / 2 failed**.
После передачи instance до open — **2 passed / 0 failed**. Для запуска red
введён только новый тип callback с optional instance и механический адаптер
старого вызова, передававший None; до изменения порядка runtime игнорировал
новый аргумент, как прежний callback. Это отдельная квалификация порядка,
не утверждение, что неизменённый старый API уже имел такой аргумент.

Самый первый тестовый запуск не зачтён: direct fixture не содержал session
registry с sovereign binding и открывал payload под неверным именем. После
исправления fixture красный отказ обеих веток — именно provenance, не ошибка
расшифровки/сборки/предусловий. Тесты не используют таймеры и сетевые модели.

## Native-квалификация малого сценария

A/B — одна личность, C — другая; отдельные Mac/JIT процессы. Три строки,
включая 160015 байт, записаны в живое encrypted storage A вне device journal.
При recovery C offline, A online. Затем B запускается без A/C и сохраняет все
ID/тела/порядок/source positions/status delivered; mirrors A 0 до/после,
дублей 0. Это не проверка получения новых данных при offline обоих источников.

| SDK / фаза | Первый authenticated page от probe B | Первый list-ответ от probe B | Первая строка после API ready | Все строки от запуска B |
| --- | ---: | ---: | ---: | ---: |
| `54277f42`, до (предыдущий цикл) | 6,882 с | 0,681 с | 7,211 с | 18,299 с |
| `b8647716`, кандидат | 0,929 с | 0,720 с | 1,143 с | 12,736 с |
| `54277f42`, контроль после | 0,845 с | 0,667 с | 0,620 с | 12,617 с |

В предыдущем контроле один page-request сначала пришёл claimed на +2,881 с,
потом signed +6,882 с. В новом кандидате все наблюдаемые запросы signed с
первой попытки, повтора page нет. Но новый старый контроль тоже быстрый:
**универсальное причинное ускорение не доказано**. Связность/маршруты и timing
cold caches различаются между процессами. Механизм cached-before-open
подтверждён отдельными двумя red/green тестами.

**Базы времени:** probe B включается до group bindings и `/health`; его `open`
не равен API ready. Интервалы native source_wait/handler — отдельные локальные
измерения. Поэтому столбцы нельзя вычитать друг из друга как одну шкалу;
численно меньшая «первая строка после ready» не означает появления строки
раньше сетевого page. В двух предшествующих отчётах исправлена неверная
подпись столбца ответа «после ready» на «от открытия probe B». Исходные
reply-route/shutdown отчёты эту базу указывали правильно.

В обоих новых малых прогонах заморожены одни и те же 1400 frontend/test/
dependency hashes и HV, native проверен по сохранённому SHA. Каждый стенд
закрыт, runtime удалён; проверка exit code дополнена actual oracle JSON и
All tests passed, а не принята сама по себе.

## 2000 реальных сообщений перед добавлением B

Новый прогон выполняет actual `/send_message` A→C 2000 раз, дожидается всех
2000 на C и durable delivered на A, затем добавляет B через штатный link.
Seed занял 131,685 с. Это отдельное время подготовки, не миграция.

Текущая SDK: **2000/2000** на B, те же ID, порядок и source positions,
все статусы delivered, sending/sent/failed 0. Invalid snapshots 0,
повторов B для уже доставленной истории 0. Первая полная согласованная
выборка — **35,885 с после возврата linkProcesses**; проверка каждые ~5 с,
поэтому это время наблюдения, а не миллисекундная точность внутренней
сходимости. На первой выборке +0,110 с уже было 22 сообщения: отсчёт не от
сканирования QR и не обязательно от самого первого принятого history-кадра.
Во всех полных выборках порядок/позиции совпали сразу, без поздней поправки.

Это Mac/JIT, актуальная SDK и реальное encrypted storage, не Android/AOT,
не prolonged offline и не crash-mid-sync (offlineScenarioExecuted=false).
Все A/B/C в этапе связывания online. Перенос с одновременно offline A/C
не заявлен; mailbox для своих устройств отключён по указанию владельца.

Пассивный B-census: 243 message-log commits и 703 other commits. Settings
затронуты в 622 commits; namespace-метрики inclusive и пересекаются с этими
же commits. 5172 KV gets и 1686 readLogBatch. Append completed 2001 — счётчик
всех разговоров, а не только 2000 проверяемых строк; duplicate append attempts
0 и failed 0. RPC/file/append await измерения **перекрываются**, их суммы нельзя
объявлять exclusive временем диска. Эти счётчики задают следующую точку
профилирования оставшегося I/O, но не доказывают необходимость убрать барьеры.

Большой стенд закрыт: 18 PID/22 порта проверены, runtime удалён, native/HV SHA,
1400 frontend/test/dependency hashes и чистота SDK сверены.

## Остаток и следующий гейт

Исправлен подтверждённый порядок восстановления **доступного локально**
сертификата до первого open. Полностью холодный сертификат, который ещё
нужно проверять в сети, по-прежнему не даёт права принимать claimed-кадры:
прежние bounded warm/retry механизмы сохраняются. Причину всех прежних
6-секундных пауз одним этим исправлением не объявляем доказанной.

Начальная миграция 2000 сообщений квалифицирована на актуальной native SDK,
но вся multi-device матрица не завершена. Следующий практический гейт —
аварийное завершение B **посреди** большой догрузки, продолжение после запуска
и точное совпадение истории/порядка/статусов без дублей. Этот сценарий в
записанных здесь прогонах не выполнялся. Длительный offline, partition/revoke
и device/platform combinations тоже остаются отдельными проверками.

Все изменения локальны; push, релиз и публичные сиды не затрагивались.
Relay mailbox для собственных устройств не добавлен.
