# Владение запросом после передачи sink в entry point загрузки

Продолжение [защиты auto-resume opener](../resume-opener-ownership-2026-10-30/README.md).
Обнаружена следующая граница: четыре публичных download entry points ожидали
storage/source discovery без собственного владельца. Отмена или clear могли
уже завершиться, новый запрос — сохранить новый путь, но старый callback затем
записывал прежний mode/path в реестр и продолжал запрашивать reoffer. Два
store entry points вдобавок очищали cancel latch только после первого await,
самостоятельно отменяя уже сделанную отмену. Это гонка подготовки, а не
доказанная причина старой остановки сети на «33%».

Каждая подготовка теперь получает RAM token до первого await. Отмена, clear,
новое явное действие и dispose инвалидируют token. Проверки вокруг ожиданий
останавливают устаревшую подготовку; write-chain проверяет владельца до чтения
реестра и перед формированием мутации. Уже выданный storage commit не пытаются
откатывать: последовательный cancel/new commit сохраняет прежний durable-порядок.
После потери владельца старый результат не продолжает следующую стадию, не
запрашивает reoffer и не сообщает ошибку от старого запроса как ошибку нового.
Автоматическая подготовка не вытесняет уже идущую явную подготовку.

RAM-запись назначения теперь хранит path и token владельца. Очистка старого
sink снимает только свою запись; строкового равенства путей недостаточно,
поскольку новое действие могло выбрать тот же путь. Обычные payload consumers
по-прежнему получают строковый path; добавленный token в реестр не записывается.
Close обёрнут в один сохранённый Future: повтор не вызывает close второй раз,
и ошибка закрытия не превращается при повторе в ложный успех. Ошибка cleanup
устаревшего sink не повреждает новое назначение. Запись активных preparation
слотов удаляется при выходе из setup call, destination token — вместе с RAM-path;
дополнительного реестра всей истории загрузок нет.

В основном diff обрамлены четыре существующих entry points и их await-границы.
Алгоритмы wire/ratchet, ACL, подписи, manifest/piece hashes, mailbox и приоритеты
реле не менялись. Синхронный request-reoffer остаётся синхронным; промежуточная
попытка завернуть его в Future-only helper не компилировалась и отброшена.
Схема durable registry и производственные retry/TTL лимиты не менялись.

## Воспроизведение

На исходном `0b3ee48a` storage.hasFile удерживался Completer до действия
пользователя. Затем проверялись реестр, число новых сетевых отправок и close
устаревшего plaintext sink. Матрица: четыре entry points × отмена / новый путь /
очистка реестра = 12 сценариев. **10 красных, 2 контроля зелёные**: обычная
отмена двух file entry points уже соблюдала старый cancel latch; store
entry points его сбрасывали слишком поздно. При замене store-запросом менялся
mode нового plaintext намерения; при file-замене возвращался старый path.
После исправления проходят все 12, без исходящих reoffer от старого запроса.
Это не двенадцать независимых сетевых дефектов.

Четыре дополнительных сценария выбирают в новом pending запросе тот же path:
обычный/any-source старый entry point × успешный/ошибочный close старого sink.
Старый close вызывается один раз, новый pending sink остаётся открытым, а
последующая отмена нового запроса возвращает правильный путь и закрывает его
один раз. Фикстуры используют HiddenVolumeStorage/FakeKvLogStore и offline
transport; реальных peer IDs или пользовательских файлов в них нет.

## Проверки и границы

Окончательный прогон: **124 теста** auto-resume, registry persistence и stream
transfer, без ignored/skipped; **3 native-storage регрессии**, без пропусков.
Native-набор из прошлого раунда повторён на окончательном коде с настоящими
hidden-volume контейнером и файловым sink, библиотека сверена по SHA-256; новую
Rust-библиотеку не собирали. Analyze семи затронутых файлов — без замечаний.
В изменённом stream-тесте также добавлены скобки в двух прежних lint местах,
без изменения поведения.

Один прежний тест parked native open ожидал started от результата, вернувшегося
после dispose. Теперь устаревшая подготовка возвращает существующий noOffer,
как и отменённые операции. Ожидание обновлено сознательно: дедлайн быстрого
shutdown 500 мс и проверка abort позднего stream сохранены, добавлена проверка
сохранности запроса на следующем service instance. Это не удалённая красная
проверка ресурса. Первый широкий прогон имел только это несовпадение результата;
окончательный прогон полностью зелёный.

Guard не отменяет уже выполняющийся backend Future и не заменяет per-stream
lifecycle. Проверки внутри работающих payload workers, запоздавшие side effects
самого backend до возврата await, local-export cancellation и UI-обработка
устаревшего результата требуют отдельной квалификации. Нельзя считать этим
раундом закрытыми все payload race conditions или весь случай «33%».
Production AOT, Android/Windows и реальные реле в этом раунде не запускались.
Тестовые группы процессов завершены, native-фикстуры удалены. GUI-стенд не
запускался. Коммит без подписи; push/релиза нет.
