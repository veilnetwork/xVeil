# Публикация готового входящего circuit без ожидания соседа

SDK `21fe5130`, после `201b14eb`. Локальная правка, без push, релиза или
обновления реле. Телефон в этом цикле не доступен по ADB; приложения Mac/Android
не запускались. Проверки ниже не являются физическим файловым прогоном.

## Подтверждённый механизм

`76d9db45` запускал все receive-feed уже открытого набора до подтверждений,
но сами подтверждения выполнялись последовательно. Production-подтверждение
включает probe, проверку актуальности first-hop session и публикацию объявления.
Поэтому второй уже готовый путь не мог опубликоваться, пока первый не ответит
или не исчерпает свой `CIRCUIT_CONFIRM_TIMEOUT` — 10 секунд. Несколько молчащих
предшественников складывали ожидания. Это отдельный барьер после исправленного
барьера запуска приёма.

Все feed по-прежнему запускаются первыми. Подтверждения затем опрашиваются
независимо, не более восьми одновременно (предел соответствует числу ad slots).
Даже большой локально закреплённый список не создаёт неограниченный набор probe.
Для обычного набора до восьми готовый кандидат может выполнить свою публикацию,
пока другой ожидает. Для большего набора действуют ограниченные волны.
Подготовка/open самих circuit до этого этапа остаётся последовательной.

Production-замыкание подтверждения не изменено: для каждого кандидата сохранены
probe и его deadline, проверка текущего поколения сессии, отказ от публикации
неподтверждённого/устаревшего handle и retirement/grace. Запросы не вынесены
в spawned tasks; отмена batch отменяет незавершённые confirmation futures.
Receive-feed имеют прежний собственный runtime lifetime — тест отмены не
выдаётся за проверку их полной очистки.

Результаты возвращаются в прежнем порядке входного набора; побочные действия
готового подтверждения выполняются независимо. Финальное объединение пула и
строка PINNED по-прежнему ждут завершения всего batch. Время PINNED нельзя
выдавать за время первой пригодной регистрации. C ABI, wire, подписи, ratchet,
правила mailbox и приоритеты реле не менялись; новых признаков медиа нет.
`futures` уже был в дереве зависимостей, теперь явно используется FFI-пакетом.

Под публикацией здесь понимается вызов прежнего production-публикатора после
подтверждения. Это не обещание, что есть свободный publisher slot или удалённый
узел уже прочитал DHT-объявление: эти проверки и механизмы не менялись.

## Проверки

| Проверка | Результат |
|---|---|
| Старое последовательное подтверждение + новый тест | 1 выполнен, 1 FAILED: список публикаций пуст вместо второго готового кандидата |
| Новый планировщик подтверждений | Второй публикуется при закрытом gate первого; после освобождения результата порядок batch остаётся прежним |
| Отмена oversized-набора | При удержанных futures запущено ровно 8, после drop batch активных подтверждений 0 |
| Production-feature FFI suite, без test-low-difficulty | 331 passed, 2 ignored |
| Circuit-fixture FFI suite, с test-low-difficulty только в тестовом профиле | 368 passed, 10 ignored |
| Clippy lib/tests с запретом warnings; fmt; whitespace | passed |
| Native macOS arm64 и Android arm64 | Собраны из чистого SDK `21fe5130`, release/production-seeds, без low-difficulty и native test hooks; SHA зафиксированы |

Красный тест наблюдает состояние после poll при явно закрытом gate. В нём
нет задержки сети, сравнения elapsed и порога производительности. Низкая PoW
и runtime/network fixtures ему не нужны: он выполняется с production features.
Первый ошибочно выбранный запуск с 0 тестов не засчитывался; зачтённый красный
запуск действительно выполнил и провалил один тест. Наборы features не
складываются как уникальное покрытие; ignored не считаются пройденными.

## Уточнение 120-секундного случая

Повторно прочитана сохранённая трасса Mac → новая личность Android из
[предыдущего прогона](../inbound-feed-barrier-2026-10-30/README.md).
Четыре медленных семейных отправки относились именно к новой личности:

| Путь | Family resolve, мс | Возвращено сертификатов |
|---|---:|---:|
| call_device_fanout | 5001 | 1 |
| relay_device_fanout | 9015 | 1 |
| relay_device_fanout | 9015 | 1 |
| relay_device_fanout | 9004 | 1 |

Следовательно, нельзя описывать эти четыре попытки как возврат пустого семейства
или отсутствие найденного сертификата. При этом `family_certificates=1` не
доказывает прохождение последующих guards и доставку, а `family_seal_ms=0` /
`family_admission_ms=0` не доказывают, что этап не выполнялся: времена округлены
до целых миллисекунд. В старых строках нет достаточного результата каждого
этапа, чтобы установить причину недоставки конкретного предложения.

Исправление публикации stream также не объявляется причиной/устранением этой
недоставки: предложение ещё не начинало скачивание, путь его доставки другой.
Исходное «33%», недостающий диапазон после reconnect и обрыв звонка около 25 с
не закрыты этим раундом. Пер-cell связь с relay `Missing` остаётся незавершённой.

## Гигиена

Rust target на внешней ФС проверяется перед сборкой и каждые 0,5 с. При потере
mount watchdog завершает только принадлежащую ему группу. Все выполненные
тестовые группы завершились; приложения/ADB forward в этом цикле не создавались.
Рабочие реле, QA APK и контейнеры не менялись. В публичном отчёте нет исходных
ID, адресов, секретов, сырых журналов или абсолютной временной шкалы.
