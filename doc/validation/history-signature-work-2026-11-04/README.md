# Повторная проверка подписей при догрузке истории

2026-11-04. Продолжение [проверки разреженного начала истории](../history-sparse-prefix-2026-11-04/README.md).
Модель multi-device остаётся live-only: mailbox собственных устройств не добавлен.

## Что показали замеры

Пассивный test-only census теперь отдельно измеряет завершённые
`markMessageStatus` и `adoptMessageOrdering`: число вызовов, inclusive await,
максимум, число изменений (`true`) и исключений. Возврат `false` не различает
no-op и внутренний отказ метода. Исключения пробрасываются;
сброс окна обрезает время уже начатого ожидания. Ни ID, ни текст сообщения,
ни путь, ни исходное исключение в эти поля не попадают.

Контроль на прежнем production-коде `f7dc0abe`, native Mac/JIT, 2000 сообщений,
SIGKILL B, возврат B без A/C и затем только A:

| Метод | Вызовы | Изменения | Inclusive await |
| --- | ---: | ---: | ---: |
| B: статус | 505 | 0 | 31 мс |
| A: статус после рестарта | 1069 | 0 | 111 мс |
| B: восстановление source ordering | 87 | 87 | 1747 мс |

Все 2000 ID, порядок, source positions и delivered сошлись; повторный запуск
B без источников сохранил историю. Полная сходимость после готовности API A —
56,328 с. Следовательно, проверка уже установленного delivered **не является
главным остаточным тормозом** этого прогона. Длительности вложенных методов
нельзя суммировать как независимое время диска.

Отдельная CPU-диагностика сохранила профили каждого завершённого boot до их
перезаписи следующим запуском worker. В recovery-окне B: 2575 main-isolate
сэмплов, из них 1154 включали `_messagesOfBundle`, 845 — `_validMessageFor`,
263 — `NativeGroupSigner.verifySovereign`. Это пересекающиеся inclusive стеки,
не доли независимого времени и не доказательство сетевой задержки.

Профилировочный прогон также сошёлся и сохранил все сообщения, но не выполнил
дополнительный oracle «после crash есть поздний хвост с provisional positions».
Его квалификатор вернул отказ. Как повтор sparse-сценария и точку сравнения
скорости он **не засчитан**.

## Изменение

У `NativeGroupSigner` появился ограниченный 512 записями кэш **только**
результата `verifySovereignSignature`: проверка подписи и соответствия
полного публичного ключа node ID. Этот native-предикат не читает часы,
документ личности, список устройств или отозванные права.

Ключ — SHA-256 от algorithm/node ID/public key/message/signature с отдельной
длиной каждого поля. При каждом вызове читаются текущие байты; изменение
mutable input не наследует прежний результат. Кэш привязан к одному verifier,
хранит только digest и bool, ограничен FIFO; исключения не запоминаются.
Свежий журнал, проверка принадлежности, fork/chain fold и revoke остаются
на прежних местах. Принятая история и списки адресатов не кэшируются.

## Проверки

Два теста стоимости/изоляции падали на прямом passthrough без кэша.
После исправления проверены границы полей, изменение каждого аргумента,
свежие объекты с теми же байтами, mutable input, отрицательный результат,
ограничение размера и повтор после исключения.
Native-контроль проверяет настоящие Ed25519 и hybrid подписи, неверный node ID,
изменённое сообщение и подпись. Общая серия: **507 passed**, включая group
service, свежесть own routing/revoke, device sync, own history и census.
Analyzer изменённых Dart-файлов: без замечаний.

## Изолированная стоимость

Дополнительный синтетический контроль на той же native-библиотеке: один
настоящий `ed25519+falcon512` signer, неизменные message/key/signature,
2048 байт сообщения, прогрев и 500 проверок в каждой фазе:

| Прямой verifier A₁ | Кэш B | Прямой verifier A₂ |
| ---: | ---: | ---: |
| 53,761 мс | 7,005 мс | 53,220 мс |

Внутри кэша native verifier вызван ровно один раз за прогрев и повторные
проверки. Это измерение стоимости одного чистого предиката, **не** A/B/A
всего приложения. Оно не объясняет десятки секунд полной догрузки.

## Native-квалификация

Первый кандидатный прогон: после SIGKILL на диске B осталось 1556 сообщений,
включая поздний хвост с неверными provisional positions. До возврата A
источники A/C были выключены. Все 2000 ID, порядок, source positions и delivered
затем сошлись и сохранились после повторного запуска B без A/C. Потерь,
дублей, invalid snapshot и completed-history retry нет. Оба дополнительных
oracle — sparse-копия после crash и runtime offer нескольких prefix proofs —
выполнены. После готовности API A полная сходимость заняла **56,328 с**.

Повтор: после crash на диске было 1570 строк, 98 ordering repairs; оба oracle
выполнены. Все 2000 строк/positions/delivered сошлись без потерь/дублей/invalid
snapshot/completed-history retry и сохранились после запуска без источников.
Полная сходимость после готовности API A — **56,242 с**. При poll около пяти
секунд общее ускорение против контрольных **56,328 с не обнаружено**.

Методические границы: разные фактические частичные копии после kill,
одна машина/Mac/JIT, loopback native-транспорт. Это проверка корректности и
наблюдение времени, не строгая причинная оценка всей оптимизации.
Оба кандидатных стенда завершены: по 27 owned PID и 33/31 порт проверены,
процессов/сокетов стендов нет, временные runtime удалены. По 1403 frozen
source/dependency файла, выбранные CLI/FFI/HV и чистота SDK сверены после
завершения. Контрольный и профилировочный стенды также завершены и очищены.

Общий latency-дефект **не закрыт**. Расширенная multi-device матрица, Android/AOT
и реальные сети этим локальным Mac/JIT прогоном не квалифицированы.
По census остаётся большой объём свежих чтений группового журнала: в первом
кандидатном окне B было 9733 `kv.readLogBatch` с суммарным inclusive await
15,629 с и 9657 `kv.get` с 11,562 с. Это разные/вложенные вызовы и не основание
складывать их в эксклюзивное время, но следующий профиль должен различить
именно повторную загрузку сегментов и обработку очередной страницы.

Внешние библиотеки и SDK не пересобирались; APK, реальные контейнеры и реле
не менялись. Push, релиз и изменение engine pins не выполнялись.
