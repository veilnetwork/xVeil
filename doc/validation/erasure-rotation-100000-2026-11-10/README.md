# Сходимость удалений в старых разговорах

## Подтверждённый дефект

Device-erasure anti-entropy сравнивает последние 30 разговоров и ещё один
старый разговор. Для каждого проверяются новейшая страница из 200 сообщений
и одна старая. Обе ротации использовали один persisted global round.
При общем делителе их периодов старый разговор всегда попадал только
в часть собственных страниц. Это не просто медленная проверка: при
неизменной истории пропущенные страницы не посещались никогда.

Контрпример: два старых разговора, у одного пять страниц. Он выбирается
по чётным round; его четыре старые страницы по прежней формуле чередуются
только как 2/4/2/4. Страницы 1 и 3 не проверяются. Четыре удаления в серединах
этих страниц оставляют два видимых сообщения даже после повторного цикла.
Новейшая страница сравнивается и раньше, но отсутствующий delete-log event
в старой странице она не восстанавливает.

## Исправление

Для ротируемого старого разговора номер посещения вычисляется из global
round с делением на число старых разговоров. Его старая страница теперь
продвигается на каждом собственном посещении. Для недавних разговоров
прежний темп сохранён. Persisted setting и восстановление после перезапуска
сохраняются; новых чтений/записей настроек или запросов не добавлено.
При стабилизировавшемся составе все страницы каждого разговора посещаются,
даже если конечное изменение состава оставило произвольную фазу round.

Лимиты прежние: до 30 недавних и один старый разговор, до двух страниц
на разговор, до 200 ключей на запрос. Throttle, принадлежность устройства,
аутентификация и проверка точных ранее запрошенных ключей не изменены.
Незатребованный ответ не получает права удалять строки. Mailbox для собственных
устройств не добавлен, wire/storage format прежние.

## Проверки

Planner: все 272 сочетания 1–17 старых разговоров и 2–17 страниц в двух
начальных фазах (0 и 137), полный охват страниц каждого выбранного разговора.
Отдельно проверены отсутствие лишних запросов для пустой/единственной страницы,
прежняя скорость недавних страниц и отказ нулевого периода.

Интеграционный fixture содержит ровно **100000 сообщений / 32 разговора**:
1000 в самом старом, один во втором старом, по одному в 29 недавних и 98970
в самом новом. Источник хранит четыре настоящих tombstone. Восемь presence
проходов с перезапуском MessagingService между каждым используют реальный
persisted round. Ответы проходят обычный authenticated inbound deviceGone,
а не прямой вызов storage delete. Запросы содержат не более 200 ключей;
их число остаётся 32/33 поочерёдно. После apply проверяются все оставшиеся
ID, тела, авторы, sequence/canonical positions, статусы и timestamps в мс.
Четыре ожидаемых удаления отличены от случайной потери других строк.

Unit parent assertion-red сохраняет два удалённых сообщения. Candidate и
presence/security checks проходят. Related suite: **576 passed / 1 skipped**;
явно включаемый roster lifecycle probe не засчитан пройденным. Анализатор
production-файла и двух новых тестов чист. После косметических braces/format
правок теста отдельно повторены три новых checks; native production-код
не менялся после квалификации.

Native контроль использует два настоящих worker-backed контейнера: источник
с tombstone и получатель со всеми 100000 строками. На старом production-коде
после восьми проходов и холодного повторного открытия остаются **99998** строк:
два ожидаемых удаления не применены. На candidate — **99996/99996** точных
уникальных оставшихся строк, ни одного из четырёх удалённых ID. Критерий не
равенство двух неполных выборок: ожидаемые исходные 100000 строк и четыре
разрешённых удаления заданы независимо от полученного состояния.

Оба native варианта проходят один и тот же final fixture с проверкой холодного
повторного открытия. Ранний native pair без cold-open тоже подтвердил
расхождение; окончательная квалификация использует более строгий oracle,
включая conversation ID и timestamps по millisecondsSinceEpoch.
Вывод о скорости из этих correctness-прогонов не делается.

SHA native-библиотек сверены, фактический mapping HVS проверен у тестового
процесса. Все остальные lib/test/config inputs зафиксированы и сверены
до/после каждого варианта; production candidate восстановлен. По три собственных
процесса завершились в каждом native варианте, runtime с обоими контейнерами
удалён. Сырые журналы и локальные пути остаются вне Git.

## Границы

Это восстановление пропущенного device-log удаления между своими устройствами,
а не получение истории при offline всех её держателей. При большой истории
полный цикл всё ещё долгий: один старый участок на посещение. Непрерывное
изменение порядка/размера разговоров не квалифицировано; конечные изменения
и последующая стабилизация не создают прежней modulo-ловушки.

Проверка Mac/JIT со storage и messaging layer не заменяет Android/AOT,
полный ratchet/relay/device-group стенд или revoke/split-brain матрицу.
Доставка 100000 строк по-прежнему требует отдельного ускорения; NETCALL
и остальные пробелы matrix открыты. Push и релиза нет.
