# Пакетное сохранение выдаваемой истории — 2026-11-01

Подтверждён лишний последовательный путь при выдаче истории новому устройству.
`replayHistoryForAsk` ожидал `postDeviceEvent` после каждой строки. Параметр
`batch: 25` задавал только паузу и проверку свободного места у sibling; он не
позволял существующему durable-дренеру собрать эти 25 строк в одну запись.
Каждая строка отдельно загружала и сохраняла групповой журнал.

Теперь выдача собирает до 25 событий и передаёт их существующему дренеру одним
ограниченным вызовом. Новый `postDeviceEvents` принимает максимум 64 события,
как и сам дренер. Последовательный API для обычных событий сохранён. Подписи,
admission, сериализация группы, финальное сохранение и последующая рассылка
используют прежний путь.

Успех и счётчики выдачи появляются только после завершения сохранения. Отказ
финальной записи возвращает false для всей порции. При частичном отказе
подготовки считаются только действительно принятые строки и новые порции не
отправляются. Отмена отбрасывает ещё не переданный буфер; уже принятая запись
завершается и учитывается. Очередь сохраняет порядок относительно live-событий,
между порциями остаётся прежняя проверка backlog и пауза.

## Контроль локального механизма

На одном и том же storage/service 25 последовательных ожидаемых вызовов дали
50 файловых записей — segment и header на каждое сохранение. Один вызов с
25 событиями и отдельное последующее live-событие дали четыре записи: две на
порцию и две на live-событие. Это счётчик fixture с отдельными файловыми
записями, **не число native-транзакций/fsync**.

Отдельные проверки удерживают сохранение и backlog gate: до их освобождения
нет раннего успеха/прогресса или следующей порции. Проверены порядок и вложения,
неполная последняя порция, частичный отказ, ошибка сохранения, отмена до/во
время commit, некорректная длина ответа, закрытый service и предел порции.

## Межпроцессный сценарий

Новый fixture использует настоящие embedded-узлы и worker-backed контейнеры
в отдельных A/B/C процессах на одном Mac; A/B — одна личность, C — другая.
Три локальных реле, публичные сиды/discovery выключены; прямые локальные
соединения разрешены. Каждый message ID считывается через работающий storage,
поскольку обычный UI-hook ограничивает хвост истории тысячей сообщений.
Равенство пустых списков не считается прохождением.

Сценарий: создать 2000 сообщений A→C, связать B и проверить все старые ID;
выключить B минимум на пять реальных минут, отправить ещё 100 сообщений A→C;
выключить C, вернуть B и проверить все 100 исходящих копий и прежние 2000 ID.
После возвращения C повторно сравнить ID/порядок и отсутствие дублей.

До правки подготовка не прошла: новое B не получило все 2000 сообщений за
360 секунд ожидания. В промежуточном наблюдении было 1449 строк; точное число
на последнем такте timeout не сохранено. Этап 100 offline-сообщений поэтому
**не выполнялся**, прежние 106 секунд догрузки этим запуском не переизмерены.
В журнале B 849 событий пришли через 739 ingest, 736 из них — с одной новой
строкой. Это подтверждает мелкую гранулярность той выдачи, а не объясняет всю
стоимость приёмника.

Native SDK/CLI и HV не пересобирались: SHA совпали с исходным прогоном.
SDK собран из Veil `f7a4fb97`, runtime эквивалентен текущему `06eeddf5`;
различия — документация и simulation tests. Изменения runtime Dart заморожены
на время прогона. Это host/JIT-квалификация, не Android/AOT и не строгая серия
A/B/A. Причинная оценка локальных записей отделяется от сквозных времён.

На кандидате полная исходная история B совпала по всем 2000 ID и порядку;
первое полное наблюдение — **237 149 мс** после завершения link-подготовки.
До остановки B зарегистрировано 80 group ingest / 1978 новых событий, ни
одного ingest с одной новой строкой. Это не все пути появления сообщений:
часть истории приходит также через отдельный own-device history exchange.
Сравнивать число group ingest с числом итоговых chat message ID напрямую нельзя.
Последние 25 строк отсутствовали в промежуточном наблюдении при пустом Outbox
обоих устройств, затем появились автоматически; причина этого ожидания не
установлена. Все задержки синхронизации исправленными не объявляются.

Связанный scoped-набор: **483 passed, 3 skipped**, analyzer семи изменённых
файлов чист. Первоначальная проверка счётчика fixture ошибочно ожидала одну
файловую запись на сохранение; она исправлена на segment+header и полный набор
повторён. Это исправление oracle теста, не второй production-дефект.

## Результат offline-догрузки

**PASS, один native-прогон.** B был offline минимум пять реальных минут и
оставался выключенным до остановки C. После запуска B первое полное наблюдение
всех 100 исходящих копий — **10 419 мс от готовности**, или **20 941 мс от начала
запуска**. Готовность заняла 10 521 мс. Наблюдения: 0 → 77 → 100; запросы
состояния занимали 103–205 мс, интервал между ними — около пяти секунд.
Это верхняя граница по наблюдателю, не точное время последней доставки.

До возвращения C совпали все 100 новых и 2000 старых ID/порядок на A/B.
После возвращения C проверены те же ID/порядок на A/B/C; лишних и повторных
ID не наблюдалось ни на одном опросе. Общее время с подготовкой и teardown —
756,708 с. Прежние 106 секунд получены на Android в другом прогоне: сравнение
«ускорено в десять раз» **не производится**.

Это проверка online A / offline C при возвращении B. Одновременное отсутствие
A и C, часы/сутки offline, все crash-cut, revoke и остальные пункты матрицы
этим сценарием не закрываются. Долгая догрузка на телефоне остаётся активной;
следующий участок — остаточные ожидания доставки/обработки уже сохранённых
строк, включая описанный хвост из 25 сообщений.

После обоих прогонов независимо проверены выход собственных процессов/групп,
отсутствие слушателей на занятых портах и удаление runtime-каталогов с
контейнерами. На кандидате проверены 10 PIDs и девять портов; остатков нет.
Результаты без идентификаторов — [summary.json](summary.json).
Публичные ID, адреса, пути контейнеров, ключи и сырые логи не публикуются.
Без push/релиза; production-сиды и пользовательские устройства не менялись.
