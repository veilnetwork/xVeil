## Подтверждённый дефект и исправление

`pace_params` возвращал unpaced `(0, u32::MAX)`, пока нет живого `srtt`,
**до** проверки сохранённой оценки `btl_bw`. Поэтому warm-start уже мог иметь
BBR window cap, но выпускал весь начальный flight в одном poll-loop. При seed
без RTT не работали ни window cap, ни pacing. Это противоречило контракту
`Config::warm_btl_bw` о shaping с первой отправки.

Теперь BBR pacing использует положительную оценку полосы независимо от наличия
RTT. Расчёт BDP/window cap по-прежнему требует RTT. Настоящий cold start без
оценки полосы остаётся прежним; BBR off также сохраняет прежний путь.
Размеры pacing-пачек, gain, coalesced-wake catch-up (до восьми ticks с общим
`max_pacing_batch` cap), ACK/RST, retry-лимиты, RTO, wire/C ABI не менялись.
Никакого типа приложения или приоритета реле не добавлено.

Два регрессионных теста выполняют SYN/SYN_ACK, затем отправляют данные до
первого DATA ACK: seed с RTT и без него. При MSS 1000, seed 100 KB/s и
`max_pacing_batch=4` прежний код выпускал **60/64** DATA сразу; новый — **4**
и следующую пачку через 20 мс. ACK проходит сразу между ticks. Отдельно
проверена задержка первой прикладной записи до 4000 мс: pacing сохраняется,
late-wake catch-up ограничен тем же batch cap. В первоначальной заготовке
теста не был погашен SYN; этот ложный красный результат не используется.
Зачтённые старые падения получены после настоящего handshake на количестве DATA.

## Контроль A/B/A

[queue_probe.rs](queue_probe.rs) — настоящие sans-I/O StreamEngine, неизменный
двунаправленный FIFO, 2048 wire bytes на каждый frame, MSS 1982, начальное окно
64 MSS, receive window 8 МиБ, ACK every 16 / 5 мс, RACK/BBR on. По умолчанию
25 мс propagation в каждую сторону; специальные профили — по 250 мс. Размер
payload **3 МиБ + 251 байт**, warm seed — половина заданной полосы и 200 мс RTT.
Все часы виртуальные. Потерь/переупорядочивания в модели нет.

Источники probe для двух SDK побитово одинаковы. Baseline — отдельный чистый
checkout `3bea8780`, candidate — каноническая SDK с данной правкой; targets
разделены. A₁/A₂ запускали один проверенный baseline-бинарник и получили
побитово одинаковый stdout во всех профилях. Точные хеши: [summary.json](summary.json).
Оба EOF и каждый payload byte проверены assertions внутри probe.

## Почему начальное окно пока не уменьшено

Отдельный эксперимент на baseline, тот же probe и assertions: окно 64 → 10 MSS
на cold 32 КиБ/с уменьшает очередь 4194 → 819 мс, полное время 99732 мс прежнее.
Но при propagation 250 мс и 1 МиБ/с время растёт **5231 → 8031 мс**, а при
16 МиБ/с — **4557 → 8019 мс**. Даже на 25-мс/16-МиБ/с пути 430 → 653 мс.
Поэтому такое уменьшение не внесено: оно ухудшает быстрые высоколатентные пути.
Все 24 экспериментальные строки с seed/cold и EOF сохранены в summary отдельно
от A/B исправления. Это не заявление об устранении холодного разгона.

## Проверки и границы

Прошли **218 stream-тестов**, ignored нет; **326 FFI unit-тестов**, два ignored.
Пять ignored FFI doctests посчитаны отдельно; внутренний subprocess не прибавлен
к 326. FFI: `--no-default-features --features node-embedded,production-seeds,packet-tunnel`.
Clippy stream `--lib --tests -- -D warnings` и rustfmt прошли. Дополнительное
падение промежуточного теста поздней записи исправлено в самом ожидании:
четырёхсегментный общий batch cap ограничивает и восемь catch-up ticks.

Это проверка движка и совместимости сборки, **не новый физический прогон**.
Ускорение публичных цепочек Android и исправление жалобы «33%» не доказаны.
Ожидание DHT около 3,5 с также не менялось. Телефон/GUI/звонки и реле не
запускались, установленная QA-сборка не заменялась. Все build/test/probe процессы
завершены; mount внешнего target непрерывно проверялся. Для вариантов SDK и probe
использованы отдельные targets и SHA-проверки бинарников. Push/релиз не выполнялись.

Для повторения поместить probe в отдельный Cargo crate, подключить выбранную
SDK через path и взять её lockfile. Базовый запуск — без аргументов. Параметры
модели: `PROBE_IW`, `PROBE_RATE`, `PROBE_PROP_US`, `PROBE_SEED_BW`,
`PROBE_SEED_RTT`; `--long` увеличивает payload до 16 МиБ + 251. Для разных
SDK/checkout/dependency overrides targets должны быть разными; применяются
mount-правила AGENTS.md.
