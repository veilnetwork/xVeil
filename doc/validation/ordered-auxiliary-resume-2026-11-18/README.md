# NETCALL-01: настоящий auxiliary transport после resume

**В контроле с двумя настоящими NodeRuntime сбой не воспроизведён.** Новая
RTData прошла в обе стороны по вспомогательному obfs4/TCP-каналу до смены
сессии, при удержанном завершении старой и после него. Основной поток leaf
во время каждого такого обмена был заблокирован. Мобильная пауза остаётся
открытой: это локальный контроль механизма, не физическая квалификация звонка.

## Стенд и граница проверки

Продолжен [контроль основного потока](../resumed-canonical-data-2026-11-18/README.md),
где ручной leaf не обслуживал auxiliary lanes. Здесь оба конца используют
настоящие SessionRunner, а leaf — также настоящий outbound connector. Роли
Core/Leaf заданы явно, ключи различаются, обычные PoW и sovereign handshake
сохранены. Вспомогательные каналы, exporter binding, admission и session AEAD
не подменены. Использованы loopback peer streams, без публичных bootstrap,
meeting points, PEX и real-user profiles.

Транспортная обёртка наблюдает только canonical stream leaf. Дополнительные
каналы обходят её через обычный StreamParallelHandle; offer не отключается.
На Core старый основной сокет выбирается по точному соответствию его peer
address выбранному client socket на loopback. Поэтому возможная backup-dial
попытка не считается нужным сокетом по одному лишь порядку accept. Это
локальная корреляция стенда, не решение NAT-корреляции мобильного захвата.

## Что утверждает тест

1. Leaf получает настоящий session ticket от Core, обработанный и сохранённый
   его runner. После прогрева обеих сторон блокируются чтение и запись
   canonical stream leaf. Свежая APP_RTData доходит в оба app endpoint, все
   поля, отправитель и синтетический AEAD payload совпадают. Счётчики байтов
   основного потока во время обмена не изменяются: fallback на него не может
   заменить auxiliary-доставку.
2. Чтение старого Core canonical stream удерживается отдельно, чтобы EOF
   уходящего leaf не успел освободить admission. Через настоящий
   MobileEventForwarder отправляется NetworkChanged; connector закрывает
   старую локальную сессию и переподключается с её ticket.
3. Неизвестный leaf отсутствует в dial-таблице Core. При живой прежней
   регистрации новый полный handshake не может её вытеснить; требуется
   аутентифицированный resume своего предшественника. Меняются регистрация,
   session ID и оба направленных ключа. Старый Core runner уже выходит из
   run/release_session, но его финальный shutdown и SessionGuard удержаны gate.
4. Новый auxiliary channel прогревается. При заблокированном **новом**
   canonical stream снова проходит двусторонний обмен свежими кадрами.
5. Старое завершение разрешается; тест дожидается полного выхода его task.
   Новая регистрация сохраняется, третий обмен проходит с тем же запретом
   основного потока. Проверяется, что canonical подключений было ровно два,
   и **обе стороны** всё ещё принадлежат той же возобновлённой session ID.
   Дополнительный незамеченный reconnect не может скрыть отказ.

Всего в новом тесте проверены шесть RTData-кадров, по одному на направление
в каждом из трёх этапов. Gate подтверждает конкретные точки исполнения;
watchdog не используется как утверждение о скорости восстановления.

Это проверка native RT transport. Нет Dart CallService, кодирования Opus,
звукового устройства, слышимости речи, видео, ratchet-контейнера приложения,
P2P между удалёнными клиентами или onion-цепочки. NetworkChanged здесь —
настоящая обработка native-события, но ОС не меняет Wi-Fi/мобильный маршрут.
Нет NAT, потерь пакетов и медленных/молчащих first flights. Успех не исключает
ошибок при этих условиях и не устанавливает причину прежних mobile пауз.

## Проверки и очистка

Окончательный новый тест прошёл. Также прошли шесть связанных проверок:
два canonical DATA-контроля, три resume-admission и один NetworkChanged
retirement/redial. **7 passed / 0 skipped**; промежуточный запуск того же
нового теста не прибавляется к числу уникальных проверок. Отфильтрованные
integration binaries с нулём запущенных тестов не засчитываются.

Release-профиль, production-seeds feature, без test-low-difficulty. Clippy
release/tests с `-D warnings`, форматирование и privacy gate прошли.
Исходники и тестовый binary фиксировались SHA; внешняя файловая система
проверялась перед Cargo и непрерывно во время него. Использован target того
же checkout без dependency override. Изменены только native-тесты.

Оба runtime остановлены, connector/acceptor и их session tasks завершены,
временные synthetic directories удалены. Основные приложения, контейнеры,
сеть телефона, реле и фокус Mac не менялись. Нового SDK/APK не устанавливалось.

## Отдельный отрицательный контроль TCP timestamp

Для следующего mobile-захвата проверен доступ к read-only TCP_TIMESTAMP на
подключённом Poco. В Linux 5.10 getter читает текущие TCP clock/offset, тогда
как изменение offset относится к repair setter. [Исходник Linux 5.10](https://raw.githubusercontent.com/torvalds/linux/v5.10/net/ipv4/tcp.c).

Маленький отдельный NDK probe под shell UID создал только два loopback TCP
соединения. Чтение поддерживается, errno=0; оба счётчика продвигались, но
значения двух соединений совпали. Поэтому этот показатель **не принят как
самостоятельный уникальный идентификатор сокета**. Он не добавлен в product
trace/export. Probe не проверяет UID приложения, мобильный путь или сохранение
timestamps через NAT. Значения не печатались; временный executable после
проверки SHA удалён с телефона. APK и UI не запускались.

Дальше нужен контролируемый mobile-захват с однозначным соответствием попытки
сокету/потоку на реле, а не вывод по одинаковым агрегатным счётчикам. Сохранённый
handshake trace содержит local/peer port и локальные connection/backup attempt
номера, но не общий operation context с выбранной строкой peer/целевым Core.
У трёх Core одинаковый порт; при перекрывающихся попытках одного ближайшего
времени недостаточно. Следующий захват должен иметь такой **локальный,
operator-gated** context без добавления меток на wire, а также измеренные
границы соответствия часов телефона/реле. По прежним файлам индивидуальная
атрибуция здесь не объявляется полученной. NETCALL-01
остаётся активным. Скорость и устранение паузы не заявляются; push/релиза нет.
