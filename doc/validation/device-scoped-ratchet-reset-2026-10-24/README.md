# Сброс цепочки одного устройства — 24 октября 2026

## Дефект и воспроизведение

При проверке отзыва B обнаружен отдельный дефект ещё **до отзыва**. A/B — два
устройства X, C — другая личность Y. Входящий C → X звонит на A и B; после его
отмены новый B → C не появляется на C за 40 секунд.

Журналы показали: подписанное «не могу расшифровать» от B заставляло C удалить
цепочки шифрования **всей X**, включая независимую цепочку A. Последующие кадры
получали ошибки аутентификации; ответы о сбое создавали дополнительные сбросы.
Отдельный детерминированный Rust-тест подтвердил неправильную область действия:
из четырёх подготовленных цепочек удалялись три вместо двух — цепочки B под
двумя адресами и чужая цепочка его соседнего устройства A.

## Исправление

Новый метод `RatchetRuntime.forget_peer_device` выбирает только физический
instance, установленный проверенной подписью документа или OVL1-сессией.
Сброс учитывает оба адреса этого устройства: общий адрес личности и физический
ключ. Цепочки остальных устройств той же личности сохраняются.

Метод используется и для подписанного ответа через реле, и для ответа
`AppSendUnopenable` по прямой сессии. Перезагрузка сертификатов остаётся штатной;
проверки подписей, срока действия и отзыва не ослаблены. Полное удаление контакта
по-прежнему может использовать отдельный `forget_peer` для всех его цепочек.

Для старого одиночного узла с произвольным instance ID сохранён ограниченный
fallback. Если по старому ответу нельзя однозначно выбрать один instance,
несколько независимых цепочек не удаляются наугад. Отдельно проверен случай,
когда физический ключ основного устройства совпадает с адресом личности,
но у неё есть ещё одно устройство.

Формат пакетов, C ABI, политика mailbox и правила работы реле не менялись.
Код исправления общий для сообщений и управления звонками; это не отдельный
режим приоритета звонка и не метка аудио на реле.

## Независимые процессы A/B/C

| Этап | Online | Ожидаемое состояние | Фактический результат |
|---|---|---|---|
| C → X до отзыва | A, B, C | A и B звонят; отмена завершает оба входящих | Выполнено |
| B → C после отмены | A, B, C | C получает новый входящий | Исходная версия: не появился за 40 с. Исправленная: появился |
| Подписанный отзыв B | A, C; B offline | C получает актуальный документ | Документ на C сравнен с документом A; C не перезапускался |
| C → X после возвращения B | A, B, C | Новый вызов приходит A; старый ключ B не получает его | A звонит; B не звонит и не содержит записи нового вызова |
| B → C после отзыва | A, B, C | B не инициирует вызов и не отправляет сообщение как X | За 60 213 мс вызов/сообщение не приняты; записи вызова на C нет |
| Контроли после окна отказа | A, B, C | A → C сообщение и C → A новый звонок продолжают работать | Выполнено; сообщение ровно одно, отмена завершает звонок |

В исправленном запуске от первой записи отправки B-приглашения до первой
записи его приёма C прошло **58,159 мс**. Это разность времён dispatch в двух
процессах на одном Mac с локальными реле; она не измеряет путь от нажатия в UI
и не обещает такую задержку в интернете.

B перезапускался со старым физическим ключом. C сохранял процесс и прогретое
состояние. Никакой CID, ключ или call ID нового вызова B отдельно не передавался.
Использованы настоящие контейнеры hidden-volume, native-узлы и production-
провайдеры xVeil в независимых процессах. Соединение через реле проверялось при запрете P2P в
политике контактов; сам стенд использует loopback QUIC-сессии и не моделирует
каждый вариант NAT, Wi-Fi или мобильного провайдера.

## Проверки и границы

* 89 Rust-тестов runtime/service tasks и 5 тестов dispatcher/unopenable прошли.
* 254 Flutter/Dart теста FSM звонков, realtime-сигналов, нескольких устройств
  одной личности и синхронизации настроек прошли без пропусков.
* Clippy четырёх затронутых/зависимых crates с `-D warnings`, Rust format и
  `flutter analyze --no-pub` прошли.
* CLI реле и клиентская библиотека построены вместе, заморожены и сверены
  с исходниками. Внешний target проверялся до и во время Rust-сборок.
* Сборка Android и хеши артефактов указаны в [summary.json](summary.json).

Звонки в этом сценарии завершаются **до ответа**: микрофоны/медиа не открывались.
Результат квалифицирует приглашения, отмену и запрет старого ключа после
получения отзыва. Он не квалифицирует разговор после ответа, качество речи,
видео, весь список из 63 сценариев или отсутствие шифротекста для старого ключа
при всех маршрутах. Не доказывается и тождество причины этому сбою в сообщениях
пользователей Windows 10: их исходных журналов нет.

Все собственные процессы двух запусков завершены, временные контейнеры удалены.
Телефон и установленные приложения не менялись. Сырые журналы, идентификаторы,
адреса, пароли и ключи остаются локально; публичный JSON содержит только
счётчики, флаги, длительности и хеши ПО. Исторический каталог
`multi-device-2026-10-17` не изменён.
