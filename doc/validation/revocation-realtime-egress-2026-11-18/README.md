# Отзыв устройства: crash автора и исходящие сигналы звонка

## Подтверждённый дефект

Новый выбранный сценарий multi-device проверяет автора A, связанное устройство B
той же личности и контакт C другой личности. A сохраняет подписанный отзыв B,
но теряет ответ записи и завершается до публикации документа работающим узлом.
После cold-open A сам публикует сохранённый документ, без ручного повтора отзыва.
Эта часть уже работала в опубликованной SDK.

Усиленная проверка обнаружила другой дефект на SDK из релиза 0.13.102: C уже
сохранил точный документ отзыва и отвергал входящие сообщения/звонки B, однако
новый исходящий offer C → личности A также попадал B. Приватная трасса B
подтвердила декодированный realtime offer с тем же call ID; это не только
запоздалое уведомление о завершении или строка истории. Старый sibling roster A
также оставался возможным источником пересылки отозванному устройству.

`APP_RT_SEND` выбирал адресатов из живых транспортных регистраций без повторной
проверки текущего документа. Проверки family certificate / обычного seal этот
быстрый путь не покрывали. Дефект затрагивает сигналы звонка; offer содержит
вклад вызывающего в медиаключ. Успешный ответ отозванного устройства, получение
полного ключа разговора или прослушивание живого аудио **не доказаны**.

## Изменение

Veil `2cd89257` проверяет каждого локального application realtime-получателя
перед постановкой кадра в транспорт. Для собственной личности используется
актуальный sovereign document, для контакта — monotone authorization floor,
включая durable checkpoint, expiry и tombstones. Адресная отправка физическому
устройству проверяет его аутентифицированную связь с личностью. Исключение всех
кандидатов не включает fallback обратно на общий адрес личности.

Проверка синхронная и локальная, без DHT ожидания. Не менялись wire, C ABI,
приоритеты, срок short-control, ratchet, транзит чужих кадров и политика mailbox
собственных устройств. Неизвестная standalone legacy-сессия без document floor
сохраняет прежнюю семантику; attached host остаётся fail-closed до checkpoint.

## Проверки до исправления

- Сначала узкий crash-тест прошёл: точная запись пережила SIGKILL, A
  перепубликовал её после удаления runtime и замены всех тестовых реле;
  B → C отвергался, A ↔ C работал. Это не проверяло исходящую копию B.
- Усиленный тест на тех же опубликованных native bytes упал именно на новом
  offer у B. До отрицательной проверки отдельно наблюдались сохранённый
  checkpoint C и отказ допуска B. Исходники и выбранные библиотеки не менялись.
- Три native regression assertions упали на прежней механике, один допустимый
  контроль прошёл. Невыполненный ранний запуск без требуемой bootstrap feature
  не считается воспроизведением.

## Локальные проверки исправления

Четыре native теста покрывают identity fanout, исключение всех устройств,
адресный physical target и допустимые legacy/authorized controls. Каждый
проверяет обычный и short-control путь. Они входят в общий счёт ниже.

Связанная последовательная Rust-серия: **1024 passed, 16 ignored** отдельно;
Clippy для обоих изменённых пакетов со всеми targets прошёл с `-D warnings`.
Первый параллельный запуск имел один отказ несвязанной admin fixture: socket
не появился за 60 секунд. Изолированный повтор прошёл, затем полная
последовательная серия прошла. Причина первоначального отказа не установлена;
он не скрывается и не объявляется доказанной случайной ошибкой.

Свежая FFI и CLI собраны из чистого коммита `2cd89257`; выбранные копии
проверены по SHA, исходные опубликованные библиотеки сохранены неизменными.
Усиленный native A/B/C сценарий прошёл: 30 секунд отвергаются новые сообщения
и звонки от B, затем восемь секунд B не получает свежий offer, ответное сообщение
и запись о новом звонке, а A получает и сообщение, и ringing. Проверка
использует настоящий сохранённый checkpoint C, а не только наличие документа
в DHT. Повтор после уточнения остановки измерительных часов также прошёл:
30,410 с отрицательного наблюдения, затем отдельное окно нового offer более
восьми секунд. Исходники и байты библиотек внутри каждого прогона совпали;
все 33/39 отслеженных процессов завершились, по 28 TCP-портов освобождены.
Результаты последнего повтора: [summary.json](summary.json).

В первом узком прогоне мгновенная проверка bind трёх портов не прошла после
завершения всех процессов; позднейшая независимая проверка всех 28 портов
прошла. Это не переименовано в изначально чистый teardown. Усиленные baseline
и candidate имеют чистый собственный teardown; проверка reuse учитывает
закрытые TCP-соединения и отдельно контролирует отсутствие живых процессов.

Отрицательный контроль самого теста также сработал: только в одноразовом
контейнере автора перед cold-start намеренно возвращён исходный старый
подписанный документ. Сценарий упал на точной проверке самостоятельной
публикации сохранённого tombstone, до возврата B и проверок вызова. Все 33
процесса этого контроля завершились, 22 порта освобождены. Намеренный отказ
не прибавляется к числу пройденных сценариев.

## Границы

Стенд использует отдельные OS-процессы на одном Mac, настоящий SDK, контейнеры,
подписанные документы, durable storage и локальные реле. Fault injection
разрешён только в тесте: реальная запись завершается до потери её ответа.
Cold-read не исправляет контейнер; его SHA проверяется до/после чтения.
Обычный app-код не получает новых test endpoints.

Это выбранный author-crash/revocation сценарий, а не вся матрица из 63 пунктов,
Android/AOT, power loss или длительный offline. Никаких пользовательских
профилей, production-сидов и окон не затронуто. Изменение после выпуска
0.13.102, локальное; нового push или релиза нет.
