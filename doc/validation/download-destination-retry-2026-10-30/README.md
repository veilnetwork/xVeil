# Не удалять запрос загрузки при временном отказе файла назначения

В `_resumePlainFile` отказ `plainFileSinkOpener` с результатом null вызывал
`complete(contentId)`: сохранённый запрос исчезал, хотя файл не был скачан и
пользователь не отменял загрузку. Исключение из того же opener, напротив,
уже попадало в обычный backoff. Стандартный opener возвращает null при ошибках
открытия/создания файла; он не доказывает ни постоянную потерю пути, ни отмену.

Теперь null переводится в фиксированную ошибку назначения, обрабатываемую
обычным планировщиком повторов. Сохранённый запрос, путь и частичные байты
не удаляются. Лимиты не увеличены: после восьми неудач запрос припаркован;
остаются прежние сигналы возобновления, ручной выбор места и явная отмена.
Сохраняется и прежний срок загрузочного реестра — 14 дней при чтении после
старта; это не обещание бесконечного хранения. Новый путь не появляется
автоматически, разрешения файловой системы не обходятся. Потерянный sandbox
grant может потребовать повторного выбора назначения пользователем.

## Воспроизведение и регрессия

На исходном `0e59f6ac` два одинаковых сценария различались только поведением
opener: null и исключение. Сначала в реальный временный файл записана одна
часть 256 КиБ из 700000 байт, сохранён запрос, сеть отключена, служба заменена.
После отказа нового opener и ещё одного старта null-сценарий потерял запрос
(красный), исключение сохранило его и завершило загрузку (контроль зелёный).
После исправления оба сохраняют запрос и начальные байты; при следующем старте
с доступной сетью и стандартным файловым opener собирают исходные 700000 байт
без ручного повторного запроса. Полное содержимое сравнивается побайтно.

Отдельный сценарий удерживает opener недоступным: ровно восемь попыток, затем
многократный интервал повтора без девятой. Запрос остаётся в реестре, явная
отмена удаляет его и после следующего старта. Задержки в тесте уменьшены через
существующие настройки; производственные интервалы и число попыток не менялись.

Прошли **100 тестов** трёх связанных файлов: auto-resume, durable registry и
stream transfer. В том числе прежняя проверка подтверждает, что уже
проверенные части на диске не запрашиваются повторно. Новых сценариев здесь три;
один из них был зелёным до исправления. Analyze четырёх файлов — без замечаний.

Дополнительно прошли **2 native-storage теста без пропусков**: прежние 24
сохранённых запроса/отмена и новый отказ назначения. Новый случай открывает
настоящий hidden-volume контейнер, записывает намерение, закрывает/открывает,
запускает resumer с null-opener, снова закрывает/открывает и проверяет запрос.
После отмены ещё одно открытие подтверждает его отсутствие. Использована
существующая FFI-библиотека с сохранённым SHA-256; новую Rust-библиотеку не
собирали. Argon min — только у временной фикстуры native-storage теста;
production node, PoW и сетевые политики здесь не менялись.

## Границы

Reliable-stream канал регрессии — in-process loopback, реестр первого набора
на FakeKvLogStore; файл назначения настоящий. Дополнительная native-проверка
использует настоящий контейнер, но без сети. Реальная смена mounts, отказ
NSSavePanel grant на macOS, внешний диск и Android permissions физически не
вызывались: отказ воспроизведён через уже существующий opener интерфейс.
Это доказанный дефект потери запроса на таком отказе, не доказанная причина
исходного пользовательского «33%», сетевых пауз или медленного cold resolve.
Нативные тестовые процессы завершены; их временные файлы удалены. GUI для этой
файловой правки не запускался. Параллельная Android UI-проверка фоновой работы
имеет отдельный отчёт. Коммит без подписи; push и релиза нет.
