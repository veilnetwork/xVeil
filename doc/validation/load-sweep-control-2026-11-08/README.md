# NETCALL-01: нагрузка при постоянных TCP/TLS-соединениях

**Подтверждено:** уменьшение предложенной нагрузки в четыре раза не
устраняет секундные паузы на текущем мобильном пути. Изменение нагрузки
не является единственным объяснением: один участок с высокой нагрузкой
тоже прошёл без секундных задержек. **NETCALL-01 остаётся открытым**;
product-код, параметры аудио и транспорта не менялись.

Предыдущий [одновременный TCP/TLS-контроль](../tls-path-control-2026-11-08/README.md)
сохранял четыре канала, но удваивал нагрузку относительно TLS-only.
Новый контроль проверяет именно этот оставшийся фактор.

## Протокол

Один native C executable, без SDK Veil, под UID shell. К двум тем же
серверным адресам открываются четыре соединения: TCP и TLS к каждому.
**В течение каждого прогона соединения сохраняются на всех четырёх
ступенях**; сетевой интерфейс и target network не переключаются.

Каждый кадр содержит 512 Б синтетических данных. Общий tick создаёт
по одному кадру для всех каналов. Меняется только период генерации:

- 50 мс — 40 КиБ/с полезной нагрузки на направление для четырёх каналов;
- 200 мс — 10 КиБ/с на направление.

Это не wire bitrate: TCP/IP/TLS overhead не включён. Вместе с байтовой
нагрузкой меняется частота пакетов; эти два фактора здесь не разделены.
Это также не тест другого окна кодирования Opus: payload остаётся фиксированным.

Заранее заданы Wi-Fi 40 с и два мобильных прогона по 180 с. Мобильные
ступени длятся по 45 с, порядок — H/L/H/L и L/H/L/H. На каждом канале
2250 кадров за полный мобильный прогон: 1800 при H и 450 при L.
Полное содержимое echo проверяется клиентом. Server sessions и точный
порядок sequence сопоставлены с client sends; одна server session
каждого канала покрывает все четыре ступени без reconnect.

Оба порядка проверены на loopback до deployment. Искусственная пауза
1100 мс обнаруживается при правильном числе кадров и регулярном источнике;
испорченный CA-файл и недоверенный сертификат отвергаются. Перед телефоном
Mac smoke дал по 50/50 echoes на всех четырёх каналах. TLS verification
не отключалась; временный сертификат доверен только измерителем.

## Результаты

В таблице максимумы среди четырёх каналов. RTT относится к кадрам,
созданным на соответствующей ступени. Silence — наибольший промежуток
без echoes в центральных 35 с ступени, включая края этого окна;
первые и последние 5 с исключены, чтобы уменьшить влияние перехода.
Это не one-way audio latency. При L нормальный интервал генерации — 200 мс.

| L/H/L/H, 2 | 40 КиБ/с | 631 мс | 522 мс | 488 мс | 0 |

Все **18000 мобильных кадров** и **2000 Wi-Fi кадров** вернулись.
Пропусков, дублей, испорченных кадров, skipped work, missed ticks и I/O
errors нет. Wi-Fi max RTT 272 мс; нормальные интервалы низкой частоты
не объявляются сетевыми паузами. Producer gaps <57 мс при H и <208 мс
при L; max local write wait <14 мс. Тайминги измеряются одним клиентом.
Server arrival gaps — разности времени внутри каждого сервера перед echo,
без вычитания несинхронизированных часов. Это application observation,
не NIC capture и не указание конкретного виновного хопа.

Среди мобильных echoes RTT >1 с имеют 59/3600 кадров L и 790/14400 кадров H.
Это описательные доли этой серии, не причинное доказательство ускорения
при L: радио/маршрут меняются со временем, а редкие кадры иначе сэмплируют
одну и ту же паузу. Видно и обратное: здоровый H во втором прогоне и
секундные паузы на обоих L первого. Заменять настройки продукта по этим
долям нельзя. Средняя пропускная способность всей мобильной сети и
её поведение вне проверенного диапазона этим не определены.

## Состояние устройства и следующий измеритель

36 environment snapshots: target network VALIDATED, Awake, питание
подключено, Doze/Light Doze ACTIVE. В каждом срезе main и QA процессы xVeil
отсутствуют. Дополнительно сохранены счётчики активного сетевого интерфейса;
они не интерпретируются как доступная полоса или трафик только измерителя.
Это не непрерывный контроль suspend; клиент использует CLOCK_MONOTONIC.
Screen-off/OEM, app UID, настоящий звонок и handover здесь не квалифицируются.

Проверена доступность следующего варианта пути: на default mobile link
есть IPv4 и нет IPv6, на обоих тестовых серверах нет global IPv6 addresses.
IPv6-control на этом стенде недоступен; APN/адресация не изменялись.
Это не ограничение или дефект IPv6 в Veil.

Следующий шаг — **TCP_INFO на отправляющем Poco** одновременно с echoes:
unacked/retransmissions/RTO и accepted-but-not-sent bytes. Он должен
различить ожидание внутри TCP и задержку после локального принятия данных.
Пока диагноз ядра, модема или промежуточной сети не установлен.

Отдельный собственный Android loopback helper уже проверил ABI чтения:
ядро возвращает 232 байта TCP_INFO, поэтому поля за этой границей читать
нельзя. При echo 512 Б счётчики sent/received/acked выросли ровно на 512,
локальных retransmissions нет. Контроль с малым receive buffer реально
создал backpressure: accepted 107136 Б, sent 1728 Б, not-sent 105408 Б.
Это проверка измерителя, **не захват мобильной паузы**. Его sockets закрыты,
процесс завершён и собственная directory удалена; внешняя сеть не использовалась.

## Восстановление

Все процессы и локальные серверы измерителей завершены. Собственные
телефонные binary/token/CA/directories удалены по owner marker. Исходные
Wi-Fi/data/stay-on и validated сеть восстановлены; APK main/QA и исходный
QA root container сверены по SHA, включая независимую проверку после уборки.
Контейнеры не открывались, приложения не устанавливались и не запускались.

Временные server units/root credentials удалены, порты свободны;
production PID/restarts/binary/config обоих серверов проверены независимо.
Frozen source/binary/runtime hashes совпали. Raw records и operational
metadata остаются private. Коммит без подписи; push/релиза нет.
