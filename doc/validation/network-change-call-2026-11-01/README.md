# NETCALL-01: входящий звонок не приходит после Wi-Fi → mobile

**Статус: активный пользовательский репорт с точными шагами.** Независимое
стендовое воспроизведение и причина пока не установлены. Исправление не заявлено.

## Воспроизведение, сообщённое владельцем

1. На телефоне включены мобильные данные и Wi-Fi.
2. Открыть xVeil и дождаться подключения к сидам через Wi-Fi.
3. Отключить Wi-Fi, оставив мобильные данные включёнными.
4. Позвонить с телефона на компьютер. В сообщённом случае интерфейс показывал
   один активный узел на момент вызова.

Фактически телефон показывает исходящий вызов, но компьютер не получает
входящего. Ожидается доставка предложения по доступной новой сети; если маршрут
не восстановлен, интерфейс должен сообщать реальное состояние попытки.
Число активных узлов само по себе не доказывает пригодность сессии после смены
локального адреса. Длительность ожидания, результат отложенного повтора и
конкретный оставшийся маршрут в исходном репорте неизвестны.

## Проверка

- Контрольный звонок при стабильном Wi-Fi и при стабильной мобильной сети.
- Немедленный вызов после отключения Wi-Fi, затем повтор после восстановления
  сессий: получение offer, ответ, RTP обоих направлений, завершение.
- Сопоставить событие ОС о смене сети, состояние подключений и TX-регистраций,
  фактическую попытку отправки signaling, результат admission/повторов и
  появление offer на компьютере. Не принимать локальную постановку за доставку.
- Обратный переход mobile → Wi-Fi и входящий вызов после переключения.
- Дополнительная гипотеза владельца: смена сети во время активного разговора.
  Проверить отдельно; этот вариант ещё не объявляется подтверждённым дефектом.

Использовать отдельные QA-профили, сохранить пользовательские личности и
исходные настройки сети. Публичная сводка — только категории, длительности и
счётчики; адреса, идентификаторы, ключи и частные журналы не публикуются.

## Подтверждённый пробел интеграции и локальная правка

В текущем xVeil не было ни подписки на `onConnectivityChanged`, ни вызовов
`VeilClient.notifyNetworkChanged`. SDK предоставляет такой механизм, а runtime
по уведомлению снимает старые TX-регистрации и будит переподключение. Существующий
`resumeReconnectProvider` работает только после возвращения из фона с отсутствием
не менее 45 секунд, поэтому не покрывает описанный переход при открытом UI.
Это подтверждено по коду; причинная связь с исходным звонком ещё не доказана.

Добавлена отдельная подписка из постоянно подключённого UI-моста. Она сообщает
изменения всем запущенным узлам личностей, не дублируя активный узел all-online
сессии. Локальный control-клиент отделён от очередей mailbox и media, всегда
закрывается после уведомления и не добавляет новых сидов или транспортов.

Повторы одного состояния подавляются; уведомления последовательны и ограничены
текущим/последним состоянием. Поколение перехода сохраняется даже для быстрого
Wi-Fi → mobile → Wi-Fi во время незавершённого IPC. Поздний ответ начального
опроса не затирает новое событие, dispose отменяет подписку и отложенные действия.
Отказ уведомления не отмечается как успех; очередное наблюдение может повторить
попытку. Подписка не определяет доступность интернета: её задача — сообщить ОС
смену подключения; восстановление маршрутов остаётся за узлом.

### Проверки этой правки

- 9 тестов наблюдателя/production-provider: переход при открытом приложении,
  дубликаты, поздний initial query, смена во время IPC, быстрый возврат Wi-Fi,
  отказ и повтор, dispose, все online-личности без двойного уведомления.
- Совместно с тестами приёма транспорта и анонимной диагностики: 24 passed.
- Анализ семи затронутых Dart-файлов: без замечаний.
- Проверка opt-in анонимного diagnostic-артефакта: passed.
- Отдельная ARM64 Android QA-сборка собрана; все три native-библиотеки в ней
  побайтно совпадают с опубликованными библиотеками, извлечёнными с телефона.
  Изменения приложения не требуют замены native SDK.

В анонимной диагностике сохраняется `networkChange`: coarse `state`
(unknown=0, wifi=1, cellular=2, ethernet=3, offline=4), `success` и `durationMs`.
Это результат локальной попытки уведомить узел, **не** подтверждение доставки
звонка или восстановления сети. SSID/IP/интерфейсы/ключи/число скрытых личностей
не собираются этим событием.

### Что остаётся

Первая установка изолированного QA-приложения на Poco отклонена Android с
`INSTALL_FAILED_USER_RESTRICTED`. Пока установка не разрешена, контрольный
звонок и Wi-Fi → mobile на новой проводке не выполнены. Настройки сети телефона
не менялись, основное приложение и его личность не заменялись.

Статус репорта остаётся открытым: **правка подтверждённого пробела выполнена;
устранение пользовательского симптома физически ещё не проверено**.

Windows: новая Dart AOT-сборка также собрана и запущена с отдельным QA-профилем;
после разблокировки `/health` показал `ready`, `realStack=true`, prod. В devlog
не обнаружено `handover notification failed` или `MissingPluginException`.
Это проверка запуска приложения с новой проводкой, а не handover-звонка.
Runner/plugins и native-библиотеки остаются опубликованными; полная сборка
Windows C++ ограничена отсутствующими на стенде ATL headers.

После проверки QA-приложение Windows остановлено, обе собственные scheduled
задачи отсутствуют, SSH-туннель закрыт. На телефоне QA-процессы не запускались;
неизменность Wi-Fi/mobile data проверена повторно. Push и релиза нет.

Дополнительный контроль после добавления проводки: Mac → Windows установил
звонки с аудиопакетами/выходными сэмплами по P2P и принудительному relay при
стабильной сети. [Границы контроля](../receive-only-audio-2026-11-01/README.md):
на Mac явно использована более старая native SDK. Это не проверка смены сети
на Poco и не основание закрыть NETCALL-01.
