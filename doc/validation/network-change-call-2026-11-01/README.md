# NETCALL-01: входящий звонок не приходит после Wi-Fi → mobile

**Статус: активный пользовательский репорт с точными шагами.** Исходная полная
недоставка входящего на текущем стенде не воспроизвелась. Дополнительно
подтверждена пауза аудио при смене сети внутри разговора; причина всей паузы
пока не установлена. Полное устранение NETCALL-01 не заявлено.

## Воспроизведение, сообщённое владельцем

1. На телефоне включены мобильные данные и Wi-Fi.
2. Открыть xVeil и дождаться подключения к сидам через Wi-Fi.
3. Отключить Wi-Fi, оставив мобильные данные включёнными.
4. Позвонить с телефона на компьютер. В сообщённом случае интерфейс показывал
   один активный узел на момент вызова.

Фактически телефон показывает исходящий вызов, но компьютер не получает
входящего. Ожидается доставка предложения по доступной новой сети; если маршрут
не восстановлен, интерфейс должен сообщать реальное состояние попытки.
Число активных узлов само по себе не доказывает пригодность сессии после смены
локального адреса. Длительность ожидания, результат отложенного повтора и
конкретный оставшийся маршрут в исходном репорте неизвестны.

## Проверка

- Контрольный звонок при стабильном Wi-Fi и при стабильной мобильной сети.
- Немедленный вызов после отключения Wi-Fi, затем повтор после восстановления
  сессий: получение offer, ответ, RTP обоих направлений, завершение.
- Сопоставить событие ОС о смене сети, состояние подключений и TX-регистраций,
  фактическую попытку отправки signaling, результат admission/повторов и
  появление offer на компьютере. Не принимать локальную постановку за доставку.
- Обратный переход mobile → Wi-Fi и входящий вызов после переключения.
- Дополнительный сценарий владельца: смена сети во время активного разговора.
  В последующем физическом цикле подтверждена пауза аудио (см. ниже); завершения
  звонка при этом не наблюдалось.

Использовать отдельные QA-профили, сохранить пользовательские личности и
исходные настройки сети. Публичная сводка — только категории, длительности и
счётчики; адреса, идентификаторы, ключи и частные журналы не публикуются.

## Подтверждённый пробел интеграции и локальная правка

В текущем xVeil не было ни подписки на `onConnectivityChanged`, ни вызовов
`VeilClient.notifyNetworkChanged`. SDK предоставляет такой механизм, а runtime
по уведомлению снимает старые TX-регистрации и будит переподключение. Существующий
`resumeReconnectProvider` работает только после возвращения из фона с отсутствием
не менее 45 секунд, поэтому не покрывает описанный переход при открытом UI.
Это подтверждено по коду; причинная связь с исходным звонком ещё не доказана.

Добавлена отдельная подписка из постоянно подключённого UI-моста. Она сообщает
изменения всем запущенным узлам личностей, не дублируя активный узел all-online
сессии. Локальный control-клиент отделён от очередей mailbox и media, всегда
закрывается после уведомления и не добавляет новых сидов или транспортов.

Повторы одного состояния подавляются; уведомления последовательны и ограничены
текущим/последним состоянием. Поколение перехода сохраняется даже для быстрого
Wi-Fi → mobile → Wi-Fi во время незавершённого IPC. Поздний ответ начального
опроса не затирает новое событие, dispose отменяет подписку и отложенные действия.
Отказ уведомления не отмечается как успех; очередное наблюдение может повторить
попытку. Подписка не определяет доступность интернета: её задача — сообщить ОС
смену подключения; восстановление маршрутов остаётся за узлом.

### Проверки этой правки

- 9 тестов наблюдателя/production-provider: переход при открытом приложении,
  дубликаты, поздний initial query, смена во время IPC, быстрый возврат Wi-Fi,
  отказ и повтор, dispose, все online-личности без двойного уведомления.
- Совместно с тестами приёма транспорта и анонимной диагностики: 24 passed.
- Анализ семи затронутых Dart-файлов: без замечаний.
- Проверка opt-in анонимного diagnostic-артефакта: passed.
- Отдельная ARM64 Android QA-сборка собрана; все три native-библиотеки в ней
  побайтно совпадают с опубликованными библиотеками, извлечёнными с телефона.
  Изменения приложения не требуют замены native SDK.

В анонимной диагностике сохраняется `networkChange`: coarse `state`
(unknown=0, wifi=1, cellular=2, ethernet=3, offline=4), `success` и `durationMs`.
Это результат локальной попытки уведомить узел, **не** подтверждение доставки
звонка или восстановления сети. SSID/IP/интерфейсы/ключи/число скрытых личностей
не собираются этим событием.

### Что остаётся

Первая установка изолированного QA-приложения на Poco была отклонена Android с
`INSTALL_FAILED_USER_RESTRICTED`. В следующем подготовительном цикле установка
для пользователя 0 с подтверждением штатного диалога прошла; отдельный QA-профиль
создан обычным onboarding, `/health` вернул `ready`. Dart-код соответствует
`d6de0ac0`, три native-библиотеки APK совпадают с опубликованными. Это снимает
прежний блокер установки, но само по себе не подтверждает восстановление звонков.
На этом подготовительном этапе контрольные звонки ещё не выполнялись, настройки
сети телефона не менялись, основное приложение и его личность не заменялись.

Для закрытия нужен фактический входящий вызов на компьютере после перехода
Wi-Fi → mobile и работающее аудио после ответа. Отдельно фиксировать время
события ОС, появления пригодной новой сессии, отправки offer и его приёма;
одного узла в UI или успешного локального уведомления недостаточно. Смену сети
во время разговора учитывать отдельным результатом, не выводить её исправность
из успешного нового вызова.

Статус репорта остаётся открытым: **правка подтверждённого пробела выполнена;
полное устранение пользовательского симптома не подтверждено**. Результаты
последующего физического цикла приведены ниже.

Windows: новая Dart AOT-сборка также собрана и запущена с отдельным QA-профилем;
после разблокировки `/health` показал `ready`, `realStack=true`, prod. В devlog
не обнаружено `handover notification failed` или `MissingPluginException`.
Это проверка запуска приложения с новой проводкой, а не handover-звонка.
Runner/plugins и native-библиотеки остаются опубликованными; полная сборка
Windows C++ ограничена отсутствующими на стенде ATL headers.

После проверки QA-приложение Windows остановлено, обе собственные scheduled
задачи отсутствуют, SSH-туннель закрыт. В том Windows-цикле QA-процессы на
телефоне не запускались; неизменность Wi-Fi/mobile data проверена повторно.
Последующий запуск Android QA для подготовки отмечен выше. Push и релиза нет.

Дополнительный контроль после добавления проводки: Mac → Windows установил
звонки с аудиопакетами/выходными сэмплами по P2P и принудительному relay при
стабильной сети. [Границы контроля](../receive-only-audio-2026-11-01/README.md):
на Mac явно использована более старая native SDK. Это не проверка смены сети
на Poco и не основание закрыть NETCALL-01.

### Физический цикл Poco → Windows и backoff call-control

[Новая проверка](../call-handover-retry-2026-11-01/README.md) использовала
изолированные профили реального Poco и Windows 11. В трёх немедленных вызовах
после отключения Wi-Fi входящий появился за 0,77–0,83 с. Исходное условие ровно
одного активного узла специально не создавалось. В первом случае ответ Windows
пришёл с большой задержкой; найден отдельный механизм длинных интервалов
повторения сигналов, подтверждён красным regression и исправлен ограничением
backoff двумя секундами. 130 связанных тестов прошли; это не SLA доставки.
Последний вызов на текущих QA с обеих сторон стал `active` через 5,31 с.
Серии не являются A/B, вся прежняя задержка правке не приписывается.

При переключении внутри активного звонка все три разговора сохранили call ID,
но возраст последнего audio payload доходил до 12,4–14,7 с, включая текущие QA.
Эта пауза — **подтверждённый открытый дефект**, а не отложенная гипотеза. Речь
человеком не проверена, жалоба об отсутствии слышимого звука не закрыта.
Стенд остановлен, сетевые настройки восстановлены, основное приложение не
заменялось; опубликованных обновлений нет.

### Поздний первый capture-отчёт и история приёма при rebuild

[Следующий цикл](../late-capture-audio-recovery-2026-11-01/README.md) подтвердил
два дефекта. Первый `capture.audio=true`, пришедший после аудиопакетов, начинал
expectation заново и лишал ранний детектор свидетельства установленного приёма.
Пересоздание медиадвижка также стирало время последнего реального приёма для
liveness. Обе ошибки исправлены; startup grace для явного unmute/нового receive
session и 20-секундный liveness timeout сохранены. Прошёл 261 связанный тест.

На физической QA с первым исправлением Windows запустил раннее audio recovery
при native age около 3,8 с, но relay candidate оставался неподтверждённым.
Один прогон сохранил звонок, второй завершился по liveness timeout. Прежнее
утверждение «все звонки в двух новых прогонах пережили переключение» отозвано:
наблюдатель ошибочно пропускал очистку call в null; теперь это считается отказом.
Значения native age до 14,5 с относятся к отдельным media epoch, не являются
верхней границей всего перерыва. Итог проверки обоих исправлений и агрегаты —
в отчёте цикла. Общий NETCALL-01 и жалоба о слышимости не закрыты.

### Закрытие outbox при переключении сети

[Следующий цикл](../session-outbox-close-2026-11-01/README.md) подтвердил и исправил
игнорирование EOF исходящей очереди ожидающим SessionRunner. Это задерживало
возврат к существующему teardown до чужого таймера/сетевого события. Красные
regression и полный session/integration/FFI наборы подтверждают исправление
механизма. Физический кандидат сохранял разговор, но audio age снова достигал
примерно 14,3 с; вся пауза не устранена. Новый немедленный post-cut вызов дошёл
до Windows за 1,1 с. Исходное условие одного активного узла не квалифицировано;
NETCALL-01 остаётся активным.

### Принудительное закрытие при копии sender

[Следующий цикл](../registry-retirement-2026-11-01/README.md) исправил задержку
административного unregister при удерживаемом producer sender, в том числе у
неопрошенной future production-адаптера. Обычная замена регистрации сохраняет
поддерживаемую отправку в прежний канал. Прошли 677 session, 119 integration и
334 FFI теста; ignored посчитаны отдельно.

В физическом кандидате звонок пережил переключение, но непрерывный свежий RX
не подтверждён (максимальные sampled ages 4,1/6,3 с). Новый post-cut входящий
появился за 1,1 с, первые свежие RX-срезы — примерно через 19,9 с после cut.
Причинный эффект правки на эти времена не доказан. NETCALL-01 остаётся активным.

### Отдельно: доставка сигналов и запуск медиа

[Разложение сохранённого случая и новый парный прогон](../call-signaling-delay-2026-11-01/README.md)
уточнили прежние ~20 с: телефон ждал `answer` в состоянии dialing примерно
17 с, а первый свежий RX наблюдался примерно через секунду после первого
connecting-среза. Это не доказательство 20-секундного запуска аудиодвижка.
Быстрые повторы ответа реально выполнялись; долгий старый backoff в этом
случае не подтвердился.

На SDK `8eab7507` с обеих сторон новый post-cut `offer` дошёл до Windows за
16,652 с, ответ — быстро. При отдельной смене сети внутри активного P2P-звонка
оба endpoint сохранили call state все 40 post-cut срезов, но непрерывный свежий
RX не прошёл; максимальные sampled ages — 10,3/13,5 с, телефон не прошёл
fresh-RX guard на последнем срезе. Ровно один активный узел не создавался.
Для следующего обращения отдельно сохраняются 12 обезличенных этапов звонка,
чтобы транспортный поток не вытеснял их до копирования отчёта. Правка журнала
проверена unit/report/AOT-тестами и ещё не включена в физический frontend этого
цикла. NETCALL-01 и жалоба о слышимости остаются открытыми.

### Подтверждение обработки уведомления до закрытия клиента

[Следующий цикл](../network-notification-receipt-2026-11-01/README.md) подтвердил
потерю NetworkChanged в локальной writer-очереди при немедленном уничтожении
временного runtime. Два regression были красными, включая реальный client/server
с 0 callbacks вместо 1. SDK теперь дожидается существующего inline RPC на том
же IPC-соединении, прежде чем временный клиент можно закрыть.

420 native-проверок и 9 Flutter observer/provider тестов прошли; 3 ignored
посчитаны отдельно. На Poco новый вызов после cut дошёл за 7,281 с, setup/RX
квалифицирован. Но active-handover **не прошёл**: примерно через 21,2 с вызов
исчез на обоих концах с livenessTimeout. Уведомление обработано около +0,696 с
и сняло одну TX-регистрацию; после него были Network unreachable и таймауты,
наблюдаемые новые сессии появились только через 16–22 с. Вся оставшаяся проблема
не объясняется потерей уведомления. Следующий кандидат — отмена старого dial
при смене сети. A/B нет; ни ускорение, ни причинная регрессия не доказаны.
NETCALL-01 остаётся активным, условие одного узла на момент place не проверено.

### Отмена незавершённого dial при смене сети

[Следующий цикл](../pending-dial-network-change-2026-11-01/README.md) подтвердил:
connect-ветка outbound connector не слушала force-reconnect, в отличие от
backoff-ветки. Тест с настоящими NodeServices и gated transport был красным
по отсутствию отмены. Теперь старая попытка отменяется, проверки peer и dial
начинаются заново. Прошли 785 runtime и 334 FFI теста, 13 ignored отдельно.

Новый post-cut вызов в итоге установился; активный P2P-звонок пережил все
40 post-cut срезов со свежим RX в конце. Но непрерывный RX не квалифицирован:
sampled ages достигли 15,5/14,5 с. Это не A/B и не закрытие всей паузы.
Следующий отдельный стенд по запросу владельца —
[линия из шести testnet-узлов](../linear-testnet-2026-11-01/README.md),
с проверкой P2P и полного relay-маршрута. Пока выполнена только подготовка,
звонки через линию не проверены. NETCALL-01 остаётся активным.
