# NETCALL-01: парный native-захват проб при Wi-Fi → cellular

Дата: 2026-11-01. Дополнительный физический прогон после `15791454`.
Production-код и бинарники в этом цикле не менялись. Получен парный native-захват,
сужающий следующий участок расследования. **Перерыв аудио не устранён.**

## Физический результат

Poco ↔ Windows 11, прежние отдельные QA-профили, production-сеть. Перед cut оба
endpoint действительно имели один ожидаемый active call, P2P и свежий audio RX.
Wi-Fi был default network, после cut default стала cellular. Проверки исходного
случая с ровно одним активным узлом и живой речи человеком в этом цикле не было.

Один call ID сохранился на всех 40 выборках после cut; наблюдение длилось около
41,7 с. В конце свежий аудиоприём был на обоих устройствах. Максимальный sampled
native age: Poco 11358 мс, Windows 14685 мс. Это значения внутри отдельных media
epoch, **не верхняя граница всего перерыва**. Критерий непрерывного свежего аудио
не пройден. Причинное улучшение/ухудшение относительно прошлых серий не заявляется:
нет fixed-route A/B, а native trace был включён с обеих сторон.

## Что добавили native-журналы

На телефоне две ранние relay-квалификации (бюджет 600 мс) начались через 6011 и
14916 мс после `ipc.mobile.network_changed(kind=Cellular)`. Это интервалы в часах
одного телефона; они не требуют сверки часов с Windows. Сразу после начала каждой
попытки наблюдалась первая sealed cell нового candidate: sequence 1, 60 байт,
`media.cell.sample stage=relay_send`. Для обеих имеются точные совпадения
header/sequence/size с локальным `ipc.rt_trace.sealed_sample stage=relay_queued`.
Это **доказательство приёма локальной очередью первого хопа**, не отправки в сеть
и не доставки получателю.

В native-захвате Windows не наблюдалось соответствующих authenticated `received`
для этих двух заголовков. На телефоне не наблюдались matching replies именно
для двух ранних попыток. Поздняя relay-квалификация началась через 24742 мс после
того же события ОС и получила matching reply за 347,063 мс, внутри прежнего
600-мс бюджета. Непрерывный RTP и попытки квалификации разных маршрутов — разные
наблюдения; эти времена не объявляются длительностью перерыва аудио.

Не установлено, где находятся первые две клетки между локальной очередью
отправителя и authenticated receive второго endpoint. В захватах нет notices
`observability.console_dropped`, но у этого AOT hook нет способа прочитать
flush/write-error counters native console в том же процессе. Поэтому полнота
console capture не квалифицирована; отсутствие записи **не доказательство
сетевого дропа**. Закрытый candidate также может уже не наблюдать поздний ответ.
Факт ответа позднее 600 мс не установлен, бюджеты/cooldown не менялись.

Следующий конкретный участок — сопоставить эти же opaque cells с transit/egress
на выбранных реле: queue admission → фактический исходящий транспорт → следующий
хоп → доставка endpoint. Реле не получают роль media или plaintext. Нужны
операторские локальные корреляции с ограниченным временем и возвратом конфигурации,
как в прежней проверке файлов; перезапуски production-реле в этом цикле не делались.

## Контроль отсутствующего Windows-вывода

Временный launcher с отсоединением родительской консоли позволил получить
native-файл. Однако последующий контроль **на исходном launcher**, тех же
бинарниках и с явно включённым Windows `rt_trace` тоже дал native-записи. Поэтому
прежнее объяснение «лог теряется из-за способа запуска» отозвано: два изменения
(launcher и включение trace) сначала были смешаны. Причина исторического пустого
файла не установлена. Изменять runner на основании этого опыта нельзя.

Поведение стандартных handles при attach зависит от наследования и
`STARTF_USESTDHANDLES`; это описано в
[Microsoft GetStdHandle](https://learn.microsoft.com/en-us/windows/console/getstdhandle#attachdetach-behavior).
Общая возможность такого эффекта не доказывает его наличие в нашем запуске.

## Воспроизводимый анализ и приватность

`scripts/summarize_media_probe_capture.py phone.log windows.log` принимает закрытые
журналы одного lifetime процесса с каждой стороны и выводит только агрегаты.
Сопоставление использует epoch/sequence/size внутри памяти; они, исходные строки,
адреса, peer/call IDs, токены, пути и payload в JSON не попадают. Размер 60 байт
сам по себе **не определяет тип plaintext**. Сопоставленные исходные клетки не
считаются доставленными на основании одного `relay_queued`.

Success/failure ratio из этих счётчиков не выводится: preparation и qualification
различаются, повторные ответы и другие живые контексты могут давать дополнительные
observations. `matches=false` не превращается в отказ собственного candidate.
Скрипт не сравнивает часы разных устройств и не выдаёт отсутствующим выборкам
статус потерь. Код выхода 0 означает только успешное построение сводки.

Девять новых тестов прошли: точная корреляция, неверный epoch/sequence/размер,
дубли, запоздалые/чужие/отменённые ответы, отсутствующий begin, пустой захват, локальный
admission против удалённого receive и privacy canaries. Восемь прежних тестов
handover analyzer также прошли. Flutter/Rust заново не собирались: их исходники
не менялись. Агрегаты — в [summary.json](summary.json); закрытые журналы не
добавлялись в репозиторий и не являются анонимными пользовательскими отчётами.

## Происхождение и завершение

SHA установленного Android APK повторно совпал с проверенным артефактом прошлого
цикла. Windows AOT SHA повторно проверен; три native DLL совпадают с опубликованными.
Runner/plugins не менялись. Временные изменения launcher были только в частном
стенде, исходный запуск отдельно проверен. Windows QA и его tasks закрыты,
отсутствие listener проверено через IPGlobalProperties. Телефонный QA и собственный
logcat остановлены; trace выключен на обоих концах. ADB-forward и SSH-туннель
закрыты, локальные listeners отсутствуют. Настройки телефона восстановлены,
основной процесс сохранил PID, его контейнер не открывался. Mac-стенд не запускался.
Push, релиза и обновления сидов нет.
