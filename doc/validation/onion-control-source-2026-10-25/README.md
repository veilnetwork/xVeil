# Очередь управления звонком и холодные маршруты — 25 октября 2026

Стенд: A/B — отдельные процессы одной личности X, C — другой личности Y.
Три локальных реле, настоящий SDK и медиадвижок, анонимная маршрутизация,
зашифрованные контейнеры. Отдельная C–B сессия не создаётся.

## Подтверждённые находки

| Находка | Проверка | Исправление |
|---|---|---|
| Анонимное управление звонком расходовало кредиты очереди восстанавливаемых данных вместе с файлами и синхронизацией | Один onion cell размером 16 КиБ занимает все четыре DATA-кредита; следующий DATA-пакет отклоняется даже после извлечения первого из входной очереди | `sendRealtime` явно выбирает существующую локальную полосу 1; её приём не расходует DATA-кредиты |
| Поиск маршрутов уже известных устройств начинался после обновления документа личности | Тест удерживает ответ с документом до запроса объявления устройства; прежний порядок не получает маршрут вовремя | Ограниченная предварительная загрузка публичных объявлений параллельно исходной отправке |
| Отмена DHT-поиска оставляла занятый слот ожидающего запроса | Тест отменяет действительно зарегистрированный запрос; прежний код сохраняет его в таблице | Очистка принадлежащих поиску записей при завершении и отмене через RAII |

Локальная полоса существует только на стороне отправителя. Анонимная
аутентификация и тело сообщения сохраняются; onion-заголовки не сообщают
реле, что передаётся звонок. Новых приоритетов на реле нет. Локальная полоса
не создаёт отдельную зарезервированную входную очередь и не устраняет любую
возможную перегрузку транспорта.

Предварительная загрузка ограничена восемью уже авторизованными устройствами.
Она не разрешает отправку: исходная операция по-прежнему обновляет документ
и проверяет точную пару личности и устройства перед передачей. Готовая
отправка не ждёт ненужных предварительных запросов; фоновые задачи не остаются,
ненужные объявления не включаются в периодическое обновление кэша.

SDK-коммиты: `6b8b26f6` и `1297b3de` (последний добавляет только тесты).

## Звонки на настоящем SDK

Время отсчитывается от принятия звонка на B. Опрос состояния — примерно раз
в 400 мс. Это отдельные прогоны, не p95 и не распределение задержек.

| Сборка, A online | Ответ замечен C, мс | Двусторонний приём RTP, мс | После замеченного ответа, мс |
|---|---:|---:|---:|
| Только предварительный поиск маршрутов | 19 121 | 19 594 | 473 |
| Исправлена локальная очередь управления | 3 721 | 4 137 | 416 |
| Повтор исправленной сборки | 3 692 | 13 975 | **10 283** |

Предварительный поиск сам по себе ускорения всего звонка не доказал.
После выбора локальной полосы задержка ответа сократилась в двух прогонах,
но **холодный запуск медиа остаётся нестабильным**. Последний результат
не позволяет считать установление звонка исправленным целиком.

В первом исправленном прогоне поиск документа получателя ответа закончился
через 3 502 мс от первой попытки B отправить ответ; доставка аутентифицированного
ответа в native-слой C зарегистрирована через 3 509 мс. Остаточное ожидание
ответа в этом прогоне приходится преимущественно на поиск метаданных.
Причина отдельного ожидания медиа в повторе ещё не установлена.

При offline A исправленная сборка в двух прогонах дала ответ за 38/35 мс,
двусторонний RTP за 451/452 мс. Во всех трёх конфигурациях после начала медиа
счётчики приёма B/C росли в течение пяти секунд, A не удерживал звонок,
завершение с B доходило C. Это проверка пакетов, а не разборчивости речи.

## Продолжение: физический Android и раздельные направления медиа

Отдельная QA-сборка обновлена до приложения `ba4c50c9` и SDK `1297b3de`.
Android-библиотеки собраны с production-seeds, без test-low-difficulty;
медиадвижок собран без тестовых хуков. Хеши библиотек внутри APK сверены
с результатом штатного удаления символов из свежих нативных сборок.
Первичная настройка новой тестовой личности закончилась; приложение
открыло настоящий сетевой стек. Основная установка пользователя сохранена.

На физических Mac и Android:

* Системное окно сохранения сертификата открылось, запись завершилась,
  содержимое файла совпало с сертификатом. Использована отдельная тестовая
  личность; экспортированный тестовый файл после проверки удалён.
* Запрос контакта Android → Mac: 4 999 мс; весь обмен до получения
  подтверждения на Android: 6 259 мс.
* Mac → Android: файл 8 МиБ, отправитель принудительно завершён на 4 МиБ,
  запуск через 10 секунд. Загрузка закончилась за 38,747 с, SHA-256 совпал.
* Android → Mac: тот же размер и остановка источника на 4 МиБ. Загрузка
  закончилась за 90,331 с, SHA-256 совпал. После перезапуска были повторные
  открытия стрима, отказ авторизации и повторное объявление источника.
  Файл восстановлен, но длительная пауза перед возобновлением остаётся
  предметом исследования. Источник её целиком пока не установлен.

Обе передачи выполнялись с запрещённым P2P для тестового контакта.
Проверка не подменяла транспорт локальным копированием файла между получателем
и отправителем; локально сравнивалась только контрольная сумма результата.

Автоматический аудиозвонок Android → Mac через реле: входящий за 203 мс,
двусторонний приём пакетов за 1 863 мс после ответа. За следующие 15 секунд
счётчики приёма выросли на 313/392 пакета; вызов завершён на обоих устройствах.
Первый запуск до выдачи разрешения на микрофон свежей QA-установке закончился
ошибкой запуска аудио; повтор выполнен с разрешением. Это различие настройки
стенда, а не подтверждение исправления отсутствия звука в пользовательском
репорте. Живая речь, громкость и видео не проверялись.

После проверки QA-приложение на Android остановлено, собственные группы
процессов Mac проверены после завершения, собственный ADB forward удалён.
Разрешение на микрофон тестовой установки возвращено в исходное состояние;
тестовый профиль Mac перенесён обратно в закрытый каталог стенда.

В следующем локальном прогоне добавлены наблюдения по каждому направлению,
только в тестовом сценарии. При online A первые пять пакетов приняты C
через 3 766 мс, B — через 5 801 мс от принятия вызова. При offline A:
C — через 439 мс, B — через 14 253 мс. Пока B показывал нулевой приём,
на C рос счётчик передачи, а обратное направление B → C уже работало.
Это локализует наблюдаемую паузу до направления C → B после старта
движков, но ещё не разделяет очередь отправителя, маршрут и обработку
на получателе. Отдельные успешные быстрые прогоны выше этой проблемы
не исключают. Все процессы локального стенда завершены и проверены.
