# Отправка каждой личности через регистрации её устройств — 25 октября 2026

Следующий цикл проверки выявил перезапись документа с отзывом устаревшей
публикацией. Повторный тест с отозванным B сначала завершился неудачей;
обработчики записи исправлены и сценарий повторён. Подробности, границы
проверки и оставшаяся задержка первого ответа — в
[отчёте следующего цикла](../onion-family-document-refresh-2026-10-25/README.md).

A/B — отдельные процессы личности X, C — процесс личности Y. Использованы
настоящий SDK, три локальных реле, зашифрованные контейнеры и анонимный режим.
Отдельная C–B сессия не создавалась; публичные сиды отключены.

## Причина задержек

Реле хранит session-backed rendezvous по паре `(receiver, cookie)`.
При регистрации устройство получает собственную запись и, при наличии
проверенного делегирования, дополнительную запись общей личности.
A и B используют общую cookie, но разные ключи X25519. Дополнительная пара
`(X, cookie_X)` вмещает одного получателя: регистрацию второго устройства
отклоняет защита от подмены ключа. Пары `(A, cookie_X)` и `(B, cookie_X)` при этом
независимы и могут одновременно работать.

Прежний анонимный отправитель выбирал объявление общей личности и отправлял
только туда. Объявление могло принадлежать B, тогда как регистрация общей пары
ещё принадлежала A. При offline A доставка зависела от обновлений и повторных
попыток. Пересылка предложения звонка между своими устройствами помогала, когда
первый адрес всё-таки получал его.

В исходном прогоне зафиксированы **20** отказов регистрации B под X с причиной
`PubkeyRotationNeedsFreshCookie`. У C при этом уже было **2** chat-объявления
физического B. Несмотря на online A/B, звонок не появился ни на одном из них
за **60 с**. Отдельный прогон предыдущего цикла показал входящий на B через
**33.053 с** при offline A. Это разные замеры; первый отрицательный тест до
своего offline-этапа не дошёл.

## Изменение

* При отправке на адрес личности SDK получает её проверенный текущий документ
  и отправляет кадр на физический адрес каждого разрешённого устройства.
* Поиски и отправки выполняются параллельно, с прежними ограниченными сроками.
  Недоступное A не удерживает отправку B за своим поиском. Число устройств
  ограничено протоколом документа — максимум 8.
* Перед непосредственной отправкой проверяется конкретная пара «личность,
  устройство» через общий монотонный авторизационный барьер. Известный отзыв,
  срок ключа и подтверждение сохранения продолжают ограничивать доступ.
* Адресованная конкретному устройству синхронизация остаётся адресованной ему;
  обратной рассылки всей семье нет. Одинаковые кадры по нескольким путям
  по-прежнему дедуплицируются идентификаторами приложения.
* Для неизвестного документа сохранён прежний путь к самостоятельному узлу.
  Известная личность без разрешённых устройств не получает запасного пути,
  обходящего её авторизацию.
* Ответ через одноразовую reply-circuit очищает состояние зависшей отправки
  и у личности, и у доказанно ответившего физического устройства.

Защита регистрации реле от смены чужого ключа не ослаблена. Протокол и FFI ABI
не менялись, новых разрешений relay или признаков типа медиа на проводе нет.
Mailbox не расширялся. Серверы и пользовательские приложения не изменялись.

## Проверки

* **715 тестов runtime и 366 тестов FFI прошли**, по 11 штатно отключены в каждом наборе.
* Строгий Clippy runtime `--lib --tests -- -D warnings`: чист.
* Dart-анализ нового сценария: замечаний нет.
* Проверены выбор обоих физических адресов, исключение отозванного устройства,
  невозможность возврата через старый документ, истечение срока и запрет до
  подтверждения host checkpoint.
* Native SDK пересобран, CLI и FFI заморожены по SHA-256 с проверкой
  884 Rust/Cargo-файлов. Native медиадвижок не менялся относительно предыдущего
  цикла и также проверен по хешу; он собран без test hooks.

Оба принятых звонка сохранили onion. Счётчики проверялись на реальном приёме,
а не по локальному ответу SDK об очереди. Разборчивость речи не проверялась.
Задержка установки первого медиапотока **9.897 с** остаётся отдельной проблемой;
полное устранение задержек сигнализации не заявляется.

## Повторный прогон и регрессия сообщений

В итоговом сигнальном тесте предел для **обоих** режимов online/offline установлен
в **10 с**: online-ограничение ужесточено с 60 с после исходного отрицательного
прогона. SDK-библиотека в повторе та же, что в первом положительном прогоне.
Оба устройства зазвонили за **49 мс**, после выключения A устройство B — за
**429 мс**. Отмена C дошла в обоих случаях. Базовая версия исходного теста
сохранена вместе с приватным доказательством её хеша; отрицательный результат
не заменён положительным.

Регрессия доставки и отзыва также прошла:

| Действие и состояние | Фактический результат |
| --- | --- |
| A offline после привязки B, C отправляет личности X | B получил за **430 мс** |
| A/B/C online, C отправляет новую запись | По одной копии на A/B за **833 мс** |
| Повторное открытие B | Обе записи сохранены, дублей нет |
| B/C offline, A отзывает B; затем B/C возвращаются со старым состоянием | Активный A получил новую запись C; на B её не было за **20153 мс** наблюдения |

Непосредственная проверка права конкретного устройства остаётся обязательной
после поиска маршрута: самостоятельная подпись физического объявления не даёт
отозванному устройству права получать данные личности.

Каждый стенд закрыт и проверен отдельно по PID и process group. Базовый,
сигнальные и медиастенд: по **5 групп / 9 PID**, регрессия сообщений:
**9 групп / 13 PID**. Живых процессов и каталогов временных контейнеров нет.
После итоговых прогонов хеши исходников и программ сверены повторно.
Исправления SDK сохранены в `7415af3d`; hidden-volume не менялся.

## Границы

Это локальный стенд отдельных процессов, не физический Android/Windows или
межоператорная сеть. Длительный offline, вся матрица 63 сценариев, большие
файлы и все гонки изменения состава устройств здесь не квалифицированы.
Тесты выполнялись с `TMPDIR=/private/tmp/`; Rust-сборки следили за отдельной
файловой системой внешнего target и завершились без исчезновения монтирования.
В публичных материалах только агрегаты и хеши программ/исходников. Адреса,
ключи, runtime ID, контейнеры и сырые журналы остаются приватными.
