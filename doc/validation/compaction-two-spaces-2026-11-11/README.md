## Подтверждённые ошибки рядом со сжатием

1. Список был привязан к отображаемой подписи с порядковым номером, а не к
   паролю/пространству. Повторный пароль выглядел второй найденной личностью.
   Теперь прямое добавление одного пароля/SpaceKeys под другой подписью
   отвергается. Legacy-метод добавления subordinate-ссылок сохранён.
   Native-вызов дедуплицировал пароли и раньше: это не доказанная причина
   повреждения. Отдельные скрытые пространства с одинаковым паролем native
   библиотека создать не разрешает.
2. Исключение compactStorageKeeping выходило из callback, оставляя busy и
   отключённые кнопки. Теперь показывается ошибка и можно закрыть окно;
   повторное сжатие/пробы требуют нового сеанса сбора. Контроллер уже
   попытался открыть контейнер в finally — повторный unlock из Cancel после
   такого отказа не запускается. Ошибки пробы также снимают busy. В журнале
   сохраняются этап и frames, без исходного текста исключения/пароля/пути.
3. barrierDismissible:false не запрещал системный Back. Диалог исчезал, а
   сессия оставалась остановленной. PopScope запрещает такой выход;
   явная «Отмена» проходит штатное восстановление.
4. Controller теперь отказывает до teardown/native I/O, если список не
   содержит пароль, которым он обязан открыть текущую личность после сжатия.
5. Ввод дополнительных паролей больше не обрезает краевые пробелы.

Красные проверки до исправления: повтор под другой подписью принимался;
ошибка rewrite не обрабатывалась; system Back удалял диалог; отсутствие
reopen-пароля доходило до следующего шага вместо явного отказа. Ошибка
mock-предусловия SharedPreferences исправлена отдельно и не считается
дефектом продукта. Проверки — `compaction_failure_dialog_test.dart` и
существующие compaction suites.

## Android: переходы маршрутов при сборе паролей и завершении

На отдельном QA-приложении подтверждены ещё три ошибки интерфейса:

1. Контроллер публикует ready во время открытия, до завершения всей операции.
   GoRouter удалял страницу preparing вместе с диалогом; ожидающий его код
   получал null и объявлял успешно выполненное сжатие отменённым.
2. При быстром teardown диалог успевал привязаться к старой странице, прежде
   чем роутер отрисовал preparing. Следующее обновление удаляло диалог ещё
   до первого ввода пароля: хранилище закрыто, приложение остаётся на загрузке.
   Это воспроизведённое зависание интерфейса **до rewrite**, а не доказанное
   повреждение контейнера. После восстановления обе личности читались.
3. Завершение через Navigator.pop могло закрыть более новый popup вместо
   собственного диалога. Этот сценарий подтверждён GoRouter widget-тестом.

Теперь сборщик открывается после кадра с preparing, результат rewrite или
отмены ожидается отдельно от жизни диалога, закрывается только его маршрут.
Если сборщик удалён до запуска операции, сессия восстанавливается только при
сохранённой авторизации исходной личности. После lock/switch/dispose старый
пароль автоматического восстановления не используется. Это защита ветви
брошенного сборщика; lock/crash в процессе native rewrite ею не квалифицированы.

## Блокировка во время ручного сжатия и прерывание native-процесса

Следующая проверка подтвердила отдельную ошибку авторизации: lock завершился,
но поздний finally ручного сжатия всё равно вызывал unlock сохранённым паролем.
Красный сценарий — реальный AppController.lock при удержанном close; отказ
close до native rewrite приводил к неожиданному вызову unlock. На настоящей
библиотеке проверена и другая граница: rewrite/remap завершены, завершение
контроллера удержано gate, затем lock, затем отпускание gate. Старый контроллер
снова пытался открыть сессию. Парный контроль без lock сохраняет восстановление.

Исправление: исходная IdentityLease проверяется после stat, teardown и native
rewrite/remap; finally открывает контейнер только пока эта авторизация жива.
Уже запущенный native rewrite этим не отменяется. Тест считает вызовы unlock
через override, но lock, переписывание и remap выполняются настоящим кодом.
Это не физическая Android-квалификация новой проверки авторизации.

- `compaction_lifecycle_test.dart`: 4/4 passed с проверенной native-библиотекой,
  0 skipped. До правки сценарий отказа был красным; single-file rollback
  AppController отвергается обоими lock-сценариями, оба live-session контроля
  проходят. Замена одного файла, не всей исходной версии приложения.
- Вместе с `native/compaction_two_spaces_test.dart`: 7/7 passed, 0 skipped.

  Эти две итоговые серии не пересекаются; анализатор изменённых Dart-файлов чист.
- Отдельный Mac native процесс: два пространства, 16384 значения, суммарно
  33554432 проверяемых байта; исходный файл 90181632 байта. Три SIGKILL после
  наблюдаемой записи временного файла (278528, 8486912, 33722368 байт).
  Перед убийством процесс остановлен, исходный inode ещё на месте — проверка
  попадает **до rename**, а не угадывает стадию по времени. После каждого
  убийства исходный файл побайтно прежний; свежий процесс открывает оба пароля
  и проверяет каждый байт. Обычное завершение того же rewrite также проходит
  проверку всех данных, inode действительно заменён.

Native-прогон использует ту же проверенную hidden-volume 2.7.0, новую Rust-сборку
не делали. Синтетический KDF min; это не Android process-kill и не потеря
питания/проверка durability после rename. После SIGKILL остаются зашифрованные
временные файлы rewrite: стенд удалил свои файлы после проверки. Поведение
app wipe и авто-сжатия при незавершённом rewrite требует отдельного разбора;
его нельзя считать покрытым проверкой ручного сжатия или объявить исходную
потерю доступа исправленной.

В следующем раунде эти ветви разобраны отдельно: lifecycle авто-сжатия,
