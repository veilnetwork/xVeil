# Ответ на повторный запрос не держит входящую очередь — 2026-11-05

База `5fc5e2ff`. Локальная правка без push/релиза, APK/engine pins, изменений
сидов, Rust/native ABI и mailbox для собственных устройств.

## Подтверждённый механизм

При request/reconnect от уже принятого контакта `handleRequestOrReconnect`
повторял accept через `sendDurable` с ожидаемой первой сетевой попыткой.
Эта операция выполнялась внутри обычной сериализованной входящей полосы.
Локальный Outbox уже содержал ответ, но последующие кадры всё ещё ждали сеть
до стандартного `liveLegDeadline=10s`. В частности, там застревал следующий
call offer, пришедший на ordinary inbox. Независимая realtime-полоса этим
воспроизведением не квалифицировалась.

Четыре настоящих assertion-red на базе: request/reconnect × ordinary/worker
native HVS. Входящий запрос содержит frameId, как production handshake.
Его ACK транспорт не задерживает; gate держит именно accept. Затем через
обычный transport stream приходит offer. Перед снятием gate callback отсутствует
на базе и присутствует с исправлением. В тесте большой live deadline исключает
победу таймера как ложный успех; измерения скорости и порога latency нет.
Первоначальная ошибка fixture (несуществующий inject у LoopbackTransport)
исправлена до зачтённых red; compile failure не является product reproduction.

## Исправление

Ingress по-прежнему ждёт полного durable enqueue accept. Сеть запускается
отдельной PostReceiptQueue: 128 jobs / 128 KiB, до четырёх независимых получателей,
одна задача на получателя. Повторные запросы объединяются по одному стабильному ключу accept.
Рабочая задача ждёт реальную отправку, а не создаёт новую detached попытку на
каждое истечение таймера. Отказ/переполнение очереди оставляет durable retry.
Mailbox deposit и прежняя long-silent policy сохранены.

Перед отправкой проверяются точная текущая Outbox copy, accepted status и
владелец сервиса. В рабочей задаче нет повторного enqueue: ACK/retirement не
воскрешают старую запись. Закрытие сервиса останавливает waiting jobs и
присоединяет реальную активную отправку до закрытия транспорта/ratchet.
Подписи, provenance, consent, wire format и общие ACK/dedup gates не ослаблены.

## Проверки

Четыре новые fixture дополнительно проверяют восемь свежих request IDs при
удержанном ответе: второй initial send не появляется. Проверяется сохранённый
accept в Outbox, неизменность accepted contact, ожидание активной отправки
при dispose и сохранность ответа после cold reopen контейнера.

Scoped: **27 passed, без skip**: четыре новых случая (два native worker HVS),
request lifecycle, reconnect и PostReceiptQueue. Библиотека HVS сверена по
закреплённому SHA, native зависимости и артефакты не пересобирались.

Широкая серия: **1732 passed / 58 conditional skipped**, 93 файла. Skipped
не считаются пройденными native случаями. Изменение фигурных скобок после
этого запуска исключительно форматное; последующая control-серия проверяет
окончательные исходники.

Окончательная control-серия с `XVEIL_DIAGNOSTICS=true` и явно заданной native
HVS: **403 passed, без skip**. Включены CallService, realtime signaling,
diagnostic journal, mailbox stash, lifecycle/reconnect и queue guards. Analyzer
обоих изменённых lib и всего test чистый. Native ABI/артефакты прежние;
новых приложений стенда или серверных процессов не запускали.

## Границы

Это исправление одного доказанного ingress head-of-line. Его роль в репорте
ПК ↔ Android не атрибутирована: в исходном отчёте нет необходимых per-signal
стадий. Windows стенда сейчас недоступна по SSH, физического повтора не было.
User acceptance path и ранний общий ACK gate здесь не менялись; отказ durable
enqueue и вся транзакционность принятия контакта требуют отдельной проверки.
Оставшиеся причины задержек, весь multi-device набор и общая голосовая
связь этим не объявляются исправленными. Новый список стадий диагностики из
предыдущего раунда остаётся доступен для повторного пользовательского отчёта.
