# Повторные чтения файловых метаданных — 2026-10-31

**Подтверждено и исправлено:** `storeFile` читал manifest существующего файла,
затем повторно запрашивал его внутри `loadFile`. Для streamed-файла следовало
ещё одно чтение внутри `readFileRange`. При изменении длины новый файл всё равно
сравнивался с целиком прочитанным старым payload, хотя равенство уже невозможно.

Это лишние обращения к worker в том пути, где предыдущие физические замеры
показали дорогие save/no-op. Их вклад в полную догрузку этим раундом не измерен.

## Правка

- Уже прочитанный manifest передаётся приватным помощникам в рамках **одной**
  операции. Между вызовами ничего не кэшируется; public read/delete каждый раз
  читают актуальные метаданные.
- Различие записанного размера и длины новых байтов исключает только попытку
  no-op. Выполняется обычная настоящая замена с прежним порядком публикации.
- При равных размерах все прежние байты читаются и сравниваются. Изменение
  содержимого той же длины и отсутствие chunk не могут дать ложный успех.
- Streamed read, проверка `maxBytes`, сборка записей, GC, публикация новых
  метаданных и удаление прежних записей сохраняют свои проверки и границы.
  При замене streamed-файла manifest переиспользуется и для планирования purge;
  сведения о самих piece-run по-прежнему читаются из хранилища.
- В GroupService, подписи, ratchet, протокол ACK и транспорт правок нет.

## Контроль на настоящем worker

Выполнен A/B/A со старым/новым/старым Dart-кодом и одной проверенной native
библиотекой hidden-volume. Каждый раз — свежий тестовый контейнер, настоящий
worker, 100 повторов для каждого размера. Facade `AsyncFileStore` создаётся
заново на каждом повторе, поэтому снижение нельзя объяснить instance cache.

| На 100 одинаковых сохранений | Старый A₁ | Кандидат B | Старый A₂ |
|---|---:|---:|---:|
| Manifest RPC, каждый из размеров 2 / 6000 / 64000 Б | 200 | 100 | 200 |
| Body batch RPC, каждый размер | 100 | 100 | 100 |
| Коммиты | 0 | 0 | 0 |

Суммарно: **600 → 300 → 600** чтений manifest при неизменных 300 чтениях
payload в каждой фазе. Это 900 → 600 → 900 RPC на проверенные no-op, считая
только manifest и body. Другие операции HVS/GroupService сюда не включены.

Контроль замены 2 → 3 Б: manifest RPC **2/1/2**, body RPC **1/0/1**,
коммиты **2/2/2**. Порядок commit и durability не ослаблены.

Время 100 no-op, мс: для 2 Б — 30,161 / 21,267 / 31,158; для 6000 Б —
39,091 / 31,496 / 38,659; для 64000 Б — 257,666 / 249,505 / 259,239.
Это один локальный worker-микропрогон по каждому профилю, не оценка полной
доставки или Android под нагрузкой. Основное доказательство — счётчики RPC.
