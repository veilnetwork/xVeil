# Меньше резервных коммитов при пакетной догрузке

## Подтверждение и исправление

Каждая полная prepared-публикация из 64 строк исчерпывала обычное окно
внутренних log IDs (максимум 64). Следующая порция требовала отдельного
durable reserve commit, помимо самой записи данных. На parent контроль
1024 сообщений потребовал **16** резервных коммитов вместо проверяемого
предела **6** — assertion-red, без таймингового порога.

Durable-барьер сохранён: ID выдаются только из подтверждённого резерва,
данные и shard markers публикуются прежней транзакцией, fresh admission и
erasure guards выполняются перед ней. Запись данных не объединялась с
резервом: параллельные потоки и потерянные ответы сохраняют прежнюю модель.

У полных **успешных** prepared-порций появилось отдельное окно 64→128→256.
Рост учитывает фактически выбранные новые строки/ordering ops; отказ,
неполная порция, noop и uncertain reply не увеличивают его. Обычные записи
сохраняют 8→64, обычный новый сеанс начинает с 8, prepared — с 64. Lifecycle
reset сбрасывает накопленное состояние, старый store не прогревает новый.

Максимум prepared reserve — **256 внутренних ID**, с прежним clamp на
конечной shard capacity. Это не page/publication budget: wire page 128,
128 КиБ/64 части, публикации по 64 и live coalescing по 16 прежние. Кэша
авторизации/истории нет; sibling mailbox не включён.

Цена: неиспользованный остаток резерва после штатного перезапуска или падения
может стать пропуском **внутренних log IDs**. Для этого пути окно ограничено
256; отдельно существуют уже выданные, но ещё не опубликованные ID и явно
большие allocations. Это не потеря сообщений и не разрыв author sequences.
Обычные-only сеансы сохраняют прежнюю политику 8→64 с теми же исключениями
для явно больших allocations. Формат, число namespaces и их capacity не менялись.

## Регрессионные проверки

Проверены reserve census, границы неиспользованного окна, холодное открытие,
раздельный reset обычного/prepared окна, отказ admission, partial/noop,
отказ записи и потеря ответа после commit, блокировка grown reserve,
следующая меньшая обычная запись, уникальность физических ID и финальный shard.

Native-проверки на настоящем зашифрованном контейнере подтверждают:
1024 строки сохраняются, reserve commits ≤6, 16 data cohorts по 64;
после двух рестартов окна начинают с 8/64. Во время ожидания/refusal/потери
ответа резервирования новые данные не публикуются. Затем обычная запись и
повтор bulk дают полный набор 257 сообщений, unique physical IDs и
`conversationSync` highWater=257 без holes после повторного открытия.

**393 related passed / 0 skipped**, отдельно **19 native cohort checks**;
analyzer чист. Ранние семь native Outbox skips выполнены повторно с
закреплённой библиотекой. Первые три новые native-проверки были невалидны:
тест читал внутренний `msg_next_id` через API пользовательских настроек
(префикс `set:`). Исправлен прямой native read; исходный отказ сохранён
в приватном evidence и не засчитан как пройденная проверка.

## Native A/B/A

Parent `c7602344` → candidate → parent. Общие instruments, четыре Mac/JIT
процесса, три изолированных Core, настоящий FFI/ratchet/HVS. Два полных
источника, первый apply удержан до authenticated ответов обоих. Compact
observer каждые 5000 мс, sampling/work trace/VM timeline выключены; seed и
проверка исходного append order выполнены до измеряемого окна.

Резервных коммитов стало меньше на **1171–1172**, данные сохраняются прежними
порциями. Общий RPC total **не уменьшился**: сокращение одной категории
durable commits не выдаётся за сокращение всех чтений/запросов или чистое
время fsync. Source query→reply P50: parent 81–84 мс, candidate 75–78 мс.
Full reply→next query P50: parent 168–171 мс, candidate 141–147 мс; этот
интервал включает очередь, применение, cursor, подготовку запроса и доставку.

Все **100000 архивных плюс одна прежняя строка** совпали по ID, телу,
delivered, canonical positions и порядку, без пропусков/дублей/лишних строк.
Оба cursor завершены, cold boot без A/E/C сохранил полный набор. Не засчитаны
только равенство счётчиков или пустые snapshot. Wire/census не обрезаны.

В каждой фазе по 782 page queries на источник, без повторных запросов;
200002 apply callbacks. Одинаковы **54217516 application-frame bytes** каждого
источника — это не полный сетевой трафик. Setup census подтвердил одинаковые
100001 строки и append order (1 новая + 100000 архивных) у обоих источников.

На этом стенде candidate быстрее обоих контролей на **26–31 с**. Observer
имеет шаг 5000 мс и включает финальную проверку; независимый passive witness
показывает сокращение этапа примерно на 28–32 с. Он включает доставку
следующего inventory и не является точной меткой UI. Это одна локальная JIT
серия, не универсальный коэффициент для AOT/Android или другой нагрузки.
**Latency остаётся активной: около 3 мин 30 с на 100000 сообщений.**

## Происхождение и уборка

**1531 frozen inputs**, один production variant, остальные 1530 одинаковы.
Candidate восстановлен; все исходники совпали с квалифицированной фазой B.
Runtime allocator census также отличает candidate от обоих parent controls.
Native SHA/mappings проверены до/после, Rust не собирался.

нет, synthetic runtime удалён. Cache **92→92** во всех фазах, новых entries 0;
место во время измерений не чистилось. Свободно около **149 ГиБ**. Приватные
данные проверяются по полным изменённым файлам и новым reachable Git objects.

Агрегаты: [summary.json](summary.json); raw captures/IDs приватны. Сохраняются
оставшиеся apply/очереди, source scan, NETCALL-01, физическая/AOT квалификация
и остальная multi-device matrix. Коммит локальный unsigned, push/релиза нет.
