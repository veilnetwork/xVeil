# Одно чтение контейнера при получении контакта

Агрегаты: [summary.json](summary.json).

## Подтверждение и изменение

В предыдущем native-прогоне догрузки у B было 5603 `kv.get.contacts`.
Проверка кода нашла лишний запрос: `getContact` читал запись для проверки
наличия, затем `_contactFor` повторял чтение для декодирования. На рабочем
storage worker это две отдельные RPC вместо одной.

Теперь `getContact` разбирает уже полученные bytes через общий приватный
decoder. Его тело побайтно совпадает с прежним разбором. Кэш не добавлен:
каждый вызов заново читает контейнер и видит актуальную блокировку/политику.
Отсутствующая запись в `getContact` остаётся `null`, а fallback списка чатов
без записи — `pendingOutgoing`, не согласие на переписку.

Детерминированный тест читает 32 сохранённые записи разных статусов через
публичный Storage API с in-memory KV, проверяя результаты и namespace reads:
**64 на базе → 32 после правки**. База — 1 assertion-red / 2 passed.
Контроли проверяют добавление, блокировку, удаление без кэша и передачу
ошибки чтения вызывающему коду вместо ложного `null`.

## Связанные проверки

- 181 passed / 24 native skipped в storage/history/contact suites, включая
  три новых теста. Пропуски не считаются passed.
- Затем те же contact decision/preferences/consent suites запущены с
  immutable HVS: 48 passed без пропусков, из них 24 native. Остальные
  24 пересекаются с первым запуском; числа не суммируются как уникальные.
- Гонки stale accepted → block по-прежнему не разрешают call offer и
  endpoint-control; отсутствующая запись не становится согласием.
- Analyzer и diff checks чисты. Первый ошибочный запуск с несуществующим
  именем test-файла не засчитан; итоговые suites выбраны из существующих.

## Native regression: 2000 сообщений

Три Mac/JIT приложения A/B/C, A/B одной личности, C другой; три loopback
Core, настоящий transport/ratchet и HVS. Provider fixture, не полный
foreground SessionPipeline, мобильный провайдер или Android.

| Измерение | До (`3acd5a58`) | После |
|---|---:|---:|
| Все 2000 строк у B | 32,737 с | 32,439 с |
| Полные ID/порядок/позиции/delivered | 38,065 с | 37,664 с |
| `kv.get.contacts` у B | 5603 | 3219 |
| Сумма ожиданий этих RPC | 18,097 с | 16,271 с |

Сумма ожиданий параллельных RPC не равна вкладу в wall-clock задержку.
Снижение чтений подтверждено отдельным контролируемым тестом; общий выигрыш
по времени **не доказан**. По одному сквозному прогону на свежих identities,
с poll около 5 с и разным scheduling — не строгий A/B. Видно, что основная
задержка догрузки остаётся. В новом прогоне также 430 message-log и 746
settings namespace commit observations; это не число уникальных общих
транзакций, поскольку одна транзакция может затрагивать разные namespaces.

Все 2000 исходных ID, итоговый порядок, канонические позиции и `delivered`
сошлись без дублей/потерь. Между полным count и итоговой сходимостью ещё
наблюдалось различие позиций; oracle дождался исправления. Повторов
завершённой истории — 0. Offline/crash сценарии migration-only не выполнял.

SDK `b9b88bb7` и HVS `eceb9158` прежние. Проверены SHA immutable FFI/CLI/HVS
до и после прогона, а также OS mappings двух библиотек во всех трёх рабочих
процессах, включая перезапущенный B. 1498 frozen source/package inputs
остались неизменными; CPU profile содержит samples. Сырые IDs, адреса и
журналы приватные.

Стенд остановлен: 22 PID / 34 порта проверены, своих процессов/listeners нет,
runtime root удалён. Телефон отключён пользователем; production-реле и
пользовательские контейнеры не затрагивались. Push/релиза нет.
