# NETCALL-01: пробуждение relay retry после возврата сессий

## Уточнение последнего захвата

Во [втором AOT звонке](../call-direct-admission-reuse-2026-11-08/README.md)
шесть коротких наблюдений relay-кандидатов на Poco прошли до открытия новых
сессий с Core. 18 зашифрованных 60-байтовых source cells сопоставлены с
`socket_written` → `daemon_read` → `handler_enter` на телефоне (как правило
≤1 мс, один обработан через 7 мс). Relay queue admission и получателя для
этих cells в захвате нет. Новые Core session.open — около +12,97/+13,03 с;
следующий кандидат телефона начал проверку лишь на +20,83 с. Поэтому прежняя
гипотеза об исключительно позднем обратном echo не объясняет эти 18 cells:
до обработчика они дошли быстро, но пригодной overlay-сессии ещё не было.
Для следующего успешного кандидата есть source queue, Core A и received
на Mac; совпавший fresh reply получен за 379780 мкс.

Дополнительные TCP-данные отделяют первое ожидание от call FSM: четыре
ранних obfs4 client handshakes отправили 107–149 байт и завершились с 0
прочитанных байт; kernel acked_bytes=1 (SYN), retransmitted_bytes=321–596.
Последующие соединения завершили handshake за 152/170 мс. В PCAP двух Core
для ранних flows видны SYN/SYN-ACK/ACK, но не payload; kernel-drop counters
нулевые. Это свидетельство проблемы передачи первого TCP payload, а не
долгого шифрования RTP. На Core A capture-vs-filter count отличается на 7
пакетов, его SSH clock bound ±1,031 с (B ±0,408 с); точная межхостовая
задержка и физическая причина потери из этого не выводятся.

## Подтверждённый механизм в приложении

После неподтверждённого relay-кандидата CallService оставлял P2P и ждал
пятсекундный cooldown независимо от появления новых overlay-сессий. Теперь
его production-владелец подписывает service на существующий sessionCount
stream. Только переход 0 → positive будит уже отложенную попытку этого же
активного direct-posture call. Начальное positive значение, повторные
positive count, отсутствие отложенного перехода и receiver repair не
запускают новый handover.

Число соединений не доказывает пригодность пути: новая попытка проходит
прежний sealed qualification, старый sender сохраняется до доказанного
успеха. Ни timeout, ни криптографические/consent проверки не ослаблены.
Событие во время native open/qualification запоминается поколением;
после отказа оно не теряется и не запускает параллельную операцию. Успешный
первый кандидат не создаёт лишнего retry. Hangup/identity disposal отменяют
подписку и не позволяют старой попытке перейти к другому call.

событие терялось внутри in-flight, событие не будило неподтверждённый путь.

Использованы gates/виртуальные часы; успешность не зависит от скорости сети.
Ещё 6 provider/history replay проверок прошли, включая три с native HVS: новая
подписка не обходит восстановление finished-call журнала.

Причина первых TCP-flow отказов, полное устранение пауз и ускорение на

## AOT проверка `dc0af18d`: один полный сценарий, один отказ

На обеих сторонах полные profile AOT с runtime source/digest guard и проверкой
фактических mappings/APK SHA. До первого звонка готовы все наблюдатели;
setup-процесс завершился до placement. Нативные библиотеки и два Core frozen.
Оба вызова начинались с фактического двустороннего P2P-приёма.

| Вызов | Последовательность | Max observed audio RX age на Cellular (Mac / Poco) | Возврат Wi-Fi |
|---|---|---|---|
| 1 | Wi-Fi → Cellular 120 с → Wi-Fi 45 с, завершён | 7287 / 11189 мс | 6771 / 4651 мс |
| 2 | Cellular наблюдался лишь 18,87 с; сценарий прерван | 11953 / 6127 мс | Не выполнен |

У первого вызова Mac epoch 1, Poco 1 → 3 и один срез без native counters.
У второго Mac 3 → 5, Poco 5; два Mac-среза без native counters. Отсутствующие
данные не интерполируются. Числа — возраст цифрового приёма, не слышимость.

**Второй вызов сам завершён Mac с `livenessTimeout` примерно на +21,84 с
после выключения Wi-Fi.** Это произошло до cleanup hangup скрипта. На Poco
новые overlay-сессии наблюдались в +1,26 с, а relay recovery началась в +3,84 с.
Первый кандидат не подтвердился на +8,67 с; до завершения Mac успешного relay
commit телефона в захвате нет. Poco сохранял P2P, Mac уже отправлял relay.
Новая ветка раннего wake не выполнена: событие соединения пришло раньше
отложенной попытки. Поэтому этот прогон не квалифицирует положительную ветку
wake и не доказывает ни ускорения, ни регрессии от неё. A/B не проводился.

Полный qualification-gate закономерно завершился ошибкой; исходный
`probeExit=0, cleanupExit=1` сохранён (ошибка второго теста переотправлена
через finish-driver). Финальная уборка независимо прошла: оба временных Core,
app/collectors/ports/runtime закрыты; production PID/binary/config неизменны;
QA/основной APK, старый QA-контейнер, разрешения, P2P policy, сеть и debug
properties восстановлены. Ошибка испытания не переименована в успешный
cleanup-resume. Подробности — [qualification-dc0af18d.json](qualification-dc0af18d.json).

## Продолжение: cooldown не запускал повтор при одностороннем обрыве

Найден отдельный подтверждённый механизм FSM: `_relayCandidateRetry.until`
только запрещал повтор до срока, но **не назначал сам повтор**. Если входящий
звук остаётся свежим, детектор тишины больше не вызывает recovery; peer relay
health тоже не обязан повторно запустить его для первоначального P2P. В итоге
уже запрошенный переход способен навсегда остаться в deferred после одного
отказа. Это согласуется с новым захватом, но вся причина его завершения ещё
не объявляется доказанной этим единственным механизмом.

Теперь после неподтверждённого перехода сохраняется **один отменяемый таймер
на пять секунд**. Он повторяет уже разрешённый запрос независимо от свежего
входящего аудио. Появление overlay может разбудить его раньше. Если native
repair ещё занят, один таймер с шагом 1 с сохраняет намерение без параллельных
native операций. Hangup/смена call/dispose и успешный переход отменяют таймер;
проверяются точные peer/call и владелец таймера. Старый таймер не расходует
ожидание нового звонка. Порог liveness не увеличен, доказательство доставки
кандидата и сохранение старого sender до успешной проверки не менялись.

На `dc0af18d` три assertion-red: свежий входящий звук оставлял outbound без
повтора; регулярный bounded retry отсутствовал; wake терялся при занятом
repair. После исправления: **321 related tests passed, 0 skipped**. Контроль
со сменой звонка реально создаёт второй вызов, проверяет старый дедлайн,
затем собственный новый дедлайн — это не проверка только пустого состояния.
Анализатор чистый. Физическая проверка версии с таймером — ниже.
SDK/HV не менялись, Rust не пересобирался; push/релиза нет.


## AOT проверка `f36a472d`: таймер работает, NETCALL остаётся открыт

Повторены два Wi-Fi → Cellular → Wi-Fi вызова на полных profile AOT обеих
сторон. Source/digest проверены до unlock, фактические mappings и APK SHA
сверены; native/два Core заморожены. Все наблюдатели готовы до placement.

Первый вызов завершил Cellular 120 с и возврат Wi-Fi 45 с без перестроения
медиадвижка: epoch 1 на обеих сторонах. Максимальный наблюдаемый возраст
native audio RX на Cellular — **12713 / 12527 мс** (Mac / Poco), при возврате
Wi-Fi — 6733 / 4082 мс. На конце каждой фазы подтверждено продвижение счётчика
аудиопакетов, а не только статус active. Оба endpoint действительно выполнили
новый timer retry. На Mac: deferred +7,017 с → timer +12,019 с → подтверждённый
relay commit с сохранением движка +14,791 с.

**Второй вызов снова сам завершился: Mac `livenessTimeout` +22,198 с после
выключения Wi-Fi.** Телефон исполнил оба повтора таймера (+12,863 / +19,719 с),
но ни один relay-кандидат не подтвердился. Mac один раз перестроил движок
(epoch 3 → 5; три среза без native counters), Poco оставался на epoch 3.
На конце частичной Cellular-фазы аудиоприём не продвигался на обеих сторонах.
Срезы без counters не интерполированы, таймер не продлевает liveness.

Новая локализация: сессия телефона к Core B появилась около +1,061 с, затем
закрылась по keepalive на +12,244 с. Следующие Core A/B session.open — лишь
около +25,004 / +25,191 с, уже после завершения звонка. В phone-логах два
десятисекундных **node handshake timeout** к Core A; начало его canonical
handshake на сервере в этом окне не наблюдается. У первых 60-байтовых relay
samples есть локальная очередь через Core B, но matching Core ingress в
захвате отсутствует. Это ещё не доказательство конкретной сетевой причины:
нужна граница transport/classification/ingress, а не новый call timeout.
Сверка Core-часов ограничена ±58 / ±28 мс.

Полная квалификация **не пройдена**; A/B и слышимость человеком не проверялись.
Исходный driver result 0/1 сохранён: ошибку второго теста finish-driver вернул
после успешной уборки. Независимо проверены остановка своих процессов/портов,
удаление временных Core, неизменность production PID/binary/config,
восстановление APK, QA-контейнера, сети, разрешений и debug properties.
Третий условный offline-прогон не запускался и не засчитан.
Данные без ID/адресов/сырых трасс — [qualification-f36a472d.json](qualification-f36a472d.json).
SDK/HV не менялись, Rust не пересобирался; push/релиза нет.


## Уточнение TCP-границы и короткий fine-захват

В неудачном втором вызове выше **все девять** 60-байтовых relay samples
+6,043…+7,770 с сопоставлены не только с source queue, но и с одним локальным
ordered child → record → TCP socket. Каждый record достиг flushed максимум
через **2534 мкс** после source sample. У обоих Core и Mac matching ingress
этих cells не наблюдается. flushed означает локальную запись, не доставку.

Снимки **этого же сокета** показывают остановку ACK counter на 1442 байтах
между +6,554 и +7,772 с. В этом ограниченном окне queued bytes выросли
1469 → 4633, notsent — 0 → 2594, retransmitted bytes — 492 → 2598, RTO —
296000 → 1184000 мкс, backoff — 0 → 2. Это конкретный TCP delivery stall,
который нельзя объяснять долгим Dart/IPC enqueue. Этим не объясняются все
22 секунды и не установлен физический механизм потерь. В raw trace есть
локальные связи record/child/connection; в публичной
[сводке свидетеля](tcp-writer-witness-f36a472d.json) их идентификаторов нет.

На возвращённом Poco выполнен отдельный **короткий диагностический** прогон
на тех же AOT/native bytes с debug.xveil.tcp_fine=1 (1118 fine-снимков).
Первый вызов завершил 8 с Wi-Fi → 25 с Cellular → 10 с Wi-Fi; native audio
на конце каждой фазы продвигался на обеих сторонах. Cellular max observed
RX age — 6189 / 4469 мс, возврат Wi-Fi — 3997 / 4059 мс. Одна relay-проба
этого вызова сопоставлена с ingress **обоих Core и Mac**; локальный flush —
1966 мкс. Это положительный контроль наблюдения, не A/B-доказательство
ускорения. Второй вызов принят и имел двусторонний baseline, но **смена сети
не выполнена**: истёк срок read-only SSH-проверки observer на Core. Его
нельзя считать ни успешной квалификацией, ни новым NETCALL-обрывом.
Первоначальный setup тоже один раз остановился на SSH-clock probe; повтор
использовал существующие принадлежащие стенду процессы, а не второй Core.

Исходный driver result 0/1 сохранён, исходная ошибка второго сценария не
заменена зелёным результатом. Уборка независимо подтверждена полностью,
включая оба Core и production baseline. Mac после штатной grace-паузы
потребовал SIGKILL; выход точного PID проверен. APK/контейнер/permissions/
сеть/debug properties восстановлены. Подробности без сырых данных:
[diagnostic-tcp-fine-f36a472d.json](diagnostic-tcp-fine-f36a472d.json).
Новая функциональная правка по этому сравнению не выбрана: причина TCP
stall всё ещё требует проверки, пороги liveness не увеличивались.


## Повтор fine-серии: обрыв и TCP stall воспроизведены вместе

Повторены те же AOT/native bytes. Внешнюю SSH-проверку observer перед второй
сменой сети убрали из критического участка: реальные observers/инвокации и
production baseline по-прежнему проверены до первого вызова и при финальном
сборе. Сами сетевые настройки, media qualification и liveness не изменены.
Это короткая диагностическая серия, не A/B и не полный 120-секундный гейт.

Первый вызов завершил все короткие фазы, но восстановление было медленным:
Cellular max observed RX age **17630 / 17170 мс**, обе стороны перестроили P2P
engine (epoch 1 → 3). На конце Cellular и Wi-Fi аудиосчётчики продвигались;
три/два среза без counters не интерполируются. Второй вызов снова оборвался:
Mac livenessTimeout на **+23,681 с** после Wi-Fi off, до cleanup hangup.
В частичной Cellular-фазе финального продвижения аудио нет на обеих сторонах;
epoch 5, max observed RX age 23591 / 23468 мс. Возврат Wi-Fi не выполнен.

Впервые физически наблюдён и ранний overlay-wake: Poco Core B session.open
около +22,541 с → overlay restored +22,544 → wake deferred relay +22,549 с.
Предыдущие timer retries тоже реально сработали. Тем самым wake не потерян,
но соединение вернулось слишком поздно для завершения нового перехода до
liveness. Это подтверждение исполнения ветки, не доказательство пригодности
появившейся сессии или устранения дефекта.

Из 27 локальных 60-байтовых relay source samples первые девять сопоставлены
с одним ordered child/record/TCP socket и все достигли локального flushed;
у обоих Core и Mac matching ingress отсутствует. Остальные 18 samples уже
не имеют local record admission. **12 fine-снимков именно сокета первых
девяти** показывают ACK counter 1529 без продвижения с +3,970 до +10,922 с
(6,952 с наблюдаемой стойки). За это окно queued bytes выросли 411 → 5342,
notsent — 0 → 3199, retransmitted bytes — 0 → 4594, RTO — 308000 → 4928000 мкс.
Это повторно отделяет ожидание TCP-доставки от локального Dart/IPC enqueue.

Кроме того, у четырёх длительных незавершённых obfs4 socket observations
(8,844–10,003 с) read_bytes=0, acked_bytes=1 (только SYN), есть ретрансляции
первого payload. Короткие отменённые hedge sockets не объявляются отказами:
они могут быть нормальными проигравшими гонки. Не установлен физический
источник потерь: ОС, NAT, путь или фильтрация. Их нельзя переименовать в
ошибку дешифрования или объяснить все секунды звонка одним счётчиком.
Следующее сравнение должно отделить транспорт/первый TCP payload на том же
пути; очередное увеличение call timeout этим захватом не обосновано.

Оригинальный driver 0/1 сохранён; финальная уборка независимо полностью
подтверждена: оба временных Core/наблюдатели/локальные app/PID/порты удалены,
production PID/binary/config и исходные APK/QA-контейнер/permissions/сеть/
properties сохранены. Зачтено выполнение первой короткой последовательности
и воспроизведение второго обрыва, **не успешная квалификация NETCALL**.
Без ID/адресов/сырых трасс: [результаты](diagnostic-tcp-fine-repeat-f36a472d.json)
и [TCP-свидетель](tcp-writer-witness-fine-repeat.json).

Около 1865 МиБ собственных staging build/.dart_tool/framework caches удалено
после проверки отсутствия открытых файлов. Raw profile APK с проверенным AOT,
готовые app/APK/native bytes, source hashes и приватные captures сохранены.
В этом цикле функциональных изменений нет; SDK/HV, push и релиз не затронуты.
