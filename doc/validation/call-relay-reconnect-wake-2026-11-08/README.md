# NETCALL-01: пробуждение relay retry после возврата сессий

## Уточнение последнего захвата

Во [втором AOT звонке](../call-direct-admission-reuse-2026-11-08/README.md)
шесть коротких наблюдений relay-кандидатов на Poco прошли до открытия новых
сессий с Core. 18 зашифрованных 60-байтовых source cells сопоставлены с
`socket_written` → `daemon_read` → `handler_enter` на телефоне (как правило
≤1 мс, один обработан через 7 мс). Relay queue admission и получателя для
этих cells в захвате нет. Новые Core session.open — около +12,97/+13,03 с;
следующий кандидат телефона начал проверку лишь на +20,83 с. Поэтому прежняя
гипотеза об исключительно позднем обратном echo не объясняет эти 18 cells:
до обработчика они дошли быстро, но пригодной overlay-сессии ещё не было.
Для следующего успешного кандидата есть source queue, Core A и received
на Mac; совпавший fresh reply получен за 379780 мкс.

Дополнительные TCP-данные отделяют первое ожидание от call FSM: четыре
ранних obfs4 client handshakes отправили 107–149 байт и завершились с 0
прочитанных байт; kernel acked_bytes=1 (SYN), retransmitted_bytes=321–596.
Последующие соединения завершили handshake за 152/170 мс. В PCAP двух Core
для ранних flows видны SYN/SYN-ACK/ACK, но не payload; kernel-drop counters
нулевые. Это свидетельство проблемы передачи первого TCP payload, а не
долгого шифрования RTP. На Core A capture-vs-filter count отличается на 7
пакетов, его SSH clock bound ±1,031 с (B ±0,408 с); точная межхостовая
задержка и физическая причина потери из этого не выводятся.

## Подтверждённый механизм в приложении

После неподтверждённого relay-кандидата CallService оставлял P2P и ждал
пятсекундный cooldown независимо от появления новых overlay-сессий. Теперь
его production-владелец подписывает service на существующий sessionCount
stream. Только переход 0 → positive будит уже отложенную попытку этого же
активного direct-posture call. Начальное positive значение, повторные
positive count, отсутствие отложенного перехода и receiver repair не
запускают новый handover.

Число соединений не доказывает пригодность пути: новая попытка проходит
прежний sealed qualification, старый sender сохраняется до доказанного
успеха. Ни timeout, ни криптографические/consent проверки не ослаблены.
Событие во время native open/qualification запоминается поколением;
после отказа оно не теряется и не запускает параллельную операцию. Успешный
первый кандидат не создаёт лишнего retry. Hangup/identity disposal отменяют
подписку и не позволяют старой попытке перейти к другому call.

Использованы gates/виртуальные часы; успешность не зависит от скорости сети.

подписка не обходит восстановление finished-call журнала.

## AOT проверка `dc0af18d`: один полный сценарий, один отказ

На обеих сторонах полные profile AOT с runtime source/digest guard и проверкой
фактических mappings/APK SHA. До первого звонка готовы все наблюдатели;
setup-процесс завершился до placement. Нативные библиотеки и два Core frozen.
Оба вызова начинались с фактического двустороннего P2P-приёма.

| Вызов | Последовательность | Max observed audio RX age на Cellular (Mac / Poco) | Возврат Wi-Fi |
|---|---|---|---|
| 1 | Wi-Fi → Cellular 120 с → Wi-Fi 45 с, завершён | 7287 / 11189 мс | 6771 / 4651 мс |
| 2 | Cellular наблюдался лишь 18,87 с; сценарий прерван | 11953 / 6127 мс | Не выполнен |

У первого вызова Mac epoch 1, Poco 1 → 3 и один срез без native counters.
У второго Mac 3 → 5, Poco 5; два Mac-среза без native counters. Отсутствующие
данные не интерполируются. Числа — возраст цифрового приёма, не слышимость.

**Второй вызов сам завершён Mac с `livenessTimeout` примерно на +21,84 с
после выключения Wi-Fi.** Это произошло до cleanup hangup скрипта. На Poco
новые overlay-сессии наблюдались в +1,26 с, а relay recovery началась в +3,84 с.
Первый кандидат не подтвердился на +8,67 с; до завершения Mac успешного relay
commit телефона в захвате нет. Poco сохранял P2P, Mac уже отправлял relay.
Новая ветка раннего wake не выполнена: событие соединения пришло раньше
отложенной попытки. Поэтому этот прогон не квалифицирует положительную ветку
wake и не доказывает ни ускорения, ни регрессии от неё. A/B не проводился.

Полный qualification-gate закономерно завершился ошибкой; исходный
`probeExit=0, cleanupExit=1` сохранён (ошибка второго теста переотправлена
через finish-driver). Финальная уборка независимо прошла: оба временных Core,
app/collectors/ports/runtime закрыты; production PID/binary/config неизменны;
QA/основной APK, старый QA-контейнер, разрешения, P2P policy, сеть и debug
properties восстановлены. Ошибка испытания не переименована в успешный
cleanup-resume. Подробности — [qualification-dc0af18d.json](qualification-dc0af18d.json).

## Продолжение: cooldown не запускал повтор при одностороннем обрыве

Найден отдельный подтверждённый механизм FSM: `_relayCandidateRetry.until`
только запрещал повтор до срока, но **не назначал сам повтор**. Если входящий
звук остаётся свежим, детектор тишины больше не вызывает recovery; peer relay
health тоже не обязан повторно запустить его для первоначального P2P. В итоге
уже запрошенный переход способен навсегда остаться в deferred после одного
отказа. Это согласуется с новым захватом, но вся причина его завершения ещё
не объявляется доказанной этим единственным механизмом.

Теперь после неподтверждённого перехода сохраняется **один отменяемый таймер
на пять секунд**. Он повторяет уже разрешённый запрос независимо от свежего
входящего аудио. Появление overlay может разбудить его раньше. Если native
repair ещё занят, один таймер с шагом 1 с сохраняет намерение без параллельных
native операций. Hangup/смена call/dispose и успешный переход отменяют таймер;
проверяются точные peer/call и владелец таймера. Старый таймер не расходует
ожидание нового звонка. Порог liveness не увеличен, доказательство доставки
кандидата и сохранение старого sender до успешной проверки не менялись.

На `dc0af18d` три assertion-red: свежий входящий звук оставлял outbound без
повтора; регулярный bounded retry отсутствовал; wake терялся при занятом
repair. После исправления: **321 related tests passed, 0 skipped**. Контроль
со сменой звонка реально создаёт второй вызов, проверяет старый дедлайн,
затем собственный новый дедлайн — это не проверка только пустого состояния.
Анализатор чистый. **Версия с таймером ещё не квалифицирована физически.**
SDK/HV не менялись, Rust не пересобирался; push/релиза нет.
