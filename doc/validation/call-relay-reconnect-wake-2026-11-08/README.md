# NETCALL-01: пробуждение relay retry после возврата сессий

## Уточнение последнего захвата

Во [втором AOT звонке](../call-direct-admission-reuse-2026-11-08/README.md)
шесть коротких наблюдений relay-кандидатов на Poco прошли до открытия новых
сессий с Core. 18 зашифрованных 60-байтовых source cells сопоставлены с
`socket_written` → `daemon_read` → `handler_enter` на телефоне (как правило
≤1 мс, один обработан через 7 мс). Relay queue admission и получателя для
этих cells в захвате нет. Новые Core session.open — около +12,97/+13,03 с;
следующий кандидат телефона начал проверку лишь на +20,83 с. Поэтому прежняя
гипотеза об исключительно позднем обратном echo не объясняет эти 18 cells:
до обработчика они дошли быстро, но пригодной overlay-сессии ещё не было.
Для следующего успешного кандидата есть source queue, Core A и received
на Mac; совпавший fresh reply получен за 379780 мкс.

Дополнительные TCP-данные отделяют первое ожидание от call FSM: четыре
ранних obfs4 client handshakes отправили 107–149 байт и завершились с 0
прочитанных байт; kernel acked_bytes=1 (SYN), retransmitted_bytes=321–596.
Последующие соединения завершили handshake за 152/170 мс. В PCAP двух Core
для ранних flows видны SYN/SYN-ACK/ACK, но не payload; kernel-drop counters
нулевые. Это свидетельство проблемы передачи первого TCP payload, а не
долгого шифрования RTP. На Core A capture-vs-filter count отличается на 7
пакетов, его SSH clock bound ±1,031 с (B ±0,408 с); точная межхостовая
задержка и физическая причина потери из этого не выводятся.

## Подтверждённый механизм в приложении

После неподтверждённого relay-кандидата CallService оставлял P2P и ждал
пятсекундный cooldown независимо от появления новых overlay-сессий. Теперь
его production-владелец подписывает service на существующий sessionCount
stream. Только переход 0 → positive будит уже отложенную попытку этого же
активного direct-posture call. Начальное positive значение, повторные
positive count, отсутствие отложенного перехода и receiver repair не
запускают новый handover.

Число соединений не доказывает пригодность пути: новая попытка проходит
прежний sealed qualification, старый sender сохраняется до доказанного
успеха. Ни timeout, ни криптографические/consent проверки не ослаблены.
Событие во время native open/qualification запоминается поколением;
после отказа оно не теряется и не запускает параллельную операцию. Успешный
первый кандидат не создаёт лишнего retry. Hangup/identity disposal отменяют
подписку и не позволяют старой попытке перейти к другому call.

## Проверки

Сначала добавлена только проводка наблюдений при прежнем cooldown-поведении.
Три регрессии упали по assertions: готовый путь продолжал ждать, новое
событие терялось внутри in-flight, событие не будило неподтверждённый путь.
Четыре отрицательных контроля проходили. После фикса и дополнительных
контролей: **317 passed, 0 skipped** в шести связанных файлах; analyzer чистый.
Использованы gates/виртуальные часы; успешность не зависит от скорости сети.
Ещё 6 provider/history replay проверок прошли, включая три с native HVS: новая
подписка не обходит восстановление finished-call журнала.

Физическая квалификация этой правки ещё не выполнена. Это исправление
локального дополнительного ожидания; причина первых TCP-flow отказов,
полное устранение пауз и ускорение на мобильном провайдере не заявляются.
SDK/HV не менялись, Rust не пересобирался, push/релиза нет.
