# Догрузка 100000 сообщений: реальный объём, полный oracle

## Стенд расширен по указанию владельца

Controller и storage worker принимают 32..100000 архивных сообщений; default
малых гейтов остаётся 512. Production page cap 128, byte budget 128 КиБ/64 части,
подготовленные публикации по 64 и ordinary live coalescing по 16 не изменены.
В setup до 10000 строк остаются порции по 16; для большего архива используются
по 64 через настоящее encrypted storage, до измеряемого окна. Отказ/частичное
добавление не засчитывается как подготовленный источник.

Подняты именно пределы наблюдения: wire probe до 262144 записей, overlap census
до 100001 уникальных append keys. Default остальных census пользователей —
20000; новый instance limit проверяется отдельно и не допускает бесконечного
роста. Нет увеличения production admission/очередей/числа outstanding requests.
Sibling mailbox по-прежнему выключен.

Выше 10000 controller каждые 5000 мс читает только durable cursors, gate/error
счётчики и count-only census. Ответ progress не содержит `rows`, `count` или
полной wire history; controller требует явный progress marker и не допускает
зачёта такого ответа как снимка данных. В захвате он занимал 8807 байт.
После окончания cursor отдельно считываются все строки; затем все источники
выключаются и выполняется полный cold-retention oracle до подключения к сети.
Таким образом, тяжёлый full snapshot/hash не повторяется на каждом опросе.

Большой кейс имеет собственный 20-минутный migration wait внутри 45-минутного
test bound; это границы стенда, не изменение таймеров приложения. Disk guard
останавливает только собственный runner при свободном месте меньше 16 ГиБ;
он не сработал. Место/кэш во время замера не чистились.

## Фактический прогон

Четыре независимых Mac/JIT процесса: A/B/E одной личности, C другой; три
изолированных Core, loopback TCP и настоящие FFI/ratchet/контейнеры. A/E
заранее имеют по 100000 одинаковых архивных строк; B имеет одну прежнюю.
Первые authenticated ответы обоих источников получены до release apply;
sampling/timeline выключены. C offline при догрузке.

| Метрика | Результат |
|---|---:|
| Уникальных архивных сообщений | 100000 |
| Итоговых строк с прежней | 100001 |
| Apply release → наблюдаемая сходимость | 276836 мс (4 мин 37 с) |
| Release file → post-page inventory у обоих источников | 272691,318 мс |
| Страниц A / E | 782 / 782 |
| HistoryApply callbacks | 200002 |
| Коммитов сообщений / cursor | 1563 / 1566 |
| Чтений own devices в census | 437441 |

Две исходные копии намеренно пересекаются; 200002 callbacks не означают столько
логических сообщений. Проверены все IDs, тексты через body tags, delivered,
canonical positions и итоговый порядок: **нет пропусков/дублей/лишних строк**.
Оба conversation cursor завершены. Cold boot при offline A/E/C сохранил все
100001 строку до возможности сетевого восстановления. Промежуточный порядок
каждого неполного состояния этим компактным observer не квалифицирован.

Post-page inventory — отдельный passive witness по mtime файла release и
связанным request IDs. Такой запрос следует после apply/durable conversation
cursor, но показатель включает его доставку до источника и не является точной
меткой UI convergence. Основной замер включает 5000-мс polling и финальную
полную проверку. Нельзя приписывать всё отличие от 10000 строк только объёму:
observer и setup batch отличаются, A/B по масштабу здесь нет.

## Где остаётся ожидание

Все 782 forward queries каждого источника связаны с полными ответами,
provenance аутентифицирован. Первый gate-crossing ответ исключён из стадийных
метрик. Счётчики capture/census не обрезаны.

| Стадия | A P50 / P95, мс | E P50 / P95, мс |
|---|---:|---:|
| Query у источника → полный ответ у B (781) | 149,186 / 232,605 | 147,011 / 231,605 |
| Полный ответ у B → следующий query у источника (780) | 169,302 / 236,744 | 170,207 / 252,934 |

По четвертям страницы не становились систематически медленнее: query→reply
P50 у A 160,8 → 149,7 → 142,6 → 142,5 мс, у E 158,8 → 153,1 → 141,3 → 136,0.
Вторая стадия также не росла по медианам. Это отрицательный результат для
предположения о постоянно дорожающем ingest внутри данного прогона, не
доказательство отсутствия любых деградаций/GC/пауз. Максимумы около секунды
и оставшиеся ожидания сохраняются; стадии не являются exclusive CPU/I/O.

Следующий кандидат — подготовка страниц у источника: production `_snapshot`
на каждый новый page query снова получает, фильтрует и сортирует полный
разговор. Перед изменением этой политики нужен профиль на данном объёме;
свежие edit/visibility/authorization проверки нельзя заменять устаревшим cache.
**Задержка остаётся открытой**, потери данных в этом текстовом кейсе не выявлены.

## Проверки и уборка

**33 helper tests passed / 0 skipped**: новые границы archive, допустимый большой
census, сохранение default cap, отказ неверных limits и privacy/cap wire probe.
Отдельный native-кейс на 100000 завершён успешно; analyzer чист.

Production-код основан на `061b01d2`; расширения test harness находятся в
коммите с этим отчётом. Один checkout `061b01d2` без этих расширений ещё
ограничивает архив 10000 строками.

1525 frozen inputs и выбранные native SHA/mappings проверены до/после прогона,
Rust не собирался. Cleanup проверил 37 owned PID и 63 порта: процессов/listeners
не осталось, synthetic runtime удалён. Кэш **92 → 92 файла**, около 9,55 ГиБ;
после уборки runtime свободно около 149,6 ГиБ. Телефон, пользовательские
контейнеры и production не затронуты. Это не AOT/Windows/Android квалификация
и не полная multi-device матрица; revoke, split-brain, crash и медиа здесь
дополнительно не проверялись. NETCALL-01 не закрыт.

Только агрегаты: [summary.json](summary.json). Raw данные/ID/пути остаются
частными. Коммит локальный unsigned, push/релиза нет.
