# Первая причина закрытия канала аудиодоставки

**NETCALL-01 остаётся открытым.** Устранён пробел диагностики: `record plane
closed` больше не скрывает первую локально наблюдавшуюся причину. Повторная
серия Poco ↔ Mac через два независимых Core завершила четыре сценария с
успешным финальным контролем; прежняя пауза 9,6 с в этой серии не повторилась.
Это не доказательство её устранения.

## Изменение SDK

SDK `7d34e4e5` добавляет типизированную причину в локальный `RecordProgress`:
owner close, EOF, ошибка чтения/записи, неверная длина кадра, zero write,
частичная expiry, write timeout, завершение writer или отмена/выход задачи.
Первая причина сохраняется при последующем закрытии второй половины и owner.
Исходный текст ошибки, адреса, пути и содержимое кадра в поле не записываются.
`InvalidData` от шифрующего транспорта остаётся `read_error`; только собственная
проверка длины может выставить `invalid_record`.

Штатные `recv()` errors и закрытие обеих половин сохранены. Deadline 200 мс,
размер/бюджеты записей, framing, wire, ключи/ratchet, parent proof и права не
менялись. Локальная причина отражается в path counters и в opt-in terminal
событии [предыдущего раунда](../dual-core-handover-2026-11-07/README.md).
По этим полям нельзя считать EOF причиной действий удалённого телефона:
для этого нужна соответствующая диагностика на самом телефоне.

Проверки на настоящих duplex I/O и fault streams различают invalid/truncated
input, EOF, read/write error, zero write, timeout, partial expiry, owner drop
и отмену уже запущенного reader. Проверены сохранность первой причины,
отсутствие исходного error-text canary и продолжение работы независимого
канала. 173 transport и 697 session tests passed; 8 session ignored отдельно.
Focused 16 входят в общий набор, не прибавлены к нему. rustfmt и AOT-проверка
анонимного экспорта прошли. Новое поле — Rust snapshot, не C ABI и не wire.

## Физическая серия

Оба Core на разных серверах используют сборку из чистого `7d34e4e5`.
До установки проверены source snapshot, SHA, ELF architecture/no interpreter
и наличие новых диагностических маркеров. После старта проверен SHA реально
исполняемого бинарника каждого Core. Сборка использовала внешний target с
проверкой mount и watchdog свободного места/исчезновения диска.

Клиенты прежние: native `c6699c28`, неизменные QA APK, AOT/frontend и Mac dylib.
P2P denied. Глобальные discovery/PEX/built-in seeds отключены; до звонков
подтверждены соединения каждого Core с обоими клиентами и другим Core.
Захват на двух Core и Mac готов до первого звонка. На телефоне frame subscriber
не использовался. Слышимость речи, эхо, шум и mouth-to-ear delay не измерялись.

| Сценарий | Контроль после готовности/переключения | Максимальный native RX age: Poco / Mac | Финальные пять свежих срезов |
|---|---:|---:|---|
| Wi-Fi, Poco → Mac | 35 с | 424 / 397 мс | Пройдены |
| Cellular, Mac → Poco | 35 с | 1405 / 1069 мс | Пройдены |

| Cellular → Wi-Fi внутри звонка | 60 с | 1221 / 958 мс | Пройдены |

Для переходов таблица использует только post-command observations; для
фиксированных сетей — все срезы вызова. Критерий свежести прежний: тот же
active call, running, worker_stalled=0, RX packets > 0, возраст 0–1000 мс.
После 15 с baseline отдельно дожидались пяти свежих срезов перед командой,
не меняя критерий. Обе целевые сети validated, процессы клиентов прежние.
Ошибок API/OS-наблюдения нет. Финальный успех не означает свежесть каждого
промежуточного среза: отдельные превышения 1 с показаны в таблице.

## Что дали новые причины

Во всём Core-захвате — 25 / 26 terminal events с разными receiver numbers.
В консервативной внутренней части окон четырёх вызовов — **19** закрытий к
телефону: 6 `partial_record_expired`, 8 `read_eof`, 5 `read_error`.
Остальные события не приписаны звонкам.

| Core | Сценарий | Partial expiry | EOF | Read error |
|---|---|---:|---:|---:|
| A | Wi-Fi → Cellular | 1 | 4 | 0 |
| A | Cellular → Wi-Fi | 2 | 2 | 3 |
| B | Фиксированная Cellular | 1 | 0 | 0 |
| B | Wi-Fi → Cellular | 2 | 0 | 0 |
| B | Cellular → Wi-Fi | 0 | 2 | 2 |

Для этих partial-expiry events write maximum около 201 мс согласуется со
штатным пределом 200 мс. Это первая причина, зафиксированная непосредственно
веткой кода, а не диагноз по совпадению таймеров. Изменять этот предел ради
неатрибутированной старой паузы оснований пока нет.

Звонки выдержали эти закрытия без прежней многосекундной паузы. Поэтому факт
закрытия сам по себе недостаточен для диагноза: нужно определить актуальный
путь и состояние альтернатив в момент конкретной потери RX. Текущая серия
не устанавливает, что произошло в предыдущем 9,6-с случае; его старый бинарник
не содержал first-cause field. Обновление Core также включает прежний
bootstrap-retry фикс; это не A/B функционального ускорения.

## Гигиена и следующий шаг

Начальная попытка вызвала Mac unlock до готовности control API; после проверки
живого точного PID дождались API без перезапуска приложения. Mac observer
затем отверг ошибочную конфигурацию стенда без `unix://`; она исправлена и
провалидирована, старый observer подтверждён завершённым. До прохождения всех
capture/readiness gates звонки не запускались. Эти ошибки стенда не отнесены
к xVeil и не посчитаны неудачными звонками.

После серии восстановлены P2P choices, прежний QA APK, mic permission, сеть,
stay-on и исходные контейнер/normal APK hashes. Тестовые приложения и все
записанные дочерние процессы завершены, порты освобождены. Оба QA Core,
capture/subscriber units и их данные удалены; production PID/binary/config
совпали до/после. Удалён собственный runtime Mac, новый debug log вынесен из
bundle; deep/strict codesign verification прошла.

Удалённые журналы копировались после остановки писателей, оба архива и каждая
запись проверены. 27 исходных входов заморожены с приватными SHA; harness
не менялся во время вызовов. Публичный [summary](summary.json) содержит только
агрегаты, без адресов/портов, receiver/call/identity IDs, raw errors, путей,
packet previews и их хешей. Push/релиза и sibling mailbox нет.

Следующий сетевой шаг — добавить эту же диагностику в QA native телефона и
проверить несколько последовательных переходов в одном длительном звонке.
При новом повторении сопоставить причины на двух концах с конкретной потерей
приёма и реконнектом; успешные отдельные переходы этого не заменяют.
