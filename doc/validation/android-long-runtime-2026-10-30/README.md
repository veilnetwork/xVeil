# Android: длинный runtime-путь и диагностика восстановления загрузок

Репорт 0.13.93+112 / Veil 0.11.46 / hidden-volume 2.6.4 содержит два
разных наблюдения. На снимке узел не смог открыть admin socket: путь под
Android adopted storage превышает Unix `sun_path`. JSON отдельно содержит
`download-resume-read / StateError`. Общая причина этих двух событий не доказана.

## Запуск узла — подтверждённый механизм, локально исправлен

Ранее Android всегда получал pathname Unix sockets. При размещении приложения
на расширенном хранилище префикс sandbox длиннее; проверка `SUN_LEN` отклоняла
соединение ещё до успешного старта. То, что каталог приватный, не гарантирует
допустимой длины его socket address.

Теперь выбор локального транспорта учитывает фактические UTF-8 байты обоих
путей, включая место под завершающий NUL: Linux/Android — 108 байт поля,
Darwin — 104. При превышении используется существующий authenticated loopback
TCP: случайные локальные порты, private token sidecars и anchors в том же
runtime-каталоге. Windows/iOS уже используют этот механизм. Общий каталог,
публичный listener, ослабление авторизации или перенос контейнера не добавлялись.

Красная проверка выбора транспорта воспроизвела прежний результат на синтетическом
adopted-storage пути; после исправления проверены границы длины и многобайтовый
Unicode. Отдельный native-тест реально запустил deferred node и authenticated
admin/IPC под слишком длинным runtime-путём на Mac, подключился через IPC,
завершил узел и проверил удаление sidecars. Использована публичная тестовая
личность, отключены seeds/meeting points, listener локальный/эфемерный.
Библиотека для этого теста — SDK `4de50051`, production features без test hooks.

Исходный телефон пользователя с adopted storage недоступен. Blackview текущего
стенда имеет короткий путь sandbox. Поэтому это unit + host-native проверка
механизма, не физическое повторение на том Android и не релизная квалификация.
Frozen frontend файловой серии из соседнего отчёта этой Dart-правки не содержит.

## `download-resume-read` — причина исходного случая остаётся неизвестной

В опубликованной реализации обработчик заменял любую ошибку чтения фиксированным
`StateError`. По присланному JSON нельзя отличить повреждённый JSON, неполный
registry или отказ хранилища. Нельзя делать вывод о потере файлов или причинной
связи с остановленным узлом.

Диагностика теперь различает FormatException, собственный тип неполного registry
и FileSystemException с числовым errno. Исходные source/message/path и текст OS
не сохраняются даже в RAM-записи нового обработчика. Неизвестная причина всё ещё
даёт фиксированный StateError. Отказ запуска узла отдельно попадает в error journal
как `node-start`; анонимный экспорт не содержит его исходного сообщения/пути.

Сохраняются только разрешённые `package:`/`dart:` места исходного stack;
абсолютные пути отбрасываются. Это помогает локализовать и оставшийся общий
StateError без экспорта текста исключения. Canary-тест проверяет обе стороны.

Нечитаемый registry не удаляется, не заменяется пустым и не считается успешно
восстановленным. Новая загрузка не перезаписывает старые намерения. Проверены
сохранность durable bytes и повторный успешный read после временного отказа.
Спекулятивной миграции или очистки контейнера нет. При повторении нужен новый
анонимный отчёт; первоначальная причина этого resume-read не объявляется исправленной.

## Проверки

- 127 Flutter-тестов: download-resume persistence, app controller, endpoint plan,
  boot failure diagnosis, error journal. Все прошли.
- Отдельный native long-runtime тест: 1 passed, без skip.
- Анализ восьми изменённых Dart-файлов: без замечаний.
- AOT-проверка диагностического артефакта и privacy gate: прошла.
- Canary-проверки: приватные пути/сообщения не попадают в JSON; после файлового
  отказа сохранён только безопасный класс и errno.

Правки локальные, без push и выпуска. Отчёт не содержит пользовательских UUID,
адресов, ключей или сырых журналов.
