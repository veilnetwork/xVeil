# NETCALL-01: TCP_INFO телефона и echo-серверов

**Подтверждено на независимом native-контроле:** мобильные паузы сопровождаются
TCP retransmissions, отсутствием продвижения ACK и очередью not-sent.
В одном прогоне два канала завершились с I/O error, а MSS телефона на них
уменьшился с 1348 до 48 Б. **Полное прохождение доставки не заявляется.**
Product-код и настройки xVeil не менялись; NETCALL-01 остаётся открытым.

Важная граница: измеритель использовал системные send-buffer/MSS settings,
которые **отличаются от уже реализованного профиля Veil**. Эти цифры нельзя
напрямую переносить на приложение или объявлять новым дефектом его admission.

## Что измерено

Продолжение [нагрузочного контроля](../load-sweep-control-2026-11-08/README.md):
тот же Poco, два серверных адреса, четыре канала — TCP и TLS к каждому.
512 Б синтетических данных каждые 50 мс на канал. Клиент сверяет echo целиком;
контейнеры, SDK и микрофоны не используются, APK не устанавливаются.

На телефоне TCP_INFO сохраняется примерно каждые 100–120 мс. Layout полей
получен через offsetof/sizeof из того же NDK executable; декодируются только
поля, помещающиеся в реально возвращённые ядром 232 Б. Добавлены not-sent,
bytes sent/acked/received/retransmitted, unacked, MSS, RTO, backoff и другие
счётчики. TCP_INFO — учёт ядра, **не доказательство физической отправки NIC**.

Серверы сохраняют TCP_INFO при получении кадра, время завершения echo и цену
логирования. Linux ABI/endianness проверены отдельно. RTO и not-sent
интерпретируются по [реализации Linux TCP_INFO](https://github.com/torvalds/linux/blob/v5.4/net/ipv4/tcp.c#L3080):
это текущий retransmission timeout и байты, ещё не продвинутые за snd_nxt;
одно большое значение RTO само по себе не означает, что таймер сработал.

## Проверка измерителя

Два трёхсекундных Android-контроля через собственный ADB reverse к локальному
Mac echo: обычный и с намеренным удержанием echo на 1100 мс. По 60/60 кадров
на всех четырёх каналах. В held-контроле gaps >1 с действительно обнаружены,
но bytes sent/acked продолжали расти во время удержания. То есть прибор
отличает application echo hold от отсутствия TCP ACK progress.

Сохранены 116 TCP_INFO samples в каждом контроле; getter cost ≤504 мкс.
Это цена getsockopt, а не всего форматирования записи. Полная цена observer
дополнительно ограничивается фактической cadence источника в серии.
Локальные серверы завершены, собственный reverse mapping удалён с точным
восстановлением прежнего списка. Предыдущий loopback backpressure-контроль
полей not-sent/sent/acked также сохранён отдельно.

## Физическая серия

Заранее задано: Wi-Fi 20 с → Cellular 120 с → Cellular 120 с → Wi-Fi 20 с.
Перед фазой — target network/VALIDATED и новые соединения. Внутри фазы
соединения не переключаются. Это контроль стабильного пути, не handover
с сохранением одного сокета и не физический звонок.

| Фаза | Успешные echoes | Socket I/O errors | Max RTT вернувшегося кадра | Max receive gap во время генерации |
|---|---:|---:|---:|---:|
| Wi-Fi-1 | 1600 / 1600 отправленных | 0 | 116 мс | 57 мс |
| Cellular-1 | 9018 / 9059 отправленных | 2 | 1630 мс | 1520 мс |
| Cellular-2 | 9600 / 9600 отправленных | 0 | 2190 мс | 1397 мс |
| Wi-Fi-2 | 1600 / 1600 отправленных | 0 | 284 мс | 216 мс |

В первом Cellular источник создал 2400 общих ticks. После отказов R2
диагностический клиент пропустил ещё 541 подачу на закрытые каналы;
они не считаются потерянными отправленными кадрами. Из 41 отправленного
кадра без echo 25 не зарегистрированы сервером, 16 зарегистрированы и
отправлены им обратно, но не получены клиентом. Это endpoint observations
до закрытия, не NIC-доказательство окончательной потери каждого пакета.

Нет corrupted frames, duplicates или missed ticks. Producer gap <57 мс
во всех фазах. Максимумы RTT относятся только к вернувшимся кадрам:
по ним нельзя ограничивать задержку отсутствующего хвоста.

Первоначальный строгий validator полного прохождения **упал**, его результат
сохранён. Отдельный postprocessor проверил неполную доставку: суммы
sent/skipped/ticks, ошибки, server/client sequence prefixes, неполученные
хвосты и целостность данных. Frozen validator/harness не переписывались.
В итоговых данных allAttemptedDeliveryPassed=false.

## Что теперь локализовано

Для каждого канала рассчитан совместимый постоянный clock-offset interval
из generation → server arrival → client echo. Ширина интервалов 50–150 мс;
односторонняя задержка по ним не объявляется измеренной. Для server arrival
gaps ≥750 мс выбран внутренний интервал, остающийся внутри gap при любом
offset из этих границ; края прогона и интервалы с <3 samples исключены.

Получено 88 таких интервалов:

- в 79 bytes_acked телефона не продвигается;
- во всех 88 bytes_sent телефона продвигается;
- в 82 растёт счётчик retransmissions;
- в 44 растёт not-sent очередь.

Это не 88 независимых сбоев: TCP/TLS и оба сервера могут отражать одну
общую мобильную паузу. Но картина отличается от положительного held-echo
контроля: ядро действительно повторяет отправку и частично удерживает новые
байты, а не просто ожидает медленной обработки echo после исправного ACK.

На телефоне: not-sent до 11108 Б, RTO до 3876 мс, backoff до 2.
На серверах между первым/последним кадром мобильной сессии — 54–83
retransmissions, RTO snapshots до 3481 мс, not-sent до 16502 Б; это
неполные per-frame snapshots, а не непрерывный максимум серверного TCP.
На Wi-Fi retransmission deltas и not-sent равны нулю.
Server echo work ≤25,9 мс, log work ≤1,6 мс. Эти значения не объясняют
секундные паузы, но не являются непрерывным измерением scheduling до recv.
Конкретный сетевой хоп, ОС/модем или оператор пока не установлены.

### Два отказа и MSS

На R2 в первом Cellular raw TCP recv вернул ETIMEDOUT примерно через
106,44 с, TLS recv — общий I/O failure около 106,47 с. Причина закрытия
сокетов не установлена. Гипотеза «это просто пятисекундный idle timer
нашего сервера» не подтвердилась: при указанном clock-offset model сервер
успешно завершает последние echoes уже через 0,15–0,27 с после native error.
Лог server close не различает причину, поэтому точный механизм не заявляется.

Перед отказами MSS телефона на обоих этих каналах последовательно менялся
1348 → 1024 → 512 → 256 → 128 → 64 → 48 Б. TCP продолжал подтверждать
данные во время этой деградации. На остальных телефонных каналах и на
серверах MSS оставался 1348 Б. Это не доказательство реального path MTU
в 100 Б: readonly настройки телефона показывают включённый MTU probing
с base MSS 1024 и min snd MSS 48. Глобальные настройки не менялись.

## Сопоставление с продуктом и следующий шаг

В [TCP transport Veil](../../../third_party/veil/crates/veil-transport/src/tcp.rs)
уже реализованы pre-connect/pre-listen TCP_MAXSEG 1200, SO_SNDBUF 64 КиБ
и TCP_NOTSENT_LOWAT 4096 для Linux/Android. Это больше, чем один TCP_NODELAY
независимого измерителя. LOWAT — readiness threshold, а не жёсткий cap;
в существующем transport test проверяются backpressure и сохранность байтов.
Добавление такого ограничения повторно не является найденным исправлением.

Следующий контроль должен повторить **этот профиль сокетов на обоих концах**
и проверять readback, TCP_INFO, неполученные/неподанные кадры вместе с RTT.
Малый RTT за счёт отсечения данных нельзя засчитать как ускорение.
После этого нужен TCP_INFO на настоящем SDK/звонке, если симптом сохранится.

Быстрая смена retransmission policy также не внесена: в 310 phone samples
с retransmits >0 unacked нигде не меньше четырёх. Условие thin-stream
режима в [Linux](https://github.com/torvalds/linux/blob/v5.4/include/net/tcp.h#L1730)
в этих наблюдениях не выполнено; это не квалификация всех иных режимов/ядер.
Ни уменьшение audio window, ни переключение транспорта по этой серии
не объявлены исправлением NETCALL-01.

## Гигиена и границы

28 power/network snapshots: Awake, питание подключено, Doze/Light Doze
ACTIVE, target network VALIDATED. CLOCK_MONOTONIC и срезы не заменяют
непрерывного suspend test; shell UID не квалифицирует все политики app UID.
Между начальным и финальным host checks изменился ADB transport identifier.
Время переобнаружения USB и его связь с TCP-паузами не установлены; это
дополнительный фактор для следующего контроля. Native setsid процессы и
целостность выгруженных файлов проверены независимо от наблюдения по ADB.

Все свои phone/native и Mac server processes завершены; directories,
binary/token/CA и reverse mapping удалены/восстановлены по ownership checks.
Исходные Wi-Fi/data/stay-on и validated сеть, APK main/QA и QA root container
сверены независимо после уборки. Контейнеры не открывались.
Временные remote units и credentials удалены, порты свободны; production
PID/restarts/binary/config обоих серверов проверены независимо.
Frozen source/binary/runtime hashes совпали; отдельный post-processing имеет
собственный provenance. Raw operational records остаются private.
Коммит без подписи, push/релиза нет.
