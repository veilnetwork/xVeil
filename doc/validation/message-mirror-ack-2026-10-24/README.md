# ACK после восстановления own-device journal — 24 октября 2026

База xVeil `3c19a5fe`. A/B одной личности, C другой.

## Подтверждённые дефекты

| Случай | На базе | Исправление |
| --- | --- | --- |
| Строка сохранена, `onMessageStored` отказал | Первый post не ACKed, но повтор сразу ACKed по наличию строки; mirror не повторяется | Перед ACK существующая строка повторно публикуется в локальный device journal |

## Правила восстановления

Повтор использует `Storage.loadMessageById`, а не тело/имя файла/номер из
повторного пакета. Автор, исходный seq, время и сохранённые file references
сохраняются. В том числе после повторного открытия настоящего storage mapping
над FakeHvContainer. Повтор не добавляет ещё одну строку сообщения.

После успешного publisher хранится ограниченный RAM cache из 512 пар
`(peer, message id)`. Ошибка туда не попадает. Смена publisher очищает cache;
старый завершившийся callback не заполняет cache нового owner. После restart
повтор может ещё раз идемпотентно опубликовать исходную строку. Это не durable
очередь и не новая копия сообщения в mailbox.

Нормальный `_store` и duplicate recovery используют общий publisher helper.
Если callback при входе ещё не был установлен, но появился во время append,
используется уже доступный callback. Если он был установлен и отделился во
время записи, его захваченный required callback не подменяется тихим null.
Профиль без callback остаётся допустимым; квалификация произвольного окна
boot **до первого подключения group provider** сюда не включена.

Message id и отличный от него frame id ACKed после эффекта. Legacy text с
одним frame id использует его как стабильный id строки, чтобы повтор не
создавал новые UUID-строки. Consent/authentication, policy refusals и
анти-echo для уже зеркальных записей сохраняются. Blob retrieval, content
manifest ACK и другие виды control frames не объявляются целиком
crash-квалифицированными этой проверкой.

## Native-сценарий и отрицательный контроль

Три настоящих встроенных узла, отдельные encrypted-контейнеры и три локальных
процесса реле. Frontend в одном Dart процессе; это не три GUI/OS-процесса или
физических телефона.

После link A/B и contact introduction C устройство B выключается. Только на
границе `onMessageStored` A тестом инъецируется отказ; текстовая строка уже
записана. C отправляет через обычный `sendText` и его настоящий retry ladder,
без ручной подмены journal или ACK. Проверка ждёт повторной попытки публикации
либо преждевременного delivered — и требует **повтор плюс отсутствие ACK**.

На базе callback вызван один раз, а sender уже получает ACK: неизменённый
native-тест падает (`expected >=2`, `actual 1`). Возвращены пять production
файлов базы, тот же тест и те же CLI/FFI; исправленные файлы восстановлены в
`finally`.

На исправлении отказ снимается после подтверждения повторной попытки. Вызван
реальный group publisher, journal присутствует к моменту ACK; успешная
публикация одна. C выключается, B включается и получает сообщение от A.
Перезапуск B сохраняет одну копию, исходные author/seq/timestamp и направление.
Поздние async errors контролируются fixture и должны быть нулевыми.

Первый private runner ошибочно передал три production-модуля как test targets
(`main` отсутствует). Сам native-кейс завершился, но exit 1 такого runner не
засчитан PASS; аргументы исправлены перед отрицательным и финальными прогонами.
Это ошибка запуска проверки, не дефект приложения.

## Результаты и границы

Агрегаты, software SHA и cleanup — в `summary.json`. Сырые журналы, fixture
идентификаторы и stack traces остаются в private cache. Новые fault injection
и evidence switches находятся только в тестах.

Финальные результаты: **186 selected regression tests passed, 0 skipped**,
анализ изменённых Dart-файлов без замечаний. Финальный native runner завершён
с exit 0; все lifecycle gates и нулевой late-error gate проходят. Worker,
три реле и временный root проверены после каждого из четырёх запусков стенда.

SDK/HV не менялись и не пересобирались. Использованы pinned CLI/SDK FFI и
проверенная HV FFI из предыдущей итерации (`47c28bc4`), с актуальными Dart
checksums. Flutter: `TMPDIR=/private/tmp/`. Пользовательские приложения,
телефоны, личности, микрофон и внешние реле не затронуты. Все owned процессы
и root каждого запущенного стенда проверяются после завершения.

Это закрывает проверенный retry/ACK пропуск. Native crash A на каждой границе
записи/ratchet, long-offline, произвольные одновременные edit/delete/link,
уведомления ОС после crash и вся multi-device матрица здесь не квалифицированы.
