# Подготовка оставшейся части history cohort

В `_HistoryWriteCohort` убраны отдельные последовательные волны по четыре
строки внутри одной 16-строчной публикации. Подготовка заполняет **оставшийся
бюджет той же публикации**, учитывая уже staged rows. Порядок применения,
смешанные insert/ordering families, проверка актуального доступа перед
публикацией и storage commit, durable result и checkpoint не изменены.

**Ускорение полной догрузки не доказано.** Подтверждено устранение конкретного
ожидания: удержанная первая подготовка больше не мешает начать остальные 15
строк этой публикации. Native-проверки подтвердили сохранность, но пока не
дали основания объявить общий выигрыш времени. Догрузка остаётся активной.

## Регрессии и предел работы

Два независимых gate-сценария без порога elapsed time:

- прежний код при удержанной первой строке начинал 4 подготовки вместо 16;
  assertion-red воспроизведён на текущей базе;
- промежуточное простое увеличение волны до 16 нарушало выбранный общий
  бюджет: после 8 опубликованных posts и 8 staged ordering rows запускало
  ещё 16 вместо 8. Новый тест дал 32 started вместо 24. Этот вариант отклонён.

Окончательный код вычисляет `16 - pending.length`, сдвигает input cursor по
фактической длине волны и сохраняет последовательную публикацию. В смешанном
сценарии после снятия gate получены ровно `post / ordering / post`, размеры
`8 / 8 / 16`, все исходные ID, тела и canonical positions, без дублей.

Пройдено **94 history + 15 retry-lifecycle tests**, всего 109 различных тестов.
После временных control-подмен два gate-теста повторно прошли на возвращённом
candidate; это не два дополнительных различных теста. Targeted analyzer и
format/diff checks прошли. Проверки revoke, отказа commit, позднего завершения
abort, overlap двух источников и порядка разных families входят в history suite.

## Native-сценарии и границы сравнения

Три отдельных Mac/JIT provider-процесса, две личности, три private loopback
Core, настоящие SDK/ratchet/HVS. Runtime SDK зафиксирован на `c6699c28`,
source checkout SDK — `7d34e4e5`; бинарники между фазами не менялись. Это
квалификация Dart-изменения с прежними проверенными native artifacts, не новая
квалификация всех изменений текущего SDK. CPU profiling выключен.

Сначала выполнены control / candidate / control для свежего B. Во всех фазах
сошлись **2000/2000 ID, порядок, позиции и delivered**, completed-history
retries — 0. Наблюдаемое полное время: 20,655 / 20,562 / 20,558 с. Но wire
разбор показал **0 primary history-page pairs A → B**: основная история пришла
через snapshot. Эти времена не считаются оценкой данной оптимизации.

Первый предварительный запуск также имел сошедшиеся данные, но его private
скрипт ошибочно требовал одновременно `receiverCrashRequested=true` и `false`.
Он исключён из квалифицированных фаз; после исправления контроль повторён.
В последующих результатах отдельно сохранён реальный exit code теста и код
квалификатора. Пройденный тест и пройденный стендовый gate не смешиваются.

Затем выполнен сценарий, который действительно использует missing-history
pages: частичный приём → настоящий SIGKILL B → A/C offline → boot inspection B
до сети → возвращается только A → полные 2000 → A/C offline → повторный boot
inspection B. Последним выполнен тот же сценарий на прежних четырёх волнах.

| Наблюдение | Candidate: оставшийся бюджет 16 | Control: волны 4 |
|---|---:|---:|
| Строк наблюдалось перед SIGKILL | 574 | 687 |
| Сохранилось до создания сети нового B | 622 | 687 |
| Строк при одновременно offline A/C | 622 | 687 |
| После возврата из `start(A)` до полной сходимости | 20,469 с | 20,559 с |
| Page query A → last part B, медиана | 91,705 мс | 89,860 мс |
| Last part B → next query A, медиана | 280,257 мс | 303,207 мс |
| Полных неповторённых page replies | 39 | 44 |
| Completed-history retries | 0 | 0 |

Все наблюдавшиеся до kill ID, тела, delivered и уже canonical positions
сохранены. Дополнительные in-flight строки разрешены только из исходного
полного набора: 622 после старта вместо ранее наблюдавшихся 574 не потеря.
В обоих сценариях полные **2000/2000** сохранились при финальном старте до сети,
без повторного контакта с A/C и без sibling mailbox.

Меньшая медиана receiver stage не объявлена причинным ускорением: точки crash,
частичные истории, число страниц, случайные IDs/keys и scheduling различались.
Общее время практически одинаково, polling грубее wire timestamps. Изменение
снимает доказанный барьер подготовки и прошло проверки корректности; Android,
AOT, WAN и устойчивый общий выигрыш остаются для дальнейшей квалификации.

## Подлинность, очистка и приватность

В каждом native run заморожены **1509 source/dependency inputs**. Между
controls/candidate отличается ровно один production Dart-файл; A1/A2 source
inputs совпали побайтово. Native SHA проверены до/после, выбранные FFI/HVS
наблюдались в mappings трёх живых workers. SDK/HVS исходники не менялись.

Все пять зачтённых native-сценариев имеют test exit 0, qualification 0 и
cleanup 0. Проверены 18/18/18/27/27 PID и 26/23/19/25/29 портов: своих живых
процессов и listeners нет, runtime directories и одноразовые контейнеры убраны.
Исключённый harness run тоже очищен. Blackview и Poco не использовались,
production и реальные профили не менялись. Push/релиза нет.

[Summary](summary.json) содержит только агрегаты; raw logs, device/request IDs,
адреса, порты, пути, body tags и digests остаются приватными.
