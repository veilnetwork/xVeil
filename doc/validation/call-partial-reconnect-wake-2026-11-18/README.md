# NETCALL-01: повтор после частичного восстановления соединений

**Исправлен подтверждённый отдельный механизм лишнего ожидания.** Полное
восстановление звука при смене сети не исправлено. Окончательная AOT сохранила
звонок с возрастом последнего audio RX до 5,131 с; промежуточная серия дала
25,976 с. Устойчивого ускорения эти отдельные прогоны не доказывают.

## Механизм и правка

После неудачной проверки relay-кандидата CallService сохраняет работающий
direct и назначает повтор через пять секунд. Возврат overlay-соединений
может разбудить этот повтор раньше, но прежний observer распознавал только
переход `0 → положительное число`. При `2 → 1 → 2` оставшаяся сессия
скрывала возврат другой; уже пригодный кандидат ждал обычный таймер.
Такой же hint терялся, если частичное восстановление происходило во время
незавершённой проверки кандидата.

Observer теперь соединяет наблюдавшиеся уменьшение и рост в любом порядке:
замена может зарегистрироваться до завершения старого runner (`2 → 3 → 2`).
Пара потребляет один wake hint; полный `0 → positive` сохраняется. Первый
положительный snapshot, одинаковые числа и изменения только в одну сторону
не обходят delay. Существующие
сериализация, generation-проверка завершения flight, отмена при hangup/dispose
и ожидание native receive repair сохранены.

Число сессий остаётся **только поводом проверить** уже отложенный переход:
нет нового автоматического handover без pending intent, допуск пути и sealed
peer echo по-прежнему обязательны. Не подтверждённый кандидат оставляет
direct; anonymous/consent guards не менялись. Native SDK, wire, таймауты,
схема хранения и mailbox не менялись.

## Регрессии

Три новых теста на исходном коде упали assertion-red: второй switch не
происходил. Затем два дополнительных assertion-red отвергли промежуточный
вариант, учитывавший только loss-before-growth. В окончательном варианте
прошли пять новых сценариев:

- возврат сессии при выжившей другой — до любого продвижения fake clock;
- публикация замены до teardown предшественника, также без продвижения часов;
- частичный reconnect в обоих порядках во время удержанного completer — без
  перекрывающихся opens, с сохранением wake после отказа старого flight;
- повторная проверка всё ещё не подтверждённого пути — без переключения,
  отбоя и дополнительных повторов от дубликатов/последующего роста.

Итоговая серия **453 passed / 0 skipped** включает 18 overlay-reconnect
проверок, включая эти пять. Отдельные focused прогоны не прибавлены к числу
уникальных проверок. Исходники хешированы до/после финальной серии и стабильны;
focused analyze чист. Flutter выполнялся с `TMPDIR=/private/tmp/`.

## Физический контроль без ручных банов

Продолжена [предыдущая квалификация](../netcall-handover-qualification-2026-11-18/README.md).
В disposable QA-пакетах список тестнет-сидов уменьшен до одного разного
сида на каждом конце. Однако native sessions затем показали **три Core**,
с дополнительными динамическими записями из rendezvous-диапазона. Свежий
discovery и восстановление прежних записей здесь не разделены. Этот контроль
**не засчитан как один активный Core**, в отличие от одного настроенного
сида. Банов на обоих клиентах не было.

В Android baseline сохранены прежние AOT/native bytes, изменён только seed
asset и подпись QA. Mac не перекомпилировался: менялся seed resource его
подписанного контейнера. Поэтому SHA подписанного App.framework не объявляется
неизменным — повторная подпись меняет его байты. В кандидате пересобрана
**только Android AOT**: из product
source изменён только CallService; добавлена отдельная QA version marker.
Все 13 остальных native libraries внутри APK совпали с baseline побайтно;
подпись и SHA установленного APK проверены. Mac использовал прежнюю компиляцию AOT и SDK
`53fbbe34`, Android SDK/media/storage — из 0.13.102. Нового Rust build не было:
Cargo для этого probe был явно запрещён. Это не квалификация всех последних
group/revoke-изменений текущей ветки или новой Mac AOT.

Оба звонка начинались с подтверждённых active P2P и свежего native audio RX.
Mac принимал без микрофона. Слышимость человеком, двустороннее аудио и видео
не проверялись; аудиозаписи не создавались.

| Сборка | Wi-Fi → cellular: максимальный наблюдавшийся возраст RX | Первый свежий RX после обнаружения cellular | Cellular → Wi-Fi: максимальный возраст RX |
|---|---:|---:|---:|
| Baseline | 6,320 с | 5,669 с | 0,645 с |
| Промежуточный Android candidate | 25,976 с | 25,354 с | 0,392 с |
| Окончательный Android candidate | 5,131 с | 4,600 с | 0,347 с |

Все три вызова сохранились в обеих сменах сети. В промежуточном варианте
журнал телефона
показал настоящий `overlay sessions restored after partial loss` и сразу
`retrying deferred relay`. Hint пришёл через **3308 мс** после предыдущего
defer, до прежнего пятисекундного срока. Следующий open начался; это
подтверждает работу новой проводки в AOT, **не сокращение полной паузы**.

В окончательном варианте реально наблюдались три partial-restoration hint;
отложенных повторов в этом звонке не потребовалось, liveness timeout не было.
Для него перед захватом отдельно проверены active P2P, media transport,
число Core и пустой набор банов на обоих концах. Native trace/pcap для этого
последнего функционального повтора не включались.

Промежуточная серия хуже по ожиданию RX. Причинность правки не доказана:
маршруты/число отвечающих соединений не зафиксированы, выборка — один звонок
на вариант, параметры пассивного захвата отличаются. На телефоне кандидата
также наблюдались два Core keepalive timeout. Ускорение, отсутствие регрессии
в общей длительности или устранение NETCALL-01 не заявляются.

Возраст RX — периодически наблюдаемый native age, не точная сетевая тишина.
Время после default отсчитывается от первого опросного обнаружения типа сети.
Native link/nonce снимки подтверждают реальные замены сессий. Числа включают
P2P peer, поэтому четыре сессии на старте — три Core и собеседник.

## Новый материал по transport first flight

Короткие pcap с `snaplen=96` сняты на testnet: один в baseline и три
одновременно в промежуточном candidate. Они остаются private; это усечённые пакеты, а не
полный payload. Три capture кандидата завершились без kernel drops.
Production и конфигурации сервисов не менялись.

По общему новому source после handover получены 39/46/28 TCP flows на трёх
Core; у 23/39/19 есть подтверждённое открытие TCP, но нет наблюдавшегося
payload в pcap. Соответствие source телефону выведено из контролируемой смены
сети и совпадения нового source в независимых захватах, не из расшифровки.
На телефоне зафиксирован 81 незавершённый obfs4 handshake: приложение записало
69–194 байта первого обмена, чтение осталось нулевым. Во всех этих срезах
`acked_bytes=1`, `received_bytes=0`, `notsent_bytes=0`; в 80 есть retransmitted
bytes. Разность sent и retransmitted bytes соответствует записанному размеру
всех 81 первых обменов. Это согласованная **агрегатная** картина отсутствия
подтверждения данных после TCP handshake.

NAT меняет source ports: точного client-socket ↔ pcap-flow сопоставления
получить не удалось. Равенство счётчиков 81 и 81 его не заменяет. Не доказаны
конкретный отбрасывающий hop, DPI, системный фильтр, причина keepalive timeout
или принадлежность каждого пропавшего обмена квалификатору media. GRO/GSO
также не позволяют читать размер pcap-record как точный размер пакета на
проводе. Следующий transport-контроль требует отдельного безопасного
сопоставления first-flight и socket progress. Также нужен двусторонний DATA
контроль настоящего TCP resume при ещё удерживаемом старом runner: принятие
нового handshake само по себе этого не доказывает. Гипотеза о старом
child/parent generation не объявляется установленной причиной.

## Ограничения обвязки и очистка

Первый контроль one-seed отклонён как доказательство one-session после
проверки настоящих sessions. При cleanup повторный launcher перезаписал
признак владения ADB forward; оставшийся собственный mapping удалён отдельно
с точной сверкой устройства и двух портов. Остальные forwards не менялись.
В разборе вывода Android сначала ошибочно приняли capability `NOT_VPN` за
транспорт VPN; проверка исправлена до любых изменений VPN. В последних
валидированных срезах были обычные Wi-Fi/cellular. Запрос разрешения на
отключение VPN явно снят, настройки VPN не менялись. Чтение kernel counters
также уточнено до точной границы имени `sent_bytes`, без захвата `notsent_bytes`.
Эти ошибки оператора не являются дефектами продукта.

Оба QA приложения locked/остановлены, службы телефона отсутствуют.
Исходный QA APK восстановлен с проверкой SHA и оставлен остановленным с
синтетическими данными. Основной APK не менялся; Wi-Fi/mobile-data и QA-only
permissions восстановлены. Contact P2P вернулся к deny, trace выключен.
Mac seed asset и подпись восстановлены, процесс завершён обычным SIGTERM.
Четыре собственные remote capture-группы независимо проверены как завершённые,
локальные listeners/forward освобождены. В двух сборочных раундах удалено
суммарно примерно 2,1 ГиБ собственных промежуточных build caches; точные APK,
provenance и private evidence сохранены.
Адреса, порты, ключи, PID, device/call IDs и raw captures в Git не добавляются.
[Анонимная сводка](summary.json).

Правка локальная, push/релиза нет. NETCALL-01 остаётся активным.

## Проверка прямой сессии при недоступном снимке аудио

После выпуска 0.13.103 воспроизведено ещё одно ожидание на стороне CallService.
Если кэш показывал остановку уже работавшего аудио, пустой ответ движка,
исключение или тайм-аут пропускали проверку текущей прямой сессии. Это могло
оставить закрытый путь до обычного десятисекундного окна восстановления.
Теперь при недоступном снимке проверяется допуск текущего устройства.
Только отрицательный ответ запускает ранний релейный кандидат. Свежий приём
аудио отменяет раннее переключение, а релейный путь по-прежнему требует
подтверждения доставки. Семь проверок из десяти падали до исправления.
После исправления прошли 445 связанных тестов без пропусков. Отдельно
повторены 272 теста CallService со включённой диагностикой. Физический
переход Wi-Fi → cellular в этом раунде не проверен.

## Ответ о состоянии прямой сессии после восстановления подключений

Если xVeil замечает восстановление подключений во время запроса о прямой
сессии, отрицательный ответ может описывать уже закрытую сессию. Пока звук
ещё не вернулся, такой ответ запускал переключение на реле. Теперь при
продолжающейся тишине CallService проверяет сессию устройства заново на
следующем секундном тике. Свежий отрицательный ответ по-прежнему запускает
проверку релейного пути.

До правки оба теста запускали переключение по устаревшему ответу. После
правки свежий положительный ответ сохраняет прямой маршрут, а отрицательный
запускает переход на реле. Прошли 447 связанных тестов и отдельный прогон
274 тестов CallService с диагностикой. Этот сценарий проверен со
смоделированным восстановлением сессий. Переход Wi-Fi → мобильная сеть
на Poco в этом раунде не проверен.

## Восстановление во время повторной отправки готовности P2P

После переключения на P2P приложение повторяет сигнал готовности, пока
собеседник не подтвердит свой прямой маршрут. Если отправка ждала записи,
приложение пропускало раннюю проверку прямой сессии и откладывало переход
на реле по сигналу собеседника. Теперь на уже активном P2P оба пути могут
запустить проверку реле сразу. Переход по-прежнему требует подтверждения
доставки на новом маршруте. Незавершённая проверка кандидата P2P и
первичный запуск звонка сохраняют существующую очередь переключения.
Готовность получает время до асинхронной отправки, чтобы запоздавшая копия
сохранила свой возраст.

Проверены три сигнала восстановления при удержанной записи: недоступность
прямой сессии, объявление релейного маршрута и heartbeat с отзывом согласия
на P2P. Все три теста падали до правки. После правки прошли 450 связанных
тестов и 277 тестов CallService с диагностикой, без пропусков. На Poco
эту версию ещё предстоит проверить при смене сети.

## Запись уведомления о маршруте и проверка P2P

Два сценария показали, что запись служебного уведомления в Outbox могла
задержать проверку прямого пути. Один удерживал повтор сигнала готовности
после получения готовности собеседника. Второй удерживал уведомление об
уже подтверждённом переходе на реле. На контрольной версии в обоих
случаях звонок оставался на реле до завершения записи.

Сигналы по-прежнему идут через обычную надёжную отправку, а проверка
маршрута больше не ждёт её завершения. Повтор готовности текущей попытки
объединяется с незавершённой отправкой. Уведомление получает время события
до обращения к хранилищу. Для возврата на P2P по-прежнему требуются
согласие обоих участников, свежая готовность и подтверждение доставки
напрямую. В тесте текущий релейный маршрут сохраняется до завершения
проверки даже при свободном запуске кандидата.

Две проверки падали до правки. После правки прошли 469 связанных тестов
и 279 тестов CallService с диагностикой, без пропусков. Состояние Outbox
смоделировано удержанной отправкой. Длительность паузы на мобильной сети
в этом раунде не измерялась.

## Незавершённая проверка маршрута после отбоя

Хост воспроизвёл два независимых ожидания. В CallService новый звонок
пропускал проверку замолчавшего P2P, пока завершалась релейная попытка
прошлого звонка. В VeilCallMediaController новая сессия считалась занятой
чужой проверкой доставки и откладывала ремонт своего маршрута.

Отбой теперь освобождает очередь для следующего звонка. Старая команда
закрывает собственный кандидат при выходе. Команда, которая ждала за ней,
отбрасывается даже при повторном идентификаторе звонка с другим собеседником.
Переключения внутри одного звонка по-прежнему сериализуются.

Оба теста падали до исправления. После него прошли 471 связанный тест и
402 теста CallService и VeilCallMediaController с диагностикой, без
пропусков. Ответ старого канала удерживался управляемым тестовым транспортом.
Переход с Wi-Fi на мобильную сеть на Poco в этом раунде не проверен.

## Свежий приём во время проверки реле

Проверка релейного кандидата держит очередь операций, даже пока прежний
медиадвижок принимает пакеты. Из-за этого два запроса свежей статистики
возвращали пустой ответ. Если звук возобновился между периодическими
замерами, проверка перед тайм-аутом могла его пропустить.

Теперь оба запроса читают статистику, пока движок подключён. Активная
проверка маршрута при этом по-прежнему удерживает очередь переключений.
Проверены восстановление приёма при удержанном ответе реле, отказ для
зависшего движка, неизменное время при повторном чтении счётчика и пустой
ответ после отбоя. Два теста падали до правки. Прошли 488 связанных тестов
и 404 теста с диагностикой, без пропусков. Тест удерживал ответ реле в
медиаконтроллере с тестовым транспортом и движком. Физический handover
на Poco не проверен.

## Повтор релейного восстановления после возврата сети

Если согласованный релейный канал не удалось открыть при восстановлении,
приложение завершало звонок даже при уже замеченном переподключении. Теперь
при пустом медиаканале и новом поколении overlay-сессий оно один раз пробует
открыть тот же согласованный маршрут. Повтор проходит через существующую
сериализацию и поднимает медиадвижок через обычный запуск. При повторном
отказе звонок завершается. Снимок счётчика или односторонний рост сессий сам
по себе повтора не запускает.

На исходном коде упали три теста с полным и частичным переподключением.
Проверены также отсутствие восстановления, рост без потери сессий и
неудачный повтор при ещё одном переподключении. Отдельный тест контроллера
подтвердил повторное открытие согласованного реле после отказа сборки
медиаканала. Прошли 494 связанных теста и 410 тестов с диагностикой,
без пропусков.

### Повтор на Poco и Mac

На физическом стенде выполнены три звонка по одному и тому же тестнету.
В кандидате Android заменена только AOT-библиотека Dart. Она собрана с
тремя актуальными файлами управления маршрутом поверх прежнего QA-стенда.
Остальные 13 библиотек, сетевые ресурсы и сертификат подписи совпали.
SHA установленного пакета проверялся до запуска. На Mac использовалась
прежняя QA-сборка в скрытом окне. Mac принимал звук с телефона, аудио не
записывалось. Слышимость человеком и обратное аудионаправление не проверялись.

| Прогон | Возраст последнего audio RX на Mac при Wi-Fi → cellular | Cellular → Wi-Fi | Звонок сохранился |
|---|---:|---:|---|
| Прежняя Android AOT, начало на реле | 0,717 с | 0,359 с | да |
| Новая Android AOT, начало на реле | 3,563 с | 0,555 с | да |
| Новая Android AOT, начало на P2P | 8,623 с | 1,096 с | да |

Прогоны различались по живым соединениям, поэтому цифры характеризуют
отдельные звонки. В последнем прогоне с начальным P2P оба устройства
ушли на реле после отключения Wi-Fi, вернулись на P2P после включения
Wi-Fi и примерно через 15 с снова оказались на реле. Аудио на Mac после
первого обнаружения cellular появилось за 7,873 с. Переход обратно на
P2P сработал, устойчивость прямого маршрута остаётся открытой.

Неудачное открытие того же реле с новым поколением overlay-сессий в этих
трёх звонках не наблюдалось. Новый повтор проверен тестами выше. Первый
старт контрольного захвата остановился до смены сети из-за устаревшего
адреса QA admin socket. Зачтён повтор с заново проверенным адресом.

Прежний QA APK и сетевые настройки телефона восстановлены, основной
APK совпал по SHA. Оба QA-приложения остановлены, Mac завершился по
SIGTERM, порты и ADB forward освобождены. Пауза NETCALL-01 остаётся
открытой. Новый релиз и push не выполнялись.

## Тишина в звонке с выключенным захватом у собеседника

Журналы предыдущего прогона показали причину второго перехода на реле
после возврата Wi-Fi. Счётчик принятых медиапакетов Poco стоял на 70.
Mac в это время продолжал принимать аудио с телефона и сообщал, что
микрофон, камера и демонстрация экрана выключены. После 13 с на P2P
телефон запустил `silent direct path`, хотя Mac продолжал принимать
аудиопакеты.

Теперь отсутствие медиа от собеседника с явно выключенным захватом
само по себе не запускает смену маршрута или запрос ремонта. Отрицательный
ответ о допуске прямой сессии и явный запрос ремонта от собеседника могут
запустить восстановление. Обычный таймер завершения звонка при потере
связи сохраняется. При включении любого вида захвата применяется обычное
окно ожидания медиа, повторы того же состояния его не продлевают.

Четыре теста падали до правки и прошли после неё. Проверены оба вида
маршрута, закрытие прямой сессии при выключенном захвате, явный запрос
ремонта и возобновление захвата аудио или видео. Прошли 498 связанных
тестов и 414 тестов с диагностикой, без пропусков.

В новой Android QA-сборке поменялся только исходник CallService среди трёх
файлов, перенесённых в предыдущую AOT. SHA установленного APK и прежние
13 native-библиотек сверены. Mac работал в режиме приёма без микрофона.
В первом физическом повторе звонок сохранился в обе стороны смены сети.
На переходе к cellular оба клиента запустили раннее восстановление и дважды
исчерпали проверку релейного кандидата. На Poco новый частичный reconnect
разбудил третью попытку раньше пятисекундного таймера. Максимальный
наблюдавшийся возраст последнего аудиопакета на Mac составил 17,677 с,
первый свежий приём после обнаружения cellular — 16,932 с.

При возврате Wi-Fi первая попытка вернуться на P2P закончилась после
отрицательной проверки допуска прямой сессии на Poco. Затем оба клиента
вернулись на P2P, с этим маршрутом закончился захват. Физический прогон
подтвердил сохранение звонка и показал, что задержка при первом переходе
остаётся. Слышимость и обратное аудионаправление не измерялись.

В длинном повторе оба устройства оставались на P2P 44,282 с после возврата
с реле до завершения захвата. Внутри этого окна счётчик Poco не менялся
20,506 с при выключенном захвате Mac. За этот интервал Mac принял ещё 165
аудиопакетов от Poco. Ложный переход на реле из предыдущей сборки не
повторился при тех же признаках тишины. При Wi-Fi → cellular максимальный
возраст аудиопакета в длинном повторе был 7,239 с. Набор живых сессий
различался между прогонами, так что задержки до и после правки напрямую
несопоставимы.

Первое ожидание установки прежнего QA APK истекло. Повторная проверка
подтвердила исходный SHA на телефоне. Настройки сети и разрешения QA
восстановлены, основной APK совпал по SHA. Оба тестовых приложения
остановлены, порты и ADB forward освобождены. Нового push или релиза нет.

## Повтор после подтверждения релейного маршрута собеседником

В медленном прогоне после отключения Wi-Fi Mac зарегистрировал уведомление
Poco о переходе на реле за 469 мс до окончания своего таймера повтора.
Следующая попытка началась только по таймеру. Разница измерена по журналу
одного Mac. Первые две попытки на обоих устройствах завершились без
подтверждённой доставки, поэтому эти 469 мс объясняют лишь часть задержки.

Теперь датированное сообщение текущего собеседника с явным статусом
согласия может один раз ускорить уже начатое релейное восстановление на
данном прямом маршруте. Сигнал во время проверки кандидата сохраняется
до её завершения. Устаревшие сообщения, старый формат без статуса,
чужой отправитель и повторы не открывают дополнительные попытки.
После ускоренного отказа остаётся обычный таймер. Переход по-прежнему
требует подтверждённой доставки по новому релейному маршруту.

Четыре теста падали до правки. После неё прошли 502 связанных теста и 418
тестов с диагностикой, без пропусков. Изменение проверено управляемым
транспортом. Задержка на Poco после применения этой версии не измерялась.

## Повторная проверка уже открытого релейного кандидата

В медленном физическом прогоне оба устройства тратили около 1,1 с от
начала открытия релейного канала до первой проверки доставки. После
неудачной проверки следующие попытки повторяли открытие и подготовку.

Медиаконтроллер теперь сохраняет настроенный кандидат P2P → реле для
одного повтора. Канал остаётся без привязки медиадвижка. На повторе
проверяется свежая доставка по тому же каналу с новым запросом.
Если повтор не подтвердился, следующая попытка открывает новый канал.
Отбой и пересоздание сессии закрывают сохранённый кандидат. Неиспользованный
кандидат закрывается через семь секунд, включая обычную пятисекундную
задержку повтора.

Три теста на прежнем коде воспроизвели повторное открытие и закрытие
кандидата сразу после первой неудачи. После правки проверены успешный и
неуспешный повтор, очистка при отбое и истечение окна на виртуальных часах.
Прошли 506 связанных тестов и 422 теста с диагностикой, без пропусков.

Для физического контроля новая Android AOT установлена в отдельный QA APK.
Сверены сертификат подписи, SHA установленного APK и неизменность остальных
13 библиотек. Кандидат включает также досрочный повтор по сообщению
собеседника из предыдущей правки. Mac использовал прежнюю QA-сборку,
работал без захвата звука. Изменения в Veil SDK в этот раунд не входили.

Два реальных звонка Poco → Mac сохранились при Wi-Fi → cellular → Wi-Fi.
В первом реле подтвердило доставку с первой попытки. Аудио появилось на Mac
через 6,161 с после первого наблюдения cellular. Во втором Poco не получил
подтверждения после трёх проверок. Через 126 мс после постановки повтора
пришло датированное сообщение Mac о переходе на реле. Через 7 мс после этого
пошла новая проверка по сохранённому каналу. Повтор подтвердил работу обеих
правок, но снова исчерпал три проверки без ответа. В этом звонке опрос
зафиксировал свежий счётчик audio RX после cellular через 21,833 с.
Пересоздание медиадвижка влияло на возраст и счётчик пакетов, поэтому это
показание опроса, а не точная длина сетевого провала. Устойчивое ускорение
и устранение NETCALL-01 пока не подтверждены.

Прежний QA APK восстановлен по SHA, основной APK и настройки сети сверены.
Оба тестовых приложения завершены, порты и ADB forward освобождены.
Промежуточная AOT-сборка очищена, подписанный QA APK и её происхождение
сохранены локально. Push и релиз не выполнялись.

## Восстановление после закрытия прямой сессии

В медленном прогоне Poco получил запрос на восстановление от Mac, уже
перешедшего на реле. При пересоздании медиасессии SDK дважды ответил,
что прямой канал не активен. Между первым отказом и началом открытия
релейного канала прошло около 319 мс по журналу Poco. Само открытие реле
заняло ещё около трёх секунд.

Пересоздание медиасессии текущего звонка теперь открывает разрешённый
релейный канал после первого такого ответа SDK. Таймаут и ошибка
проверки P2P по-прежнему допускают повтор. При первоначальном открытии
повтор сохраняется и после ответа о неактивной сессии: прямой канал может
ещё регистрироваться. В правке использован существующий путь открытия
реле с адресацией на устройство и ключами звонка.

Регрессионный тест до исправления зафиксировал вторую попытку открыть P2P
во время восстановления. После исправления проверены первая установка P2P,
переход на реле и сохранение повтора после ошибки или таймаута проверки.
Прошли 510 связанных тестов и отдельный прогон 426 тестов с диагностикой,
оба без пропусков. Анализ изменённых Dart-файлов прошёл без замечаний.

На Poco установлена отдельная Android AOT сборка с этой правкой. Сверены
установленный APK, подпись и неизменность остальных 13 библиотек. Mac
использовал прежнюю QA-сборку в режиме приёма. Один вызов Poco → Mac
сохранился при Wi-Fi → cellular → Wi-Fi: оба конца прошли P2P → реле → P2P.
После обнаружения cellular свежий audio RX на Mac появился через 6,186 с,
максимальный наблюдавшийся возраст последнего аудиопакета составил 6,657 с.
При возврате на Wi-Fi RX обновился в первом опросе с этой сетью.

Пересоздания медиадвижка в этом звонке не потребовалось. Новая ветка
перехода по отказу SDK подтверждена регрессионным тестом. Физический прогон
не подтверждает общего ускорения или слышимость речи. Длительная пауза
NETCALL-01 остаётся открытой.

Прежний QA APK, сетевые настройки и тестовые разрешения восстановлены.
SHA основного приложения совпал. Оба тестовых процесса завершены, порты
и ADB forward освобождены. Push и релиз не выполнялись.

## Проверка P2P сразу после локальной смены сети

В последнем захвате на Poco между выбором отправителя реле и началом
проверки доставки прошло 3,024 с. От начала первой проверки до переключения
прошло ещё 104 мс по тем же часам. Из существующего журнала нельзя выделить
длительность отдельных этапов внутри открытия канала. В частности, SDK
может ждать подготовки локальных медиаканалов до трёх секунд.

После передачи SDK новой рабочей сети xVeil сразу проверяет прямую сессию
устройства текущего собеседника. Во время первых трёх секунд следующая
секундная проверка тоже может найти закрытие, если при первом вызове SDK
ещё видел активную сессию. Начальное подключение, `offline` и `unknown`
сами такой проверки не запускают. При действующей или неизвестной сессии,
свежем приёме либо устаревшем результате остаётся текущий маршрут. Смена
маршрута требует свежего зашифрованного подтверждения от собеседника.

Если досрочная проверка реле не получает подтверждения, прежний медиадвижок
остаётся на месте. Повтор может состояться к концу обычного окна ожидания
тишины. Если подтверждения снова нет, действует прежний интервал повторов.
Это сохраняет возможность восстановления, когда релейный путь становится
пригоден уже после первой попытки.

Семь сценариев покрывают раннюю проверку точного устройства, позднее
закрытие, действующую или неизвестную сессию, свежий приём, новый handover
во время проверки и реле, пригодное только на повторе. Первые тесты падали
из-за отсутствия проверки до истечения таймера. Отдельный тест падал у первого
варианта правки из-за лишнего пятисекундного ожидания повтора.
Итоговая серия прошла 517 связанных тестов и 433 с диагностикой без
пропусков. Анализ трёх изменённых Dart-файлов прошёл без замечаний.

Подписанный изолированный Android APK собран из проверенных исходников.
В QA-пакете заменилась только Dart AOT, остальные 13 библиотек совпали
побайтно. Poco отсутствовал в ADB, поэтому новую сборку на телефоне пока
не проверяли. Пауза NETCALL-01 остаётся открытой. Push и релиз не выполнялись.
