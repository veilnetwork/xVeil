# NETCALL-01: повтор после частичного восстановления соединений

**Исправлен подтверждённый отдельный механизм лишнего ожидания.** Полное
восстановление звука при смене сети не исправлено. Окончательная AOT сохранила
звонок с возрастом последнего audio RX до 5,131 с; промежуточная серия дала
25,976 с. Устойчивого ускорения эти отдельные прогоны не доказывают.

## Механизм и правка

После неудачной проверки relay-кандидата CallService сохраняет работающий
direct и назначает повтор через пять секунд. Возврат overlay-соединений
может разбудить этот повтор раньше, но прежний observer распознавал только
переход `0 → положительное число`. При `2 → 1 → 2` оставшаяся сессия
скрывала возврат другой; уже пригодный кандидат ждал обычный таймер.
Такой же hint терялся, если частичное восстановление происходило во время
незавершённой проверки кандидата.

Observer теперь соединяет наблюдавшиеся уменьшение и рост в любом порядке:
замена может зарегистрироваться до завершения старого runner (`2 → 3 → 2`).
Пара потребляет один wake hint; полный `0 → positive` сохраняется. Первый
положительный snapshot, одинаковые числа и изменения только в одну сторону
не обходят delay. Существующие
сериализация, generation-проверка завершения flight, отмена при hangup/dispose
и ожидание native receive repair сохранены.

Число сессий остаётся **только поводом проверить** уже отложенный переход:
нет нового автоматического handover без pending intent, допуск пути и sealed
peer echo по-прежнему обязательны. Не подтверждённый кандидат оставляет
direct; anonymous/consent guards не менялись. Native SDK, wire, таймауты,
схема хранения и mailbox не менялись.

## Регрессии

Три новых теста на исходном коде упали assertion-red: второй switch не
происходил. Затем два дополнительных assertion-red отвергли промежуточный
вариант, учитывавший только loss-before-growth. В окончательном варианте
прошли пять новых сценариев:

- возврат сессии при выжившей другой — до любого продвижения fake clock;
- публикация замены до teardown предшественника, также без продвижения часов;
- частичный reconnect в обоих порядках во время удержанного completer — без
  перекрывающихся opens, с сохранением wake после отказа старого flight;
- повторная проверка всё ещё не подтверждённого пути — без переключения,
  отбоя и дополнительных повторов от дубликатов/последующего роста.

Итоговая серия **453 passed / 0 skipped** включает 18 overlay-reconnect
проверок, включая эти пять. Отдельные focused прогоны не прибавлены к числу
уникальных проверок. Исходники хешированы до/после финальной серии и стабильны;
focused analyze чист. Flutter выполнялся с `TMPDIR=/private/tmp/`.

## Физический контроль без ручных банов

Продолжена [предыдущая квалификация](../netcall-handover-qualification-2026-11-18/README.md).
В disposable QA-пакетах список тестнет-сидов уменьшен до одного разного
сида на каждом конце. Однако native sessions затем показали **три Core**,
с дополнительными динамическими записями из rendezvous-диапазона. Свежий
discovery и восстановление прежних записей здесь не разделены. Этот контроль
**не засчитан как один активный Core**, в отличие от одного настроенного
сида. Банов на обоих клиентах не было.

В Android baseline сохранены прежние AOT/native bytes, изменён только seed
asset и подпись QA. Mac не перекомпилировался: менялся seed resource его
подписанного контейнера. Поэтому SHA подписанного App.framework не объявляется
неизменным — повторная подпись меняет его байты. В кандидате пересобрана
**только Android AOT**: из product
source изменён только CallService; добавлена отдельная QA version marker.
Все 13 остальных native libraries внутри APK совпали с baseline побайтно;
подпись и SHA установленного APK проверены. Mac использовал прежнюю компиляцию AOT и SDK
`53fbbe34`, Android SDK/media/storage — из 0.13.102. Нового Rust build не было:
Cargo для этого probe был явно запрещён. Это не квалификация всех последних
group/revoke-изменений текущей ветки или новой Mac AOT.

Оба звонка начинались с подтверждённых active P2P и свежего native audio RX.
Mac принимал без микрофона. Слышимость человеком, двустороннее аудио и видео
не проверялись; аудиозаписи не создавались.

| Сборка | Wi-Fi → cellular: максимальный наблюдавшийся возраст RX | Первый свежий RX после обнаружения cellular | Cellular → Wi-Fi: максимальный возраст RX |
|---|---:|---:|---:|
| Baseline | 6,320 с | 5,669 с | 0,645 с |
| Промежуточный Android candidate | 25,976 с | 25,354 с | 0,392 с |
| Окончательный Android candidate | 5,131 с | 4,600 с | 0,347 с |

Все три вызова сохранились в обеих сменах сети. В промежуточном варианте
журнал телефона
показал настоящий `overlay sessions restored after partial loss` и сразу
`retrying deferred relay`. Hint пришёл через **3308 мс** после предыдущего
defer, до прежнего пятисекундного срока. Следующий open начался; это
подтверждает работу новой проводки в AOT, **не сокращение полной паузы**.

В окончательном варианте реально наблюдались три partial-restoration hint;
отложенных повторов в этом звонке не потребовалось, liveness timeout не было.
Для него перед захватом отдельно проверены active P2P, media transport,
число Core и пустой набор банов на обоих концах. Native trace/pcap для этого
последнего функционального повтора не включались.

Промежуточная серия хуже по ожиданию RX. Причинность правки не доказана:
маршруты/число отвечающих соединений не зафиксированы, выборка — один звонок
на вариант, параметры пассивного захвата отличаются. На телефоне кандидата
также наблюдались два Core keepalive timeout. Ускорение, отсутствие регрессии
в общей длительности или устранение NETCALL-01 не заявляются.

Возраст RX — периодически наблюдаемый native age, не точная сетевая тишина.
Время после default отсчитывается от первого опросного обнаружения типа сети.
Native link/nonce снимки подтверждают реальные замены сессий. Числа включают
P2P peer, поэтому четыре сессии на старте — три Core и собеседник.

## Новый материал по transport first flight

Короткие pcap с `snaplen=96` сняты на testnet: один в baseline и три
одновременно в промежуточном candidate. Они остаются private; это усечённые пакеты, а не
полный payload. Три capture кандидата завершились без kernel drops.
Production и конфигурации сервисов не менялись.

По общему новому source после handover получены 39/46/28 TCP flows на трёх
Core; у 23/39/19 есть подтверждённое открытие TCP, но нет наблюдавшегося
payload в pcap. Соответствие source телефону выведено из контролируемой смены
сети и совпадения нового source в независимых захватах, не из расшифровки.
На телефоне зафиксирован 81 незавершённый obfs4 handshake: приложение записало
69–194 байта первого обмена, чтение осталось нулевым. Во всех этих срезах
`acked_bytes=1`, `received_bytes=0`, `notsent_bytes=0`; в 80 есть retransmitted
bytes. Разность sent и retransmitted bytes соответствует записанному размеру
всех 81 первых обменов. Это согласованная **агрегатная** картина отсутствия
подтверждения данных после TCP handshake.

NAT меняет source ports: точного client-socket ↔ pcap-flow сопоставления
получить не удалось. Равенство счётчиков 81 и 81 его не заменяет. Не доказаны
конкретный отбрасывающий hop, DPI, системный фильтр, причина keepalive timeout
или принадлежность каждого пропавшего обмена квалификатору media. GRO/GSO
также не позволяют читать размер pcap-record как точный размер пакета на
проводе. Следующий transport-контроль требует отдельного безопасного
сопоставления first-flight и socket progress. Также нужен двусторонний DATA
контроль настоящего TCP resume при ещё удерживаемом старом runner: принятие
нового handshake само по себе этого не доказывает. Гипотеза о старом
child/parent generation не объявляется установленной причиной.

## Ограничения обвязки и очистка

Первый контроль one-seed отклонён как доказательство one-session после
проверки настоящих sessions. При cleanup повторный launcher перезаписал
признак владения ADB forward; оставшийся собственный mapping удалён отдельно
с точной сверкой устройства и двух портов. Остальные forwards не менялись.
В разборе вывода Android сначала ошибочно приняли capability `NOT_VPN` за
транспорт VPN; проверка исправлена до любых изменений VPN. В последних
валидированных срезах были обычные Wi-Fi/cellular. Запрос разрешения на
отключение VPN явно снят, настройки VPN не менялись. Чтение kernel counters
также уточнено до точной границы имени `sent_bytes`, без захвата `notsent_bytes`.
Эти ошибки оператора не являются дефектами продукта.

Оба QA приложения locked/остановлены, службы телефона отсутствуют.
Исходный QA APK восстановлен с проверкой SHA и оставлен остановленным с
синтетическими данными. Основной APK не менялся; Wi-Fi/mobile-data и QA-only
permissions восстановлены. Contact P2P вернулся к deny, trace выключен.
Mac seed asset и подпись восстановлены, процесс завершён обычным SIGTERM.
Четыре собственные remote capture-группы независимо проверены как завершённые,
локальные listeners/forward освобождены. В двух сборочных раундах удалено
суммарно примерно 2,1 ГиБ собственных промежуточных build caches; точные APK,
provenance и private evidence сохранены.
Адреса, порты, ключи, PID, device/call IDs и raw captures в Git не добавляются.
[Анонимная сводка](summary.json).

Правка локальная, push/релиза нет. NETCALL-01 остаётся активным.

## Проверка прямой сессии при недоступном снимке аудио

После выпуска 0.13.103 воспроизведено ещё одно ожидание на стороне CallService.
Если кэш показывал остановку уже работавшего аудио, пустой ответ движка,
исключение или тайм-аут пропускали проверку текущей прямой сессии. Это могло
оставить закрытый путь до обычного десятисекундного окна восстановления.
Теперь при недоступном снимке проверяется допуск текущего устройства.
Только отрицательный ответ запускает ранний релейный кандидат. Свежий приём
аудио отменяет раннее переключение, а релейный путь по-прежнему требует
подтверждения доставки. Семь проверок из десяти падали до исправления.
После исправления прошли 445 связанных тестов без пропусков. Отдельно
повторены 272 теста CallService со включённой диагностикой. Физический
переход Wi-Fi → cellular в этом раунде не проверен.

## Ответ о состоянии прямой сессии после восстановления подключений

Если xVeil замечает восстановление подключений во время запроса о прямой
сессии, отрицательный ответ может описывать уже закрытую сессию. Пока звук
ещё не вернулся, такой ответ запускал переключение на реле. Теперь при
продолжающейся тишине CallService проверяет сессию устройства заново на
следующем секундном тике. Свежий отрицательный ответ по-прежнему запускает
проверку релейного пути.

До правки оба теста запускали переключение по устаревшему ответу. После
правки свежий положительный ответ сохраняет прямой маршрут, а отрицательный
запускает переход на реле. Прошли 447 связанных тестов и отдельный прогон
274 тестов CallService с диагностикой. Этот сценарий проверен со
смоделированным восстановлением сессий. Переход Wi-Fi → мобильная сеть
на Poco в этом раунде не проверен.

## Восстановление во время повторной отправки готовности P2P

После переключения на P2P приложение повторяет сигнал готовности, пока
собеседник не подтвердит свой прямой маршрут. Если отправка ждала записи,
приложение пропускало раннюю проверку прямой сессии и откладывало переход
на реле по сигналу собеседника. Теперь на уже активном P2P оба пути могут
запустить проверку реле сразу. Переход по-прежнему требует подтверждения
доставки на новом маршруте. Незавершённая проверка кандидата P2P и
первичный запуск звонка сохраняют существующую очередь переключения.
Готовность получает время до асинхронной отправки, чтобы запоздавшая копия
сохранила свой возраст.

Проверены три сигнала восстановления при удержанной записи: недоступность
прямой сессии, объявление релейного маршрута и heartbeat с отзывом согласия
на P2P. Все три теста падали до правки. После правки прошли 450 связанных
тестов и 277 тестов CallService с диагностикой, без пропусков. На Poco
эту версию ещё предстоит проверить при смене сети.

## Запись уведомления о маршруте и проверка P2P

Два сценария показали, что запись служебного уведомления в Outbox могла
задержать проверку прямого пути. Один удерживал повтор сигнала готовности
после получения готовности собеседника. Второй удерживал уведомление об
уже подтверждённом переходе на реле. На контрольной версии в обоих
случаях звонок оставался на реле до завершения записи.

Сигналы по-прежнему идут через обычную надёжную отправку, а проверка
маршрута больше не ждёт её завершения. Повтор готовности текущей попытки
объединяется с незавершённой отправкой. Уведомление получает время события
до обращения к хранилищу. Для возврата на P2P по-прежнему требуются
согласие обоих участников, свежая готовность и подтверждение доставки
напрямую. В тесте текущий релейный маршрут сохраняется до завершения
проверки даже при свободном запуске кандидата.

Две проверки падали до правки. После правки прошли 469 связанных тестов
и 279 тестов CallService с диагностикой, без пропусков. Состояние Outbox
смоделировано удержанной отправкой. Длительность паузы на мобильной сети
в этом раунде не измерялась.

## Незавершённая проверка маршрута после отбоя

Хост воспроизвёл два независимых ожидания. В CallService новый звонок
пропускал проверку замолчавшего P2P, пока завершалась релейная попытка
прошлого звонка. В VeilCallMediaController новая сессия считалась занятой
чужой проверкой доставки и откладывала ремонт своего маршрута.

Отбой теперь освобождает очередь для следующего звонка. Старая команда
закрывает собственный кандидат при выходе. Команда, которая ждала за ней,
отбрасывается даже при повторном идентификаторе звонка с другим собеседником.
Переключения внутри одного звонка по-прежнему сериализуются.

Оба теста падали до исправления. После него прошли 471 связанный тест и
402 теста CallService и VeilCallMediaController с диагностикой, без
пропусков. Ответ старого канала удерживался управляемым тестовым транспортом.
Переход с Wi-Fi на мобильную сеть на Poco в этом раунде не проверен.

## Свежий приём во время проверки реле

Проверка релейного кандидата держит очередь операций, даже пока прежний
медиадвижок принимает пакеты. Из-за этого два запроса свежей статистики
возвращали пустой ответ. Если звук возобновился между периодическими
замерами, проверка перед тайм-аутом могла его пропустить.

Теперь оба запроса читают статистику, пока движок подключён. Активная
проверка маршрута при этом по-прежнему удерживает очередь переключений.
Проверены восстановление приёма при удержанном ответе реле, отказ для
зависшего движка, неизменное время при повторном чтении счётчика и пустой
ответ после отбоя. Два теста падали до правки. Прошли 488 связанных тестов
и 404 теста с диагностикой, без пропусков. Тест удерживал ответ реле в
медиаконтроллере с тестовым транспортом и движком. Физический handover
на Poco не проверен.

## Повтор релейного восстановления после возврата сети

Если согласованный релейный канал не удалось открыть при восстановлении,
приложение завершало звонок даже при уже замеченном переподключении. Теперь
при пустом медиаканале и новом поколении overlay-сессий оно один раз пробует
открыть тот же согласованный маршрут. Повтор проходит через существующую
сериализацию и поднимает медиадвижок через обычный запуск. При повторном
отказе звонок завершается. Снимок счётчика или односторонний рост сессий сам
по себе повтора не запускает.

На исходном коде упали три теста с полным и частичным переподключением.
Проверены также отсутствие восстановления, рост без потери сессий и
неудачный повтор при ещё одном переподключении. Отдельный тест контроллера
подтвердил повторное открытие согласованного реле после отказа сборки
медиаканала. Прошли 494 связанных теста и 410 тестов с диагностикой,
без пропусков.

### Повтор на Poco и Mac

На физическом стенде выполнены три звонка по одному и тому же тестнету.
В кандидате Android заменена только AOT-библиотека Dart. Она собрана с
тремя актуальными файлами управления маршрутом поверх прежнего QA-стенда.
Остальные 13 библиотек, сетевые ресурсы и сертификат подписи совпали.
SHA установленного пакета проверялся до запуска. На Mac использовалась
прежняя QA-сборка в скрытом окне. Mac принимал звук с телефона, аудио не
записывалось. Слышимость человеком и обратное аудионаправление не проверялись.

| Прогон | Возраст последнего audio RX на Mac при Wi-Fi → cellular | Cellular → Wi-Fi | Звонок сохранился |
|---|---:|---:|---|
| Прежняя Android AOT, начало на реле | 0,717 с | 0,359 с | да |
| Новая Android AOT, начало на реле | 3,563 с | 0,555 с | да |
| Новая Android AOT, начало на P2P | 8,623 с | 1,096 с | да |

Прогоны различались по живым соединениям, поэтому цифры характеризуют
отдельные звонки. В последнем прогоне с начальным P2P оба устройства
ушли на реле после отключения Wi-Fi, вернулись на P2P после включения
Wi-Fi и примерно через 15 с снова оказались на реле. Аудио на Mac после
первого обнаружения cellular появилось за 7,873 с. Переход обратно на
P2P сработал, устойчивость прямого маршрута остаётся открытой.

Неудачное открытие того же реле с новым поколением overlay-сессий в этих
трёх звонках не наблюдалось. Новый повтор проверен тестами выше. Первый
старт контрольного захвата остановился до смены сети из-за устаревшего
адреса QA admin socket. Зачтён повтор с заново проверенным адресом.

Прежний QA APK и сетевые настройки телефона восстановлены, основной
APK совпал по SHA. Оба QA-приложения остановлены, Mac завершился по
SIGTERM, порты и ADB forward освобождены. Пауза NETCALL-01 остаётся
открытой. Новый релиз и push не выполнялись.

## Тишина в звонке с выключенным захватом у собеседника

Журналы предыдущего прогона показали причину второго перехода на реле
после возврата Wi-Fi. Счётчик принятых медиапакетов Poco стоял на 70.
Mac в это время продолжал принимать аудио с телефона и сообщал, что
микрофон, камера и демонстрация экрана выключены. После 13 с на P2P
телефон запустил `silent direct path`, хотя Mac продолжал принимать
аудиопакеты.

Теперь отсутствие медиа от собеседника с явно выключенным захватом
само по себе не запускает смену маршрута или запрос ремонта. Отрицательный
ответ о допуске прямой сессии и явный запрос ремонта от собеседника могут
запустить восстановление. Обычный таймер завершения звонка при потере
связи сохраняется. При включении любого вида захвата применяется обычное
окно ожидания медиа, повторы того же состояния его не продлевают.

Четыре теста падали до правки и прошли после неё. Проверены оба вида
маршрута, закрытие прямой сессии при выключенном захвате, явный запрос
ремонта и возобновление захвата аудио или видео. Прошли 498 связанных
тестов и 414 тестов с диагностикой, без пропусков.

В новой Android QA-сборке поменялся только исходник CallService среди трёх
файлов, перенесённых в предыдущую AOT. SHA установленного APK и прежние
13 native-библиотек сверены. Mac работал в режиме приёма без микрофона.
В первом физическом повторе звонок сохранился в обе стороны смены сети.
На переходе к cellular оба клиента запустили раннее восстановление и дважды
исчерпали проверку релейного кандидата. На Poco новый частичный reconnect
разбудил третью попытку раньше пятисекундного таймера. Максимальный
наблюдавшийся возраст последнего аудиопакета на Mac составил 17,677 с,
первый свежий приём после обнаружения cellular — 16,932 с.

При возврате Wi-Fi первая попытка вернуться на P2P закончилась после
отрицательной проверки допуска прямой сессии на Poco. Затем оба клиента
вернулись на P2P, с этим маршрутом закончился захват. Физический прогон
подтвердил сохранение звонка и показал, что задержка при первом переходе
остаётся. Слышимость и обратное аудионаправление не измерялись.

В длинном повторе оба устройства оставались на P2P 44,282 с после возврата
с реле до завершения захвата. Внутри этого окна счётчик Poco не менялся
20,506 с при выключенном захвате Mac. За этот интервал Mac принял ещё 165
аудиопакетов от Poco. Ложный переход на реле из предыдущей сборки не
повторился при тех же признаках тишины. При Wi-Fi → cellular максимальный
возраст аудиопакета в длинном повторе был 7,239 с. Набор живых сессий
различался между прогонами, так что задержки до и после правки напрямую
несопоставимы.

Первое ожидание установки прежнего QA APK истекло. Повторная проверка
подтвердила исходный SHA на телефоне. Настройки сети и разрешения QA
восстановлены, основной APK совпал по SHA. Оба тестовых приложения
остановлены, порты и ADB forward освобождены. Нового push или релиза нет.

## Повтор после подтверждения релейного маршрута собеседником

В медленном прогоне после отключения Wi-Fi Mac зарегистрировал уведомление
Poco о переходе на реле за 469 мс до окончания своего таймера повтора.
Следующая попытка началась только по таймеру. Разница измерена по журналу
одного Mac. Первые две попытки на обоих устройствах завершились без
подтверждённой доставки, поэтому эти 469 мс объясняют лишь часть задержки.

Теперь датированное сообщение текущего собеседника с явным статусом
согласия может один раз ускорить уже начатое релейное восстановление на
данном прямом маршруте. Сигнал во время проверки кандидата сохраняется
до её завершения. Устаревшие сообщения, старый формат без статуса,
чужой отправитель и повторы не открывают дополнительные попытки.
После ускоренного отказа остаётся обычный таймер. Переход по-прежнему
требует подтверждённой доставки по новому релейному маршруту.

Четыре теста падали до правки. После неё прошли 502 связанных теста и 418
тестов с диагностикой, без пропусков. Изменение проверено управляемым
транспортом. Задержка на Poco после применения этой версии не измерялась.

## Повторная проверка уже открытого релейного кандидата

В медленном физическом прогоне оба устройства тратили около 1,1 с от
начала открытия релейного канала до первой проверки доставки. После
неудачной проверки следующие попытки повторяли открытие и подготовку.

Медиаконтроллер теперь сохраняет настроенный кандидат P2P → реле для
одного повтора. Канал остаётся без привязки медиадвижка. На повторе
проверяется свежая доставка по тому же каналу с новым запросом.
Если повтор не подтвердился, следующая попытка открывает новый канал.
Отбой и пересоздание сессии закрывают сохранённый кандидат. Неиспользованный
кандидат закрывается через семь секунд, включая обычную пятисекундную
задержку повтора.

Три теста на прежнем коде воспроизвели повторное открытие и закрытие
кандидата сразу после первой неудачи. После правки проверены успешный и
неуспешный повтор, очистка при отбое и истечение окна на виртуальных часах.
Прошли 506 связанных тестов и 422 теста с диагностикой, без пропусков.

Для физического контроля новая Android AOT установлена в отдельный QA APK.
Сверены сертификат подписи, SHA установленного APK и неизменность остальных
13 библиотек. Кандидат включает также досрочный повтор по сообщению
собеседника из предыдущей правки. Mac использовал прежнюю QA-сборку,
работал без захвата звука. Изменения в Veil SDK в этот раунд не входили.

Два реальных звонка Poco → Mac сохранились при Wi-Fi → cellular → Wi-Fi.
В первом реле подтвердило доставку с первой попытки. Аудио появилось на Mac
через 6,161 с после первого наблюдения cellular. Во втором Poco не получил
подтверждения после трёх проверок. Через 126 мс после постановки повтора
пришло датированное сообщение Mac о переходе на реле. Через 7 мс после этого
пошла новая проверка по сохранённому каналу. Повтор подтвердил работу обеих
правок, но снова исчерпал три проверки без ответа. В этом звонке опрос
зафиксировал свежий счётчик audio RX после cellular через 21,833 с.
Пересоздание медиадвижка влияло на возраст и счётчик пакетов, поэтому это
показание опроса, а не точная длина сетевого провала. Устойчивое ускорение
и устранение NETCALL-01 пока не подтверждены.

Прежний QA APK восстановлен по SHA, основной APK и настройки сети сверены.
Оба тестовых приложения завершены, порты и ADB forward освобождены.
Промежуточная AOT-сборка очищена, подписанный QA APK и её происхождение
сохранены локально. Push и релиз не выполнялись.

## Восстановление после закрытия прямой сессии

В медленном прогоне Poco получил запрос на восстановление от Mac, уже
перешедшего на реле. При пересоздании медиасессии SDK дважды ответил,
что прямой канал не активен. Между первым отказом и началом открытия
релейного канала прошло около 319 мс по журналу Poco. Само открытие реле
заняло ещё около трёх секунд.

Пересоздание медиасессии текущего звонка теперь открывает разрешённый
релейный канал после первого такого ответа SDK. Таймаут и ошибка
проверки P2P по-прежнему допускают повтор. При первоначальном открытии
повтор сохраняется и после ответа о неактивной сессии: прямой канал может
ещё регистрироваться. В правке использован существующий путь открытия
реле с адресацией на устройство и ключами звонка.

Регрессионный тест до исправления зафиксировал вторую попытку открыть P2P
во время восстановления. После исправления проверены первая установка P2P,
переход на реле и сохранение повтора после ошибки или таймаута проверки.
Прошли 510 связанных тестов и отдельный прогон 426 тестов с диагностикой,
оба без пропусков. Анализ изменённых Dart-файлов прошёл без замечаний.

На Poco установлена отдельная Android AOT сборка с этой правкой. Сверены
установленный APK, подпись и неизменность остальных 13 библиотек. Mac
использовал прежнюю QA-сборку в режиме приёма. Один вызов Poco → Mac
сохранился при Wi-Fi → cellular → Wi-Fi: оба конца прошли P2P → реле → P2P.
После обнаружения cellular свежий audio RX на Mac появился через 6,186 с,
максимальный наблюдавшийся возраст последнего аудиопакета составил 6,657 с.
При возврате на Wi-Fi RX обновился в первом опросе с этой сетью.

Пересоздания медиадвижка в этом звонке не потребовалось. Новая ветка
перехода по отказу SDK подтверждена регрессионным тестом. Физический прогон
не подтверждает общего ускорения или слышимость речи. Длительная пауза
NETCALL-01 остаётся открытой.

Прежний QA APK, сетевые настройки и тестовые разрешения восстановлены.
SHA основного приложения совпал. Оба тестовых процесса завершены, порты
и ADB forward освобождены. Push и релиз не выполнялись.

## Проверка P2P сразу после локальной смены сети

В последнем захвате на Poco между выбором отправителя реле и началом
проверки доставки прошло 3,024 с. От начала первой проверки до переключения
прошло ещё 104 мс по тем же часам. Из существующего журнала нельзя выделить
длительность отдельных этапов внутри открытия канала. В частности, SDK
может ждать подготовки локальных медиаканалов до трёх секунд.

После передачи SDK новой рабочей сети xVeil сразу проверяет прямую сессию
устройства текущего собеседника. Во время первых трёх секунд следующая
секундная проверка тоже может найти закрытие, если при первом вызове SDK
ещё видел активную сессию. Начальное подключение, `offline` и `unknown`
сами такой проверки не запускают. При действующей или неизвестной сессии,
свежем приёме либо устаревшем результате остаётся текущий маршрут. Смена
маршрута требует свежего зашифрованного подтверждения от собеседника.

Если досрочная проверка реле не получает подтверждения, прежний медиадвижок
остаётся на месте. Повтор может состояться к концу обычного окна ожидания
тишины. Если подтверждения снова нет, действует прежний интервал повторов.
Это сохраняет возможность восстановления, когда релейный путь становится
пригоден уже после первой попытки.

Семь сценариев покрывают раннюю проверку точного устройства, позднее
закрытие, действующую или неизвестную сессию, свежий приём, новый handover
во время проверки и реле, пригодное только на повторе. Первые тесты падали
из-за отсутствия проверки до истечения таймера. Отдельный тест падал у первого
варианта правки из-за лишнего пятисекундного ожидания повтора.
Итоговая серия прошла 517 связанных тестов и 433 с диагностикой без
пропусков. Анализ трёх изменённых Dart-файлов прошёл без замечаний.

Подписанный изолированный Android APK собран из проверенных исходников.
В QA-пакете заменилась только Dart AOT, остальные 13 библиотек совпали
побайтно. Poco отсутствовал в ADB, поэтому новую сборку на телефоне пока
не проверяли. Пауза NETCALL-01 остаётся открытой. Push и релиз не выполнялись.

## Квота IPC при подготовке медиаканала

Открытие P2P и реле использовало один и тот же цикл подготовки. Пока одна
полоса оставалась в `Warming`, каждые 100 мс повторялись и запросы по уже
готовым медиаполосам. При лимите в 10 запросов в секунду с начальным запасом
в 30 запросов очередной опрос мог получить отказ и отложить проверку на
350 мс.

Теперь SDK сначала проверяет полосы, которые ещё не готовы. Основная
полоса проверяется периодически и во время ожидания других, чтобы заметить
потерю поддержки. После дополнительного запроса цикл оставляет время на
пополнение квоты. Перед завершением подготовки SDK повторно проверяет
все отложенные статусы медиаполос. Трёхсекундный предел и проверка доставки
по новому реле сохранены.

Регрессия на виртуальных часах использует прежний лимит IPC и одну медленно
готовящуюся полосу экрана. При готовности экрана через 2,65 с подготовка
сократилась с 3,0 с до 2,7 с, число запросов с 65 до 34, отказов по квоте
с шести до нуля. При восьми оставшихся запросах и готовности через 2,8 с
первый вариант правки пропускал срок. Итоговый вариант подтвердил готовность
через 2,8 с и завершился без отказов по квоте. Проверены также смена статуса
основной полосы перед подтверждением готовности, потеря поддержки во время
ожидания и общий таймаут. Полная серия FFI с `node-embedded,testnet-seeds`
на macOS дала 365 пройденных и один пропущенный тест. Ещё три интеграционные
проверки локального IPC прошли без пропусков.

Предыдущий захват звонка не содержал счётчика этих отказов, поэтому этот
механизм нельзя приписать наблюдавшимся на Poco трём секундам. Исходная
пауза NETCALL-01 остаётся открытой.

На Poco использовали отдельный APK с новой Android ARM64 библиотекой Veil
и Dart-привязками из того же дерева. Сверены соответствие ABI, SHA
установленного APK, подпись, выравнивание ELF на 16 КиБ и SHA остальных
12 библиотек. Первые попытки запуска со старой Dart AOT исключены из
замеров: проверка ABI отклонила пару до входа в приложение. Отдельное
вмешательство установщика Android подтверждено журналом: завершившееся с
задержкой восстановление прежнего APK остановило следующий тестовый запуск.
Перед финальной установкой проверили отсутствие незавершённых сессий.

Звонок Poco → Mac сохранился при Wi-Fi → cellular → Wi-Fi. Свежие
аудиопакеты на Mac появились через 1,116 с после обнаружения cellular и
через 0,520 с после обнаружения Wi-Fi. Максимальный наблюдавшийся возраст
пакета составил соответственно 1,667 с и 0,812 с. На Poco сработала ранняя
проверка P2P из предыдущей правки. По журналу телефона первая проверка
доставки через реле началась через 28 мс после выбора отправителя, переход
завершился через 0,995 с после обнаружения закрытой P2P-сессии. На Mac
первая серия проверок своего реле не дала подтверждения; от первой проверки
до успешного переключения прошло 7,69 с. Микрофон Mac был выключен, поэтому
замеры относятся к направлению Poco → Mac. Оба устройства вернулись на P2P
при живом звонке.

Один физический прогон с двумя изменениями на телефоне не выделяет вклад
правки квоты IPC. Прежний QA APK и настройки восстановлены и проверены.
Основной APK совпал по SHA. Тестовые процессы, порты, ADB forward и сессии
установщика очищены. Временная сборка и несовместимый APK удалены. Релиз и
push не выполнялись.

## Повторный поиск реле после замены соединений

Два трассированных звонка Poco → Mac на одной сборке сохранились при обеих
сменах сети. После перехода на мобильную сеть свежие аудиопакеты появились
через 9,517 и 1,128 с. В медленном прогоне первый отмеченный запрос
подтверждения реле прошёл очередь SDK и дошёл до локального обработчика.
Для этой клетки в захвате нет записи `relay_queued` или приёма на Mac.
Поиск к тому же получателю завершился отрицательно через 501 мс, а
восстановление overlay на телефоне наблюдалось позднее. Захват не содержит
ответов локальных очередей на сам запрос поиска, поэтому его исход нельзя
установить по этой записи.

В прежнем коде поиск ждал 500 мс и сохранял отрицательный результат на
10 секунд даже при отказе всех локальных очередей. Теперь такой поиск
сразу возвращает текущий результат кэша и освобождает запись ожидания
своего неотправленного запроса. Поиск реле с допущенным запросом сохраняет
кэш отрицательного результата для текущих регистраций. При появлении
новой регистрации можно сразу повторить поиск. Это работает и при
подключении к тому же реле с прежним ID.

Два регрессионных теста используют настоящие очереди `SessionTxRegistry`.
В первом полный outbox блокировал поиск до таймера; освободившаяся очередь
должна принять следующий запрос сразу. Во втором один и тот же ID сначала
сохраняет отрицательный результат на старом соединении, затем допускает
поиск на новом. Оба теста воспроизвели дефекты на прежнем коде.
Итоговые прогоны `veil-ipc`, `veil-session` и embedded FFI дали 1293
пройденных и 14 пропущенных тестов. В том числе прошли прежние проверки
общего поиска для одновременных отправок, повторного использования
отрицательного результата на прежнем соединении и смены регистрации.

В новом Android QA APK заменилась только библиотека Veil. Проверены хеши
исходников, установленного пакета и 13 остальных библиотек, совпадение ABI,
выравнивание ELF и подпись. Mac использовал ту же фоновую сборку, что в
двух контрольных звонках. Микрофон Mac был выключен во всех трёх прогонах.

Звонок на новой сборке сохранился в обе смены сети. Свежий аудиопакет
на Mac зафиксирован через 6,700 с после обнаружения мобильной сети и
через 0,521 с после обнаружения Wi-Fi. На мобильном переходе после выбора
отправителя Poco ждал 3,020 с до первой проверки доставки. Эта проверка

перед первой проверкой повторилась, поэтому NETCALL-01 остаётся открытым.
Серия не позволяет оценить вклад исправления кэша на живой сети.

Трассировка на обоих концах выключена. Исходный QA APK, настройки и
разрешения телефона восстановлены. Основной APK совпал по SHA. Оба QA
процесса и сборщик журналов завершены, порты и ADB forward освобождены,
незавершённых сессий установщика нет. Push и релиз не выполнялись.

## Подготовка первого участка реле

Локальный IPC запрашивал подготовку двух предпочтительных реле и возвращал
`Warming` или `Unsupported`, даже если один из двух участков уже был готов.
При отправке медиаклеток готовый участок и так выбирается первым. Теперь
локальная готовность одного из двух позволяет начать проверку доставки.
Подготовка по-прежнему запрашивается у обоих реле, проверка прямого маршрута
для каждого известного устройства сохраняется. Переключение живого
звонка по-прежнему требует зашифрованного ответа от собеседника.

Регрессия воспроизвела `Warming` при готовом первом участке. Она проверяет
оба порядка (`Ready` с `Warming` и `Unsupported`) и прямой путь для тех же
двух устройств. Для физических проверок в действующую переключаемую
трассировку добавлены длительность локальной подготовки, последний статус
каждой полосы и длительность последующей проверки медиаполос. У записей
нет адресов, содержимого медиаданных и идентификаторов звонка.

До исправления, но уже с этой диагностикой, на Poco дважды переключили
живой P2P-звонок с Wi-Fi на мобильную сеть. Свежие пакеты на Mac появились
через 1,128 и 1,101 с после обнаружения новой сети. От выбора отправителя
на телефоне до первой проверки реле прошло 14,7 и 7,0 мс. В обоих случаях
IPC сразу вернул `Unsupported` для основной полосы, и открылся прежний
совместимый путь. Наблюдавшееся ранее ожидание в 3,020 с в этой паре
не повторилось. Его причина по-прежнему неизвестна.

После исправления проверили отдельный подписанный Android QA APK. SHA
установленного пакета, подпись, ABI, выравнивание ELF и остальные 13
библиотек сверены. Оба звонка сохранились при Wi-Fi → cellular. Свежие
пакеты на Mac появились через 11,690 и 0,517 с после обнаружения мобильной
сети. В первом прогоне SDK начал проверку реле спустя 30,5 мс после выбора
отправителя. Десять проверок истекли без совпадающего ответа. Между двумя
сериями с повторным открытием реле контроллер выждал около пяти секунд.
Одиннадцатая проверка получила совпадающий ответ за 370 мс, после чего
контроллер переключил канал без перезапуска медиадвижка. Для двух первых
выборочно записанных зашифрованных клеток есть отметка входа в обработчик
IPC на Poco. В захвате нет совпадающих отпечатков на входе медиаканала Mac.
Конкретное место потери по этим выборочным записям установить нельзя.

Все открытия реле на Poco в этих двух звонках получили `Unsupported` для
основной полосы до истечения миллисекунды. Ветка с одним готовым из двух
участков подтверждена тестом. Вклад этой ветки во время восстановления на
живой сети здесь не измерен. NETCALL-01 остаётся открытым: самая длинная
пауза в этой серии пришлась на повторные проверки доставки и ожидание до
повтора. Замеры относятся к приёму аудиопакетов на Mac с выключенным
микрофоном, без оценки слышимости.

Проверки `veil-ipc`, `veil-session` и embedded FFI: 1294 пройдено,
14 пропущено. Ещё три интеграционные проверки IPC прошли. Трассировка
на обоих концах выключена, QA APK и настройки Poco восстановлены,
основной APK совпал по SHA. Стенд и сборщик журналов остановлены, порты
и ADB forward освобождены. Push и релиз не выполнялись.

## Срок повтора при раннем переподключении

Первый отказ реле после подтверждённой потери P2P назначал следующий
поиск на конец трёхсекундного окна восстановления. Событие переподключения
могло начать проверку раньше. Если она тоже оставалась без ответа, новый
вызов терял исходный срок и добавлял ещё пять секунд. Эта последовательность
наблюдалась в медленном прогоне выше.

Теперь попытка, начатая раньше исходного срока, передаёт его дальше. Если
она заканчивается после срока и подтверждения нет, контроллер начинает
следующую попытку сразу после завершения предыдущей. После начала попытки
в исходный срок или позже возвращается обычный интервал повтора. Успех
снимает таймер. Параллельных переключений нет, зашифрованный ответ от
собеседника по-прежнему обязателен.

Тест на виртуальных часах воспроизвёл потерю срока на прежнем коде. Событие
переподключения приходит в 1 с во время начальной проверки. Вызванная им
попытка начинается в 2 с и завершается без ответа в 3,2 с. Теперь в 3,2 с
доступна следующая попытка, без дополнительной паузы до 8,2 с. После ещё
одного отказа действует обычный интервал. Контроль с
успешной проверкой в 3,2 с подтверждает отмену повтора. Четыре серии
звонков и переключений маршрута дали 448 пройденных тестов. Анализатор Dart
не нашёл замечаний в изменённых файлах.

Для прогона на Poco в отдельном QA APK заменили только Dart AOT. Проверили
исходники, подпись, ABI, режим снимка Flutter и SHA остальных 13 библиотек.
Первая попытка сборки была в release при профильном Flutter в исходном APK.
Телефон отклонил снимок при запуске, до первого звонка. Исходный APK после
этой попытки был восстановлен и сверён.

На исправленной сборке три звонка Poco → Mac сохранились при Wi-Fi →
cellular. Свежие аудиопакеты появились через 0,520, 1,122 и 3,913 с после
обнаружения мобильной сети, максимальный возраст последнего пакета составил
1,262, 1,680 и 4,610 с соответственно. Mac работал в фоне и принимал звук
с выключенным микрофоном. В первых двух звонках Poco начал проверку реле
через 17 и 10 мс после обнаружения закрытого P2P. В третьем звонке
восстановление начал Mac после тишины на P2P. От первой проверки реле до
переключения прошло около 130 мс на каждом конце. В этом прогоне основное
ожидание было до запуска проверки.

Случай с двумя сериями проверок без ответа в трёх звонках не повторился.
Исправление таймера подтверждено регрессией на виртуальных часах, вклад
в длительность физических пауз по этой серии отдельно не измерен.
NETCALL-01 остаётся открытым. QA APK и настройки Poco восстановлены,
основной APK совпал по SHA. Трассировка выключена, тестовые процессы
и сборщик журналов остановлены, порты и ADB forward освобождены.

## Исходящий P2P после смены сети

В медленном звонке из предыдущей серии сверили старый P2P link по журналу
Poco и списку сеансов. Старый link закрылся за 198 мс до уведомления ядра о
мобильной сети. После закрытия на Poco счётчик принятых медиапакетов вырос
с 54 до 56, счётчик аудио остался нулевым. Этот захват не содержит ответов
на запросы доступности P2P и времени прихода этих двух пакетов в нативный
декодер. Контроль Mac начал восстановление после 3,8 с без приёма аудио.

В SDK проверка доступности смотрела на список сеансов для интерфейса.
При смене сети очередь исходящего сеанса удаляется синхронно, запись в
этом списке ждёт выхода её обработчика. Теперь доступность требует
завершённого рукопожатия и открытой очереди с тем же владельцем. Проверка
адреса личности по-прежнему учитывает её подтверждённые устройства.
Зарезервированная очередь без завершённого рукопожатия и хвост старого
сеанса не дают положительного ответа. Та же проверка определяет, нужно ли
заново устанавливать P2P.

В приложении рост общего счётчика приёма мог отменить раннее восстановление
даже при закрытом исходящем пути. Теперь он вызывает повторную проверку
исходящего сеанса. Если сеанс снова доступен, сохраняется P2P. Если его
по-прежнему нет, приложение может начать проверку реле. При неизвестном
результате действует обычное ожидание. Переключение сохраняет требование
свежего зашифрованного подтверждения от собеседника.

Нативная регрессия использует установленный TCP-сеанс с заблокированной
записью: после команды смены сети старый обработчик ещё виден, а исходящая
очередь уже удалена. Старый код ошибочно отвечал положительно. Проверены
зарезервированная замена, закрытый обработчик и второе устройство личности.
Тесты Dart на старом коде воспроизвели отмену восстановления при росте
счётчика. Отдельно проверены восстановившийся исходящий сеанс и прежняя
защита смены поколения маршрута. Прошли 457 тестов Flutter, анализатор Dart
без замечаний.

Полный прогон `veil-node-runtime`, `veil-session` и embedded FFI дал
1911 пройденных и 20 пропущенных тестов. Четыре прежних теста цепочек
воспроизвели `NoRelays` и на исходном SDK: их фикстура записывала номер
TX-регистрации `1` вместо номера реально созданной очереди. Фикстура
теперь берёт номер из реестра. В тесте запуска P2P-обработчика также
добавлена запись завершённого рукопожатия, как в рабочем рантайме.

Отдельный Android QA APK содержал новую библиотеку Veil и Dart AOT.
Сверены хеши исходников и установленного APK, подпись, ABI, режим снимка,
16-КиБ выравнивание и совпадение остальных 12 библиотек. Mac использовал
прежнюю фоновую сборку с выключенным микрофоном.

Все три звонка Poco → Mac сохранились при Wi-Fi → cellular. Свежие аудио-
пакеты на Mac появились через 1,109, 1,099 и 1,649 с после обнаружения
мобильной сети. Максимальный возраст последнего пакета составил 1,826,
1,646 и 2,473 с. Poco во всех трёх звонках обнаружил закрытый P2P раньше
обычного ожидания тишины и начал проверку реле через 46, 9 и 10 мс после
этой отметки. В третьем звонке первые три проверки остались без ответа.
После события восстановления сеансов Poco повторно использовал уже
подготовленный канал и переключился на реле через 2,194 с после обнаружения
закрытого P2P. Ветка повторной проверки при свежем входящем пакете
подтверждена тестом Dart. В этом физическом прогоне она не сработала.
NETCALL-01 остаётся открытым для длинных пауз восстановления.

Трассировка выключена, прежний QA APK и настройки Poco восстановлены,
основной APK совпал по SHA. Оба тестовых процесса завершены, порты и
ADB forward освобождены.

## Двусторонний звук и уведомление о переходе на реле

На Mac запустили фоновую QA-сборку с Dart и SDK той же ревизии, что на
Poco. Тестовый аудиомодуль Mac генерировал сигнал и потреблял выход
декодера без физических микрофона и динамиков. Poco использовал обычный
медиадвижок. Учитывали счётчики RTP, возраст последнего принятого пакета
и счётчики декодера. Содержимое звука не сохранялось.

В контрольном звонке обе стороны получали аудио по P2P перед сменой сети.
На мобильной сети Poco переключился на реле. Mac продолжал принимать
аудио от Poco, оставаясь на P2P для отправки. Зафиксированы локальная
постановка `transportInfo(relay)` и девять повторов без наблюдаемого
перехода Mac. На Poco возраст последнего аудиопакета достиг 10,322 с,
после чего локальная пересборка приёмника сбросила счётчик. Poco завершил
звонок по `livenessTimeout`, через 20 с без активности от Mac. На Mac
тест завершил сохранившийся вызов отдельно. В другом контрольном звонке
переключение сохранилось, а возраст аудиопакета на мобильном переходе
дошёл до 3,044 с на Poco. На возврате в Wi-Fi оба оставались на реле в
конце окна наблюдения.

Во втором контрольном звонке также физически сработала предыдущая правка:
Poco перепроверил исходящий сеанс после входящего пакета, снова получил
`false` и начал раннее восстановление.

После подтверждённого перевода активного P2P-звонка на реле xVeil теперь
отправляет ту же датированную запись о переходе по зашифрованному каналу
управления звонком. Обычная надёжная доставка сохраняется. Из сообщений
о маршруте медиаканал допускает только состоявшийся переход на реле
для текущего прямого звонка. Для перехода у второй стороны по-прежнему требуется
собственное подтверждение доставки. Ответ, отбой, приглашение на P2P и
выбор адреса реле остаются на обычном канале сигнализации.

Регрессия с двумя сервисами воспроизводит состояние P2P/relay при
недоставленных обычных сообщениях. После правки второй сервис начинает
переключение по сообщению с медиаканала. Поздняя копия той же даты не
повторяет переключение. Отдельно проверены сообщение другого звонка,
отбой, отсутствие даты и лишнее поле состояния микрофона. Прошли 537
тестов Flutter, анализатор Dart без замечаний.

В повторной серии на обоих устройствах заменили только Dart AOT и сверили
хеши исходников, режим снимка Flutter, ABI и подпись QA APK. На Poco
побайтно совпали остальные 13 библиотек. Оба звонка остались активными на
обоих концах при Wi-Fi → cellular → Wi-Fi. В обоих звонках Mac получил
уведомление на медиаканале. От его получения до перехода Mac на реле
прошло 109 мс и 1,215 с по часам Mac. В первом звонке уведомление
разбудило уже отложенную попытку. После возврата в Wi-Fi обе стороны
вернулись на P2P в обоих звонках.

Максимальный наблюдавшийся возраст последнего аудиопакета на переходе
Wi-Fi → cellular составил 12,820 с на Poco и 12,805 с на Mac в первом
звонке, 3,182 и 2,252 с во втором. Пакеты, принятые около первого
наблюдения новой сети, были видны раньше последующей паузы. Поэтому
первый принятый пакет не описывает длительность этого разрыва. В медленном
звонке Poco потратил около 12 с от обнаружения закрытого P2P до
подтверждённого реле, включая серии проверок без ответа. На обратном
переходе максимальный наблюдавшийся возраст был 0,728 с на обоих концах
за два прогона. NETCALL-01 остаётся открытым для этих длинных пауз.

Настройки телефона и исходный QA APK восстановлены. Основной APK совпал
по SHA. Оба стенда остановлены, трассировка выключена, порты и ADB forward
освобождены.

## Повтор на Poco и ожидание первого TCP ACK

В медленном звонке предыдущей серии после уведомления ядра о мобильной
сети сразу начались три obfs4-подключения к Core. Каждое запустило свой
запасной TCP-кандидат. TCP открылся на всех шести сокетах. На каждом
ядро приняло от приложения первые 127–185 байт и зарегистрировало 4–6
повторных передач. К закрытию `acked_bytes` оставался на исходном
значении 1, прочитано 0 байт. Три попытки дошли до общего 10-секундного
дедлайна obfs4. Первая подтверждённая сессия к Core появилась через
11,288 с после уведомления о мобильной сети. Отдельное подключение QUIC
к собеседнику в тот же период не открывало сессию к Core. Захват на
клиенте показывает отсутствие подтверждения данных. Место потери данных
или подтверждений неизвестно.

На тех же сборках и в том же тестнете провели ещё три двусторонних звонка.
Все сохранились на обоих концах и вернулись с реле на P2P после возврата
Wi-Fi. Максимальный наблюдавшийся возраст аудиопакета при переходе в
мобильную сеть составил 11,346 / 10,771, 7,824 / 7,797 и 10,238 / 6,896 с
на Poco / Mac. На обратном переходе максимум 0,853 с. Слышимость речи
и акустическое качество не оценивали.

В первом повторе две сессии Core открылись за 220 и 230 мс после
уведомления о смене сети, пока третье obfs4-подключение ещё ждало TCP ACK.
Проверки реле оставались без ответа. Одна из открывшихся сессий закрылась
по keepalive через 7,217 с от уведомления. В этом звонке клиенты дошли
до пересоздания локальных медиасессий. По раннему открытию Core нельзя
судить о времени готовности реле для данного звонка.

Для исходящего основного obfs4-подключения на Android установлен
`TCP_USER_TIMEOUT` в 3 с на время obfs4-рукопожатия. Это предел для
данных, которые TCP не смог подтвердить или отправить при закрытом окне.
Сокет с подтверждёнными данными может дожидаться ответа obfs4 в пределах
прежних 10 с. Оба кандидата получают один и тот же предел, открытие
резервного через 1 с и политика повторов остались прежними. После успешной
проверки obfs4 лимит сбрасывается до значения ядра, до передачи сокета в
OVL1. Входящие соединения и дочерние потоки работают по прежним правилам.
[Справка Linux по `TCP_USER_TIMEOUT`](https://man7.org/linux/man-pages/man7/tcp.7.html#Socket_options).

В QA APK для сравнения заменили только ARM64-библиотеку Veil. Сверены SHA
исходников и APK, подпись, ABI, выравнивание ELF 16 КиБ и совпадение 13
остальных библиотек. Mac использовал прежний фоновый AOT-стенд. В двух
попытках на Poco оба TCP-кандидата открылись, затем остались без
подтверждения первого обмена до `ETIMEDOUT`. От открытия каждого сокета
до его закрытия прошло 3,577–3,626 с. Две попытки подключения вернули
ошибку через 4,791 и 4,825 с от начала каждой, включая задержку до
запуска запасного кандидата. Точка потери в сети остаётся неизвестной.

с телефона. В фоновом Mac QA проверена политика запуска без активации.

## Подготовка реле для голосового звонка

В сохранённом медленном звонке Poco аудиоканал уже был готов, пока
каналы камеры и демонстрации экрана оставались `Warming`. Открытие
реле вернулось по общему дедлайну через **3,001 с**. В другом звонке
локальная готовность всех каналов заняла 105 мс, затем подтверждение
доставки для всей группы заняло ещё 1,001 с и истекло по дедлайну.
Эти ожидания происходили до проверочного пакета, который разрешает
переключить работающий звонок на новый маршрут.

xVeil теперь запрашивает подготовку аудиоканала, если в согласованном
медиа есть звук и нет камеры или демонстрации экрана. Это применяется
при открытии реле и при переходе на него после отказа P2P. Подготовка
проверяет локальную готовность аудиоканала и его свежий ответ до передачи
управления приложению. Решение о переключении по-прежнему требует своей
отдельной зашифрованной проверки. Для видео и демонстрации экрана остаётся
полная подготовка. Каналы видео и демонстрации экрана открытой голосовой
сессии по-прежнему можно использовать при добавлении медиа. Обычная
отправка по реле запрашивает подготовку соответствующего канала при первом
трафике. Новая локальная функция FFI добавлена к прежней, формат ячеек и
адреса получателя сохранены.

Регрессия на виртуальных часах дала полный дедлайн 3 с для прежнего
режима с готовым аудио и постоянно прогревающимися визуальными каналами.
При подготовке только аудио та же фикстура завершилась на первом
запросе без движения часов. Отдельно проверены свежесть ответа,
изоляция каналов и передача настройки через обе ветки открытия реле
из Dart. Прошли **474 теста Flutter** и **367 тестов FFI**, в FFI
6 пропущенных. Анализатор изменённых Dart-файлов без замечаний.
Тест Veil IPC отдельно проверил запуск подготовки видеоканала при отправке
и переход на предпочтительный путь после его готовности.

В QA APK для Poco заменили только Dart AOT и ARM64 FFI. Совпадение 12
остальных библиотек, ABI-контракт, подпись, выравнивание и хеш
установленного APK сверены. Mac остался на прежней фоновой сборке.
Три двусторонних голосовых звонка сохранились при Wi-Fi → мобильная
сеть → Wi-Fi. На мобильном переходе максимум возраста последнего
аудиопакета на Poco / Mac составил **10,128 / 2,998 с**,
**1,752 / 2,011 с** и **1,730 / 1,719 с**. На возврате в Wi-Fi
максимум 1,048 с, две пары вернулись на P2P к концу окна наблюдения.
Физические звонки с видео в этой серии не выполнялись.

В первом звонке позднее повторное открытие реле на Poco показало
**103 мс** локальной подготовки и **102 мс** до ответа на зашифрованную
проверку аудиоканала. Другие источники в этот проход не запрашивались.
Первая сессия Core в том же звонке открылась через 199 мс после
уведомления о мобильной сети. Первое переключение Poco на реле произошло
через 2,580 с. Приложение поставило компактное уведомление о переходе в
очередь, но в журнале Mac его получения в мобильном окне нет. Mac
продолжал отправлять по P2P. Poco возобновил приём после локального
пересоздания медиасессии на ранее выбранном маршруте реле. Пауза первого звонка
остаётся открытой частью NETCALL-01. Журналы показывают постановку
уведомления, но не место его потери. Во втором и третьем звонках Mac
получил компактное уведомление и подтвердил собственный переход на реле.

Телефонные настройки и QA APK восстановлены, хеш основного APK совпал.
Трассировка, тестовые процессы и сборщик остановлены, порты освобождены.

## Уведомление о переходе по проверенному пути

В предыдущем захвате сопоставили зашифрованное компактное уведомление
о переходе по номеру эпохи и последовательности. В медленном звонке
уведомление прошло запись IPC, чтение демоном и локальную постановку в
одну очередь первого хопа. На Mac в мобильном окне нет совпадающего
аутентифицированного приёма. В двух остальных звонках совпадающий приём
есть. Само место потери пока неизвестно.

До правки компактное уведомление использовало отдельный канал
сигнализации на узле. Проверка перед переходом подтверждала аудиоканал.
Теперь короткое датированное уведомление о состоявшемся переходе идёт
по той же локальной ветке отправки через реле, что короткие аудиопакеты.
Оно сохраняет отдельное IPC-подключение для управления звонком,
шифрование ключом звонка, ограниченную очередь и короткий срок
допуска в неё. Порог размера учитывает накладные расходы шифрования.
Пригодные альтернативные первые хопы выбирает существующий механизм.
На проводе конверт несёт нейтральный приоритет. Приложение также
отправляет обычную сигнальную копию. Принимающая сторона проверяет дату,
идентификатор и состояние звонка, затем подтверждает свой путь
зашифрованной проверкой.

Нативный тест провёл обе ветки через настоящий Unix IPC, демультиплексор
и построение конверта, затем открыл его ключом получателя. Он проверил
аудиоветку для уведомления, отдельную сигнальную ветку для обычного
состояния, одинаковый нейтральный приоритет на проводе, отклонение слишком
большого пакета и отказ использовать новый путь на прямом канале.
Прошли 779 тестов Flutter и 368 тестов FFI, в FFI 6 пропущенных.
Анализатор изменённых Dart-файлов без замечаний.

В четырёх голосовых звонках Poco ↔ Mac с Wi-Fi → мобильная сеть →
Wi-Fi сменили только AOT и FFI в QA APK телефона. Сверены подпись,
16-КиБ выравнивание, ABI и хеш установленного APK. Mac работал в фоне
на прежней сборке. Все звонки сохранились и вернулись на P2P к концу
окна наблюдения после возврата Wi-Fi. Все пять отправленных Poco
уведомлений из этой серии наблюдались в очереди того же локального
канала, что аудио, и затем в аутентифицированном приёме Mac. Сопоставление
проверено по зашифрованному хешу. Четыре из пяти уведомлений получили
две постановки на разных первых хопах, одно получило одну.

На мобильном переходе максимальный наблюдавшийся возраст последнего
аудиопакета на Poco / Mac составил 3,678 / 2,474 с, 3,560 / 1,743 с,
8,571 / 8,542 с и 5,390 / 4,815 с. Максимум на обратном переходе 1,082 с.
В самом медленном звонке от раннего запуска восстановления до перехода
на реле на Poco прошло 8,404 с. За это время одна проба подготовки
получила правильный, но просроченный ответ через 1,448 с. Первое
подтверждение, по которому Poco переключился, пришло за 105 мс после
начала новой проверки. Уведомление доставилось, а основной разрыв
возник до его отправки. Общая длительность паузы по-прежнему зависит
от доступности медиа маршрута, NETCALL-01 остаётся открытым.

Исходный QA APK и настройки Poco восстановлены. Хеш основного APK
совпал. Трассировка выключена. Оба тестовых процесса и сборщик
остановлены, порты и ADB forward освобождены.
