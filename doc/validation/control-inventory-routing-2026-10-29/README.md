# Обнаружение моделей и достоверная диагностика управления — 2026-10-29

## Подтверждённые дефекты

1. Запрос и ответ «Спросить у контактов» отправлялись через APP_RT. Этот вход
   принимает только сигналы звонков и P2P-адреса, поэтому кадры каталога
   отбрасывались до обработчика моделей. Два соединённых `MessagingService`
   воспроизвели отсутствие запроса в обоих режимах анонимности.
2. Обычный живой маршрут мог заменить адрес контакта адресом одного устройства,
   известного P2P-службе. После первого исправления два дополнительных прогона
   теста обнаружили неверный адрес назначения. Каталог другого устройства
   личности так нельзя было запросить.
3. Общий helper рассылки считал обмен P2P-адресами и моделями сигнализацией
   звонка, включая категорию ошибки `call-signal-send`. Входящий APP_RT также
   увеличивал счётчик звонков до разбора типа. Пять тестов исходного кода
   воспроизвели потерю каталога и неверную классификацию.

## Исправление

Запрос и ответ моделей идут обычной живой отправкой на адрес личности контакта.
Они проходят прежнюю проверку принятого контакта и больше не наследуют адрес
устройства от P2P/звонка. Сохраняются анонимный транспорт, согласие отвечающего,
окно ожидаемого ответа и пределы каталога. Outbox, mailbox, ACK и история чата
для этих кадров не создаются. Ошибка живой отправки остаётся best-effort и
регистрируется отдельно; исчезнувший из сети контакт не получает отложенный
запрос спустя дни. APP_RT не расширен новыми типами.

Диагностические метки задаёт тип протокола: отдельно звонок, P2P bootstrap и
каталог моделей. Для каждого есть sent/failed/received и собственная категория
ошибки. Значения enum добавлены в конец. Приём учитывается после определения
допустимого типа в соответствующем входе, до consent/dedup: это прибытия кадров,
а не число звонков, авторизованных действий или логических сообщений.
Успешная отправка означает возврат транспорта, а не получение ACK; несколько
живых путей дают несколько попыток. Отсутствие необязательного realtime-реле
больше не выдаётся за неудавшуюся попытку. Для анонимной и обычной fallback-
сигнализации также учитывается фактически использованный путь.

В экспорт добавлены только исходные метки типов. Адреса, ключи, имена устройств,
пути, списки моделей, языки и тексты ошибок не добавлены. Опт-ин и прежние
границы памяти сохранены. На реле не появились приоритеты или признаки медиа;
Veil `4857bebc` и hidden-volume `1ea2366f` не менялись.

## Проверки

Один и тот же набор из **415 тестов в 12 файлах** прошёл с включённой и
выключенной диагностикой; эти числа пересекаются. В файле realtime-контроля
добавлены 16 тестов. Проверка моделей соединяет две службы обмена моделями
через два настоящих `MessagingService` и канал с отдельными обычным/realtime
входами. Контакт с тестовым каталогом ru → en возвращает предложение, которое
принимает запросившая служба, в обоих режимах анонимности. Несмотря на заданный
маршрут к другому устройству, назначения остаются адресами личностей. Файлы
каталога служат фикстурой инвентаризации; выполнение перевода этим не проверялось.

Проверены разделение успехов и ошибок P2P, исключение содержимого из отчёта,
отсутствие ложной сигнализации от неподдерживаемых realtime-кадров, сохранение
ошибок/результатов call health для обычного, realtime и анонимного транспорта,
а также отсутствие сохранённых кадров каталога при сбое.

Анализ пяти изменённых Dart-файлов не нашёл замечаний. Существующая проверка
сериализации контроллера и терминальных причин выполнена в product AOT с
настоящим флагом диагностики; приватные поля не вышли, стендовая история
контроллера выключена.

## Физический стенд

A — Android на Wi-Fi, B — его sibling той же личности, C — другая личность.
B и C — два изолированных клиента на одном Mac. Android — AOT/profile, Mac —
debug; нативные test hooks и пониженная сложность выключены. Проверены инвентари
исходников и артефакты; приложения работают с обычными production-библиотеками.

На первой сборке с разделением метрик и обычным каналом моделей выполнены два
видеозвонка C → A/B по 180 с: сначала ответ на A, затем на B. Оба устройства
звонили, неответивший sibling переставал звонить. После ответа активность
наблюдалась через 3345/1216 мс. Последние активные выборки — 179,066/179,079 с;
неожиданных терминальных событий перед командой стенда не было. Под нагрузкой
отправлены 54 сообщения: все сошлись без логических дублей, истории содержат
по 1829 записей с равным порядком. Нативные счётчики звука и показанных кадров
на активных концах выросли. Это не оценка громкости или разборчивости речи.

Затем исправлена обнаруженная адресация на устройство и пересобраны все три
клиента. На этой окончательной сборке запрос C дошёл до **A и B**, а счётчики
сигналов звонка до начала вызова остались нулевыми при работающем P2P-обмене.
Метод вызван через штатный локальный Dart VM service; временного API в продукт
не добавлено. Контрольный минутный звонок C → A также прошёл: последняя активная
выборка — 59.613 с, sibling B перестал звонить, история
из 1829 записей с телами и порядком сохранила равенство на A/B/C.

Терминальные записи отличают завершение командой diagnostic API, полученный
remoteSignal и siblingSelection. Временные окна отделены до/после команды
стенда; последующая очистка не приписывается прежнему завершению.

Установка QA сохранила профили, режимы анонимности восстановлены. Один финальный
прогон остановился из-за отсутствующего в журнале адреса Android VM; его
материалы сохранены отдельно, стенд закрыт, сборщик наблюдений исправлен.
В итоговом прогоне счётчики доступны у всех трёх ролей.
После всех прогонов приложения закрыты. Независимый аудит **211** записанных
групп процессов, Android-пакета и ADB/VM-пробросов не обнаружил остатков стенда.

Причина старого завершения через 25,1 с остаётся неизвестной: отсутствие повтора
в этих звонках не доказывает её устранение. Громкость в наушниках, разборчивость
живой речи, Windows 10, мобильный провайдер и вся матрица multi-device этим
прогоном не квалифицированы. Для полного обмена каталогом обе стороны должны
иметь исправленную отправку: старая версия может по-прежнему отправлять свой
запрос/ответ в неподходящий APP_RT.
