# Потеря padding-пробы не равна потере изображения

2026-11-03. Локальный цикл, без push/релиза и изменения engine pins.

## Подтверждённый дефект

После предыдущего timing-фикса лимит видео снижался по persistent-loss.
Сопоставлены RTP отправителя, ingress/доставка в WebRTC получателя и настоящие
RTCP-отчёты. В двух контрольных захватах все принятые источником, но не
полученные пакеты **в середине активной видеофазы** оказались padding-only.
Пакеты с изображением там дошли; некоторые позже отчёта о потере. Startup и
хвост teardown исключены из этого вывода. Это не доказательство декодирования
каждого кадра или его показа на экране.

Усиленный захват сопоставил пропавшие padding-пробы с `budget_admit` и
`datagram_accepted` источника, но не с приёмом первого реле. Локальный приём
Quinn не доказывает отправку на NIC или доставку. Где именно они потерялись,
не установлено; нулевые drops шейпера не доказывают отсутствие иных потерь.

Общий RR-счётчик не различает изображение и padding с тем же SSRC. Тест
настоящего production shim воспроизвёл лишний application loss-event даже при
TWCC, который точно описывал единственную потерю padding. Красный контроль
повторён с **включёнными независимыми transport-feedback пространствами** на
неизменённом прежнем shim в изолированной копии. Первая попытка без включения
этой возможности не используется как доказательство дефекта точного пути.

## Изменение

- Ограниченная история метаданных связывает transport sequence с RTP timestamp/sequence
  и наличием payload. Нет содержимого картинки, нового wire-формата, C ABI или
  новых полей пользовательского экспорта. Не более 4096 записей истории.
- Для application quality ladder используется свежий TWCC с явным target SSRC
  нашего видео. Независимые audio/video sequence spaces не смешиваются.
- Padding остаётся частью исходной обратной связи GCC. Для снижения
  application-лимита требуется незакрытая **payload**-дыра, выдержавшая три
  секунды и подтверждённая новым продвижением отчёта. Поздний оригинал или
  успешный retransmission того же RTP снимает дыру; replay не обновляет время.
- Если запись неизвестна, истекла или превышен лимит, точная классификация
  отключается до следующего явного source/route epoch. Короткий последующий
  здоровый отчёт не прячет неизвестную старую потерю. Устаревший/отсутствующий
  TWCC использует прежний RR-контроль. Raw RR/NACK/GCC не переписываются.
- В группе история отправителя общая, состояние потерь отдельное для каждого
  authenticated peer. Оно не переносится между участниками или через смену
  source/route epoch.

## Проверки

Production shim с настоящими WebRTC builders/parsers прошёл девять вариантов:
padding-only; реальный payload gap; late fill; чужой SSRC; неизвестная запись;
повреждённый compound; ненеготированный TWCC; legacy RR; успешный RTP repair.
Raw loss остаётся ненулевым при подавлении ложного application-события.
Standalone model проверяет replay, wrap, переполнение кольца, expiry, изоляцию
участников, новые epoch и обратный ход часов. Добавлен в стандартный call-plane
runner. Legacy persistence, настоящие native direct/group RTCP controls прошли.

Test-hook и обычная macOS dylib собраны отдельно. Проверены source manifest,
хеши реальной загруженной библиотеки и transport; обычная dylib не экспортирует
test hooks. Пять Python-проверок анализатора прошли: он теперь читает и проверяет
полноту Sender Report records, ранее отвергавшихся как неизвестные.

## Нативный прогон

Один Mac, два настоящих Opus/VP8 endpoint и локальное зашифрованное QUIC-реле.
Слепое удержание UDP на 250 мс каждую секунду; 70 секунд, видео с 20-й секунды.
Синтетическая камера 320×240. Только periodical-tone oracle явно выключает
AEC/NS, потому что одинаковые синхронные тоны конфликтуют с AEC; это не режим
продукта. Проверка обычного production DSP остаётся отдельной.

| Метрика | Сторона 0 | Сторона 1 |
| --- | ---: | ---: |
| Новые persistent image-loss события | 0 | 0 |
| Raw nonzero loss-report witnesses | 6 | 4 |
| Первый разрешённый лимит 60 FPS после включения видео | 18 с | 15 с |
| Финальный разрешённый лимит | 60 FPS | 60 FPS |
| Средний decoded counter, включая разгон | 20,37 FPS | 20,92 FPS |
| Принятые tone edges / ожидаемые | 50/50 | 50/50 |
| Quiet PCM blocks в видеофазе | 0/4999 | 0/4999 |

В середине этого прогона не получены четыре source-accepted padding-пакета;
source-accepted пакеты с изображением дошли до WebRTC. Конечные sampled pixels
менялись на обеих сторонах. Raw loss не исчез, ложный persistent image-loss не
повторился. Это не native A/B/A и не оценка ускорения против прежней серии.
Лимит 60 FPS не равен фактическому FPS камеры, декодера или экрана.

**Общий прежний гейт остаётся красным:** tone latency в видеофазе доходила до
324 мс, а в начале прогона зарегистрировано по одному 210-мс interruption
(счётчик в видеофазе далее не рос). Порог 200 мс и гейт не изменены.

Все started producers/SDK nodes/policy остановлены, sockets/processes
проверены, временные контейнеры удалены после сохранения обезличенной сводки и
приватных свидетельств. Пользовательские телефоны, профили, Windows и публичные
реле не тронуты. Полный физический звук/видео Poco ↔ Windows, mobile handover,
холодный QUIC, большая история и полная multi-device матрица остаются отдельными
задачами. Новых engine pins и публикации не было.
