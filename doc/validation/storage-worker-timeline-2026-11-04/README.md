# Ожидание storage worker при догрузке — 2026-11-04

## Зачем измерение

Предыдущий sparse crash/reconnect восстановил 2000 сообщений за 41,020 с после
готовности A. Остались длительные inclusive waits свежих own-device lookup и
history apply. Await RPC включает ожидание очереди, обработку worker и возврат
в main isolate; его нельзя целиком объявлять диском или native CPU.

В production worker запросы выполняются синхронно, по одной очереди. Добавлены
**только test-fixture инструменты**: фиксированная метка TimelineTask вокруг
реального RPC и штатные VM HandleMessage spans реального `_workerEntry`.
Worker, протокол RPC, storage, ratchet, ACK и проверки устройств не заменяются.
В lib/ нет новых вставок или альтернативного applier.

## Контракт измерения

Трассировка включается только явным stand env с меткой одного устройства,
по умолчанию выключена. Capture сохраняет только RPC begin/end и обработку
выбранного worker. Посторонние VM-события и поля не записываются. Исходные
параметры VM восстанавливаются при закрытии, в том числе при ошибках.
Файлы остаются приватными стендовыми артефактами и не входят в пользовательский
анонимный экспорт. Raw VM IDs/thread IDs используются лишь для локального
сопоставления; агрегатор возвращает только фиксированные категории и числа.

Действуют потолки 200 000 событий / 96 МиБ на capture. Достижение лимита,
пропуск внутри трассы, неизвестная категория, пустой результат, несколько
storage workers или несоответствие количества RPC/handlers запрещают атрибуцию.
Незаписанные крайние spans можно только исключить из закрытого окна; его
покрытие указывается отдельно. Enqueue sequence проверяется без таймингового
порога. Пустые batch-запросы, не посылающие сообщение worker, не размечаются.

Смысл полей:

- `beforeHandlerUs`: до начала callback worker — подготовка/копирование RPC,
  очередь, доставка между isolates и планирование. Это **не чистая очередь**.
- `handlerUs`: синхронный callback, включая Dart adapter, FFI и работу native.
  Это **не чистое fsync/I/O/CPU-время**.
- `signedReplyTailUs`: finish RPC минус конец callback. Может быть отрицательным:
  worker посылает ответ до выхода из HandleMessage, и main уже может его получить.

Нативный live-контроль: 40 RPC (4 commit, 32 get, 4 grouped read) сопоставлены
с 40 обработками. Дополнительно пустые getBatch/readLogBatch/readLogGroups
не создают фиктивные worker spans. Все байты реального контейнера проверяются.
Существующий CPU-profile control также прошёл отдельно с VM service.

## Проверка самой диагностики

У measurement-кода обнаружены и устранены свои ошибки; они не считаются
дефектами приложения:

1. Нестабильная сортировка одинаковых VM timestamps создавала ложные вложенные
   spans. Санитизированный fixture реального 36-RPC контроля был красным до
   исправления, теперь сохраняется исходный порядок событий одного thread.
2. RPC с одинаковым временем начала ранжировались по порядку завершения.
   Красный тест с обратным finish-order закрепил enqueue sequence как tie-break.
3. VM публикует длительность после завершения операции. Продвижение origin
   каждого запроса теряло поздно опубликованный begin из предыдущего интервала.
   Capture повторно читает от первоначального origin и дедуплицирует выбранные
   события. Отдельные красные тесты воспроизводили позднюю публикацию и отказ
   прежнего агрегатора обнаружить пропуск в середине; оба исправлены.

Первый большой stand прошёл точную сходимость/retention и sparse-контроль,
но исходный capture имел пропуски VM-событий на границах. Ранние числа из его
непрерывного хвоста **не приняты как итоговая атрибуция**: усиленный анализатор
отвергает этот файл. Teardown: 31 PID, 40 портов, runtime удалён, 1412 inputs
и native SHA во время того прогона не менялись. Повтор потребовался после
исправления collector; прежняя успешная сходимость не подменяет его результат.

## Повтор на исправленном collector

Второй capture уточнил ещё один источник потери событий: родительский сценарий
около 15 с перезапускал A и не запрашивал B; VM ring перезаписал часть событий.
Его приложение также сохранило точные 2000 строк и прошло sparse/retention,
но строгий анализ **отверг** файл времени. Teardown: 33 PID / 40 портов,
1412 inputs и native SHA неизменны во время прогона. В collector добавлен
независимый опрос каждую секунду: незавершённые captures объединяются, timer
отменяется при close, ошибки опроса делают атрибуцию недопустимой. Lifecycle
таймера, budgets и удаление посторонних VM-полей проверены тестами.

Третий прогон прошёл и сценарий приложения, и строгую атрибуцию времени:

- SIGKILL B при 1797 строках; после локального восстановления — 1798,
  включая 100 поздних provisional rows за дырой.
- A/C offline при перезапуске B; возвращается только A. Prefix fallback
  реально выполнен. Все 2000 ID, порядок, source positions и delivered
  сошлись и сохранились после нового запуска B без A/C.
- Completed-history retries — 0, invalid snapshots не наблюдались.
- После готовности A — 31,299 с. Объём восстановления и диагностическая
  нагрузка отличаются от прежних прогонов; это время не используется для
  вывода об ускорении. Production lib/ и зависимости в этом цикле не менялись.
- Teardown: 29 PID / 37 портов, owned процессов/listeners нет, runtime удалён.
  1412 frozen inputs и native SHA не менялись во время прогона.

Из 43,130 с capture получено закрытое окно **42,996 с** с **10 912 RPC и
10 912 обработками worker**. На краях исключены по 74 завершённых spans
каждого набора; capture содержит 10 986 завершённых RPC и столько же handlers. Пропусков в середине нет,
последовательность enqueue непрерывная, budgets/poll-error flags не сработали.
Сохранено около 5,3 МБ выбранных метаданных; VM-события вне нужного набора
не попадают в файл. Окно включает обращения B при offline источниках и
восстановлении; это не отдельный замер только `historyApply`.

|---|---:|---:|---:|---:|---:|
| grouped log read | 1202 | 5,609 | 0,080 | 5,300 | 0,229 |
| commit | 429 | 7,656 | 0,367 | 7,055 | 0,234 |

У групповых чтений и commit основная наблюдаемая стоимость находится внутри
callback worker; перестановка очереди не убирает эту работу. У одиночных
metadata get обработка быстрая, значительны подготовка/очередь/планирование
и возврат результата. Один signed tail отрицателен; он не обнулён и не выдан
за сетевую задержку. Суммы await могут перекрываться и не складываются с
context timings или wall-clock как независимые физические расходы.
В частности, таблица **не отделяет fsync от native crypto/decompress/adapter**.

98 профильных тестов прошли; отдельно прошли native 40/40 и прежний CPU-profile
live control. Analyzer десяти файлов чистый, граф обновлён AST-only. Новый
oracle не принимает пустые результаты, разрыв последовательности, несоответствие
RPC/handler, неизвестную метку операции, потерю события в середине или cap/error.

Следующее направление — уменьшать повторную материализацию свежего device
journal и число необходимых durable операций, сохраняя проверки отзыва,
изоляцию личности и ACK-барьеры. Долгая догрузка остаётся открытой; этот цикл
даёт измерительную основу для исправления, без изменения поведения приложения.

Локальная уборка: 11 неиспользуемых/отвергнутых raw captures сжаты с проверкой
обратной распаковки и SHA (70,3 → 3,0 МБ). Зачтённый raw capture сохранён;
ранние aggregate artifacts явно помечены `qualified: false` и заменены ссылкой
на итоговый результат, прежние предварительные числа оставлены только для аудита.

## Границы

Mac/JIT — это квалификация данного стенда, не Android/AOT или всей multi-device
матрицы. Диагностический режим добавляет VM events/loopback capture, поэтому
его wall-clock не является парным performance-контролем обычной сборки.
Mailbox для собственных устройств не подключается. Push, релиз, engine pins,
APK и production-реле не менялись.
