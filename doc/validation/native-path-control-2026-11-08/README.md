# NETCALL-01: контроль TCP/UDP без Veil

**Подтверждено:** секундные задержки воспроизводятся на том же Poco и двух
серверных адресах без вызовов SDK Veil. Это локализует самостоятельный
сетевой/системный механизм; не доказывает причину всех исторических случаев
NETCALL-01 и не закрывает сам случай.

Product-код не менялся. На телефоне запускался отдельный native C executable
под UID shell; его ELF и SHA проверены, зависимости — только системные
libraries. Он не читает контейнеры, не захватывает звук и не реализует Veil.
APK не переустанавливались. На серверах — две временные Python echo-службы,
отдельные от production Veil, с ограничением времени/памяти/CPU/connections
и случайным тестовым token. В payload только синтетические данные.

## Проверка самого инструмента

Клиент/сервер проверены на loopback TCP и UDP. Контроль с искусственной
1100-мс задержкой обнаружил её при нормальной cadence отправителя;
контроль с потерей ровно одного UDP ответа показал ровно один пропуск
на каждом канале. В обоих обычных loopback-контролях все frames вернулись.
Mac-контроль к обоим удалённым echo-серверам перед серией дал 40/40
ответов по TCP и 40/40 по UDP на каждом адресе.

Каждый frame — 512 байт; новые frames создаются каждые 50 мс для каждого
из двух серверов. Сохраняются реальная cadence, время принятия локальным
socket, RTT отражённого frame и интервалы приёма. Полученное содержимое
сверяется полностью; frames не считаются успешно полученными только
по факту успешного send. RTT измеряется на одном клиенте, без вычитания
удалённых clocks. Server request sets отдельно сопоставляются с client send
sets, а не только с одинаковыми итоговыми counts.

## Серия

Порядок зафиксирован заранее: Wi-Fi TCP 45 с → Cellular TCP 60 с →
Cellular UDP 60 с → Cellular TCP 60 с → Wi-Fi TCP 45 с. Перед каждой фазой
проверены target network/VALIDATED. **Каждая фаза открывает новые sockets**:
это контроль стабильного пути после смены сети, не сохранения TCP-сессии
во время handover. На каждом сервере отдельный канал; ниже числа R1 / R2.

| Фаза | Sent / echoes на каждом сервере | Median RTT R1 / R2 | Max RTT R1 / R2 | Max receive gap R1 / R2 |
|---|---|---:|---:|---:|
| Wi-Fi, TCP-1 | 900 / 900; 900 / 900 | 110 / 54 мс | 115 / 63 мс | 58 / 59 мс |
| Cellular, TCP-1 | 1200 / 1200; 1200 / 1200 | 173 / 104 мс | 1515 / 1394 мс | 1220 / 1229 мс |
| Cellular, UDP | 1200 / 1; 1200 / 2 | — | — | — |
| Cellular, TCP-2 | 1200 / 1200; 1200 / 1200 | 158 / 108 мс | 1250 / 3932 мс | 638 / 2931 мс |
| Wi-Fi, TCP-2 | 900 / 900; 900 / 900 | 116 / 56 мс | 282 / 151 мс | 216 / 103 мс |

RTT и receive gap — разные метрики. Например, 3932 мс — round trip
одного frame, 2931 мс — максимальный промежуток между ответами во время
отправки. Это не измерение one-way audio latency или слышимости.

Во всех фазах max producer gap **52,3–62,3 мс**, max lateness ≤12,6 мс;
нет skipped work, bad frames или I/O errors. Max local write wait ≤9,2 мс
(в TCP ≤5 мс). Поэтому секундные RTT/gaps нельзя объяснить такой же
секундной остановкой генератора в его используемом clock domain.

Все **8400 TCP frames** всей серии вернулись, включая все 4800 мобильных.
Из мобильных TCP echoes **368/4800** имеют RTT >1 с. Это наблюдаемая доля
в данной серии, не оценка всех будущих звонков или доступности сети.
Медиана значительно ниже хвоста: постоянного RTT в несколько секунд нет.

## UDP

Из 1200 отправленных UDP frames на каждом адресе клиент получил **1/2**
ответа. Echo-службы зарегистрировали только **4/3 валидных запроса**,
все в начале фазы. Основное расхождение возникает уже до регистрации
запроса службой; клиент получил echoes меньше, чем служба зарегистрировала
запросов. Из этого ещё не следует, где были потеряны или не отправлены ответы.
Отсутствие NIC capture в этом контроле не позволяет назвать точку потери
или отличить все причины непринятого запроса.

RTT единичных вернувшихся UDP frames не представлен как "быстрый UDP":
выборка несопоставима при почти полном отсутствии ответов. Интервал между
ответами при единственном sample — unknown, не 0 мс. Post-processing v2
сохраняет этот unknown и использует nearest-rank percentile; исходный
клиент и raw output не менялись между фазами.

Это **сырой UDP control на этих адресах/443**, не проверка QUIC, STUN,
P2P или любого другого UDP-протокола. Из него не следует, что весь UDP
заблокирован или что простая замена transport гарантированно поможет.
Один и тот же echo-server успешно прошёл UDP smoke с Mac, но это другой
сетевой путь. Политики ОС/UID, NAT, фильтрация и промежуточная сеть ещё
не разделены; виновность конкретного оператора не установлена.

## Состояние устройства и границы вывода

28 environment snapshots: Awake, питание подключено, Doze/Light Doze ACTIVE;
target network VALIDATED во всех срезах. Исходное состояние также Awake.
Это не многочасовой screen-off/OEM test. Native executable работает под
shell UID, поэтому отрицательный контроль не исключал бы проблемы SDK,
протокольной классификации или политики другого UID. Здесь контроль
**положительно воспроизвёл** секундные задержки без SDK.

Клиент использует CLOCK_MONOTONIC. На Android он не является самостоятельным
доказательством отсутствия deep suspend; показания power/snapshots и фактические
cadence приведены отдельно. Перед TLS/обходными изменениями нужно учитывать
эти границы, а не объявлять любой сетевой симптом внешним по одному тесту.

Последовательная Wi-Fi/Cellular серия не фиксирует один и тот же маршрут
или radio state. Она не является причинным A/B изменения кода. Raw TCP
и UDP здесь не имеют framing/encryption Veil, возможна protocol-specific
обработка. Тем не менее Veil не обязателен для воспроизведения данного
класса длинных задержек на выбранном пути.

## Дальше и уборка

**NETCALL-01 остаётся открытым.** Новое изменение быстрых SDK queues
ради этого результата не внесено. Следующий проверяемый вариант — такой
же небольшой поток через TLS, чтобы исследовать protocol-specific обход;
успех контроля сам по себе ещё не квалифицирует transport для xVeil.

Все пять фаз и десять client lane summaries проверены. Server sessions
сопоставлены по протоколу, порядку валидных sessions и sets sequence, а не
по последовательным connection IDs; клиент сверяет body целиком.
До phone campaign выполнено одно плановое обновление lease
своих echo-services; прежние smoke logs сохранены. Это не auto-restart
production или повтор при неизвестном состоянии процесса.

Все own native processes завершились. Directory/binary/token с телефона
удалены с проверкой owner marker. Исходные Wi-Fi/data/stay-on и validated
сеть восстановлены; APK обоих приложений и исходный QA root container
сверены по SHA. Containers не открывались. Echo units и root credentials
удалены, порты освобождены. Production PID/restarts/binary/config обоих
серверов сверены независимо после очистки. Frozen harness/source/binary
hashes совпали; raw synthetic records и operational metadata остаются private.
Никакого test-кода в production app/SDK не добавлено. Push/релиза нет.
