# Границы операций с личностями — 2026-11-11

Продолжение отложенной проверки `addIdentity` после аудитов R33–R35.
Подтверждены продолжение I/O после lock, автоматическое восстановление старой
сессии, ложный успех после отмены и отсутствие ожидания принятого создания
перед wipe. Ошибка первоначального экспорта ключей также могла запускать
ненужные teardown/recovery вместо сохранения здоровой текущей сессии.

## Исправление

Общий admission покрывает восемь изменений: add, bind, unbind, delete, decoy,
анонимность в master и две настройки одиночной личности (анонимность/lazy mining).
Он приобретается до первого await и остаётся занят до очистки всех принятых
операций. Новые sign-in/onboarding/reopen/compaction не заменяют используемый
этим владельцем storage; другой edit возвращает обычный отказ без I/O.

Каждый основной асинхронный шаг проверяет исходный lifecycle до вызова и после
ответа; освобождение собственных ресурсов выполняется и после отмены. Вернувшиеся ключи/ростеры регистрируются для очистки **до** проверки
отмены. Для заимствованных live master/roster ключей используются собственные
копии: lock может очистить кэш, пока worker ещё работает с принятыми данными.
Невзятые в новый живой кэш буферы обнуляются в finally. Это best-effort очистка
наших буферов в Dart heap, не гарантия уничтожения копий moving GC или строк
паролей; принятая модель RAM-hardening не менялась.

Lock/startOver/wipe не дают старому edit вызвать новый open/save или заново
войти в сессию. Принятый до отмены Storage/worker вызов может закончиться; его handle
закрывается, новые sign-in исключены до quiescence. Wipe присоединяется к этому
барьеру до удаления контейнера. Уже сохранённый префикс операции не откатывается:
это не транзакция сразу над всеми пространствами. Завершившееся до lock сохранение
ростера может быть видно при следующем настоящем unlock.

Выбор другой личности во время edit отменяет старую операцию и ждёт её cleanup.
Последний допустимый запрос выбора выигрывает; запрос не теряется как «busy».
Неизвестное имя не вытесняет уже ожидающий корректный выбор. Выбор исходной
личности во время начального export также проходит через закрытие/новый вход,
чтобы сессия соответствовала новому lifecycle. Существующая
all-online activation ordering сохранена. Общая квалификация параллельных прямых
`pickIdentity` вне редактирования остаётся отдельным пробелом.

Recovery использует исходного владельца и его lifecycle. При переходе к locked
сбрасываются master keys/roster и инвалидируются leases. Отказ финального открытия
новой личности возвращает false. Ошибка первоначального экспорта до teardown
оставляет исходную сессию открытой. Ошибки закрытия при отмене имеют отдельную
фиксированную категорию `identity-edit-close`, без параметров пользователя.

Источник ростера по-прежнему — master на диске. Сравнение паролей не расширено
до перечисления скрытых пространств; доступ к неизвестным пространствам не
добавлен. No sibling mailbox и другие сетевые политики не менялись.

## Доказательства

- На прежнем `b10d1549` все **11 первоначальных add-сценариев** дали assertion
  failure: девять точек lock, отсутствие барьера создания, лишнее восстановление
  после export failure. Это не ошибки компиляции или предусловий.
- Дополнительный immutable-baseline контроль соседних мутаций: **9 failures /
  1 passed** из десяти. Bind на раннем чтении ростера уже безопасно отказывал;
  этот проход не объявлен новым дефектом. Поздний bind и остальные операции
  продолжали работу после lock или возвращали успех. Исходный candidate восстановлен
  в finally со сверкой SHA. Первоначальный verifier ошибочно ждал десять failures;
  исправлен учёт, код не менялся ради количества красных проверок.
- Текущая управляемая матрица: **38 passed / 0 skipped**. Помимо lock/startOver,
  охвачены dispose, pending admission, два конкурирующих выбора, ложный успех
  финальной активации и teardown failure. Гейты наблюдают реальные этапы Storage,
  а барьер проверяется по зависимости Future, без порога длительности.
- Связанная серия controller/master-unlock/lifecycle/compaction/reopen/onboarding:
  **205 passed, 2 skipped**. Два пропуска требуют qualified hidden-volume.
  Их файл затем отдельно исполнен с проверенной библиотекой: **4 passed /
  0 skipped**, включая обе ранее пропущенные native rewrite проверки. Эти
  пересекающиеся числа не суммируются.
- **3 native controller/worker сценария passed / 0 skipped** на настоящем
  hidden-volume: отмена после чтения ростера обнуляет возвращённые копии, но
  оставляет сохранённые ключи/профили/70000 байт данных пригодными; принятый create
  заканчивается до wipe, файл отсутствует; добавление в существующий master без
  предыдущего unlock сохраняет все записи и отдельную не включённую в roster
  личность. Бинарник сверялся по SHA перед запуском. Native node boot запрещён
  fixture; это проверка контейнера/controller, не сетевой стенд.
- Отдельный assertion-red на промежуточном candidate обнаружил сохранение
  старого master/roster cache после dispose. Исправлена очистка и при отмене
  до первого teardown; два dispose сценария проверяют старые буферы напрямую.
- Два дополнительных assertion-red на промежуточном candidate проверили
  неизвестное имя после допустимого выбора и выбор текущей личности во время
  начального export. Исправлены порядок проверки выбора и обязательный re-entry
  после отмены; существующие all-online ordering проверки проходят.
- Analyzer трёх изменённых/новых Dart-файлов чист.

Первый native wipe fixture не задавал свой каталог необязательной speech-модели;
он получил `speech-model-unknown` от недоступного platform path provider.
Исправлена изоляция теста: model store теперь указывает на его временную папку,
translation root отключён. Это не дефект приложения и не результат проверки
пользовательских моделей. Все временные контейнеры создавались отдельно и удалены.

Opt-in native запуск:

```bash
TMPDIR=/private/tmp/ XVEIL_NATIVE_IDENTITY_EDIT=1 \
XVEIL_HV_DYLIB=/absolute/path/libhidden_volume_ffi.dylib \
flutter test --no-pub test/native/add_identity_lifecycle_test.dart
```

Без флага три native-only сценария явно пропускаются и не считаются пройденными.
Телефоны, пользовательские контейнеры и реле не использовались. Нет GUI/Android,
power-loss или полного перебора всех отказов I/O. Медиапины и итоговая упаковка
приложения остаются отдельными задачами перед релизом. Push/релиза нет.
