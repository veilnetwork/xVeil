# Очередь поиска маршрутов после перезапуска

2026-11-01, SDK `4f9c85f2`. Исправлены три механизма ожидания. На прежней
шестисерверной линии три входящих появились за 1,37–1,45 с **после наличия
реальных клиентских сессий с seed**. В одном запуске сама сессия Mac → S1
восстанавливалась 58,69 с. Все причины холодной задержки не закрыты.

Продолжение [предыдущего цикла](../cold-chain-delivery-2026-11-01/README.md).
Линия и профили прежние: `Mac — S1 — S2 — S3 — S4 — S5 — S6 — Blackview`.
Blackview на Wi-Fi; Windows и мобильный handover здесь не проверялись.

## Подтверждённые дефекты

| Механизм | Воспроизведение | Правка |
|---|---|---|
| Один неответивший адресат держит всю очередь route miss до конца flood/DHT ожидания | Первый lookup удерживается gate; второй не начинает discovery на прежнем коде | До четырёх одновременно живых lookup, прежний bounded input channel; один адресат не имеет двух активных поисков даже после истечения короткого dedup TTL |
| RouteResponse уже пришёл, но waiter ещё не зарегистрирован | Кэш заполнен до первого poll; notify_waiters не хранит permit; прежний код возвращает Pending вместо Ready(true) | Waiter включается перед чтением кэша, готовый маршрут используется сразу |
| Уведомления о чужих маршрутах расходуют backoff-попытки нужного | Без движения часов три чужих уведомления завершают ожидание отказом | Чужой wake только перепроверяет кэш; исходные накопленные deadlines сохраняются, поздний poll и поток уведомлений не продлевают бюджет |

Первый набор на прежнем коде: **4 passed / 2 failed**. После исправления wait
добавлен независимый HOL-тест: **0 passed / 1 failed** до scheduler-правки.
Это реальные assertion failures, не ошибка компиляции и не нулевой фильтр.
HOL проверен на виртуальных часах при закрытом gate первого lookup; это не
порог сетевой производительности.

Регрессии дополнительно фиксируют cap 4, продвижение очереди после освобождения
одного слота, dedup незавершённого поиска после TTL, отмену/join дочерних задач
при shutdown и прекращении обработчика. `JoinSet` принадлежит обработчику;
отмена родителя не оставляет независимые фоновые поиски. Сигнатуры, PoW,
reputation, DHT quotas, число реплик и route-request hop budget не ослаблялись.
Настройки временных окон прежние. Параллельность может увеличить короткий
burst до четырёх поисков — это ограниченный предел, не снятие admission gates.

## Что подтверждает прежняя трасса

Из собственного node.log отдельно извлечено окно прежнего 51-секундного
вызова. На S6 видны шесть запусков fallback к личности Mac и четыре — к
устройству; первый зарегистрированный device fallback начинается на +13,681 с.
Одно ожидание fallback в этом окне занимало около пяти секунд. Это подтверждает
наличие неудачных поисков и последовательных окон, но не даёт общего call/IPC
correlation ID и **не приписывает все 51 с исправленным механизмам**.

## Физическая проверка

На всех шести **изолированных** службах и обоих клиентах одна SDK.
Core-конфиги, идентичности, listener allowlists, per-service IP ACL и ресурсы
прежние. Отдельные production-службы не перезапускались и не обновлялись.
Frontend/AOT, медиадвижок и hidden-volume заморожены; менялась native SDK.

Вызовы телефон → Mac, P2P denied, после полного перезапуска клиентов:

| Попытка | До входящего от начала call-скрипта | Независимая проверка RX после первых пяти свежих samples |
|---|---:|---|
| 1 | 1,366 с | На Mac три stale samples, максимум native age **3443 мс**; непрерывный fresh-RX контроль не пройден |
| 2 | 1,446 с | Оба active/relay, 14 samples на конец, максимум age 333 / 32 мс |
| 3, после восстановления seed-сессии | 1,420 с | Оба active/relay, 16 samples на конец, максимум age 307 / 49 мс |

Для двух последних наблюдение продолжалось более 20 секунд после квалификации;
все сохранённые samples этого участка имели age ≤1000 мс. Это контроль пакетов,
не слышимость речи и не гарантия отсутствия пауз между срезами.

**Третий первоначальный гейт подключения провалился:** сессии Mac → S1 не
было за окно 45 с. Сам вызов тогда не запускался и не засчитан. Автоматические
повторы дали несколько 10-секундных handshake timeout; `session.open` появился
на +58,690 с от arming узла. Затем реальные подключения снова проверены и
только после этого запущен вызов №3. Transport self ID Mac не менялся.
Этот результат нельзя прятать за быстрым offer: восстановление подключения
остаётся отдельным подтверждённым ожиданием. Причина не установлена и
регрессия не исключена; нужен контроль dial/accept/OVL1 на обоих концах.

Самый ранний снимок в попытке №1 также был пустым на Mac: oracle остановил
серию до звонка. Следующий запуск продолжил тот же boot после настоящего
подключения. Поэтому №1 не является замером времени от открытия приложения.

В каждом вызове снят полный core graph: 10 направленных связей, нужные
клиентские привязки, отсутствие чужих core-соседей, ожидаемые SHA загруженных
бинарников/конфигов, исходные production PID/бинарник/конфиг 6/6. Самостоятельные
native IPC snapshots обоих клиентов содержали только S1/S6. Это подтверждает
линию; отдельной per-cell media-трассы всех шести реле здесь нет.

После серии два сообщения на уже готовых сессиях дошли в противоположных
направлениях за 1,135 и 1,163 с: по одной копии с тем же message ID. Это
**тёплые** отправки, не A/B против прежнего холодного окна и не доказательство
причинного ускорения. [Агрегированные результаты](result.json).

## Исправление проверки стенда

Старый private call driver ставил `qualified=true`, если после первых пяти
fresh samples прошло 20 секунд, даже при последующем stale RX. Здесь это
обнаружено независимым разбором сырых samples: первый вызов по RX не зачтён.
[Проверяющий скрипт](verify_call_observation.py) игнорирует старый green flag,
требует тот же call ID/transport, непустые samples обоих концов, RX packets,
age и длительность. Выводит только агрегаты. Четыре regression controls
покрывают поздний stall, пустой endpoint/другой call, короткое наблюдение и
положительный случай. Будущий private driver сбрасывает интервал при stale RX.

## Проверки и завершение

- Интеграционно: **124 routing + 299 dispatcher + 785 runtime + 200 IPC passed**;
  отдельно 11 runtime и 5 IPC ignored. Clippy routing/tests с `-D warnings`
  чист; первоначальное замечание к сложному типу test harness устранено.
- Linux static x86-64, macOS и Android arm64 собраны с прежними testnet features,
  отдельными Cargo targets и mount-watchdog. SDK source SHA до/после сборок
  совпал с коммитом. На Mac проверены библиотека после codesign и реально
  загруженный путь, на Android — установленный native SHA и APK перед удалением.
- Установлен только собственный QA-пакет через `--no-incremental`; восстановлен
  собственный профиль, основной xVeil/контейнер не менялся. Сетевые настройки
  телефона не переключались. Собственные профили сохранены приватно.
- Mac/Android/logcat остановлены и проверены; QA-пакет, отсутствовавший до
  цикла, удалён после backup/SHA. Свой ADB forward снят. Все шесть тестовых
  служб остановлены, порты освобождены; production PID/бинарник/конфиг
  сохранены 6/6. Старый node-log capture сжат 71 → 1,8 МиБ приватно.
- Коммиты unsigned. Push и релиза нет.

Остаются активными восстановление подключения (новый boot 58,69 с), полное
объяснение cold latency и аудиоприём/слышимость в исходных пользовательских
условиях. Windows, Poco/mobile handover, миграция большой истории и биометрия
этим циклом не квалифицированы. Три исправленных механизма не объявляются
доказанным объяснением всей прежней пользовательской жалобы.
