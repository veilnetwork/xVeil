# История: одна свежая control-свёртка внутри routing-чтения

`addressableOwnDevices` загружает bundle и складывает управляющий журнал,
чтобы определить состав собственных устройств. Затем выбор объявления
ведущего устройства проходил через `_deviceSyncStateOfBundle` и
`_messagesOfBundle`, где тот же control-журнал складывался повторно.
Message-проекция меняет только набор кандидатов, а не control-журнал.

Теперь первая свёртка передаётся частными параметрами в announcement-проекцию
этого же bundle. Передача происходит в том же синхронном участке, до
существующих async-границ; новое ожидание не добавлено. Следующий вызов снова
читает durable journal и заново проверяет control. Завершённое состояние
не сохраняется в поле/кеше и не используется для другого bundle.

Остальные callers `_deviceSyncStateOfBundle` / `_messagesOfBundle` по-прежнему
сами складывают control. Внешняя проверка `_deviceAddressReadEpoch`, смены
устройства/group pointer и закрытия сессии остаётся: обогнавшая чтение revoke
или новое объявление заставляют его повториться. Проверки message signature,
fork/chain, ACL, retention, lifecycle, clock и проверка актуального source
перед durable publication/checkpoint не удалены. Native, wire и media pins
не менялись.

## Подтверждение повторной работы

Регрессия использует два последовательных routing-запроса к настоящему
`GroupService` и подсчитывает вызовы sovereign-верификатора для каждой
control-записи. На прежнем коде assertion ожидает 4, получает **6**; после
правки — **4**. Два чтения durable header сохранены; адрес ведущего устройства
и байты журнала совпадают. То есть устранена одна повторная свёртка на запрос,
а не свежая проверка следующего запроса. Загрузка bundle и исходная routing-
свёртка по-прежнему проверяют control.

**625 related tests passed, 0 skipped**, с включёнными native SDK/HVS gates:
весь `group_service_test`, own history, device sync, native snapshot expiry и
Flutter-free headless closure. Проверены revoke во время чтения, смена master
announcement, caller-owned NodeId, закрытие сессии, clock skew, retention,
повреждённые/escaped/duplicate JSON кандидаты, префиксы, forks и writer scope.
Первый запуск без native env дал 607 passed / 18 skipped; он не объявляется
полной native-квалификацией. Финальная серия выполнила все 625.

Полный analyzer чист. После сравнительных прогонов восстановленный candidate
отдельно проверен focused-регрессией и analyzer; diff checks чисты.

## Native A/B/A: 2000 архивных сообщений

A/B/E одной личности, C другой; четыре Mac/JIT процесса и три изолированных
Core на loopback. A/E содержат по 2000 одинаковых архивных сообщений, у B
одна прежняя строка. Оба полных authenticated ответа получены до release
первого apply. Равенство неполных историй не считается успехом.

A₁ и A₂ используют `group_service.dart` из родительского коммита, B —
candidate. Остальные **1523** frozen inputs и native библиотеки одинаковы.
Всего в каждой фазе проверены 1524 frontend/test/dependency inputs до/после;
между source-вариантами отличается только этот production-файл. Библиотеки
не выбирались по чистоте исходников: SHA проверены, FFI/HVS подтверждены
в OS mappings минимум трёх одновременно живых worker.

В отличие от предыдущей серии, **CPU sampling и VM timeline выключены во
всех фазах**. Census/wire oracle и 1000-мс опрос одинаковы. Сравнение с
прежними временами под VM trace не делается. Времена от gate release не
равны полному offline→reconnect времени: подготовка профилей и ожидание
тестового барьера находятся до этого интервала.

Все три сценария прошли. Проверены точные ID/тела/delivered/canonical positions/
порядок, завершение обоих source cursors, отсутствие дублей, пропусков и
посторонних строк. История сохранилась при cold boot с offline A/E/C.

**Полного ускорения догрузки эта серия не доказала.** Сокращение повторной
работы подтверждено счётчиком в регрессии; macro-время не улучшилось, а
контроль A₂ оказался быстрее B. Опрос и разброс scheduling не позволяют
приписывать разницу одному изменению. Дефект большой задержки остаётся
активным. Нового SIGKILL-момента этот цикл не проверял; предыдущая
[crash-квалификация 2000 строк](../history-contact-frontier-2026-11-09/README.md)
остаётся отдельным доказательством для прежнего кода, не объявляется новым
прохождением current candidate.

## Следующий измеренный участок

Во всех трёх окнах census: **2000 `markMessageStatus`, changed = 0**. Сумма
ожиданий 1,117 / 1,163 / 1,128 с пересекается с другими ожиданиями и не является
исключительным временем операции. Один источник — duplicate outgoing mirror:
после чтения уже delivered строки код всё равно вызывает durable status API.
Это направление следующей проверки; исправление здесь ещё не сделано.
Нельзя ради него убирать восстановление sent→delivered, pending ACK races,
ordering adoption или свежие admission-границы.
