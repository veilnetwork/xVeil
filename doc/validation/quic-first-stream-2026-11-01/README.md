# QUIC до первого OVL1-кадра

2026-11-01. SDK `c8bdfd97`, продолжение
[предыдущего захвата](../handshake-refresh-2026-11-01/README.md).
**Холодная задержка не устранена.** В этом цикле устранён пробел наблюдения
между приёмом QUIC Initial и стартом OVL1; таймауты и wire не менялись.

## Диагностика

Прежний `handshake.stage.begin` появляется после `accept_bi`: он не различал
ожидание TLS и первого application stream на сервере. Теперь общий RT trace
показывает dequeue, начало TLS, начало ожидания первого потока и итог, включая
ошибку, timeout и отмену. Снимки QUIC содержат локальные UDP/STREAM/ACK/PTO,
flight и driver counters. Счётчики не являются доказательством доставки.

У trace guard только **заимствование** connection: диагностический handle не
удерживает её после отмены. Gate выключен по умолчанию, включается существующим
`VEIL_RT_TRACE` или runtime toggle. В новых событиях нет адресов, wire CID,
публичных/приватных ключей, plaintext, роли приложения или текста ошибки пира.
Локальные accept/connection ordinal остаются в приватном захвате и исключены
из публичного результата.

Оба listener entrypoint используют прежние раздельные deadlines по 10 секунд
для TLS и первого stream. `Incoming` потребляется один раз до timeout над
`Connecting`; последовательность получения peer metadata сохранена. Scanner
shield, pre-spawn semaphore, аутентификация, PoW и P2P-политика не менялись.

## Что подтверждено

Шесть Mac boot на одном SDK с двумя изолированными тестовыми службами S1/S2.
Frontend/AOT, media, hidden-volume, профиль и конфиги заморожены; native SDK
обновлён с контролем SHA до/после подписи. Маркер новой диагностики проверен
в обоих выбранных бинарниках, Mac codesign проверен. Это **не A/B/A** и не
квалификация Android/Windows или полной линии из шести серверов.

| Boot | До двустороннего ACTIVE | ACTIVE с одним server link ≥3 с | После lock |
|---|---:|---|---|
| 1 | 38,864 с | Да | Удалённой строки нет при первом опросе |
| 2 | 12,499 с | Да | Удалённой строки нет при первом опросе |
| 3 | 39,534 с | Да | Удалённой строки нет при первом опросе |
| 4 | Не достигнуто за 80 с | Нет | Не засчитано как проверка закрытия успешной сессии |
| 5 | 1,533 с | Да | Удалённой строки нет при первом опросе |
| 6 | 1,681 с | Да | Строка оставалась в окне наблюдения 6,212 с |

Последний случай — наблюдение **удалённого состояния**, не доказательство, что
клиент продолжал работать после lock. Все шесть app-процессов затем завершены
и проверены. Причина сохранения строки не установлена; прежние успешные
stop-прогоны не дают гарантии для этого пути.

В S1-окнах есть шесть завершённых ожиданий первого stream с timeout и 13 ready.
Не все принадлежат клиенту Mac: S2 тоже активен. Для **трёх timeout** отправленный
S1 ciphertext sample однозначно совпал с полученным sample QA Mac в пределах
захвата. Так подтверждена принадлежность этих server connection тестовому
клиенту, без сопоставления по похожему времени или порядковому номеру:

- TLS ready через **63,615 / 63,746 / 83,676 мс** после dequeue;
- до timeout **10,065 / 10,065 / 10,084 с**;
- UDP RX connection оставался **3 → 3**, STREAM RX — **0**;
- PTO достигал **5–6**; локальная подготовка и запись HELLO у клиента сами по
  себе не доказывают, что соответствующий STREAM дошёл до сервера.

Это исключает долгий TLS как объяснение именно этих трёх ожиданий и сужает
участок до передачи после TLS/доставки первому stream. Другие TLS timeout тоже
наблюдались, их этим выводом не объясняем. Ciphertext fingerprint — корреляция
в пределах приватного захвата, не новая криптографическая аутентификация.

## NIC-захват и его пределы

На S1 дополнительно выполнен ограниченный 180 сек захват **только UDP-порта
изолированного стенда**, с независимым deadline. Он охватывает boot 5/6,
которые оказались быстрыми, поэтому **не атрибутирует** ранние timeout.
В pcap есть записи больше 1500 байт, в том числе UDP payload 2400 байт.
Без учёта offload/coalescing простое отсутствие одиночного UDP fingerprint
в таком pcap нельзя объявлять сетевой потерей.
Capture сообщил 780 записей и ноль kernel drops; это не доказательство
отсутствия потерь до NIC или в других стадиях. Raw pcap и журналы приватные.

Следующий целевой захват: воспроизвести медленную попытку **во время** NIC-
наблюдения, учитывать GRO/GSO и сопоставить client handoff, server NIC и UDP
socket. До него нельзя выбрать между потерей в сети/на хосте, offload и иной
ошибкой доставки. Отдельно нужно повторить сохранение server entry после lock.
Сокращение 10-с таймаута не вводилось как замена поиску причины.
