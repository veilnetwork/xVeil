# Обмен аватарами при подтверждении контакта — 2026-11-11

## Подтверждённый дефект

Предыдущий раунд восстановил запрос картинки в уже открытой карточке после
принятия контакта. Управляемый обмен между двумя MessagingService выявил
следующий самостоятельный случай:

1. A ожидает подтверждения своего запроса; B принимает A.
2. Видимая карточка B отправляет запрос аватара раньше, чем A получает accept.
3. A правильно отклоняет avatar request от ещё не принятого контакта.
4. Accept доставляется, оба контакта приняты. Карточка A запрашивает B и
   получает его картинку. У B картинка A остаётся пустой: ранний запрос уже
   израсходовал минутный лимит и сам не повторяется.

Воспроизводитель доставляет **все** кадры, без потерь и таймаутов. При обычном
FIFO обмен проходит на прежнем коде; при опережающем запросе не проходит
сравнение peer avatar в хранилище B. Это не вывод из пустой картинки: проверены
оба принятых статуса, точные непустые исходные картинки и содержимое обоих
кэшей. Оба Flutter widget element остаются прежними.

На прежнем коде итоговый тест даёт **один успешный контроль и один assertion-
отказ**. Между доставками обрабатываются события интерфейса; пустая transport
queue при ещё не обработанных UI callbacks не считается завершением обмена.

## Исправление

Когда A обрабатывает accept для ранее отправленного запроса, после сохранения
accepted он также отправляет B свой текущий аватар существующим live frame.
Это завершает обмен даже после отклонённого раннего вопроса. Обновление
направлено только этому контакту; снятие rate limit или общая рассылка не нужны.

Состояние контакта и его revision проверяются перед чтением картинки и снова
после чтения, перед допуском отправки. Блокировка/закрытие сервиса прекращает
ожидающее продолжение. Ошибка аватарного пути не отменяет принятие контакта;
сеть не ожидается внутри сериализованной входящей полосы.

Повторный accept уже принятого контакта не запускает этот переход. Поля и
wire kind не менялись, нового mailbox/Outbox обязательства, таймера или
подписки присутствия нет. Это одно best-effort обновление после перехода
pendingOutgoing → accepted, не гарантия доставки при произвольных потерях.

## Проверки

Управляемый стенд использует настоящие MessagingService, сериализацию
WireEnvelope, contact storage и два настоящих avatar widgets. Transport и
KV backing контролируемые; нижняя криптография/физическая сеть не моделируются.
Ответная картинка формируется вторым сервисом, а не подставляется в UI.

В обоих порядках кадров проходят:

- Принятие контакта и начальный обмен обоими аватарами.
- Замена картинки A, объявление, приём, сохранение и обновление того же widget B.
- Удаление картинки B с передачей tombstone и очисткой того же widget A.

Сравниваются точные значения source/peer settings и байты MemoryImage;
пустые списки не могут дать успешное сравнение. Лимит 64 доставок обнаруживает
цикл обратных ответов. Отдельный управляемый случай в fake KV и настоящем
worker задерживает чтение собственного аватара после accept, завершает block
и проверяет отсутствие поздней отправки.

На **macOS 79 related tests без skips** и на **Windows 11 те же 79 без skips**
прошли: paired/widget avatar, прежние avatar/consent, native worker races,
обычная контактная переписка и gating. Нативный HV вход проверен по SHA.
Итоговые четыре Dart-файла прошли analyzer. Серии пересекаются с прежними
раундами и не суммируются с ними.

На Windows использовались 12 явно учтённых файлов собственной QA-копии;
после проверки прежние байты восстановлены, новые файлы удалены. Повторно
сверены canonical frontend, packaged DLL и исходные QA-контейнер/prefs.
Приложения/звонки не запускались, owned app/task count равен нулю.

## Границы

Это доказанный app-level механизм, не установленная причина исходного репорта
Windows 10. Windows 10/Android, реальная сеть, ratchet/платформенный GUI и новые
AOT bundles этим стендом не квалифицированы. Локальные AV bundles предшествуют
этим Dart-правкам; новые immutable media pins также остаются до выпуска.
Произвольные потери live avatar frames по-прежнему могут потребовать повторного
открытия карточки. Пользовательские данные и реле не изменены; push/релиза нет.
