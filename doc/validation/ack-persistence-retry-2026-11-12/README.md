# Повтор подтверждения после отказа хранилища

**Подтверждено и исправлено локально:** временный отказ сохранить статус
доставки мог оставить сообщение в состоянии `sent` до перезапуска или
вытеснения записи кэша. Полученный ACK уже находился в session cache:
повторный ACK пропускал запись, а очередь сообщений считала доставку известной
и не отправляла сообщение повторно. Это отдельный механизм от предыдущей
sender-crash проверки: там `delivered` уже был на диске и восстанавливался
сверкой истории; здесь его запись не состоялась.

## Подтверждение

На исходном коде `307645f6` четыре регрессионных сценария падают именно на
поведении восстановления, без порогов времени:

| Временный отказ | Повторный ACK после восстановления storage | Повторная отправка после восстановления storage |
|---|---|---|
| Чтение целевого сообщения | Статус остаётся `sent` | Сообщение не отправляется |
| Commit status-op до применения | Статус остаётся `sent` | Сообщение не отправляется |

Использованы настоящий `MessagingService`/ACK dispatch, `HiddenVolumeStorage`
и mapping журнала, loopback transport и fault-injected KV store. Отказ чтения
вводится на границе point-read, отказ commit — перед применением реальных
KV/log operations. Wire ACK проходит обычный dispatch; успешная запись
не подставляется вместо отказа.
Это моделирование локального отказа, не аппаратная ошибка диска.

## Изменение

Раннее подавление пересылки во время записи ACK сохранено. Если запись
завершается ошибкой, удаляется только receipt этой пары peer/message. Если
`markMessageStatus` вернул `false`, дополнительно проверяется результат:
отсутствующий control-frame id или уже `delivered` допустимы, а существующая
строка с незаписанным статусом не считается завершённой. Ошибка повторного
чтения тоже снимает receipt. Повторный ACK снова может сохранить статус;
обычная очередь снова может получить ACK пересылкой того же сообщения.

Ни один отказ не создаёт статус для отсутствующего сообщения. Записанные
`delivered` остаются монотонными. Успешный повтор уведомляет собственные
устройства только при реальном изменении; последующие дубли не добавляют
коммиты. Данные разных peer не делят слот удаления. При потерянном ответе
после фактически применённого commit статус остаётся доставленным и
сообщение заново не отправляется.

## Проверки и границы

**58 тестов прошли без skips:** семь новых сценариев восстановления и границы
ожидания, cache isolation, monotone status, порядок mirror/status,
ACK coalescing и восстановление публикации зеркала. Targeted analyze и
`git diff --check` проходят.

На macOS arm64 последовательно пройдены **3 native E2E**, без skips:
sender-crash после status commit с новым пустым островом реле и выключенным
получателем; receiver-crash до append и после append, с обычными повтором,
ACK и дальнейшим двусторонним обменом. CLI/SDK 0.11.50 (`e963fbdb`), локальная
hidden-volume `293792d`; перед запуском проверены SHA inputs, исходники и
inputs не менялись до завершения. Прямые адреса, журналы и тестовые ID
остаются вне публичного результата. После стенда проверены выход его
процессов/групп, освобождение зарегистрированных портов и отсутствие test VM.

Первый совместный native-запуск не зачтён: параллельные Flutter runners
столкнулись при копировании `NativeAssetsManifest.json` до старта одного
клиента. Его процессы завершены; полный повтор с `--concurrency=1` прошёл.
Сбой подготовки ресурсов не объявляется дефектом приложения.

Исправление не доказывает причину прежних жалоб о доставке и не закрывает
всю multi-device матрицу. Восстановление после отказа записи здесь проверено
при повторном ACK или получении нового ACK пересылкой; автономное сохранение
полученного подтверждения без нового трафика этим изменением не обеспечивается.
Физический отказ Android/Windows storage не воспроизводился. Изменения
не запушены и не опубликованы.
