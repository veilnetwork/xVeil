# Чтение файла при смене личности — 2026-10-31

**Подтверждено и исправлено:** `loadFile`, `readFileRange`, `fileSize` и
`hasFile` ожидали on-disk metadata, затем заново обращались к `_as`. Если
между этими действиями закрыть A и открыть B, старый запрос продолжался уже
в B. В воспроизведении whole-file/range вернули байты B, size — размер B.
При erase с последующей записью под тем же file ID старое чтение тоже могло
вернуть новую запись вместо отказа.

Это дефект локальной границы сессии Storage. Передача данных по сети, показ
чужого файла в конкретном экране или причина прежних пользовательских жалоб
этим воспроизведением не доказаны. Находка получена при разборе дорогих чтений
журнала; исправление **не объявляется ускорением догрузки**.

## Правка

- Четыре read API фиксируют исходный backing store, blob tier и поколение
  файлового обслуживания до первого await.
- После metadata и перед возвратом результата проверяются та же сессия,
  тот же tier и отсутствие close/erase. При смене возвращается `StateError`,
  без идентификаторов, путей или содержимого файла в тексте ошибки.
- File maintenance увеличивает поколение: erase ловится и при неизменном
  объекте backing store. Проверка перед возвратом отвергает также байты,
  прочитанные до переключения, но завершившие свой Future после него.
- Чтения остаются параллельными. Они не встают на очередь записи, не заставляют
  close ждать крупный read и не выполняют дополнительных worker RPC/коммитов.
  Принятые записи по-прежнему дренируются прежним механизмом.
- Ограничение размера по сохранённым metadata, диапазоны, blob precedence,
  подписи, ratchet, ACK и формат хранения не меняются. Кэша между чтениями нет.

## Доказательства

Пять исходных unit-сценариев красные на базовом коде: четыре API при close/open
и read через erase с сохранением backing object. После правки они проходят;
старый запрос не делает ни одного чтения новой сессии. Дополнительно проверены
поздний результат payload, смена blob directory и независимое чтение при
незавершённой записи — **8/8**.

Отдельный контроль с двумя настоящими encrypted containers и worker-изолятами:
старый Dart **0/2**, новый **2/2**. Gate стоит после реального ответа worker
на metadata; close успевает закрыть A и open — открыть B до снятия gate.
Whole-file и range отклоняются, worker B не получает запросов от старого read,
обычное чтение B работает. Повторное открытие A подтверждает освобождение
native lock и сохранность его прежних байтов. Источники восстановлены в finally.

Итоговый scoped-набор: **663 passed, 3 skipped**, analyzer без замечаний.
Worker-backed набор: **5 passed**, включая чтение при смене сессии, прежние
file close/erase и сравнение durable bytes. Первый широкий запуск содержал
ошибочно указанный несуществующий путь теста; он не засчитан как успешный.
После исправления списка выполнен чистый итоговый прогон.

Native-оверлей: 4/4 сообщения всем 12 узлам без дублей; узлы остановлены,
12 слушателей освобождены, ошибок cleanup нет, host process завершён. Один
процесс/Mac, TCP, DHT включена, группа без шифрования эпох. Агрегаты и teardown
фиксируются в [summary.json](summary.json).
Телефон и реле не менялись, GUI-переключение личности в этом цикле не проверялось.
Публичный отчёт содержит только синтетические примеры, агрегаты и source SHA.
Без push/релиза.

Активная задача задержек остаётся: в предыдущем A/B/C прогоне B получил только
78/100 за 300 секунд при online A/offline C; после возврата C всё сошлось.
Следующий участок — стоимость повторных load/save и обработка старых кадров,
затем оставшаяся multi-device матрица. Исторические невоспроизводимые жалобы
не возвращаются в активную очередь без нового воспроизведения.

Уточнение прошлого захвата: 100 начатых обработок `groupEntry` имели 100 разных
frame ID; на callback зафиксировано 156 доставок с 112 различными ID. Поэтому
обычное отбрасывание одинакового frame ID не устраняет наблюдавшуюся стоимость
повторной обработки истории. Отсутствие новых notification-строк само по себе
по-прежнему не доказывает, что всё состояние кадра совпадает с сохранённым.
