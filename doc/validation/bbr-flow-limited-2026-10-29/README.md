# BBR: ожидание приёмного окна не является полосой сети — 2026-10-29

Veil `6d33974d`, предыдущий вариант `524112a2`. Продолжение проверки
[смешанных версий и уведомлений о чтении](../flow-window-reopen-2026-10-29/README.md).

## Подтверждённый механизм

В смешанном воспроизводителе новый отправитель мог продолжать работу с оценкой
BBR всего **628 байт/с** после ожидания закрытого окна. При этом SRTT составлял
6 мс, outstanding DATA отсутствовали в ожиданиях persist, а старый получатель
уже освободил буфер. Приложение отправителя имело большой backlog, поэтому
`bbr_on_delivered` считало весь интервал пригодным для обучения сети.

Следствие — два разных ожидания складывались: старый получатель не создавал
ACK при чтении, затем ложная низкая оценка растягивала pacing даже после
получения ненулевого окна. Ускорение только второго механизма не устраняет
первый. Высокий ping или потеря DATA не требуются для такого занижения модели.

## Изменение

После проверки возраста/допустимости ACK, если его окно равно нулю либо этот
ACK открывает ранее нулевое окно, движок завершает текущий интервал delivery-rate:
очищает `rate_samples` и отмечает ограниченный источником период. Первый
пригодный последующий образец начинается после открытия окна.

Счётчик доставленных байтов, `bw_samples`, уже известная полоса/seed, STARTUP,
SRTT/RTO, ProbeRTT и loss recovery не сбрасываются. Это не повышение оценки
полосы и не выдача send credit. Существующий window cap и pacing продолжают
использовать прежние ограничения. Следующая реальная доставка при открытом
окне снова может обучать модель, включая уменьшение оценки при действительном
снижении пропускной способности.

Устаревший zero-window ACK ниже `snd_una` и ACK ещё не отправленных байтов
не могут оборвать свежий интервал. Wire, C ABI, ratchet, durable apply, ACK/SACK,
подсказки старых DATA, mailbox и равенство обслуживания реле не менялись.

## Регрессия и проверки

Новый тест на прежнем `524112a2` получил **128 байт/с** вместо отсутствия
достоверного образца: два заполнения буфера по 128 байт и ожидания его открытия
превратились в измерение сети. После правки фиктивный образец отсутствует,
а все 256 доставленных байт остаются учтены. Затем получатель читает нормально:
доставка 64 байт каждые 8 мс даёт ровно **8000 байт/с**, то есть обучение после
ограничения не выключено навсегда.

Отдельная проверка сохраняет warm seed и его образцы на границах закрытия и
открытия, а также проверяет, что старые/невозможные ACK не меняют свежие rate
checkpoints и отметку ограничения.

**199 stream-тестов прошли, ignored нет. 326 FFI-тестов прошли, два ignored**
при `--no-default-features` и `node-embedded,production-seeds,packet-tunnel`.
Дочерний subprocess не прибавлен к 326. Clippy `--lib --tests -- -D warnings`
и rustfmt прошли. Включены прежние проверки падения реальной полосы,
адаптации warm seed, длительного bounded-rate FIFO, переупорядочивания и
возобновления чтения. Проверки не ослаблялись.

## Контроль A/B/A

[mixed_probe.rs](mixed_probe.rs) — прежняя модель с одинаковыми дополнительными
trace-вставками во всех фазах, выключенными без переменной `TRACE`. На проводе
два FIFO по 3 мс; MSS 64, окно 128 байт, по 4096 байт в каждую сторону, BBR on,
RACK on/off, приложения сначала не читают 25 мс, затем читают с тактом 3/5 мс.
Вариант потери выбрасывает первое открытие окна в каждом направлении.
Сериализация полосы, публичные реле, Android и криптография не моделируются.

`old` — неизменный `04eb1c1d`. Метка `new` означает `524112a2` в A и
`6d33974d` в B. Для каждой фазы выполнены все 16 сочетаний. A₁ и A₂ дали
одинаковые числовые строки всех профилей. В каждой фазе каждый байт совпал,
оба направления достигли EOF. Время — виртуальное, до полного закрытия:

| Сочетание | Потеря обновления окна | A₁, мс | B, мс | A₂, мс |
| --- | --- | ---: | ---: | ---: |
| old / old | нет | 4130 | 4130 | 4130 |
| old / old | есть | 4237 | 4237 | 4237 |
| old / new | нет | 344 | 344 | 344 |
| old / new | есть | 5935 | 1251 | 5935 |
| new / old | нет | 4540 | 3397 | 4540 |
| new / old | есть | 13 872 | 8431 | 13 872 |
| new / new | нет | 344 | 344 | 344 |
| new / new | есть | 349 | 349 | 349 |

Значения RACK on/off совпали в этой модели. Это один детерминированный контроль,
не статистика скорости на публичной сети. Смешанный `new / old` с потерей
по-прежнему медленнее old/old: сохранены ожидания persist у старого получателя,
не отправляющего уведомления после чтения. Общее исправление совместимости
по скорости **не заявляется**. В этой модели new/new не ухудшился.

Для повторения создать отдельный Cargo binary с `old`/`new` path-зависимостями
на эти версии `veil-onion-stream` и поместить воспроизводитель в `src/main.rs`.
Private standalone-копии отличались от соответствующих production-исходников
только manifest-версиями (`0.1.0-validation-old` и `0.1.0-validation-reference`)
и снятым наследованием workspace lints. Source A восстановлен из git; source B
из текущего checkout. Для reference и candidate использованы разные внешние
target. `cargo run --offline --release` без `TRACE` печатает только метрики.
Сводка и хеши — [summary.json](summary.json).

## Границы

Не доказана связь этого механизма с прежними физическими «33%» или длинными
паузами на проблемном провайдере. Начальное окно, неизвестные 343 cells,
per-hop времена и остальные открытые пользовательские случаи не изменены.
Остаток задержки смешанных версий остаётся в журнале находок.

Телефон, GUI и работающие реле не запускались/не изменялись, звонков не было.
Все Cargo/test/probe процессы завершены; процессы проверены после выполнения.
Rust-сборки непрерывно проверяли внешний mount, targets разделены по source/
override. Приватные трассы не публикуются. Push, релиз и установка не выполнялись.
