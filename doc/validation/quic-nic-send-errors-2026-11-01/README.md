# Холодный QUIC: NIC-захват и ошибки UDP send

2026-11-01. Продолжение [проверки первого stream](../quic-first-stream-2026-11-01/README.md).
SDK `c8bdfd97` → `026dd915`. **Задержка не устранена.** Исправлен пробел
диагностики: прежний UDP `stage=send` означал приём вызова API, хотя backend
может скрыть локальный отказ ОС. Наблюдения ниже не являются A/B или доказанным
ускорением. R31 уже проверен [отдельно](../report31-2026-11-01/README.md).

## NIC во время неудачных попыток

Четыре запуска Mac на SDK `c8bdfd97` с двумя изолированными службами S1/S2.
До двустороннего ACTIVE: **11,964 / 13,091 / 1,504 / 12,769 с**. Во всех случаях
один server link оставался ACTIVE не менее трёх секунд.

Ограниченный capture только тестового UDP-порта S1 теперь охватил медленные
попытки: **1614 pcap-записей**, 1615 received-by-filter, **0 kernel drops** по
сводке tcpdump. Это не утверждение об отсутствии потерь до capture.
Анализ учитывает GRO/coalescing: ищет известные зашифрованные samples внутри
записи, не выдаёт кандидатные сегменты за доказанные wire-границы. Все
**45/45 server receive** и **46/46 server send** samples найдены в pcap —
положительный контроль анализа. Client send: 31/40 совпадений; оставшиеся
девять не объявляются девятью потерянными пакетами.

У двух server connection с timeout первого stream принадлежность Mac
сопоставлена через server-send ciphertext, также полученный Mac. Их потоки
в пределах захвата однозначны. Для каждого на NIC видно четыре входящих UDP
записи, содержащие четыре QUIC Initial и один Handshake; **1-RTT не видно**.
На серверном connection STREAM RX остаётся 0, UDP RX — 3 до timeout.
В этих записях нет IP-фрагментации или нераспознанного QUIC version. Два других
server timeout не сопоставлены Mac и к нему не приписаны. У успешных потоков
есть 1-RTT, однако некоторые разделяют UDP tuple: их статистика не выдаётся за
однозначную поконнектную атрибуцию.

Для этих двух попыток причина ожидания находится **до наблюдаемого NIC S1**,
а не в последующей OVL1-обработке. Это ещё не выбор между клиентским kernel/
фильтром, промежуточной сетью и иным механизмом перед сервером. Полный исходящий
capture на Mac не выполнен: текущий процесс не имеет доступа к BPF и
неинтерактивному sudo. На production capture не запускался.

## Диагностический дефект и правка

`UdpSocketState::send` намеренно сохраняет прежнюю политику QUIC: ошибки, кроме
`WouldBlock`, могут превращаться в `Ok`, включая `EMSGSIZE`. Поэтому прежнее
описание `udp_socket_sent_bytes`/`stage=send` как гарантированного kernel handoff
было слишком сильным. Менять транспортную политику по одному подозрению нельзя.

В `026dd915` добавлен выключенный по умолчанию observer фактического результата
UDP send на Unix/Windows/fallback. Он не удерживает пакет и не меняет возврат,
повторы или wire. При включённом RT trace сохраняются числовой errno,
категория ошибки и размер. Адреса и свободный текст исключения не выводятся.
Для ограниченной корреляции зашифрованных datagram действует прежний sampling;
эти raw records остаются приватными и не входят в анонимный экспорт приложения.
Обычная сборка с выключенным trace молчит. Инициализация по environment-gate
выполнена до первой отправки connection.

Регрессия использует настоящий UDP socket: слишком большой datagram и
IPv6-адрес на IPv4 socket. `try_send` возвращает ошибку; `send` сохраняет `Ok`,
но observer видит оба отказа. Удаление только production-вызовов observer даёт
**0 passed / 1 failed**, восстановление — **1 passed**. `WouldBlock` не считается
потерянной отправкой. Первый вариант fixture ошибочно ожидал запрета порта 0
на Mac; он исключён из доказательства red. Ошибки настройки отдельного Quinn
probe также не засчитаны как проверки продукта.

## Физический отрицательный контроль

Три запуска Mac на `026dd915`, сервер на неизменном `c8bdfd97`: **12,134 /
12,791 / 25,182 с** до двустороннего ACTIVE. Во всех трёх link удержан ≥3 с.
**Ноль событий локальной ошибки send** при включённом trace. В этих случаях
подавленная ошибка syscall не наблюдалась; гипотеза ослаблена, не исключена
для любых других устройств/маршрутов. Изменение только диагностическое;
сравнения производительности двух SDK эта серия не даёт.

## Дополнительный opaque UDP proxy

Для наблюдения без Mac BPF выполнены два запуска через локальный UDP proxy:
он принимает зашифрованные datagram, проверяет полный размер успешной отправки
и пересылает тому же S1. TLS/OVL1 не расшифровываются и не подменяются,
bootstrap key/nonce не меняются; наблюдаемая TOS/ECN-категория сохраняется.
Это стендовый инструмент вне production-кода. Loopback и новый upstream socket
меняют локальный путь, поэтому эксперимент не равнозначен прямому подключению.

Задержки сохранились: **37,469 / 23,813 с**, оба запуска достигли двустороннего
ACTIVE ≥3 с. Четыре неудачных server connection сопоставлены разным proxy-flow
по зашифрованным ответам. Для каждого proxy успешно отправил **29 или 30**
short-header datagram, но server STREAM RX остался 0. Среди sampled server RX
совпадений с этими short-header datagram нет; для успешного контрольного flow
есть 6 совпадений из 101 отправленного. **Отсутствие sampled-совпадений не
является доказательством потери каждого пакета.** NIC-capture в этой серии не
запускался; её нельзя молча объединять с предыдущей в один полный packet path.
Показано, что SDK отдаёт datagram следующему локальному сокету; задержка
воспроизводится и без прямой отправки SDK во внешнюю сеть.

Первый вариант proxy не был задействован: bootstrap invite запрещает вложенный
query, а один ранний observer выбирал резервный JSON вместо свежего снимка.
Эти попытки сохранены отдельно и исключены из квалификации. Итоговые два
запуска используют допустимый endpoint и фактически наблюдаемый proxy-трафик.

## Проверки и уборка

- Runtime **795 passed / 11 ignored**, transport **156 passed**.
- Настоящий UDP observer: **1 passed**; Quinn log bridge/correlation: **2 passed**.
  Vendor-тесты запускались через отдельные manifest/probe с path dependencies
  на проверяемый исходник; корневой `-p` для исключённых vendor-пакетов не принят.
- Windows GNU UDP `cargo check` прошёл; это не физическая проверка Windows.
- Privacy/AOT/summary: **10 passed**; новая raw trace остаётся приватной.
- Внешние target разделены для SDK, standalone UDP, Quinn probe и Windows;
  mount проверялся до сборки и watchdog не фиксировал его потерю. У Mac SDK
  проверены source commit, binary marker/SHA и codesign; frontend/AOT заморожен.
- Все собственные Mac-процессы девяти зачтённых запусков завершены, runtime
  удалены. Приложения исключённых попыток тоже завершены. Proxy/hasher и SSH
  observer завершены; исходный bootstrap-list восстановлен. Capture завершён.
- Все шесть тестовых служб остановлены, порты освобождены. S1/S2 возвращены
  на исходные test binaries, trace drop-in удалены, unit definitions сверены,
  autorollback остановлен. Итоговые независимые preflight прошли **6/6** для
  каждой серии; в первой серии промежуточный SSH banner timeout потребовал
  повторной проверки. Production PID/binary/config сохранены **6/6**.
- Телефон/Windows не менялись, push и релиза нет. SDK-коммит unsigned/local.

NETLINE-01 и NETCALL-01 открыты. Следующий различающий захват — одновременное
наблюдение исходящего трафика Mac и NIC S1 на медленной попытке либо проверка
того же пути через другой разрешённый транспорт. Наличие сетевого фильтра
или конкретный виновный hop пока не доказано. Таймауты не сокращены, защитные
политики и архитектура доставки не ослаблены.
