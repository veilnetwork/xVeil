# NETCALL-01: данные после настоящего TCP resume

**Основной возобновлённый поток прошёл контроль; новый дефект в нём не найден.**
Для TCP и obfs4/TCP проверены настоящие зашифрованные APP_RTData в обе стороны
до возобновления, при удержанном завершении предшественника и после него.
Это не закрывает мобильную паузу NETCALL-01 или работу вспомогательных каналов.

## Что проверено

Предыдущий тест unknown-leaf resume проверял handshake, смену TX-регистрации
и поздний Drop старого admission guard, но не запускал SessionRunner. Новый
контроль использует настоящий inbound SessionRunner Core и ручной leaf на
loopback. Оба узла имеют разные реальные ключи с обычным PoW. Встроенные сиды,
настроенные peers, meeting points и PEX отключены.

Leaf получает ticket из зашифрованного SessionMsg::Ticket самого runner —
тест не обращается к issuer для его изготовления. Перед новой сессией старая
остаётся открытой. Для неизвестного leaf обычный полный handshake не имеет
права вытеснить её: новая регистрация требует аутентифицированного resume
именно её ticket. Отдельные прежние negative controls сохраняют эту границу.

Проверка удерживает **финальный stream.shutdown старого Core runner** после
его выхода из run/release_session, оставляя живым старый SessionGuard. Это
не имитация продолжающегося старого run-loop. Gate подтверждает достижение
этой точки; проверка не опирается на паузу заданной длительности.

На каждом транспорте:

1. Данные leaf → Core доходят через dispatcher в настоящий app endpoint;
   Core → leaf проходят обычную TX-очередь и проверку session AEAD.
2. Реальный resume меняет TX-регистрацию, session ID и оба направленных ключа.
3. Обмен повторяется, пока старое завершение удерживается gate.
4. Старое завершение разрешается и дожидается полного выхода task. Новая
   регистрация остаётся прежней, двусторонний обмен снова проходит.

Всего проверены 12 прикладных кадров: шесть на каждом транспорте. Payload —
синтетический AEAD-маркер, сверяются все поля и байты; настоящего аудио нет.
Чтение также аутентифицирует промежуточные control-кадры, сохраняя nonce counter.

## Ограничения и ошибки обвязки

Ручной leaf реализует основной поток, но не auxiliary lanes. Поэтому fixture
явно не предоставляет Core parallel-stream offer, сохраняя настоящий obfs4,
exporter binding и OVL1/session authentication. Это **контроль canonical path**,
а не квалификация production media lane или старого child/parent generation.

Промежуточная обвязка предлагала obfs4 auxiliary lanes, которых ручной leaf
не обслуживал: ticket приходил, обратная RTData не принималась. Такой отказ
не засчитан как дефект продукта. В первой очистке также повторно опрашивался
уже завершённый JoinHandle: это ошибка теста, исправленная перед итоговым
прогоном. Ошибки компиляции и эти падения не называются assertion-red на
прежнем продукте. Production-код, wire, таймауты и транспортная политика
в этом цикле не менялись.

Нет Android, NAT, смены сети, потерь, слышимости человеком, длительного soak
или проверки вспомогательных медиаканалов. Успех на loopback не исключает
ошибок этих путей и не объясняет наблюдавшиеся незавершённые mobile first flights.

## Итог и воспроизводимость

Два новых integration-теста прошли в release-профиле с production-seeds
feature, без test-low-difficulty и без игнорирования. Отфильтрованные отдельные
integration binaries с нулём запущенных тестов не прибавляются к результату.
Также прошли три существующих resume-admission проверки (включая запрет
вытеснения новым полным handshake и старым ticket) и один NetworkChanged
redial-контроль. Итого **6 passed / 0 skipped**, повторные запуски не суммируются.
Профилирование скорости и A/B не выполнялись.
Clippy release/tests с `-D warnings`, форматирование и проверки приватности
прошли. Изменения native относятся только к тестам.

Внешняя файловая система проверялась перед Cargo и непрерывно во время его
работы. Использован target того же checkout, без dependency override; исходники
фиксировались SHA. Первый случайно запущенный debug build остановлен: его
отдельно созданный каталог, около 590 МиБ, удалён после проверки времени
создания всех файлов. Shared release cache сохранён.

По ответу владельца повторена установка отдельного Network Call QA на Poco:
успех, установленный APK проверен по SHA; основной APK побайтно не изменён.
Приложение не запускалось, разрешения/сеть не менялись, фокус Mac не затрагивался.
Новых production или remote capture-процессов не создавалось.

Следующий участок — вспомогательные каналы при смене parent и безопасная
атрибуция mobile first flight к socket/flow. NETCALL-01 остаётся активным.
Без push и релиза.

проверил auxiliary RTData при заблокированном основном потоке, включая native
NetworkChanged/resume и поздний старый teardown. На loopback он прошёл;
физическая mobile-атрибуция по-прежнему открыта.
