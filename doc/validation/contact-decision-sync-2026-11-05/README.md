# Доставка решений о контактах своим устройствам — 2026-11-05

База `9bfd42aa`. Локально, без push/релиза, обновлений сидов, APK,
engine pins и mailbox для собственных устройств.

## Подтверждённый механизм

После атомарного сохранения accepted и ответа собеседнику публикация решения
в журнал своих устройств всё ещё зависела от callback в памяти. Исключение,
отсутствующий callback или остановка до его выполнения оставляли только
локальную запись контакта. При новом запуске воспроизведения этой обязанности
не было. **Два assertion-red на базе**: ordinary и worker/native HVS; после
отказа callback контакт принят и контейнер повторно открыт, но durable
обязательство передать решение своим устройствам отсутствует. Это отдельная
граница от ответа внешнему собеседнику из предыдущего исправления.

## Изменение

Принятие теперь сохраняет статус, contact index, адресный ответ и локальное
намерение синхронизации одной транзакцией. Для block/unblock и входящего
accept статус и намерение тоже сохраняются вместе. Pending-запросы остаются
локальными doorbell-событиями и не получают такой записи.

В зашифрованном settings namespace находятся исходные peer/status/timestamp
решения и ordering floor. Новое локальное решение получает монотонную версию,
учитывающую уже применённые verified remote решения этого контакта. Повтор
публикации сохраняет исходную версию. Floor обновляется вместе с проекцией;
задержанное более старое событие не отменяет локальный block/accept, даже если
его публикация ещё не состоялась. Одинаковое время разрешается тем же порядком
status payload, что использует device fold.

Callback только будит ограниченный publisher. Повтор выполняется при запуске,
при появлении группы устройств и периодически. До linking намерения сохраняются;
после linking используются существующие signed device-group события и durable
replication admission. Собственные pair/self контакты исключены. Нового
сетевого транспорта или relay mailbox не добавлено.

ACK локального намерения сравнивает token точной сохранённой версии: завершение
старой отправки не удаляет более новый block/unblock. Для восстановления после
потерянного ответа publisher читает committed verified журнал, присоединяясь
к его сериализованной записи; события из ещё не сохранённого batch не считаются
доказательством. Точные дубли подавляются и при откате часов. Другое будущее
решение за допустимым clock-skew не скрывает сегодняшнее решение; для этого
читаются все retained версии, а не только максимальная будущая строка.

Предварительный `deviceOutgoing` сигнал статуса не применяется как durable
floor: он возникает до group commit. Preferences и остальные виды собственных
событий продолжают прежний путь. При linking решения с известным floor
переигрываются с исходной версией; legacy контакты без версии сохраняют прежний
catch-up. Уже потерянные старым кодом намерения не выдумываются из текущего
состояния всей адресной книги.

Publisher ограничивает batch 64 записями, проход восемью страницами и число
повторных проходов. Ошибка одного результата оставляет его на повтор, не
удаляет остальные намерения. Close останавливает admission/timer и присоединяет
текущий handoff. При ошибках создаётся анонимный `contact-status-sync` без
исходного текста, пути, payload, peer/token. Удаление контакта/erase удаляет
его локальные записи; обычный ACK сохраняет ordering floor.

## Проверки

Scoped: **36 passed**, включая 20 расширенных тестов принятия (десять
worker/native HVS), два cold-callback теста (один worker/native) и 14 тестов
publisher/ledger. Проверены CAS при новом решении во время отправки,
pre-commit отказ/lost reply, повтор после ошибки публикации/ACK и перезапуска,
отсутствие echo у mirrors, исходные timestamp, одинаковое время, delayed
mirror после cold reopen, future/exact/shadowed dedupe, bounded backlog,
исключение self/pair контактов, close, corrupt record, удаление/erase и canaries.
Финальный committed-journal контроль дополнительно проверяет gate успешной
и отклонённой записи: read не завершён до commit; future rows не становятся
эффективными из-за использования dedupe API.

Финальная control-серия с диагностикой и явно выбранной HVS: **505 passed,
без skip**, 20 файлов. Широкая серия: **1951 passed / 3 conditional skipped**,
105 файлов, HVS также выбрана явно. Skip не считается квалификацией. Analyzer
семи lib inputs и всего test чистый. Начальная ошибка имени getter в новом
process fixture исправлена до запуска стенда и не считается red-результатом.

Headless AOT собран штатным `dart build cli`, `--help` завершился с кодом 0.
578 source/pub hashes неизменны при сборке; собственные 14 МБ артефактов удалены
после SHA/smoke. Это build/argument проверка, не headless сетевой прогон.
Veil/HVS не пересобирались; используются прежние проверенные source/artifact
пины. Данные пользователя и подключённый телефон не менялись.

## Сквозной process A/B/C

Три отдельных native процесса на одном Mac, текущие production providers,
signer/device bridge, шесть локальных реле. A/B — одна личность, C — другая.
После обычного подтверждения контакта и linking B сначала действительно
показывает accepted. A остановлен; через настоящий HVS storage port записан
block без callback. Это точное построение durable состояния после commit и
до публикации, **не** заявление о SIGKILL в момент UI нажатия или power-loss.

После запуска A штатный boot publisher передал исходное решение в журнал;
на A и B одновременно проверены blocked и **тот же исходный timestamp**,
а на A через live owner проверена пустая очередь намерений. Повторный запуск
сохранил версию и пустую очередь. Пройдены все три process gates. Это проверка
логического fold, не доказательство отсутствия всех дублирующих transport rows.

Финальный teardown: **25 PID / 41 порт**, собственных процессов/listeners нет,
runtime удалён. **1467 frozen inputs** и native SHA неизменны, Veil/HVS clean.
Серия заняла 218,9 с; эта длительность не сравнение скорости доставки.
Это квалификация GUI bridge на native Mac-процессах, не Android/Windows/AOT
стенд и не полная multi-device/crash матрица.

## Границы

Windows недоступна по SSH; исходная недоставка PC ↔ Android не объявляется
объяснённой этим механизмом. Полная contact conflict/crash матрица, все другие
writers контактной записи, длительный offline, слышимость звонков и общая
latency остаются отдельными проверками. Публикация через GUI device bridge
не является квалификацией всех headless multi-device сценариев.
