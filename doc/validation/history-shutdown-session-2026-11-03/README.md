# Штатное выключение не оставляет сессию до keepalive

2026-11-03. Продолжение [разбора начального history-ответа](../history-reply-route-2026-11-03/README.md).

## Подтверждённый механизм

`NodeRuntime::do_stop_tasks` уже отправляет всем активным сессиям
`Session/Detach(SHUTDOWN)` перед остановкой. По определению протокола эта
причина означает «node is going down». Однако dispatcher обрабатывал её
только как освобождение gateway attachment, а SessionRunner продолжал ждать
новые кадры. Пока не случались EOF или keepalive timeout, открытая локальная
очередь могла оставаться пригодной для выбора исходящим отправителем.

Теперь canonical runner после расшифровки и обычного dispatch завершает
**свою** сессию при принятом `SHUTDOWN`. Rate-limit/decode/violation path не
обходятся. `NORMAL`, `MIGRATING`, `ERROR` и неизвестные причины сохраняют
прежнее поведение. Ни таймауты, ни wire-формат не менялись. Завершение идёт
через существующий teardown с проверкой владельца регистрации: старый runner
не получает права удалить новую сессию того же peer.

Это не распознавание обрыва питания: без полученного уведомления остаются
обычные механизмы EOF, keepalive и reconnect. Mailbox собственных устройств
не используется и не добавляется.

## Воспроизведение и проверки

Новый integration test запускает настоящий SessionRunner с AEAD-ciphers,
передаёт зашифрованный `SHUTDOWN` и намеренно оставляет сокет отправителя
открытым. Keepalive и idle timers отключены. На прежнем коде runner не
завершался; на исправленном завершается без panic, сокет получает EOF.
Виртуальный timer ограничивает отсутствие перехода состояния, а не задаёт
производительный норматив.

Парный контроль после четырёх других причин detach передаёт encrypted Ping,
получает и расшифровывает Pong: соединение продолжает работать. Принятый
красный прогон — 1 passed / 1 failed; ошибки AAD/типа в черновом тесте были
исправлены до него и подтверждением дефекта не считаются. Перед финальной
квалификацией oracle усилен: одного завершившегося JoinHandle недостаточно,
внутренний результат задачи тоже обязан быть успешным.

Полные относящиеся к изменению серии:

| Серия | Успешно | Пропущено | Ошибки |
| --- | ---: | ---: | ---: |
| veil-node-runtime unit | 797 | 11 | 0 |
| veil-session unit | 683 | 8 | 0 |
| runner integration, включая новые случаи | 121 | 1 | 0 |
| Всего уникальных тестов | **1601** | **20** | **0** |

Пропуски не засчитываются как успехи. Integration suite повторена после
усиления oracle с тем же результатом. В runtime suite прошли существующие
проверки owner-checked cleanup после замены регистрации. Новых гарантий
относительно физического Windows/Android из host-тестов не выводится.

## Native-квалификация

Сценарий A/B/C и пассивный observer неизменны: три строки вне device journal
A, средняя 160015 байт; B возвращается при online A/offline C, затем
перезапускается один для проверки локальной сохранности. История подготовлена
через live encrypted storage искусственно, естественная compaction не проверяется.

| Фаза | SDK | Ready B от запуска, с | Первая строка после ready, с | Все три от запуска, с | Первый ответ, с от открытия probe |
| --- | --- | ---: | ---: | ---: | ---: |
| A₁: контроль | `8dac85ce` | 10,064 | 14,764 | 26,810 | 14,502 |
| B: исправление | `fbf524e1` | 9,677 | 11,731 | 22,429 | 11,353 |
| A₂: обратный контроль | `8dac85ce` | 9,684 | 14,822 | 25,982 | 14,503 |

Каждая фаза получила **3/3** с точными ID/телами/порядком/source positions и
delivered, без дублей. Проверочных mirrors в journal A до/после 0. B сохраняет
все строки при следующем запуске без A/C. Это три одиночных прогона на одном
Mac, JIT-хосты/loopback и включённый локальный trace; процент универсального
ускорения и квалификация большой миграции/Android/AOT не заявляются.

### Что изменилось и что не удалось закрыть

В контролях один и тот же inventory-запрос приходит A уже на +0,529/+0,523 с,
а B впервые видит ответ лишь на +14,502/+14,503 с после повторов.
В кандидате A получает запрос на +0,571 с и повтор на +6,478 с; промежуточная
копия на +2,482 с имеет claimed provenance и по-прежнему отвергается.
Первый ответ B видит на +11,353 с.

В кандидате A зарегистрировал `session.peer_shutdown` для того же physical
recipient примерно за 11,171 с до открытия probe B: новый обработчик реально
сработал. Но существенное ожидание ответа осталось. Поэтому исправление
закрывает игнорирование уведомления о штатной остановке; **вся задержка
начального history-ответа этим не закрыта**, гипотеза об одной старой сессии
как полной причине не подтверждена.

Начало локальных 420-байтовых ответов в кандидате — +0,591 и +6,516 с. Это
всё ещё лог перед вызовом транспорта, а не подтверждение admission. Рядом
наблюдаются несколько native `direct_or_fallback` sends к тому же получателю
длительностью около 11 и 20 с, заканчивающиеся у первого ответа. У этих
записей нет размера payload и общего с Dart request-ID; отождествлять их с
конкретными inventory-ответами нельзя. Следующий участок — ожидания между
началом вызова, native direct/relay admission и его завершением, с явной
связью наблюдений. Приписывать остаток исключительно сети оснований нет.

## Происхождение и очистка

До пересборки сохранены и проверены старые CLI/FFI `8dac85ce`, поэтому
обратный контроль использует те же байты, а не Cargo cache по чистому checkout.
Кандидат — production CLI/FFI, собранные с теми же четырьмя features и HV;
SHA и наличие/отсутствие нового диагностического маркера проверены отдельно.
External target принадлежит тому же checkout без dependency overrides;
монтирование/место контролировались на протяжении Rust-сборок и тестов.
SDK перед/после build проверен по HEAD и содержимому 1524 tracked-файлов.

Production fix — `af221389`; финальный SDK `fbf524e1` добавляет только усиление
unit oracle. A₁ закончился и прошёл cleanup до этой тестовой правки, B/A₂
начались после неё и финального build. Этот Rust integration-test не входит
в native workers. Хеши всех **1400** Dart/application/fixture/dependency files
равны между A₁/B/A₂ и не менялись во время каждого прогона. HV одинаков во
всех фазах; CLI/FFI обоих контролей побайтно равны.

Все три родительских теста и cleanup завершились с кодом 0, с положительным
`passed` oracle и штатным `All tests passed`. Проверки PID/портов по фазам:
**24/26**, **22/25**, **25/19**. Живых собственных процессов и оставшихся
listeners нет, runtime-контейнеры удалены, probe drops 0. Raw evidence/ключи/
адреса и непрозрачные request-ID в этот отчёт не включены.

Изменение SDK и этот журнал сохранены локальными неподписанными коммитами.
Публичные сиды, пользовательские приложения и engine pins не изменялись;
push/релиза нет. Остаточная задержка и расширенная multi-device матрица
остаются активными; mailbox не добавлялся.
