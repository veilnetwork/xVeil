# Android: вход после перезапуска и гонки уведомлений

## Подтверждённые дефекты уведомлений

На исходном коде два widget-теста воспроизвели потерю уже показанного
уведомления при запоздавшем завершении другого показа:

| Сценарий | До исправления | После исправления |
| --- | --- | --- |
| ОС ещё не завершила первый показ сообщения; приходит и показывается следующее | Первый вызов замечал устаревший ticket и отменял общий OS ID, убирая новое сообщение тоже | Для одного ID завершение показа и необходимая отмена упорядочены; новое сообщение показывается после отмены старого |
| ОС ещё не завершила показ запроса очистки чата; приходит обычное сообщение | Общий счётчик делал запрос устаревшим и отменял его отдельное уведомление | Запрос имеет собственный identity/lifecycle ticket и не отменяется сообщением |

Сообщения по-прежнему заменяют **одно** общее уведомление. Новых уведомлений
на каждый чат и изменения содержимого скрытого preview нет. Запросы очистки
сохраняют отдельный OS ID. Ошибка платформенного показа не блокирует следующую
операцию; разные OS ID не ждут друг друга.

Публикация также проверяет актуальность личности непосредственно при завершении
платформенной операции, даже если messaging provider ещё не успел перепривязаться.
При смене личности, возвращении в приложение или уничтожении binder старый
показ снимается до следующего показа того же ID. Обработчик больше не отправляет
запоздавшую отмену поверх нового уведомления. Attribution для inline reply
сохраняется только после успешного актуального показа.

Дополнительная проверка выявила, что запуск групповой службы мог отменять
ожидающий alert списка запросов очистки того же messaging service. Эти источники
разделены; принадлежность запроса личности проверяется отдельно.

**164** выбранных Flutter/Dart теста прошли без пропусков. Включены **10** новых
проверок порядка показа/отмены, отказа ОС, независимых ID, очереди устаревших
операций, смены личности до перепривязки provider и удаления binder.
Проверки прежней атрибуции inline reply, приватности preview, screen lock,
lifecycle, background controller и быстрого входа тоже прошли.
`flutter analyze --no-pub`: **0 замечаний**.

## Физический Blackview: графический вход после остановки процесса

Использовано отдельное debug-приложение с собственным application ID и приватным
каталогом. Entry point находится только в `test/native/` и отказывается работать
в основном пакете, вне Android или в release. Установленная пользовательская
xVeil не заменялась, её данные не открывались и не удалялись.

Для каждого размера сетки создан отдельный настоящий hidden-volume контейнер
со случайным паролем. Пароль не сохранялся в обычном файле и не возвращался
управляющему процессу. Через production `QuickUnlockVault` он сохранялся в
защищённом хранилище Android и затем использовался для открытия контейнера.

| Сетка | Правильный ключ до перезапуска | Неправильный ключ | После полного force-stop и нового процесса |
| --- | --- | --- | --- |
| 3×3 | Контейнер открыт, маркер прочитан | Отказ | Контейнер открыт, маркер прочитан |
| 4×4 | Контейнер открыт, маркер прочитан | Отказ | Контейнер открыт, маркер прочитан |
| 5×5 | Контейнер открыт, маркер прочитан | Отказ | Контейнер открыт, маркер прочитан |

Это новый OS-процесс, а не только новый экземпляр Dart-объекта. Неверные
последовательности имеют допустимую длину и координаты: проверяется отказ на
неправильный секрет, а не только валидация ввода. Перед удалением тестового
приложения все три записи быстрого входа явно удалены и отсутствие проверено.

Система сообщает о доступной биометрии. Реальный отпечаток/лицо и показ
биометрического запроса **не проверены**; автоматический ввод не заменяет палец.
Этот прогон также не проверяет весь пользовательский экран ввода рисунка.

## Фоновая служба при выключенном экране

Настоящая foreground service и её partial wake lock наблюдались через Android.
Отдельное тестовое приложение временно добавлено в Doze whitelist, имитация
зарядки отключена, экран выключен, deep idle принудительно переведён в `IDLE`.
Во время измерительного окна телефон не опрашивался.

За **40 501 мс** приложение в lifecycle `paused` выполнило **81** срабатывание
500-мс таймера из ожидаемых **81**. Процесс оставался жив, deep idle был `IDLE`
до и после окна. По команде служба прекратила foreground-работу.

Это проверка службы/таймера с разрешённой фоновой работой. **Узел Veil не
запускался, доставка сообщений и звонков в Doze не проверялась.** Этот результат
не закрывает исходную неопределённую жалобу о «засыпании», часы/сутки работы,
vendor task killers, нехватку памяти или принудительный force-stop пользователем.
Гонки уведомлений подтверждены независимо; их связь с той полевой жалобой
не установлена.

## Сборка, очистка и границы

После теста foreground service остановлена, OS-vault записи и фиктивные
контейнеры удалены, тестовый пакет удалён, его процесс отсутствует. ADB forward
снят. Временный whitelist удалён, forced idle и имитация батареи сброшены,
экран возвращён во включённое состояние. SHA-256 и пути установленного исходного
APK совпали до и после теста. Пользовательское приложение этим тестом не запускалось.

Временная подмена application ID для сборки стенда восстановлена побайтно.
Обычный APK заново собран с явным `--target lib/main.dart` и основным application
ID, чтобы тестовый APK не остался стандартным выходным артефактом. Сборки
наблюдались с проверкой, что внешний build-диск остаётся отдельной файловой
системой; отключения не было. Flutter использовал `TMPDIR=/private/tmp/`.

На телефон обычный новый APK не устанавливался. Windows 10, живую речь,
полную multi-device матрицу и релизные артефакты этот цикл не квалифицирует.
Push, релиз и обновление серверов не выполнялись. Исходный незакоммиченный
каталог `multi-device-2026-10-17` сохранён.

[summary.json](summary.json) содержит только результаты, счётчики, относительное
время и хеши ПО. Сырые журналы, runtime-пути, адреса, ключи, пароли и идентификаторы
устройств остаются вне репозитория.
