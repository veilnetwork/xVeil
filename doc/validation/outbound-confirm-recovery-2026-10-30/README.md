# Исходящий circuit: готовая альтернатива без ожидания первого кандидата

SDK `08b67a6e` исправляет последовательную подготовку/confirmation исходящих
circuit-кандидатов. Это прямое продолжение [физического наблюдения](../stale-rto-recovery-2026-10-30/README.md):
после восстановления сессии первый кандидат ждал 10019 мс, следующий был готов
через 87 мс после его таймаута. Само отсутствие ACK первого кандидата этим ещё
не объяснено.

## Изменение

Теперь на одно открытие пула одновременно готовятся и подтверждаются не более
двух кандидатов.
Первый подтверждённый результат сразу проходит существующий publisher и становится
доступным селектору; молчащий предыдущий не удерживает его за своим timeout.
Ранжирование определяет порядок запуска, а готовность — порядок публикации
среди уже разрешённых ad-кандидатов. Проверки подписи/свежести и допустимые старые
ads не менялись. Общие DHT pending/route/pool limits и admission не повышались.

По достижении target оставшиеся попытки отменяются; неопубликованный кандидат
владеет отдельным guard до окончания publication. Guard сохраняется и в уже
завершённом, но ещё не потреблённом результате scheduler. Для shared file pool
оставлен прежний receive grace, для isolated producer — существующая ownership
политика. Обычная публикация и live-stream accounting не откатываются старым
snapshot. Warm reuse сохраняет исходный circuit и его счётчики.

После confirmation дополнительно проверяется именно TX-регистрация кандидата,
а не просто наличие какой-либо сессии того же first hop. Потеря регистрации
не карантинит свежую замену. Receiver binding, ratchet, ACL, wire и relay
приоритеты не менялись. Timeout в 10 с сохранён; если оба текущих кандидата
молчат, следующий всё ещё ждёт освобождения одного из двух слотов. Исправление
не обещает мгновенного открытия любого пути.

## Регрессионные проверки

Сначала production-цикл был выделен с последовательным scheduler. Два новых
теста дали 0 passed / 2 failed: закрытый gate первого кандидата не позволял
получить готовый второй; активировалась одна попытка вместо двух. После
bounded concurrency готовый второй доступен до открытия gate первого.
Пороги wall-clock не используются.

Отдельно проверены потолок одновременной работы и отмена futures без spawned
хвоста. Реальная фикстура NodeServices/stream_recv проверяет receive grace,
последующее удаление только неопубликованного sink и сохранение опубликованного.
При проверке границы grace учтён отдельный turn миллисекундного timer wheel Tokio:
сам advance не гарантирует выполнения всех готовых задач. Промежуточный сбой
этой фикстуры не объявляется дефектом протокола.

Clippy `--all-targets -D warnings`, rustfmt edition 2024 и diff-check чистые.
Фикстуры с test-low-difficulty не входят в физические production-библиотеки.

Полный итоговый набор: 395 FFI-тестов прошли, 11 ignored учтены отдельно;
дочерняя изолированная проверка прошла.

## Физическая проверка Mac ↔ Blackview

Оба конца — native SDK `08b67a6e`, production-фичи
`node-embedded,production-seeds,packet-tunnel`, без circuit-trace/test hooks.
Замороженный frontend `48a2d436`, Dart plugin SDK `ea7e8388`; native-only
квалификация. Существующие QA-личности, контакт P2P deny, circuit bulk backend.
Wi-Fi/data исходно включены, default route/провайдер не установлен. Реле не менялись.

| Направление | Размер | Radio off | Загрузка | Первая проверенная часть | Максимальный интервал проверенных частей | SHA-256 |
|---|---:|---:|---:|---:|---:|---|
| Mac → Android | 32 МиБ + 251 Б | 9,058 с | 80,818 с | 3,461 с | 16,958 с | Совпал |
| Android → Mac | 32 МиБ + 251 Б | 8,268 с | 84,332 с | 4,556 с | 20,407 с | Совпал |

Обе передачи продолжились автоматически **в прежних stream**. На каждом конце
наблюдались два stream за всю серию — по одному на файл. В полных API devlogs
обоих концов (dropped=0) нет payload-idle и stream-pull attempt failure.
В прошлой серии на `ed902b70` получатели по одному разу достигали payload-idle
и переоткрывали stream. Это наблюдение новой серии, не доказательство общего
устранения всех причин пользовательского «33%».

### Что именно измерено как пауза

В новой серии на Android не было стоячего prefix с OO; при намеренном обрыве
наблюдался 14,168-с plateau без OO. На Mac receive-prefix с OO стоял 14,538 с.
Эти интервалы включают отключённую сеть, а не только ожидание при готовом пути.
RTO достигал 10 с, consecutive RTO — 4; локальный blocked-cell age телефона до
15,689 с также включает отключение radio. Зарегистрированы два удаления старых
handle на Android, NoRelays/no-progress quarantine не наблюдались.

По трём ADB-пробам до/после серии разброс оценки смещения часов около ±38 мс,
максимальный RTT пробы 64,863 мс. Это калибровка наблюдений, не гарантия отсутствия
промежуточного скачка часов/очереди логирования. Driver-срезы примерно через 0,5 с.

| Направление | Возврат radio → первый новый session.open телефона | Возобновление payload относительно этого session.open по срезам |
|---|---:|---:|
| Mac → Android | около 5,336 с | примерно +0,7…+1,3 с |
| Android → Mac | около 7,455 с | около момента session.open: окно −0,2…+0,35 с |

Во второй строке интервал наблюдений пересекает момент открытия сессии —
строгий порядок событий по нему не устанавливается. В обеих строках речь
о первом новом transport session, не о доказанном первом хопе каждой клетки.
Большой дополнительной паузы после него в этих срезах нет. Команда включения
radio не означает, что ОС уже дала маршрут; в 5–7,5 с входят сеть ОС, dial и
handshake, их доли пока не разделены.

Лог первого **нового построения** outbound circuit после session.open во втором
случае появляется лишь через 38,091 с, когда payload уже давно продвигается.
Он не является метрикой первой доступности пути: reuse и продолжающий работать
существующий stream не обязаны печатать `outbound circuit ready`. Нельзя объявлять
эти 38 с блокировкой восстановления. В этой серии confirmation-timeout исходящих
кандидатов вообще не наблюдался; сам отказ первого кандидата прежнего прогона
не повторён и причинно не объяснён.

Нет A/B/A и фиксированных маршрутов. Разность общих времён с прошлым SDK не
приписывается scheduler. Строгое подтверждение исправления head-of-line механизма
даёт gate-тест с прежним последовательным production scheduler; физика подтверждает
целостность и продолжение без нового stream только в этих двух сценариях.

## Границы результата и возврат стенда

Требуют дальнейшей проверки: повторения на исходном проблемном провайдере,
параллельный bulk, mixed-версии, длительный offline и multi-device матрица.
Причина старого 120-с предложения и неожиданный звонок около 25 с не исследовались
этим прогоном. Первоначальная самопроизвольная остановка «33%» не атрибутирована.
Сокращением payload-idle симптом не скрывался: прежний timeout сохранён.

Сборки из чистого SDK head; mount внешней ФС проверен до/во время Cargo.
Подтверждены SHA упакованного native и APK, Mac mapped library после codesign.
Исходный QA APK восстановлен по хешу, preferences и launcher metadata побайтно.
Настройки контакта/анонимности, radio, debug property и whitelist возвращены;
QA/Mac/logcat/forward закрыты. Основное приложение не менялось. Активный
QA-контейнер продвинул ratchet и не откатывался. Синтетика удалена после SHA.
Удалены прежние собственные копии стендовых пакетов (около 1 ГБ), сохранены
native-библиотеки, proof/logs и одна актуальная копия исходного rollback APK.

Отчёт не содержит raw-логов, IDs, адресов, ключей, пользовательских путей или
абсолютных timestamps. Коммиты локальные, без подписи, push и релиза.
