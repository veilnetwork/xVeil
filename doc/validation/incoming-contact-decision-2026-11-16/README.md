# Входящие запросы не отменяют решение о контакте

Продолжение [проверки исходящих действий](../contact-request-decision-2026-11-16/README.md).
База `b4562212`. Локальное исправление, без push/релиза и новых native-сборок.

## Подтверждённый механизм

`handleRequestOrReconnect` получал снимок ContactStatus, затем ожидал
асинхронную проверку собственного адреса. За это время пользователь мог
принять или заблокировать контакт. Продолжение использовало старый снимок:

- Из unknown/pendingOutgoing оно перезаписывало решение в pendingIncoming.
- Из pendingIncoming оно могло записать старое приветствие после нового
  решения, хотя обработчик уже принятого контакта такое приветствие игнорирует.
- Из accepted оно могло создать новый durable accept после блокировки.

На базе воспроизведены **28 assertion-red / 4 passed** в матрице из 32 случаев:
request/reconnect × четыре начальных состояния × accept/block × ordinary/native
HVS. Начальные состояния: отсутствующий контакт, pendingOutgoing,
pendingIncoming, accepted. Gate удерживает реальный async self-check после
чтения статуса; решение полностью сохраняется до продолжения запроса.
Это допустимый порядок завершения futures, а не измерение длительности IPC
или доказательство такого interleaving на устройстве пользователя.

## Исправление

Общий `prepareContactRequest` теперь готовит обе стороны запроса под contact
write lock. Статус читается внутри той же сериализации, что accept/block;
текущие решения сохраняются, одинаковое pending не переписывается.

Входящий обработчик выбирает действие по возвращённому текущему статусу:
accepted сохраняет durable повтор ответа, blocked отказывается от обработки,
pending сохраняет обычное приветствие. Начальный снимок остаётся только
подсказкой для подавления повторного уведомления об undecided request.
Новый входящий запрос не является автоматическим согласием на переписку.

Обработчик возвращает признак выполненной обработки. Deferred request ACK
разрешён только после успеха, как и ранее — после durable admission ответа.
Отказ/закрытие сообщает carrier о локальном неприменении, чтобы не удалять
нужную другим собственным устройствам копию. Mailbox собственных устройств,
wire, подписи, ratchet и правила блокировки не менялись.

## Проверки

32 случая матрицы дополнены реальным приёмом сообщения и обычной отправкой
через MessagingService после гонки: accepted разрешает, blocked сохраняет
сообщение в существующей очереди held и не показывает его в истории.
Решение повторно читается после cold-open контейнера.

Ещё восемь lifecycle-контролей проверяют закрытие сервиса во время self-check:
request/reconnect × accepted/pendingIncoming × ordinary/native HVS. Нет новых
сообщений, Outbox или ACK; carrier получает отказ. Они поймали промежуточную
ошибку собственной правки — ранний return при закрытии без явного отказа.
Эти восемь падений не приписываются исходному релизу.

Финальная expanded-серия с diagnostics: **316 passed, 0 skipped**, 23 файла.
Включены исходящий stale action, атомарный accept, consent/reconnect,
ACK/admission, собственные решения/настройки, уведомления, tray, camera state
и chat consent UI. После исправления только lint-скобок и комментария
повторно прошли **40 focused cases**, без skips. Analyzer пяти runtime-файлов
и всего `test` чистый; diff check чистый.

Использована та же ранее проверенная HVS-библиотека, её SHA сверена с прежним
provenance; все 49 UniFFI checksum entries соответствуют текущим bindings.
Native/Rust не собирались. Transport синтетический, native касается настоящего
worker/storage, а не сквозного Windows↔Android звонка. Первый compile failure
fixture с отсутствующим импортом worker opener не считается воспроизведением;
зачтённая baseline-матрица завершилась именно assertion failures.

## Границы

Это не доказанная причина исходной односторонней переписки. Встречные запросы
от двух пользователей, полная multi-device conflict-матрица и сетевые отказы
требуют отдельных проверок. Камера Windows 10 и видимость настоящего Windows
toast этим раундом не проверялись и не объявляются исправленными.

Проверки выполнялись без запуска пользовательских окон, активации приложений
или управления клавиатурой/мышью. Реальное приложение пользователя не тронуто;
физический телефон, Windows и production-сиды в этом раунде не использовались.
