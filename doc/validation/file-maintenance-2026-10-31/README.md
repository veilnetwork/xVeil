# Файловая очередь при close/erase и разложение save

База приложения `402dd4f8`, SDK `c46d94db` без изменений. При разборе storage
gate найдена и исправлена отдельная гонка: закрытие и стирание не дожидались
принятых файловых операций. Медленная доставка остаётся открытой; этот фикс
не объявляется причиной или решением прежних сетевых пауз.

## Подтверждённая гонка

`storeFile`, `storeFilePiece` и `deleteStoredFile` пользовались `_fileGate`,
а `close`/`eraseSpace` ждали только conversation/ratchet IO. На управляемом
тесте удержана первая файловая операция, за ней приняты часть другого файла
и удаление. Затем выполнены close/open другого хранилища:

- ожидавшая часть записалась уже в новую личность;
- ожидавшее удаление могло обратиться к одноимённому файлу новой личности;
- в сценарии erase незавершённая запись восстановила файл после стирания.

Три исходных теста были красными на базе. Это проверка storage-примитива с
настоящей очередью и управляемым backend, не наблюдение пользовательской утечки
в GUI. В проекте этот lifecycle используется: `AppController.switchIdentity`
и roster-операции закрывают и вновь открывают тот же storage adapter;
`deleteIdentity` вызывает `eraseSpace`. Полный GUI-сценарий с активной сетевой
загрузкой во время переключения этим раундом не квалифицирован.

Теперь close/erase последовательно завершают conversation, ratchet и файловый
IO. Новые файловые операции отвергаются с начала обслуживания; ранее принятые
заканчиваются в прежнем space. Каждый queued job дополнительно привязан к
объекту storage session. Ошибка одной записи не отравляет очередь, а ошибка
erase освобождает fence для восстановления. Обычные scan и файловые операции
по-прежнему имеют отдельные gates; формат, wire и native ABI не менялись.

Граница фикса — операции, уже принятые файловой очередью, и новые вызовы во
время close/erase. Проверки владельца/эпохи у поздних callbacks после открытия
новой личности остаются обязанностью их существующих сервисных guards.

## Проверки

- Пять новых unit-сценариев: close/reopen с queued write/piece/delete,
  erase без восстановления файлов, отказ публикации перед close, queued
  on-disk piece с последующим удалением ciphertext, восстановление после
  ошибки erase. Первоначальный green-run не зачтён из-за неверного sync-reader
  streamed-части в тесте; helper заменён на поддерживающий её async-reader.
- Два native worker-backed теста: реальные контейнеры, публикация/часть/удаление
  до close/erase, отказ поздней записи и повторное native-открытие A. Данные
  остаются только в A либо отсутствуют после erase; исходный файл B сохранён.
  Использованы два контейнера-фикстуры, не пользовательский master-roster.
- 513 scoped storage/file/group/device-sync проверок, включая новые unit и
  native atomic publication, прошли; ещё 94 проверки identity/app-controller/
  on-disk прошли. Отдельные два worker-backed теста прошли. Analyzer чист.
- Не тестировались долгий offline, revoke/split-brain и полная multi-device
  матрица. Незакрытые старые жалобы автоматически не повышаются до исправленных.

## Физические замеры на Android

Три QA-устройства: A/Mac и B/Android одной личности, C/Mac другой. B offline,
A создаёт восемь сообщений, C ещё два; после получения всех десяти A/C
выключен C и возвращён B. Все **10/10** появляются на B при online A до
возвращения C, с одинаковыми ID/порядком и без дублей. Первое полное наблюдение
через **63,876 с**, опрос примерно раз в 10 с. Это не пятиминутный сценарий
со 100 сообщениями, не A/B скорости и не восстановление без A/C.

QA-копия вне репозитория разделила file gate, подготовку, metadata/prior reads
и прямые commit-вызовы `AsyncFileStore.storeFile`. За C-offline окно:
90 операций, 29 записей, **61 byte-identical no-op по 2 байта**, ошибок 0,
ring dropped=0. Источник этих 61 операций не атрибутирован: `other` не называет
файл/вызывающий сервис. Они не сделали commit, но читали данные для сравнения.

| Тип | Операций | Прямых commit | Commit median / max, мс | Gate median / max, мс |
|---|---:|---:|---:|---:|
| Group header | 14 | 28 | 45,591 / 89,946 | 0,083 / 119,135 |
| Group segment | 15 | 15 | 76,712 / 115,042 | 0,043 / 43,787 |
| Other, без изменений | 61 | 0 | — | 0,046 / 255,954 |

Commit здесь — ожидание worker RPC, включая scheduling/IPC, native работу и
возврат на main isolate, **не чистое время fsync**. Подсчитаны прямые вызовы
этого метода, не все commit приложения, ratchet или возможных GC helpers.
Чтение прежнего содержимого: header median/max 41,906/244,900 мс;
other 37,401/519,107 мс. В 13 завершённых ingest стадия save имела
median/max **765,467/1358,929 мс**; вложенные интервалы не складываются.

Постоянная многосекундная блокировка файлового gate в этой серии не наблюдалась.
Прежние пики 3,32 с относятся к другим сериям и этим не атрибутированы.
Результат сужает поиск, но не доказывает исправления всей задержки. Следующий
участок — ожидания до ingest, control Outbox/retry и общие worker RPC;
также требуется определить источник 61 повторного no-op.

## Происхождение и уборка

Android profile/AOT содержит текущий product-код и только задекларированные
QA-таймеры в трёх внешних копиях файлов. Продукт не содержит probes. Native
библиотеки, signer и 16-КиБ alignment проверены; Rust не пересобирался.
Mac использует прежний QA Runner/Dart на базе с тем же native SDK, поэтому
эта серия не квалифицирует новый Mac release или GUI-переключение личности.
Flutter outputs на внешней ФС с mount-watchdog.

Все запущенные QA-приложения закрыты, процессы/ports/свой forward проверены,
runtime-каталоги удалены. Исходный QA APK восстановлен по SHA, данные профилей
сохранены, основное Android-приложение не менялось. Лишние промежуточные APK
удалены. После проверок удалён собственный внешний Flutter output и дубли
native inputs; проверенные candidate/rollback APK и evidence сохранены.
В публичном summary только агрегаты и source/artifact SHA; нет
личностей, адресов, ключей, содержимого переписки или пользовательских путей.
