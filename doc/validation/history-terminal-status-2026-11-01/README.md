# Завершённая история становилась очередью повторных отправок — 2026-11-01

Разбор прошлого межпроцессного прогона (`1cecdb78`) подтвердил лишнюю работу:
после связывания B повторно отправлял старые исходящие сообщения A→C.
За полный прогон в журнале B — **9640 попыток по 1968 разным message ID**.
Для всех 1968 на A раньше зарегистрирован receipt от C: sender-side
`[timeline]: delivered` предшествует первому `[timeline]: retry` B по тем же ID.
Это журнал приёма ACK перед сохранением статуса, **не самостоятельное
доказательство успешного fsync каждого статуса A** и не счётчик реально
доставленных сетевых пакетов.

Механизм подтверждён кодом и тестом: `deviceMirrorOf` не переносил состояние
доставки, публичный `applyMirroredMessage` не передавал его уже существовавшему
внутреннему applier. Новый исходящий mirror сохранялся как `sent`, и обычный
message retry считал его незавершённой отправкой. Отдельные `msgStatus` дают
обновления в живой работе, но их bounded-журнал не заменяет начальное состояние
при передаче большой старой истории.

Прежнее наблюдение «пустой Outbox» относится к `/outbox_depth`: этот hook
читает durable **control frames**. Обычные сообщения повторяются из message
log другой подсистемой, поэтому нулевой ответ hook не означал отсутствия
повторных отправок. Судьба конкретной старой порции из 25 строк по сохранённым
логам не установлена; этот раунд исправляет выявленный источник лишней работы,
не объявляет его доказанной единственной причиной всех ожиданий.

## Исправление

Текстовые и файловые mirrors исходящей истории несут известное конечное
состояние `delivered` или `failed`. Оно включено в подписанный body и проверяется
штатным applier авторизованной device-group. Неверное/неподдерживаемое значение
не угадывается. Начальная запись сразу содержит этот статус: даже retry,
попавший между видимостью append и завершением его Future, не начинает старую
отправку. Незавершённые `sent`/`sending` сохраняют прежнюю возможность retry
другим устройством; повторы sibling-проекций целиком не отключались.

Если старый mirror уже находится в storage как `sent`, подтверждённая доставка
обновляет только статус исходящего сообщения. Текст, timestamp, порядок и
provenance остаются прежними. Удалённая строка не восстанавливается, входящая
не становится исходящей; старый failed-snapshot не отменяет новую попытку.
Поздние изменения по-прежнему идут отдельными `msgStatus`, timestamp сообщения
ради смены статуса не меняется.

При равных provenance/time fold теперь предпочитает завершённую копию;
`delivered` выше `failed`, а тот выше начального mirror без конечного статуса.
Это общий компонент детерминированного порядка, без попарных исключений;
проверены транзитивность и свёртка в разных порядках. Авторитет оригинальной
позиции остаётся выше статуса, сравнение времени сохранено. Полноценная
compaction и новый экземпляр GroupService сохранили завершённый mirror.

## Проверка

До правки два новых контроля упали: codec терял `delivered`, а fold оставлял
неправильного победителя среди sent/failed/delivered. Незавершённая отправка
прошла как отрицательный контроль. На кандидате связанный набор —
**521 passed, 3 skipped**, дополнительный compaction-кейс — **1 passed**.
Analyzer изменённых файлов чист; пропуски не считаются прохождением.

Межпроцессный A/B/C сценарий усилен: перед связыванием B нужны все 2000
**сохранённых** delivered-статусов A; после появления полной истории на B
сверяются те же статусы и отсутствие попыток повторить эти ID в timeline.
Наличие самого timeline проверяется отдельно. Затем прежняя проверка:
B offline минимум пять минут, ещё 100 сообщений, C выключен до запуска B,
проверка всех ID/порядка до и после возвращения C.

Native SDK/CLI/HV побитово совпадают с предыдущим прогоном; runtime Dart
зафиксирован на время теста. Публичные сиды/discovery выключены, три локальных
реле, прямые соединения разрешены. Каждый из A/B/C — отдельный OS-процесс с
реальным native-узлом и worker-backed контейнером на одном Mac. Это host/JIT,
не Android/AOT и не строгая серия A/B/A.

Подготовка кандидата прошла: исходные 2000 сообщений имеют `delivered` на A
до связывания B. Все 2000 появились на B с тем же статусом и теми же
ID/порядком; первое полное наблюдение — **77 949 мс** после завершения link.
Попыток повторно отправить эти ID на B — **0**. В предыдущем прогоне было
237 149 мс и описанные выше повторы; исходная подготовка отличается дополнительным
ожиданием всех durable-статусов A, поэтому это наблюдения двух прогонов,
не доказанная оценка устойчивого ускорения на телефоне.

**Offline-проверка PASS:** после минимум пяти реальных минут offline B вернулся
при выключенном C. Все 100 новых исходящих копий присутствуют через **10 316 мс
от ready**, или **19 596 мс от запуска**. Ready занял 9279 мс. Наблюдения:
0 → 75 → 100; это опрос примерно раз в пять секунд, не точное время доставки
последнего сообщения. Прежние 2000 строк сохранились. После возврата C все
2100 проверяемых ID/порядок совпали на A/B/C; дублей не наблюдалось. Один
native test passed, полное время с подготовкой/teardown — **601,408 с**.

В журнале **всего** прогона нет попыток повторить старые 2000 ID. Однако
обнаружен отдельный активный остаток: **375 попыток по 96 из новых 100 ID**.
Для всех 96 на A есть более ранний receipt; это live-mirrors, созданные в
момент отправки, а не выдача старой завершённой истории. Значит, корректность
ID/порядка прошла, но перенос их delivery-state ещё требует исправления.
Причина пока не доказана; проверяются порядок применения отдельных msgStatus
и mirror, а также восстановление пропущенного статуса. Ноль для первоначальных
2000 не распространяется на новые 100.

Позднейший [раунд порядка прихода](../mirror-status-arrival-2026-11-01/README.md)
подтвердил и исправил потерю `delivered` до видимости mirror/append. В новой
native-серии все 100 ID **и статусов** сошлись при offline C; повторов этих
live-копий не было. Это результат следующего исправления, цифры текущего
исторического прогона (375/96) остаются неизменными.

После прогона независимо проверены 10 собственных PIDs/групп и девять портов:
процессов/слушателей нет, runtime-каталог с контейнерами удалён. UI Poco проверен
только чтением: ADB авторизован, видны пароль и кнопка разблокировки. Приватный
UI-dump удалён; пароль не подбирался. Звонки Poco→Windows/NETCALL-01 этим
циклом не проверены и остаются активными. Агрегаты — [summary.json](summary.json).

Без push/релиза. Пользовательские установки и production-сиды не менялись.
В публичных результатах нет message/device/identity ID, адресов, ключей,
частных путей и сырых журналов.
