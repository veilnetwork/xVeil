# Изоляция и публикация master roster

Агрегаты: [summary.json](summary.json).

Статус: **подтверждено на публичной storage-границе и исправлено**.
Это список скрытых личностей с их opaque SpaceKeys, не список устройств
multi-device. Он остаётся внутри зашифрованного контейнера: небольшие списки
в settings, большие — в файловой части того же volume. Внешний plaintext
файл или mailbox не добавлялись.

## Подтверждённые механизмы

| Случай | Исправление |
|---|---|
| Приостановленное сохранение попадало в следующий открытый контейнер; старое чтение возвращало его список | Writer закреплён за исходным store, reader за captured session/epoch |
| Close/erase обгоняли принятую запись; поздняя запись могла вернуть данные | Вся операция участвует в существующем file writer fence; новые producer во время maintenance отклоняются |
| Несколько одинаковых сохранений создавали повторные транзакции | Сравнение и публикация сериализованы на writer gate; fresh burst из 16 вызовов даёт одну транзакцию |
| При уменьшении списка сохранение сообщало успех, но старый файл продолжал скрывать новый settings-список | Новый setting и удаление старого файла/chunks публикуются одной транзакцией; отказ сохраняет прежний список |
| Повреждённый/неполный файл позволял перезаписать список, опираясь на устаревшую маленькую копию | Объявленный нечитаемый файл не считается отсутствующим; writer отказывает без изменения старых данных |
| Повтор уже опубликованного большого списка навсегда пропускал очистку старой settings-копии | Идемпотентный повтор также пробует завершить cleanup, без повторной записи частей файла |

Приоритет действующего файла сохранён. Необязательная очистка маленькой
копии после его durable publication остаётся best-effort, как предусмотрено
проектом: её отказ не отменяет успешно сохранённый большой список. Ошибка
чтения такой тени не скрывает действующий файл и не блокирует его обновление.
Ошибка чтения единственной основной settings-копии остаётся ошибкой,
не превращается в «контейнер без master roster».

Reader не удерживает writer или другие чтения. Если публикация произошла
во время snapshot, проверка локальной revision повторяет чтение. Закрытие,
смена пространства и erase проверяются отдельной session/epoch-границей.
Данные файла, записанные до отказа финальной публикации, не делают новую
версию видимой: прежний roster остаётся доступен до durable publication.

Legacy empty-file marker, настройки имён/anonymous и формат SpaceKeys
сохранены. Неожиданный external-tier descriptor именно этого приватного файла
обрабатывается fail-closed: штатный `saveRoster` создаёт его только in-volume.
Файловая подсистема обычных медиа не менялась.

## Доказательства

Один и тот же suite запускается с in-memory KV и настоящим HVS. Управляемые
Futures и виртуальные часы задают interleavings без wall-time порогов.

| Режим | Исходный файл `bff45255` | Candidate |
|---|---|---|
| In-memory | 17 assertion-red / 11 passed / 1 native-only skipped | 28 passed / 1 skipped |
| Настоящий зашифрованный HVS | 17 assertion-red / 12 passed | 29 passed / 0 skipped |

Числа относятся к проверкам, не к числу независимых уязвимостей. Baseline
каждый раз восстановлен из точного исходного файла, candidate возвращён
побайтно. Начальная ошибка имени поля в fixture, давшая compile failure,
не считалась красным воспроизведением.

Связанные storage/history/metadata suites: **149 passed / 1 skipped**,
включая 28 in-memory проверок выше. Native-набор отдельно выполняет и
пропущенный crypto-сценарий. Analyzer и diff checks чисты.

Проверены оба обычных размера — 1 и 24 строки, ошибки публикации и cleanup,
close/reopen/erase, замороженные входные keys, отсутствие блокировки свежих
чтений старым ответом. Стресс с 2400 синтетическими строками проходит несколько
data commits: перед инъекцией отказа подтверждено наличие durable chunks,
после отказа доступен прежний список; повтор и уменьшение также проходят.
Это не 2400 реальных личностей или устройств.

Отдельный crypto-сценарий создаёт настоящий child и master в одном контейнере:
promote списка в файл → close/reopen → shrink → fresh open → unlock child
сохранённым SpaceKeys → проверка его профиля. Дополнительные строки списка
синтетические; реальное открытие проверено для одного child.

Первые варианты candidate сами дали шесть assertion-red: очередь чтения
задерживала новый session/writer, а broad catch скрывал primary IO failure
и делал доступность действующего файла зависимой от старой тени. Эти варианты
не квалифицированы; окончательный revision-based reader проходит контроли.
