# Отзыв устройства: прикладной входящий допуск после crash

## Подтверждено

После исправления исходящей адресации в `819eae75` тот же author-crash
сценарий выявил соседний путь: A уже публикует сохранённый tombstone B и
исключает B из `addressableOwnDevices()`, но `isMyDevice(B)` и
`isMyDeviceOrMaster(B)` всё ещё отвечают true. Их источник — старый
валидный control journal и его положительный membership cache.

Это **подтверждённое неправильное решение прикладного допуска**. Успешный
сетевой обход native proof/floor, получение нового plaintext или аудио этим
контролем не доказаны. Входящий транспорт сохраняет свои отдельные барьеры.

## Изменение

Membership cache хранит только состав и sovereign-владельца этого состава.
Положительный ответ теперь отдельно сверяется с явно отозванными устройствами
в свежем сохранённом документе. Отрицательные ответы для посторонних peers не
запускают чтение документа. Запасной путь через объявленное главное устройство
применяет ту же проверку; старое объявление больше не возвращает ему допуск.
Логический адрес личности сохраняет прежнюю семантику.

Документ читается strict-режимом предыдущего исправления, верификация и
identity scope остаются в SDK. Не кешируется положительное решение об
отсутствии отзыва: утраченный ответ записи не обязан сопровождаться изменением
group-control cache. Новый await сохраняет проверки generation/dispose; после
изменения состава решение повторяется, после shutdown возвращается отказ.
Реализация проверки разделяется с исходящей адресацией.

Журнал и история не переписываются, неизвестные устройства не получают новых
прав. Native source, wire и mailbox не менялись. Повторно использована точная
qualified SDK `26c0a8a5` и storage из предыдущего цикла; Rust-тесты заново
**не запускались и не прибавлены** к итогам этого цикла.

## Проверка

- На исходном коде: два unit assertion-red (положительный membership cache и
  отдельное объявление главного устройства) и полный OS-process assertion-red
  после настоящего durable revoke / SIGKILL / cold-open. Прежний outgoing
  фильтр в этом контроле уже работал — B не был адресатом, но ещё допускался.
- Четыре unit-контроля прошли: обе ветки, ошибка чтения/верификации и
  восстановление чтения, а также group revoke и shutdown во время удержанного
  чтения. Gate/completer проверяет порядок без порогов времени.
- **550 group tests passed / 0 skipped**, с точными native library SHA;
  focused analyze трёх изменённых файлов — без замечаний.
- Полный A/B/C crash-сценарий прошёл. До отзыва проверены true для адресации,
  membership и трёх ingress-вызовов, включая реальные callbacks MessagingService
  и CallService. Null wiring не считается отказом — это ошибка самого стенда.
  После crash все четыре admission-ответа false при неизменённом старом roster.
  Сохранены точная перепубликация документа, разрешённые сообщения и звонок,
  отрицательные наблюдения входящего B→C и новых C→семейство offer/reply.
- Исходники/native bytes не менялись в процессе E2E. Все **40** отслеженных
  процессов завершились; **28** портов освобождены. Повторный независимый
  аудит PID + start stamp чист. [Машинная сводка](summary.json).

Полный сценарий доказывает реальные callback decisions и обычный сетевой
positive/negative контроль; callback probe не выдаётся за новый malicious
packet replay. Это выбранная crash/revoke граница на одном Mac, не вся matrix,
Android/AOT или произвольный power loss. Производительность новой проверки не
объявляется улучшенной: у положительного sovereign-member появляется свежее
чтение документа. Вся прежняя история остаётся источником состава.

Окна, ввод, пользовательские профили и production не затрагивались. Poco
виден, но QA-пакет не установлен; подтверждение повторной установки после
отказа Android ожидается. NETCALL-01 остаётся открыт. Push/релиза нет.
