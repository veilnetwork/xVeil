# Открытые случаи — обновлено 2026-10-29

Это список незакрытых случаев и ограничений проверки, а не утверждение, что
каждая прежняя жалоба воспроизводится в текущей сборке.

В локальной ветке устранён подтверждённый риск повторного использования ключа
после параллельных отправок и аварийного восстановления. Проверка резерва теперь
атомарна с расходованием ключа. [Механизм и проверки](../ratchet-publication-2026-10-29/README.md).
Исправление ещё не опубликовано; установленный пользовательский релиз его не
содержит.

| Случай | Текущий статус |
| --- | --- |
| Длительная доставка сообщений, подтверждений и синхронизации | Подтверждено. Устранены ожидания исходящего ACK внутри последовательной входящей обработки: [после сообщения](../post-receipt-queue-2026-10-28/README.md) и [после снимка группы](../group-receipt-queue-2026-10-29/README.md), а также [лишние повторные уплотнения журнала](../device-compaction-margin-2026-10-29/README.md). Закрыт [обход локального сохранения фоновым повтором и дозапросом](../outgoing-mirror-retry-2026-10-29/README.md). [Профиль CPU и A/B/A](../journal-hash-work-2026-10-29/README.md) подтвердили лишнее хеширование: три локальные записи занимают 6,19 с вместо 8,48/8,44 с, выигрыш около 27%. В последнем обычном шифрованном прогоне все 18 сообщений видны к 58,7 с, очередь частей синхронизации пуста к 75,4 с. Эти сетевые прогоны не являются контролируемым сравнением; ускорение доставки не доказано. Локальные записи всё ещё занимают секунды, декодирование сегментов и построение ключа проверки остаются заметными в CPU-профиле; остальные причины задержек ещё не устранены. |
| Самопроизвольное завершение звонка на телефоне примерно через 25 с | Причина не доказана. Пользователь не трогал телефон; прежняя классификация как ручного завершения отменена. Последующие трёхминутные звонки и возврат P2P прошли, однако это не доказывает исправление исходного случая. [Диагностика завершения](../call-terminal-cause-2026-10-28/README.md), [возврат P2P](../relay-to-p2p-return-2026-10-28/README.md). |
| Длительные паузы/низкая скорость файлов через анонимный stream | Докачка после возврата источника проверена. Места ожидания данных/ACK и больших RTO ещё не установлены полностью; закрытие всех причин жалобы «зависло на 33%» не доказано. [Проверки восстановления и ограничения](../source-crash-file-resume-2026-10-26/README.md). |
| Windows 10 ↔ Android: односторонняя доставка, отсутствие звука; onboarding со старым контейнером | Незакрытые пользовательские репорты. Исправления общих путей и проверки Mac/Android не заменяют запуск проблемного сценария на Windows. Нельзя утверждать, что эти жалобы окончательно устранены. [Ограничения проверки](../report29-2026-10-24/README.md). |
| Тихий звук в наушниках и «засыпание» Android | Окончательное устранение не подтверждено. Счётчики RTP и автоматические прогоны не доказывают слышимую громкость; для «засыпания» нет точного воспроизводимого сценария. |
| Старые незавершённые групповые передачи и смешанные версии | Новые передачи с новым ACK исправлены. Старые уже осиротевшие хвосты автоматически не восстанавливаются; смешанные версии сохраняют прежнее ограничение при перезапуске получателя после частичного ACK. [Совместимость](../group-transfer-commit-ack-2026-10-28/README.md). |

Отдельно остаются незавершённые проверки: вся матрица из 63 сценариев, длительный
offline на часы/дни, физические revoke/split-brain/crash-сценарии и ручное
подтверждение записи сертификата системным диалогом macOS. Непройденная проверка
сама по себе не является обнаруженным дефектом.

Отсутствие источника исходящего сообщения при одновременном offline A и C и
отсутствии заранее сохранённой копии для B исключено из дефектов по согласованной
модели хранения. Возврат с реле на проверенный P2P и большие анонимные тексты
проверены отдельно и не перечислены как открытые дефекты.
