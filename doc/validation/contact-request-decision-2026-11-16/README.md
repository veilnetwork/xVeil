# Повторное действие запроса после принятия контакта

## Подтверждено

`sendRequest` безусловно записывал `pendingOutgoing`. Если старый callback
композера выполнялся после принятия контакта, он отменял локальный `accepted`.
Партнёр оставался принятым и мог отправлять сообщения, которые первая сторона
отклоняла своим consent gate. Обратное accept могло восстановить состояние,
но его доставка не должна быть условием сохранения уже принятого решения.
Та же запись могла отменить завершившуюся конкурентную блокировку.

Это воспроизведённые механизмы, а не доказанная причина пользовательской
жалобы: исходного журнала его рукопожатия нет. Одновременные встречные запросы
и полная сетевая матрица этим раундом не квалифицированы.

## Исправление

`Storage.prepareContactRequest` читает текущее отношение и готовит pending
под той же сериализацией, что принятие и блокировка. Завершённые решения
`accepted`/`blocked` сохраняются вместе с остальными полями контакта.

Для уже принятого контакта непустой текст проходит обычный `sendText`,
пустое действие ничего не записывает. Заблокированный контакт остаётся
заблокированным, отправка отказывается. Новый контакт по-прежнему проходит
обычный запрос и явное принятие. Нет автоматического согласия по входящему
запросу, новых wire-полей, изменений криптографии или mailbox своих устройств.

Булев результат `sendRequest` уточнён: для нового запроса он описывает relay
deposit, для уже принятого контакта — локальную отправку обычного сообщения;
ни один исход не доказывает удалённую доставку. Исправлен устаревший комментарий,
утверждавший, что неудачный deposit не оставляет durable повторов.

## Проверки

На исходных runtime-файлах получены **8 assertion-red**: четыре сценария
на обычном и worker/native HVS. Новый тест использует настоящие два
MessagingService: рукопожатие, повторное действие и по одному сообщению
в обе стороны без доставки промежуточного repair-accept. Дополнительно
проверены пустое действие и запрос, ожидающий завершения accept/block.
Конкурентные случаи используют явный gate, а не пороги времени; решения
повторно проверены после закрытия и открытия хранилища.

Финальная серия с diagnostics: **265 passed, 0 skipped**, 21 файл. Включены
consent, атомарное принятие, ACK/admission, reconnect, собственные контактные
решения, уведомления, tray, скрытие окна, camera state и приватность diagnostics.
Analyzer изменённых runtime-файлов и всего `test` чистый. Использована ранее
проверенная native HVS; её SHA совпал с сохранённым provenance, все 49 UniFFI
checksum entries соответствуют текущим bindings. Rust не пересобирался.

Ошибочные предварительные запуски не зачтены: fixture сначала не импортировала
`dart:async`; выбранная библиотека установленного приложения не содержала
prepared-compaction API текущих bindings; в одном expanded списке неверно
назван tray-test. Финальная серия использует исправленную fixture, подходящую
библиотеку и существующие файлы. Форматирование посторонних runtime-участков
исключено из diff.

## Два других сообщения пользователя

- **Windows 10, ожидание камеры:** жалоба открыта. На доступной Windows 11
  отдельный фоновый Media Foundation probe дал stage 0 / HRESULT 0 / 8
  непустых образцов. Его 15 allowlist-проверок и watchdog также прошли.
  Это не проверка преобразования в I420, кодирования, звонка или устройства
  пользователя. [Инструмент и ограничения](../windows-camera-probe-2026-11-13/README.md).
- **Входящий при закрытом окне:** существующее локальное исправление системного
  уведомления включено в регрессионную серию. Проверены hidden/background,
  close-to-tray, готовность backend и отсутствие автоматической активации
  окна до клика. Видимость реального Windows toast этим не доказана;
  опубликованный релиз исправленным не объявляется.
  [Предыдущий разбор](../desktop-incoming-call-alerts-2026-11-13/README.md).

## Без перехвата управления

Новые окна xVeil на macOS/Windows не запускались, мышь и клавиатура пользователя
не использовались. Реальная Windows проверялась отдельным консольным probe;
профили не открывались, медиа не записывалось. Временные исходники/бинарники
probe удалены; пользовательское приложение не запускалось. Первые неудачные
попытки передачи скрипта не считаются проверкой камеры. Существовавший
собственный headless Android stand остановлен с сохранением тестовых данных;
физический телефон не затронут. Изменения локальные, без push и релиза.
