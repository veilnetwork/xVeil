# Растущий источник истории: воспроизведение встречной выдачи

## Что установлено

Inventory сверяет доступный у источника набор только с первым `count` локальных
строк. Если у источника есть короткий старый префикс и известная поздняя строка,
а у клиента — весь архив, такое сравнение не узнаёт уже имеющийся sparse набор.
После первой обычной страницы клиент дополнительно отбрасывал все prefix hints,
даже когда их границы оставались впереди cursor. Источник, который догружался
параллельно, уже не мог подтвердить ставшую подходящей подсказку.

Управляемая проба: получатель B изначально хранит 1024 исходящих сообщения плюс
известный поздний tail; A начинается с 32 плюс tail, затем добавляет 64
последовательные строки при каждом новом page-запросе. Обратный pull отключён
для изоляции. Первый ответ не может подтвердить наименьшую 128-row подсказку,
второй уже может. Это детерминированная модель роста по запросам, а не временной
A/B стенд с одинаковым независимым сетевым расписанием.

Старый код сделал **17 запросов**. Прототип с сохранением подсказок — **2**,
повторно применив только 64 posts и tail после проверенного jump. Весь заранее
имевшийся набор B сохранил точные тела/status/позиции. Рост A прекращается с
окончанием запросов; эта проба не доказывает полную сходимость двух устройств.

Изначальная fixture на 512 строках уже позволяла подтвердить подсказку в первом
ответе и не воспроизводила нужный случай. После увеличения до 1024 старый код
дал 17 запросов. Финальный red-control расширенной проверки упал на отсутствии
подсказки во втором запросе; это assertion-red, не compile/timeout failure.
Verifier, ожидавший прежний порядок assertions, был исправлен отдельно.

## Проверки прототипа

Пять новых сценариев прошли: стабильные данные, новое локальное редактирование,
новое редактирование на источнике, revoke во время свежей проверки и отказ
сохранить prefix cursor. Изменившийся локальный snapshot вызывает fallback от
старого cursor, source mismatch не подтверждает jump, revoke/отказ commit
оставляют первый durable cursor неизменным. Query budget 1500 байт сохранён.

Прототип прошёл **207 related / 0 skipped** с 16 native HVS; затем вместе с
hook/cache правкой — **233 / 0 skipped**, analyzer чист. Пять новых проб и
само простое удержание подсказок **не оставлены в product tree**; сохранены
приватно для следующего шага. Итоговый cache-only набор: **228 passed / 0 skipped**, analyzer чист.

## Native серия 10 000

Три функциональных запуска: четыре Mac/JIT процесса A/B/E одной личности,
C — другой, три изолированных Core, одинаковые native CLI/FFI/HVS. Все 10000
архивных плюс одна прежняя строка совпали по ID/телам/delivered/canonical order
и сохранились после cold boot при offline источниках. Нет дублей/пропусков,
оба проверяемых cursor завершены. Frozen inputs, OS mappings/SHA проверены.

| Наблюдение | Parent A₁ | Прототип | Parent A₂ |
|---|---:|---:|---:|
| Page-запросы, принятые B для встречной выдачи | 24 | 18 | 157 |
| Соответствующие полные ответы, полученные A | 24 | 18 | 157 |
| Запросы из этого набора с prefix hints | 1 | 18 | 1 |
| Принятые application-frame bytes ответов | 799300 | 607132 | 5425560 |

Запросы связаны с ответами по private IDs; все индексы частей получены,
close-footers dropped=0. Байты относятся к расшифрованным application frames,
не к полному трафику circuit/TCP/UDP. IDs/порты/payloads не экспортируются.
В прототипе предложения действительно повторяются после первой страницы.
Число встречных страниц на parent сильно варьируется; эти числа не доказывают
постоянный коэффициент экономии в реальной сети.

**Timing этой серии дисквалифицирован.** В середине по сообщению владельца
пришлось очищать 156 ГиБ generated kernel cache: свободное место/I/O изменились.
Проверки данных остаются действительными, но 35,105 / 33,718 / 34,972 с нельзя
использовать как сопоставимое A/B/A и объявлять ускорением алгоритма.

## Почему простой прототип пока не принят

Удержание всех отвергнутых hints во всех страницах может повторять вычисление
content digest, если источник уже имеет достаточно строк, но содержание
подсказки устарело. Верхняя граница такой повторной работы ещё не проверена;
измеренной CPU-регрессии здесь нет. Принять несколько строк удаления clear
без этого контроля означало бы оставить новый непроверенный риск задержек.

Следующий шаг — удерживать только ещё недоступные источнику предложения,
а явно отвергнутые при достаточном prefix extent снимать. Отрицательное
сведение об объёме snapshot может лишь отключать оптимизацию, не разрешать
применение/ACK/продвижение cursor. Любой jump всё равно требует совпадения
на источнике, свежего локального snapshot, current authorization и durable
checkpoint. Для источника без таких сведений безопасен прежний plain-page путь.
Также нужно дешёво отклонять hint с count больше всего свежего snapshot до
обхода строк/хеширования. Это направление проверки, а не выпущенный механизм.

Cleanup трёх запусков завершён: PID/порты в summary, runtime удалены, native
artifacts не изменились. После проверки экспериментальные source/test edits
возвращены к квалифицированному parent; принята отдельная
[правка kernel cache](../test-kernel-cache-2026-11-09/README.md).
Догрузка и NETCALL-01 остаются активными; полная matrix не закрыта. Телефон,
production и реальные контейнеры не затронуты; sibling mailbox выключен.
Push/релиза нет. [summary.json](summary.json) содержит только агрегаты.
