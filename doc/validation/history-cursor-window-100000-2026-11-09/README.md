# Начало страницы архива без повторного обхода префикса

## Подтверждение

Источник строил свежий отсортированный snapshot, затем на каждом запросе
выполнял `where(position > cursor).take(limit + 1)` от начала списка.
При 100000 строках и страницах по 128 это **39087488 повторных посещений
пройденного префикса** на источник, сверх копирования самих страниц.
Это расчёт по алгоритму для полного архива, не runtime-счётчик сравнений.

Теперь начало окна находится двоичным поиском в том же свежем snapshot;
копируются прежние `limit + 1` строк с lookahead. Поиск читает не более
17 строк на 100000. Удалённый cursor и позиция за последним сообщением
обрабатываются без привязки к наличию самой строки cursor.

Свежий snapshot, фильтрация видимости, paired edit frontier и сортировка
сохраняются. Устранена одна лишняя линейная петля, **не все полные обходы
архива**. Кэша или повторного использования старых authorization/policy данных
нет. Page cap 128, byte cap 128 КиБ/64 части, публикации по 64, ordinary live
coalescing по 16 и durable cursor прежние. Sibling mailbox не включён.

## Единый порядок cursor

Для двоичного поиска необходим одинаковый порядок сортировки и cursor.
Прежде сортировка сравнивала DateTime с микросекундами, а wire/cursor — только
миллисекунды и ID. При обратном порядке ID внутри одной миллисекунды источник
мог выдать страницу, которую получатель отклоняет как не продвигающую cursor.

Общий comparator теперь использует **wire milliseconds → ID**. Сами Message,
их timestamps и обычный UI display order не меняются. HVS при fold уже
нормализует timestamps до миллисекунд; исходное расхождение воспроизведено
на contract fixture хранилища, сохраняющего более точные значения. Это не
объявляется причиной прежней пользовательской жалобы на живом HVS.

## Регрессионные проверки

На parent source test assertion-red: выдаёт обратный wire order. На исправлении
та же проверка удостоверяет порядок/ timestamps ответа, полное применение
и завершение cursor без ошибок. Линейный lookup-контроль отдельно assertion-red
на near-tail запросе: превышает предел 17 индексных чтений. Candidate проходит.

Helper-проверки покрывают independent linear oracle, пустой архив, границы,
пропавший cursor, равные позиции, разные time zones, отрицательные timestamps,
submillisecond значения, immutable list и полную пагинацию 100000 строк.
782 helper lookup требуют не более **13294** индексных чтений; копирование
самих сообщений в этот счёт не включено. Это work bound, не тайминговый порог.

**228 related passed / 0 skipped**, отдельно **16 native HVS**. Сохранены
revoke, edit/read hooks, publication/storage failures, prefix proofs, byte
boundaries, oversized records и restart guards. Analyzer чист.
