# Проверка отчётов R33–R35

Проверка текущего кода, а не принятие оценок аудитора как доказательства.
Перед изменениями владельцу передана сводная таблица. После аудитов выполнен отдельный раунд
[lifecycle операций с личностями](../identity-edit-lifecycle-2026-11-11/README.md);
проверены отмена, admission и ожидание принятого создания перед wipe. Продолжение
также охватывает обычные pick/switch, reboot, конкурирующий выбор и leases
при смене открытого пространства: 237 related passed (+2 skips), отдельно
11 native/compaction passed без skips. Исходная жалоба Windows 10 не закрыта.

**Текущее состояние R33-07:** disk adapter уже использует native publication,
recovery перед scan и root admission; last-window регрессия проходит. Открытый
релизный остаток — проверка итогового GUI и платформенных
артефактов. Локальная macOS arm64 AOT-упаковка с актуальным media уже собрана;
два SDK-сценария прошли на библиотеке непосредственно из app bundle.
[Квалификация и ограничения](../media-package-provenance-2026-11-11/README.md). Список, экспорт и явная очистка уже реализованы; **139 macOS
проверок прошли на полном SDK через штатную загрузку и default ABI gate**.
Абзацы ниже описывают последовательные этапы; актуальное продолжение —
в разделах о копиях и «Квалификация полного SDK на macOS».

## Архивы: R33-10, R33-11, R33-12, R34-01

Все четыре механизма подтверждены регрессионными тестами на прежнем коде:

| Находка | Наблюдение до исправления | Исправление |
|---|---|---|
| R33-10 | Запись 3 МиБ выводила лишь один полный шифроблок, оставляя остальные в staging | Каждый полный блок передаётся sink с backpressure; staging ограничен одним блоком |
| R33-11 | UUID-вложение отсутствовало в CID-only GC inventory и архиве | Отдельный набор UUID/CID вложений из сообщений объединяется с inventory; GC не меняется |
| R33-12 | Manifest-only CID экспортировался как фиктивный пустой payload | `null` размера означает пропуск с записью в `skippedFiles`; настоящий размер 0 сохраняется |
| R34-01 | File record создавал служебный `master:roster.v2` | Импорт отвергает пространство `master:` до записи; экспорт также его исключает |

Произвольные имена внутренних файлов из метаданных сообщения не расширяют
набор экспорта: добавляются только форматы UUID/CID. Перенос личности сохраняет
свой отдельный явный путь. Новый MAC roster не вводится: проблема была во входном
пространстве имён, а не в аутентификации уже записанных байтов контейнера.
Подтверждено создание roster через прежний import; доступ к существующим чужим
пространствам или исполнение кода этим не доказаны.

Проверки:

- Четыре новых assertion-failure на прежнем коде, затем **66 passed** в transfer,
  round-trip и экранных проверках экспорта.
- **2 passed, 0 skipped** на настоящем hidden-volume 2.7.0: UUID payload после
  export/import/cold reopen; отказ внедрения roster и отсутствие его после reopen.
  Нативная библиотека проверена по закреплённому SHA-256 до запуска. Rust не собирался.
- Проверки не обращались к пользовательским контейнерам и не запускали приложения.

## Дополнение R34: ответ WebSocket 404

Повторно прочитан дополненный `report34_prepare.md`: один новый конкретный
пункт **R34-02**. Подтверждено отражение недоверенного request path в теле 404
общим callback для WS/WSS. Исправлено постоянным `path not found`; правила
выбора path, статус отказа, успешный upgrade и default `/` сохранены.
HTML/script execution в браузере не воспроизводилось и не объявляется доказанным:
percent-encoded URI сам по себе не доказывает исполнение отражённой разметки.

Регрессионная проверка делает настоящий tungstenite client/server upgrade через
`tokio::io::duplex`, разбирает HTTP-отказ на клиенте и проверяет точные байты тела
для обычного и percent-encoded пути. На прежнем callback — **1 assertion-failure**,
после правки — **6 passed, 0 skipped**, включая прежние accept/reject проверки.
Для экономии диска это отдельный offline harness с точным извлечённым production
callback и всем его test-модулем, версиями Tokio/tungstenite/http из SDK lock;
весь transport crate, TLS и production-реле в этом прогоне не собирались.

R34 также ошибочно пометил R33-07 целиком закрытым по upload/version-stamp
исправлениям. Это не принято: download last-window reproducer остаётся красным,
и журнал выше/ниже сохраняет открытый статус. R34-01 новых исправлений не требует;
остальные дополнения отчёта не содержат новых конкретных находок.

## R33-01: опубликованное сжатие с предупреждением

Подтверждено и исправлено. Четыре типизированных `RenameVisible` исхода с
проверенным новым содержимым теперь проходят remap master→child перед передачей
исходного предупреждения вызывающему коду. Само сжатие повторно не вызывается.
`RenameVisibleContentUnverified`, `PublishUncertain` и прочие ошибки не дают
такого разрешения; общий `mayHaveApplied` намеренно не используется как допуск.

Четыре assertion-red на прежнем controller; отрицательный контроль непроверенного
содержимого проходит. Исправлена и ошибка счётчика тестового override: раньше
инкремент происходил лишь при установленном callback. Red повторён с исправленным
оракулом. После правки **51 passed** в roster/remap/probe/wipe проверках.
Отдельно **1 native passed, 0 skipped**: настоящий контейнер с жёсткой ссылкой,
реальное предупреждение `RenameVisibleAliasesNotRevoked`, один rewrite, холодное
чтение нового roster и открытие дочерних данных по его ключам. Библиотека та же
проверенная по SHA-256, без пересборки Rust и без пользовательских контейнеров.
Crash между rename и remap этим не проверен и не объявлен устранённым.

## Остальная очередь

R33-08 подтверждён и исправлен: два assertion-red на прежнем коде — новый ответ
стирается завершающимся upload-проходом; два параллельных ответа теряют один из
ключей. Per-storage/per-pair очередь охватывает только свежий read/merge/save
метаданных, не сетевые операции. Ответы получают сохраняемые serial/revision;
pass потребляет только собственные исходные receipts, сохраняя более новые,
даже при той же кнопке для того же пути. Root/refusal записи также сохраняют
новые ответы; итоговый report использует актуальный набор конфликтов.
**39 passed**, analyzer чист. Дополнительный ABA-guard проверен мутацией:
удаление сравнения revision снова стирает свежий одинаковый ответ и даёт
assertion-failure. Финальный код восстановлен и повторно проверен.

R33-05 подтверждён и исправлен. Четыре assertion-red: streamed import терял
соседний mirrored pack, откатывал rename, воскрешал удалённую цель; два controller
теряли одну из параллельно созданных записей. Все писатели `stickers.v1` теперь
используют общую per-storage очередь свежего read/merge/publication. Нормализация
и потоковая подготовка новых UUID-blobs остаются вне неё: зеркало может завершиться
пока импорт ждёт продолжения входного потока. Import добавляет только подготовленные
items к свежей цели, сохраняет её имя и чужие наборы. Удалённая за это время цель
не создаётся заново, неподхваченные новые blobs удаляются. Подписи не обходятся;
локальный fork по-прежнему снимает чужое авторство. Delete публикует манифест до
очистки прежних файлов. Callback синхронизации вызывается после публикации и только
для соответствующего активного storage.

**40 passed**, analyzer чист: дополнительные случаи двух импортов в одну цель,
отсутствовавшей первоначально default-цели с последующим create/delete, холодный
reload, подписи, device sync и существующие проверки смены личности. Это не
проверка нескольких процессов, одновременно открывших один контейнер.

R33-02 подтверждён и исправлен в исходниках Veil `84f5eb97`. Non-Windows FFI
вызывала stop/set/init/start мимо уже существующего транзакционного helper.
Теперь все платформы проверяют необходимые результаты, не сохраняют неудачный
выбор и пытаются восстановить прежний выход. Windows OS-role default сохранён;
вне Windows при неизвестном прежнем выборе fallback использует числовой индекс 0.
Восстановление драйвера — попытка, не гарантия при отказе самого старого устройства.

Проверка извлекает точное production тело FFI без переписывания ветвлений и
компилирует с контролируемым ADM: на прежнем коде **11/20 проверок провалились**,
после правки **20/20 passed**; соседний helper **25/25 passed**. Без физической
проверки драйверов. Закреплённые медиабинарники этим source-коммитом не заменены:
до выпуска нужны их пересборка, новый immutable pin и source-digest проверка.
Это не объявляется уже установленным/выпущенным исправлением звука.

R33-06 подтверждён тремя контролируемыми interleaving: A enable с токеном,
enable после создания токена, disable; между записью и продолжением активируется B.
На прежнем коде три assertion-failure (исправлены отдельно ошибки fixture: stream
в fake и адрес HTTP контрольного запроса). Теперь enable/disable и соседние
изменения токенов/roots/webhook держат исходное хранилище и generation, проверяют
их после await до следующей записи или изменения live-состояния.
**12 passed**, analyzer чист; включённый B после запоздавшего disable A по-прежнему
отвечает на настоящий loopback HTTP `/v1/account` своим токеном и своей личностью.
Токены и сетевые защиты не ослаблены. Обход аутентификации токеном A для B не доказан
ни исходным отчётом, ни этой проверкой; подтверждён именно перенос управляющего действия.

R33-04 подтверждён чтением: список сохранял завершённые echo timers. Теперь
набор содержит лишь ожидающие timers, callback удаляет себя, dispose отменяет
и очищает остаток. Это ограничено демонстрационным loopback, не сетевым транспортом.

R33-09 подтверждён контролируемой гонкой: после допустимого stat тест увеличивает
piece до 4 МиБ. На прежнем коде происходит whole-file read, после исправления

проверках, analyzer чист. Обычные проверки шифрования,
range-read, MAC, удаления и пропущенных частей сохранены.

R33-07 (гонки локальной версии при folder sync) подтверждается текущим потоком

Она не объявлена исправленной и должна быть закрыта до выпуска этого батча.

### Download: версия плана и подтверждённая версия

Дополнительно исправлены три наблюдаемых окна R33-07:

- Правка, пока ожидается `openDownload`, больше не принимается как исходная
  версия для замены: writer получает именно версию из scan.
- Правка во время чтения/записи временного файла выявляется перед публикацией;
  исходный файл сохраняется, pass регистрирует конфликт вместо успешного download.
- Правка сразу после реального rename не получает contentId скачанных байтов:
  receipt содержит метаданные подготовленного временного файла, не последующий
  stat пользовательского файла. Новая правка остаётся dirty и отправляется позже.

Три assertion-red на прежнем коде с настоящими файлами и управляемыми границами
ожидания. Первый некорректный setup не засчитан: базовая версия теперь создаётся
настоящим upload до скачивания. После правок **75 passed, 1 skipped**, analyzer
чист. Дополнительный прогон с проверенной по SHA-256 библиотекой Veil, ABI gate и
обязательными native open/create: **3 passed, 1 skipped**. Native walk в этом
прогоне не означает native atomic publication: финальный rename пока Dart.

Пропуск — **не закрытый дефект**: опциональный
`XVEIL_R33_PUBLISH_RACE_REPRO=1` включает реальную правку непосредственно перед
rename, уже после последнего stat. Он по-прежнему даёт assertion-failure:
изменённых байтов нет ни в основном файле, ни в другой копии папки. Нужен
publisher, сохраняющий вытесненную версию даже в этой гонке и при crash, с прежней
защитой от symlink/reparse. Дополнительный stat не объявляется полным решением.

На доступной Windows 11 отдельно проверен `ReplaceFileW` в одноразовой папке:
обычная замена может затереть уже существующий backup; удержание parent-directory
handle с запретом sharing приводит к отказу 1175; символическая leaf-ссылка в
этом probe отвергнута (1464), внешние fixture-байты сохранены. Всё удалено после
проверки. Это данные против наивного fallback, не квалификация готового publisher.
Контракт API также различает частично выполненные исходы — их нельзя считать
доказательством rollback. [Документация Microsoft](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-replacefilew).

### Native-подготовка безопасной публикации

Добавлена внутренняя same-parent операция с удержанием directory handle и
атомарным запретом заменить занятое имя: `renameatx_np(RENAME_EXCL)` на Apple,
`renameat2(RENAME_NOREPLACE)` на Linux/Android и descriptor-relative
`NtSetInformationFile` без `ReplaceIfExists` на Windows. Пути с разными parent,
небезопасные компоненты и Windows ADS отвергаются. Подмена parent после
подготовки не перенаправляет move; занятый leaf, включая link/junction,
не заменяется. Отказ не запускает path-based fallback.

Это **внутренний building block**, пока без C ABI и подключения к Dart.
Он не обещает crash-transaction: для двух moves нужны журнал восстановления
и его обработка до scan. R33-07 этим этапом **не закрыт**; opt-in воспроизводитель
финального окна приложения остаётся красным.

Проверки точного production FS-модуля в отдельном offline harness:
**27 passed на macOS**, **18 passed на настоящей Windows 11**, без пропусков.
Финальный Windows EXE проверен по SHA-256 на обоих концах. Временное снятие
exclusion снова дало три assertion-failure на macOS и два на Windows,
включая появление destination после подготовки; финальные исходники восстановлены
и прогоны повторены. Дополнительный Windows boundary-тест сначала выявил
ошибку нового кода: для однобуквенного имени буфер был короче полного NT header.
Исправлен минимум размера; отдельно проходят ASCII, BMP и surrogate-pair имена.
Все Windows fixtures и запущенные тестовые процессы завершены/удалены;
пользовательское приложение и контейнеры не затрагивались. Это не сборка и
квалификация всего SDK или Android. C header остался побайтно прежним.

### Native-протокол замены и восстановления

Добавлен внутренний `fs_beneath/publication.rs`. Одна операция держит один
parent-directory handle от проверки до завершения. Перед первым move создаётся
эксклюзивный bounded intent с именем целевого файла и флагами состояния;
файл журнала синхронизируется. Прежняя запись переносится под отдельное
`.previous` имя, входящая устанавливается с no-replace. Поздно появившаяся
пользовательская запись выигрывает имя. Прежние байты, включая запись через
ранее открытый дескриптор, сохраняются в recovery-копии.

Восстановление незавершённого intent возвращает прежнюю запись, если основное
имя свободно; занятое имя и остальные копии сохраняются. Неполный, чрезмерный,
невалидный журнал или неоднозначное отсутствие обеих копий дают явный отказ,
а не пустой scan. Запрет symlink/reparse при доступе сохранён; присутствие
записи для recovery проверяется отдельно, без требования «это regular file».
Новый тест поймал ошибку первой реализации: внешняя замена файла папкой/ссылкой
перед move оставляла её резервную копию, но не возвращала исходное имя.
Теперь эта запись восстанавливается без перехода по ссылке.

Publisher/recovery сериализуются также между процессами: Unix блокирует сам
pinned directory, Windows — открытый lockfile с запретом DELETE sharing.
Одновременно запущенный второй процесс получает именно busy; проверка
подтверждает, что он не успел отметить активный intent завершённым.

Проверки точного FS-модуля в том же отдельном offline harness:
**43 passed на macOS**, **34 passed на настоящей Windows 11**, без пропусков.
Дочерний процесс реально завершается через `process::exit` без деструкторов
на пяти границах, после чего основной процесс восстанавливает файлы и проверяет
наличие обеих версий. Отдельно проверены ошибка с возвратом из каждой стадии,
поздние in-place/atomic-replace правки, новый файл/папка/Windows junction на месте
цели, подмена parent ссылкой (Unix), занятые recovery-имена и испорченные intents.
Мутация с удалённым restore снова роняет interruption/process-exit тесты на обеих
ОС; финальные исходники восстановлены, оба прогона повторены. Windows EXE
проверен по SHA-256, его fixtures удалены. Clippy с `-D warnings` чист на обеих
платформах. Дополнительно проходят cross-check Linux musl и Android aarch64,
armv7, i686; это компиляция, не физические Android-проверки.

На этом native-этапе **C ABI и Dart ещё не были подключены**; header оставался
побайтно прежним. Следующее подключение описано ниже.
До закрытия R33-07 нужны recovery до scan, общий admission для scan/publication
(чтобы другой проход не увидел временно отсутствующее имя), новая публикация
вместо Dart rename, доступ пользователя к сохранённым версиям/явной очистке
и повтор исходного last-window воспроизводителя. Предыдущие версии сохраняются; они не становятся
автоматически удаляемыми `.xveil-part`. Unix синхронизирует parent после moves;
Windows flush-ит файлы, portable directory-fsync/power-loss гарантия не заявлена.
Проверено завершение процесса, не отключение питания. Это не квалификация
всего SDK/приложения и не устранение дефекта уже установленной сборки.

### Общий root admission и проверенный Dart → C ABI

Сессия теперь держит допуск **всей выбранной папки**, а не только родителя
одного файла. Восстановление и host scan могут выполняться в одной сессии;
новая публикация из другого процесса/вложенной папки получает busy. Дочерние
пути проходят от уже закреплённого root handle. Подмена pathname корня
выявляется отдельной проверкой identity; это не обещание атомарного snapshot
внешних редакторов. Для одного handle также добавлен try-lock операций:
параллельный recover не может отметить незавершённый publish settled.
Снятие этой защиты даёт assertion-failure на обеих ОС.

Добавлены `veil_fs_folder_open/matches_root/recover/publish/close`, сгенерированы
C header и соответствующие ABI-константы Rust/Dart. Низкоуровневая Dart-сессия
освобождает ошибки тем же native destructor, оставляет в исключениях только
категории, отвергает NUL и некорректные UTF-16 строки до C-string marshalling.
Последний guard проверен мутацией: без него unpaired surrogate выбирает реально
существующее имя с U+FFFD и получает LocalChanged вместо отказа от некорректного
имени. Полноценные surrogate pairs поддержаны. POSIX filename с двоеточием
сохранён; Windows ADS остаются запрещены.

**50 native passed на macOS / 40 на Windows 11**, без пропусков; точные
production FS-модули, фактический Windows EXE с проверкой SHA-256 и удалением
fixtures. Clippy `-D warnings` чист на обеих ОС; Linux musl и Android
(aarch64/armv7/i686) проходят cross-check. Это не физическая Android/Win10
квалификация и не сборка всего SDK.

**10 Dart → native passed, 0 skipped** на macOS: реальная замена с receipt,
сохранение прежних байтов, recovery до scan, замена root, ссылка-intent за пределы
папки (валидная внешняя запись остаётся неизменной), ownership ошибок и admission.
Вместе с соседними ABI gate проверками **15 passed / 3 skipped**: три пропуска
относятся к полному SDK, который в этом прогоне не собирался; они не зелёные.

Добавлен маленький `crates/veilclient-ffi/tests/fs_fixture` со standalone Cargo
workspace и версиями libc/windows-sys/zeroize из SDK lock. Он компилирует ровно
production FS-модули и извлекает production `veil_free_string`, без SDK ABI/version
маркера. Проверка подтверждает, что production ABI gate отвергает fixture как
полный SDK; тесты передают библиотеку явно. Он не является release-зависимостью.
CI собирает его в отдельном target и задаёт `XVEIL_REQUIRE_FOLDER_FS=1`, поэтому
отсутствующий fixture не превращается в незамеченные пропуски. Workflow pins
проверены. Локальный пример (macOS, для Linux расширение `.so`):

```bash

  --manifest-path third_party/veil/crates/veilclient-ffi/tests/fs_fixture/Cargo.toml
TMPDIR=/private/tmp/ \
XVEIL_FS_TEST_DYLIB=/private/tmp/veil-fs-fixture-target/debug/libveil_fs_test_ffi.dylib \
XVEIL_REQUIRE_FOLDER_FS=1 flutter test test/folder_publication_native_test.dart
```

**R33-07 остаётся открыт:** `LocalFolderSyncDisk` пока использует финальный Dart
rename. Новая сессия проверена как компонент, ещё не встроена в адаптер. Следующий
шаг — стадийная запись/публикация, recovery под тем же допуском до обычного scan,
пользовательский доступ к сохранённым версиям и повтор исходного last-window
теста через production-адаптер. Существующий default ABI gate не ослаблен.

Активный остаток аудитов: R33-07. Отдельно до выпуска медиаправки
требуется пересборка и pin движков, как указано выше.

Этот документ — промежуточный журнал. Push и релиза нет.

## Интеграция root publisher в disk adapter

`LocalFolderSyncDisk` больше не выполняет финальный Dart rename. Сетевой source
читается порциями до 256 КиБ в отдельный приватный временный каталог, без root
admission и создания папок назначения. Только полная копия переносится локально
в `.xveil-<32 hex>.incoming` через уже закреплённый корень, flush/close, version
guard и native recoverable publication. Scratch-путь не выбирается по имени
пользовательского файла; старые `.xveil-part` не усыновляются и не удаляются по
одному сходству имени. Предыдущие версии и intent не удаляются автоматически.

Перед scan одна native-сессия держит recovery и всю enumeration; root substitution
или повреждённый intent не превращаются в пустой инвентарь. Перед публикацией
восстанавливается только родитель цели, чтобы не обходить всю историю/дерево на
каждый скачанный файл. До создания incoming повторно проверяется исходная версия;
последняя проверка Dart остаётся ранней диагностикой, авторитетной границей
публикации служит native compare/move протокол. Stamp выдаётся от incoming,
а не от пользовательского файла после публикации.

Добавлен `veil_fs_folder_create_incoming`: exclusive create только protocol-имени,
mkdir/open каждого родителя от pinned handle с no-follow/OBJ_DONT_REPARSE.
Неверное имя проверяется до создания каталогов. Занятый файл не принимается
как временный и не обнуляется. C header и обе ABI-константы перегенерированы;
default SDK gate сохранён. Существующий descriptor writer используется и
обычным create-beneath, и новым admitted create — не два варианта flush/close.

**Проверки:**

- **53 Rust passed на macOS / 43 на Windows 11**, 0 ignored. В том числе создание
  вложенных папок, exclusive create, file-parent и symlink/junction refusal;
  Windows EXE запущен на реальной ОС со сверкой source/binary SHA и cleanup.
- **51 Dart/adapter/FFI passed, 0 skipped** с явно переданным FS-only fixture.
  Сетевая задержка не держит admission; adapter восстанавливает прерванную
  публикацию до инвентаризации. Baseline-test post-recovery исправлен: previous
  перемещается обратно в target, второй дубликат старых байтов не обещается.
- Last-window тест теперь внедряет правку **после последнего Dart stat**, когда

### Список и экспорт сохранённых копий

В карточке синхронизируемой папки добавлена кнопка «Сохранённые копии».
Список показывает `.previous` и неприменённые `.incoming`, включая копии
без пригодного intent. Неполный incoming явно описан в подсказке по `?`.
Имена из intent используются только для отображения и предлагаемого имени
экспорта; они не разрешают открытие другого пути. Повреждённый intent не
скрывает сохранившиеся байты. Пагинация удерживает не более одной страницы
плюс следующий указатель, а не весь список файлов в памяти. Обход при этом
потоковый, но полный; обновление не является атомарным снимком дерева.

Чтение идёт через новый native descriptor-open с прежними no-follow/root
ограничениями. Admission отпускается до системного выбора назначения,
дескриптор остаётся привязан к открытому файлу. Экспорт читает порциями
до 256 КиБ и сообщает успех только после `finish()`. Отмена, смена личности
или root не дают продолжить старое действие в новой сессии; незавершённое
назначение получает `abort`, источник закрывается. Отказ ОС в записи получает
отдельное сообщение о доступе. Текущий mirror target/base и исходная копия
не переписываются. Перед завершением проверяются размер и полная native mtime
открытого источника: это обнаружение обычных изменений, не immutable snapshot
и не защита от намеренного восстановления тех же метаданных.

Ошибки попадают в анонимную диагностику только как этап и фиксированная
категория. Пути, имена, временные метки и текст исключений не экспортируются.
Собственный промежуточный `Debug` с новой временной меткой исправлен до коммита
после assertion-red проверки; это не установленная утечка пользовательского
диагностического отчёта.

Проверки текущего исходного кода:

- **189 Flutter tests passed, 0 skipped**: folder sync, native binding, список,
  пагинация, экспорт, widgets, journal и document export. Включают реальную
  filesystem fixture, сохранность current/previous, освобождение admission
  перед picker, root/identity/dispose отмены, ошибки write/finish, symlink refusal
  и запрет ложного успеха. Это общий счёт, вложенные серии к нему не прибавляются.
- **56 macOS native / 45 Windows 11 native**, без ignored. Windows EXE исполнен
  на ОС со сверкой source/binary SHA и удалением тестовых данных. Точный
  sub-millisecond mtime witness использует Rust `FileTimes`; Dart-тест такого

### Явное удаление сохранённой копии

В списке добавлено удаление одной выбранной копии с отдельным подтверждением
и предупреждением о необратимости. Сначала источник открывается через
no-follow native descriptor, затем admission отпускается на время подтверждения.
После согласия заново приобретается root admission и проверяется текущая
личность. Смена личности/root/закрытие окна отменяет действие; подтверждение
старого диалога не разрешает удаление в новой сессии.

Native-операция принимает живой дескриптор выбранного файла. Проверяются
идентичность объекта и полная исходная size/mtime, затем имя захватывается
no-replace move в новый случайный служебный `.incoming`. После захвата
проверка повторяется. Поэтому подмена исходного имени между первой проверкой
и move сохраняется, а не стирается; восстановление исходного имени также
никогда не перезаписывает новое занятие. При остановке процесса после захвата
байты остаются в доступной для экспорта orphan-копии. Это имя может потерять
связь с исходным названием — список честно показывает неизвестное имя.

Удаление разрешено только при валидном **settled** intent либо для orphan
incoming, который ещё не публиковался. Незавершённые/повреждённые журналы
и orphan previous требуют восстановления; очистка их не обходит. Matching
settled intent удаляется после последней своей копии, остальные копии и
текущий файл остаются. Ранее оставшиеся intent без копий не подвергаются
массовой уборке. Автоматического удаления предыдущих версий нет.

На Unix удаляется leaf через `unlinkat` закреплённого родителя; Windows
помечает открытый no-reparse объект через NT file disposition. Нет pathname
`File.delete` fallback. Случайное capture-имя зарезервировано admitted
операцией; это явное пользовательское удаление, не immutable snapshot против
постороннего процесса, продолжающего запись через ранее открытый дескриптор.
Process-exit гарантии не расширены до power-loss, особенно для Windows
без portable directory-fsync. При отказе интерфейс обновляет список:
сохранившийся capture не должен остаться невидимым до следующего открытия.
Анонимная диагностика добавляет только origin=discarding и код cleanup.

### Квалификация полного SDK на macOS

Собран полный `veilclient-ffi` из текущего чистого SDK checkout: release
profile, `production-seeds,node-embedded,packet-tunnel`, без понижения PoW
и без dependency overrides. До и после сборки сверены HEAD и SHA отслеживаемых
исходных файлов, отдельно записан SHA dylib. Это отдельный target текущего
checkout, не target FS fixture или dependency-overridden эксперимента.

Локальный default-strip запуск завершился ошибкой E0463 при загрузке
`zeroize_derive`. Прямой `dlopen` того же proc-macro дал
`mis-aligned LINKEDIT string pool`. Контроль с build-override stripping
также не загрузился; контроль с `CARGO_PROFILE_RELEASE_STRIP=none` загрузился.
Для host-квалификации полный SDK собран с этим явно записанным override.
Настройки Cargo проекта не менялись. Это **локальный квалификационный
артефакт**, не готовый релизный бинарник и не подтверждение штатного CI build.
Не утверждается общая причина всех аналогичных E0463.

В тестовом helper добавлен отдельный opt-in `XVEIL_FULL_FOLDER_SDK=1`:
приложенческий loader открывает `VEIL_FFI_DYLIB`, default ABI gate проверяет
контракт, сравниваются handles выбранной и загруженной библиотек, адаптер
создаётся **без** `library:` injection. Непригодный SDK не выбирает запасной
pathname publisher. Обычный FS-only режим остаётся прежним.

**139 passed / 0 skipped** на полном SDK: все `folder_sync*`, saved versions
и два новых SDK-gate сценария. Включены исходный last-window witness
(`edits == 1`), admission/recovery, symlink containment, реальный цикл
публикация → список → экспорт 600017 байт → явное удаление копии
с сохранностью текущего файла. Отказ отдельной проверки неверного ABI
не портит успешный process default. Embedded-node символы присутствуют,
но сам узел этим тестом не запускался.

Отдельный отрицательный запуск **того же full-SDK режима с FS fixture**
закончился ожидаемым `VeilAbiContractMismatch` / отсутствующим ABI marker.
Он зачтён как проверка отказа, не как пройденные сценарии публикации.
Обычный fixture-режим после изменения helper: 21 related passed; analyzer
двух новых/изменённых файлов чист. Эти пересекающиеся серии не суммируются.

Повторяемый opt-in запуск (путь должен указывать на полный SDK):

```bash
TMPDIR=/private/tmp/ \
VEIL_FFI_DYLIB=/absolute/path/libveilclient_ffi.dylib \
XVEIL_FULL_FOLDER_SDK=1 flutter test --no-pub \
  test/folder_sync*_test.dart test/folder_saved_versions_test.dart \
  test/folder_publication_sdk_test.dart
```

В обычной CI-серии без этого режима три SDK-only теста явно пропускаются;
пропуски не считаются доказательством полной квалификации. Отрицательный
FS-only gate в `folder_publication_native_test.dart` сохраняется отдельно,
его не переключают на полный SDK.

Сборка ограничена watchdog: минимум 80 ГиБ свободного места, максимум
24 ГиБ target и 40 минут; фактический размер target после сборки — около 2 ГиБ.
Внешний диск с оставшимися 1,3 ГиБ не использовался для полной сборки.
GUI-приложение не запускалось, пользовательские данные/телефоны/реле
не менялись. **Остаток перед выпуском:** итоговая упаковка/AOT и платформенная
проверка приложения, актуальные immutable media pins, обычные release/ABI
артефакты. Их нельзя заменить этим host-тестом. Push/релиза нет.
