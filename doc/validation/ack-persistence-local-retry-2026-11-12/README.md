# Сохранение полученного ACK без повторного трафика

**Подтверждено и исправлено локально:** после отказа записать `delivered`
предыдущее исправление `8f0b640e` позволяло обработать следующий ACK, но всё ещё
зависело от его получения. На свежем сообщении maintenance оставлял `sent`;
у сообщения старше 90 минут обычная give-up политика могла записать `failed`,
хотя подтверждение уже было получено. Оба сценария воспроизведены как assertion
failures, без ожидания 90 реальных минут: у старого сообщения задана реальная
старая timestamp. Получатель в тесте не существует и второго ACK нет.

## Изменение

Неудавшийся локальный эффект сохраняется в отдельной RAM-очереди пар
peer/message. Её предел — 4096 записей, размер одного прохода — 64. Ошибки
переносятся в конец, чтобы не блокировать следующие подтверждения. При
переполнении старейшая запись теряется вместе с её receipt в session cache:
для неё остаётся обычное восстановление через сеть. Ни ключи, ни тела сообщений
в эту очередь не копируются; plaintext или резервный файл не создаются.

Полученный ACK продолжает подавлять лишнюю пересылку и give-up, пока его
сохранение ожидает повтора. Обычный периодический driver запускает отдельную
coalesced задачу записи. Он не ждёт её I/O и остаётся доступен для новых
сообщений. Задача не бесхозная: сервис удерживает её Future и при dispose
останавливает допуск, очищает ожидающие элементы и ждёт начатые записи с
трёхсекундным лимитом ожидания этих задач. Опоздавшее завершение не вызывает
UI/journal callbacks закрытого сервиса.

Для одной пары одновременно работает один status writer; присоединившийся
вызов не получает повторное `moved=true`. Изменение интерфейса, уведомление
своих устройств и mailbox dedup выполняются после сохранения. Если target
уже удалён или ACK относился к отсутствующему control-frame id, статус или
журнальное событие для него не создаются. Успешно завершённый orphan ACK не
авторизует начальный статус будущего зеркала. Собственные устройства не
получили mailbox-доставку: модель multi-device не менялась.

## Проверки

**97 тестов прошли, без skips.** Среди них 17 сценариев ACK persistence:
отказы point-read/commit и потерянный ответ уже применённого commit, повторный
ACK, maintenance без получателя, старое сообщение, остановленная запись,
дубликат/повтор во время записи, dispose, изоляция двух peer с одинаковым ID,
удаление target, orphan ACK и проверка лимита на 4097 отказавших ACK.
В отдельном сценарии первые 64 записи продолжают отказывать, но следующие
шесть получают `delivered`; ложного `failed` и сетевой пересылки нет.

На виртуальных часах остановленная status-запись переживает следующий тик,
а новое независимое сообщение всё равно отправляется. Контрольный кандидат
с ожиданием ACK-задачи внутри общего timer driver падает на этом assertion;
вариант с независимой owned-задачей проходит. Два ранних варианта timer-fixture,
смешивавшие зоны выполнения при setup/cleanup, исключены; окончательный fixture
создаёт работу в одной FakeAsync-зоне и отдельно дренирует cleanup.

Первый кандидат maintenance также задерживал explicit flush за уже начатой
inbound-записью; существующий gate-тест поймал ожидание. Maintenance теперь
пропускает такие writers. Добавлены checks прежних cache/status/mirror,
route-up retry, own-history lifecycle и inbound admission/teardown.
Targeted analyze и `git diff --check` проходят.

Повторены **3 native E2E без skips**, последовательно с `--concurrency=1`:
sender-crash после status commit, затем восстановление sibling через новый
пустой остров при выключенном получателе; receiver-crash до и после append
с настоящими SIGSTOP/SIGKILL, последующим повтором и двусторонним обменом.
macOS arm64, JIT-хосты, CLI/SDK 0.11.50 (`e963fbdb`) и локальная hidden-volume
`293792d`. SHA inputs проверены перед запуском; native inputs и весь снимок
исходников lib/test неизменны до завершения. После стенда все 30 учтённых
процессов/групп завершены, 30 зарегистрированных портов свободны, test VM нет.
Реле, Android-приложения и пользовательские контейнеры вне стенда не менялись.

## Границы

Отказы storage смоделированы через настоящий `HiddenVolumeStorage` и mapping
KV/log операций с управляемыми отказами; это не аппаратная ошибка диска.
Native E2E проверяют корректность обычного и crash-путей на новой логике,
но не воспроизводят аппаратный отказ записи и не заменяют Android/AOT-проверку.
Очередь RAM-only: аварийное завершение до сохранения ACK теряет её, после
чего действуют прежние durable history и network retries. Нельзя обещать
сохранность ещё не записанного подтверждения при постоянно недоступном диске
и потере процесса. Случаи за пределами лимита очереди отдельно не объявляются
восстановленными без сети. Вся multi-device матрица этим раундом не закрыта.
Изменения не запушены и не опубликованы.
