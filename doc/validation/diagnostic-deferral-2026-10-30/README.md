# Диагностика отложенных жалоб — 2026-10-30

Пользователь попросил продолжать подтверждённые дефекты, а неподтверждённые
жалобы отложить до повторного упоминания после проверки диагностического
покрытия. Это изменение диагностики и приоритетов, не заявление об устранении
Windows-симптомов, низкой слышимой громкости или длительного OEM-засыпания.
Релиз, push и установка на телефон в этом цикле не выполнялись.
Изменения SDK: `201b14eb`.

## Проверенные механизмы

| Случай | Уже было | Добавлено |
|---|---|---|
| Односторонняя доставка Windows/Android | События отправки/приёма, native numeric failure, повторы, delivery ACK, версии | Проверено наличие в диагностическом экспорте; transport acceptance по-прежнему не считается доставкой |
| Нет звука / тихий звук | Audio start, mute, payload/receive counters, потери, concealment, worker stalls | Раздельные результаты последнего запуска capture/playout; грубые диапазоны RMS входа/выхода WebRTC; speaker mute; категория и исход выбора телефонного маршрута |
| Android громкость/микрофон | Прикладной mute и маршрут | Системный microphone mute и процент громкости STREAM_VOICE_CALL, без имени/ID устройства |
| Возврат к onboarding | Startup, открытие контейнера, завершение/отказ, класс ошибки | Этап отказа; явный preferenceStoreFallback с классом/числовым OS-кодом, без текста/пути |
| Фоновая доступность Android | Lifecycle, intent start/stop result и выбранный режим | Реальная foreground-служба и wake lock, interactive/Doze/power-save/exemption/background-restricted; read-only снимки при lifecycle, после управления службой и перед экспортом |

Ответ startService означает приём intent, а не завершённый onStartCommand.
Снимок службы немедленно после intent может ещё показывать false; последующий
lifecycle/export отвечает о фактическом состоянии. Эти два наблюдения не
объединены в ложное «служба работает».

Результат запуска аудио: -1 — не предпринимался, 0 — отказ, 1 — принят.
Это результат последнего startAudio, не текущая проверка драйвера. Диапазоны
RMS: -1 неизвестно, 0 цифровая тишина, 1 до приблизительно -60 dBFS, 2 до -45,
3 до -30, 4 до -15, 5 выше. Нет raw PCM, энергии, записи речи или точных
амплитуд; отчёт семплируется не чаще раза в пять секунд. При worker_stalled
неизвестные измерения не выдаются за измеренную тишину. Эти поля относятся
к парному звонку; peer-keyed карты групп не экспортируются.

Последнее аудио, состояние ОС/службы, исход выбора маршрута и этапы onboarding
теперь имеют отдельное хранение фиксированной мощности. Сетевой burst не
вытесняет их до открытия настроек. Все данные остаются в памяти процесса,
очищаются общей очисткой и утрачиваются при exit/crash. Перезапущенный пустой
журнал не позволяет доказать ни смерть ОС, ни отсутствие сбоя.

## Граница приватности

Экспорт ограничен исходными enum-метками, booleans, диапазонами/кодами и
относительным временем. Нативные snapshot целиком не копируются. Для новых
аудио enum-полей проверяются целочисленность и диапазон; для OS-флагов — bool,
для громкости — integer 0..100. Неизвестные поля, вложенные peer-карты,
устройства, уведомления, numeric IDs, wall-clock epochs и свободные строки
не добавляются в экспорт.

Clipboard и save используют один builder, перед ними выполняется ограниченный
одной секундой read-only probe. Старый/отсутствующий plugin и отказ различимы.
Обычная сборка без XVEIL_DIAGNOSTICS не вызывает этот OS-probe. Никакой
автоматической отправки, raw log, сетевого debug API или изменения поведения
реле не добавлено. Служба, разрешения и аудиомаршрут сами по себе диагностикой
не включаются.

## Проверка

- 78 Flutter-проверок с XVEIL_DIAGNOSTICS=true: журнал/приватность, clipboard и
  save, маршрут аудио, служба, onboarding rollback и preferences.
- Дополнительная проверка отклоняет неверный тип/диапазон процента громкости
  (в том числе число, похожее на абсолютное время), не строкифицируя объекты.
- Тот же набор без диагностического флага проверяет обычную ветку.
- Реальная AOT-компиляция журнала в двух режимах: новые безопасные поля есть
  только в включённой ветке; artifact gate отвергает обычную как diagnostic.
- Реальная WebRTC/Opus сборка и --silence smoke: входящий и исходящий тон
  наблюдались в диапазонах 1..5, после длительной цифровой тишины оба стали 0;
  нет захвата микрофона/воспроизведения на физических устройствах.
- Android :veil_flutter:compileDebugKotlin, flutter analyze и diff-check.

Новые native поля проверены на macOS, Android bridge скомпилирован. Физические
Windows 10/Android-звонки и часы фоновой работы этим циклом не квалифицируются.
Проверочные приложения на Mac/телефоне не запускались; временная native smoke
библиотека и процесс удаляются harness-ом. Публичные исходники/отчёт не содержат
приватных журналов прежних стендов.

## При повторном обращении

Использовать следующий собранный -debug артефакт с XVEIL_DIAGNOSTICS, повторить
симптом и до перезапуска выбрать «Настройки → диагностический отчёт» (копирование
или JSON). Для доставки/звонка нужны отчёты обоих концов и описание направления
сбоя. Сырой лог вместо анонимизированного JSON не запрашивать.

Подтверждёнными активными случаями остаются 120-с недоставка предложения новой
личности, файловое восстановление после reconnect, остаточная медленная доставка
и ранее зафиксированный неожиданный отбой. Причина исходного «33%» не объявлена
установленной. Перенос жалоб не заменяет квалификацию смешанных версий или
multi-device матрицу.
