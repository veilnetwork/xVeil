# Сохранность отзыва после аварийного завершения получателя

Проверяется часть multi-device crash-матрицы: C уже сохранил подписанный отзыв
устройства B, затем C завершается через SIGKILL. Может ли старое B вернуть
свои права после перезапуска C, когда автор отзыва A выключен, а прежние
реле и их очереди уничтожены?

**Усиленный native-сценарий прошёл:** отзыв сохранился после SIGKILL,
без прежних runtime-файлов, автора отзыва и старых реле. Новый дефект в этом
окне не обнаружен; production-код не менялся.

## Сценарий

Три отдельных процесса приложения: X=A+B, Y=C; настоящие контейнеры,
MessagingService, FFI, ratchet и три локальных Core. Публичные seeds и
meeting points отключены. Собственный mailbox не добавляется.

1. B действительно доставляет сообщение C и вызывает у него входящий звонок.
   Native fence C разрешает устройство B. Это положительные предусловия.
2. B выключается. A подписывает отзыв B. C получает контрольное сообщение A.
   Приватный file-probe читает состояние через живого владельца контейнера:
   fence уже запрещает B, а сохранённый документ побайтно совпадает с текущим
   подписанным документом A. Probe ничего не импортирует и не делает flush.
3. Проверяется принадлежность фактического VM к группе C; вся группа получает
   SIGKILL. Перед холодным чтением проверяется выход именно VM, а не только
   родительской Flutter-обёртки. Холодный reader вновь сверяет документ.
4. A и прежние реле останавливаются. Runtime C удаляется. Создаётся новый
   остров с пустыми каталогами и другими портами. Сначала запускается только C:
   он по-прежнему запрещает B и разрешает A, до появления обоих в новой сети.
5. Возвращается старый B с тем же device ID и контейнером до отзыва. B отправляет
   сообщение и пытается звонить C. В течение 60 секунд опрашиваются входящие
   сообщения и состояние звонка C; ни сообщение, ни входящий вызов не допустимы.
6. Возвращается A. Новые сообщения A→C и C→A должны пройти по восстановленному
   ratchet. Ответ C не должен появиться у отозванного B в проверенном срезе.

Новый probe находится только в `test/e2e/device_process_worker_test.dart`:
он добавляет PID и boolean сравнения документа к существующему приватному
file-протоколу. В приложение, HTTP debug API и анонимный экспорт новые поля
не добавляются. Документы, device IDs, пути и журналы остаются вне отчёта.

## Контроль oracle

Во временной копии сценария после успешной холодной сверки намеренно очищен
checkpoint авторизации в **тестовом** контейнере C. Runtime также удалён.
Этот прогон падает после запуска C на проверке наличия точного сохранённого
документа; до старта B. Это ожидаемый отрицательный контроль, не обнаруженный
дефект приложения. Изменение fixture восстановлено побайтно перед финальным
прогоном; очистки checkpoint в итоговом тесте нет.

## Результат и cleanup

Финальный native E2E: **1 passed, 0 skipped**, 109,9 с внутри suite
(112,2 с вместе с запуском Flutter). За 60,195 с отрицательного окна сделано
118 проверок входящих сообщений и состояния звонка. Последующий обмен A↔C
прошёл. Предварительный прогон также прошёл, но не включал удаление runtime;
результат финального сценария учитывается отдельно.

19 unit-проверок `peer_authorization_persistence_test.dart` прошли без skips.
Targeted analyze и `git diff --check` проходят.

Снимок source/native inputs до и после финального запуска совпал. Проверены
выход 14 учтённых процессов/групп, освобождение 13 зарегистрированных портов
и отсутствие test VM. Синтетические контейнеры удалены штатным teardown.
Отрицательный контроль также завершён и очищен отдельно (12 процессов/групп,
11 портов). Никаких тестовых процессов поверх установленного xVeil не осталось.

## Границы

macOS arm64, JIT-процессы на одном компьютере; CLI/SDK `e963fbdb` (0.11.50),
локальная hidden-volume `293792d`. SHA трёх native inputs проверяются перед
запуском; 1558 выбранных source inputs и native bytes фиксируются до/после.
Установленный пользовательский xVeil 0.13.98 не используется как стенд.

Проверено аварийное завершение **после наблюдаемого durable checkpoint**.
Это не потеря питания, не сбой записи до checkpoint, не восстановление старой
резервной копии и не все варианты link/revoke/crash. Нет часов/суток offline,
Android/AOT, физической Windows или проверки слышимости звонка. Изолированный
узел не обязан знать отзыв, который он ещё не получил. Вся 63-сценарная
матрица этим прогоном не объявляется пройденной.
