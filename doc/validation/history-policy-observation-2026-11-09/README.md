# История: один снимок политики видимости

Внутри одной проверки видимости истории повторно читалась одна и та же
контактная запись: для retention, для TTL и, при включённом read-clock,
ещё раз перед чтением его watermark. Каждое `getContact` обращается к storage;
это не работа уже готового локального объекта. Отдельное завершающее чтение
статуса блокировки имеет другой смысл: оно защищает публикацию после
асинхронной работы с read-clock.

Теперь retention, TTL и read-clock используют одну свежую контактную запись.
Чтение watermark и его сохранение не убраны. Политика не кешируется между
строками/публикациями. `disappearingOf` использует тот же чистый конструктор
политики из контакта; его обычные callers по-прежнему читают storage.
Отдельная свежая проверка блокировки после read-clock, roster/revoke gates,
durable publication и checkpoint остаются на прежних границах.

## Регрессии

В production history-пути удерживается последняя roster-проверка настоящего
`beforeCommit`, без таймингового порога. Измеряются контактные чтения внутри
этой конкретной проверки, до публикации 16 входящих сообщений:

| Режим | До | После |
|---|---:|---:|
| Без read-clock | 3 | 2 |
| С read-clock | 4 | 2 |

Два оставшихся обращения — снимок видимости и независимая свежая проверка
блокировки. Обе регрессии assertion-red на прежнем коде: actual 3/4 вместо 2.
После освобождения gate все 16 сообщений сохраняются одной публикацией.

Три отдельных сценария меняют block, TTL или retention непосредственно перед
коммитом: ни сообщения, ни cursor страницы не публикуются. Ещё один меняет
block во время чтения read-clock, после снимка видимости: публикация тоже
отвергается. Отрицательный контроль с удалённой последней block-проверкой
записал 16 запрещённых строк и упал на assertion; candidate затем восстановлен.
Это доказывает необходимость сохранённой границы, а не только снижение счётчика.

Первый вариант наблюдателя пытался читать сообщения при удержанном append и
сам ожидал эту публикацию. Он остановлен и не зачтён; окончательный gate
проверяет синхронный счётчик commit без такого дополнительного storage-read.

**268 related tests passed, 0 skipped**, включая own-history, retry lifecycle,
backfill, disappearing/startup/group expiry, native snapshot admission и
fixture guards. Полный Flutter analyzer и diff checks чисты.

## Native-проверка восстановления

Четыре независимых Mac/JIT процесса: A/B/E одной личности, C другой, три
изолированных Core. В архиве A/E 512 известных сообщений; у B — одна прежняя
строка. Два полных authenticated ответа уже получены B, но первый apply
удерживается. B завершается SIGKILL, после чего A/E/C недоступны.

- Первый boot B до создания сети: прежняя строка сохранена, архивных строк 0.
- Возвращается только A: все 512 архивных + 1 прежняя строка сходятся.
- Следующий cold boot B при offline A/E/C: все 513 строк сохранены до сети.

Oracle сверяет точные ID, тела, delivered, canonical positions и порядок;
равенство двух неполных историй не принимается. Дублей, отсутствующих и
посторонних сообщений нет. Native scenario **1 passed, 0 skipped**.
От начала `start(A)` до сходимости 10,640 с; весь driver с teardown 164,416 с.
Это не A/B и не чистое время истории: менялись объём остаточной работы,
кэши и scheduling. Причинное ускорение полной догрузки не заявляется.

Использована проверенная CLI/FFI пара из Veil `v0.11.48` с
`allow-empty-seeds`, актуальные Dart bindings и опубликованная HVS 2.7.0.
Изменения текущего SDK `b7f4f02a` относительно этих native исходников
ограничены Windows VPN helper и его Windows-only dependency feature;
Mac runtime этим не менялся. Новых Rust-сборок или подмены media pins нет.
Выбранные binary SHA проверены до/после, FFI/HVS подтверждены в OS mappings.

Сверены **1475** frozen frontend/test/dependency inputs. Cleanup проверил
**43 owned PID и 62 порта**: живых своих процессов/listeners нет, временные
runtime-контейнеры удалены. Raw IDs, traces, машинные пути и witnesses private;
публичные агрегаты — [summary.json](summary.json).

**Большая догрузка и NETCALL-01 остаются открытыми.** Этот цикл не является
Android/AOT/WAN-квалификацией, полной multi-device матрицей или доказательством
доставки при offline всех источников. Sibling mailbox не подключён.
Телефон, реальные профили, production и сиды не менялись; push/релиза нет.
