# Разложение доставки и независимые адресаты data-delta

Подтверждены два поведения последовательного fanout: медленный первый
отправитель удерживал остальные адресаты, а ошибка первого callback оставляла
здоровых без попытки отправки. Для data-delta добавлены до **четырёх активных
recipient callbacks на один broadcast**. Все работы присоединяются; первая
наблюдавшаяся ошибка возвращается после попыток остальных адресатов.
Это не глобальный лимит всех broadcast и не гарантия удалённого получения.

Построение пакета, фильтрация получателей/эпох/каналов, receipts и отметки
переданных документов сохранены. Control fanout и отдельные redacted notices
удалённым участникам остаются на исходном последовательном пути. Wire,
ratchet/durable authorization, лимиты и приоритеты реле не менялись.

**Общая задержка остаётся открытой.** Ни устранение двух этих механизмов, ни
сокращение отдельных времён не доказывают устранения всех секунд доставки.

## Проверки поведения

На исходном коде: blocked-target тест увидел **1** начавшийся callback вместо
доступных четырёх; error-target тест увидел попытку только одному адресату.
Оба красных случая используют Completer, а не сетевой таймаут. Кандидат
обслуживает независимых адресатов, держит ограничение четырёх работ и не
возвращает ошибку, пока активные работы не закончены. Объект ошибки сохранён.

Первый вариант третьего теста ошибочно требовал сохранения wire-order между
двумя post. Старый post намеренно запускает broadcast без ожидания сети;
протокол допускает переупорядочивание и восстанавливает историю по цепочке.
Это требование отозвано, не объявлено дефектом. Вместо него проверена обратная
доставка двух последовательных signed rows: история сходится без дублей и
пропусков. Контроль этого случая прошёл и до исправления fanout.

**472 теста прошли, 0 skipped/ignored**: GroupService, chunks, topology,
durable source/receipt queues, PostReceiptQueue, removed-member notices,
group epochs; включены native XVSB/XVRC проверки. Targeted analyze production
GroupService и нового test adapter: **no issues**. Пакетные filters остались
в одном прежнем recipient-body; изменён способ запуска callback.

## Проводка измерений

Только test adapter вокруг настоящих HiddenVolumeStorage/VeilFlutterTransport
фиксирует durable enqueue и реальный transport-call. Все восемь optional
capabilities native-транспорта сохранены и проверяются runtime mask=255.
Пассивный callback получателя и GroupService ingress/visible используют один
Stopwatch. Временный номер copy привязан к source/destination и durable fid;
отдельный body token связывает неизменённый JSON с входом группы.

Сами fid/body остаются лишь ключами RAM-карты стенда; в timing trace попадают
синтетические номера. Приватные исходные журналы/identity files не экспортируются
в этот отчёт, JSON содержит агрегаты без идентификаторов и графа участников.
Продукт не импортирует adapters и не получил тестового переключателя.

Первый черновой захват использовал `WireEnvelope.id` вместо `frameId` и дал
пустую wire trace; он исключён. После исправления wrapper требует все пять
wire-этапов и покрытие всех 44 несобственных первых доставок, а не только
успешное завершение стенда.

Для каждого последнего получателя найдена единственная активная ingress;
по enqueue внутри предыдущей ingress цепочка восстановлена до автора.
В зачтённой серии **24 пути** разбиты на неперекрывающиеся интервалы, сумма
совпадает с временем первой видимости в микросекундах. Неоднозначное
соответствие, повторный send одной copy или некаузальный порядок были бы
отказом атрибуции. Все 202 group-data copy каждого запуска имели ровно один
enqueue/send/callback, все end успешны. ACK и прочий трафик в это число не входят.

## Native A/B

Контроль frontend `4559d456`, одна frozen release библиотека SDK `081bb6d1`.
12 реальных native узлов, local TCP full mesh, все с DHT, encrypted containers,
native crypto/ratchet/host authorization. Legacy-группа без epoch encryption,
roster передан вне сети. Одни cached production-PoW identities, свежие
контейнеры и instance keys. Один Mac/JIT host и общий диск; физические
неисправности сети в этой серии не вводились. Медленный/отказавший callback
квалифицирован unit-сценариями выше.

Последовательно A1/B1/A2/B2/A3/B3; четыре источника 0/6/5/11. Время —
первая видимость всем 12, не пиксели UI. Следующие сообщения не являются
повтором той же пары, порядок дерева доставки может измениться.

Телефон и production-реле не менялись; Rust не пересобирался. Без push/релиза.

## Что именно задерживает наблюдаемые пути

Пример A1, сообщение 4: три перехода групповой рассылки, **3046,2 мс**.

| Неперекрывающийся участок полной цепочки | мс |
|---|---:|
| Автор до enqueue выбранной ветви | 273,7 |
| Durable enqueue | 180,7 |
| После enqueue до transport-call: очередь и ratchet preflight | 497,6 |
| Transport-call до callback получателя | 35,0 |
| Callback до GroupService ingress | 214,3 |
| Обработка группы до следующего enqueue / последней видимости | 1844,9 |

Это суммы по выбранному пути, не средние всех параллельных копий.
Последний пункт включает проверку/сохранение и подготовку дальнейшей пересылки.
`queue_or_preflight` пока не разделяет ожидание source queue, reservation и
остальные preconditions — весь интервал нельзя приписывать самой очереди.

По всем шести запускам cold transport-call→callback на критическом пути:
**1371–2461 мс**, последующие сообщения: **5–185 мс**. Это включает native
очереди/resolve/authorization и callback, не измерение ping. На последующих
сообщениях обработка группы до следующего шага занимает суммарно
**714–1885 мс**, queue/preflight — **196–792 мс**. Причина каждой внутренней
паузы ещё не доказана; таймаутов/ретраев по совпадению констант не назначаем.

Следующий разбор: внутри group apply отделить реальную запись header/segments
и её очередь от остальных действий; внутри native cold handoff — resolve и
durable host authorization. Контрольная рассылка, multi-device матрица и
ранее отложенные неповторяющиеся жалобы этим раундом не закрыты.
