# NETCALL-01: история аудио при первом health и пересоздании движка

Дата: 2026-11-01. Локально исправлены два подтверждённых механизма потери
свидетельства приёма. NETCALL-01 остаётся открытым: при Wi-Fi → cellular
внутри звонка перерыв аудиопакетов всё ещё наблюдается. Общего ускорения и
устранения пользовательского случая этот цикл не доказывает.

## Два дефекта

**Первый capture-отчёт сбрасывал установленную историю аудио.** До первого
health с `capture.audio=true` аудио уже могло приниматься. `_set` начинал
новую expectation от текущего времени, а ранний детектор требовал приём после
этого момента. Если сеть пропала между пакетом и отчётом, свидетельство
установленного аудио переставало подходить даже при живой parent session.

Теперь первый отчёт сохраняет реальный timestamp только в том же активном
звонке, с тем же собеседником и устройством, при поддерживаемой telemetry и
приёме после начала текущего call/receive session. Timestamp из будущего не
подходит. Наблюдавшийся unmute `false → true` сохраняет startup grace. Fresh
native snapshot, posture, delivery qualification и cancellation guards прежние.

**Пересоздание медиадвижка стирало свидетельство liveness.** Обнуление aggregate
receive activity заставляло FSM вернуться к более старому сигналу собеседника.
В физическом прогоне до исправления Windows завершил звонок по liveness timeout
после локального rebuild; телефон получил remote end. Это свидетельство
применимости механизма, а не доказательство единственной причины завершения.

Теперь внутренний rebuild того же call/peer/identity/device сохраняет время
последнего реально наблюдавшегося пакета. Счётчик обнуляется только при старте
замены: старый движок во время teardown не должен заново предъявлять накопленные
пакеты как новый приём. Новое устройство, новый звонок и полный stop не наследуют
историю. Пересоздание не становится новым свидетельством жизни. Liveness timeout
остаётся 20 секунд; отсутствие новых пакетов по-прежнему завершает звонок.

## Регрессии

- Три virtual-time сценария первого health: поздний первый отчёт, явный unmute,
  новая receive session. На прежнем коде первый был красным, два контроля зелёными.
- Тест настоящего `VeilCallMediaController` с заменой движка: первый принял пакеты,
  второй имеет нулевой RX. На прежнем коде timestamp становился null. Теперь он
  сохраняется без обновления, а stop и новый звонок очищают историю.
- Проверка counter rebase: нулевой/неуспешный snapshot не даёт новой жизни;
  первый пакет нового движка обновляет timestamp.
- FSM на виртуальных часах: последний приём t=9, rebuild t=10. В t=25 звонок
  жив, в t=30 завершается; локальный ремонт не продлевает дедлайн.

261 связанный Flutter-тест прошёл, analyzer шести изменённых Dart-файлов чист.
Отдельно прошли восемь Python-тестов анализатора физических наблюдений.

## Физические наблюдения

Poco ↔ Windows 11, отдельные QA-профили; пользовательское приложение не заменялось.
Непосредственно перед каждым из трёх переключений оба endpoint имели один
ожидаемый активный звонок, P2P, RX >0 и native audio age ≤1000 мс. Проверены
фактические default network: Wi-Fi до, cellular после. Прогрев endpoints выполнялся
обычным production API с сохранением admission/policy gates.

| Прогон | Сборка | Звонок через ≥40 с | Максимальный sampled native age Poco / Windows |
|---|---|---|---|
| 1, без native trace | Только первый фикс | Сохранился, в конце свежий RX | 14507 / 14531 мс |
| 2, operator trace Poco | Только первый фикс | **Завершился** | 7188 / 12665 мс |
| 3, без native trace | Оба фикса | Сохранился, в конце свежий RX | 12323 / 12564 мс |

В прогоне 1 Windows начал раннее audio recovery при native age 3796 мс, даже при
положительном parent admission. Кандидат relay остался неподтверждённым, поэтому
это не устранило весь перерыв. В прогоне 2 Windows завершился по liveness timeout;
первое отсутствие звонка наблюдалось через 17,728 с после cut, на телефоне через
18,767 с. Телефон получил remote timeout. Прежнее утверждение о сохранении обоих
первых звонков **отозвано**: наблюдатель ожидал `ended`, но пропускал последующее
очищение call в null. Исправленный oracle считает null, другой call ID и любое
неактивное состояние отказом.

В прогоне 3 оба endpoint оставались active на всех 40 последующих выборках,
наблюдение длилось около 41,5 с. Переходы relay → P2P прошли с сохранением движка.
Поэтому этот прогон **не квалифицирует физически именно ветку rebuild** второго
фикса; её доказательство в этом цикле — красный тест настоящего контроллера.
Перерыв аудио сохраняется. Вторая попытка на финальных QA остановлена **до cut**:
телефон уже выбрал relay, свежий RX у него не подтвердился, тогда как Windows
показывал P2P и RX. Её журналы сохранены; это не пройденный handover и не доказанный
длительный односторонний отказ.

Максимумы native age относятся к отдельным media epoch: они **не являются
верхней границей всего перерыва аудио**. Плотность выборок и сохранность call
проверяются отдельно от свежести аудиопакетов. Все три завершённых захвата не
прошли критерий непрерывного свежего аудио; один провалил также сохранность
звонка. Это не fixed-route A/B: маршруты, кэши и trace различались. Разборчивость
и громкость живой речи человеком не проверялись; исходная жалоба о слышимости
телефон → Windows и условие ровно одного активного узла остаются неквалифицированными.

## Наблюдение и следующий участок

`scripts/analyze_physical_handover.py` читает закрытый захват и выводит только
агрегаты. Пустые/короткие/редкие выборки, call=null, смена call ID, отсутствующий
движок и устаревший RX не дают зелёного результата. Сброс media epoch не скрывает
предыдущий сбой. Tests включают canary ID/peer; они не попадают в вывод.

В operator-захвате прогона 2 были начала preparation probes (1000 мс) и relay
qualification (600 мс), но записей ответов не было. Это **не доказательство
сетевого дропа**: истёкший/закрытый candidate может уже не иметь наблюдателя.
Бюджеты проб и cooldown не менялись, неподтверждённый маршрут не объявлялся
пригодным. Следующий участок — сопоставить probe, его приём/эхо на другом
endpoint и результат квалификации после смены сети.

## Происхождение и завершение

Android и Windows — profile/AOT на `c663ed75` плюс три указанных production-файла.
Все 590 переданных Windows source files сверены перед установкой. APK после
установки сверён с локальным артефактом. Native-библиотеки опубликованные;
Windows runner/plugins не пересобирались. Rust не собирался. Flutter Android
build прошёл с проверкой отдельной внешней ФС и mount-watchdog. SHA и числовые
результаты — в [summary.json](summary.json).

QA-приложения закрыты, Windows tasks удалены, собственные listeners/ADB-forward/
SSH-туннель освобождены. Native trace выключен, собственный logcat остановлен. Первый Windows teardown
check принял записи PID 0 за слушателя: Get-NetTCPConnection вернул CLOSED и
TIME_WAIT вопреки фильтру. Отсутствие listener отдельно подтверждено через
IPGlobalProperties, netstat и отказ TCP connect; приложений и задач также нет.
Mac-стенд не запускался. Исходные настройки телефона восстановлены; PID основного
приложения сохранился, его контейнер не открывался. QA-профили сохранены для
продолжения. Частные журналы, адреса, peer/call IDs, tokens, ключи и payload не
публиковались. Push, релиза и обновления сидов нет.
