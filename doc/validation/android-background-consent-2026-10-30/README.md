# Android: согласие на фоновую службу и проверка доставки

Подтверждён дефект стартового предложения: «Разрешить» запрашивало только
исключение из ограничений батареи Android. Переключатель `keep_node_background`
оставался выключенным по умолчанию; foreground-служба приложения не запускалась.
Если OS-разрешение уже выдано, предложение вообще переставало появляться.
На стенде обнаружено именно сочетание OS-exemption и отсутствующего app-choice;
причина исходной жалобы другого пользователя этим ещё не доказана.

Кнопка теперь сначала сохраняет и применяет выбор фоновой работы через обычный
BackgroundNodeController, затем запрашивает OS-exemption. Текст объясняет
постоянное уведомление, возможный расход батареи и отдельный автозапуск OEM.
Выбор по умолчанию остаётся выключенным: отсутствующая настройка — повод
предложить; сохранённое `false` — явный отказ, повторного предложения нет.
«Позже», «Не спрашивать», переход в настройки и закрытие диалога службу не
включают. Подавление предложения хранится в текущем профиле, как раньше.
Ошибки настройки показывают фиксированный текст без данных исключения.

## Проверка кода

На исходном `01e3c19c` добавленный тест сочетания OS-exemption и отсутствующего
app-choice упал (ожидалось предложение, получено false). После исправления
прошли 16 тестов: политика предложения, реальные нажатия диалога, сохранение
через настоящий controller до OS-запроса, порядок async-вызовов, отказы и
существующие гонки запуска/остановки службы. Analyze четырёх изменённых файлов
не нашёл замечаний. Это не тест Android API на host: платформенные вызовы
в widget-тестах заменены callbacks.

## Физическая проверка конфигурации до UI-исправления

Проверен исходный Dart `01e3c19c`, Android profile/AOT и Mac JIT, production
network. Native зафиксирован по SHA на `c96bd930`; plugin source — `ea7e8388`.
Различия SDK между ними в проверяемых runtime/FFI/stream/plugin путях отсутствуют;
Windows-изменения этим тестом не квалифицируются. Native test hooks и упрощённой
сложности нет. Это сознательная фиксация сборки, а не заявление о запуске всего
текущего SDK. Исходники и артефакты сверены, их приватный provenance сохранён.

У Android API 30 OS-exemption уже был выдан; whitelist не менялся. Для проверки
самой службы во время остановленного QA-процесса временно включена только
настройка приложения. UI-исправление в этой серии ещё не установлено.
Узлы — разные личности, P2P запрещён с обеих сторон. В каждом случае сначала
наблюдался delivered/read у отправителя на Mac, и только затем запрашивался
список сообщений телефона. Таким образом, опрос QA API телефона не был условием
получения исходного ACK. Остаётся воздействие USB/ADB и пассивных dumpsys.

| Состояние Android до отправки Mac → Android | ACK, с | Копий у получателя |
| --- | ---: | ---: |
| Приложение открыто | 3,095 | 1 |
| Home, приложение в фоне 60 с | 2,062 | 1 |
| Экран выключен 60 с | 2,055 | 1 |
| После отключения обеих сетей на 45 с и восстановления, экран выключен | 2,044 | 1 |
| Принудительный deep Doze IDLE, выдержка 300 с | 2,078 | 1 |

Во всех пяти случаях процесс, foreground-служба и wake lock существовали;
в Doze до и после доставки зафиксирован IDLE. Между отправками приложение
не выводилось в foreground. Это не многочасовой OEM-тест, не естественный Doze
на разряженном телефоне и не гарантия работы на всех прошивках. Аудио/видеозвонки
и реальная слышимая громкость здесь не проверялись.

## Очистка

QA-приложения на телефоне и Mac закрыты; процессы и собственный logcat завершены,
ADB-forward удалён. Выключены trace, возвращены p2p/anonymous настройки, исходные
preferences восстановлены побайтно, исходный установленный QA APK возвращён и
сверен по фактическому SHA. База/ratchet не откатывались. Радионастройки,
батарейная симуляция и forced-idle восстановлены; whitelist не менялся.
Первоначальная bind-проверка портов ошиблась без диагностики причины; отдельная
проверка с SO_REUSEADDR затем подтвердила свободные порты и отсутствие процессов,
forward, forced-idle и battery simulation. Причина первого отказа не доказана.
Основное пользовательское приложение не изменялось. Push и релиза нет.

Открыты: исходный пользовательский случай «засыпания», другие OEM/Android,
длительный offline, входящие звонки при блокировке и физическое нажатие
обновлённого стартового предложения. Полные численные результаты — в summary.json.
