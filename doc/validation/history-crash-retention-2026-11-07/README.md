# Частичная история переживает аварийный перезапуск

Агрегаты: [summary.json](summary.json). Production-код в этом цикле не менялся.

## Усилена проверка

Прежний crash-сценарий проверял только ненулевое количество и уникальность
строк после запуска. Этого недостаточно: равные количества могут скрыть
потерю одного ID и появление другого; последующая сеть могла восстановить
утраченную durable-часть и сделать итоговый тест зелёным.

Контроллер теперь сохраняет expectation для уже наблюдавшихся записей в
одноразовом fixture directory. Inspector открывает тот же реальный контейнер
**до создания узла/transport/providers**, сравнивает точные ID, содержимое,
доставку и уже известные canonical positions, закрывает свой handle и только
затем разрешает обычный запуск. Он не добавляет и не восстанавливает сообщения
из expectation. Новые in-flight записи разрешены только из полного множества
исходной истории; повторы, подмена ID, статусная регрессия и пустое сравнение
отклоняются. Ещё provisional позиция вправе улучшиться; уже canonical —
не вправе откатиться.

Тело сравнивается по локальному content witness. ID/author/content tags
находятся только в памяти и private control-файле одноразового стенда.
Boot-probe и публичный отчёт содержат фиксированные счётчики; сами ID,
тексты, content hashes и ключи туда не попадают. Control-файл удаляется
вместе с runtime root. Это test-only механизм, не код diagnostic export.

Новый независимый oracle проверен на равных/неравных наборах, замене ID
при прежнем count, повторах, чужих ID, пустых snapshots, потере доставки,
изменении тела, откате canonical pair, допустимом provisional upgrade и
malformed witness. **10 новых + 24 прежних oracle tests passed, skips нет.**
Mutation без проверки missing set делает соответствующий тест assertion-red;
oracle восстановлен побайтно. Analyzer/format/diff checks чисты.

## Реальный сценарий A/B/C

Mac/JIT: A и B — одна личность, C — другая; три loopback Core, реальные
transport/ratchet/HVS, provider fixture без полного foreground SessionPipeline.
Исходная история A ↔ C — 2000 отправленных и delivered сообщений.

1. Во время догрузки на B получили snapshot с **815** сообщениями.
2. B завершён настоящим `SIGKILL`, exit **−9**; A и C остановлены.
3. До сети нового B inspector обнаружил **815/815 исходных ID**, те же
   тела и delivery status, **765/765** уже canonical positions. Пропусков,
   замен и дублей нет. Остальные позиции ещё не были canonical до аварии.
4. При обоих offline источниках B держит те же 815 строк и всё ещё нуждается
   в остальной истории. Затем возвращается **только A**, C остаётся выключенным.
5. B автоматически получает все **2000** ID, тела, итоговый порядок,
   canonical positions и delivered; retries завершённой истории — 0.
6. A снова выключен, C по-прежнему выключен. B ещё раз перезапущен. До
   его сетевого старта проверены **2000/2000 ID, тел, delivered и canonical
   positions**; обычное чтение после запуска подтверждает тот же результат.

Expectation записан до kill из одного live-owner snapshot, а boot-check
читает disk state до reconnect. Проверка не зависит от совпадения двух
одинаково неполных устройств. Параметр crash threshold был 500; из-за 5-с
опроса фактическая точка — 815, строго между нулём и полной историей.

## Новый точно измеренный остаток задержки

Сохранность и сходимость прошли, однако скорость после аварии остаётся
открытой: полная история сошлась за **121,539 с** от начала миграции.
`start(A)` завершился на 34,524 с — до итоговой сходимости ещё **87,015 с**.
Это не чистое время сети/обработки и не свидетельство готового маршрута A ↔ B:
сценарий включает kill, остановки, cold boots, discovery и восстановление.

Private wire probe сопоставил запрос на A и ответные части на B после
перезапуска A. Из 62 request ID один с повторными запросами исключён;
61 ответ наблюдался целиком и без повторных частей: 60 page и один list.
Медиана `query ingress на A → последняя part на B` — **447,6 мс**.
Медиана `последняя part на B → следующий query ingress на A` — **591,1 мс**.
Все клиенты на одном Mac; использована одна clock domain. Эти интервалы
включают приложение, очереди и transport, не приписываются одному слою.

Дополнительный сигнал: source A выполнил **4303**, receiver B — **5950**
обращений к `myOtherDevices` в сохранённых census-окнах после restart.
Их суммарные await пересекаются и не являются wall time. Следующий разбор —
стоимость повторного получения roster/authorization во время history pages;
свежие revoke/identity/binding проверки должны остаться обязательными.
Причина секундного темпа страниц этим наблюдением ещё не доказана.

## Границы и очистка

Это квалификация части сценариев interruption/reconnect/crash consistency,
а не полная multi-device матрица. Не проверены все точные crash-стадии
decrypt/write/ACK/ratchet, аппаратная потеря питания, часы/сутки offline,
concurrent revoke/split-brain, media и мобильный handover. Новая доставка
при одновременно недоступных источниках не заявляется; sibling mailbox
не добавлялся по принятой модели.

SDK `b9b88bb7`, HVS `eceb9158` и production app `ba1ff89a` прежние.
SHA immutable FFI/CLI/HVS проверены до/после, 1506 source/package inputs
неизменны в прогоне. После crash/offline marker OS mappings подтвердили
выбранные библиотеки у двух живых клиентов A/B. CPU/VM profiling отключён:
нет попытки склеить незавершённую трассу убитого процесса.

Проверены 27 PID / 26 портов: своих процессов/listeners нет, runtime root
и expectation удалены. Все устройства были синтетическими; пользовательские
контейнеры, телефон и production не менялись. Сырые журналы и request ID
остаются в private cache; публичные агрегаты не содержат их. Push/релиза нет.
