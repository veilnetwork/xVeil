# Межпроцессные multi-device проверки — 2026-11-01

Проверены отдельные пункты матрицы на одном Mac: настоящие embedded-узлы,
зашифрованные контейнеры, штатные providers и messaging/device-sync, отдельный
OS-процесс для каждого устройства. Для запуска нужен только локальный остров
из трёх реле; публичные сиды и discovery отключены. Прямые соединения внутри
острова разрешены: результат не означает, что каждый пакет шёл через реле/onion.

Текущий Dart — `0526e40a`; далее изменён только crash-тест. SDK/CLI сверены
по SHA с сохранённым release-stand proof для Veil `f7a4fb97`. Между этой сборкой
и текущим `06eeddf5` менялись документация и simulation tests, production runtime
одинаков. Использована прежняя native HV-библиотека с сохранённым SHA.
Пересборки Rust и изменений production-реле не было.

## Разделение сети: сценарии 31/32, частично 12/17–20

Личность X — A/B, личность Y — C/D. При связывании устройств штатно
перезапускаются B/D; после подготовки тест запоминает PIDs и больше не
перезапускает процессы или native-кэши во время разделения/восстановления.

Сеть разделена на A+C и B+D. Административные bans закрыли все соединения между
половинами, включая прямые пути и связи реле. Проверен фактический список сессий
всех семи узлов. Обе половины оставались работоспособны: каждое устройство
отправило четыре сообщения, всего 16. Чужие для своей половины сообщения до
восстановления не появились.

Параллельно A редактировал исходное сообщение, B удалял его **локально для
личности X**, A/B меняли/удаляли реакцию, D добавлял реакцию личности Y.
Каждое устройство отмечало прочтение своей видимой переписки. Затем bans сняты
и восстановлена только сеть; журнал, контейнеры и очереди не подменялись.

Результат: **PASS**. Во всех четырёх историях каждый из 16 текстов присутствует
ровно один раз, порядок каждого автора сохранён. Внутри A/B и C/D совпали
ID/порядок/направления/правки; сошлись реакции и позиции прочтения. У X сообщение
удалено локально, у Y сохранилась его правка — это ожидаемая семантика, не
проверка конфликта с «удалить у всех».

- Первое полное наблюдение сходимости: **20 084 мс** от начала восстановления,
  включая снятие bans и повторные соединения.
- Согласованное состояние наблюдалось ещё **10 400 мс**; полный recovery —
  **30 485 мс**. Это один прогон, не медиана и не измерение публичной сети.
- Общее время с подготовкой/teardown: **131,505 с**, 1 native test passed.

## Завершение процесса после отправки: сценарий 13

Начальный тест завершился неуспешно: A убит через **114 мс** от начала отправки,
B offline, C не получил сообщение за три минуты. При этом тест не возвращал A,
пока C не получит сообщение, то есть блокировал сам путь восстановления.

Проверка отдельной копии выключенного A через настоящий HV-worker нашла
ровно одно исходящее сообщение со статусом `sent`. В reader не запускались
сеть или MessagingService и не добавлялись строки. Это сохранённая локальная
отправка, не подтверждённая удалённая доставка. Успех API/send admission не
обещает доставку C при выключенном единственном источнике; `delivered`
подтверждается отдельно. Причиной потери этот timeout не объявляется.

Исправлен **тест**, production-путь не менялся: сначала вернуть A, затем
дождаться C, вернуть B и проверить восстановление его исходящей копии.
Дополнительно итоговые ID теперь сравниваются с C, а не только A/B.

Повторный прогон: **PASS**. A убит через **96 мс** от начала отправки. Сразу
после убийства C ещё не показывал сообщение; A вернулся, исходное сообщение
дошло C/B. Новые сообщения A→C и C→A тоже дошли. После второго запуска B
все три проверяемых сообщения присутствуют ровно один раз и с одинаковыми ID
на A/B/C. Общее время — **92,587 с**, 1 native test passed. Анализ обоих
межпроцессных тестов чист.

Это cut **после возврата send API**, а не пять отдельных cut внутри приёма,
расшифровки, записи, fsync и ACK. Подтверждена пригодность дальнейшего
зашифрованного обмена, а не формальное отсутствие любого ratchet/nonce дефекта.

## Что остаётся и очистка

Эти два прогона не закрывают всю матрицу: большой backlog/длительный offline,
остальные crash/revoke этапы, файлы, TTL/clock skew и реальные разные ОС/устройства
проверяются отдельно. Задержка догрузки 100 сообщений за 106 с не переизмерена
и остаётся активной.

Фактический Poco доступен в ADB; основная 0.13.94 открывается, но контейнер
заблокирован паролем. У Android user 0 разрешения камеры/микрофона выданы;
разрешения другого профиля не принимались за его состояние. Это не измерение
работающего захвата. Обычный процесс xVeil на Windows в момент read-only probe
не был запущен, поэтому его mixer state неизвестен. Новые звонки не выполнялись,
пароль не подбирался, контакты/данные не менялись. Poco→Windows и NETCALL-01
остаются активными; запрос ручной разблокировки оставлен владельцу.

После обоих прогонов, включая неуспешный baseline, проверены выход собственных
процессов/групп, отсутствие слушателей и удаление runtime-каталогов. Временная
forensic-копия контейнера удалена после чтения. Windows-задача read-only observer
удалена. Исходный пользовательский процесс телефона не завершался принудительно.
Публичные результаты — [summary.json](summary.json); приватные журналы, адреса,
ID и ключи сюда не скопированы. Без push/релиза.
