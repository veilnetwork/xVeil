# Отказ камеры и отмена отложенного включения

Подтверждены два дефекта управления камерой:

1. Desktop camera start возвращал false или бросал исключение, но `Call.cameraOn`
   оставался true. Это состояние используют кнопки интерфейса и сообщение о
   локальном захвате для собеседника. Звук мог работать при фактически отсутствующей
   камере. Воспроизведение использует настоящие CallService и VeilCallMediaController
   с управляемым результатом engine API: начальный запуск и повторное включение,
   false и exception — **четыре red на прежнем коде**.
2. Во время ожидания `setVideoEnabled(true)` в аудиозвонке нажатие OFF считалось
   пустой операцией. После завершения ожидания старая ON-попытка запускала захват
   вопреки более позднему выбору. Отдельный red держит Future закрытым до OFF;
   никаких порогов времени в критерии нет.

## Изменение

Явный desktop-отказ теперь поступает в FSM с call ID и текущим результатом
попытки. Camera intent и состояние интерфейса выключаются, capture=false
отправляется собеседнику штатным health-сигналом. Приём и звук сохраняются, если
их нативные потоки запущены. При отказе самого video pipeline звонок может
продолжиться со звуком; наличие работающего video receive при таком отказе
не заявляется.

Результат применим только к текущей попытке и звонку. Успешное восстановление
прежней камеры при неудачном выборе новой нейтрализует уже поставленное событие
отказа. Поздняя ошибка старой попытки не выключает успешный повтор. OFF отменяет
отложенный переход к видео ещё до публикации нового media set. Когда video receive
уже успешно создан, его media set объявляется даже при отказе camera capture:
следующий успешный повтор камеры не должен остаться неизвестным аудио-пиру.

Первый кандидат оставлял camera intent включённым после отказа video mount.
Дополнительная проверка поймала это до коммита; intent теперь публикуется только
после успешного актуального mount. Этот промежуточный случай не объявлен дефектом
предыдущего выпущенного приложения.

## Проверки

- **405 PASS / 0 skipped** с выключенной диагностикой: полный CallService,
  media-start и наборы camera/screen/microphone lifecycle, Android ownership,
  permission и route-operation/qualification.
- **425 PASS / 0 skipped** с `XVEIL_DIAGNOSTICS=true`: тот же набор плюс журнал.
  Проверено наличие cameraStart с success=0 и правильным origin; в JSON нет
  camera ID, текста driver exception, call ID и адреса тестового собеседника.
- Отдельный Python-тест верификатора diagnostic artifact проходит.
- Targeted analyze: 0 issues; `git diff --check` проходит.

Критерии включают состояние активного звонка, capture=false у отправленного
сигнала, отсутствие позднего camera start после OFF, успешный выбор предыдущей
камеры, отказ обеих камер, отказ после замены движка, старое событие другого
звонка и успешный повтор после старой ошибки. Начальные ошибки транспортного
test double исправлены отдельно и не засчитаны как red продукта.

Это unit-квалификация Dart control path с подставленным engine API, без новой
физической сборки/GUI-проверки. Hardware start, пропажа кадров после успешного
start и причины жалобы исходного Windows 10 этим не доказаны. Android permission
denial и native Camera2 failure не получили нового producer события в этой
правке; прежние Android ownership-проверки сохранены.

Формат сигналов, маршруты и privacy-политика не менялись. Новые строки/идентификаторы
в анонимный отчёт не добавлялись. Тестовые процессы завершены, cache удалён;
пользовательские приложения и серверы не менялись. Исправления локальные,
без push/релиза.

Позднее текущий Windows frontend физически проверен в трёх relay-звонках с
настоящей камерой и OFF/ON. Обнаружена и устранена отдельная проблема ACL
публичного export. Это не меняет исторические unit-счётчики выше и не закрывает
исходный Win10. [Продолжение и границы](../windows-camera-runtime-2026-11-12/README.md).
